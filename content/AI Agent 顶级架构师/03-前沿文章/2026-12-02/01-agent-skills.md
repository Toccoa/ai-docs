## 为什么今天读这篇

因为它是"程序性记忆该放在哪儿"这个问题目前最省事的一份工程答案：不写进权重、不往系统提示里塞，而是做成一个带 YAML 头的目录，按需加载。它给出的三级渐进式披露（元数据 → SKILL.md 正文 → 被引用的附加文件）实际上是一条上下文预算的分层策略，直接对应你在做技能库时"启动时到底该让模型看见多少"的取舍。更关键的是它把"技能"和"代码执行"绑在一起论证：排序这类操作交给脚本跑，比让模型逐 token 生成便宜几个数量级——这是把 A4-03 的沙箱能力当成技能载体的前提。最后，文中关于恶意技能的安全段落说明技能目录本身就是一个供应链信任边界，这在做技能市场或团队共享技能库时是必须提前设计的。

## 三句话摘要

1. 一项技能就是一个包含 `SKILL.md` 的目录，该文件必须以 YAML frontmatter 开头，至少含 `name` 与 `description` 两个必填字段；智能体在启动时会把所有已安装技能的这两个字段预加载进系统提示。
2. 这套设计叫渐进式披露，分三级：元数据（第一级，常驻系统提示）、`SKILL.md` 正文（第二级，判断相关才读入）、被引用的附加文件（第三级及以后，按需导航）。因为有文件系统和代码执行工具，技能能打包的上下文量实际上是无限的。
3. 技能的开发应当从评测出发——先在代表性任务上跑出能力缺口，再增量地补技能；同时因为技能可以携带任意指令与代码，只能从可信来源安装，来自弱可信来源的技能必须逐文件审计。

随着模型能力提升，我们现在可以构建与完整计算环境交互的通用智能体。例如 [Claude Code](https://claude.com/product/claude-code) 可以借助本地代码执行与文件系统，跨领域完成复杂任务。但随着这些智能体变得更强，我们需要更可组合、更可扩展、更可移植的方式，来为它们配备领域专精能力。

这促成了 [**Agent Skills**](https://www.anthropic.com/news/skills) 的诞生：它是“有组织的指令、脚本与资源文件夹”，智能体可以发现并动态加载它们，从而在特定任务上表现更好。技能把你的专长打包成 Claude 可组合的资源，以此扩展 Claude 的能力，把通用智能体变成符合你需求的专用智能体。

为智能体构建一项技能，就像给新员工准备一份入职指南。你不必为每个用例单独造一个碎片化的定制智能体；现在任何人都可以把自己的程序性知识沉淀并分享出来，用可组合的能力让智能体变得专门化。本文解释技能是什么、它们如何工作，并分享构建你自己技能的最佳实践。

*一项技能就是一个包含 `SKILL.md` 文件的目录，这个目录里组织着指令、脚本与资源，为智能体提供额外能力。*

## 一项技能由什么构成

为了看清技能在实战中如何运作，我们走一个真实例子：支撑 [Claude 近期上线的文档编辑能力](https://www.anthropic.com/news/create-files)的技能之一。Claude 本已很懂如何理解 PDF，但在直接操作它们（例如填写表单）方面能力有限。这个 [PDF 技能](https://github.com/anthropics/skills/tree/main/document-skills/pdf)让我们能把这类新能力交给 Claude。

最简单地说，一项技能就是一个包含 `SKILL.md` 文件的目录。该文件必须以 YAML frontmatter 开头，其中包含一些必填元数据：`name` 与 `description`。启动时，智能体会把每个已安装技能的 `name` 与 `description` 预加载进它的系统提示。

这份元数据是*渐进式披露*的**第一级**：它只提供刚好够用的信息，让 Claude 知道每项技能何时该被使用，而不必把整份技能都载入上下文。文件的实际正文是**第二级**细节。如果 Claude 认为该技能与当前任务相关，它就会把完整的 `SKILL.md` 读入上下文，以此加载技能。

*`SKILL.md` 文件必须以 YAML Frontmatter 开头，其中包含一个文件名与描述，启动时被载入系统提示。*

当技能变得复杂时，它们可能包含太多上下文，塞不进单个 `SKILL.md`；也可能包含只在特定场景下才相关的上下文。遇到这种情况，技能可以在技能目录内打包额外文件，并在 `SKILL.md` 里按文件名引用它们。这些被链接的附加文件构成**第三级**（以及更深层级）细节，Claude 可以自行选择只在需要时去导航和发现。

在下文所示的 PDF 技能中，`SKILL.md` 引用了两个附加文件（`reference.md` 与 `forms.md`），这是技能作者选择与核心 `SKILL.md` 并置打包的。通过把填表指令挪到单独文件（`forms.md`），技能作者得以让技能核心保持精简，并信任 Claude 只在填表时才去读 `forms.md`。

*你可以通过附加文件把更多上下文纳入技能，然后由 Claude 根据系统提示来决定何时触发它们。*

渐进式披露是让 Agent Skills 既灵活又可扩展的核心设计原则。就像一本编排良好的手册：先目录，再具体章节，最后是详细附录——技能让 Claude 只在需要时加载信息：

*具备文件系统与代码执行工具的智能体，在处理某个特定任务时，不需要把整项技能读进上下文窗口。这意味着，一项技能能打包的上下文量实际上是无限的。*

### 技能与上下文窗口

下图展示了当一条用户消息触发某项技能时，上下文窗口如何变化。

*技能通过你的系统提示，在上下文窗口中被触发。*

图中展示的操作序列：

1. 初始时，上下文窗口里有核心系统提示、每个已安装技能的元数据，以及用户的初始消息；
2. Claude 通过调用 Bash 工具读取 `pdf/SKILL.md` 的内容，触发 PDF 技能；
3. Claude 选择读取该技能打包的 `forms.md` 文件；
4. 最后，由于已经加载了 PDF 技能中的相关指令，Claude 继续执行用户的任务。

### 技能与代码执行

技能也可以包含代码，让 Claude 自主决定把它们当作工具执行。

大语言模型擅长很多任务，但某些操作更适合交给传统代码执行。例如，用 token 生成来排序一个列表，比直接跑一个排序算法贵得多。除了效率考量，很多应用还需要只有代码才能提供的确定性可靠性。

在我们的例子里，PDF 技能包含一段预先写好的 Python 脚本，它读取 PDF 并抽取所有表单字段。Claude 可以运行这段脚本，而既不需要把脚本也不需要把 PDF 载入上下文。又因为代码是确定性的，这条工作流一致且可复现。

*技能也可以包含代码，让 Claude 依据任务性质自主决定把它们当作工具执行。*

## 开发与评估技能

以下是一些上手撰写与测试技能的实用准则：

- **从评测出发：** 让智能体在代表性任务上运行，观察它在哪儿卡住、在哪儿需要额外上下文，从而找出能力上的具体缺口。然后增量地构建技能来补这些短板。
- **为规模化而组织：** 当 `SKILL.md` 变得笨重时，把内容拆到独立文件并引用它们。如果某些上下文互斥或很少一起使用，把路径分开会减少 token 消耗。最后，代码既可以作为可执行工具，也可以作为文档；应当明确 Claude 是该直接运行脚本，还是该把它读入上下文作为参考。
- **从 Claude 的视角思考：** 在真实场景中观察 Claude 如何使用你的技能，并据此迭代：留意意料之外的轨迹，或对某些上下文的过度依赖。要特别关注技能的 `name` 与 `description`——Claude 正是用它们来判断是否应当为当前任务触发该技能。
- **与 Claude 一起迭代：** 当你和 Claude 一起做任务时，让它把成功的做法与常见的错误沉淀为技能里可复用的上下文与代码。如果它在使用某项技能完成任务时跑偏了，就让它自我反思哪里出了问题。这个过程会帮你发现 Claude 真正需要什么上下文，而不是试图事先去预判。

### 使用技能时的安全考量

技能通过指令与代码为 Claude 提供新能力。这既让它们强大，也意味着恶意技能可能在使用它们的环境里引入漏洞，或引导 Claude 外泄数据、执行意料之外的操作。

我们建议只从可信来源安装技能。从弱可信来源安装技能时，使用前要彻底审计：先读技能打包文件的内容，弄清它做了什么，尤其注意代码依赖，以及图像、脚本这类打包资源。同样地，要留神技能里那些让 Claude 连接到潜在不可信外部网络源的指令或代码。

## 技能的未来

Agent Skills [目前已经支持](https://www.anthropic.com/news/skills)[Claude.ai](http://claude.ai)、Claude Code、Claude Agent SDK 以及 Claude Developer Platform。

未来几周，我们会继续补齐特性，以支持技能的创建、编辑、发现、分享与使用的完整生命周期。我们尤其期待技能能帮助组织和个人把他们的上下文与工作流分享给 Claude。我们还会探索技能如何与[模型上下文协议](https://modelcontextprotocol.io/)（MCP）服务器互补——方法是教给智能体涉及外部工具与软件的更复杂工作流。

再往远处看，我们希望让智能体能够自己创建、编辑和评估技能，把它们自己的行为模式固化为可复用的能力。

技能是一个简单的概念，格式也相应地简单。这种简单性让组织、开发者与最终用户更容易构建定制化智能体，并赋予它们新能力。

我们很期待看到大家用技能做出什么。现在就可以从我们的技能[文档](https://docs.claude.com/en/docs/agents-and-tools/agent-skills/overview)与[示例集](https://github.com/anthropics/claude-cookbooks/tree/main/skills)开始。

## 与路线图的挂接

- **A3-01（记忆分层：工作 / 情景 / 语义 / 程序性）**：这是"程序性记忆"这一层少见的、可直接落地的形态。技能不是被检索进上下文的片段，而是被*加载*的能力包：元数据常驻（相当于一个极薄的索引层），正文按相关性载入（工作记忆），附加文件与脚本按需导航（外部存储 + 执行）。四层记忆里"写入频率"与"失效方式"各不相同的判断，在这里变成了三级披露的物理实现——技能更新只需改目录，不动权重。
- **A3-03（长期记忆的写入与遗忘）**：文中"与 Claude 一起迭代"那一条，本质是一套写入策略：把成功的做法与常见的错误沉淀为可复用的上下文与代码，而不是让每次会话从零开始。它同时暗示了粒度选择——技能该拆到多细，取决于"是否互斥、是否常一起用"；拆得过粗会浪费 token，拆得过细会让模型找不到入口。

## 三个自测问题

1. 如果你的技能库增长到 200 项，系统提示里塞 200 条 `name` + `description` 会发生什么？你会用什么方式（分层命名、检索式技能、还是按会话预筛）把启动开销压回可接受范围？
2. 渐进式披露的第三级依赖模型主动"导航"和发现文件。在什么情况下模型会漏读本该读的文件？你能设计一个什么信号来检测这种漏读？
3. 技能可以携带任意脚本与网络请求，这与"从可信来源安装"的建议之间是什么关系？如果必须接入一个第三方技能，你的审计清单上最关键的三项检查是什么？
