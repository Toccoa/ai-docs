## 为什么今天读这篇

这是目前少见的、把"执行架（harness）是易腐资产"这件事讲透的工程文。它的核心判断很硬：执行架编码的是"模型做不到什么"的假设，而模型一进步，这些假设就会过期——文中给出了具体证据（Sonnet 4.5 的"上下文焦虑"在 Opus 4.5 上消失，为它加的上下文重置变成了死重）。由此推出的架构结论是：不要在容器里养宠物，要把大脑（模型 + 执行架）、手（沙箱与工具）、会话（事件日志）三者解耦成互相假设极少的接口。文中还给出了几个可复用的量化收益与安全论证：p50 TTFT 降约 60%、p95 降超 90%；把凭据移出沙箱以结构性消除提示注入的杠杆。对任何正在自建长周期智能体运行时的人，这是一份可直接对照分层的参考设计。

## 三句话摘要

1. 执行架编码的是关于"模型不能做什么"的假设，而这些假设会随模型进步而过期，因此执行架必须被设计成可替换的。
2. 把会话、执行架、沙箱耦合进同一个容器，等于领养了一只宠物：容器坏了会话就丢了，且无法定位故障；解法是把"大脑"从"手"和"会话"中解耦，三者各自成为可独立失败、独立替换的接口。
3. 把凭据排除在沙箱可达范围之外，是应对提示注入的结构性修复，而不是靠收窄权限范围这种会随模型变强而失效的假设。

## 译文


### 不要领养宠物

*按照我们的[文档](https://platform.claude.com/docs/en/managed-agents/overview)开始使用 Claude Managed Agents。*

工程博客上有一条持续的话题：如何[构建有效的智能体](https://www.anthropic.com/engineering/building-effective-agents)、如何为[长周期工作](https://www.anthropic.com/engineering/harness-design-long-running-apps)设计[执行架](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。这些工作的一条共同线索是：执行架编码了关于"Claude 自己做不到什么"的假设。然而这些假设需要被频繁质疑，因为随着模型改进，它们会[过期](http://www.incompleteideas.net/IncIdeas/BitterLesson.html)。

仅举一例：在此前的工作中[我们发现](https://www.anthropic.com/engineering/harness-design-long-running-apps)，Claude Sonnet 4.5 会在感知到上下文上限临近时过早收尾任务——这种行为有时被称为"上下文焦虑"。我们通过在执行架中加入上下文重置来解决它。但当我们在 Claude Opus 4.5 上使用同一个执行架时，我们发现这个行为消失了。那些重置变成了死重。

我们预期执行架会持续演化。所以我们构建了 Managed Agents：Claude 平台中的一项托管服务，通过一小组接口代你运行长周期智能体——这些接口旨在比任何特定实现都更长寿，包括我们今天自己运行的那些实现。

构建 Managed Agents 意味着解决计算机科学里的一个老问题：如何为一个"[尚未被想到的程序](http://www.catb.org/esr/writings/taoup/html/ch03s01.html)"设计系统。几十年前，操作系统通过把硬件虚拟化成抽象——*进程、文件*——来解决这个问题，这些抽象足够通用，能容纳当时还不存在的程序。抽象比硬件活得更久。`read()` 命令不关心它访问的是 1970 年代的磁盘组还是现代 SSD。上层的抽象保持稳定，而下层的实现自由变化。

Managed Agents 遵循同样的模式。我们把智能体的各个组件虚拟化了：一个会话（session，记录所发生一切事情的仅追加日志）、一个执行架（harness，调用 Claude 并把 Claude 的工具调用路由到相应基础设施的循环）、以及一个沙箱（sandbox，Claude 可以在其中运行代码、编辑文件的执行环境）。这使得每一个组件的实现都可以被替换而不干扰其他组件。我们对这些接口的**形状**有明确主张，但对它们背后运行什么不作主张。

### 不要领养宠物

我们一开始把所有智能体组件放进同一个容器，这意味着会话、智能体执行架和沙箱共享同一个环境。这种做法有好处，包括文件编辑是直接的系统调用，而且没有需要设计的服务边界。

但把所有东西耦合进一个容器后，我们撞上了一个老的基础设施问题：我们领养了一只[*宠物*](https://cloudscaling.com/blog/cloud-computing/the-history-of-pets-vs-cattle/)。在"宠物 vs 牲畜"的类比里，宠物是一个有名字的、被亲手照料的个体，你承受不起失去它；而牲畜是可互换的。在我们的情形里，服务器就成了那只宠物；如果一个容器挂了，会话就丢了。如果一个容器失去响应，我们得把它护理回健康状态。

护理容器意味着要调试失去响应的卡死会话。我们唯一的观察窗口是 WebSocket 事件流，但它无法告诉我们故障**发生在哪里**——这意味着执行架里的一个 bug、事件流里的一次丢包、或者一个容器掉线，看起来全都一样。要弄清出了什么错，工程师必须进到容器里开一个 shell，但由于那个容器往往同时存着用户数据，这种做法实质上等于我们不具备调试能力。

第二个问题是，执行架假设"Claude 所操作的一切都住在它所在的容器里"。当客户要求我们把 Claude 连接到他们自己的虚拟私有云时，他们要么必须把自己的网络与我们的网络对等互联，要么必须在我们执行架跑在他们自己的环境里。一个被烘进执行架的假设，在我们想把它接到不同基础设施上时就成了问题。

### 把大脑与手解耦

我们最终得到的解决方案，是把我们心目中的"大脑"（Claude 及其执行架）与"手"（执行动作的沙箱与工具）以及"会话"（会话事件日志）解耦。每一者都成为一个对其他两者假设极少的接口，每一者都可以独立失败或被替换。

**执行架离开容器。** 把大脑与手解耦，意味着执行架不再住在容器里。它像调用任何其他工具那样调用容器：`execute(name, input) → string`。容器变成了牲畜。如果容器死了，执行架把该失败捕获为一次工具调用错误，并把它回传给 Claude。如果 Claude 决定重试，一个新容器可以用标准配方重新初始化：`provision({resources})`。我们不再需要把失败的容器护理回健康状态。

**从执行架故障中恢复。** 执行架也变成了牲畜。由于会话日志位于执行架之外，执行架里没有任何东西需要在崩溃后存活。当一个执行架失败时，一个新的执行架可以用 `wake(sessionId)` 重启，用 `getSession(id)` 取回事件日志，并从最后一个事件处继续。在智能体循环期间，执行架通过 `emitEvent(id, event)` 写入会话，以保持事件记录的持久性。

**安全边界。** 在耦合的设计里，Claude 生成的任何不可信代码都与凭据跑在同一个容器中——所以一次提示注入只需要说服 Claude 去读它自己的环境就够了。一旦攻击者拿到那些 token，他们就能开出新的、不受限制的会话，并把工作委派给它们。收窄权限范围是一种显而易见的缓解，但这编码了一个关于"Claude 用一个受限 token 做不到什么"的假设——而 Claude 正变得越来越聪明。结构性的修复，是确保 token 从 Claude 生成代码所运行的沙箱中永远不可达。

我们用两种模式来确保这一点。认证可以与资源捆绑，或存放在沙箱之外的保险库中。对于 Git，我们用每个仓库的访问 token 在沙箱初始化时克隆仓库，并把它接入本地 git remote。`push` 和 `pull` 在沙箱内部即可工作，而智能体从头到尾都不需要自己处理 token。对于自定义工具，我们支持 MCP，并把 OAuth token 存放在安全保险库中。Claude 通过一个专用代理调用 MCP 工具；这个代理接收一个与该会话关联的 token。代理随后可以从保险库中取出相应凭据，并向外部服务发起调用。执行架从头到尾都不会知道任何凭据。

### 会话不是 Claude 的上下文窗口

长周期任务常常超过 Claude 上下文窗口的长度，而应对这一点的标准做法都涉及关于"保留什么"的不可逆决策。我们在[此前关于上下文工程的工作](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)中探索过这些技术。举例来说，压缩（compaction）让 Claude 保存其上下文窗口的摘要，而记忆工具让 Claude 把上下文写入文件，从而支持跨会话学习。这可以与上下文裁剪配合，后者选择性地移除旧工具结果或思维块等 token。

但关于"选择性保留或丢弃上下文"的不可逆决策可能导致失败。很难知道未来的轮次会需要哪些 token。如果消息被压缩步骤转换过，执行架会把被压缩的消息从 Claude 的上下文窗口中移除，而这些消息只有在被存储的情况下才可恢复。此前的工作[已经探索过](https://arxiv.org/pdf/2512.24601)以"把上下文存成一个活在上下文窗口**之外**的对象"来应对这一问题。例如，上下文可以是 REPL 中的一个对象，LLM 通过编写代码来过滤或切片，从而以编程方式访问它。

在 Managed Agents 中，会话提供了同样的好处，充当一个活在 Claude 上下文窗口之外的上下文对象。但上下文不是存在沙箱或 REPL 内部，而是持久地存在会话日志中。接口 `getEvents()` 允许大脑通过选取事件流的位置切片来审问上下文。这个接口可以灵活使用，让大脑从它上次停止阅读的地方接着读、回退到某一时刻之前的几个事件以看清前因、或者在某个动作之前重读上下文。

任何取回的事件也可以在执行架中被变换，再传给 Claude 的上下文窗口。这些变换可以是执行架编码的任何东西，包括为达到高提示缓存命中率而做的上下文组织，以及上下文工程。我们把"会话中可恢复的上下文存储"与"执行架中任意的上下文管理"这两个关注点分开，因为我们无法预测未来的模型会需要什么样的具体上下文工程。接口把这种上下文管理推给执行架，只保证会话是持久的、可供审问的。

### 许多大脑，许多手

**许多大脑。** 把大脑与手解耦，解决了我们最早的客户抱怨之一。当团队希望 Claude 针对他们自己 VPC 中的资源工作时，唯一的路径是把他们的网络与我们的对等互联，因为承载执行架的容器假设每一个资源就坐在它旁边。一旦执行架不再在容器里，这个假设就消失了。同一个改动还带来了性能回报。当我们最初把大脑放进容器时，它意味着许多大脑需要同样多的容器。对每个大脑来说，在该容器被供给之前无法进行任何推理；每个会话都要预先支付完整的容器设置成本。每个会话——即便是永远不会碰沙箱的会话——都必须克隆仓库、启动进程、从我们的服务器拉取待处理事件。

那段死时间体现在首 token 时延（time-to-first-token，TTFT）上，它衡量一个会话从接受工作到产出第一个响应 token 之间等待多久。TTFT 是用户**感受**最强烈的时延。

把大脑与手解耦，意味着容器只在需要时由大脑通过一次工具调用 `(execute(name, input) → string)` 来供给。于是一个不需要立刻使用容器的会话就不必等待容器。一旦编排层从会话日志中拉出待处理事件，推理就可以开始。使用这种架构，我们的 p50 TTFT 下降了约 60%，p95 下降了超过 90%。扩展到许多大脑，只意味着启动许多无状态的执行架，并在需要时才把它们连接到手。

**许多手。** 我们还希望能把每个大脑连接到许多手。在实践中，这意味着 Claude 必须对许多执行环境进行推理，并决定把工作送到哪里——这比在单一 shell 中操作是更难的认知任务。我们最初把大脑放在一个容器里，是因为更早的模型做不到这件事。随着智能水平提升，单一容器反而成了限制：当那个容器失败时，我们就失去了大脑所伸向的每一只手的状态。

把大脑与手解耦，让每一只手成为一个工具，`execute(name, input) → string`：一个名字和输入进去，一个字符串出来。这个接口支持任何自定义工具、任何 MCP 服务器，以及我们自己的工具。执行架并不知道沙箱是一个容器、一部手机，还是一个 Pokémon 模拟器。而且由于没有任何一只手与任何大脑耦合，大脑之间可以互相传递手。

### 结论

我们面临的挑战是个老挑战：如何为一个"尚未被想到的程序"设计系统。操作系统之所以能延续数十年，是因为它把硬件虚拟化成足够通用的抽象，能容纳当时还不存在的程序。有了 Managed Agents，我们的目标是设计一个能容纳未来围绕 Claude 的执行架、沙箱或其他组件的系统。

Managed Agents 是同一精神下的一个元执行架（meta-harness），对 Claude 未来将需要的**特定**执行架不作主张。相反，它是一个拥有通用接口、能容纳许多不同执行架的系统。举例来说，Claude Code 是一个优秀的执行架，我们在各种任务中广泛使用它。我们也已经展示过，面向特定任务的智能体执行架在窄领域里表现出色。Managed Agents 可以容纳其中任何一个，并随着时间匹配 Claude 的智能水平。

元执行架设计意味着对 Claude 周围的接口有明确主张：我们预期 Claude 将需要操作状态（会话）和执行计算（沙箱）的能力。我们也预期 Claude 将需要扩展到许多大脑和许多手的能力。我们设计这些接口，使它们能在长时间跨度上可靠、安全地运行。但我们对 Claude 将需要多少个大脑或手、以及它们位于何处，不作任何假设。

## 与路线图的挂接

- **A0-03**（目标型智能体 / 长周期运行）：本文把 A0-03 中"长周期"这一维落到运行时层面：会话必须比执行架活得久，因此会话日志必须是执行架之外、仅追加、可位置切片读取的持久对象。这为"智能体如何跨越上下文窗口继续工作"提供了接口级的答案（`getEvents()`、`wake(sessionId)`、`emitEvent(id, event)`）。
- **A2-07**（执行架 / Harness 设计）：这是该知识点最直接的一手材料。三个要点：一是执行架中的假设会随模型进步而过期（Sonnet 4.5 的上下文重置在 Opus 4.5 上成为死重），所以执行架必须是易替换的；二是执行架应把"上下文存储（会话）"与"上下文管理（变换）"分开，因为无法预测未来模型需要什么上下文工程；三是执行架本身应无状态，崩溃后可从会话重放恢复。
- **A8-01**（智能体安全边界与凭据隔离）：本文给出了一个结构性论证——收窄 token 权限范围是一种"关于模型能力上限"的假设，会随模型变强而失效；真正的修复是让 token 从生成代码所运行的沙箱中不可达。落地手段是两条：Git 用克隆时注入的 remote 凭据，MCP 用会话级 token + 代理 + 保险库换取真实凭据，执行架永不接触凭据。

## 三个自测问题

1. 你当前的执行架里，哪些代码是在补偿某个特定模型的缺陷？如果明天换上一个更强的模型，你如何发现这些代码已经变成死重，而不是继续付它的成本？
2. 你的会话日志是否独立于执行架与沙箱存在？如果执行架崩溃，能否只靠会话日志恢复到"最后一个事件"，而不丢失已发生的工具调用结果？
3. 假设攻击者通过提示注入让模型执行任意代码。在你的架构里，凭据与这段代码之间隔了几层？如果只隔了"权限范围"，那么你在赌模型的什么能力不会变强？
