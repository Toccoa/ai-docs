## 为什么今天读这篇

因为它把"执行架与模型的匹配度"从经验之谈变成了可测的工程量：同一个 Qwen3.8-27B，配 pi 执行架时 Terminal-Bench 2.1 只有 39%，冻结权重加一个在该执行架内训出来的 LoRA 适配器就到 55% pass@1，而每任务平均 token 从 2.9K 降到 1.5K——**更准且更省**同时发生。这篇真正的价值不是"再训一个 LoRA"，而是它给出了在真执行架里训练的完整配方：为什么不重写 agent 循环而是用代理记录 harness 与 vLLM 之间的真实 token、为什么要先做"有效性校验"再做"难度校验"这两道过滤（1,127 个任务只剩 278 个可用）、以及 GRPO 为什么必须要求"模型有时能做对"。对做框架选型的团队，它还顺手回答了一个常见疑问：换执行架会不会把训练成果丢掉——pi 的适配器在 OpenCode 上仍保住了专科适配器的大部分增益。

## 三句话摘要

1. 为每个执行架各训一个 LoRA（pi、Hermes Agent、OpenCode），在各自执行架、两个基准上都同时打赢底座模型的表现与效率；三个适配器权重更新的余弦相似度只有 0.01–0.02（近乎正交），因此可以按秩拼接成 rank 96 的"超级适配器"，以 ½ 权重合并后在三个执行架下都不输底座（六对里五胜一平，thinking 模式下平均 55.5% → 63.5%，p=0.004）。
2. 训练侧的关键设计是不重写 agent 循环：执行架按原样运行，训练器学习它真实产出的 token（由 harness 与 vLLM 之间的代理记录）；数据侧的关键设计是双重过滤——`openenv validate` 的语义校验（1,127 个候选中 858 个通过）与基于底座模型的难度校验（442 个已打分任务中 151 个每次都解出、120 个从未解出，只剩 171 个"有时解出"的合格任务）。
3. 结果带明确代价：专科适配器在 SWE-bench Pro（hard 51）上把 pi 从 39.2% 提到 64.7%（+25.5 点，新解 15 个 vs 丢 2 个，p=0.002），同时在其与底座都能解出的任务上少 53–72% 的工具调用；而在分布外的 AutomationBench 上，适配器与底座基本持平（pi 27.0%、OpenCode 25.3%、合并版 23.7%、Hermes 17.7%，底座 23.0%），差异在噪声内。

## 译文

在自定义任务分布上做 RL，并与你惯用的智能体执行架结合，能为该目标执行架与任务分布产出更准确、更高效的模型。

模型并没有针对所有执行架和你正在做的任务做完整优化。它们瞄准的是通用表现。所以当你把一个模型和一个执行架组合起来时，你实际上在为"你真正在做的事"白白浪费表现与效率。借助 RL，你可以训练一个自定义的执行架适配器，为你的"执行架 + 任务"组合把模型的潜力全部榨出来。

以 Qwen3.8-27B 为例，它在 pi 执行架上的 Terminal-Bench 2.1 得分是 39%，平均每个任务消耗 2.9K token。如果我们冻结这些权重，加一个用 RL 训练的自定义 LoRA 适配器，就能得到 55% 的 pass@1，平均 token 用量 1.5K。这其中的大部分来自模型推理更少、调用工具更少，并且一次就把事情做对。

我们早前的工作（[multi-harness RL](https://huggingface.co/spaces/FineEnvs/multi-harness-rl)、[执行架适配器](https://huggingface.co/blog/harness-hub/harness-adapters)）表明，在你自己任务分布上、在你自己的执行架内部做 RL，能给出更准确也更高效的模型。那些实验覆盖了数据分析与代码构建类任务。这里我们想把这件事往前推：看看结论在 27B 规模、在更难的现实软件工程任务上、跨三个执行架（Pi、OpenCode 与 Hermes Agent）是否仍然成立。最重要的是，分享一份完全可复用的配方，让你能在自己的"任务、执行架、模型"组合上复现。

### TL;DR

- 我们为 Qwen3.8-27B 按执行架各训了一个 LoRA 适配器（pi、Hermes Agent、OpenCode），RL 就在执行架内部进行。

### 在智能体执行架内部训练

我们利用 [OpenEnv 中的 Harbor 集成](https://openenv.github.io/OpenEnv/main/environments/harbor)与 [TRL 的 OpenEnv](https://huggingface.co/docs/trl/openenv) 指南，在我们为最终训练选定的执行架内部训练模型。我们为全部 RL 任务构建了开箱即用的 Docker 镜像，其中已预装目标执行架。在最终镜像里，我们使用 Pi `1.5.2`、OpenCode `2.2.7` 与 Hermes Agent `v0.22.6`。前面提到的博客中的下图很好地解释了整个协议。

〔图〕执行架与 vLLM 之间通过代理记录真实 token 的协议示意图。

多数 RL 框架训练的是 agent 循环的**重新实现**：agent 是针对框架自己的接口写的，例如 [verl 的 AgentLoop](https://verl.readthedocs.io/en/latest/advance/agent_loop.html)、[SkyRL-Gym](https://github.com/NovaSky-AI/SkyRL) 环境、[rLLM](https://github.com/rllm-org/rllm) 的 agent 与环境类、[slime](https://github.com/THUDM/slime) 的自定义 rollout 函数，或 [ART](https://github.com/OpenPipe/ART) 在你自己的 Python agent 里的客户端。而在我们这里，执行架完全按它发布时的样子运行，训练器从它真实产出的 token 中学习——这些 token 由执行架与 vLLM 之间的一个代理记录。近期工作也朝同一方向推进：[Agent Lightning v1.0](https://huggingface.co/papers/2608.17528) 通过代理把部署时的执行架保留在循环中（"harnessed agentic RL"），[SkyRL 的 Harbor 集成](https://novasky-ai.notion.site/skyrl-harbor)则在 Harbor trial 上训练，把其聊天历史转换成训练器可用的 token。

### 在 Hugging Face 上生成自定义 RL 任务

为这份配方，我们用 Hub、OpenEnv 与 [Repo2RLEnv](https://github.com/huggingface/Repo2RLEnv) 创建了一个面向智能体编码的自定义数据集。我们把以下几件事组合进同一条数据流水线：从既有 RL 环境检索任务、用 Repo2RLEnv 生成任务、用 OpenEnv 校验任务，以及采样。这给了我们一组质量最高、经过校验且相关的任务，用来提升 Qwen3.8-27B 在智能体编码上的表现。本节带你看我们怎么构建它，以便你在自己的领域上试用。

RL 训练需要智能体可以尝试的任务、给每次尝试打分的校验器，以及"校验器是正确的"这一证据。一个会接受错误答案的校验器教出的是错误行为。一个本来就已经可解的任务则教不会模型任何东西。

本节描述我们如何从三个来源构建任务集：两个来自 Hugging Face Hub，第三个用 Tasksmith（Repo2RLEnv 中的一条流水线）生成。每个任务都要通过 `openenv validate` 的资格筛查，并通过针对底座模型 Qwen3.8-27B 的同一套难度检查。

#### 三个来源

每个任务使用 Harbor 格式，Terminal-Bench 2.1 也用该格式。对 Hub 上 Harbor 环境的广泛搜索返回了约 59,000 个任务，但其中包含重复项、评测集，以及被标记为不可用于训练的任务。我们过滤后只剩两个为训练而构建的 Hub 来源，并自己生成了第三组：

- SWE-smith（[Python](https://huggingface.co/datasets/SWE-bench/SWE-smith-py)、[Go](https://huggingface.co/datasets/SWE-bench/SWE-smith-go)）向真实的 Python 与 Go 仓库注入 bug，方式可以是 LLM 改写，也可以是诸如翻转运算符之类的变异。抓到每个 bug 的测试成为该任务的测试。它提供**体量**。
- SWE-Gym，以 Harbor 任务形式打包在 [TaskTrove](https://huggingface.co/datasets/open-thoughts/TaskTrove) 中，把真实 GitHub issue 及其已合并修复转成任务。它提供**真实世界的 bug**。
- [Tasksmith](https://huggingface.github.io/Repo2RLEnv/pipelines/tasksmith/) 从已合并的拉取请求生成任务。一个 LLM agent 写出指令与测试，Tasksmith 再检查结果：参考答案与一个有效替代方案必须通过，而未修复的代码与一个已知错误的解法必须失败。

我们用 Tasksmith 补齐缺口。我们先梳理目标基准（Terminal-Bench 2.1、SWE-bench Pro 的 hard 子集、DeepSWE）所考察的技能，然后挑选会用到这些技能的拉取请求，例如 HTTP 流式传输、文件系统操作与序列化。从 30 个已合并的拉取请求中，Tasksmith 在 10 个 Python 仓库里产出了 24 个通过其检查的任务，其中 17 个是在第二次运行时产出的。它的检查不能替代我们的检查，因此这些任务与其余任务走同一条流水线。

#### 用 `openenv validate` 做校验

先跑元数据筛查。它保留来自训练切分、且许可宽松的任务；剔除重复项、被标记为不可用于训练的任务、我们目标基准中的 253 个任务，以及任何来自这些基准所用仓库的任务。然后我们在全新 trial 中对每个任务运行 `openenv validate` 的语义检查：

- 参考解法拿到最高奖励（`semantic.oracle_max`）。
- 什么都不做明显得分更低（`semantic.floor_gap`）。
- 没有哪个 canary 的得分高于"什么都不做"（`semantic.canary_floor`）。
- 重放参考解法得到相同奖励（`runtime.episode_determinism`）。

每个 trial 作为独立的 Hugging Face Job 运行，这让我们能一次校验几十个任务。`openenv validate` 对任何 Harbor 任务都提供同样的选项：

```
openenv validate path/to/task --sandbox hf-sandbox
```

1,127 个 Hub 候选中 858 个通过。错答对照捕获了缺陷，包括一个 Tasksmith 任务接受了不完整的实现，以及一个 Terminal-Bench 2.1 校验器（regex-log）接受了已知错误的答案。多数失败是基础设施问题，例如镜像没能启动。失败的任务留在 rejected 切分中，并记录失败的那项检查。

#### 用底座模型做难度检查

一个有效任务仍然可能教不会任何东西。GRPO（组相对策略优化）是把每次尝试与同一任务的其他尝试比较打分，所以一个"每次都通过"或"每次都失败"的任务提供不了学习信号。训练之前，Qwen3.8-27B 对每个任务尝试 4 次，对每个仓库分层抽取的六个任务尝试 8 次。

在 442 个已打分任务中，Qwen3.8-27B 有 151 个每次都解出、120 个从未解出。它只偶尔解出的那 171 个任务构成合格集。下图展示分数如何在两端堆积，以及不同来源之间的差异。模型每次都解出多数 Go 任务，在超过三分之一的 SWE-smith Python 任务上每次都失败，而在 73% 的 SWE-Gym 任务上落在中间。

〔图〕Qwen3.8-27B 在 442 个已打分任务上的结果。绿色标记合格任务，即模型在某些尝试上解出、并非全部解出。

这个例子展示了我们如何把 1,127 个任务过滤并校验到 278 个，直接纳入最终数据集。流水线随后把其余 522 个被拒任务交给 Tasksmith 做修复与复杂化，并重复校验。

### 用短训练运行检验过滤器

流水线施加两个过滤器：校验剔除坏任务，难度检查保留底座模型只偶尔解出的任务。本节检验这两个过滤器是否改变了模型所学到的东西。我们训了四次短运行，每次至多 50 步，各用来自流水线不同阶段的任务，并在 Terminal-Bench 2.1 上与底座模型比较。

每次运行都用 LoRA 与 GRPO、使用 TRL 的 `AsyncGRPOTrainer`、在 32 个任务上训练 Qwen3.8-27B。四次运行使用同一执行架（OpenCode，最多 48 次模型调用）、同样的设置，以及一个 8×H200 的 Hugging Face Job，奖励是校验器的通过或失败。任务集的区别在于它们如何被过滤：

- **未校验**：24 个通过的任务加 8 个未通过校验的任务。
- **已校验**：32 个通过的任务，不考虑难度选取。
- **不合格**：32 个通过、但底座模型总是解出或从未解出的任务。
- **合格**：32 个通过、底座模型在某些尝试上能解出的任务。

### 用 `AsyncGRPOTrainer` 做更高效的 GRPO 训练

我们使用了 TRL 中 `AsyncGRPOTrainer` 的稳定版本，其主要优势是训练器不必等所有 rollout 完成才进入下一个训练优化步。

关于该训练器及其构建模块的更详细阅读，请参考 [AsyncGRPO 博客](https://huggingface.co/spaces/trl-lib/async-grpo-stable)。

### 训练设置

为得到最终的执行架适配器，我们用 TRL 的 `AsyncGRPOTrainer`，在 [Qwen/Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B) 之上训练 LoRA 适配器。适配器通过 `all-linear` 标志挂到模型上。为最大化训练效率，rollout 阶段关闭了思考模式，而我们最终适配器在有思考与无思考两种设置下都做了评测以便更广泛地比较。

最终奖励函数由校验器的正确性，加上一个小的工具效率加成（0.1，取自[上一代执行架适配器的早期实验](https://huggingface.co/blog/harness-hub/harness-adapters)，那些实验显示 0.1 效果最好）构成。

我们在 Termgrade 环境上用 50 步做了小规模学习率扫描（1e-5、5e-5 与 1e-4），注意到 1e-5 几乎没推动训练正确性（从 0.52 到 0.50），1e-4 使 rollout 崩溃而非改善（每 rollout 的轮数从 18 变成 6，同时熵上升），只有 5e-5 明显改善（到第 40 步从 0.49 到 0.60）。更长的 5e-5 运行随后表现出不稳定迹象（rollout 长度崩塌、熵上升），所以我们最终运行定在 2e-5。

#### 训练基础设施

每个执行架适配器使用 NVIDIA 2×B200 GPU 训练，一块 GPU 分配给 vLLM 服务器，另一块分配给训练进程。我们先做了一些压力测试，以最大化在单个优化步内能训练到的 RL 任务数量。为此，我们把 `AsyncGRPOTrainer` 的 `--token-budget` 参数在我们这套设置下"顶"到极限。下图展示每个执行架每步组数的演化（蓝色：Pi，绿色：OpenCode，橙色：Hermes）。

〔图〕每个执行架每步组数随训练步数的变化。

随着模型在训练中越来越好，它每个训练步能容纳越来越多的组，这使模型在每次优化步得到的信号更加多样。

训练之前，任务被放入一个固定顺序，按"家族"（对我们生成的 RL 环境来说即其仓库；对 Termgrade，我们只按名称排序，因为每个任务都算自己的家族）交错排列，使得每个训练步在遵循混合分布的前提下尽量混合更多仓库。

#### 循环中的 safeagents

我们还接入 [safeagents](https://github.com/huggingface/safeagents) 工具，以在训练期间阻断模型的任何不当行为。最终插件（由针对 RL 任务与测试路径的正则与模式规则构成）托管在 [harness-hub/qwen-safeagents-plugin](https://huggingface.co/harness-hub/qwen-safeagents-plugin)，任何人想复现该训练设置，都可以用最新版 safeagents 开箱使用。

### 超级适配器：把所有适配器合并为一个

合并模型常常能组合它们的能力，同时保留各自原本能做的大部分事情。三个执行架适配器训练完成后，我们问了两个问题：合并会损失准确率吗？单一的"超级适配器"能否在每个执行架下都既准确又高效？

我们先逐层比较三个适配器的权重更新。任意两者之间的余弦相似度约为 0.01–0.02：每个适配器在训练中把模型推向了近乎正交的方向。这是合并的最佳情形，因为更新之间几乎不相互干扰。

我们把三个 LoRA 适配器沿秩维度拼接（PEFT 的 `combination_type="cat"`）。合并后的适配器秩为 96（3 × 32），精确地施加 w · (ΔW_pi + ΔW_hermes + ΔW_opencode)。此前的合并工作（[task arithmetic](https://huggingface.co/papers/2212.04089)、[TIES](https://huggingface.co/papers/2306.01708)、[KnOTS](https://huggingface.co/papers/2410.19735)）发现把每个更新缩放到 1 以下效果最好，所以我们在全部 89 个 Terminal-Bench 2.1 任务上、在每个执行架下、用第 120 步的适配器比较了三种权重：

- ⅓（平均）：每个执行架只保留自己更新的三分之一。
- ½：每个更新以一半强度施加。
- 1（直接求和）：每个更新完整施加。

| 权重 | pi | hermes | opencode | 三个执行架平均 | 每任务工具调用数 |
|---|---|---|---|---|---|
| 底座模型 | 39.1% | 46.0% | 44.8% | 43.3% | 49.2 |
| ⅓（平均） | 49.4% | 51.2% | 47.1% | 49.2% | 35.6 |
| **½** | 48.8% | 53.5% | 55.2% | **52.5%** | 25.9 |
| 1（求和） | 40.2% | 62.8% | 47.1% | 50.0% | 13.4 |

直接求和会过度施加更新。agent 变得非常短（每任务 13 次工具调用，底座模型是 49 次），而虽然 Hermes 峰值到 62.8%，pi 却回落到与底座模型相当的水平。平均则会稀释每个执行架自身的更新。½ 给出最佳平衡，所以我们用已发布的检查点（pi 第 160 步、hermes 第 160 步、opencode 第 150 步）在权重 ½ 下构建了最终超级适配器。

#### 适配器合并的评测结果

在每个执行架下、在每次运行都打分的任务上（SWE-bench Pro 为 50–51 个，Terminal-Bench 2.1 为 82–85 个），每任务一次尝试（括号内是相对底座模型的效率提升）：

| 执行架 | 基准 | Qwen3.8-27B | Qwen3.8-27B-\<harness\>-adapted | Qwen3.8-27B-super-adapter | Qwen3.8-27B（thinking） | Qwen3.8-27B-super-adapter（thinking） |
|---|---|---|---|---|---|---|
| pi | SWE-bench Pro（hard 51） | 40.0% | 64.0%（−60%） | 46.0%（−73%） | 74.0% | 74.0%（−48%） |
| hermes | SWE-bench Pro（hard 51） | 29.4% | 43.1%（−56%） | 47.1%（−60%） | 45.1% | 60.8%（−36%） |
| opencode | SWE-bench Pro（hard 51） | 35.3% | 51.0%（−72%） | 45.1%（−63%） | 47.1% | 66.7%（−31%） |
| pi | Terminal-Bench 2.1 | 40.0% | 56.5%（−56%） | 48.2%（−56%） | 52.9% | 57.6%（−25%） |
| hermes | Terminal-Bench 2.1 | 44.7% | 58.8%（−70%） | 55.3%（−53%） | 58.8% | 63.5%（−19%） |
| opencode | Terminal-Bench 2.1 | 47.6% | 52.4%（−53%） | 52.4%（−68%） | 54.9% | 58.5%（−22%） |

"thinking"指聊天模板的思考模式在其默认强度（xhigh）下的表现。专科适配器是在关闭思考的情况下训练与服务的。

在关闭思考时，超级适配器在全部六对"执行架—基准"上超过底座模型（平均 pass@1 39.5% → 49.0%；新解 71 个任务 vs 丢失 34 个，p < 0.001）。

尽管它完全没有在开启思考的情况下训练过，它仍是我们评测过的、在思考模式下最强的模型。对照同一强度下的底座模型思考模式，它在六对中赢五对、平一对（平均 55.5% → 63.5%；新解 67 个 vs 丢失 37 个，p = 0.004）。最大增益出现在 SWE-bench Pro：hermes 下 +16 点、opencode 下 +20 点。在 pi 下的 SWE-bench Pro（仅思考模式就已达到 74%）上打平。

关闭思考时请用专科执行架适配器。每个执行架自己的适配器在六对中领先四对，差距最大的是 pi（SWE-bench Pro 64.0% 对 46.0%，Terminal-Bench 上 56.5% 对 48.2%）。把一个模型拆分到三个执行架，pi 损失最大。如果你只用一个执行架、并且保持关闭思考，就用它的专科适配器。

超级适配器也高效得多。在底座模型与超级适配器都能解出的任务上，关闭思考时它每任务的工具调用少 53–73%、生成的 token 少 44–60%，在 130 个任务中有 111 个工具调用更少。开启思考时，它在 SWE-bench Pro 上仍把工具调用削减 31–48%、token 削减 24–43%。在 Terminal-Bench 上，工具调用下降 19–25%，token 数大致不变。

½ 这个权重是在 Terminal-Bench 2.1 上用第 120 步适配器选出来的，所以 Terminal-Bench 的数字略偏乐观；SWE-bench Pro 未参与这个选择。完整配对结果见[超级适配器的模型卡](https://huggingface.co/harness-hub/Qwen3.8-27B-super-adapter)。

### 最终结果

本节先报告训练期间发生了什么，然后报告适配器在其自身执行架内外、在留出基准上的得分。

#### 训练结果

训练累计运行 598 步，共训练 78,114 个样本，恰好对应 1.67 亿个训练 token。

训练期间，我们看到一个清晰信号：模型学会用越来越少的步数解决任务，且没有明显的饱和迹象。尽管有时有明确的上升趋势，训练正确性总体上似乎持平。这可以解释为：模型在训练中不断遇到新任务，而随着轨迹变短，一步的 token 预算能容纳的组数翻了一倍多。准确率增益体现在下一节的留出基准上。

另一方面，safeagents 成功阻断了多次可疑尝试。在三次训练运行中，共检查了 130 万次工具调用，共阻断 647 次工具调用。

#### 评测结果

本节覆盖评测设置、执行架内结果、跨执行架迁移，以及一项分布外检查。

##### 评测设置

我们在每个适配器被训练的那个执行架内部评测它，使用两个智能体编码基准：[Terminal-Bench 2.1](https://huggingface.co/datasets/harborframework/terminal-bench-2.1) 的全部 89 个任务（每任务 1 小时与 100 个 agent 步），以及 SWE-bench Pro 最难的 51 个任务（2 小时与 100 个 agent 步）。我们把每任务的最大 token 数上限设为 131072。我们不调整 agent 设置，对所有执行架使用默认配置。例如 Pi 会自动应用上下文压缩，而 OpenCode 与 Hermes 不会，这主要影响 SWE-bench Pro 的结果，因为上下文会迅速溢出。因此你不能跨不同执行架比较结果（用 Pi 并不必然比 Hermes 或 OpenCode 得到更好的结果），但在同一执行架内部比较、并据此下结论是公平的。

每次 rollout 都通过与训练相同的 Harbor 与 OpenEnv 栈、在 HF 沙箱中运行，每任务一次尝试，温度 0.8，关闭思考。每个 LoRA 检查点被合并进底座权重，在单块 GPU 上用 vLLM 单独服务，并发数与底座模型评测时相同。

对所有评测基准，我们报告 pass@1，以及工具调用数与总轮数——既对全部任务，也对已解出的任务。

为保持开放，最终评测的全部模型轨迹都推送到这个公开 bucket：[harness-hub/harness-adapters-trajectories](https://huggingface.co/buckets/harness-hub/harness-adapters-trajectories)。

##### 最终评测结果

三个专科适配器在各自执行架下、在两个基准上都超过底座模型。在 SWE-bench Pro（hard 51）上，pi 从 39.2% 到 64.7%（+25.5 点：新解 15 个任务 vs 丢失 2 个，p = 0.002），hermes 从 29.4% 到 43.1%，opencode 从 35.3% 到 51.0%。在完整 Terminal-Bench 2.1 上，pi 增益 +16.3 点（16 vs 2，p = 0.001），hermes +14.1（19 vs 7，p = 0.03）。Opencode 总体增益 +6.0，在未参与其检查点选择的 66 个任务上增益 +13.6（12 vs 3，p = 0.035）。

适配器解决任务也高效得多：在它们与底座模型都能解出的任务上，SWE-bench Pro 上每任务工具调用少 56–72%，Terminal-Bench 2.1 上少 53–70%。单一超级适配器在三个执行架下也都超过底座模型（SWE-bench Pro 上 +6 到 +18 点，Terminal-Bench 2.1 上 +5 到 +10 点），工具调用的削减幅度同样大（53–73%）。在关闭思考时它保留的各专科增益较少，pi 下最少；但在开启思考时，它在六对"执行架—基准"中的五对上超过同强度下的底座模型思考模式（见[超级适配器一节](#super-adapter-merging-all-adapters-into-one)）。每个模型卡都有完整的配对结果。

##### 效率与表现能力会跨执行架迁移吗？

为回答这个问题，我们还把 pi 执行架适配器放到 Hermes Agent 与 OpenCode 下评测。

在 OpenCode 下，它在 Terminal-Bench 2.1 上与 OpenCode 自己的专科适配器相当（44.8% → 54.0%，对照 46.4% → 52.4%）。在 Hermes 下，它保住了专科适配器约三分之二的增益（46.3% → 56.1%，对照 44.7% → 58.8%），两者工具调用都同样削减约 45%。因此看来，新学到的能力确实跨执行架迁移。

##### 在分布外任务与设置上的评测

如果我们在分布外任务上、在适配器未参与训练的执行架之外评测，会发生什么？

我们在 300 个 [AutomationBench 任务](https://github.com/zapier/AutomationBench)上跑了全部五个模型——该基准由业务自动化工作流评测构成——并使用 AutomationBench 自己的 agent 循环，而不是 Pi、Hermes 或 OpenCode。这样我们可以交叉检验两个不同的问题：模型能解 SWE 类任务之外的问题吗？当模型被放到它未参与训练的执行架之外时会发生什么？

结果显示适配器与底座模型接近。Pi 与 OpenCode 略领先（pass@1 分别为 27.0% 与 25.3%，底座 23.0%），合并版持平（23.7%），Hermes 落后几个点（17.7%）。除 Hermes 之外，差异都在噪声范围内，因此执行架内部的 RL 既没有明显迁移到这个差异极大的设定，也没有在其中把模型弄坏。

| 模型 | pass@1（全部断言满足） | 相对底座 | 部分得分（满足断言的占比） | 相对底座 |
|---|---|---|---|---|
| 底座 | 23.0% | – | 62.2% | – |
| pi 160 | 27.0% | +4.0 | 66.2% | +4.0 |
| opencode 150 | 25.3% | +2.3 | 65.2% | +3.0 |
| 合并版 | 23.7% | +0.7 | 60.6% | −1.6 |
| hermes 160 | 17.7% | −5.3 | 56.6% | −5.6 |

### 开放问题：模型究竟学到了什么？

我们感谢用户与社区的反馈，社区的初步测试与结果总体上似乎非常正面，我们希望未来继续这个方向。我们也看到了一些出人意料的结果，例如有用户报告[执行架适配器在 Qwen3.8 的衍生模型（如 Swift-1.5）上效果非常好](https://huggingface.co/harness-hub/Qwen3.8-27B-opencode-adapted-GGUF/discussions/2)。

这个问题是我们在发布之后思考的一个开放问题。仔细检查评测基准生成的轨迹后可以发现，在非思考模式下，模型倾向于在提出工具调用之前生成一小段文本，而底座模型几乎不生成任何文本就直接发出工具调用。

这一现象可以看作某种"推理泄漏"：模型学会了通过生成一些有时看起来像推理痕迹的文本（例如：..等等？..让我看看，等等），从它的非思考版本"逃逸"到思考版本。[近期一篇论文](https://huggingface.co/papers/2610.14270)也很好地描述了 LLM 在 RL 阶段的行为。

这会让我们训出的模型失效吗？我们认为不会，因为最终结果依然有效：在完全相同的条件下（固定 token 预算），我们的适配器确实（大幅）超过底座的非思考模型，并追平思考版本的表现，同时 token 效率高得多。社区的正面反馈进一步确认了这一点。

不过，这也引出了开展正式后续工作的必要：我们将尝试把同一条流水线重新应用于纯思考模型，并探索混合思考/非思考训练，以更好理解 RL 训练在混合思考模型上的行为。一旦得到结论性结果，我们会与社区分享下一步发现（以及新的执行架适配器）。

### 结语与未来方向

通过这项工作，我们证明了：在你目标执行架内部对你的模型做 RL 训练，会在同等条件下评测时带来更高效、因而更准确的最终模型。这一观察与 Hugging Face 团队此前的多项工作一脉相承，例如 [multi-harness-RL](https://huggingface.co/spaces/FineEnvs/multi-harness-rl) 或[执行架适配器的早期迭代](https://huggingface.co/blog/harness-hub/harness-adapters)。

未来，我们将探索把这份配方应用到更多模型，同时更好地研究混合思考/非思考模型的训练策略。

我们也向社区公开分享完整配方与流水线，以便复现一切，并邀请每个人基于自己的代码库或任何相关材料构建自己的 RL 任务，把同样的训练配方与思路应用到他们喜欢的模型与执行架上，得到更高效的智能体模型。我们希望这篇博客能成为构建者未来构建并分享自己的执行架适配器的起点。

## 与路线图的挂接

- **A1-01（模型能力光谱与选型）**：本文给"选型"加了一个常被忽略的维度：同一个模型在不同执行架下的能力是不同的。Qwen3.8-27B 在 pi 下 Terminal-Bench 2.1 是 39%、在 opencode 下是 47.6%、在 hermes 下是 44.7%——这些差异不是随机噪声，而是模型与执行架提示/工具接口的匹配度。它给出的选型判据因此变成三段式：先按任务定执行架，再在**该执行架下**测候选模型，最后才决定是否用适配器把差距补上。文中还明确指出跨执行架的数字不可直接比较（Pi 自带上下文压缩，OpenCode 与 Hermes 没有），这条告诫本身就能纠正很多"看排行榜选执行架"的做法。
- **A2-07（执行架与框架选型）**：这篇是"框架解决编排、不解决正确性"的正面案例：它不重写 agent 循环，而是让执行架按发布状态运行，用一个代理记录 harness 与 vLLM 之间的真实 token 供训练器学习。这直接说明执行架不只是编排层，它的提示、工具接口与轮次策略会实质影响模型表现——因此"自研还是用现成 harness"这个取舍多了一条依据：现成执行架的优势在于可以被原地训练，而不只是省开发工时。同时它也暴露了执行架选型的粘性成本：把一个模型拆到三个执行架，pi 损失最大（专科 64.0% 降到超级适配器 46.0%）。
- **A6-06（成本工程）**：文中给出了成本侧最硬的三个数字。其一，适配器同时降本增效：在两者都能解出的任务上，工具调用少 53–73%、每任务 token 少 44–60%（130 个任务中 111 个工具调用更少），切换思考模式后仍少 31–48% 的调用。其二，成本是训出来的而非调出来的——奖励函数里有一个 0.1 的工具效率加成，作者注明这个值来自上一代实验。其三，训练本身的账：598 步、78,114 个样本、1.67 亿训练 token、每个适配器 2×B200（一块跑 vLLM、一块跑训练），外加 130 万次工具调用被 safeagents 检查（阻断 647 次）。这组数字足以支撑"自建适配器是否比直接换大模型更划算"的成本估算。

## 三个自测问题

1. 三个适配器的权重更新余弦相似度只有 0.01–0.02，作者说这是"合并的最佳情形"。请解释为什么"近乎正交"有利于合并，以及为什么在这种前提下仍然需要把权重缩到 ½ 而不是直接求和（提示：看 1（求和）那一行的 pi 与每任务工具调用数）。
2. 难度检查要求任务"底座模型有时能解出、有时不能"。请说明 GRPO 的组相对打分为什么使"全对"与"全错"的任务都无信号，并解释为什么 1,127 个任务过滤到 278 个之后还要把 522 个被拒任务送去 Tasksmith 修复而不是直接丢弃。
3. 在分布外的 AutomationBench 上，适配器与底座基本持平（23.0% 上下，Hermes 甚至低 5.3 点），但作者认为这不影响结论。请说明这个结果支持什么、不支持什么；如果你要把这套配方用在自己的执行架上，这个 OOD 结果会让你在验收标准里加哪一条？
