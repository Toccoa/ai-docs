## 为什么今天读这篇

因为它是"工具接口设计"这条知识点目前最完整的一手材料：不是给建议清单，而是给一条可复现的工程回路——先搭原型、再造评测集、再让 agent 读自己的 trace 去改工具，最后用留出集验证改动没有过拟合。它解答的是架构师每天都要面对的具体问题：该做 `list_contacts` 还是 `search_contacts`、工具该不该按服务加前缀、返回值里该不该带 `uuid`、响应体该截断到多少 token。文中还给了两个可以直接抄的默认值：Claude Code 把工具响应限制在 25,000 token，以及"详细/简洁"两档响应的实测 token 对比（206 vs 72）。读完你应该能判断：你手上这套工具集里，哪些是"把 API 端点包了一层"，哪些才是"给模型看的工具"。

## 三句话摘要

1. 工具是一种新形态的软件契约——它不是确定性系统之间的契约，而是确定性系统与非确定性 agent 之间的契约，所以必须按 agent 的"可供性"（affordance）设计，而不是按人类开发者的习惯把 API 端点包一层。
2. 更有效的做法是少而准：围绕高价值工作流做几个能合并多步操作的复合工具（`schedule_event` 而不是 `list_users`+`list_events`+`create_event`），用命名空间划清边界，只回传高信号字段，并为可能吃满上下文的响应预设分页、范围选择、过滤与截断。
3. 所有改动都要用评测说话：工具的提示工程——尤其是描述与参数命名——改动虽小，收益却可能极大；作者称 Claude Sonnet 3.5 在 SWE-bench Verified 上拿到当时最优成绩，就来自对工具描述的精细打磨。

### 什么是工具？

[模型上下文协议（MCP）](https://modelcontextprotocol.io/docs/getting-started/intro)可以让 LLM 智能体拥有上百个工具，去解决真实世界的任务。但我们要怎么让这些工具发挥最大效力？

本文介绍我们在一系列智能体 AI 系统中提升表现时，最有效的一些技术¹。

我们先讲你可以怎么做：

- 为你的工具搭出原型并测试
- 用 agent 为你的工具建立并运行一套完整的评测
- 与 Claude Code 这类 agent 协作，自动提升工具的表现

最后总结我们在这个过程中识别出的高质量工具的关键原则：

- 选择该实现（以及不该实现）的工具
- 用命名空间为工具划定清晰的功能边界
- 从工具向 agent 回传有意义的上下文
- 针对 token 效率优化工具响应
- 对工具描述与规格做提示工程

### 什么是工具？

在计算领域，确定性系统在给定相同输入时每次都会产生相同的输出；而*非确定性*系统——比如 agent——即使起点条件相同，也可能产生不同的响应。

我们传统上写软件，是在确定性系统之间建立一份契约。例如 `getWeather("NYC")` 这样的函数调用，每次被调用都会以完全相同的方式获取纽约市的天气。

工具是一种新形态的软件，它体现的是确定性系统与非确定性 agent 之间的契约。当用户问"我今天该带伞吗？"，agent 可能会调用天气工具，可能直接凭常识回答，甚至可能先反问一句"你在哪个城市？"。偶尔，agent 会产生幻觉，或者干脆没搞懂该怎么用某个工具。

这意味着我们为 agent 写软件时，必须从根本上重新思考方法：不能像给其他开发者或系统写函数和 API 那样去写工具和 [MCP 服务器](https://modelcontextprotocol.io/)，而要*为 agent* 设计它们。

我们的目标是扩大 agent 的有效作用面积——让它们能借助工具、采取各种成功的策略，去解决范围广泛的任务。幸运的是，按我们的经验，那些对 agent 来说最"顺手"（ergonomic）的工具，对人类来说往往也出奇地直观。

### 如何编写工具

本节讲你如何与 agent 协作，既写出工具，也改进你交给它的工具。先快速搭一个工具原型并在本地测试；接着跑一套完整的评测，用来度量后续改动；然后与 agent 并肩工作，反复执行"评测—改进"的循环，直到 agent 在真实任务上表现足够强。

#### 搭建原型

如果不亲自动手，很难预判 agent 会觉得哪些工具顺手、哪些不顺手。所以先快速搭一个原型。如果你用 [Claude Code](https://www.anthropic.com/claude-code) 来写工具（可能一次性写完），那么把工具所依赖的软件库、API 或 SDK（包括可能用到的 [MCP SDK](https://modelcontextprotocol.io/docs/sdk)）的文档交给 Claude 会有帮助。对 LLM 友好的文档通常以扁平的 `llms.txt` 文件形式放在官方文档站上（这里是我们 [API 的](https://docs.anthropic.com/llms.txt)）。

把你的工具包进一个[本地 MCP 服务器](https://modelcontextprotocol.io/docs/develop/connect-local-servers)或[桌面扩展](https://www.anthropic.com/engineering/desktop-extensions)（DXT），就可以在 Claude Code 或 Claude 桌面应用里连接并测试它们。

要把本地 MCP 服务器接到 Claude Code，运行 `claude mcp add &lt;name&gt; &lt;command&gt; [args...]`。

要把本地 MCP 服务器或 DXT 接到 Claude 桌面应用，分别进入 `Settings > Developer` 或 `Settings > Extensions`。

工具也可以直接传入 [Anthropic API](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/overview) 调用，用于程序化测试。

亲自试用这些工具，找出粗糙的地方。收集用户的反馈，围绕你期望工具支撑的用例与提示词建立直觉。

#### 运行评测

接下来，你需要通过跑评测来度量 Claude 使用你工具的水平。先从生成大量评测任务开始，这些任务要扎根于真实世界的用法。我们建议与 agent 协作来分析结果、判断如何改进工具。完整流程见我们的[工具评测 cookbook](https://platform.claude.com/cookbook/tool-evaluation-tool-evaluation)。

##### 生成评测任务

有了早期原型，Claude Code 可以快速探索你的工具，并生成几十组"提示—响应"对。提示应当受真实用法启发，并基于真实的数据源与服务（例如内部知识库与微服务）。我们建议避免过于简化或表面的"沙箱"环境——那种环境无法以足够的复杂度给你的工具施加压力。强评测任务可能需要多次工具调用——甚至几十次。

以下是一些强任务的例子：

- 下周和 Jane 开个会，讨论我们最新的 Acme Corp 项目。把我们上次项目规划会议的笔记附上，并预订一间会议室。
- 客户 ID 9182 报告说，一次购买尝试被扣了三次款。找出所有相关日志条目，并判断是否有其他客户受到同一问题影响。
- 客户 Sarah Chen 刚提交了取消请求。准备一份挽留方案。请确定：(1) 她为什么离开，(2) 什么样的挽留方案最有吸引力，(3) 在提出方案前我们应该注意哪些风险因素。

以下是一些较弱的任务：

- 下周和 jane@acme.corp 开个会。
- 在支付日志里搜索 `purchase_complete` 和 `customer_id=9182`。
- 找到客户 ID 45892 的取消请求。

每条评测提示都应当配一个可验证的响应或结果。你的校验器可以简单到对标准答案与采样响应做精确字符串比较，也可以复杂到请 Claude 来评判响应。要避免过严的校验器——它们会因为格式、标点或合法的替代表述这类无关差异而把正确响应判为错误。

对每组"提示—响应"对，你还可以选择性地指定期望 agent 在解题时调用的工具，以便在评测中度量 agent 是否成功把握了每个工具的用途。不过，由于解对任务可能存在多条有效路径，尽量避免过度指定或对某种策略过拟合。

##### 运行评测

我们建议用直接的 LLM API 调用，以程序化方式运行评测。使用简单的智能体循环（用 `while` 循环包住交替进行的 LLM API 调用与工具调用）：每个评测任务一个循环。每个评测 agent 应当只拿到一条任务提示和你的工具。

在评测 agent 的系统提示里，我们建议不只要求 agent 输出结构化的响应块（用于校验），还要求它输出推理块与反馈块。要求 agent 在工具调用与响应块*之前*输出这些内容，可能通过触发思维链（CoT）行为来提升 LLM 的有效智能。

如果你用 Claude 跑评测，可以打开[交错思考](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking)来"开箱即用"地获得类似能力。这有助于你探查 agent 为什么调用或不调用某些工具，并凸显工具描述与规格中具体的改进点。

除总体准确率之外，我们还建议收集其他指标：单次工具调用与单个任务的运行时长、工具调用总次数、token 总消耗量、工具错误数。跟踪工具调用有助于发现 agent 常走的常见工作流，并提示某些工具有合并的机会。

##### 分析结果

agent 是你发现问题、提供反馈的好帮手——从自相矛盾的工具描述，到低效的工具实现，再到令人困惑的工具模式，它们都能说上话。但要记住：agent 在反馈和响应里*省略*的内容，往往比它写出来的更重要。LLM 并不总是[言其所想](https://www.anthropic.com/research/tracing-thoughts-language-model)。

观察 agent 在哪里卡住或困惑。通读评测 agent 的推理与反馈（或 CoT）来定位粗糙之处。审阅原始 transcript（包括工具调用与工具响应），以捕捉 agent 的 CoT 里没有明确描述的行为。要读出言外之意；记住，你的评测 agent 未必知道正确答案与策略。

分析你的工具调用指标。大量冗余的工具调用，可能说明分页或 token 上限参数需要重新调校；大量因参数非法导致的工具错误，可能说明工具需要更清晰的描述或更好的示例。我们发布 Claude 的[网页搜索工具](https://www.anthropic.com/news/web-search)时发现，Claude 会不必要地往工具的 `query` 参数后面追加 `2025`，这会让搜索结果产生偏置、拉低表现（我们通过改进工具描述把 Claude 引回了正确方向）。

#### 与 agent 协作

你甚至可以让 agent 分析你的结果并替你改进工具。只需把评测 agent 的 transcript 拼接起来，粘贴进 Claude Code。Claude 是分析 transcript、一次性重构大量工具的专家——例如确保在新改动发生时，工具实现与描述仍然自洽。

事实上，本文的大部分建议，都来自我们与 Claude Code 反复优化内部工具实现的过程。我们的评测建立在内部工作区之上，复刻了内部工作流的复杂度，包括真实的项目、文档与消息。

我们依靠留出测试集来确保没有对"训练用"评测过拟合。这些测试集显示，即便与我们用"专家"级工具实现所达到的水平相比，我们仍能提取出额外的性能提升——无论那些工具是研究人员手写的，还是 Claude 自己生成的。

### 编写有效工具的原则

本节把我们学到的东西提炼成几条编写有效工具的指导原则。

#### 为 agent 选择正确的工具

工具更多并不总是带来更好结果。我们观察到的一个常见错误是：工具只是把已有的软件功能或 API 端点包了一层——不管这些工具是否适合 agent。这是因为 agent 相对于传统软件有其独特的"可供性"（affordance）——也就是说，它们感知"自己能用这些工具做什么"的方式不同。

LLM agent 的"上下文"是有限的（即它们一次能处理的信息量有上限），而计算机内存既便宜又充裕。考虑在通讯录里查找联系人的任务。传统软件程序可以高效地存储并逐个处理联系人列表，检查完一个再看下一个。

然而，如果 LLM agent 用的工具返回*全部*联系人，然后它必须逐个 token 读过去，那就是把有限的上下文空间浪费在无关信息上（想象你查通讯录时从上到下逐页读——也就是暴力搜索）。更好也更自然的做法（对 agent 和对人都一样）是先跳到相关那一页（也许是按字母顺序找到它）。

我们建议围绕具体的高价值工作流，精心做少量工具，让它们与你自己的评测任务对齐，再由此扩展。在通讯录这个例子里，你可能选择实现 `search_contacts` 或 `message_contact` 工具，而不是 `list_contacts` 工具。

工具可以合并功能，在底层处理可能*多个*离散操作（或 API 调用）。例如，工具可以在响应里补充相关元数据，或在一次工具调用中处理频繁串联的多步任务。

举几个例子：

- 与其实现 `list_users`、`list_events` 和 `create_event` 三个工具，不如考虑实现一个 `schedule_event` 工具，由它查找可用时间并安排事件。
- 与其实现 `read_logs` 工具，不如考虑实现 `search_logs` 工具，只返回相关日志行及其周边上下文。
- 与其实现 `get_customer_by_id`、`list_transactions` 和 `list_notes` 工具，不如实现一个 `get_customer_context` 工具，一次性汇编某位客户近期且相关的全部信息。

要确保你建的每个工具都有清晰、独特的目的。工具应当让 agent 能够像人在拥有同样底层资源时会做的那样，把任务细分并求解，同时减少本来会被中间输出消耗掉的上下文。

工具过多或功能重叠，也会分散 agent 的注意力，让它不去追求高效策略。对建什么（以及不建什么）做审慎而有所取舍的规划，回报确实很大。

#### 为工具设置命名空间

你的 AI agent 可能会接触到几十个 MCP 服务器、上百个不同工具——包括其他开发者提供的。当工具功能重叠或目的含糊时，agent 就可能搞不清该用哪一个。

命名空间（把相关工具归到共同前缀下）有助于在大量工具之间划清边界；MCP 客户端有时默认就这么做。例如按服务命名（如 `asana_search`、`jira_search`）、按资源命名（如 `asana_projects_search`、`asana_users_search`），可以帮助 agent 在恰当的时候选到恰当的工具。

我们发现，在前缀式与后缀式命名空间之间做选择，对工具调用评测有相当显著的影响。这种影响因 LLM 而异，我们建议你依据自己的评测来选择命名方案。

agent 可能会调错工具、用错误的参数调用正确的工具、调用过少的工具，或者错误地处理工具响应。通过有选择地实现那些名字能反映任务自然划分的工具，你同时减少了两件事：加载进 agent 上下文的工具数量与工具描述长度；并把智能体计算从 agent 的上下文里转移到工具调用本身。这降低了 agent 犯错的整体风险。

#### 从工具回传有意义的上下文

同理，工具实现应当注意只把高信号的信息回传给 agent。它们应当优先考虑上下文相关性而非灵活性，并回避底层技术标识符（例如 `uuid`、`256px_image_url`、`mime_type`）。而 `name`、`image_url`、`file_type` 这类字段更有可能直接支撑 agent 的下游动作与响应。

agent 处理自然语言的名称、术语或标识符时，明显比处理晦涩的标识符更成功。我们发现，仅仅把任意的字母数字 UUID 解析成语义上更有意义、更可解释的语言（甚至只是一个从 0 开始的 ID 方案），就能通过减少幻觉显著提升 Claude 在检索任务中的精确度。

在某些情况下，agent 可能需要同时与自然语言和技术标识符两种输出交互的灵活性——哪怕只是为了触发下游的工具调用（例如 `search_user(name='jane')` → `send_message(id=12345)`）。你可以通过在工具里暴露一个简单的 `response_format` 枚举参数来同时支持两者，让 agent 控制工具返回"简洁"还是"详细"的响应（见下图）。

你还可以加入更多格式以获得更大灵活性，类似 GraphQL 里你可以精确选择想收到哪些信息。下面是一个用于控制工具响应冗余度的 `ResponseFormat` 枚举示例：

```
enum ResponseFormat {
   DETAILED = "detailed",
   CONCISE = "concise"
}
```

Slack 的 thread 与 thread 回复由唯一的 `thread_ts` 标识，抓取 thread 回复时必须提供它。`thread_ts` 以及 `channel_id`、`user_id` 等其他 ID 可以从"详细"响应中取得，以便发起需要这些 ID 的后续工具调用；"简洁"响应只返回 thread 内容，不含 ID。在这个例子里，使用"简洁"响应只花了约 ⅓ 的 token。

甚至连工具响应的结构——例如 XML、JSON 或 Markdown——也会影响评测表现：没有一劳永逸的方案。这是因为 LLM 是在下一 token 预测上训练的，往往在与其训练数据匹配的格式上表现更好。最优的响应结构因任务和 agent 而差异很大。我们建议你基于自己的评测来选择最佳响应结构。

#### 针对 token 效率优化工具响应

优化上下文的质量很重要，但优化工具响应回传给 agent 的上下文*数量*同样重要。

对于任何可能吃满上下文的工具响应，我们建议组合使用分页、范围选择、过滤和/或截断，并给出合理的默认参数值。对 Claude Code，我们默认把工具响应限制在 25,000 token 以内。我们预计 agent 的有效上下文长度会随时间增长，但对上下文高效的工具的需求会一直存在。

如果你选择截断响应，务必用有帮助的指令引导 agent。你可以直接鼓励 agent 采用更省 token 的策略，例如在知识检索任务里做多次小而精准的搜索，而不是做一次宽泛的大搜索。同样，如果某次工具调用抛错（例如在输入校验阶段），你可以对错误响应做提示工程，清楚传达具体且可执行的改进方式，而不是只给晦涩的错误码或 traceback。

#### 对工具描述做提示工程

现在我们来到改进工具最有效的方法之一：对你的工具描述与规格做提示工程。因为它们会被加载进 agent 的上下文，所以它们能共同把 agent 引向有效的工具调用行为。

写工具描述与规格时，想想你会怎么向团队里的新同事介绍这个工具。考虑你可能不自觉带入的上下文——特殊的查询格式、小众术语的定义、底层资源之间的关系——并把它明确写出来。通过清楚描述（并用严格的数据模型强制）期望的输入与输出，避免歧义。特别是输入参数要命名得毫不含糊：与其叫 `user`，不如叫 `user_id`。

有了评测，你就能更有把握地度量提示工程的影响。即便是对工具描述的小幅打磨，也可能带来戏剧性的提升。在我们对工具描述做了精细调整之后，Claude Sonnet 3.5 在 [SWE-bench Verified](https://www.anthropic.com/engineering/swe-bench-sonnet) 评测上取得了当时的最优表现，错误率大幅下降，任务完成度提升。

关于工具定义的其他最佳实践，见我们的[开发者指南](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/implement-tool-use#best-practices-for-tool-definitions)。如果你在为 Claude 构建工具，我们还建议读一读工具是如何被动态加载进 Claude 的[系统提示](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/implement-tool-use#tool-use-system-prompt)的。最后，如果你在为 MCP 服务器写工具，[工具注解](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)有助于披露哪些工具需要开放世界访问权限，或会做出破坏性变更。

### 展望

要为 agent 构建有效的工具，我们需要把软件开发实践从可预测的、确定性的模式，重新定向到非确定性的模式。

通过本文描述的这套迭代式、评测驱动的过程，我们识别出了工具成功的稳定规律：有效的工具是被有意且清晰地定义的，审慎地使用 agent 的上下文，能在多样工作流中相互组合，并让 agent 直观地解决真实世界任务。

未来，我们预计 agent 与世界交互的具体机制会继续演化——从 MCP 协议的更新，到底层 LLM 本身的升级。只要我们对"改进 agent 工具"保持系统化、评测驱动的方法，就能确保在 agent 变得更强时，它们所用的工具也随之演化。

## 与路线图的挂接

- **A2-05（工具接口设计）**：本文是这条知识点最直接的一手来源，且给出了可执行的判据而非原则口号。三个可以直接落地的动作：一是**粒度合并**——工具应当在底层合并多步操作（`schedule_event` 取代 `list_users`+`list_events`+`create_event`），因为"工具越多越好"在 agent 上不成立，重叠工具会分散策略；二是**命名空间**——按服务（`asana_search`）与按资源（`asana_projects_search`）划界，且前缀式与后缀式的选择对评测有"相当显著"的影响，必须以自己的评测决定；三是**回传高信号**——避免 `uuid`、`mime_type` 这类技术标识符，把 UUID 换成有语义的名称或 0 基索引即可显著降低幻觉。它还提供了一个实用的折中方案：用 `response_format` 枚举在"详细/简洁"两档之间让 agent 自己选，实测同一份内容 206 token 可压到 72 token（约 ⅓）。
- **A1-04（结构化输出与工具调用协议）**：本文把"schema 是契约"这件事推到了 schema 之外——JSON Schema 只能定义结构合法性，定义不了使用习惯。因此它主张参数命名要无歧义（`user_id` 而非 `user`）、描述要像写给新同事、必要时用严格数据模型强制约束；同时给出"契约破裂时的兜底"这一侧的具体做法：错误响应要写成可执行的改进提示（而不是错误码或 traceback），截断响应要附带引导 agent 改用过滤或分页的指令。对做协议设计的架构师，文中的默认值（Claude Code 单次工具响应 25,000 token 上限）与"响应结构（XML/JSON/Markdown）本身会影响评测表现、没有通用最优解"这两条，是可以直接写进设计文档的锚点。

## 三个自测问题

1. 原文说"工具更多并不总是带来更好结果"，并给出通讯录这个例子。如果你手上有一套把内部 CRM 的 40 个 REST 端点一一映射成的工具，你会按什么标准把它们收敛成几个？收敛之后，哪些能力会被牺牲，你打算怎么补偿？
2. `response_format` 的"简洁/详细"两档看似只是省 token，但它同时改变了下游工具调用能不能拿到 `thread_ts` 这类 ID。这个设计对"agent 自己决定要看哪一档"提出了什么隐含要求？如果 agent 选错了档，你的错误语义该怎么设计？
3. 作者把"留出测试集"作为防止对评测过拟合的手段，并声称即便对照专家手写的工具实现仍有额外提升。请说明：为什么"用 Claude Code 优化工具、再用同一批评测验证"会构成过拟合风险？你会怎么切分训练用评测集与留出集？
