## 为什么今天读这篇

因为它把"agent 补丁比人大"这个被广泛当作缺陷的观察，拆成了一个可以逐块验证的因果问题：补丁里每一块改动，究竟是哪一步写下的、删掉它任务测试还过不过。结论会直接推翻你的直觉——在 SWE-bench Verified 上，多出来的行主要不是代码而是测试（61%）和文档（13%）；真正的代码层面，18 个模型里有 11 个留下的无谓代码比人类开发者**更少**（NP_code 0.887 对 0.864）。对做架构决策的人，它给出三个高价值事实：无谓代码几乎全部来自"修"这一步（83%）而不是"调试"（154/3,987），所以事后清理才是有效杠杆；89% 的无谓代码会改变行为，评审不能跳过；以及"解决率"与"代码必要性"在两个基准上一个无关、一个负相关——这意味着你现在用的排行榜可能正在奖励更脏的补丁。

## 三句话摘要

1. 作者提出 Delta Residue Attribution（DRA）：重放 agent 轨迹，把最终补丁切成可独立回退的"单元"，追溯每个单元是第几步写的，然后逐个回退并重跑任务测试来判定它是否"必要"；判定器 O_test 会把 33% 的开发者代码单元判为无谓，加强版 O⁺ 只判 3%，因此必须用同一把尺子给人类补丁打分做校准。
2. 在 18 个前沿模型、7,660 条已解决的 GitHub Copilot CLI 轨迹上：补丁行数中位数是人家的 2.33 倍，但代码层面 agent 平均不比人差（SWE-bench Verified 0.887 vs 0.864；DeepSWE 0.797 vs 0.785）；agent 补丁里平均仍有 11% 的代码单元无谓，其中 89% 会改变行为。
3. 事后清理的效果与代价很具体：自审精确（65.7%）但只捞到 35.5% 的无谓代码，还会弄坏 1.8% 的已解补丁；用 agent 自己的测试加仓库回归测试做剪枝能捞到 67.3%，精确率掉到 46.3%，但 89.1% 的补丁仍能通过任务测试；而在"首次全绿"处提前停止几乎没用（NP_code 从 0.700 只到 0.710）。

## 译文

### 摘要

agent 补丁比开发者的补丁更大，这被广泛解读为过度编辑。但补丁大小说明不了那些多出来的编辑是否必要、它们是什么、以及从哪来。我们提出 Delta Residue Attribution（DRA）：它重放 agent 轨迹，把最终补丁的每一个块（单元）追溯到写下它的那一步，逐个回退该单元，并重跑任务测试来判定该单元是否必要。我们把 DRA 应用于 18 个前沿模型在 SWE-bench Verified（6,728 条）与 DeepSWE（932 条）上的 7,660 条已解决的 GitHub Copilot CLI 轨迹，并用同样的方法给开发者补丁打分。agent 补丁确实比开发者改动了更多行；在 SWE-bench Verified 上，多出来的编辑大多是加测试（61%）与加文档（13%），而在 DeepSWE 上，多出来的编辑大多是代码（58%）。在两个基准上，agent 的代码平均至少与开发者的一样必要（SWE-bench Verified 上 NP_code 均值 0.887 对 0.864，其中 18 个模型里有 11 个留下的无谓代码比开发者少；DeepSWE 上 0.797 对 0.785）。平均而言，SWE-bench Verified 上 agent 补丁的代码单元中有 11% 仍然无谓，其中 89% 会改变行为。agent 新增的测试能检出大部分注入的 bug（68%，任务测试是 77%）；所有注入 bug 中有 5% 是被 agent 新增或加强的测试抓到、而任务测试漏掉的。调试步骤几乎不写下任何无谓代码。代码必要性因模型差异很大；它在 SWE-bench Verified 上与解决率无关，在 DeepSWE 上与之负相关（Spearman −0.59，p=0.01）。在 SWE-bench Verified 上，只用 agent 能看到的测试（它自己的测试与仓库的测试）做 DRA 剪枝，能去掉大部分无谓代码，但也会去掉一些必要代码（召回 67%，精确率 46%），且 89% 被剪枝的补丁仍能解决任务；让 agent 审自己的 diff 更精确但更不有效（召回 36%，精确率 66%）。我们建议基准在报告解决率的同时报告代码必要性，并建议通过模型训练与执行架层面的剪枝来应对过度编辑。

### 1 引言

语言模型现在经常被要求编辑既有代码，而不是从零写起。通过测试是必要的，但不充分：一个用改五十行来修三行 bug 的补丁更难评审，也更可能携带非预期改动。在一项维护者研究中，大约一半通过 SWE-bench 的补丁本不会被合并（Whitfill 等，2026），而许多看似合理的补丁在测试未覆盖的输入上表现得与开发者修复不同（Wang 等，2026）。我们把这种"改得比必要的多"的倾向称为*过度编辑*。在函数级的最小编辑任务上，模型改动远超任务要求（Zhu 等，2026）。在仓库层面，成功的 agent 补丁所含改动约为开发者补丁的两倍，而"最小化"提示几乎没用（Luo 等，2026）。因此，更大的 agent 补丁被广泛读作过度编辑。

保留性提示（Zhu 等，2026；Chai 等，2026）与编辑感知训练（Zhu 等，2026；Yang 等，2026；Ke 等，2026）能减少函数级过度编辑。但补丁大小说明不了多出来的编辑是否必要、属于哪一类、在轨迹的哪个时刻写下；而这三个问题的答案决定了修复应该长什么样。如果多出来的编辑是调试残留，执行架可以清理它们；如果是测试，那可能正是想要的；如果是写进了修复本身，那就得改模型。

我们在单个块与写下它的轨迹步骤这一层级上研究仓库级补丁中的过度编辑。我们的研究问题是：RQ1：与开发者相比，agent 过度编辑了多少？RQ2：那些无谓编辑是什么？RQ3：它们来自轨迹的哪个位置？RQ4：哪些模型过度编辑更多，过度编辑是否与解决率同步？RQ5：无谓代码能被自动移除吗？

为回答这些问题，我们构建了 DRA。DRA 重放一条已解决的轨迹，把最终补丁切成单元（可独立回退的连续改动行块），并把每个单元追溯到写下它的那一步。它通过回退该单元并重跑任务测试来判定其是否必要，延续了 delta debugging 的传统（Zeller 和 Hildebrandt，2002）。必要单元所占比例即*必要性精确率* NP，而 NP_code 是代码单元上的该比例。由于基准测试会漏掉一些必要行为（Wang 等，2026），我们还用行为探针检查无谓代码（第 3.4 节），并以同样方式给开发者补丁打分。我们把 DRA 应用于 18 个模型在 SWE-bench Verified 与 DeepSWE 上的 7,660 条已解决编码 agent 轨迹。

#### 发现

agent 补丁确实比开发者改动更多行，但在 SWE-bench Verified 上多出来的行主要是测试（61%）与文档（13%），而在 DeepSWE 上多出来的编辑主要是代码（58%；RQ2）。在代码层面，SWE-bench Verified 上 18 个模型里有 11 个留下的无谓代码比开发者少（NP_code 均值 0.887 对 0.864），4 个未检出显著差异（这并不等于证明了等价），3 个留下更多（RQ1，第 5.1 节）。在 DeepSWE 上，agent 与开发者持平（0.797 对 0.785），但没有任何模型显著高于开发者基线。平均而言，agent 补丁的代码单元中有 11% 仍是无谓的，其中 89% 会改变行为（RQ2）。调试步骤（探索、复现或探查）几乎不写下任何代码残留（3,987 个单元中只有 154 个）；修复步骤写下了其中 83%（RQ3）。代码必要性因模型而异，在 SWE-bench Verified 上与解决率不相关（Spearman −0.10），但在 DeepSWE 上与之反相关（−0.59，p=0.01；RQ4）。在 SWE-bench Verified 上，生成之后，自审很精确（65.7%）但只找到 35.5% 的无谓代码；用 agent 自己的测试加仓库回归测试做剪枝，在 2,495 个合格补丁上找到 67.3%、精确率更低（46.3%）；提前停止几乎不改变 NP_code（0.700 到 0.710；RQ5）。我们的贡献是：一项块级过度编辑实证研究（开发者补丁用同一方法打分）、DRA 方法（第 3 节），以及对评测与执行架设计的启示（第 6 节）。附录 A.1 列出了我们预注册的假设与我们对假设的偏离。

### 2 相关工作

#### 度量过度编辑

Zhu 等（2026）与 PDB（Chai 等，2026）以已知的最小修复为参照来度量无谓编辑，多数在单函数上；CanItEdit（Cassano 等，2024）度量测试覆盖了函数编辑的多少；编辑感知训练能降低它（Yang 等，2026；Ke 等，2026）。在仓库层面，RECAP（Luo 等，2026）比较补丁大小。覆盖率类指标把"被测试执行"与"被任务要求"混为一谈。DRA 通过反事实移除来度量必要性，且不需要唯一的参照补丁。

#### 无谓改动为何代价高昂

改动规模能预测缺陷（Nagappan 和 Ball，2005；Kamei 等，2013），纠缠的改动会扭曲缺陷数据（Herzig 和 Zeller，2013）。评审者偏好小而聚焦的改动（Rigby 和 Bird，2013；Bacchelli 和 Bird，2013），而更大的改动需要更长的评审时间（Sadowski 等，2018）。agent 的拉取请求常常需要评审者介入或后续返工（Peralta 等，2026；Pham 和 Ghaleb，2026）。看似合理的补丁在未测试输入上常常与开发者修复不同（Wang 等，2026）。通过现有测试的 LLM 重构仍可能改变行为（Dristi 和 Dwyer，2026）。这两项发现促成了我们的行为检查。

#### 智能体执行架、轨迹与 delta debugging

关于智能体执行架与轨迹的工作（Yang 等，2024；Wang 等，2025；SWE-agent Team，2025；Shu 等，2026；Ceka 等，2026）没有把单个补丁块归因到写下它的步骤。DRA 建立在 delta debugging（Zeller 和 Hildebrandt，2002）之上，并继承了基于测试的修复的过拟合告诫（Smith 等，2015），因此我们以开发者补丁为参照做校准。扩展讨论见附录 I。

### 3 把编辑追溯到轨迹步骤：DRA

DRA 有四步：重放、单元溯源、步骤角色标注、必要性打分。Figure 1 用一个小例子展示了整条流水线（附录 B.1），Algorithm 1 给出伪代码。

**Algorithm 1（Delta Residue Attribution，DRA）**

- 输入：基础文件 S₀、已解决轨迹 τ=((a_t,o_t))_{t=1}^{T}、提交的补丁 Δ、判定器 O
- 1：在 S₀ 上重放 τ 的编辑与创建调用，每一步之后记录行级 blame
- 2：断言重放得到的最终状态等于 Δ
- 3：对 Δ 的每个单元 u∈U(Δ)：
- 4：　t*(u) ← 最后写下或删除 u 中某一行的步骤
- 5：　r(t*(u)) ← Rules(a_{t*}) 或 Judge(a_{t*}, o_{t*}, context)
- 6：　class(u) ∈ {code, test, docs, nonsemantic, config}
- 7：　n(u) ← 1 − O(S_T ⊖ u)
- 8：结束
- 9：返回 NP_test(Δ)、NP_code(Δ)、ρ，以及逐单元表

#### 3.1 定义

agent 产生一条动作与观察组成的轨迹；执行一个任务的前 t 个动作得到工作树状态 S_t，提交的补丁是 Δ=diff(S₀,S_T)。我们把 Δ 分解为可各自独立回退的单元 U(Δ)={u₁,…,u_n}，并用 S_T ⊖ u 表示回退了单元 u 之后的状态。判定器 O 若通过某项检查则接受某状态（O(S)=1）。任务测试判定器 O_test 运行 SWE-bench 的 FAIL_TO_PASS 与 PASS_TO_PASS 测试（Jimenez 等，2024；在 DeepSWE 上则是任务自带的测试）。我们只分析已解决的补丁，因此 O(S_T)=1。若回退某单元导致判定被拒，则该单元对 O 是*必要的*（n_O(u)=1，记作 needed），否则是*无谓的*（n_O(u)=0，记作 unneeded）。补丁的*必要性精确率* NP_O 是其必要单元数除以全部单元数：

```
n_O(u) = 1 − O(S_T ⊖ u)                                    (1)
NP_O(Δ) = (1/|U(Δ)|) · Σ_u n_O(u)                          (2)
```

当且仅当 Δ 是 1-最小的（Zeller 和 Hildebrandt，2002）时 NP=1，也就是说没有任何单个单元可以在判定器仍接受的前提下被移除；更大的单元组合可能仍然是可一起移除的。*单元*是一次编辑的原子片段。*无谓代码*指代码文件中的无谓单元；测试文件中的单元单独计分（第 3.2 节）。NP 继承了判定器的盲区：测试不需要的单元可能仍然服务于开发者的意图（Smith 等，2015）。因此我们把无谓单元的占比当作真实冗余量的上界，并把 agent 与用同样方法打分的开发者补丁做比较（附录 B.2 区分了三种最小性概念）。

#### 3.2 重放、单元与溯源

agent 轨迹记录每一次工具调用，但不记录中间仓库状态。我们在任务的基线文件上重放结构化的文件编辑调用，并在每一步之后做行级 blame；我们排除重放最终状态与提交补丁不完全一致的轨迹（SWE-bench Verified 有 96.7% 的轨迹可重放）。一个单元是一个文件内连续的改动行块（被至多一行未改动行分隔的块会被合并），新增或删除的文件算一个单元。每个单元要么是*代码*单元，要么是非代码单元（测试、文档、配置，或注释与格式类编辑）。SWE-bench 判分会重置测试文件，因此测试改动不改变判定器的结果。所以我们把测试编辑与代码分开报告为*未计分*，并把未计分的测试编辑与无谓单元合称补丁的*额外编辑*。我们以 NP_code 作为主指标（规则见附录 B.3）。单元的引入步骤 t*(u) 是最后写下或删除其任一行的步骤，所以一个最初在调试步骤写下、后来在修复步骤被修改的单元，会归因到修复步骤。

#### 3.3 步骤角色标注

每个引入单元的步骤都会得到一个角色。我们把角色归为三类：调试（探索、复现、探查步骤）、修复（修复与精修步骤）、清理（回退早期改动的步骤）。先跑两条确定性规则，其余由 LLM 裁判（GPT-6.1 Sol）基于 issue、压缩后的历史、动作与 agent 的自述来标注（附录 B.4 给出六个细粒度角色与评分准则）。

#### 3.4 判定器：给必要性打分

对每个单元，我们在任务容器里回退它的那些行，并重跑任务测试。无法施加的回退（会退回基线状态或无法解析）我们计为必要。任务测试不会覆盖所有输入路径，所以我们还用模仿 PatchDiff（Wang 等，2026）的行为探针检查无谓代码单元。我们报告 O_test 下的必要性，并用探针来验证其"无谓"判定；加强版判定器 O⁺ 也会救回那些回退后与开发者补丁一致的单位，它使用同一套探针标签。对每个被 O_test 判为无谓的代码单元，一个 LLM（GPT-6.1 Sol）会看到 issue 与回退的 diff（不给它任务测试，也不给开发者补丁），并写出若干差异化调用：即调用被改动代码并打印带标签输出的探针脚本输入。我们在 agent 补丁、回退后的状态、开发者补丁三种状态下运行它们。在 O⁺ 下，若某单元的回退通不过任务测试，或产生了与开发者补丁相同的行为变化，则该单元被计为必要。分解明细见附录 C.1。单元是一次回退一个（第 6 节）。

#### 3.5 步骤归因与开发者校准

无谓单元构成残留 E_dbg ∪ E_fix：E_dbg 存放引入步骤为调试步骤的单元，E_fix 存放其余。调试占比为

```
ρ = |E_dbg| / |E_dbg ∪ E_fix|                              (3)
```

而 ρ_code 把它限制到代码残留上。一个被需要的调试步骤编辑不算残留，因为那次实验最终成了修复。

开发者补丁里也含有测试不需要的代码，所以我们用同样方法给 SWE-bench Verified 的开发者补丁（仅代码文件）打分，并对每个模型报告均值差

```
Δ_dev = mean(NP_code)(agent) − mean(NP_code)(developer)     (4)
```

该差值在两者都有代码单元的实例上计算，配 95% 的实例自助法置信区间（B=2000；除特别说明外，本文所有 CI 都是实例上的 95% 自助区间）。若 Δ_dev<0，说明 agent 留下的无谓代码比开发者多。

### 4 研究设置

#### 4.1 数据

我们用 GitHub Copilot CLI（GitHub，2026）编码 agent，在四个厂商的 18 个模型上评测 SWE-bench Verified（Jimenez 等，2024；Chowdhury 等，2024；500 个 Python 编码任务）与 DeepSWE（Huang 等，2026；113 个长时程编码任务，语言为 Go、TypeScript、Python、Rust 与 JavaScript）。SWE-bench Verified 的解决率范围为 64.0% 到 89.4%。某模型的解决率，是其尝试过的任务中最终补丁通过任务测试的比例。对每个模型，我们使用其所有轨迹可精确重放的已解决 SWE-bench Verified 实例，以及其所有已解决的 DeepSWE 任务。DeepSWE 的模型级统计使用至少有 10 个已打分任务的 17 个模型。本研究覆盖 6,728 个 SWE-bench Verified 补丁（30,265 个单元；482 个不同实例，其中 114 个被全部 18 个模型共享）与 932 个 DeepSWE 补丁（26,209 个单元）。我们在 SWE-bench Verified（470 个已分析实例，1,317 个代码单元）与 DeepSWE（103 个已打分任务；4 个开发者补丁未通过任务测试被剔除）上跑了开发者基线。其他执行架与 SWE-bench Pro 见附录 D。所有单元都在官方评测镜像中于 O_test 下打分；行为探针验证"无谓"判定（第 3.4 节）。角色与探针裁判是 GPT-6.1 Sol。第二位裁判（Claude Opus 5.5）对随机抽取的 10,000 个步骤重新标注，与主裁判在 84.4% 的角色标签上一致（κ=0.69），在 89.1% 的"调试 vs 非调试"标签上一致（κ=0.55；附录 B.4）。

#### 4.2 研究问题与分析

对每个研究问题，我们预注册了期望的结果（附录 A.1），包括阈值与对原始实验计划的偏离。一个双模型先导实验显示多数额外编辑是测试编辑，因此我们为代码与测试实现了分开的分析，把代码单元作为主总体，并增加了开发者校准。

### 5 结果

附录 E.6 列出逐模型结果，附录 D 收录下文提到的次级分析。

#### 5.1 RQ1：agent 过度编辑了多少？

按规模看，agent 补丁显得臃肿。在 SWE-bench Verified 上，模型改动行数的中位数是开发者补丁的 2.33 倍，与 Luo 等（2026）一致。仅看代码单元，该比值是 0.86，逐任务中位数是 1.00。在测试文件之外，agent 改动的行数仍比开发者多（中位数比值 1.09）。按必要性看，agent 的 NP_code 均值为 0.887，而在同一批实例上开发者补丁为 0.864。所以 agent 产生更多非测试改动，但它们写的大部分代码是必要的。开发者补丁充当判定器的基线：仅 O_test 就把 33% 的开发者代码单元判为无谓，而加强版 O⁺ 只判 3% 无谓（附录 C.1）。

Figure 2 展示了两个基准上的差值 Δ_dev。在 SWE-bench Verified 上（Figure 2a），11 个模型留下的无谓代码显著少于开发者（GPT-6 Astra 只是勉强，CI 下界为 0.002），4 个没有显著差异（Kimi K3、Claude Haiku 4.5、GPT-6 Sol、GPT-6.1 Sol），3 个留下显著更多：Gemini 3.8、3.7 与 3.6 Flash。在 DeepSWE 上（Figure 2b），NP_code 均值为 0.797，103 个开发者补丁为 0.785；只有两个模型显著低于开发者基线，没有任何模型显著高于（平均差值 −0.005）。SWE-bench Verified 上差值的符号取决于判定器：在 O⁺ 下它从 +2.3 翻转到 −4.5 个百分点（附录 C.1）。

**发现 1。** agent 补丁比开发者的大（行数为 2.33 倍）。在测试之外，agent 改动的行数是 1.09 倍，但它们的大部分代码是必要的。在 SWE-bench Verified 上，18 个模型中有 11 个留下的无谓代码少于开发者（NP_code 均值 0.887 对 0.864），4 个无显著差异，三个 Gemini Flash 模型留下显著更多。在 DeepSWE 上，agent 与开发者持平（0.797 对 0.785），但没有模型显著高于开发者基线。平均而言，agent 补丁的代码单元中有 11% 是无谓的。

#### 5.2 RQ2：那些无谓编辑是什么？

Figure 3 展示了额外编辑的类别。在 SWE-bench Verified 上，61% 是测试文件编辑，21% 是代码，13% 是文档，5% 是注释或格式类编辑。测试编辑极其普遍（81.5% 的 agent 补丁会编辑测试文件）且不计分，评审者可能欢迎其中许多。若把它们计为无谓，会主导全单元口径的 NP，那样 NP 主要反映的只是一个模型写了多少测试。在 DeepSWE 上构成反转：任务是功能实现，每个补丁的单元数约多六倍。代码占额外编辑的 58%，测试占 26%（附录 D）。

在 SWE-bench Verified 上，3,987 个无谓代码单元之中，行为探针（在 3,559 个无谓 agent 单元上运行）显示 89% 会改变行为，例如在邻近输入上抛出或吞掉异常。其余 11% 是惰性守卫或重复检查（附录 C.1）。

我们用变异测试（Jia 和 Harman，2011；Just 等，2014）来问 agent 新增的测试是否有用。在通过我们有效性检查的 271 个 SWE-bench Verified 实例上，我们用 mutmut（Hovmöller，2026）向打过补丁的代码注入 1,962 个变异体（小型人工 bug）。agent 新增的测试抓到其中 68.1%：多于同文件内既有回归测试（45.6%），少于任务测试（77.1%）。它们抓到必要代码中 73.2% 的变异体，以及无谓代码中 31.2%。agent 的测试还能抓到任务测试漏掉的 bug。在从任务测试漏过的变异体中，22.7%（102 个）被 agent 新增或加强的测试抓到；这占全部变异体的 5.2%（附录 F.1）。多数 agent 测试写在修复之后，很少出现"先失败后通过"的运行（附录 D）。

**发现 2。** 在 SWE-bench Verified 上，代码之外，补丁主要是在加测试（61%）与文档（13%）；在 DeepSWE 上，多数额外编辑是代码（58%）。新增测试比回归测试抓到更多注入 bug（68.1% 对 45.6%），但少于任务测试（77.1%），且它们抓到了任务测试漏掉的 22.7% 的 bug，因此 agent 写的测试有助于加强基准测试套件。最后，89% 的无谓代码单元会改变行为。

#### 5.3 RQ3：无谓编辑来自哪里？

如果残留主要来自调试，它就会在调试步骤进入补丁并再也不被回退。全部残留上的合并调试占比为 ρ=0.257，但 4,898 个调试步骤残留单元中有 4,676 个是 agent 在修复之前作为回归测试写下的测试文件 hunk。就代码而言，3,987 个代码残留单元中只有 154 个（分布在 55 个补丁里）来自调试步骤，因此 ρ_code=0.039。临时脚本与调试打印几乎从不存活到已解决的补丁中。

修复步骤写下了 83% 的无谓代码，修订步骤写下 11%。在修订修复时写下的代码，其无谓率只比首次修复的代码略高（0.29 对 0.25），而且修订很少见（附录 D）。在 DeepSWE 上，在溯源精确的单元中，ρ_code 为 0.037。

**发现 3。** 调试步骤几乎不写下任何无谓代码（3,987 个单元中 154 个，ρ_code=0.039）；修复步骤写下了其中 83%，而来自修订的代码其无谓率只比首次修复代码略高（0.29 对 0.25）。

#### 5.4 RQ4：哪些模型过度编辑更多？

在 SWE-bench Verified 上的 18 个模型中，解决率与 NP_code 的 Spearman 相关为 −0.10（原始 p=0.69；95% CI [−0.28, +0.05]，按每个模型的实例做自助法）。在几乎相同的解决率下，Sonnet 5（80.6%）的 NP_code=0.922，而 Gemini 3.7 Flash（81.4%）为 0.789，因此 Gemini 3.7 Flash 每个任务留下的无谓代码单元约为对方的 3.6 倍（1.23 对 0.34）。

控制单元粒度与任务选择之后，模型效应依然存在（附录 D.4）。多单元口径与按行加权的变体保持同样的排序，任务固定效应下仍然是那三个 Gemini Flash 模型低于开发者。

在 DeepSWE 上关系反转：NP_code 与解决率负相关（Spearman −0.59，p=0.01；按任务调整后 −0.52，p=0.03），也就是说解决更多任务的模型留下更多无谓代码。模型排序在两个基准间中等一致（+0.59），而 Gemini 3.7 与 3.8 Flash 在两个基准上都偏低（Table 9）。

**发现 4。** 无谓代码的数量因模型而异。它在 SWE-bench Verified 上不随解决率变化（Spearman −0.10），即便控制了单元粒度与任务选择之后也是如此；但在 DeepSWE 上，解决率更高的模型留下更多无谓代码（−0.59）。

#### 5.5 RQ5：无谓代码能被自动移除吗？

部署时拿不到任务测试，所以我们测试三种不需要任务测试的策略（Table 1）。RQ5 的全部实验都使用 SWE-bench Verified。

**在首次全绿处停止。** 下列数字覆盖全部已解决的 SWE-bench Verified 补丁。对每条轨迹，我们找到 agent 自己测试首次全绿的那一步，重放到该步，并对补丁打分。早期补丁在 3,031 个已打分案例中仍有 2,948 个通过任务测试（97.3%），但代码单元几乎没变（7,419 到 7,269），这些补丁上的 NP_code 也只从 0.700 移动到 0.710。

**自审。** 我们要求每个模型为最终 diff 的每一个 hunk 给出理由，并丢弃它说不出理由的那些。在全部已解决的 SWE-bench Verified 补丁上（18 个模型中的 17 个；附录 D.5），被丢弃的代码 hunk 有 65.7% 的时候与 O⁺ 判为无谓的某个单元吻合，但这次自审只找到全部这类单元的 35.5%（κ=0.39）；这些丢弃弄坏了 1.8% 的已解决补丁。模型是有选择性的：它们丢掉了 40.5% 那种"去掉后行为与打完补丁一致"的无谓单元，而对"去掉后行为等于完整补丁"的那类只丢 14.7%。施加这些丢弃把 NP_code 从 0.924 提到 0.944。

**用 DRA 剪枝。** 多数 agent 会跑自己的测试，6,728 条轨迹中有 4,860 条到达了全绿。我们跑一个简化的累积式 DRA：只要 agent 的测试命令 O_agent 仍然通过，就回退该单元；我们还要求既有的 PASS_TO_PASS 测试也通过（O_agent+P2P）。这适用于 6,724 个补丁中的 2,495 个，其余没有独立测试命令或在基线检查上失败（附录 G.1）。用 O_agent+P2P 时，剪枝移除 67.3% 的无谓代码单元，接近自审召回的两倍，但精确率只有 46.3%（自审为 65.7%）。它把 NP_code 从 0.936 提到 0.975，89.1% 的补丁仍通过任务测试。只用 O_agent 时，剪枝达到 39.6% 精确率与 66.5% 召回，86.6% 的补丁仍通过任务测试。多数误删是那些实现了"既有测试与 agent 测试都未覆盖的行为"的代码单元。

**发现 5。** 在 SWE-bench Verified 上，自审与基于测试的剪枝在精确率与召回之间取舍。自审精确（65.7%）但只找到约三分之一的无谓代码（35.5%），其丢弃会弄坏 1.8% 的已解决补丁。用 agent 自己的测试加仓库回归测试剪枝，在 2,495 个合格补丁上找到约三分之二（67.3%）、精确率更低（46.3%），其中 89.1% 仍能解决。提前停止几乎不改变补丁（NP_code 从 0.700 到 0.710），因为多数无谓代码在 agent 的测试首次通过时就已经在补丁里了。

### 6 讨论与局限

#### 这个指标测的是我们声称的东西吗？

我们用开发者补丁来检验该指标。若某代码单元位于开发者补丁所触及的每个函数之外，则称其为*补丁外*单元。在 6,596 个实例的 14,591 个 agent 代码单元中，有 2,607 个是补丁外单元。DRA 的无谓标记预测补丁外单元的 AUROC 为 0.718，而单元规模为 0.478（差值 +0.24，95% CI [0.21, 0.27]）；它以 0.43 的精确率与 0.62 的召回标出 3,753 个单元。在实例层面，无谓行占比与补丁外占比的 Spearman 相关为 0.40，而编辑距离为 0.21、相对开发者补丁的行数为 0.25。该指标标出"开发者大概不会写"的代码，比补丁规模做得更好，尽管被标出的单元里不到一半是补丁外的。评审者是否真的会删掉被标出的单元，需要人工标注（附录 D）。

#### 启示

模型写下的无谓代码量，在 SWE-bench Verified 上不随其解决率变化，在 DeepSWE 上与之反相关；而且多数无谓代码会改变行为，所以评审者不能跳过它们（第 5.2、5.4 节）。由于代码必要性因模型而异，编码基准应当在报告解决率的同时报告 NP_code 并给出开发者补丁基线。与开发者补丁做规模比较时，应当把测试编辑与代码编辑分开。调试步骤写下的代码残留很少，所以在环内清理可清理的东西不多（尽管我们没有测试它），生成后清理是更有希望的目标。它的两种形式各有取舍：自审很少丢掉必要代码，但漏掉多数无谓代码；而用 agent 的测试加仓库回归测试剪枝能找到其中大部分，代价是更多误删（第 5.5 节）。由于无谓代码是在构建与修订修复的过程中写下的，我们建议给训练轨迹"去膨胀"：在监督微调之前丢掉测试不需要的单元，这与编辑感知训练（Yang 等，2026；Ke 等，2026）一致，也是 PDB 的主张（Chai 等，2026）。

#### 局限

必要性取决于判定器，在 DeepSWE 与 SWE-bench Pro 上它是无谓代码的上界（DeepSWE 上开发者基线为 0.785）。行为检查由 LLM 撰写，而判定器判为无谓的代码仍可能是想要的。单元是一次回退一个，所以"联合必要"的配对与混合块可能误导结论。我们研究的是成功轨迹（即已解决补丁）中的过度编辑，把失败轨迹中的过度编辑留给未来工作。角色标签仅对照第二位 LLM 裁判做了验证，没有人工审计（附录 B.4）。调试占比的结论建立在 3,987 个代码残留单元中的 154 个之上，变异结果覆盖 271 个实例（1,962 个变异体）。溯源需要可重放的轨迹：SWE-bench Verified 有 3.3% 的重放不精确（228 个重放不一致、6 个自检失败、5 个二进制补丁），DeepSWE 有 33.4% 的补丁（932 个中的 311 个）至少含一个无溯源单元（占单元 14.9%，占代码单元 12.7%）。主要结果使用单一执行架 Copilot CLI（其他执行架见附录 D）。SWE-bench Verified 只含 Python，且可能已被污染。

#### 未来工作

人工标注（附录 B.5）可以检验评审者是否认同该判定器。基于性质的测试（MacIver 等，2019）与 LLM 生成的差异化测试（Hu 等，2026）可以把基于探针的打分扩展到没有开发者补丁的基准上。在 OpenHands（Wang 等，2025）与 mini-SWE-agent（SWE-agent Team，2025）这类开源执行架上、使用公开轨迹（SWE-bench Team，2026）重复该实验，可以揭示执行架设计如何影响过度编辑。

### 7 结论

我们取了 7,660 条已解决的编码 agent 轨迹，把最终补丁的每个块追溯到写下它的那一步，然后用任务测试给必要性打分，并用行为探针验证无谓代码。agent 补丁比开发者的大，但在 SWE-bench Verified 上多出来的行主要是测试与文档。在代码层面，平均约 11% 的 agent 补丁代码单元是无谓的；在 SWE-bench Verified 上，18 个模型中有 11 个留下的无谓代码少于开发者，三个 Gemini Flash 模型留下更多，而在 DeepSWE 上 agent 与开发者持平。剩下来的无谓代码是在构建与修订修复时写下的，通常会改变行为，并因模型而异，在 SWE-bench Verified 上与解决率无关、在 DeepSWE 上负相关。生成之后，自审能精确地移除它但只找到约三分之一；而用 agent 自己的测试加仓库回归测试剪枝，在其适用的补丁上能找到约三分之二、精确率更低。我们建议在解决率旁边报告代码必要性，并通过模型训练与执行架层面的剪枝来应对过度编辑。

## 与路线图的挂接

- **A2-06（错误处理与重试语义）**：本文给这条知识点补了一个反直觉的数据点——"重试/调试"并不是脏补丁的主要来源。调试步骤（探索、复现、探查）只写下 3,987 个无谓代码单元中的 154 个（ρ_code=0.039），而修复步骤写下 83%。这意味着"把重试次数压下去"不会让补丁变干净，真正的改进点在修复本身如何被构造与修订。同时它把"幂等"这个要求推到了清理环节：DRA 剪枝之所以可以累积执行，前提是"回退一个单元"是一个可独立判定、可独立施加的操作——这正是 A2-06 里"副作用操作要能补偿与回退"的另一种形态。
- **A6-01（demo 到生产的三道坎）**：本文是"长尾"这一坎的量化证据。同一批模型在 SWE-bench Verified 上解决率 64.0%–89.4%，但解决率与补丁质量之间的关系在两个基准上方向相反：SWE-bench Verified 上无关（Spearman −0.10），DeepSWE 上负相关（−0.59，p=0.01）——越能解长任务的模型留下越多无谓代码。对准备上生产的团队，结论很直接：只盯解决率的验收会在长任务上系统性失守，代码必要性必须作为并列指标进回归集。另一条可用的事实是 agent 新增测试的质量：它们抓到 68.1% 的注入 bug（既有回归测试 45.6%，任务测试 77.1%），并抓到任务测试漏掉的 22.7%。
- **A4-05（副作用与人工审批）**：本文给出了"自动清理补丁"这件事的边界条件，可以直接换算成人机分工的依据。两种自动移除手段的实测代价是：自审会弄坏 1.8% 的已解决补丁（精确率 65.7%、召回 35.5%）；测试驱动剪枝精确率 46.3%、召回 67.3%，13.4% 到 10.9% 的补丁不再通过任务测试（86.6% 与 89.1% 的通过率）。也就是说，把"删代码"这种不可逆动作全自动放行，会以十分之一量级的概率破坏原本正确的修复。按 A4-05 的原则，剪枝应当输出"建议删除清单 + 复核差异"，把最终合并决策留给人；尤其因为 89% 的无谓代码会改变行为，误删的后果不是无害的。

## 三个自测问题

1. 用 O_test 给开发者补丁打分，会把 33% 的代码单元判为无谓；换用加强版 O⁺ 只判 3%。请说明这两个数字之间的差距说明了什么，以及为什么作者坚持"必须用同一把尺子给开发者打分"才能得出"agent 不比人差"的结论。如果省略这一步校准，RQ1 的结论会朝哪个方向偏？
2. agent 新增测试抓到 68.1% 的注入变异体，低于任务测试的 77.1%；但又有 22.7% 的变异体是任务测试漏掉、被 agent 测试抓到的。这两个数字如何同时成立？它对"agent 写的测试是否有价值"这个问题给出的判据是什么？
3. 三种生成后清理策略里，"首次全绿就停"几乎无效（NP_code 0.700→0.710），而"自审"与"测试剪枝"分别在精确率和召回上占优。请解释为什么提前停止无效——这与"83% 的无谓代码由修复步骤写下"这一发现是什么关系？如果你只能选一种上线，你会选哪个，接受什么代价？
