## 为什么今天读这篇

因为这篇是"上下文工程"这个词从行业黑话变成工程学科的那道分界线：在此之前，大家讨论的是"怎么把提示写好"；在此之后，讨论的是"整个上下文状态怎么管"。它给出的不是一个技巧清单，而是一条可以拿去做架构评审的判据——**上下文是有限资源，好的上下文工程是找到那组尽可能小的高信号 token**。对要做 Agent 架构决策的人，这条判据能直接回答三个问题：系统提示该写到多"高"、工具集该收敛到什么粒度、长任务该用压缩还是外部化。更关键的是，它把 context rot、n² 注意力、按需检索、压缩、笔记、子智能体这几件看似无关的事，串成了同一条"注意力预算"账本。

## 三句话摘要

1. 上下文工程是提示工程的演进：它管的不只是提示词，而是推理时进入上下文窗口的全部 token（系统指令、工具、MCP、外部数据、消息历史）。
2. 因为 transformer 的注意力是 n 个 token 产生 n² 个两两关系，上下文越长、注意力越被摊薄，"上下文腐烂"是所有模型的共性，因此上下文必须当作有限预算来花。
3. 长时程任务靠三根杠杆绕开窗口限制——压缩、结构化笔记、子智能体架构——它们的共同目标都是只让高信号 token 进入注意力预算。

## 译文

### 上下文工程 vs. 提示工程

在 Anthropic，我们把上下文工程视为提示工程的自然演进。提示工程指的是撰写和组织 LLM 指令以取得最优结果的方法（关于概览与实用的提示工程策略，见[我们的文档](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)）。**上下文工程**指的是在 LLM 推理过程中，策展并维护最优 token 集合（信息）的一整套策略，其中也包括提示之外可能落入上下文的其它一切信息。

在早期用 LLM 做工程时，写提示是 AI 工程工作中最大的一块，因为日常聊天互动之外的大多数用例，都需要针对一次性分类或文本生成任务优化过的提示。顾名思义，提示工程的主要关注点是"如何写出有效的提示"，尤其是系统提示。然而，当我们走向构建能力更强的 agent——它们在多轮推理和更长的时间尺度上运行——我们就需要管理整个上下文状态的策略（系统指令、工具、[Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro)（MCP）、外部数据、消息历史等等）。

一个在循环中运行的 agent 会产生越来越多*可能*与下一轮推理相关的数据，而这些信息必须被循环地精炼。上下文工程是[一门艺术与科学](https://x.com/karpathy/status/1937902205765607626?lang=en)：从那个不断膨胀的可能信息宇宙中，策展哪些内容将进入有限的上下文窗口。

与"写提示"这种离散任务不同，上下文工程是迭代的——每当我们决定要传给模型什么，策展阶段就发生一次。

### 为什么上下文工程对构建高能力 agent 至关重要

尽管 LLM 速度快、能处理越来越大的数据量，但我们观察到，它们和人类一样，会在某个点上失去焦点或陷入混乱。针对"大海捞针"式基准的研究揭示出[上下文腐烂](https://research.trychroma.com/context-rot)（context rot）这一概念：随着上下文窗口中 token 数量增加，模型从该上下文中准确召回信息的能力会下降。

有些模型的退化比另一些更平缓，但这一特性在所有模型上都会出现。因此，上下文必须被视为一种有限资源，其边际收益递减。人类的工作记忆容量有限，LLM 同样有一个"注意力预算"，在解析大量上下文时从中支取。每引入一个新 token，都会消耗掉这份预算的一部分，这就更要求我们仔细策展提供给 LLM 的 token。

这种注意力稀缺源于 LLM 的架构约束。LLM 基于 [transformer 架构](https://arxiv.org/abs/1706.03762)，该架构让每个 token 都能在整段上下文上[注意](https://huggingface.co/blog/Esmail-AGumaan/attention-is-all-you-need)到其它每一个 token。于是 n 个 token 就产生了 n² 个两两关系。

随着上下文长度增加，模型捕捉这些两两关系的能力会被摊薄，从而在上下文规模与注意力焦点之间形成一种天然张力。此外，模型的注意力模式是从训练数据分布中学来的，而训练数据中短序列通常比长序列更常见。这意味着模型对跨上下文的依赖关系经验更少，专门用于此的参数也更少。

像[位置编码插值](https://arxiv.org/pdf/2306.15595)这样的技术，可以让模型通过把更长序列适配到最初训练的较小上下文来处理它们，但代价是对 token 位置的理解有所退化。这些因素造成的是一条性能渐变带，而不是一道断崖：模型在更长的上下文上仍然很有能力，但相比在较短上下文上的表现，其在信息检索和长程推理上的精度可能下降。

这些现实意味着，要构建高能力 agent，深思熟虑的上下文工程是必不可少的。

### 有效上下文的解剖学

既然 LLM 受限于有限的注意力预算，那么*好的*上下文工程就意味着：找到*尽可能小*的一组高信号 token，使某个期望结果出现的概率最大化。落实这条实践远比说起来难，下面我们按上下文的各个组成部分，讲清这条指导原则在实践中意味着什么。

**系统提示**应当极其清晰，用简单直接的语言，把想法呈现在对 agent 而言*恰当的高度*上。所谓恰当的高度，是两种常见失败模式之间的"金发姑娘区"。一端是工程师在提示里硬编码复杂而脆弱的逻辑，以引出精确的 agent 行为——这种做法造成脆弱性，并随着时间推移增加维护复杂度。另一端是工程师给出含糊的高层指导，既没能给 LLM 提供关于期望输出的具体信号，又错误地假设了共享上下文。最优的高度是一种平衡：具体到足以有效引导行为，又灵活到能为模型提供引导行为的强力启发式。

在光谱的一端，我们看到脆弱的 if-else 硬编码提示；在另一端，我们看到过度笼统、或错误假设共享上下文的提示。

我们建议把提示组织成明确的段落（如 `&lt;background_information&gt;`、`&lt;instructions&gt;`、`## Tool guidance`、`## Output description` 等），并用 XML 标签或 Markdown 标题这类手法来划分这些段落——尽管随着模型能力提升，提示的确切格式大概正变得不那么重要。

无论你决定如何组织系统提示，都应当力求用最小的信息集合完整勾勒出期望的行为。（注意，"最小"并不必然等于"简短"；你仍然需要在一开始就给 agent 足够的信息，确保它遵守期望行为。）最好的做法是：先用可用的最强模型测试一份最小提示，看它在你的任务上表现如何，然后针对初始测试中发现的失败模式，补充清晰的指令和示例来提升表现。

**工具**让 agent 能与其环境交互，并在工作过程中拉入新的、额外的上下文。因为工具定义了 agent 与其信息/行动空间之间的契约，所以工具必须促进效率——既要返回 token 高效的信息，也要鼓励高效的 agent 行为，这极其重要。

在《Writing tools for AI agents – with AI agents》一文中，我们讨论过如何构建能被 LLM 良好理解、且功能重叠极少的工具。就像设计良好的代码库中的函数一样，工具应当是自包含的、对错误鲁棒的，并且在预期用途上极其清晰。输入参数同样应当具有描述性、无歧义，并发挥模型的固有优势。

我们见到的最常见失败模式之一，是工具集臃肿——覆盖了过多功能，或导致"该用哪个工具"的决策点变得模糊。如果一位人类工程师都无法明确说出某个场景该用哪个工具，就不能指望 AI agent 做得更好。正如我们稍后会谈到的，为 agent 策展一套最小可行的工具集，也能在长交互中带来更可靠的上下文维护与剪枝。

提供示例，也就是所谓的少样本提示（few-shot prompting），是一项众所周知的最佳实践，我们继续强烈推荐。然而，团队常常把一长串边缘情况塞进提示，试图把 LLM 在某项任务上应当遵循的每一条可能规则都讲清楚。我们不建议这样做。我们建议的是：努力策展一组多样、典型的示例，有效地呈现 agent 的期望行为。对 LLM 来说，示例就是"一图胜千言"里的那张图。

我们在上下文各组成部分（系统提示、工具、示例、消息历史等）上的总体指导是：用心思考，让上下文既有信息量，又保持紧致。接下来，我们深入看在运行时动态检索上下文。

### 上下文检索与 agentic 搜索

在《Building effective AI agents》中，我们强调过基于 LLM 的工作流与 agent 之间的区别。自那篇文章以来，我们逐渐倾向于一个[简单的](https://simonwillison.net/2025/Sep/18/agents/) agent 定义：LLM 在循环中自主使用工具。

在与客户并肩工作中，我们看到这个领域正收敛到这个简单范式上。随着底层模型能力增强，agent 的自主程度也可以随之扩展：更聪明的模型让 agent 能独立地在微妙的问题空间中导航，并从错误中恢复。

我们现在正看到工程师设计 agent 上下文方式的转变。今天，许多 AI 原生应用采用某种基于嵌入的推理前检索，把重要上下文呈现给 agent 供其推理。随着领域转向更 agentic 的做法，我们越来越多地看到团队用"按需即时"（just in time）的上下文策略来增强这些检索系统。

与其预先处理所有相关数据，采用"按需即时"方式构建的 agent 会维护轻量级的标识符（文件路径、存储的查询、网页链接等），并在运行时用工具通过这些引用把数据动态载入上下文。Anthropic 的 agentic 编码方案 [Claude Code](https://www.anthropic.com/claude-code) 就用这种方式在大型数据库上做复杂数据分析。模型可以写针对性查询、存储结果，并借助 `head`、`tail` 这类 Bash 命令分析海量数据，而完全不必把完整的数据对象载入上下文。这种方式与人类认知相仿：我们一般不会把全部信息语料背下来，而是引入外部组织和索引系统，比如文件系统、收件箱和书签，按需取回相关信息。

除了存储效率，这些引用的元数据还提供了一种高效精炼行为的机制——无论这些元数据是显式提供的，还是直觉可得的。对于一个在文件系统中工作的 agent，`tests` 文件夹里存在一个名为 `test_utils.py` 的文件，与 `src/core_logic/` 下的同名文件所暗示的用途是不同的。文件夹层级、命名约定和时间戳，都提供了帮助人类和 agent 理解"如何、何时使用某条信息"的重要信号。

让 agent 自主导航和检索数据还实现了渐进式披露（progressive disclosure）——换句话说，让 agent 通过探索逐步发现相关上下文。每一次交互都产出为下一次决策提供依据的上下文：文件大小暗示复杂度；命名约定提示用途；时间戳可以作为相关性的代理指标。agent 可以一层层地搭建理解，只把必要的东西留在工作记忆中，并借助记笔记策略获得额外的持久化。这种自管理的上下文窗口让 agent 专注于相关子集，而不是淹没在详尽但可能无关的信息里。

当然，这里有权衡：运行时探索比检索预先算好的数据更慢。不仅如此，还需要有主见、经过深思的工程，才能确保 LLM 拥有合适的工具和启发式，以有效导航它的信息地形。缺乏恰当的引导，agent 可能会误用工具、追入死胡同，或未能识别关键信息，从而浪费上下文。

在某些场景下，最高效的 agent 可能采用混合策略：为了速度预先取回一部分数据，同时自行酌情开展进一步的自主探索。所谓"正确"的自主程度，其决策边界取决于任务。Claude Code 就是采用这种混合模式的 agent：`CLAUDE.md` 文件被直接放进上下文，而 `glob`、`grep` 这类原语让它能导航环境、按需即时取回文件，从而有效绕开索引陈旧和复杂语法树带来的问题。

对于内容动态性不那么强的场景，比如法律或金融工作，混合策略可能更合适。随着模型能力提升，agentic 设计将趋向于让智能模型智能地行动，人类策展的成分逐步减少。考虑到这个领域的进展之快，"做能跑通的最简单的事"很可能仍是给基于 Claude 构建 agent 的团队的最佳建议。

#### 长时程任务的上下文工程

长时程任务要求 agent 在 token 数量超过 LLM 上下文窗口的一系列动作上，保持连贯性、上下文和目标导向行为。对于持续几十分钟到多个小时的工作（例如大型代码库迁移，或综合性研究项目），agent 需要专门的技术来绕开上下文窗口大小的限制。

等待更大的上下文窗口看起来像是个显而易见的策略。但很有可能，在可预见的未来，各种规模的上下文窗口都会受制于上下文污染与信息相关性问题——至少在那些追求最强 agent 表现的情形下如此。为了让 agent 能在延长的时间尺度上有效工作，我们发展出几种直接针对这些上下文污染约束的技术：压缩、结构化笔记，以及多智能体架构。

##### 压缩（Compaction）

压缩是指：当对话接近上下文窗口上限时，对其内容做摘要，并用摘要重新开启一个新的上下文窗口。压缩通常充当上下文工程中的第一根杠杆，用以驱动更好的长期连贯性。压缩的核心，是以高保真方式蒸馏一个上下文窗口的内容，使 agent 能在性能退化最小的前提下继续。

以 Claude Code 为例，我们这样实现：把消息历史交给模型，让它摘要并压缩最关键的信息。模型保留架构决策、未解决的 bug 和实现细节，同时丢弃冗余的工具输出或消息。随后 agent 可以带着这段压缩后的上下文，加上最近访问的五个文件，继续工作。用户因此获得连续性，而不必担心上下文窗口的限制。

压缩的艺术在于取舍：保留什么、丢弃什么。因为过度激进的压缩可能导致丢失那些微妙但关键的上下文——它们的重要性要等到后来才显现。对实现压缩系统的工程师，我们建议在复杂的 agent 轨迹上仔细调优你的提示。先从最大化召回开始，确保压缩提示能捕获轨迹中每一条相关信息，然后通过剔除多余内容来迭代提升精确度。

一个容易识别的多余内容例子，是清理工具调用和结果：一旦某个工具在消息历史深处被调用过，agent 为什么还需要再看到原始结果呢？最安全、最轻手的一类压缩就是工具结果清理，这也是最近在 [Claude 开发者平台](https://www.anthropic.com/news/context-management)上线的一项功能。

##### 结构化笔记

结构化笔记，或称 agentic 记忆，是一种让 agent 定期把笔记持久化到上下文窗口之外的内存中的技术。这些笔记会在之后被拉回上下文窗口。

这种策略以极小的开销提供了持久记忆。就像 Claude Code 创建待办清单，或你的自定义 agent 维护一个 `NOTES.md` 文件——这个简单的模式让 agent 能在复杂任务中跟踪进度，维护那些否则会在几十次工具调用中丢失的关键上下文与依赖关系。

[Claude 玩《宝可梦》](https://www.twitch.tv/claudeplayspokemon)展示了记忆如何在非编码领域改变 agent 的能力。这个 agent 在数千个游戏步骤中维护精确的计数——追踪诸如"在过去 1,234 步里，我一直在 1 号道路训练宝可梦，皮卡丘已升了 8 级，目标是升 10 级"这样的目标。在没有任何关于记忆结构的提示下，它会绘制已探索区域的地图、记住自己解锁了哪些关键成就，并维护战斗策略笔记，帮它学会哪种招式对不同对手最有效。

在上下文重置之后，agent 会读取自己的笔记，继续数小时长的训练序列或地牢探索。这种跨摘要步骤的连贯性，使得仅靠把全部信息留在 LLM 上下文窗口里不可能实现的长时程策略成为可能。

作为我们 [Sonnet 4.5 发布](https://www.anthropic.com/effective-context-engineering-for-ai-agents)的一部分，我们在 Claude 开发者平台上公测了[一个记忆工具](http://anthropic.com/news/context-management)，它通过基于文件的系统，让在上下文窗口之外存储和查阅信息变得更容易。这使 agent 能随着时间积累知识库、跨会话维护项目状态、引用此前的工作，而不必把所有东西都留在上下文里。

##### 子智能体架构

子智能体架构提供了另一种绕开上下文限制的方式。与其让一个 agent 试图在整个项目上维护状态，不如让专门的子智能体以干净的上下文窗口处理聚焦的任务。主智能体以高层计划进行协调，子智能体则执行深度技术工作，或用工具寻找相关信息。每个子智能体可能大量探索，用掉数万 token 甚至更多，但只返回一份浓缩、蒸馏后的工作总结（通常是 1,000–2,000 token）。

这种方式实现了清晰的关注点分离——详细的检索上下文被隔离在子智能体内部，而主智能体专注于综合与分析结果。这个模式在[《How we built our multi-agent research system》](https://www.anthropic.com/engineering/multi-agent-research-system)中讨论过，在复杂研究任务上相比单智能体系统展现出实质性提升。

在这些方式之间如何选择，取决于任务特征。例如：

- 压缩适用于需要大量来回交互的任务，因为它维持了对话的流动；
- 笔记适用于有清晰里程碑的迭代式开发；
- 多智能体架构适用于复杂的研究与分析，因为并行探索在这里能带来收益。

即便模型持续变强，"在延长的交互中维持连贯性"这一挑战，仍将是构建更有效 agent 的核心。

### 结语

上下文工程代表了我们在用 LLM 构建系统时的一次根本转变。随着模型能力增强，挑战不只是打磨一份完美的提示——而是在每一步用心策展哪些信息进入模型有限的注意力预算。无论你是在为长时程任务实现压缩、设计 token 高效的工具，还是让 agent 按需即时地探索环境，指导原则始终不变：找到那组尽可能小的高信号 token，使期望结果出现的概率最大化。

我们概述的这些技术会随着模型改进继续演化。我们已经看到，更聪明的模型需要的规范性工程更少，允许 agent 以更高的自主性运行。但即便能力规模扩展，把上下文视为珍贵而有限的资源，仍将是构建可靠、有效 agent 的核心。

今天就在 Claude 开发者平台上开始实践上下文工程，并通过我们的[记忆与上下文管理](https://platform.claude.com/cookbook/tool-use-memory-cookbook) cookbook 获取实用技巧与最佳实践。

## 与路线图的挂接

- **A1-02（Token 经济学与上下文窗口的物理限制）**：本文给出了这条知识点最底层的物理解释——注意力不是无限画布，而是 n 个 token 对应 n² 个两两关系的预算。凡是"把窗口开大一点就行"的架构判断，在这里都要被证伪：位置编码插值只带来"性能渐变带"而非消除退化。做容量规划时，上下文长度应当按"精度衰减后的有效长度"算，而不是按标称窗口算。
- **A2-04（上下文工程：压缩、摘要、卸载）**：本文就是这条知识点的原始出处。它把压缩（compaction）拆成可执行的工程动作：保留架构决策、未解决的 bug、实现细节，丢弃冗余工具输出；并给出调优顺序——先最大化召回，再迭代提升精确度。同时明确了"工具结果清理"是最轻手的第一刀。
- **A3-02（短期记忆与上下文装配）**：文中"每一轮都是重新策展一次视图"的判断，正是上下文装配的语义。结构化笔记（`NOTES.md`）、渐进式披露、按需即时检索三者合起来说明：装配不是"追加历史"，而是"决定这一轮该看见什么"——写入外部存储的东西，只有在被拉回窗口时才真正进入模型的世界。
- **A2-05（工具接口设计）**：本文对工具集臃肿的诊断值得单列——如果人类工程师都说不清某个场景该用哪个工具，agent 只会更糟。最小可行工具集既是成功率问题，也是长交互中上下文可维护性的前提。

1. 如果你的 agent 在长会话后段开始"忘事"，你凭什么判断根因是上下文腐烂，而不是检索没命中或工具返回太啰嗦？请给出一个能区分三者的观测方案。
