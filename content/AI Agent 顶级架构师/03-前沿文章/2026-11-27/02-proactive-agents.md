## 为什么今天读这篇

这是一篇少见的、由真正在跑内部智能体的团队写出来的"形态选择 + 记忆设计 + 评审体验"三联文章：它的主角不是模型能力，而是后台自治形态下绕不开的两个工程约束——记忆怎么长出来、人怎么被消耗。对做架构决策的人来说，它给出了三个可以直接搬走的判断：主动性智能体的触发源只有三类（现实事件、开发者调度、智能体自建调度），记忆必须按"种子/反馈/结果"三种信号分时间轴设计，而每一次主动找你确认，本质是在花掉你有限的注意力预算。更实际的是它给出了可测量的指标——草稿多久被批准、发出的邮件回复率、"找你确认的事情里你真正动手的比例"——这些是把"体验"翻译成架构验收标准的样本。如果你正准备把一个 chat 形态的智能体推向后台上百次无人值守运行，这篇文章基本就是变更清单。

## 三句话摘要

1. 主动性智能体不再等你敲提示词，而是被三类事件唤醒：现实世界事件、开发者设定的调度、以及智能体自己创建的调度——在 LangChain 的内部实践里，Managed Deep Agents 上超过 70% 的运行已经来自调度而非人工临时提示。
2. 记忆决定它值不值得被信任：种子（过去）、反馈（现在）、结果（未来）三类信号各自入场；真正的难点不是"存"，而是显著性、过期与重复这三件事，很多团队用"做梦"这种定时后台作业来整理。
3. 每一次主动确认都在消耗人的注意力，所以 UX 是架构问题不是皮肤问题：要高信噪比、要便于快速评审（因为评审就是反馈写回记忆的通道）、要出现在人本来就在的地方。

## 译文

想想你是怎么带一个新人的。第一周，你给他小而边界清晰的任务，比如分诊一个 bug 报告，或者更新一篇文档。很快你开始给他更大的任务，最后你把一个宏大的目标交给他，让他自己想怎么啃下来。他仍然会带着澄清性的问题和评审请求来找你，只是频率会随时间下降。

智能体已经好到可以用同样的方式上手了，而且就像一个好新人，它们正在变成主动的问题解决者。像 Muse、Instinct 和 OpenAI 的 [dots](https://learn.chatgpt.com/docs/dots) 这类个人智能体，让主动性智能体流行了起来——它们在后台运行，朝更大的目标推进，而不是等着一个提示词。[Hone](https://hone.com/blog/introducing-engines/) 说得最直接，把它家的 Engines 描述为"被指派目标，而不是被指派任务"的 AI。目标是让这些智能体去接那些要跑几天甚至几周、更硬的问题。

主动性智能体在你没说清想要什么、或者在东西发出去之前需要你签字的时候，仍然会来找你确认。当下属真的把活干得很好时，你可能会发现自己成了瓶颈——智能体这边也一样。随着它们接下更多目标，你的注意力就成了稀缺资源。我们认为，要造出能把这份资源用好的主动性智能体，有两件事是必需的：记忆和 UX。

### 主动性智能体

主动性智能体响应它所处环境中的事件，这些事件来自三个地方：

- **现实世界事件**，比如一封新邮件，或者一个新开的 pull request。
- **开发者设定的调度**，比如每晚跑一次、用来更新智能体记忆的作业，或者每周扫一遍积压 pull request 的巡检。
- **智能体自己设定的调度**，比如提醒自己明天跟进某个讨论串，或者用户点名要的每日简报。

本文里的例子都来自我们在 LangChain [内部](https://www.langchain.com/blog/components-building-company-harness)运行的两个主动性智能体：

- [**GTM Agent**](https://www.langchain.com/blog/how-we-built-langchains-gtm-agent)，我们的销售智能体，盯着新的线索和回复，发每日简报，起草对外邮件。
- [**Robin**](https://www.langchain.com/blog/open-swe-an-open-source-framework-for-internal-coding-agents)（前身是 Open SWE），我们的工程智能体，起草 pull request，并评审每一个新提交的 pull request。

这两个智能体三种触发方式都在用。举几个例子：Robin 的评审由现实世界事件触发，也就是一个新开的 pull request；GTM Agent 的每日简报跑在它自己创建的一个[调度](https://docs.langchain.com/langsmith/python/managed-deep-agents-schedules)上——用户提出要之后，它自己把这件事排进了日程。两个智能体我们都建在 [Managed Deep Agents](https://docs.langchain.com/langsmith/python/managed-deep-agents-overview) 上，目前其中超过 70% 的运行[来自调度](https://www.langchain.com/blog/proactive-agents)，而不是来自人临时敲的提示词。

主动性智能体自己决定什么时候来找你，而每一次找你确认都要花掉你一点注意力。它必须主动，但又不能[烦人](https://www.langchain.com/blog/context-engineering-challenges-late-2026)。对于一个替你盯收件箱的行政助理智能体来说，这意味着：老板发来的、关于明天发布的那封邮件要标出来，而每一份 newsletter 都不能标。只有当它知道什么对你重要时，才能把这两类分开，而这份知识来自**记忆**。

### 记忆让智能体随时间变强

记忆是智能体随时间学到的东西。当一个主动性智能体被一个调度或一个事件唤醒时，并没有你敲的提示词告诉它你想要什么。它可以通过连接器（比如你的收件箱、日历）拉进新鲜的上下文，但关于你偏好的那些认知，来自记忆。记忆也是它把活干得越来越好的方式，而这份活里很大一部分，就是判断什么事值得来打扰你。

#### 记忆从哪里来

智能体的记忆来自三类信号，每一类对应一个不同的时间点。下面继续用行政助理作为贯穿的例子。它的目标是让你的收件箱保持可控，所以新邮件进来时，它起草回复，并标出需要你亲自看的邮件。

- **种子（过去）**：先例与既有的上下文。你可以在第一次运行之前就灌入记忆，比如从"已发送"文件夹灌，这样助理一开始就知道你怎么写东西、你和谁共事。
- **反馈（现在）**：你对智能体所提方案的反应。当你改写了它起草的内容，或者给出理由把它打回，它对"你的笔调"就多懂一点。
- **结果（未来）**：智能体行动之后发生了什么。它起草的邮件收到了回复，它就学到什么样的写法有效。

#### 维护记忆很难

存记忆是容易的那一半，因为记忆常常[简单到就是一个文件](https://www.langchain.com/blog/how-we-built-agent-builders-memory)。难的是让它随着体量增长仍然有用，因为智能体会照着它记住的东西行动。有三个问题会冒出来：

- **显著性**：判断什么值得存，以及每条信息有多重要。
- **过期**：知道信息什么时候失效，比如一个已经过去了的上线日期。
- **重复**：把新信息并进已经存下的内容，而不是再存一份副本、日后跟第一份自相矛盾。

很多主动性智能体用"做梦"来处理这件事：一个按调度跑的后台作业，在下一轮运行之前，把智能体近期的轨迹读一遍并[更新它的记忆](https://www.anthropic.com/research/components-of-agent-memory)。

另一件难事是判断记忆到底有没有帮上忙。一个办法是挑出"一套设计良好的记忆系统本来就应该改善"的那些结果，然后持续跟踪它们。对行政助理来说，可以是它的草稿要多久才被批准，或者它发出去的邮件有多少收到回复。对任何主动性智能体来说，"它来找你确认的事情里，你真正动手处理过的比例"也值得盯着。

#### 记忆换来自主权

最好的新人都是"可教练"的。他们对反馈接受得快，学习曲线爬得陡，所以很快就不再重复你已经纠正过的错误。曾有一位导师跟我说，判断一个员工的价值，可以看他能从你手上接走多少重要工作。

智能体是同样的道理，而记忆正是建立信任的东西。一个记得你反馈的智能体不再犯同样的错，这为它换来更多自主权，也让它在没有你参与的情况下更有用。对行政助理来说，这可能意味着：当它提议的会议时间你已经不再改动，就可以让它自己去订会议了。

### 主动性智能体的 UX 设计

主动性智能体会在你没要求的时候主动找你，通常是要你回答一个问题，或者批准一个动作。它怎么把这些呈现出来，决定了你是搭理它，还是把它静音。对我们内部的智能体来说，有三件事最要紧。

#### 高信噪比

智能体只应该把有价值的东西摆到你面前。来了一封新邮件，并不等于智能体就该对它做点什么。GTM Agent 的评审界面把对话分成三类：在等你的、需要起草回复的、完全不用回的。

Slack 讨论串需要同样的判断。在你正跟同事说话时，一个智能体不打招呼就插进来，很烦人，所以在 Robin 上我们用 [Jev](https://x.com/sydneyrunkle/status/2120930714799804858) 作为"该不该加入对话"的决策模型。这让 Robin 可以旁观对话，在有东西可补的时候才参与，而不是硬挤进来，或者只在有人记得 @ 它的时候才动。

#### 为评审而设计

每一次找你确认都应该能快速评审完，因为评审正是你的反馈回到记忆里的通道。正是靠这份反馈，智能体才学到你的品味和判断力；在做开放式工作时，这往往是它能拿到的最重要的上下文，而这类东西几乎不会被写在任何地方。一个你愿意与之共事的智能体，也能拿到更多这样的反馈。[Goal Engineering](https://www.langchain.com/blog/goal-engineering) 讲的是同一件事：

> 你会希望把智能体的目标对齐到"人最容易评审"的形态上。这样你才能做出让人愉悦的评审 UX，尽可能多地提取信息，并让智能体持续学习，从而随着时间推移越来越有用、越来越自主。

#### 在你本来就在的地方

我们的智能体住在 [Slack](https://docs.langchain.com/langsmith/python/managed-deep-agents-channels-slack) 里：你可以私聊它，或者在频道里 @ 它，同事也能看到别人是怎么用它的。按调度跑的工作也出现在那儿。一旦你在某个讨论串里唤起过某个智能体，它就能自己安排后续跟进，并把报告发回那个讨论串。GTM Agent 的每日简报是一条 Slack 消息，就发在你本来正在进行的对话旁边，而不是塞进一个你还得记得去打开的面板里。这些消息我们写得很短，方便一口气读完。

Robin 也一样：先给一句到两句话的标题，细节放在讨论串的回复里，这样你一眼就能看出这件事要不要你介入。Robin 开一个 pull request 时，会在 Slack 里请求评审，带一行摘要、改动规模，以及一个"我来认领"的按钮。

### 主动性智能体时代

过去三年，做智能体一直是一门上下文工程的功课：在对的时间、为对的任务，把对的上下文交给模型。别误会：面向模型的上下文工程依然重要。但现在我们还有别的、同样好玩的难题。

在主动性智能体这个时代，摆在我们面前的新挑战，是把同一套纪律用在人身上：为了目标，在对的时间、以对的格式，把对的上下文给你。人的上下文窗口同样是有限的，能给出的时间和注意力就那么多。当记忆和 UX 配合起来，智能体来找你的次数会随时间变少、每次却更准，就像一个可教练的新人那样。

今天就可以用 [Managed Deep Agents](https://docs.langchain.com/langsmith/python/managed-deep-agents-quickstart) 搭主动性智能体，它支持[调度](https://docs.langchain.com/langsmith/python/managed-deep-agents-schedules)、[记忆](https://docs.langchain.com/langsmith/python/managed-deep-agents-memory)和[异步子智能体](https://docs.langchain.com/langsmith/python/managed-deep-agents-subagents)。如果想直接在开源执行架上搭，可以从 [Deep Agents](https://www.langchain.com/deep-agents) 里的[记忆](https://docs.langchain.com/oss/python/deepagents/memory)和[异步子智能体](https://docs.langchain.com/oss/python/deepagents/async-subagents)入手，这两者在 [JavaScript](https://docs.langchain.com/oss/javascript/deepagents/memory) 里的用法完全一样。

## 与路线图的挂接

- **A0-03 四种形态**：这篇文章是"后台自治"这一形态的一手案例。形态一旦从 copilot 推向后台自治，人机接口就从"提问—回答"变成"事件唤醒—主动找人确认"，失败代价也从"答错一次"变成"错误地在无人值守时反复行动"。文中三类触发源（现实事件 / 开发者调度 / 智能体自建调度）本质上是在给自治系统划定"谁有权启动一次运行"，而"超过 70% 运行来自调度"这个数字说明：调度权一旦交给智能体，审批点必须重新设计。
- **A3-01 记忆分层**：文中把记忆按时间轴切成种子（过去的先例）、反馈（当下的纠正）、结果（行动之后的反馈回路）三类信号，正好对应情景记忆与语义记忆的不同写入时机；"做梦"这种定时整理作业，本质是把情景层沉淀为语义层的批处理管道——分层不是分类学，而是决定"哪一层允许自动写入"。
- **A3-03 长期记忆写入与遗忘**：显著性、过期、重复这三个问题，就是长期记忆写入策略的三条硬约束：什么值得写、什么时候删、新事实怎么合并旧事实。"草稿多久被批准""发出邮件回复率""找你确认的事情你真正动手的比例"则是把记忆质量变成可测量指标的少见尝试——没有这类指标，记忆系统只能靠感觉调。

## 三个自测问题

1. 你手上这个智能体，如果改成后台自治形态，三类触发源里哪些应该交给它自己设定？哪些必须留在开发者手里？给出判断标准，而不是清单。
2. 你的长期记忆现在有没有"过期"机制？举一个已经失效但仍在影响决策的记忆条目，说明它当初为什么会被写进去。
3. "找你确认的事情里你真正动手的比例"这个指标，在你这套系统上大概是多少？如果偏低，问题更可能出在信噪比、评审体验，还是记忆压根不够准？
