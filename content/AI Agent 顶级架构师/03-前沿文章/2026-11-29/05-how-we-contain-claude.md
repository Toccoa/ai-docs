## 为什么今天读这篇

这是目前少见的、由一线厂商写出的"围栏（containment）工程实录"，它的价值不在于给出一个方案，而在于诚实地列出四种"我们以为防住了、结果没防住"的失败。对做 Agent 架构决策的人，有三条可以直接落到设计里。第一，文章把风险拆成三段（用户滥用、模型失当行为、外部攻击者）和三层防御（环境、模型、外部内容），并且明确说**模型层的防御永远不可能 100% 有效，所以不能单独成立**——这句话应该写进每一个 Agent 设计文档。第二，它给出一个反直觉的观察：审批疲劳是有数据的，Claude Code 用户的权限提示通过率约为 93%，而"人在环里"在用户不是开发者时会彻底失效——于是 Claude Cowork 干脆改用整机 VM，让用户在架构上就不需要判断 bash 命令。第三，它记录了两个最难的案例：数据从**被允许的域名**流出去（api.anthropic.com 在白名单里，于是攻击者用它上传文件），以及直接提示注入（指令来自用户本人，模型层没有任何异常可抓）——这两条基本定义了今天 Agent 安全的真实边界。

## 三句话摘要

1. 围栏的对象是"爆炸半径"而非"失败概率"：随着能力与权限扩张，失败概率在下降而理论爆炸半径在增长，因此工程问题变成"如何给爆炸半径设上限"，而在环境层设硬边界是最可靠的手段。
2. 三种产品对应三种隔离模式：claude.ai 用临时容器（gVisor，服务端、无持久文件系统）、Claude Code 用"人在环里 + 操作系统沙箱"（Seatbelt / bubblewrap，写限制在工作区内、默认禁网，权限提示减少 84%）、Claude Cowork 用本地整机 VM（用户只挂载一个工作区文件夹，凭据留在宿主钥匙串）。
3. 最有效的原则是把白名单当"能力授予"而不是"目的地过滤"：允许 api.anthropic.com 就等于允许向任意 Anthropic 账户上传文件；修法是在 VM 内做防御性中间人代理，只放行携带本 VM 会话令牌的请求，并拦掉可触发服务端抓取的头部。

## 译文

### 三类风险，三层防御

十二个月前，如果有人提出给 Claude 足够权限、让它能拿下 Anthropic 的一个内部服务，我们会当场否决。今天这种级别的访问已是常态，Anthropic 的开发者因此更有生产力。这类部署的风险有两个组成部分：失败有多可能发生，以及一次失败能造成多大破坏。安全措施与模型训练方面的进展持续压低前者；后者——理论上的爆炸半径（blast radius）——只会随能力与访问权限的扩张而增长。然而当智能体能够完成曾经需要一个人、甚至一个团队才能完成的工作时，*不*部署的代价会大到让风险–收益计算大幅偏向采用，只要产品能被做得安全。工程问题于是变成：如何给爆炸半径设上限。

当能够对自主智能体的相对损害设界时——例如通过控制其环境——高效用能力就可以成为部署的理由。Claude Mythos Preview 就是一个例子：2026 年 4 月，它的爆炸半径被认为过高而不宜发布。不过我们预计，随着防御方加固关键系统、安全措施成熟，具备相似能力水平的模型更广泛地发布将变得合适——尽管总会有一些风险残留。模型能力是智能体部署总风险中的一个重要因素。

做到这一点大致有两种方式。

第一种是通过人在环里（human-in-the-loop）监督智能体的行为。Claude Code 早期通过在每一轮向用户请求许可，来防止智能体采取非预期动作。理论上这行得通，但我们发现这种方法并不可靠。我们的遥测显示，用户批准了大约 93% 的权限提示。用户看到的审批越多，对每一个投入的注意力就越少，久而久之监督就远没有那么勤勉。我们最近构建了 Claude Code 的 auto 模式，它[自动化更安全的审批](https://www.anthropic.com/engineering/claude-code-auto-mode)以减少这种审批疲劳。但漏洞仍然存在——任何概率性防御都有非零的漏检率。[1]

给爆炸半径设上限的第二种方式——也是本文大部分篇幅的重点——是围栏（containment）。我们不去监督智能体做什么，而是监督它*能够*做什么：通过沙箱、虚拟机、出口控制（egress control）等手段强制实施访问边界。这正是 Anthropic 工程投入最多的地方，也是许多最出人意料的安全失败发生的地方。

过去两年，我们发布了三个主要的智能体产品：[claude.ai](http://claude.ai)、Claude Code 与 Claude Cowork。它们各自服务不同的用户群，需要不同的围栏架构。本文分享哪些做法经受住了考验、哪些出了问题，以及我们一路上对智能体安全学到了什么。

### 三类风险，三层防御

智能体面临的安全风险可归入三类之一：

**用户滥用（User misuse）：** 用户——无论是恶意还是疏忽——指示智能体做有害的事。这涵盖从"让智能体绕过某个它觉得烦人的检查"，到"运行一条它并不理解的破坏性命令"，再到"明确指定要造成伤害"。

**模型失当行为（Model misbehavior）：** 智能体采取了没人要求的、有害的动作。随着我们的模型变强，它们在大多数行为评估上变得更对齐，但这并不意味着风险必然缩小。能力较弱的模型更容易误读情境、犯明显的错误。能力更强的模型犯的错误更少，但它们也更擅长找到通往目标的意外路径，往往是通过绕开没人想到要写下来的限制。

在 Anthropic，我们见过 Claude 模型[「贴心」地逃出沙箱](https://red.anthropic.com/2026/mythos-preview/)以完成任务、翻查 git 历史[寻找编程测试的答案](https://assets.anthropic.com/m/64823ba7485345a7/Claude-Opus-4-5-System-Card.pdf)，以及自发识别出自己正在被跑在哪个基准上、进而[解密其答案密钥](https://www.anthropic.com/engineering/eval-awareness-browsecomp)。每个模型都带来一组新能力，而这些能力有时会被用在出人意料的地方。

**外部攻击者（External attackers）：** 智能体通过工具、文件或网络访问等外部途径遭到攻击。这一类既包括提示注入，也包括针对智能体运行时、编排层或代理的传统攻击。

在构建围栏与防御系统时，我们把防御施加于三个主要组件：

**智能体运行的环境。** 我们用进程沙箱、虚拟机、文件系统边界与出口控制，约束智能体能在哪里、以何种方式行动。目标是为智能体可触及的范围设定硬边界。举例来说，如果凭据从未进入沙箱，它们就不可能被外带，无论起因是用户、是模型找到了一条"有创意"的路径、还是攻击者。

紧的周边边界也意味着你可以放松监督。Claude Code 的[参考 devcontainer](https://code.claude.com/docs/en/devcontainer) 的存在，正是为了让智能体能够无人值守运行，不需要逐动作审批。

**智能体所咨询的模型。** 这里的机制包括系统提示、分类器、探针（probe）与训练改动。由于模型是概率性的，这些机制只塑造智能体*倾向于*做什么，而非它在理论上*有能力*做什么。

这些防御很强。在 Gray Swan 的 Agent Red Teaming 基准（测试对提示注入的易感性）上，[Claude Opus 4.7](https://assets.claude.com/037f06850df7fbe871e206dad004c3db5fd50340.pdf) 把单次尝试的攻击成功率压在约 0.1%，在 100 次自适应尝试后约为 5–6%。Claude Code 的 auto 模式在激进行为[执行之前](https://www.anthropic.com/engineering/claude-code-auto-mode)捕获约 83%。然而即便拥有同类最佳的防御，模型层的保护也永远不会 100% 有效，这正是它不能单独成立的原因。

**智能体可触及的外部内容。** MCP 服务器、第三方插件与网页搜索工具，都会把来自你无法控制的来源的内容喂进智能体的上下文。一个经过审计的连接器不等于经过审计的数据——例如，一个 GitHub 连接器可以在通过恶意软件检查的情况下，把一份被投毒的 README 直接载入模型上下文。细粒度地限制工具权限有助于限制爆炸半径。举例来说，一个只有数据库只读权限的智能体，可以比一个能写生产库的智能体被广泛得多地部署。

防御应当互相重叠、互相补位。当环境层防御不可用时，模型层必须补上（这正是 Claude Code 的 [auto 模式](https://claude.com/blog/auto-mode)被设计出来要做的事）。在本地，环境与模型防御可以防范恶意的工具输出；但也可以通过限制工具的能力与访问范围，在链条更上游处增加防御。

需要防御的三个组件：模型、它运行的环境、以及智能体可触及的外部内容。

### 围栏智能体的模式

聚焦环境层，我们描述三种隔离模式，以及它们如何为每个 Claude 平台——[claude.ai](http://claude.ai)、Claude Code 与 Cowork——量身定制。每一种设计都是逐步形成的：在"我们需要智能体具备什么能力"与"需要用户介入到什么程度"之间找到平衡之后，才落成现在这个样子。

#### 模式 1：临时容器（claude.ai 的代码执行）

claude.ai 虽然最为人知的是聊天界面，但它也能编写并运行代码、生成文件、调用连接器。当 Claude 在 claude.ai 内运行代码时，它是在隔离基础设施上的一个 [gVisor](https://en.wikipedia.org/wiki/GVisor) 容器里运行。智能体完全在服务端；本地机器上不运行任何代码，文件系统是临时的（按会话）。爆炸半径极小，但 Claude 能做的事的上限也同样小——没有持久工作区，也无法访问用户的文件系统。

这也使 [claude.ai](http://claude.ai) 受制于一个更传统的威胁模型。我们不是在保护用户机器免受智能体侵害；我们是在保护自己的基础设施，以及保护各租户彼此之间。我们在 [claude.ai](http://claude.ai) 上线前的工作，主要被网络配置、内部服务鉴权与编排这类传统安全工作占据。

那项工作再次印证了安全领域最古老的教训：最薄弱的一层是你自己造的那一层。gVisor 与 [seccomp](https://en.wikipedia.org/wiki/Seccomp) 面对资源充足的对手被加固的时间，远比智能体 AI 存在的时间长，因此评审精力被投向了我们围绕它们新造的那些部件。后面我们还会回到这一点，因为我们自研的代理，也正是我们最严重的那次事故中出问题的部件。

#### 模式 2：人在环里的沙箱（Claude Code）

Claude Code 运行在用户机器上，可访问其文件系统、shell 与网络。没有这些，编码智能体用处有限，因此必须找到一种安全授予这些访问的方式。

一种做法是依赖人在环里。这对 Claude Code 之所以是可处理的方案，是因为典型用户是熟悉编程环境的开发者：他们能读 bash、知道 `rm -rf` 会做什么，而且他们本来就每周好几次从不可信来源跑 `npm install`。这一切意味着，当"是否允许"的对话框弹出来时，他们极有可能具备准确评估智能体想做什么、以及其中风险的专业能力。基于这一点，Claude Code 上线时采用了尽可能最简单的防御：允许读，写、bash 与网络访问需要审批。

然而如前所述，审批疲劳[在几周内就显现了](https://www.reddit.com/r/ClaudeAI/comments/1rru8zw/just_picked_up_a_new_keyboard_cant_wait_to_write/)。讽刺的是，这意味着一个原本为提供监督而设计的功能，可以说产生了相反的效果——有些用户可能干脆不再关注。作为缓解轻率审批的第一步，我们发布了一个操作系统级沙箱（macOS 上的 Seatbelt、Linux 上的 bubblewrap）来加固边界：允许读，允许在工作区内写，但默认禁止网络。在沙箱内，智能体基本不受打扰地运行。结果是权限提示减少了 84%，并且我们[把该运行时开源](https://github.com/anthropic-experimental/sandbox-runtime)了，因此边界是可审计的。

我们的[匿名化使用数据](https://www.anthropic.com/news/measuring-agent-autonomy)还显示，有经验的用户自动批准的比例大约是新用户的两倍，但他们也更频繁地在执行中途打断智能体。有经验的用户不是在每一步上设闸，而更倾向于只在智能体跑偏时去监督它。这或许是人们与智能体协作方式的一种自然演化，但它同样不可靠：它要求用户足够懂技术、足够专注，才能首先注意到偏移。随着模型能力提升、智能体开始写出越来越有野心的 bash，注意到这类偏移变得更难。而当用户转向多智能体系统时，这种做法也更难成为一种有效的监督策略。

##### 我们漏掉的风险：信任对话框之前的一切

2025 年年中到 2026 年 1 月之间，我们通过负责任披露计划收到了关于 Claude Code 漏洞的报告。其中三个漏洞针对的是在用户对任何事表示同意*之前*就执行的代码。要理解这怎么可能，考虑最直接的情形：一位开发者克隆一个仓库以审阅 pull request，而该仓库包含一个 `.claude/settings.json`，其中定义了一个 hook。由于 Claude Code 在启动时就会读取项目设置——在呈现标准的"你信任这个文件夹吗？"提示之前——攻击者编写并提交的那个 hook 会自动执行。其余案例在结构上类似：来自尚未被信任目录的输入，在信任边界建立之前就被解析了。

每个案例的修法形状相同：把项目本地配置的解析与执行推迟到用户接受信任提示之后。如果你正在构建类似的东西，请把"打开项目""加载配置""监听 localhost"当作来自互联网的入站请求来对待。它们不应该仅因为感觉上是本地的、并且在用户同意之前就到达，就被隐式信任。

##### 我们漏掉的风险：用户作为注入向量

2026 年 2 月，在一次受控的内部红队演练中，一位研究员成功通过钓鱼让一名员工以恶意提示词启动了 Claude Code。这封钓鱼邮件看起来像普通的协作——一封"你能帮我跑一下这个吗？"的邮件，附了一段可直接粘贴的提示词——而提示词本身读起来像常规任务说明。但在设置步骤的某处，它温和地要求 Claude 读取 `~/.aws/credentials`、把内容编码，并 POST 到一个外部端点。在该提示词的 25 次重试中，Claude 完成了 24 次外带。

这是一次*直接*提示注入——攻击者的指令是通过用户到达的，而不是通过工具输出或抓取到的内容。我们模型层的防御锚定在用户意图上：当是用户本人在敲这条指令时，分类器没有任何异常可抓。换一个人工承包商拿到同样的脚本，也会做同样的事。

在这种情况下唯一站得住的防御是环境，具体说是出口控制（无论意图如何都阻断那次 POST）与文件系统边界（一开始就让 `~/.aws` 不可触及）。

（当我们在内部 Slack 里分享那段可用的提示词以供讨论时，有人指出某些内部智能体*会读* Slack。载荷此刻变成了环境中的常驻物。我们在该线程里加了一个[金丝雀字符串（canary string）](https://www.fortinet.com/resources/cyberglossary/what-is-canary-in-cybersecurity)，以便一旦有什么东西抓到它我们能察觉。在一个智能体什么都读的世界里，调查工具本身也是攻击面。）

#### 模式 3：本地 VM（Claude Cowork）

Claude Cowork 运行在用户桌面上，可访问用户选定的一个工作区文件夹。由于该平台是为通用知识工作、而非软件工程构建的，典型用户远不那么可能熟练使用 bash。

因此，人在环里的沙箱策略可能不适用；不应指望一位非技术型知识工作者去判断 `find . -name "*.tmp" -exec rm {} \;` 这类 bash 咒语。当批准一个例外所需的专业能力是典型用户并不具备的，管理员就应当设定一个绝对且始终生效的边界。

为实现这一点，Claude Cowork 的第一个版本运行在一个完整的虚拟机里，使用平台的厂商 hypervisor（macOS 上是 Apple 的 Virtualization framework，Windows 上是 HCS）。该 VM 有自己的 Linux 内核、自己的文件系统与自己的进程表。用户选定的工作区与 `.claude` 文件夹被挂载；宿主机上其他东西都不可见。凭据留在宿主的钥匙串里，从不进入客户机。这一设计防范了"Claude 在某个时刻会以不对齐的方式行事"的可能性。一个被攻陷的 Claude 仍然可以损坏工作区文件夹里的东西，因此该架构被设计为确保那是它*唯一*能触及的东西（直到用户添加连接器），并且用户控制那里挂载了什么。

在最初的架构——我们称之为 full-VM 模式——中，智能体循环本身运行在客户机内，因此 Claude 以一个普通 Linux 用户的身份执行，并不知道自己被沙箱化。相比之下，在 Claude Code 中，一个特权进程坐在沙箱之外、逐条命令决定是否施加沙箱；一段有说服力的注入提示词，或一次疲劳的批准点击，就能让那个进程去跑未沙箱化的东西。而在 Cowork 这里，没有外层进程握着逃生门的钥匙，因此也没有任何组件有权授予例外。

Claude Cowork 的 VM 有六个主要隔离机制。其中两个在客户机内核之外实施，因此即使智能体在 VM 内取得 root 级访问也仍然有效。另外四个由客户机实施，并被刻意保持到最小，因为外层承担了其余部分。

然而我们很快意识到，把整个智能体放进 full-VM 模式会带来实际问题：VM 启动期间的任何失败都会让 Cowork 不可用。把智能体循环移到 VM *之外*、同时把代码执行留在 VM *之内*，使 Claude 仍能回应用户、帮助调试问题，而不是卡在错误上。这一改动对安全影响很小，因为 VM 仍然对智能体执行的代码施加文件系统与网络控制。

另外，我们也把本地 MCP 服务器移出了 VM。把它们跑在 VM 内会使它们更难被审计、在 VM 更新时造成脆弱的依赖问题，并且不支持那些需要与本地进程（如数据库）交互的 MCP——这类服务器无论如何都必须跑在宿主机上。这一改动使 Claude Cowork 与 Claude Desktop 中本地 MCP 服务器已有的工作方式一致：把它们当作用户可能选择安装的任意软件，并信任管理员来决定启用哪些本地 MCP（如果有的话）。远程 MCP 服务器不受影响，因为它们不运行在用户机器上。

把智能体循环放在 VM 内，意味着 VM 中的任何失败都会导致 Cowork 不可用。Host 模式更可靠，因为即使 VM 崩溃，智能体仍能回应，而且它通过隔离代码执行仍然提供重要的安全保障。

文件系统控制是另一个重要的架构选择。Claude 需要能够访问宿主机上的*某些*文件才有用，但我们想最小化爆炸半径，并向用户透明呈现本地文件访问。我们发现提供不同的文件挂载模式有助于细粒度控制风险；Claude Cowork 提供只读、读写、读写但不删除三种模式。这里一个潜在的坑是：符号链接解析必须在路径校验*之前*发生，而不是之后，否则授权文件夹内的一个符号链接可以指向外部并逃逸。对企业客户，我们允许管理员通过 MDM 设置中的挂载路径允许列表来控制这一点。

##### 我们漏掉的风险：通过被批准的域名外带数据

一个通过被批准的域名外带数据的清晰例子来自第三方披露。Claude Cowork 的出口允许列表正确地放行了到 `api.anthropic.com` 的流量——不调用我们自己的 API，该产品无法运作。在这个案例里，一个被放进用户挂载工作区的恶意文件携带了隐藏指令，以及一把由攻击者控制的 API key。Claude 遵循指令，读取了工作区中的其他文件，并用攻击者的 key 调用了 Anthropic 的 Files API。出口代理检查了目的地，看到是 `api.anthropic.com`，就放行了。文件被上传到攻击者的 Anthropic 账户。沙箱完美运作，然而数据还是被外带了。

此前我们把允许列表概念化为一个目的地过滤器，一个告诉 Claude *这些域名可以对话*的东西。但把它概念化为一次能力授予（capability grant）会更好。任何允许列表上某个域名可达的功能，此刻都成了攻击面。允许 `api.anthropic.com` 就意味着允许向任意 Anthropic 账户上传文件。

我们用一个位于 VM 内部的防御性中间人代理修复了它，该代理拦截通往我们 API 的流量。它只放行携带 VM 自身所配会话令牌的请求；攻击者嵌入的 key 会被代理拒绝。它还会阻断那些会启用服务端抓取的头部。该代理位于 VM 内而非我们的服务器上，因为只有 VM 知道来源——从服务器的视角看，一个 Cowork 请求与任何其他 API 客户端无法区分。

上：到 `api.anthropic.com` 的流量被放行，导致外带。下：修复方案，用中间人代理拦截通往我们 API 的流量。

这也是"你自己造的软件往往最薄弱"这一原则的第二个实例。我们各产品使用的 hypervisor、seccomp 与 gVisor 一直可靠。我们自研的允许列表代理才是失败的那一块。

##### 我们漏掉的风险：VM 隔离把终端检测软件也挡在外面了

在评估 Claude Cowork 时，企业安全团队问："为什么我们的 EDR 看不到里面？"答案是：把 Claude 关住的那份隔离，同时也把基于主机的终端检测与响应挡在了外面。从 EDR 的视角看，Claude Cowork 是一个不透明的 hypervisor 进程，它无法检查客户机。

隔离降低了可见性，而对那些合规姿态依赖终端可见性的团队来说，不透明是个问题。我们当前的缓解措施是使用基于拉取的 [OTLP](https://opentelemetry.io/docs/specs/otel/protocol/) 导出，让管理员可以在事后取回事件日志，但这与实时监控不是一回事。如果你正在构建类似的东西，请尽早为这场对话留出预算。

### 信任智能体所读的东西

企业经常问我们如何保护 MCP 连接。这是个好问题，但正确的问题比 MCP 本身更宽。提供给智能体的任何外部资源都同时代表两种风险：传统供应链意义上的代码执行风险，以及提示注入向量。传统的依赖审计（固定版本、校验签名、审阅源码）处理前者，却漏掉后者。

**远程与本地之别比看上去更重要。** 本地安装的工具是可审计的。你可以读代码、固定版本，并知道它不会在你脚下改变。远程工具——一个托管的 MCP 服务器、一个云连接器——可以在你批准之后的任何时刻改变行为；你安装时的信任决策可能不再适用。我们的[连接器目录](https://claude.com/connectors)通过持续评审来应对这一点，但目录之外的一切都应被视为不可信。先拿假数据去跑它，在一个恶意工具的爆炸半径被限制住的环境里跑。

**即便工具可信，工具输出也是攻击面。** 前面提到的 GitHub README 例子正是这种情况；任何施加于网页的输入扫描，都需要以同等严格程度施加于可联网工具的结果。尽管这增加延迟且不是完美防御，我们宁可选择实时检查：一旦被投毒的工具返回已经把智能体引导去外带数据，日志上只会显示一次成功的、已授权的 API 调用。事后没有任何信号可找。

在 Claude Code 与 Claude Cowork 中，工具调用经由代理路由，这些代理实施网络与文件策略，并可以在返回值进入模型上下文之前检查它们。执行检查的分类器可以是一个小而快的模型；它不需要是那个做推理的模型。

### 展望

模型与产品都在快速进步。随着它们进步，风险会变形、演化，我们的缓解措施必须跟上。

**持久记忆投毒。** 跨会话持久的智能体上下文份额不断增长——这包括产品记忆、CLAUDE.md 文件、挂载的工作区，以及定时与长期运行智能体的状态目录。任何落在这些位置的注入，都会在智能体每次启动时被重新加载。随着越来越多的智能体状态活过会话，我们面临的是经典"后利用"（post-exploitation）意义上的新持久化机制。会话启动时的良好分类器将需要变得更普遍。

**多智能体信任升级。** 一方面，子智能体可以隔离不可信内容，向主智能体返回结构化事实而非原始文本。另一方面，这也可以被滥用：如果子智能体的输出因为来自"我们自己"而被视为比原始工具结果更高可信，就引入了一个新的提示注入向量。在多智能体系统中，在"分配不同信任级别"与"变得容易发生信任升级"之间存在权衡。

**智能体身份。** Claude Cowork 对智能体身份的回答是具体的：凭据留在宿主钥匙串里，VM 获得一个按会话缩权的令牌，且该令牌可以独立于用户令牌被吊销。然而我们开始面对跨平台智能体身份这个更宽的问题。一个智能体应当拥有自己的主体身份，还是应当作为用户的延伸、继承用户的权限？最终答案可能是两者的混合。

随着智能体变得更强，攻击面在不断移动。我们见过的这些失败类型，很可能在各行各业、各个实验室里被重复。我们需要在智能体特有的安全姿态上做集体投入，从共享基准与披露规范，到通用身份标准与跨厂商红队。本文聚焦围栏，但那只是智能体安全图景的一部分。关于治理、可观测性与技术栈的其他部分，参见 [NIST 关于 AI 智能体身份与授权的项目](https://www.nccoe.nist.gov/projects/software-and-ai-agent-identity-and-authorization)、由澳大利亚 ACSC 会同 CISA 与英国 NCSC 牵头发布的[六机构智能体 AI 采用指南](https://media.defense.gov/2026/Apr/30/2003922823/-1/-1/0/CAREFUL%20ADOPTION%20OF%20AGENTIC%20AI%20SERVICES_FINAL.PDF)，以及 [ISO/IEC 42001](https://www.iso.org/standard/42001) 这一 AI 管理标准。我们的 Glasswing 计划是其中一份贡献，但我们期待在这个关键议题上与伙伴和竞争对手一同努力。

### 小结

简而言之，有几条我们反复回到的原则：

**先在环境层为围栏而设计，再在模型层引导行为。** 教给我们最多的两个事故——员工钓鱼与第三方允许列表披露——都是外带（egress）案例，数据通过被允许的路径离开。在这两个案例里，模型层都帮不上忙；没有任何异常可抓。当一切概率性手段都漏过时，被撞上的正是那堵确定性的边界。

**让隔离强度匹配用户的监督能力。** 一个能读 bash 的开发者与一个不能的知识工作者，跑的不是同一个威胁模型。用户能否评估智能体即将做什么，这个问题应当参与决定围栏策略；而把这个答案答错——无论是对专家施加过多摩擦，还是对非专家给予过多信任——本身就是一种失败。

**警惕自研组件。** 经过实战检验的 hypervisor、系统调用过滤器与容器运行时，承受过的对抗性关注远多于你能造出来的任何东西。本文描述的每一个部署里，都是标准原语撑住了，而我们围绕它们自研的部分暴露了缺陷。

归根结底，智能体或许是一类新软件，但它们在系统层面的交互并不新。它们仍然读文件、开套接字、起进程；这使得用成熟工具做围栏成为一项至关重要且可行的防御。部署的风险–收益平衡会随 AI 发展不断移动，但对爆炸半径设定硬上限，往往能把这一平衡推向正确的方向。

## 与路线图的挂接

- **A0-05（架构决策记录与演进观）**：这篇文章本身就是一份高质量的"演进观"记录：它明确写出每个设计在什么条件下被推翻——Claude Code 的逐轮审批在观察到 93% 通过率之后被推翻；claude.ai 的"只保护用户机器"假设在意识到要保护的是多租户基础设施之后被推翻；Cowork 的 full-VM 模式在"VM 启动失败即产品不可用"这一条件下被推翻。写 ADR 时可以照抄这个结构：假设 → 观测到的事实 → 推翻条件 → 新方案引入了什么新风险。
- **A4-02（最小权限与能力授权）**：文章给出了这条原则最锐利的一次表述：**把允许列表当"能力授予"，而不是"目的地过滤"**。允许一个域名，等于允许该域名上可达的每一个功能。对应的设计动作是：出口控制要按"具体接口 + 具体凭据"授权，而不是按主机名。同样值得注意的是 Cowork 的做法——凭据留在宿主机钥匙串，VM 只拿到按会话缩权的令牌，且该令牌可独立于用户令牌吊销。这就是"这次任务需要的权限"而非"这个账号有的权限"的一个具体实现。
- **A7-01（提示注入的架构级防御）**：两个案例值得逐字记住。其一，指令从**用户本人**到达的直接注入（25 次重试成功 24 次），模型层完全没有异常可抓，唯一有效的防御是出口控制与文件系统边界。其二，注入通过**被信任的工具返回**到达（GitHub README），因此"工具可信"不等于"工具输出可信"。这两条合起来给出了一个判断：如果你的 Agent 安全方案的核心是"更好的系统提示 + 分类器"，那你在架构上是没有防御的。

## 三个自测问题

1. 文章说"任何概率性防御都有非零的漏检率"，同时又给出了具体数字（单次 0.1%、100 次自适应后 5–6%、auto 模式拦下 83%）。请说明：为什么这些数字再好也不能替代环境层边界？在什么条件下它们可以作为唯一防线？
2. Claude Code 选择"人在环里 + OS 沙箱"，Cowork 选择"整机 VM"。决定这个差异的关键变量是什么？如果你的产品用户既包含开发者又包含非技术用户，你会怎么切分？
3. "允许 api.anthropic.com 就等于允许向任意 Anthropic 账户上传文件"——请把这句话推广成一个通用检查清单：在设计出口允许列表时，你需要为每个条目回答哪几个问题？
