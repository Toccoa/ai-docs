## 为什么今天读这篇

这是一篇产品公告，但它真正解决的是一个架构治理问题：当一家公司里同时跑着工程团队的编码智能体、产品团队的客服智能体、业务部门从厂商买来的智能体，以及员工自己装的效率智能体时，"谁拥有哪个智能体、它花了多少钱、它现在表现如何"这三个问题会同时失去答案。LangChain 的应对方式是把"智能体"提升为数据模型里的一等公民——一个带 owner、不可变 ID 和 type 的记录，让 trace、环境、评测、部署全部挂到它下面。对做 Agent 架构决策的人来说，这篇文章值得读的地方在于：它示范了"先有治理对象，再有治理能力"的顺序，以及"评测标准必须随智能体类型分化"这一判断——编码智能体看 PR 是否被合并，客服智能体看延迟，用同一套指标衡量两者本身就是设计错误。

## 三句话摘要

1. LangSmith 把智能体做成贯穿全产品线的核心记录（owner + 全局唯一不可变 ID + type），使构建、运行、改进、治理四个阶段共享同一个对象，而不是四个彼此割裂的界面。
2. 智能体类型（agent type）决定了仪表盘呈现什么数据、连接哪些外部系统、按什么标准评测：通用型看描述/活跃度/在线监控/常用模型工具，编码型看合并的 PR、token 成本与工作类型。
3. 治理不要求所有团队统一到一个平台——只要能通过 OpenTelemetry Protocol (OTLP) 接入，任何平台上的智能体都会被注册、被归属、被同样度量，成本尖峰出现时有名有姓的人可以联系。

## 译文

上周我们[宣布了 C 轮融资](https://www.langchain.com/blog/series-c)，并推出了全新的 **LangSmith Agent Platform**：一个用来构建、运行、改进和治理每一个智能体的单一场所。由此，智能体成为贯穿 LangSmith 的核心对象，把此前割裂的工作流为开发者连接起来，也让平台团队能够跨整个业务管理智能体。

本文讨论我们为什么要重构产品、智能体模型如何工作、它解锁了什么，以及我们下一步把它带向哪里。

### 我们为什么重建 LangSmith？

2026 年，智能体的采用出现了一次阶跃式变化：新的[执行架](https://www.langchain.com/deep-agents)、模型与工程方法，让构建能够[可靠完成复杂、高价值工作](https://www.langchain.com/blog/how-stripe-built-their-knowledge-ai-platform-on-deep-agents)的智能体成为可能。

如今公司在整个业务范围内运行着许多智能体：工程团队用编码智能体，产品团队在建面向客户的智能体，组织内各团队还有各种各样的内部效率智能体。这些智能体用不同的框架构建、托管在不同的运行时上、使用各种各样的工具与模型。

结果是，工程师和平台团队面对的工作流都是割裂的。

**工程师**在彼此不相连的界面之间来回切换。[轨迹](https://www.langchain.com/blog/agent-traces-ai-search-langsmith)、[监控](https://www.langchain.com/langsmith/observability)和[部署](https://docs.langchain.com/oss/python/langchain/deploy)分别住在不同的地方。这要求频繁的上下文切换，而在实践中，它导致团队跳过那些困难但重要的步骤，比如搭评测。

**AI 平台团队**则难以回答基本的治理问题。存在哪些智能体，每一个归谁所有？它们花多少钱，表现如何？当成本尖峰出现时，往往找不到明确的人来问发生了什么。

我们想让团队能够从同一个地方、用任意技术栈管理完整的[智能体开发生命周期](https://www.langchain.com/blog/the-agent-development-lifecycle)，并对这一切拥有归属与治理。

### 一个平台覆盖完整的智能体开发生命周期

LangSmith 支持完整的智能体开发生命周期：构建、运行、改进、治理。现在，我们通过一个独特的智能体记录把整个过程连接了起来。

- **构建（Build）**：在 LangSmith Studio 里用新的[自然语言构建器](https://docs.langchain.com/langsmith/build-an-agent)描述一个智能体，用我们的开源执行架在代码里构建，或者使用任何其他框架。
- **运行（Run）**：部署到 [LangSmith Agent Server](https://www.langchain.com/langsmith/agent-server)，或者把智能体留在你已经在用的运行时上。
- **改进（Improve）**：轨迹、评测、数据集、标注，以及 [Engine](https://www.langchain.com/langsmith/engine)，对任何向 LangSmith 发送轨迹的智能体都能工作。
- **治理（Govern）**：LangSmith 智能体注册表与 [LLM Gateway](https://www.langchain.com/langsmith/llm-gateway) 提供组织级可见性，并对每一个已注册智能体实施严格管控。

当你打开一条智能体记录，它的轨迹、评测、Agent Server 和 Engine 问题都可以一键访问，你不需要在多个界面之间导航去找它们。每个智能体的本地、开发、预发和生产环境都挂在同一个 agent ID 之下，因此做改动之后比较性能变得很简单。

LangSmith 是可组合的，你可以只挑选自己需要的部分。如果你的智能体已经跑在另一个平台上，你可以把它接到 LangSmith 上来改进和治理，而不改动其他任何工作流。

如果你在 LangSmith 上构建并运行，你得到的不只是一个管理生命周期的地方。LangSmith 的各产品互相叠加，因此你能更快地发现、修复、发布并验证智能体中的问题。例如，LangSmith Engine 可以在你把修复合并到生产之前，先[对照 Agent Server 的预览环境验证一个候选修复](https://www.langchain.com/blog/langsmith-engine-v2-redteam)。

### 面向智能体的新数据模型

此前，发送到 LangSmith 的轨迹使用扁平的 project 层级，与任何特定智能体都没有关联。同一个智能体在不同环境中的轨迹彼此之间也没有关联。

现在有了一个智能体记录，环境和轨迹都归组在它下面。开发生命周期的每一个阶段都连接到这条智能体记录。

每条智能体记录包含三个属性：

- **Owner（归属人）**：一位具名的、对该智能体负责的人
- **ID**：全局唯一、不可变的标识符
- **Type（类型）**：它是哪一种智能体，这决定了其仪表盘呈现哪些信息、建立哪些数据连接、采用什么评测标准

### 面向不同智能体类型的评测与治理

不同的智能体做不同的工作，因此你需要不同类型的评测来治理和改进它们。举例来说，编码智能体是否合格，看它写的代码有没有被合并；而客服智能体要求低延迟。智能体类型把这些区别固化进 LangSmith 的架构，于是每条智能体记录都会提供围绕该智能体目标设计的、真正有用的资源。

智能体类型提供三样东西：

**围绕智能体工作实际构建的数据视图：** 每一种智能体类型都有量身定制的仪表盘，包含关键统计与评测标准。对通用型智能体，这包括智能体的描述、近期活动、在线监控、它常用的模型与工具，以及 Engine 暴露出来的智能体失败。对编码智能体，则是合并的 PR、token 成本，以及智能体完成的是哪一类工作。

**无需手工搭建即可获得一致的数据：** 这些仪表盘是有意"带观点"的。当你给一个智能体指定类型后，它的仪表盘立刻可用，不需要先自建任何自定义视图。同一类型的每一个智能体都按同样方式度量，所以当你有三个人分别在跑编码智能体时，这三者的度量是可比的。

**数据连接：** 编码智能体类型允许你连接 GitHub 仓库，以追踪智能体使用情况的下游结果。随着我们构建更多智能体类型，我们会持续构建集成，让你能看到并针对智能体的相关数据采取行动。

我们从通用型与编码型智能体开始，正在扩展到那些评测方式独特的更多类型。举例来说，语音智能体不仅要解决客户问题，还要以低延迟和良好音质与客户交互。有了智能体类型，我们可以默认呈现这些特定数据，让开发者更容易找到失败并修复它们。

### 治理每一个智能体，无论它跑在哪里

智能体蔓延（agent sprawl）已经变成一个治理问题，而它来自三个方向。工程团队自建智能体。业务部门采纳厂商平台上的智能体，比如 IT 用 ServiceNow、企业搜索用 Glean。员工自己也会顺手装上编码与效率类智能体。

平台团队和 AI 负责人对所有这些都负有责任，但要求每个团队统一到一个平台上并不现实。

用 LangSmith，他们不必这么做。它对运行在任何支持 OpenTelemetry Protocol (OTLP) 的平台上的智能体都有效，包括各家实验室和大型云厂商。把智能体接进来，它就会和你工程师自建的智能体一起被注册，并按同样方式被度量。

每一个已注册的智能体都有归属人、ID 和类型。对管理员来说，这提供了一致的方式来监控和管理整个智能体舰队。成本与质量指标按智能体汇总，覆盖每一个环境。如果某个 Glean 智能体出现了成本尖峰，有一个具名的负责人可以联系，同时还有能指出问题所在的轨迹细节。

### LangSmith 下一步走向哪里

智能体记录是 LangSmith 的新地基，我们很期待在它上面继续构建。当每一条轨迹、每一个环境、每一次部署都钉在智能体上时，我们就能为开发者简化更多工作流，并把治理内建进去。

以下是我们正在建设的方向示例：Engine [对你的智能体做红队测试](https://www.langchain.com/blog/langsmith-engine-v2-redteam)、找出失败，并在你发布修复后持续监控是否回归。你的团队在一个围绕自身评审流程构建的[自定义标注应用](https://www.langchain.com/blog/langsmith-custom-apps)里审阅生产轨迹，被审阅过的样本会自动流入评测数据集。你最好的运行所产生的[轨迹（trajectories）](https://www.langchain.com/blog/langsmith-trajectories-tracing)会成为[微调模型](https://www.langchain.com/blog/langsmith-fine-tuning)的数据，从而降低成本、提升智能体表现。所有这些都连接到同一条智能体记录，KPI 实时监控。

这些组成部分今天都已经存在于 LangSmith 中。现在我们正把它们连起来，让开发体验更顺。

同样在路线图上的还有：

**更多智能体类型：** 通用型与编码型智能体类型今天已经可用，语音型即将到来。我们会持续扩展，让团队能够标准化更多种类智能体的评测与治理方式，每一种都配有相关的数据连接与分析。

**组织级仪表盘：** 目前集中式仪表盘在工作区（workspace）级别可用。我们正在做组织级仪表盘，让负责人能在一个视图里看到整个公司的汇总性能指标与趋势。

**身份（Identity）**：每个智能体已经拥有唯一且不可变的 ID。接下来，你将能够在身份提供方（identity provider）中注册智能体，使安全团队可以像管理组织内其他任何身份一样管理和审计它们。

### 如何开始使用新的 LangSmith

新的 LangSmith 已在云端、BYOC 和自托管环境中全球可用。你可以[今天登录或注册](https://smith.langchain.com/)来试用。

最快的上手方式是用 [LangSmith Studio](https://docs.langchain.com/langsmith/build-an-agent) 构建你的第一个智能体，或者[接入一个你已经在运行的智能体](https://docs.langchain.com/langsmith/create-an-agent#name-an-agent-traced-from-outside-langsmith)。

## 与路线图的挂接

- **A0-05（架构决策记录与演进观）**：这篇文章本质上是一份公开的架构演进记录——"当时假设 trace 是一个扁平的 project 集合，什么条件下要推翻"被写得非常清楚：一旦公司里智能体数量超过几个人能记住的范围，扁平 project 就不再能回答"谁拥有、花多少、表现如何"。你自己写 ADR 时可以照抄这个句式：不是"旧方案不好"，而是"旧方案的隐含假设（智能体数量少、归属靠人记）失效了"。
- **A6-02（可观测性：trace / span / 语义约定）**：把"智能体"变成 trace 的归属主体，是可观测性从"调试工具"升级为"治理地基"的关键一步。值得注意的技术细节是它用 OTLP 作为接入协议——这意味着 trace 的语义约定（span 结构、属性命名）必须先稳定下来，跨平台治理才可能成立。反过来说，如果你的 trace schema 还在每周变动，先别急着做注册表。
- **A8-05（演进路线：单点 → 平台 → 基础设施）**：LangChain 明确走的是第二阶段到第三阶段的过渡：先做单点工具（tracing、eval、deploy 各自独立），再承认割裂是问题、用统一记录把它们缝起来，最后用注册表 + 网关 + 身份（roadmap 中的 IdP 集成）向基础设施层走。判断自己该不该跟：如果你还只有一两个智能体，这个阶段的"缝"你暂时不需要。

## 三个自测问题

1. 如果你的公司现在要回答"我们一共有多少个智能体在生产环境跑"，你需要在几个系统里翻？这个数字本身就是你当前治理成熟度的度量。
2. 为什么"给智能体指定类型"这件事会同时解决仪表盘、数据连接和评测标准三个问题？换句话说，类型究竟编码了什么信息？
3. 文章说治理不要求统一平台，只要支持 OTLP。这个说法的隐含前提是什么？在什么情况下它会不成立（提示：想想 trace 语义约定与数据出境）？
