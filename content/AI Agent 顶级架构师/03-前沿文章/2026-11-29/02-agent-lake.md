## 为什么今天读这篇

大多数团队把 trace 当调试工具：出了 bug 去翻一眼，翻完就关。这篇文章提出一个不同的定位——trace 是"智能体做过什么的系统记录"（system of record），因此它应该像数据湖一样被建模：一个为智能体轨迹优化过的存储层，加上跑在它上面的"智能计算"层。这个划分对做架构决策的人有直接用处：它把"要不要建数据平台"这个看起来过重的问题，拆成了两个可以分别回答的问题——你的存储能不能扛住每月几十亿次运行，你的计算层能不能自动把高信号轨迹捞出来。文章还给出了两个值得记住的量级：LangSmith 每月接入数十亿次智能体运行，Engine 已分析超过 6000 万条生产轨迹；以及一个具体的微调收益：在 IssueBench 子集上，微调后的 Kimi K3 得 96 分，基线 Kimi K3 得 90 分，GPT-5.6 Sol 得 87 分。

## 三句话摘要

1. 智能体轨迹是"非结构化推理的轨迹"，所以分析它必须依赖智能——这是"智能计算"区别于传统数据工程的地方；传统数据湖（Snowflake、Databricks）既没有为这类数据优化的存储，也没有对应的智能计算。
2. 智能体数据湖里不只有轨迹，还有结果（outcome）；结果与 thread/trace 的映射可以是一对一也可以是多对多，其来源可以是用户、系统观测、LLM-as-a-judge 代理，或人工标注队列——没有结果，就无法判断 ROI。
3. 智能计算要解决两件事：在海量数据中找出高信号轨迹（在线评测器 + AI Search），以及把改进闭环自动化（Insights 归类、Engine 定位并提 PR、SmithTune 微调）。

## 译文

智能体的轨迹（trace）是"该智能体做了什么"的系统记录。它包含关于用户意图、智能体行动轨迹（trajectory）与最终达成结果的丰富信息。使用这些轨迹最简单的方式是把它当调试工具：可视化一个 LLM 应用走过的步骤序列，判断哪里出了问题。随着智能体轨迹变长（因为智能体变得更强）且数量变多（因为智能体进入生产），这种手工调试不再可扩展。

为了用这些轨迹数据在大规模上驱动智能体的持续改进，你需要两样东西：

- 一个为智能体轨迹优化的高效数据库
- 为查询与处理这些轨迹而设计的"智能计算"（intelligent compute）

这两件事我们做了将近两年。我们推出的第一块大东西是 [SmithDB](https://www.langchain.com/blog/introducing-smithdb)，一个专为轨迹打造（purpose-built）的数据库。

过去几个月，我们不断加大在"智能计算"上的投入。之所以需要"智能计算"，是因为这些智能体轨迹本身就是非结构化推理的轨迹，分析它们需要智能。

在传统数据工程里，数据湖存储一份共享的数据语料，不同的引擎可以查询和处理它。在构建 LangSmith 的过程中，我们注意到自己的平台架构也在向这个方向收敛：一份共享的智能体数据语料（存在 SmithDB 里），加上许多不同形态的"智能计算"跑在它上面。

像 Snowflake 和 Databricks 这样的传统数据湖，既没有为这类智能体数据优化的存储，也没有为它优化的"智能计算"。当一家公司产生的数据里越来越多是智能体轨迹时，我们认为开发这种新型平台很重要。

我们把这种新型平台叫做 agent lake（智能体数据湖）。

*Agent Lake：一个把"为智能体轨迹优化的存储"与"智能计算"结合起来的平台，用来查询、分析并从中学习，从而驱动智能体的持续改进*

### 智能体数据湖里有什么

落进智能体数据湖的东西，大部分是轨迹。一条轨迹记录智能体一次运行的每一步——从用户输入，到每一次模型调用与工具调用，直到最终输出；而多轮对话会被归组为 ***threads（线程）***，这样整段交互可以一起被读取。

我们的智能体数据湖 LangSmith，每月接入数十亿次智能体运行的轨迹。有些客户（比如 Clay）每天向我们发送数亿个事件。正是这种量级，促使我们[构建了 SmithDB](https://www.langchain.com/blog/introducing-smithdb)——业界在智能体轨迹数据之上、针对实时负载性能最强的专用数据库。

智能体数据湖里还存放结果（outcome）。轨迹告诉你智能体是怎么工作的；结果告诉你这份工作的影响。思考结果有两个维度。

第一个维度是结果如何映射到 **threads** 和/或 **traces** 上。有些结果与 thread 或 trace 是一对一的。例如，对某条 trace 点一个"踩"，意味着那一轮的智能体回答是差的；对整段对话给一个低分，意味着整个 thread 是差的。另一些结果可能是多对多的。例如我们最近在 LangSmith 里上线了"编码智能体"类型。我们在那里追踪的结果之一是被合并的 pull request（PR）。一个 thread 可能开出许多被合并的 PR，一个 PR 也可能由许多 thread 共同贡献。

第二个维度是这些结果如何产生。有时它们直接来自用户（点"踩"）。另一些时候它们来自对智能体所交互系统的观测（合并的 PR、被复制的代码片段）。还有一种方式是用 LLM-as-a-judge 自动为这些结果生成代理指标作为反馈。最后，系统的开发者或构建者可以在标注队列（annotation queue）里手工给 thread 打标。

关键在于，智能体数据湖里不只有轨迹，还有结果。这最终是你判断 ROI、判断智能体是否在起效或改进的依据。

### 智能计算

大规模运行智能体的团队对"智能计算"有两项主要需求：

1. 下钻（drill down）找出值得关注的轨迹
2. 对智能体改进闭环做智能自动化

#### 在海量数据中找到高信号轨迹

在 LangSmith 早期，开发者会一条一条地翻轨迹，确认模型在每一步都遵循了指令。在大规模下这不再可能，开发者需要更自动化的手段，在如此巨量的数据里找到高信号轨迹。

在线评测器（online evaluator）是筛智能体轨迹、找出最有助于驱动改进的那些的起点。LangSmith 自带一套调好的标准评测器提示词，覆盖幻觉、毒性、用户满意度等。在线评测器对判断智能体表现至关重要，所以你不应该盲目使用它们；你需要确认它们捕捉到了你的用例中真正有意思的信号，如果没有，就调整它们。

用 LLM-as-a-judge 做在线评测的一大障碍是贵。[TypeSafe AI 在 9 月推出的决策模型（decision models）](https://typesafe.ai/blog/introducing-system-one-models-and-jev)提供了一种以更低成本评测生产轨迹的新方式。LangSmith 现在提供[若干决策模型](https://docs.langchain.com/langsmith/llm-gateway-decision-models)用于低成本的轨迹分类，而这个"低成本但智能"的在线评测方向，是我们正在积极研究的问题。

这些在线评测器会在轨迹上留下反馈。这让开发者找到相关轨迹变得极其容易（只需按反馈过滤！）。然而这有一个缺点：它要求你事先定义好想度量哪些信号。

有时候你想当场找出高信号轨迹，而事先并没有建好在线评测器。针对这种模式，我们构建了 [AI Search](https://www.langchain.com/blog/agent-traces-ai-search-langsmith)，它让你用自然语言在轨迹数据上搜索。我们在搜索结果上跑一个决策模型（快且便宜！），加上一层"语义"过滤。这让你可以搜索诸如"用户变得沮丧的 thread"或"包含 PII 的 trace"这样的东西。注意，你可以把这些语义过滤器与普通的结构化查询组合起来，搜索能力会更强。

智能体数据湖需要支持对轨迹的快速、智能搜索。在线评测与 AI Search 提供了让这成为现实的智能。

#### 智能自动化

在线评测器与 AI Search 用来把高信号轨迹暴露出来。这项数据挖掘工作是团队搭建的通用"智能体改进闭环"流程的一部分。它是该流程中有价值的一环，但之后还有更多事要做。仍然得有人搞清它们意味着什么、以及在智能体里改什么。在客户运行的量级上，这部分工作也必须自动化，所以我们自己构建了智能体，来对智能体改进闭环做这种"智能自动化"。

[Insights](https://docs.langchain.com/langsmith/insights) 展示人们实际上是如何使用你的智能体的。你针对自己的流量提一个问题，比如"我的智能体在哪里失败？"，Insights 会把近期轨迹归入若干类别，然后随着新对话到达持续把它们分进这些类别，这样你就能看到哪几类请求正在往错误的方向发展。

[LangSmith Engine](https://www.langchain.com/blog/introducing-langsmith-engine) 寻找具体可修的问题。它按计划扫描你的轨迹，把反复出现的失败归组为 issue，并用前面提到的评测器分数与用户反馈来决定看哪里。接入代码仓库后，Engine 会诊断根因并以 pull request 的形式提出修复；从 Engine v2 起，它还能在你团队看到之前，先对照评测集测试这个修复。Engine 已在我们客户群中分析超过 6000 万条生产轨迹。

当一个智能体在其执行架被调好之后仍不断犯同样的错误时，下一步往往是训练一个定制模型，而智能体数据湖里已经存着做这件事所需的语料。[SmithTune](https://www.langchain.com/blog/langsmith-fine-tuning) 是一个 CLI，它用 Fireworks 或 Baseten 在你最好的轨迹上微调模型，然后在 LangSmith 里把它与基座模型对比。我们在 Engine 自己身上跑过这件事：用 Engine 某个智能体的轨迹微调 Kimi K3。在 IssueBench（我们内部用于检测并归类轨迹中问题的基准）的一个子集上，微调后的模型得 96 分，基座 Kimi K3 得 90 分，GPT-5.6 Sol 得 87 分。

Insights、Engine 和 SmithTune 是"智能计算"的例子：它们跑在轨迹之上，把智能体改进闭环中更多的环节自动化。这些都能与在线评测配合使用。事实上，配合使用时它们尤其强大！在线评测提供的信号可以被 Insights / Engine / SmithTune 用来更快、更准地过滤或聚类问题。

### 智能体数据湖还在不断注水

随着智能体为公司做越来越多的工作，它们会为公司产生越来越多的数据。这些数据*极其*有价值，因为它可以用来改进智能体本身。这个智能体改进闭环，是"拥有你自己的智能"的核心部分。要做到这一点，你需要一个能提供两件事的智能体数据湖：

- 一种高效存储所有这些智能体数据的方式
- 跑在轨迹之上的"智能计算"，帮你把这个智能体改进闭环转起来

价值不在每一条轨迹本身，而在你能在智能体数据湖里对这些轨迹做的一切。[今天就来试用 LangSmith](https://www.langchain.com/langsmith-platform)，离智能体的持续改进更近一步！

## 与路线图的挂接

- **A0-05（架构决策记录与演进观）**：文章里最值得抄进 ADR 的一句是"我们的平台架构正在向数据湖收敛"。这是一个典型的"事后才看清的架构判断"——它不是在项目第一天设计出来的，而是在做了两年 SmithDB、做了在线评测和 Engine 之后回溯发现的。这类"收敛式判断"应该被显式记录下来，否则下一个接手的团队会以为当初就是这么设计的，从而误判哪些部分可以改、哪些是承重墙。
- **A6-02（可观测性：trace / span / 语义约定）**：文章给出了一条常被忽视的等式：**trace 的存储形态决定了你能问什么问题**。当你把 trace 存在按 project 划分的扁平结构里，你只能问"这次运行怎么走的"；当它按智能体记录组织、并附带结果标签，你才能问"这类请求的合并率是多少"。换句话说，schema 不是中立的，它预先决定了分析的上限。
- **A8-01（内部 Agent 平台该提供什么）**：这篇文章可以当作"平台该提供什么"的清单来读：存储（SmithDB）、信号提取（在线评测器、AI Search）、闭环自动化（Insights、Engine、SmithTune）。值得注意的是这三层的依赖顺序——没有稳定的 trace schema，第二层做不出来；没有第二层的高信号标签，第三层的自动化只会放大噪声。很多团队反过来做（先上 Engine 式的自动化），然后困惑于为什么自动提的 PR 都是垃圾。

## 三个自测问题

1. 文章说"价值不在每一条轨迹本身，而在你能对这些轨迹做的一切"。请用一个具体例子说明：同一条轨迹，在什么条件下值 0，在什么条件下值很多？
2. 为什么"结果（outcome）"必须和"轨迹（trace）"放在同一个湖里？如果把它们分成两个系统（trace 存可观测性平台、outcome 存业务数据库），会失去什么？
3. 在线评测器的缺点被明确写成"要求你事先定义想度量哪些信号"。AI Search 是如何绕过这个限制的？绕过的代价是什么（想想成本与可复现性）？
