## 为什么今天读这篇

因为这篇把"上下文该由谁管"从一个实现细节，变成了一个可以做对照实验的架构分叉：**执行架（harness）驱动**的压缩，和**模型驱动**的上下文编辑，在同一批任务、同一套预算刻度上被直接比了一次。对做 Agent 架构决策的人，它的价值在于给出一条可复用的判据——上下文管理的收益不是恒定的，它随"上下文压力"（任务所需 token 与窗口容量之比）单调变化，窗口越紧、收益越大；而窗口宽松时，激进压缩甚至会亏分（Kimi、DeepSeek 在无时机指令的变体上掉约 8 分）。第二层价值在推理侧：它把"压缩后必须重算后缀"这个被忽略的账单摆到台面上，并给出 suffix KV 复用这条把"更短上下文"变成"更便宜推理"的工程路径（prefill 算力降 4–15%）。读完你会有两个可落地的动作：一是把 `collapse`／`new_context` 这类上下文 API 纳入执行架的接口清单，二是把"上下文编辑之后的 KV 缓存复用"写进推理引擎的选型要求。

## 三句话摘要

1. 研究者在 NVIDIA 开源的 Agent 执行架 NOOA 上，把上下文的压缩时机与压缩范围的决策权从执行架交给模型，在 OfficeQA Pro v2 与 MLE-bench Lite 上、8K–512K 的上下文预算区间内对比两种策略：会用上下文 API 的模型在同等预算下准确率显著更高，GPT 6.1 在 32K 预算上把分数从 21% 提到 56%（接近 3 倍），Kimi 在输入 token 上最多省 41%。
2. 收益并不普遍：模型在"多久调一次 API、压得多狠、什么时候开始压"上差异极大（GPT／Kimi／DeepSeek 有 42–53% 的任务会调用，Opus 只有 4%），且提示词里的时机指令一改，压缩时机就整体漂移（Kimi 在 128K 上从 84% 掉到 29%），这就是作者命名的"上下文焦虑"。
3. 在推理侧，把 NOOA 的上下文 API 与 SGLang 中的 suffix KV 复用原型配对，在 Qwen3.6-27B、32K 上下文下把每次请求的 prefill 算力降低 4–15%，任务准确率无可测变化——指向"模型学会管上下文 + 推理引擎支持 KV 编辑"这一新的协同设计前沿。

## 译文

### 摘要

今天的 Agent 执行架是**代替模型**管理上下文的：当窗口填满时，执行架触发一次压缩（compaction），把历史摘要化。我们研究另一条路线——**模型驱动**的上下文管理，即由模型自己通过上下文 API 决定何时压缩、压缩什么。我们在 NVIDIA 开源的 Agent 执行架 NOOA 中把上下文的控制权交给模型，并在文档研究与机器学习工程两类任务上、8K 到 512K token 的上下文预算区间内比较这两种策略。有效使用上下文 API 的模型能达到更高的准确率，且往往用更少的输入 token，在预算紧张时尤其如此：在 32K 预算下，GPT 6.1 在 OfficeQA Pro v2 上的分数接近翻了三倍（21% → 56%），Kimi 则在输入 token 上最多省下 41%。然而模型之间差异巨大：调用 API 的频率、压缩的激进程度、开始压缩的时机都不同，而提示词的改动会改变这个时机。最后我们展示，推理引擎可以让模型驱动的编辑变得更便宜：通过复用编辑后未变化后缀的 KV 缓存，我们把每次请求的 prefill 算力最多削减 15%，而准确率无可测变化。这些结果共同指向一个新的协同设计前沿：被训练成会管理自身上下文的模型，由支持 KV 缓存编辑的推理引擎来服务。

### 1 引言

当我们发布 NOOA（[Furgale et al., 2026]）——NVIDIA 开源的 Agent 执行架——时，我们围绕六条核心理念来构建它。其中一条是：通过 API 把执行架的直接控制权交给模型，上下文压缩也在其中。动机很简单：一个智能体应当能够决定自己的历史里哪些部分留在上下文中、哪些被摘要化、哪些在需要时被检索回来（[Cabral and Furgale, 2026]）。

此后，围绕模型驱动上下文管理的兴趣持续增长。SideQuest（[Kariyappa and Suh, 2026]）与 Context Language Models（[Shao et al., 2026]）这类研究直接探索了这一想法，而 Agent 执行架也开始让模型管理自己的上下文。例如 Codex 引入了一个实验性的上下文管理模式（[OpenAI Codex, 2026b]），把历史与笔记同 `new_context` 工具结合起来，用于开启一个全新的上下文窗口。

这就带出几个实践问题：当前的模型能有效管理自己的上下文吗？这样做能提升任务表现吗？推理引擎能否把"模型托管上下文"变成更便宜的推理？

我们在文档研究与机器学习工程任务上比较了两种上下文管理策略。在**执行架驱动**的上下文管理中（当今执行架的默认做法），上下文窗口填满时由执行架触发压缩。在**模型驱动**的上下文管理中，由模型决定何时压缩、压缩什么。四点结论最值得注意：

### 2 从执行架驱动到模型驱动的上下文管理

**图 1**：在执行架驱动的上下文管理（上）中，当上下文使用量达到阈值时由执行架触发压缩。在模型驱动的上下文管理（下）中，模型在过程中自行编辑自己的上下文。

当一个智能体在任务上工作时，它的工具调用、输出与模型轮次构成的历史不断增长，使模型越来越难找到并使用相关信息（上下文腐烂，context rot，[Chroma Research, 2025]），并最终超出上下文窗口。

多数执行架会自动处理这件事：当上下文使用量越过某个阈值，执行架就把历史摘要化（图 1 上），这一过程通常被称为压缩。我们称之为**执行架驱动**的上下文管理。由执行架的启发式策略决定压缩何时发生、覆盖历史中的哪些部分，而模型只负责生成摘要。这种做法虽然简单，却可能是有损的，会导致模型中关键的、与任务相关的信息丢失。

**模型驱动**的上下文管理走的是另一条路：让模型自己决定何时压缩、压缩什么（图 1 下）。在 NOOA 中，模型可以通过它的上下文 API（`collapse` 调用）检视自己的历史，并把一段事件替换为一条摘要。被压缩的事件会被归档，因此模型可以按标签把原始内容检索回来。

清单 2 展示了它需要的两个操作：把一段事件折叠为摘要，以及按原始标签检索一个已归档事件。

**图 2**：通过 NOOA 的上下文 API 折叠事件，并按原始标签检索已归档事件。

### 3 实验设置

为了在多种类型的工作上检验模型驱动的上下文管理，我们使用两个基准。

**OfficeQA Pro v2**（[Databricks AI Research Team, 2026]）包含 90 个关于美国联邦收入与支出的问题。智能体通过搜索并阅读一个大型的、已预解析的文档语料来回答。阅读文档会迅速填满上下文，因此这是一个研究"智能体如何在一次研究任务中保持证据"的良好场景。

**MLE-bench Lite**（[Chan et al., 2024]；[OpenAI, ]）包含 22 个 Kaggle 竞赛，智能体必须检视数据集、编写与调试代码、评估结果并提交预测。智能体在迭代过程中必须跟踪实验、实现选择与执行反馈。

我们比较两种上下文管理策略：

- **执行架驱动**：在上下文预算的 80% 处，执行架把较早的历史摘要化，保留初始指令与最近的 10 个事件。
- **模型驱动**：模型获得 NOOA 的上下文 API、一个实时的上下文使用量指示器、一条"仅当使用量达到 85% 时才考虑压缩"的指令，以及当上下文接近上限时被加入请求的**上下文压力警告**。

我们把上下文预算从 8K 扫到 512K token。缩小预算会抬高**上下文压力**——即任务所需与窗口所能容纳之比——从而模拟长得多任务的效果。每个预算都是对请求大小的硬限制。若请求超限，一个兜底机制会移除最旧的事件并重试；三次失败之后，该次运行计为一次错误回答。

我们评估四个模型：我们评估四个模型：GPT-6.1 Sol（[OpenAI, 2026]）、Kimi K3（[Kimi Team, 2026]）、DeepSeek V4 Pro（[DeepSeek AI, 2026]）与 Claude Opus 5.5（[Anthropic, 2026]）。

### 4 模型驱动上下文管理的潜力

在实验中我们发现，能够理解并有效使用 NOOA 上下文 API 的模型，在相同上下文预算下可以达到显著更高的准确率，而且不需要额外训练。GPT-6.1 Sol 的收益最明显：在 OfficeQA Pro v2 上、32K 上下文预算下，它相对执行架驱动的上下文管理把准确率提升了接近 3 倍（图 3）。然而我们发现，这些收益并非在所有模型上都一致：DeepSeek V4 Pro 的提升较小，而 Opus 5.5 极少使用上下文 API。

**图 3**：分数 vs. 上下文预算，OfficeQA Pro v2，按模型对比执行架驱动与模型驱动。分数为通过任务数除以全部 90 次试验（含错误）。数据点为等权重的重复实验均值；误差棒跨越重复实验的最小–最大值。

**图 4**：分数 vs. 上下文预算，MLE-bench Lite，按模型对比执行架驱动与模型驱动。对 22 个任务取均值。分数为排行榜百分位（缺失分数计为零）。每个点是在该预算下所有已验证运行的平均值。

收益最强的地方在预算紧张时——此时智能体必须反复管理自己的历史才能推进——随着预算增大而缩小。在小预算上 GPT 与 Kimi 领先执行架基线，而 Opus 一直落后，直到预算大到两种策略趋于一致。在 MLE-bench Lite 上效应小得多，且仅限于最紧的预算（图 4），大概是因为它的任务所需上下文少得多。

这与近期工作（[Shao et al., 2026]；[Fan et al., 2026]；[Kontonis et al., 2026]）相印证：上下文管理在"窗口相对任务长度偏紧"时帮助最大。

模型之间的差异引出一个进一步的问题：它们是在做出不同的上下文管理决策，还是根本没能用上这项能力？为弄清这一点，我们考察了每个模型如何使用该 API。

### 5 有些模型比其他模型更会用它

所有模型收到相同的上下文 API 与指令，但它们的使用方式差别极大。GPT、Kimi 与 DeepSeek 在 42–53% 的任务中会调用它。Opus 极少伸手：它只在 4% 的任务中编辑自己的上下文（图 5）。

**图 5**：模型在使用上下文 API 的频率上存在差异。模型驱动运行、全部预算下，至少发生一次压缩调用的任务占比。

每次压缩的效应也各不相同。当 GPT 压缩上下文时，请求规模中位数缩小到 3.7 倍（图 6 左）。其他模型缩得少一些：Kimi 的中位数为 2.1 倍，DeepSeek 为 1.8 倍，Opus 为 1.5 倍。但压得更狠不是没有代价的。被压缩的事件会被归档，而模型有时会回头去找它们：GPT 在 19% 的压缩调用之后重新检索了归档内容，Kimi 是 7%，DeepSeek 是 3%（图 6 右）。Opus 是 14%，但它压缩得太少，这个估计噪声很大。综合来看，GPT 像是最适应上下文 API 的模型：它知道何时调用、每次调用压缩得最多、并且在需要时把归档内容取回来。

**图 6**：左：每次压缩调用的压缩倍数——模型决定压缩的那次请求的输入 token 除以下一次请求的输入 token（后者还携带了被执行单元的输出）。2 倍意味着上下文被减半；低于 1 倍意味着上下文反而增长。箱体覆盖调用的中间一半，中位数在箱内，须线覆盖第 5 到第 95 百分位，纵轴为对数刻度。所有已确认的压缩调用跨上下文预算合并统计。右：归档事件后来被再次检索（`self.events[…]` 或 `.get`）的压缩调用占比。这是一个下界。

模型在"上下文填满时做什么"上也不同。在 64K 预算下，我们从第一次上下文压力警告开始跟踪每个模型，直到该回合结束——要么以一个被接受的最终回答结束，要么以一次压缩调用结束。Opus 大多只是确认警告然后收尾：它在多数回合里直接给出回答，而不是继续下去。其他模型大多会压缩，而且许多会先查询点什么：GPT 在 69% 的回合中先读 API 文档再压缩，DeepSeek 在 46% 的回合中先检视事件历史，而 Kimi 在 49% 的回合中直接压缩（图 7）。这与图 5 中 Opus 极少调用 API 的现象一致。

**图 7**：模型在上下文压力下的行为。64K 上下文预算下，首次警告回合按解决方式的占比。当上下文接近上限时，我们向模型发送一条警告，并观察它如何回应。

这就让"训练"成为一个自然的问题。在一个自动压缩历史的执行架里工作，并不必然教会模型何时压缩、移除什么、或如何保留有用信息。

像 Mainplane（[16]）这样的执行架现在提供了与 NOOA 类似的上下文管理，而 Codex 那个带历史、笔记与 new-context 工具的实验模式（[OpenAI Codex, 2026a]）也让人有理由相信相关能力在 GPT 的开发过程中受到了关注。我们推测，面向模型驱动上下文管理的训练可能对 GPT 更强的结果有所贡献。然而，该功能的存在并不能告诉我们被评估的模型是如何训练的，也无法说明任何此类训练是否能迁移到 NOOA 的接口上。

我们的结果促使我们去研究：训练如何能让上下文管理更可靠、更有效。

### 6 上下文焦虑

即便是会使用该 API 的模型，也可能比需要的更激进地压缩——在空间尚存时就把上下文压得很小。我们称之为**上下文焦虑**（context anxiety），沿用了先前工作（[Igbinedion et al., 2026]）中关于模型误判剩余 token 预算的说法。

我们把压缩时机度量为一个任务中**模型首次发起压缩调用时已使用的上下文预算占比**。在"仅当使用量达到 85% 才考虑压缩"的指令下，多数模型会等到接近该点时才动手。移除这条指令会显著改变其中一些模型的行为（图 8）。

**图 8**：首次压缩时已使用的上下文：占上下文预算的中位百分比，含与不含时机指令。每个点是各任务中该任务首次压缩决策的中位数。它衡量一个模型何时开始压缩。某个预算下没有点，意味着该模型在该预算下从未压缩。

没有该指令时，Kimi 与 DeepSeek 压缩得早得多。Kimi 首次压缩的中位数在 128K 上从约 84% 的预算降到 29%，DeepSeek 在 256K 上从 83% 降到 40%。GPT 对此不那么敏感，这或许反映了它的训练方式。Opus 在有指令时几乎从不压缩，但没有指令时它规律而早地压缩——在 128K 上中位数为预算的 16%。

Kimi K3 在 token 用量上也体现出这个效应（图 9）。在 32K 预算下，两种策略的最大上下文规模相同，但模型驱动的智能体累计处理的输入 token 少 41%（36M 对 62M），分数还略高（43% 对 41%）。同样的预算，并不意味着同样的用法。

**图 9**：Kimi K3：OfficeQA Pro v2 上分数 vs. 累计输入 token，每个点标注其上下文预算。累计输入统计每一轮的全部输入 token，无论是否命中缓存。

保留更少的上下文也可能有代价。在 128K 及以上的预算上，没有时机指令的变体在 Kimi 与 DeepSeek 上比执行架基线低约 8 分。GPT 与 Opus 的准确率没有可比的变动。

为什么有些模型会提早压缩？许多模型被训练成保持上下文简短。例如 Kimi K3 在训练中用 RL 惩罚过长的 rollout（[Kimi Team, 2026]），这可能教它在空间尚存时也节省 token。

### 7 从更少 token 到更便宜推理

上下文管理最有价值的时刻，是模型用更少的输入 token 达到同等或更好的准确率。模型驱动的上下文管理恰好能做到这一点：在 64K 预算下，Kimi 比它的执行架基线少用约 11% 的累计输入 token，同时分数更高（57% 对 52%）。这一效应因模型而异：GPT 没有可比的节省，其他模型落在中间（图 10 与图 11）。

**图 10**：分数 vs. token 用量，OfficeQA Pro v2，按模型对比执行架驱动与模型驱动。累计输入 token；8K–64K 的点标注了其上下文预算。累计输入统计每一轮的全部输入 token，无论是否命中缓存。数据点按 token 排序，因此标签未必单调递增。低于 95% 轨迹覆盖率的运行被排除。

**图 11**：分数 vs. token 用量，MLE-bench Lite，按模型对比执行架驱动与模型驱动。输入 + 输出 token 总量，点标注了其上下文预算。token 用量是每次运行记录的输入与输出 token 总数，含重复的提示。连线连接递增的预算，在 token 用量上可能折返。Kimi K3 的点用等权平均合并了若干上下文预算。

然而，输入 token 计数只讲了故事的一部分。推理引擎通过为提示中未变化的前缀复用已缓存的计算（KV 缓存），避免在每一轮重新处理整个提示（[Zheng et al., 2024]；[vLLM Team, ]）。编辑上下文——例如用摘要替换一段历史——会让该缓存在编辑点之前保持有效，但会让编辑点之后的一切失效，哪怕是没变过的文本（图 12），所以更短的上下文并不自动等于更便宜。这还取决于每次编辑之后引擎必须重算多少。

**图 12**：压缩 B 缩短了提示，但摘要及其之后的一切都必须重新计算。

为解决这一点，近期论文如 NVIDIA 的 SideQuest（[Kariyappa and Suh, 2026]）、Context Language Models（[Shao et al., 2026]）与 Cache Engineering for Agents（[Fu et al., 2026]）提出：在编辑之后复用**未变化后缀**文本的 KV 缓存，而不是重算它——这是一种旨在保留有用模型状态、同时减少服务端计算量的近似。我们把 NOOA 的上下文 API 与一个在 SGLang 服务引擎（[Zheng et al., 2024]）中实现的 suffix KV 复用原型配对，使用 Qwen3.6-27B（[Qwen Team, 2026]）。在 MLE-bench Lite、OfficeQA Pro 以及 Agent 编程基准 DeepSWE（[Datacurve, 2026]）上，相比标准前缀缓存，它把每次请求的 prefill 算力削减了 4–15%，而任务准确率无可测影响（图 13）。节省在 OfficeQA Pro 上最大，因为编辑后存活下来的后缀文本很大——平均约 10K token，约占提示的 60%——原因是智能体的工具调用会检索出仍留在上下文中的长文档。

**图 13**：suffix KV 复用 vs. 标准前缀缓存，Qwen3.6-27B、32K 上下文，在模型驱动（NOOA 的上下文 API）与执行架驱动（摘要化，保留最近 10 个事件）两种上下文管理之下。左：每次请求被 prefill 的输入 token 的削减量。右：奖励的变化，按各基准自己的度量（DeepSWE：fail-to-pass 率；MLE-bench Lite：平均排行榜百分位；OfficeQA Pro：任务分数）。

这些结果表明，模型驱动的上下文管理为 Agent 系统开辟了一个新的设计空间。当模型主动塑造自己的上下文时，执行架与推理引擎不再只是各自扮演自己的角色，它们成为"决定保留什么、以及如何高效地服务它"的伙伴。我们正在积极探索模型、执行架与推理引擎之间的这种协同设计，以推进 Agent 工作负载的准确率–效率前沿。

### 8 局限性

我们的结果应在以下保留条件下解读。

- **基准偏小**。OfficeQA Pro v2 有 90 个问题，MLE-bench Lite 有 22 个竞赛，因此策略之间或模型之间的微小差异可能并不显著。
- **模拟的上下文压力**。我们通过缩小上下文预算来模拟更长的任务。这是一种代理手段：它不能捕捉真正长时程工作的每一项属性，而在到达上限时丢弃最旧事件的兜底机制本身也会影响分数。
- **四个模型，训练方式未知**。我们评估四个模型，且不知道它们是如何训练的。我们对 GPT 更强结果的解释是推测，而非经过检验的论断。
- **KV 复用只用了单一开源模型**。suffix KV 复用原型只在一个服务引擎中用单一开源模型（Qwen3.6-27B）评估。它是对完整重算的近似，而且我们度量的是 prefill 算力，不是端到端延迟或成本。

### 9 相关工作

**管理自身上下文的模型**。一条不断增长的研究线让模型对"可供其使用的信息"拥有显式控制。MemGPT（[Packer et al., 2023]）引入了分层记忆管理，而 Recursive Language Models（[Zhang et al., 2025]）把长输入放进一个外部编程环境，模型可以通过递归调用检视并处理它。更直接关注演化中的推理或交互上下文的，是 MEMENTO（[Kontonis et al., 2026]）、AgentFold（[Ye et al., 2025]）与 Context-Folding（[Sun et al., 2025]），它们发展出保留、浓缩或重构过往计算的学习机制。SelfCompact（[Li et al., 2026]）用提示评分标准、不做微调地研究模型触发的压缩。Context Language Models（[Shao et al., 2026]）把实时上下文暴露为一个可编辑的文件，同时评估现有模型与学习到的上下文管理策略；SideQuest（[Kariyappa and Suh, 2026]）则用一个辅助推理任务来选择要移除的 KV 缓存内容。我们的工作提供了一个互补的实证研究：在共享的上下文管理 API 下考察当前模型，聚焦它们的行为与任务表现如何随上下文压力变化，以及这些变化如何与服务效率相互作用。

**编辑后上下文的高效服务**。标准前缀缓存只对匹配的前缀复用缓存状态，因此历史内部的编辑可能需要重新 prefill 保留下来的后缀。面向 Agent 上下文管理，Context Language Models（[Shao et al., 2026]）引入 Suffix Cache Reuse，在匹配前缀之外保留缓存状态。一条相关路线直接作用于活跃的 KV 缓存：SideQuest（[Kariyappa and Suh, 2026]）移除选定的缓存内容，Cache Engineering for Agents（[Fu et al., 2026]）则协同设计缓存操作与服务引擎，以避免对保留下来的上下文重新 prefill。我们把一个支持 suffix 缓存复用的原型与模型驱动的上下文 API 配对，并度量它对 prefill 算力与准确率的影响（第 7 节）。

### 10 讨论与结论

我们在四个模型、两个基准上比较了执行架驱动与模型驱动的上下文管理。把上下文的控制权交给模型可以提升准确率，并且常常减少输入 token——在预算紧张时尤其如此——但收益高度依赖模型：模型在调用 API 的频率、压缩的激进程度、以及何时开始压缩上各不相同。推理引擎可以通过复用未变化后缀的 KV 缓存，让由此产生的编辑更便宜。

我们预计模型驱动的上下文管理将成为前沿模型的标准能力。走到那一步需要两件事：一是训练模型何时压缩、压缩什么；二是让上下文编辑变便宜的推理引擎。这指向两个方向：

- **提升底层能力**。有些模型已经能在从未训练过的上下文 API 上使用它，而 GPT 在预算紧张时从中获益可观。我们相信，正确地训练模型使用这些 API，将使该能力在各模型上变得可靠。
- **把执行架接到推理引擎上**。在设计服务时，让上下文编辑保留可复用的计算，并释放不再需要的 KV 缓存条目。

## 与路线图的挂接

- **A1-02（Token 经济学与上下文窗口的物理限制）**：这篇给"上下文不是免费的硬盘"补上了定量刻度。8K–512K 的预算扫描把"窗口容量"从一个静态参数变成一条压力曲线：同一个模型、同一批任务，仅因为预算不同，策略优劣就发生反转（紧预算下模型驱动领先，宽预算下两者收敛）。这直接支撑 A1-02 的核心判断——上下文预算应当作为一个**可调的设计变量**来对待，而不是"模型支持多长就用多长"。
- **A2-04（上下文工程：压缩、摘要、卸载）**：这是本文最直接的落点。它把 A2-04 里的"压缩"拆成两个可分别决策的子问题：**何时压**（时机）与**压多少**（范围），并证明这两件事交给模型自己判断时，收益取决于模型是否"会用 API"——GPT／Kimi／DeepSeek 有 42–53% 的任务会主动调用，Opus 只有 4%。同时它给出一个反例警示：压缩并非越早越好，"上下文焦虑"（Kimi 在 128K 上从 84% 掉到 29%）在 128K 以上预算会带来约 8 分的净损失。做上下文策略时，这条曲线就是你的调参依据。
- **延伸读到 A3-02（短期记忆与上下文装配）**：`collapse` + 按标签检索归档事件，本质上是一种"可回溯的上下文装配"——每一轮组装的是视图，被折叠的事件仍可按标签取回。这与"每轮重新组装一次视图"的思路同构。
