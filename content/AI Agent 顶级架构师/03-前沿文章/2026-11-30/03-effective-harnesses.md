## 为什么今天读这篇

因为这是目前少见的、把"长时程"这个模糊词拆成**四个可复现的失败模式**的工程复盘。它要回答的问题很具体：当一个编程智能体必须跨多个上下文窗口工作时，为什么即便有压缩（compaction）也会失败？Anthropic 的答案不是"模型不够强"，而是两条架构级缺陷——一是智能体总想一次把应用做完，导致下个会话从"半实现、无文档"的状态开始；二是后来的智能体会看到已有进展，然后宣布"活干完了"。对应地，他们给出的解法也不是提示技巧，而是一套**环境契约**：初始化智能体先写功能清单（claude.ai 克隆那个例子里超过 200 条）、`init.sh`、进度文件和初始 git 提交；每个后续会话只做一个功能，用 git 提交和进度记录收尾，并在开工前先跑一遍端到端冒烟测。对做架构决策的人，这篇文章的价值在于它把"跨会话状态"从"要不要做持久化"这种抽象讨论，落到 `claude-progress.txt` + git 历史 + JSON 功能清单这三件具体产物上——而且顺带回答了"为什么用 JSON 而不是 Markdown"这类看似琐碎、实则影响成功率的选择。

## 三句话摘要

1. 长时程智能体的核心困难在于：它必须在离散的会话中工作，而每个新会话开始时对之前发生的事没有任何记忆——就像一个软件项目里每班工程师都不记得上一班干了什么。
2. Anthropic 的解法是两段式：一个**初始化智能体**在第一次运行时搭好环境（功能清单、`init.sh`、进度文件、初始 git 提交），一个**编程智能体**在其后的每个会话里只做增量进展，并留下清晰的产物；Claude 的四类典型失败——过早宣布完工、留下带 bug 或无文档的状态、过早把功能标记为完成、每次都要花时间搞清怎么跑应用——各自对应一条具体对策。
3. 仍未解决的问题是：单一通用编程智能体是否优于多智能体架构（测试智能体、质量保证智能体、代码清理智能体），以及这套经验能否推广到全栈 Web 开发之外的领域。

## 译文

### 长时程智能体问题

随着 AI 智能体能力增强，开发者越来越多地要求它们承担需要跨越数小时甚至数天工作的复杂任务。然而，让智能体在多个上下文窗口之间保持一致进展，仍然是一个未解问题。

长时程智能体的核心挑战在于：它们必须在离散的会话中工作，而每个新会话开始时对之前发生的事没有任何记忆。想象一个软件项目，由轮班工作的工程师组成，而每位新到的工程师对上一班发生了什么毫无记忆。因为上下文窗口有限，且多数复杂项目无法在单个窗口内完成，智能体需要一种方式来桥接编程会话之间的间隙。

我们开发了一套两段式解法，让 [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 能跨多个上下文窗口有效工作：一个**初始化智能体**（initializer agent）在第一次运行时搭好环境，一个**编程智能体**（coding agent）负责在每个会话中取得增量进展，同时为下一个会话留下清晰的产物。代码示例见配套的[快速开始](https://github.com/anthropics/claude-quickstarts/tree/main/autonomous-coding)。

### 长时程智能体问题

Claude Agent SDK 是一个强大、通用的 Agent 执行架，擅长编程，也擅长其它需要模型使用工具来收集上下文、规划并执行的任务。它具备压缩等上下文管理能力，使智能体能在不耗尽上下文窗口的情况下处理任务。理论上，有了这套设置，智能体应当能够任意长时间地持续做有用的工作。

然而，压缩并不充分。开箱即用时，即便是一个前沿编程模型——比如 Opus 4.5 在 Claude Agent SDK 中跨多个上下文窗口循环运行——如果只给它一句高层提示，例如「做一个 [claude.ai](http://claude.ai) 的克隆」，它也达不到构建生产级 Web 应用的要求。

Claude 的失败表现为两种模式。第一，智能体倾向于一次做太多事——本质上是想一次性把应用做完。这常常导致模型在实现中途耗尽上下文，使下一个会话从一个半实现、且没有文档的功能开始。智能体随后只能猜测发生了什么，并花大量时间试图让基础应用重新跑起来。即使有压缩，这种情况依然发生，因为压缩并不总能向下一班智能体传递完全清晰的指令。

第二种失败模式常常出现在项目较晚的阶段。此时一些功能已经构建完成，后来的某个智能体实例环顾四周，看到已经有进展，于是宣布活干完了。

这就把问题分解为两部分。第一，我们需要搭好一个初始环境，为给定提示所要求的**所有**功能打下地基，使智能体能够一步一步、一个功能一个功能地推进。第二，我们应当要求每个智能体朝目标做增量进展，同时在会话结束时把环境留在干净状态。所谓「干净状态」，指的是那种适合合并到主干的代码：没有重大 bug，代码有序且文档良好，总体上一个开发者可以毫不费力地开始开发新功能，而无需先清理一堆与之无关的烂摊子。

在内部实验中，我们用一套两部分解法来应对这些问题：

1. **初始化智能体**：第一次智能体会话使用一个专门的提示，要求模型搭好初始环境：一个 `init.sh` 脚本、一个记录智能体做过什么的 `claude-progress.txt` 文件，以及一个显示新增了哪些文件的初始 git 提交。
2. **编程智能体**：其后的每个会话都要求模型做增量进展，然后留下结构化的更新。[1]

这里的关键洞见是：找到一种方式，让智能体在带着全新上下文窗口开始时能迅速理解工作的状态——而这靠的是 `claude-progress.txt` 文件配合 git 历史。这些实践的灵感来自「高效的软件工程师每天在做什么」。

### 环境管理

在更新后的 [Claude 4 提示指南](https://docs.claude.com/en/docs/build-with-claude/prompt-engineering/claude-4-best-practices#multi-context-window-workflows)中，我们分享了一些面向多上下文窗口工作流的最佳实践，其中包括一种执行架结构：为「第一个上下文窗口使用一份不同的提示」。这份「不同的提示」要求初始化智能体搭好环境，并带上未来编程智能体有效工作所需的全部上下文。下面我们深入讲一讲这样一个环境的几个关键组成部分。

#### 功能清单

为解决智能体一次做完应用、或过早认为项目完成的问题，我们提示初始化智能体写一份完整的功能需求文件，把用户的初始提示展开。在 [claude.ai](http://claude.ai) 克隆这个例子里，这意味着超过 200 条功能，例如「用户可以打开一个新对话、输入查询、按回车、并看到 AI 的回复」。这些功能最初全部标记为「不通过」（failing），以便后续编程智能体对「完整功能长什么样」有清晰的轮廓。

```json
{
    "category": "functional",
    "description": "New chat button creates a fresh conversation",
    "steps": [
      "Navigate to main interface",
      "Click the 'New Chat' button",
      "Verify a new conversation is created",
      "Check that chat area shows welcome state",
      "Verify conversation appears in sidebar"
    ],
    "passes": false
  }
```

我们要求编程智能体编辑这个文件时只改 `passes` 字段的状态，并使用措辞强硬的指令，例如「移除或编辑测试是不可接受的，因为这可能导致功能缺失或有 bug」。经过一番实验，我们最终选择了 JSON：相比 Markdown 文件，模型更不容易不恰当地修改或覆盖 JSON 文件。

#### 增量进展

有了这套初始环境脚手架，下一轮迭代中编程智能体被要求一次只做一个功能。这种增量做法最终证明是应对「智能体一次做太多」倾向的关键。

一旦开始增量工作，模型在做完代码改动后把环境留在干净状态仍然至关重要。在实验中我们发现，引出这一行为的最好方式是：要求模型用描述性的提交信息把进展提交到 git，并在进度文件中写下进展摘要。这让模型能够用 git 回退糟糕的代码改动、恢复代码库的工作状态。

这些做法还提升了效率：它们消除了智能体「猜测发生了什么、并花时间让基础应用重新跑起来」的需要。

#### 测试

我们观察到的最后一个主要失败模式，是 Claude 倾向于在没有恰当测试的情况下把一个功能标记为完成。在缺少明确提示时，Claude 倾向于做代码改动，甚至用单元测试或对开发服务器发 `curl` 命令来做测试，但会无法认识到该功能并没有端到端跑通。

在构建 Web 应用的场景下，一旦被明确要求使用浏览器自动化工具、并像人类用户那样做全部测试，Claude 在端到端验证功能上大多做得很好。

*Claude 通过 Puppeteer MCP 服务器测试 claude.ai 克隆时拍下的截图。*

为 Claude 提供这类测试工具显著提升了表现，因为智能体能够识别并修复那些仅从代码看不出的小 bug。

仍有一些问题存在，例如 Claude 的视觉能力限制以及浏览器自动化工具的限制，使得识别每一种 bug 都很困难。比如 Claude 无法通过 Puppeteer MCP 看到浏览器原生的 alert 弹窗，因此依赖这些弹窗的功能往往更容易出 bug。

### 快速进入状态

有了上述一切，每个编程智能体都被要求跑一串步骤来搞清楚状况，其中有些相当基础，但仍然有用：

1. *运行 `pwd` 看看你在哪个目录工作。你只能编辑这个目录下的文件。*
2. *阅读 git 日志和进度文件，快速了解最近在做什么。*
3. *阅读功能清单文件，挑出优先级最高、尚未完成的功能来做。*

这种做法每个会话都能为 Claude 省下一些 token，因为它不必再自己摸索怎么测试代码。它还使得「要求初始化智能体写一个能启动开发服务器的 `init.sh` 脚本，然后在实现新功能之前先跑一遍基础端到端测试」变得可行。

在 claude.ai 克隆这个例子里，这意味着智能体总是先启动本地开发服务器，然后用 Puppeteer MCP 开一个新对话、发一条消息、并接收回复。这确保了 Claude 能迅速发现应用是否被留在了坏掉的状态，并立即修复已有 bug。反之，如果智能体直接开始实现新功能，很可能让问题变得更糟。

综合以上，一个典型会话开始时是这样的助手消息：

```text
[Assistant] I'll start by getting my bearings and understanding the current state of the project.
[Tool Use] <bash - pwd>
[Tool Use] <read - claude-progress.txt>
[Tool Use] <read - feature_list.json>
[Assistant] Let me check the git log to see recent work.
[Tool Use] <bash - git log --oneline -20>
[Assistant] Now let me check if there's an init.sh script to restart the servers.
<Starts the development server>
[Assistant] Excellent! Now let me navigate to the application and verify that some fundamental features are still working.
<Tests basic functionality>
[Assistant] Based on my verification testing, I can see that the fundamental functionality is working well. The core chat features, theme switching, conversation loading, and error handling are all functioning correctly. Now let me review the tests.json file more comprehensively to understand what needs to be implemented next.
<Starts work on a new feature>
```

### 智能体的失败模式与对策

| 问题 | 初始化智能体的行为 | 编程智能体的行为 |
|---|---|---|
| Claude 过早宣布整个项目完工。 | 搭好功能清单文件：根据输入规格，建立一个结构化的 JSON 文件，内含端到端的功能描述列表。 | 在会话开始时读取功能清单文件，挑出单个功能开始做。 |
| Claude 把环境留在带 bug 或进展无文档的状态。 | 写入初始 git 仓库与进度笔记文件。 | 通过读取进度笔记文件与 git 提交日志开始会话，并在开发服务器上跑一遍基础测试以捕捉任何未记录的 bug。通过写 git 提交与进度更新结束会话。 |
| Claude 过早把功能标记为完成。 | 搭好功能清单文件。 | 自我验证所有功能。只有在仔细测试之后才把功能标记为「通过」。 |
| Claude 不得不花时间摸索怎么运行应用。 | 写一个能启动开发服务器的 `init.sh` 脚本。 | 通过读取 `init.sh` 开始会话。 |

### 未来工作

这项研究展示了长时程 Agent 执行架中一套可能的解法，使模型能够跨多个上下文窗口取得增量进展。然而仍有开放问题。

最值得注意的是：究竟是单一、通用的编程智能体在各场景下表现最好，还是通过多智能体架构能取得更好的表现，目前仍不清楚。像测试智能体、质量保证智能体、代码清理智能体这样的专门化智能体，在软件开发生命周期的各个子任务上做得更好，这一设想看起来是合理的。

此外，这个演示是针对全栈 Web 应用开发优化的。一个未来方向是把这些发现推广到其它领域。这些经验中的一部分或全部，很可能可以应用到例如科学研究或金融建模所需要的长时程 Agent 任务上。

## 与路线图的挂接

- **A2-07（执行架与框架选型）**：这篇文章给 A2-07 补了一个关键论点——执行架的"能力"不是功能表，而是**它是否强制了一套会话协议**。注意文章里那个脚注：两个"智能体"的系统提示、工具集、执行架完全相同，唯一差别是初始用户提示。也就是说，所谓"初始化智能体 + 编程智能体"不是两套代码，而是一套执行架上两种被约束住的工作模式。选型时应当问：这个框架能不能把"第一个会话做什么、后续会话做什么"写成可执行的协议？
- **A3-06（状态持久化与断点恢复）**：这是全文最硬的落点。`claude-progress.txt` + git 提交历史 + `feature_list.json` 三者共同构成了一份**可序列化、可回放**的任务状态：进度文件回答"上一班做到哪"，git 回答"改了什么、能不能回退"，功能清单回答"还差什么"。文中特别指出，压缩不足以替代这套机制——因为压缩"不总能向下一班传递完全清晰的指令"。做断点恢复时，这三级产物可以直接作为设计模板。
- **A6-01（demo 到生产的三道坎）**：文中列出的失败模式几乎就是"长尾、并发、成本"在长时程场景下的具体化身：一端是"半实现、无文档"的长尾状态，一端是"后来者看到有进展就宣布完工"的责任稀释。它同时给出一条可操作的验收标准——"干净状态"被定义为"适合合并到主干"，这个定义可以直接搬进你的 Agent 交付门禁。
- **延伸读到 A6-03（评测门禁与回归）**：`init.sh` + 每次开工先跑端到端冒烟测，本质上就是为长时程任务准备的最小回归门禁。

## 三个自测问题

1. 为什么"给执行架加上压缩"不足以解决长时程问题？请分别用文中提到的两种失败模式解释，并说明 `claude-progress.txt` 与 git 提交历史各自补上了哪一块缺口。
2. 作者选择用 JSON 而不是 Markdown 承载功能清单，理由是什么？如果一个团队坚持用 Markdown，你会用什么机制来对冲这个风险？
3. 「干净状态」被定义为"适合合并到主干"。请把这条定义转写成一条可自动检查的验收条件（至少两项检查），并说明它为什么能同时缓解"过早宣布完工"和"留下未记录 bug"两种失败。
