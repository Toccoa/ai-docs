## 为什么今天读这篇

因为绝大多数"给智能体加治理"的方案，管住的只是**一次执行之内**的事——检查这一步做对了没有、要不要重试。但这篇论文指出，对以代码为策略（code-as-policy）的机器人智能体来说，真正决定成败的是两件**持久化**的事：一次试次之内哪些已执行步骤保持"已提交"，以及跨运行之间哪些代码改动被保留下来。这两件事的时间尺度不同、失效方式不同、出错代价也不同，混在一起谈就必然管不住。作者用 180 个配对试次做了一个干净的 2×2 拆解，结论很反直觉：**"技能精炼"单独一项就把 RATs 的成功试次从 71 提到 135，而"运行期治理"单独只有 105；两者叠加是 158。**换句话说，对低成本模型而言，任务成功不只取决于生成的程序怎么被执行，更取决于它调用的**可复用技能的质量、以及这些技能如何随运行演化**。对做架构决策的人，这篇文章给了三个可直接搬走的东西：一个"提案与提交分离"的双闸门（验证器 + 审计器，固定规则合并，永不提交未通过验证的步骤）、一个"默认关闭 + 必须通过单元测试与关闭态字节等价检查"的技能变更门禁、以及一个诚实的成本账（每次试次约 2.16 元人民币，其中 65.6% 花在审计器上）。

## 三句话摘要

1. 以代码为策略的智能体缺乏治理"什么该持久化"的显式机制——一次试次内哪些动作保持已提交、跨运行哪些代码改动被保留——导致步骤级执行与跨运行适配这两个关键面向都失控；RegHarness 用两层执行架同时治理这两件事。
2. 在 180 个配对 LIBERO-PRO 试次上，RegHarness 用同一个低成本模型（deepseek-flash）贯穿所有角色，达到 87.8%（158/180）的成功率，而 RATs 为 39.4%（71/180）；五个初始状态上为 86.7%（260/300），MolmoSpaces 上为 72.0%（144/200）。
3. 2×2 消融显示两层贡献不均：技能精炼在 RATs 循环下 +64 个试次、在运行期治理下 +53 个；把 RATs 循环换成运行期治理则分别 +34 与 +23；而 RATs 自带的逐步骤重置-重放模式只有 46 个成功试次——所以"重置"本身并不能解释运行期治理的优势。

## 译文

### 摘要

以代码为策略（Code-as-Policy）的智能体生成、执行并修订机器人程序，但往往缺乏显式机制来治理跨执行什么会持久化：哪些动作在一次试次内被保留，哪些代码修改会延续到后续运行。这使得智能体行为的两个关键面向得不到充分控制：步骤级执行与跨运行适配。我们提出 RegHarness，一个两层执行架，为 RATs 智能体团队治理这两种持久化形式，且不依赖视觉-语言-动作（VLA）策略或示教。在一次试次之内，运行期治理对来自重置场景的每个拟议步骤进行评估，重放已提交的步骤；一个固定规则控制器仅在 RATs 的验证器与一个任务级 LLM 审计器**都**批准时才提交该步骤。在运行之间，一个编程智能体利用记录的失败来开发和测试对技能、原语与规则的修订，这些修订默认关闭，直到作者显式启用。在所有运行期角色上使用同一个低成本模型，RegHarness 在配对的 LIBERO-PRO 试次上达到 87.8%（158/180）的成功率，而 RATs 为 39.4%；在 MolmoSpaces 试次上达到 72.0%。对 RegHarness 两层做 2×2 消融显示：仅技能精炼就把 RATs 的成功试次从 71 提到 135，而仅运行期治理达到 105，RATs 原生的逐步骤重置-重放模式只有 46。这些发现表明，对使用低成本模型运行的以代码为策略智能体而言，任务成功不仅取决于生成的程序如何被执行，也取决于它们调用的可复用技能的质量以及这些技能如何跨运行演化。

**图 1**：RATs 在全部六次尝试中都未能完成这个试次；运行期治理与 RegHarness 都解决了它。RATs［26］用我们的低成本模型运行，写了六个程序，没有一个把碗拿起来。使用已发布的技能时，运行期治理（+ Harness）在一次抓取把碗从柜子上撞落之后重新规划，并在第三个计划上成功；RegHarness 在第一个计划上就成功。蓝色标记带有已提交步骤重放的重置场景；橙色边框标记被拒绝的执行（对 RATs 而言是失败的任务检查），绿色标记提交，行末标记显示任务检查。右：全部五种配置在 180 个配对试次上的成功率，灰色柱为 RATs 循环，紫色柱为运行期治理，深色柱为精炼后的技能，以及 RegHarness 在它那 300 个试次上的成功率。

### 1 引言

考虑这样一个任务：拿起柜子顶上的黑碗，放到盘子上。RATs［26］——一个以代码为策略［15］的智能体团队，我们用低成本语言模型运行它——对这个 LIBERO-PRO［32］任务做了六次尝试，每次都是覆盖整个计划的程序。它的静态检查器在一个程序运行之前就拒绝了它，而运行起来的五个中没有一个把碗拿起来：第一个把它留在柜子上，最后两个把它撞到了桌上。

在 180 个配对 LIBERO-PRO 试次上，RATs 在六次尝试内解决 39.4%（71/180），但只有 13 个是在第一次尝试中解决的。在其已发布的循环中，RATs 只在整个程序跑完之后才评判每一步；一次重试虽然被提示要保留有效的部分，但它仍是从重置场景重新运行的完整程序，因此一个已通过的步骤也可能改变并必须再次通过。全部 692 次重试都是完整程序，而那些跟在一次已诊断失败之后的重试中，有 86%（493/574）在失败步骤之外的代码上发生了改动（判据见补充材料）。一次干净的判定也不意味着工作完成：在 670 次失败执行中，有 117 次验证器没有标记出任何失败步骤。

这些智能体缺少的是一条"保留什么"的规则：一次试次之内哪些已执行步骤保持已提交，以及哪些代码改动延续到下一次运行。一次只测一步本身并不提供这条规则：已发布的 RATs 代码里已经含有一个逐步骤模式，默认关闭、其论文中也没有描述，它在每次尝试前重置场景并重放已通过的步骤，但它仅凭验证器通过就提交一步，而且一旦某一步的尝试次数用尽，它就未经验证地提交该步，以便计划能继续下去。重置保护了被重试的步骤不受失败测试残留物的影响，但它也抹掉了那次测试所揭示的东西；因此一个试次需要一份比重置活得更久的记忆，以及一条绝不保留未验证步骤的提交规则，而不是让编码器的下一个程序来决定哪段代码存活。在运行之间，代码本身必须改变：即便我们给 RATs 加上这样一条提交规则（+ Harness，4.3 节），180 个试次中仍有 75 个失败，其中 30 个失败于一次从未抬起非平面物体的抓取（19 个）或偏离目标的放置（11 个）。

RegHarness 在这两个时间尺度上治理"什么会持久化"（图 2）。在试次之内，它包裹 RATs 的规划器、编码器与验证器，并复用逐步骤模式的执行器，因此每一次步骤测试都会重置场景并重放已提交的步骤（重置-重放）；每个试次一个 LLM 审计器，审计计划、代码、步骤测试以及通过全部步骤却在基准任务检查上失败的已完成计划；一个含六条固定规则的控制器把审计器的提议与剩余预算转换为提交、重试、重新规划或中止，绝不提交验证器尚未通过的步骤。在运行之间，一个编程智能体（Claude Code 中的 Claude Opus 5.5）读取完整试次日志与帧，把每一项对技能、原语或规则的修复变成默认关闭的开关，该开关必须通过测试、并在关闭时通过逐字节等价检查，之后作者才能启用它。重置-重放要求场景能被软件重置，因此仅限仿真。

编程智能体与优化器早已在运行之间修订机器人执行架与技能［6, 18, 25, 4, 29, 5］，其中多数置于一个自动接受测试之后，而我们的、由作者把关的循环缺少这一步；同期工作 RegenHarness 在四足机器人上把模型的提议与一个确定性提交闸门分离开［23］。RegHarness 是一个新的执行架框架，它以两种方式改进 RATs，且不需要 VLA 策略或示教：在试次之内，它用一条针对"从重置场景测试的步骤"的提交规则替换 RATs 的循环；在运行之间，它精炼 RATs 跨任务共享的技能库。

在每一个角色上都用同一个低成本模型，RegHarness 在初始状态 0–2 的 180 个 LIBERO-PRO 试次中解决 158 个（87.8%），而 RATs 解决 71 个（39.4%）；在五个初始状态上解决 260/300（86.7%）；在 MolmoSpaces 上解决 72.0%（144/200）。2×2 拆解把这份增益不均地分给 RegHarness 的两层：精炼后的技能在 RATs 循环下增加 64 个试次、在运行期治理下增加 53 个；而把 RATs 循环换成运行期治理，在使用已发布技能时增加 34 个试次、在使用精炼技能时增加 23 个（精确 McNemar p = 1.2×10⁻⁴ 与 2.9×10⁻⁴）。RATs 自带的逐步骤模式只解决 46 个，比 RATs 本身还少，所以仅凭重置并不能解释运行期治理的优势幅度。一个 RegHarness 试次在模型调用上的成本估计为 2.16 元人民币（按 6.67 元/美元约合 0.32 美元），而 RATs 为 1.51 元（0.23 美元）（4.5 节）。两层都只在初始状态 0 上调试，然后直接在状态 1–4 上测试（4.1 节）。

我们的贡献是：

- 在以代码为策略智能体之上、不依赖 VLA 策略或示教，实现"对来自重置场景测试的步骤施以规则决定的提交"，并配以"由作者把关的共享技能库精炼"（第 3 节）。
- 在同一批 180 个配对 LIBERO-PRO 试次上，对控制循环与技能库做 2×2 拆解，并以 RATs 自带的逐步骤模式作为对照（4.2 与 4.3 节）。
- 给出对"试次之内发生了什么、还有什么仍然失败、代价是多少"的说明，包括由运行期治理本身引起的失败（4.4、4.5 与 4.6 节）。

**图 2**：RegHarness 治理一次试次之内与运行之间什么会持久化。(a) 审计器审计计划 ➊、草稿 ➋、步骤测试 ➌，以及通过全部步骤但未通过任务检查的已完成计划 ➍。每次步骤测试都在 RATs 逐步骤模式的执行器上重置场景并重放已提交的步骤。控制器仅在验证器通过且审计器提议提交时才提交该步骤。(b) 编程智能体（Claude Opus 5.5）把失败转化为由作者启用的默认关闭开关。

### 2 相关工作

#### 以代码为策略的智能体

语言模型智能体针对感知与控制 API 编写机器人程序［15, 11, 19］，并依据执行反馈一个一个程序地修订它们。Voyager 只有在自验证模块确认任务之后才把一个程序提交到它的技能库［22］。CaP-X 在一次试次之内从不重置环境，因此每个新程序都从上个程序留下的场景开始［7］。RATs 则从重置场景重新运行完整程序，并在运行之后评判其步骤；而 RegHarness 让"步骤"成为被测试与被提交的单位（3.1 节）。

#### 运行期验证与提交闸门

最接近运行期治理的执行架，要么塑造模型感知到什么［14, 28, 3］，要么在执行过程中检查结果［31, 8, 10, 9, 21, 4］，并在失败留下的任何场景中恢复；Recova 先用恢复技能把那个场景恢复过来［17］。同期工作 RegenHarness 在"提议与提交分离"上走得最远：它的模型只负责提议，一个确定性闸门在核对验证器的判定之后才推进四足机器人的可信任务状态［23］，但该论文没有描述如何撤销一次被拒绝的执行。我们改为从重置场景测试每一步——如同 RE-0 恢复仿真器快照以在被蒸馏之前检查代码修正［27］——但这是在**被评测的试次之内**：一次被拒绝的测试由下一次重置丢弃，而已通过的步骤作为被重放的代码持久化（3.2 节）。

#### 由编程智能体做跨运行精炼

ASPIRE 让 Claude Code 修复程序，并把已验证的修复纳入技能库［18］；SHAPER 让冻结的规划器修订自己的技能与上下文代码［24］；HarnessPAI 已经把两个时间尺度分开：跨 rollout 修订一个固定程序，而该程序在一次 rollout 之内检查每一步［4］。同期系统把这套循环带到 LIBERO-PRO 上，围绕一个冻结的 π0.5 策略［1］，由 Codex 元智能体在 VISTA 中探索失败来驱动［29］、由 DynaHarness 中对执行架各层的失败归因来驱动［5］、由 RoboACE 中自生成的课程来驱动［30］；EmbodiedEvo 则让行动智能体自己编写代码技能［13］。RHO 在训练期对策略仓库做搜索［6］，Scale and Selection［25］、TinyAstral［9］、VISTA、DynaHarness 与 RoboACE 都只在与前代做固定比较之后才保留一项改动，而前三个（与 ASPIRE 一样）在留出种子或任务上给结果打分。我们的跨运行精炼缺少第一道保障，因为是由作者来选择启用哪些已测试的、默认关闭的开关；它只从初始状态 0 取材，状态 1–4 是留出的（3.6 与 4.1 节）。

#### 同期工作与我们的位置

不使用 VLA 策略或示教时，AMP1 让一个前沿模型针对运动接口写代码，并在一次尝试内解决多数 LIBERO-PRO 回合［2］；RURL 训练一个推理模型在完全没有执行架的情况下行动［20］。就各论文所报告的内容而言，上述同期系统没有一个同时做到：提交从重置场景测试过的步骤、在没有 VLA 策略的情况下跨任务共享同一个技能库、并在同一批配对试次上把增益拆分到两个层级——RegenHarness 有提交闸门但没有重置，AMP1 每个回合重新写代码，AMP1+ 增加了智能体编写的库但没有提交决策，那些在运行之间精炼代码的工作最多只报告组件消融（对照表见补充材料）。它们的任务、预算、模型与成功规则都与我们不同，因此其已发布成功率（表 2）仅作背景参考。

### 3 方法

RegHarness 复用 RATs 的规划器、编码器与验证器［26］，并增加一个审计器——它可以在计划或草稿运行之前改写它们，但在一次步骤测试之后只能提议——以及一个做决定的控制器；在运行之间它精炼技能（图 2）。

#### 3.1 设定与记号

一个试次从一份保存的初始状态 $s_0$ 出发执行一条任务指令 $g$，有 $P=4$ 个计划、每步 $J=4$ 次尝试。第 $p$ 个计划 $\pi^{(p)}=(\sigma_{1},\dots,\sigma_{n_p})$ 列出各步骤，第 $k$ 步的第 $j$ 次尝试是该步代码的一个草稿 $\tilde{c}_{k}^{(j)}$，一个被运行的草稿只执行一次，在一次步骤测试中重置仿真器并重放已提交步骤的代码 $C_{k-1}=(c_{1},\dots,c_{k-1})$：

$$\bigl(s_{k}^{(j)},e_{k}^{(j)}\bigr)=\mathrm{Exec}\bigl(\mathrm{reset}(s_{0}),\;c_{1}\oplus\cdots\oplus c_{k-1}\oplus\tilde{c}_{k}^{(j)}\bigr) \tag{1}$$

其中 $\oplus$ 在技能前导之后把步骤代码连接成一个程序，$e_{k}^{(j)}$ 是执行记录；当重置成功且程序结束时没有异常、没有超时、也没有对场景的不确定改动时，$\mathrm{ok}(e)$ 成立。验证器返回 $v\in\{\textsf{succeeded},\textsf{failed},\textsf{ambiguous}\}$，而基准的任务检查 $T(s)\in\{0,1\}$ 由控制器读取，在计划运行期间不展示给任何模型。

RegHarness 保留 RATs 的规划器、编码器（现在要求一次只写一步）、静态检查器与逐步验证器，全部运行在审计器的语言模型上，且技能在一次试次之内冻结。它去掉 RATs 的外层重试循环、规划器验证器、预演（4.1 节）、反馈生成器与 SubAgent，并增加 RATs 所没有的、由规划器与计划审计读取的规划规则。

运行期治理复用已发布 RATs 代码中逐步骤模式的执行器（`--multiturn-reset`，第 1 节），但不复用该模式的提交循环。

#### 3.2 从重置场景测试一个步骤

一个草稿只能靠运行来评判，而一次失败的运行已经改变了场景：在本节开头那个任务里，运行期治理使用已发布技能时，第一个计划中的一次抓取尝试把碗从柜子上撞落了。因此每次步骤测试都从 $s_{0}$ 出发、重放已提交的步骤（式 1），于是下一次重置会丢弃被拒绝的测试所做的一切，第二个计划的第一步会发现碗又回到了柜子上。重放是重新执行代码，而不是恢复一份保存的状态，并且不会与它所重复的那次运行作核对，尽管被重放的步骤会复用它当初被提交时所取的抓取采样。与 RATs 自己在两次尝试之间的重置一样，重置-重放需要一个可被重置的场景，而即便在可重置处，有两个 LIBERO-PRO 任务的柜子在每次重置后落定的姿态都不同（场景对比见补充材料）。

对每次尝试都从重置场景测试，代价是重复执行，而不是语言模型调用：一个试次有 $N$ 次步骤测试，第 $t$ 次测试的步骤 $k_t$ 在重放 $k_{t}-1$ 个已提交步骤之后进行，共执行 $B$ 步代码，

$$B=\sum_{t=1}^{N}k_{t},\qquad \text{replayed share}=\frac{B-N}{B} \tag{2}$$

而每次步骤测试还会增加一次重置、对已重放步骤的感知、一次验证器调用与一次步骤审计调用。

#### 3.3 一个任务级审计器

重置也抹掉了失败测试所显示的东西，除非有某样东西能活过它：场景只活一次步骤测试，已提交步骤只活一个计划，审计器的上下文活整个试次，而代码活到下一次运行——只有跨运行精炼才会改变代码（生命周期标注见图 2）。审计器是每个试次一个被恢复的 Codex CLI 会话，运行在其它角色所用的语言模型上，因此一次失败尝试所揭示的东西能在其场景消失之后抵达下一个草稿与计划。它不能调用工具、不能访问环境，并以固定的 JSON schema 回答每次审计（提示与 schema 见补充材料）。

计划审计 ➊ 结合任务、场景的文本摘要以及 API 与技能接口来读每个计划；代码审计 ➋ 结合静态检查器的发现来读每个草稿；两者都不看图像。二者都接受、改写或拒绝：改写替代原始版本运行，而拒绝——与静态检查器的拦截一样——消耗掉该计划或该次尝试。每次步骤测试之后，步骤审计 ➌ 读取被执行代码、其输出的一个片段、验证器判定、剩余预算以及首末两帧相机画面，并提议提交、重试、重新规划或中止，附带一条修正（图 3）。除代码打印的内容外，任何审计都收不到奖励、完成标志、深度、点云、掩码或仿真器状态；最终审计 ➍ 被告知任务未完成。由于审计器与写代码的是同一个模型，它的改写可能引入自己的错误（4.5 节）。

#### 3.4 一个固定规则的控制器

控制器用固定规则把每个提议变成决定，因此同一提议、同一检查与同一预算总是导向同一动作。第 $k$ 步仅当

$$\kappa=\mathrm{ok}(e)\wedge\bigl(v=\textsf{succeeded}\bigr),\qquad \text{commit}\iff\kappa\wedge\bigl(a=\textsf{commit}\bigr) \tag{3}$$

时被提交，其中 $a$ 是审计器的提议。有一项确定性检查可以推翻 $v$：**握持检查**（holding check）会把一个本应抓取或握持物体、却以"夹爪被指令闭合且读数低于 0.03"结束的步骤判为失败——前提是该步骤还有一次尝试。这个阈值是编程智能体依据初始状态 0 上更早运行中的夹爪读数设定的，因此它是在基准上调出来的，可能对一次真正握住的抓取误判。

六条规则按顺序应用，把 $a$、$\kappa$ 与剩余预算映射为一个决定；而一旦任务检查成立，试次在任何规则应用之前就以成功结束（规则与伪代码见补充材料）。无论审计器提议什么，验证器未通过的步骤都不会被提交，即便其尝试次数已用尽；只有预算或任务检查能结束一个试次；实践中规则很少推翻审计器（4.4 节），因此它们提供的是这道保障，而不是自己的决定。

#### 3.5 当已完成的计划未通过任务检查

一个所有步骤都被提交的计划仍可能未通过任务检查，因为每一步只是针对自己的目标被验证。当这种情况发生且还有计划剩余时，最终审计 ➍ 读取各项判定与最后的输出，并指出让错误通过的那一步与那个测量。它最多列出五条改动，用以开启下一个计划，但不能改变结果或请求一次执行。在图 2 的那个试次里，第一个计划没找到"番茄酱"，用一瓶别的酱提交了全部八步；审计把失败追溯到"物体选择，而非搬运"，第二个计划取了那罐番茄酱。

#### 3.6 跨运行精炼

运行期治理决定哪段代码被提交，但那段代码能做什么取决于它调用的技能、原语与规则——这些只在运行之间改变。在跨运行精炼中，编程智能体（Claude Code 中的 Claude Opus 5.5）的子智能体读取一批中每个失败试次的完整日志与帧，指出最早失败的步骤与机制，并把每项精炼变成新代码副本中一个默认关闭的开关。一个开关必须通过单元测试、在关闭时与前一版本逐字节等价、经受进一步智能体的对抗性检查，并通过泄漏审计——从第四轮起，该审计禁止运行时模型看到或执行的任何内容直接读取物体位置或其它来自仿真器的数据（任务检查除外）（泄漏检查见补充材料）。由作者在代码冻结与评测之前决定启用哪些开关，在 LIBERO-PRO 上共五轮；第三轮中他们启用了 55 个拟议开关中的 41 个。

在针对已发布代码登记的 194 项改动中，78 项使代码能与我们的模型与计分一致运行，49 项实现运行期治理本身，40 项修订技能与原语，27 项未定（变更登记见补充材料）；使用已发布技能时的运行期治理保留前两组以及 3 个未定项。技能修订——例如要求手指停在物体上的抓取检查、给抓取网络用的相机帧点云、以及给外观相似实例编号——把库从 59 条扩到 71 条。

这个循环由作者把关，缺少第 2 节所述的自动接受测试；编程智能体还会读取成功检查、完整日志，以及在 MolmoSpaces 设计期间读取基准的真值，而运行时模型只收到最终审计那句"任务未完成"的通知。

### 4 实验

#### 4.1 设置

##### 基准

LIBERO-PRO［32］提供 CaP-X［7］与 RATs［26］所用的那 60 个任务：从 LIBERO［16］的 Object、Goal、Spatial 三个套件各取十个，位置扰动与任务扰动各十个。我们使用每个任务已保存的初始状态 $s=0,\dots,4$，每个"任务–状态"对是一个试次，每个系统只计分一次，作废的运行被完整重跑，且没有一次是在成功之后。

##### 对比系统

对 RATs，我们重跑已发布的代码与技能，加上运行它们所需的改动，沿用代码默认值：每个试次六次尝试、每次执行 180 秒（其论文未说明这些）。**RATs ＋ 逐步骤重放**在同一份代码中打开 `--multiturn-reset`（3.1 节），四次尝试、每步四次尝试、无预演，并对其逐步验证器收到的步骤索引做了两行修复。**RATs ＋ 精炼技能**（仅 RegHarness 的跨运行层）保留默认循环，并携带 64 项技能级精炼中的 51 项，其余属于运行期治理或从未抵达模型。**使用已发布技能时的运行期治理（+ Harness）**（仅试次内层）使用 5,844 个字符的规划规则、四个计划每步四次尝试、每次执行 480 秒；RegHarness 增加精炼技能并把规则扩展到 10,380 个字符。全部五个系统都跑初始状态 0–2 的 180 个配对试次（其中每个试次值 0.56 分），RegHarness 额外跑状态 3 与 4；补充材料列出系统之间的每一项差异。

##### 指标与协议

成功即 RATs 协议［26］下基准的任务检查：智能体在一次试次内不断重试，直到检查通过或预算耗尽，且只由环境做决定。已发布代码还会在计分执行之前，从重置场景"预演"每个程序，仅检查错误——这一步其论文没有描述；一次以任务检查为真结束的预演（在 180 个 RATs 试次中有 65 个如此）不计数，因为已发布的循环会丢弃它并运行计分执行（预演细节见补充材料）。全部五个系统都在执行期间读取任务检查，正如 SPARK 的主要结果［10］所做的那样，我们也没有跑任何不带它的对照。在运行期治理下，任务检查通过之后才抛出的错误不会撤销一次成功（+ Harness 的 105 次成功中有 3 次，RegHarness 的 260 次中有 4 次），而 RATs 论文把每次策略崩溃都计为失败。五个系统都运行的逐步验证器本意是依据目标、代码、打印值与帧来评判一步，但已发布代码无法定位某一步的代码——主要发生在该步描述含有右括号时——此时验证器仅凭帧来评判：这在 RATs 的逐步判定中占 7.7%，在 RegHarness 中占 45.8%；RATs ＋ 逐步骤重放以修复过步骤索引的两行代码运行它，两个执行架系统用各自的输入格式，因此其证据在各系统间的差异及其影响我们未加测量，尽管只有任务检查决定成败。

##### 开发暴露与模型

我们只在初始状态 0 上调试两层，并把状态 1–4 当作测试状态；+ Harness 丢弃哪些改动是在 RegHarness 与 RATs 的结果已知之后才决定的。因此状态 0 既是开发状态，又占配对试次的三分之一，所以精炼技能在这些试次上的增益是一个上界估计，而 RATs ＋ 精炼技能通过其技能继承了这一暴露。每个试次中的每个角色都使用供应方别名 deepseek-flash，思考强度为 "high"。

**图 3**：一些精选的成功案例，其中运行期治理中止了验证器本会接受的执行，或纠正了它拒绝的执行。每行是一个试次，标注其配置；边框标记被中止（琥珀色、红色）与被纠正（绿色）的执行，其它标签为控制器决定。第 1–3 行（LIBERO-PRO）：一次步骤审计 ➌ 拒绝了错误的碗抓取，握持检查在一次步骤审计重试之前推翻了一次被接受的空抓取，一次最终审计 ➍ 把失败的任务检查追溯到错误的物体。第 4 行（MolmoSpaces）：步骤审计把验证器拒绝的三次尝试变成重试。

#### 4.2 LIBERO-PRO 上的主要结果

##### RegHarness 用单一低成本模型解决 86.7% 的 LIBERO-PRO 试次

在五个初始状态上，RegHarness 解决 300 个试次中的 260 个（表 1；95% 置信区间 [79.7, 93.0]，对 60 个任务做自助重采样），从状态 0 到 4 依次为 60 个中 54、53、51、53、49 个。状态 0（其失败驱动了全部精炼）最高，但对 60 个任务的配对检验无法区分这五个状态（Cochran's Q，p = 0.32）；在测试状态 1 与 2 上，RegHarness 解决 104/120，RATs 解决 49。RegHarness 解决 180 个配对试次中的 158 个（87.8%），并保留了 RATs 所解决的 71 个中的除 3 个之外的全部。表 2 中已发布成功率只提供背景、不构成受控比较，我们也没有重跑 RHO 或 HarnessPAI，它们演化后的 LIBERO-PRO 求解器未公开。

#### 4.4 一次试次之内

##### 被拒绝的测试与改写是常态，被改动的提议与最终审计很少

我们没有对审计器的上下文、重放或控制器的规则做消融，因此下面的计数只说明每个机制多频繁地起作用，而不说明它贡献了多少（完整计数、重放失败与假提交见补充材料）。在其 300 个试次中，RegHarness 拒绝了 4,440 次步骤测试中的 1,119 次，其中 452 次发生在机械臂已经移动之后，而它的 260 次成功中有 87 次至少包含这 452 次中的一次。审计器在运行之前改写了 67.3% 的计划与 48.5% 的草稿；在步骤测试之后，它从验证器通过的 3,400 次中扣留了 135 次的提交（图 3 第 1 行），但从未对验证器未通过的步骤提议提交。控制器只改动了 4,440 个提议中的 62 个，全部是因为没有计划剩余；最终审计在 25 个试次中运行，其中 16 个由后续计划解决（第 3 行）；在 260 次成功中，有 56 次的任务检查是在一次审计器并未提议提交的步骤测试之后结束试次的。在配对试次上，一次 RegHarness 步骤测试平均重放 3.1 个已提交步骤，因此被执行步骤片段中有 75.8% 是重放（式 2）。

#### 4.5 还有什么会失败，以及代价

##### 仍然失败的是物体识别、平盘与过低的把手

一个 LLM 智能体给每个失败试次指定"后续任何计划都未能克服的第一个错误"（流程与逐试次类别见补充材料）。在 RegHarness 于五个初始状态上的 40 个失败中，20 个来自错误的物体或部件（16 个）或误读指令/目标区域（4 个），16 个来自未能抓取或推动的平盘（11 个，涉及三个任务）或过低够不到的抽屉把手（5 个，涉及一个任务）；4 个有其它原因。在仅运行期治理的 75 个失败中，5 个是它自己造成的：两个跟在审计器的一次改写之后（低置信度），三个是握持检查（它在图 3 第 2 行捕获了那次空抓取）推翻了一次已经抬起碗的抓取。在 RegHarness 的 40 个失败中，我们核查了 13 个，未发现由运行期治理造成的；另外 27 个中有两个可能是。

##### 这套系统不是免费的

在配对试次上，一个 RegHarness 试次成本估计为 2.16 元人民币（0.32 美元），其中 65.6% 花在审计器上，而 RATs 为 1.51 元（0.23 美元）；平均耗时 66 分钟对 50 分钟。精炼技能在任一种循环下都让一次成功更便宜：RATs ＋ 精炼技能为 1.38 元（0.21 美元）对 RATs 的 3.83 元（0.57 美元），RegHarness 为 2.46 元（0.37 美元）对 + Harness 的 3.85 元（0.58 美元）；而运行期治理在任一技能库下都让一个试次更贵：使用已发布技能时为 2.25 元（0.34 美元）对 1.51 元，使用精炼技能时为 2.16 元对 1.04 元（0.16 美元）（成本估算见补充材料）。RATs ＋ 逐步骤重放最贵，每试次 3.24 元（0.49 美元），每次成功 12.68 元（1.90 美元），因为每一步的每次尝试都要被单独书写与评判。

#### 4.6 MolmoSpaces

##### RegHarness 解决 72.0%（144/200）的 MolmoSpaces 试次

RATs 为 MolmoSpaces［12］发布的 40 条技能库保持逐字节一致，而它调用的抓取与感知函数、接口文档与规则则针对首次移植的 25 个失败做了精炼（那次移植解决 40 个中的 15 个）；因此全部 200 个试次——那些场景的五次重复，每次解决 26 到 30 个——都是样本内的（95% 置信区间 [60.0, 83.0]，对场景自助重采样）。六条抓取-放置指令没有指定放置目标，被计为 30 个失败；在 12 次成功中，程序在任务检查通过之后抛出了错误；RATs 论文在这些任务上报告 38.0%†（任务级结果见补充材料）。

### 5 结论

在 180 个配对 LIBERO-PRO 试次上，RegHarness 的精炼技能单独就把 RATs 从 71 个成功试次提到 135 个，其运行期治理单独达到 105 个，两者结合达到 158 个，而 RATs 自带的逐步骤重放为 46 个。这些结果凸显了技能质量在以代码为策略智能体中的重要性，尤其是在使用低成本模型运行时。虽然从重置场景测试步骤带来额外收益，但其贡献在与更完整的运行期治理框架结合时最为明显。在我们的实验中，两层都只在初始状态 0 上调试，并直接在状态 1–4 上评测。由于状态 0 占配对试次的三分之一，观察到的技能精炼增益可能是一个上界估计。我们还在 Kinova Gen3 机械臂上评估了 RegHarness，它在 45 个试次中解决 28 个，而 RATs 为 21 个。尽管是初步的，这一结果为其超出仿真的潜力提供了初步迹象。重置-重放目前限于仿真。下一步，我们将在初始状态 5–9 上评估冻结的系统，并研究用恢复技能［17］替代机器人上基于重置的执行。

**审计指令**（节选，括号内的省略号表示省略；+ Harness 收到相同片段，但缺少表 S4 所列的那些额外句子）：

- 每次审计：「你是以代码为策略机器人系统外围的有界控制-审计层。除非存在具体的、可核查的缺陷，否则保留原生候选。不要臆造观察、仿真器状态、API 或成功标签。……你只能返回所给 schema 要求的 JSON 对象。」
- 计划审计：「只依据下列规则审计原生计划的语义。原样接受（ACCEPT）、通过返回完整的替换 `output_plan` 来修订（REVISE），或以具体的计划级缺陷拒绝（REJECT）。修订后的计划必须仍然植根于可见的原生上下文。」
- 代码审计：「审计一个计划步骤的主体。原样接受、以 `final_body` 修订，或拒绝。`final_body` 的值本身必须是裸的可执行步骤代码：绝不要把包装函数或 RESULT 赋值放进 `final_body`。」
- 步骤审计：「仅当沙箱成功且原生逐步状态恰为 succeeded 时才选择 COMMIT；否则以具体修正重试、重新规划或中止。」在一个计划的最后一步还有：「这是该计划的最后一步：提交它就结束回合并声称任务完成。这次执行的打印输出还包含更早步骤的检查，那些步骤在此步之前被重放。如果其中任何检查、或本步自身的检查报告某个意图效果没有发生，就不要 COMMIT，即便逐步状态为 succeeded；当原因在本步自身的动作中时重试，当原因在更早已提交的步骤中时重新规划。」
- 最终审计：「在这次计划尝试的原生结果之后审计过程一致性，并分析其失败。该计划的每一步都被提交了，但环境自身的检查报告任务未完成；执行架将开始另一个计划尝试并把你的发现传给它。……不要猜测隐藏的仿真器状态。你不能改变 `benchmark_success`，也不能请求执行。总是返回 `recommendation=close`。」

**运行 RATs**。我们的 RATs 基线是已发布代码［26］，改动五个文件并增加一个本地代理。它使用完整的感知 API 与 Contact-GraspNet 抓取采样器，因为在默认评测接口下，在用的 45 个已发布技能中有 36 个无法被调用。

**预演**。已发布配置会把每个通过静态检查的程序，在计分执行之前从重置场景运行一次——这是 RATs 论文未描述的一个阶段；两次运行从同一重置场景与种子执行同一程序字符串，且不使用预演的任务检查。在 782 次预演中有 77 次在其结束时为真，出现在 180 个试次中的 65 个里。在 741 对"预演与同一程序的计分执行"中（另 41 次预演抛出了错误），有 76 对结局不同（精确 McNemar p = 0.57）。

**RATs ＋ 逐步骤重放**。在逐步骤模式中，已发布的逐步验证器把单个步骤索引为第一步。RATs ＋ 逐步骤重放修正了逐步验证器中的这个索引错误，未改动其它代码。当更多试次共享同一台机器时，目标类任务中的执行更常触及 180 秒上限，这可能拉低它的结果。

**RATs ＋ 精炼技能**。它携带 + Harness 从 RegHarness 中移除的 64 项改动中的 51 项，43 项逐字、8 项改写；另有一项（那对指引条目）在两个框架中都从未抵达模型，还有十二项只存在于 RATs 所缺的规划规则、审计指令或修改过的规划器中。RATs 的静态检查器会拒绝"以验证结果为条件来控制释放或放置"的程序，而握持验证类技能的文档鼓励这种写法，于是每一次拒绝（无论原因）都消耗一次尝试（该系统 680 个被检查程序中的 139 个）；SubAgent 无法调用新技能。

**作废的运行**。每个试次只计分一次：因基础设施或协议故障而中止的进程被丢弃，试次从头以完整预算重跑。在 LIBERO-PRO 上，这使两个执行架系统的 493 个进程中作废 13 个，没有一个是在任务检查通过之后；10 次重跑成功，其中两次在两次进程合计中用了多于四个计划。没有 RATs 进程被作废，被中断的 RATs ＋ 逐步骤重放与 RATs ＋ 精炼技能试次以同样方式重跑。在 MolmoSpaces 上重跑六个试次且全部成功，其中一次是在策略自身代码导致的内存溢出终止之后——我们把它计为基础设施故障；用更早一组开关运行的 MolmoSpaces 试次未报告。

**统计**。比率与配对差异的区间来自对 60 个任务做自助重采样（同一任务的全部初始状态一同重采样）；我们报告第 2.5 与第 97.5 百分位。配对检验是对不一致试次的双侧精确 McNemar 检验。

## 与路线图的挂接

- **A2-05（工具接口设计）**：这篇把"接口"这个概念推到了执行架的每一层，并给出一条很硬的判据：**提议与提交必须分离**。审计器可以改写计划与草稿（在运行之前），但在步骤测试之后它只能"提议"，提交由固定规则的控制器做，且 `commit ⇔ κ ∧ (a = commit)`——验证器不通过就绝不提交。注意作者对控制器的诚实评价：六条规则"很少推翻审计器"（4,440 个提议中只改了 62 个），所以规则的真正价值不是做决定，而是提供一道**不可绕过的保障**。设计工具接口时同理：校验层的价值往往不在它多聪明，而在它无法被绕过。
- **A3-03（长期记忆的写入与遗忘）**：这是全文最容易被忽略、但最重要的一条。作者给出的三段时间尺度值得直接抄进设计文档：场景只活一次步骤测试，已提交步骤只活一个计划，审计器的上下文活整个试次，而代码活到下一次运行（且只有跨运行精炼才改代码）。它同时暴露了"重置"这个看起来很安全的动作的代价——重置保护了重试的步骤，但也抹掉了失败测试所揭示的信息，所以必须有"比重置活得更久"的记忆来承接。技能库的写入治理同样具体：默认关闭、必须过单元测试、关闭态逐字节等价、对抗性检查、泄漏审计，最后由人启用（第三轮启用了 55 个中的 41 个）。
- **延伸读到 A6-03（评测门禁与回归）与 A0-02（架构师真正负责的质量属性）**：2×2 拆解本身就是一次评测设计示范——它证明"整体配置变好"不等于"你以为是那个机制在起作用"。RATs 自带的逐步骤重放只有 46 个成功试次（比 RATs 本身还少），说明"重置"单独并不解释运行期治理的 105；而 + Harness 的 105 里又混入了更长的规划规则与更宽的时间限制。作者把这些混杂因素逐条列出而不是掩盖，这是本文在方法论上最值得学的地方。成本侧则给出 A0-02 里"成本"这条属性的真实量级：每试次 2.16 元、每次成功 2.46 元，而 RATs ＋ 逐步骤重放每次成功要 12.68 元。
