## 知识点 1：模型路由与级联降级（A1-06）

### 一句话结论

**路由器的判据，比路由器本身更重要。** 一个能说清"什么情况下该升级"的规则表，胜过十个黑盒分类器；因为规则表可以被评审、被回归、被写进 ADR，而分类器只能被相信。

### 为什么重要

先看省钱的幅度。假设任务分布是典型的 80/20：80% 简单、20% 难。用第 003 期的示例单价：

```
全用强模型：        $1.95 / 任务
路由（80% 快 + 20% 强）：
  0.8 × $0.104 + 0.2 × $1.95 = $0.083 + $0.39 = $0.473 / 任务
省 76%
```

**但路由会引入一类新错误：错判。** 假设路由器把 5% 的难题误判成简单题，这些请求用快模型必然失败：

```
失败率 ≥ 5%（还不算快模型本身的失败）
每个失败按 10 分钟人工返工、100 元/小时计 = 16.7 元
每天 1,000 任务：1,000 × 5% × 16.7 ≈ 835 元/天
```

对比省下的钱（每天约 1,477 元），**净收益仍在，但只剩一半**。如果错判率是 15%，净收益就没了。

**这就是路由的核心张力：路由器越激进，省得越多，错判也越多。** 而错判的代价，取决于你有没有"失败可判定"（A0-04 第三问）——没有判定器，错判就是静默错误。

### 核心机制：三条路由策略 + 一条级联

| 策略 | 怎么判 | 优点 | 缺点 |
|---|---|---|---|
| **静态路由** | 按任务类型/租户/入口写死 | 可预测、可解释、零成本 | 不区分难度 |
| **启发式路由** | 按输入长度、工具数、是否含代码等特征 | 便宜、可解释 | 阈值靠调，容易过拟合 |
| **学习型路由** | 训练一个分类器判"难不难" | 精度上限高 | 黑盒、要标注、会漂移 |
| **级联** | 先便宜跑，判定不过再升级 | 不需要预判难度 | 慢一倍（失败才升级）、要判定器 |

**级联比路由更稳，但更慢。** 它的前提是"能快速判定第一次的结果行不行"——这就是为什么 A1-04 的四道关是级联的前置条件。**没有判定器，级联退化成"贵的那次总是白跑"。**

### 怎么做

1. **先有评测集，再谈路由。** 没有 30 条带标签的任务，你无法知道错判率。
2. **优先用静态 + 启发式**，学习型路由留到"规则已经榨干"之后。
3. **给路由决策留痕**：每次记录"判给了谁、依据什么特征、置信度多少"。这是你唯一能复盘错判的数据。
4. **把升级条件写成可执行规则**：不是"看起来难"，而是"工具数 > 5""输入含 SQL""上一次校验失败"。
5. **降级路径必须被验证过**：备用模型在这批任务上的失败率是多少？没测过就不算有降级。
6. **给路由设熔断**：某条路径失败率突增，自动切回单一模型，先保证可用。

### 权衡与坑

- **路由器是新的单点。** 它挂了，全系统挂。要有"绕过路由"的开关。
- **路由会让成本变得不可预测。** 财务报表上你只知道总数，不知道钱花在哪类任务上。所以要按任务类型分账。
- **缓存与路由会打架。** 不同模型的前缀缓存不共享，频繁切换会让缓存命中率归零——省下的单价可能被缓存失效吃掉。
- **别用"模型自评难度"当唯一判据。** 模型对自己难度的判断并不可靠，而且它会倾向于说"这题简单"。
- **错判的方向要选对**：宁可把简单题误判成难题（多花钱），也不要把难题误判成简单题（静默失败）。

### 自测题

1. 用你的任务分布算一遍：如果 70% 走便宜模型、30% 走强模型，平均成本是多少？错判率上升到多少时，路由就不划算了？
2. 为什么"级联"依赖判定器？没有判定器时，级联的实际成本是多少（用期望值表达）？
3. 你的路由如果错判，会往哪个方向错？这个方向你能接受吗？

## 知识点 2：三种循环（A2-01）

### 一句话结论

**ReAct 是自由循环，Plan-Execute 是先规划再执行，Reflection 是在结果上再想一遍。** 三者的差别不在"智能程度"，而在**步数可控性**——而步数直接决定端到端可靠性（`0.95ⁿ`）、成本与可测性。

### 为什么重要

**先算步数。** 同样一个任务：

```
ReAct：平均 8 步，p95 25 步      → 可靠性 0.95⁸ ≈ 0.66，成本方差极大
Plan-Execute：3 步规划 + 2×k 步执行（k=3）→ 9 步，但步数可预测
Reflection：ReAct + 每 3 步一次反思 → 10–12 步，多 2–4 次模型调用
```

**注意这里的关键不是"哪个更准"，而是"哪个的尾部长"。** ReAct 的 p95 是平均的 3 倍，意味着你的容量规划、成本预算、超时设置都要按 25 步来做——而 90% 的请求根本用不到。

**再看可控性。** 有合规要求、有副作用、需要审计的场景，你必须能回答"这一步为什么发生"。自由循环里，答案只有"模型当时这么想"；状态机里，答案是"状态 A 在条件 B 下必然转到 C"。**这是可审计性的差别，不是性能的差别。**

### 核心机制：三种循环的数据流

```
ReAct（自由）
  观察 → 想 → 选一个动作 → 执行 → 观察 → …（直到模型说完成）
  特点：步数由模型定；适合探索型任务；难测、尾部长

Plan-Execute（先规划）
  规划（一次）→ 逐步执行 → 每步校验 → 失败则重规划
  特点：步数可预测；适合流程清晰但分支多的任务；规划错则全错

Reflection（自省）
  执行一轮 → 用外部信号（测试/校验/评委）评估 → 修正 → 再执行
  特点：能纠错，但**必须有外部信号**；没有信号的反思是自我确认
```

**Reflection 的成败完全取决于"信号从哪来"。** 如果反思的依据还是模型自己的判断，那它只是在给同一个错误找新理由——这在评测里叫"自我偏好"，在工程上叫"花钱买安慰"。

### 怎么做

1. **先用 Plan-Execute 起手**：把任务拆成"可校验的步骤"，每步有明确的成功条件。这是最容易测、最容易收敛的结构。
2. **把 ReAct 限制在"探索性子任务"**：给子任务设步数上限（如 5 步）和预算上限，超了就必须返回"未完成"。
3. **Reflection 只在有外部信号时开**：测试通过率、schema 校验、规则检查、人工抽检。没有信号就别开。
4. **混合结构最常见也最实用**：外层 Plan-Execute（保证可审计），内层 ReAct（处理单步内的不确定性）。
5. **每个循环都要有"退出三件套"**：最大步数、最大成本、最大时长。缺一个就是一次会烧钱的 bug。

### 权衡与坑

- **Reflection 会让成本翻倍且收益不确定。** 有信号时它很值（测试驱动修复）；没信号时它只是把一次错误变成两次。
- **Plan 会过时。** 执行到第 4 步发现前提变了，必须有"重规划"入口，否则会沿着错误计划一路走到底。
- **自由循环的失败往往"看起来成功"。** 模型说"已完成"，但终态没检查——所以 A0-04 的终态判定比循环选型更重要。
- **别用循环复杂度冒充能力。** 三层嵌套的 agent 通常不如"一层 + 更好的工具 + 更清楚的终态"。
- **步数上限要按 p95 设，不是按平均。** 按平均设上限，会砍掉 10% 的正常请求。

### 自测题

1. 你的当前循环属于哪一种？它的 p95 步数是多少？端到端理论成功率是多少？
2. 为什么"没有外部信号的 Reflection"是有害的？请用"自我偏好"解释。
3. 给一个"外层 plan + 内层 react"的具体设计：外层几步、内层上限几步、判定器是什么？

## 今日观察

- **今天五篇其实在讨论"沉淀"这件事的五个层次**：技能（第 1 篇）沉淀的是流程；记忆（第 2 篇）沉淀的是事实；代码执行（第 3 篇）沉淀的是"少定义、多组合"；跨模型通信（第 4 篇）把沉淀变成了**安全边界**；经验规模化（第 5 篇）问的是"沉淀能不能迁移"。
- **一个反直觉点：记忆越多，系统越难解释。** 第 2 篇标题里的"记忆幻觉"值得警惕——写进去的东西会被模型重新解释，越用越偏。这解释了为什么"记忆"必须配"遗忘与校验"，就像第 004 期说的上下文必须配压缩。
- **第 3 篇给 A1-02 一个漂亮的解法**：当工具多到上下文装不下时，不要优化工具定义，而是**换一种调用方式**——让模型写一小段代码去调工具，上下文里只留代码。这是"用结构换容量"的典型。
- **第 4 篇提醒了一件容易被忽略的事**：多智能体系统里，agent 之间传递的东西**不只是文本**。如果你的架构假设"通信内容是可读可审的"，那这个假设本身就是一个风险点。
