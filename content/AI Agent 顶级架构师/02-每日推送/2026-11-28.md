## 今日速览

- **A0-03 四种形态：chat / copilot / autopilot / 后台自治**：区分它们的不是"智能程度"，而是**谁发起、谁批准、失败由谁承担**。形态决定了人机接口、审批点与失败代价，一旦选错，后面所有工程投入都在给错误的方向加固。
- **A0-04 该不该用 Agent 的判据**：判据不是"够不够先进"，而是三个可测量的问题——**路径是否确定、错误是否可逆、结果是否可判定**。三个都过关才该上 Agent；有一个不过关，workflow 或人机混合会更便宜、更可靠。

## 知识点 1：四种形态（A0-03）

### 一句话结论

**形态由"谁发起、谁批准、谁承担失败"三个问题定义，不由模型能力定义。** 同一个模型，做成 chat 是问答工具，做成 copilot 是帮手，做成 autopilot 是代驾，做成后台自治是员工——四种形态的失败代价、审批设计和成本结构完全不同。

### 为什么重要

先看一张表，它决定了后面所有设计：

| 形态 | 谁发起 | 谁批准 | 失败代价 | 典型设计要点 |
|---|---|---|---|---|
| **chat** | 人 | 人（每次都看） | 一句话说错，用户当场发现 | 延迟优先、上下文短、无需状态 |
| **copilot** | 人 | 人（接受/拒绝建议） | 采纳了错建议，人背锅 | 建议要可解释、可撤销、低干扰 |
| **autopilot** | 人 | 人（关键节点） | 执行错一步，可能已产生副作用 | 状态机收窄、副作用前置确认 |
| **后台自治** | 事件/调度 | 人（异步事后审） | 无人值守时反复做错，且越做越远 | 预算上限、审计轨迹、可中断、可回滚 |

**为什么说选错形态是最贵的错误？** 因为形态决定了三件不可逆的事：

1. **审批点在哪。** chat 天然每步都有人看；后台自治天然没人看。你在后台自治里补审批，等于把人拉回 copilot——那当初为什么要做后台？在 copilot 里省审批，等于把风险直接甩给用户。
2. **失败被谁发现。** chat 的失败由用户秒级发现；后台自治的失败可能三天后才由客户投诉发现。这直接决定你需要多强的可观测性（M6）。
3. **成本模型。** chat 的成本是"每次提问一个 token 预算"；后台自治的成本是"每个事件 × 每次唤醒 × 可能的重试"，还要加上长期记忆的存储与整理成本。用 chat 的预算去接后台自治，账单必然失控。

**一个真实的产品教训**（来自 Anthropic 关于托管智能体的复盘，见今日前沿第 4 篇）：他们在执行架里加了"上下文重置"，因为发现模型在接近上下文上限时会**提前收尾**（他们叫 context anxiety）。但换到更强的模型后，这个行为消失了——重置变成了**死重**。这说明：**形态与执行架里写满了"我们当时认为模型做不到什么"的假设，而这些假设会过期。** 形态一旦定死，假设就跟着定死了。

### 核心机制：形态是一条"自治度"连续谱

```
chat ── copilot ── autopilot ── 后台自治
 人全程在场            人逐渐退出            人只在事后出现
 副作用=0              副作用=建议            副作用=真实世界
```

沿这条谱向右移动一格的代价，大致是：

| 移动 | 你需要新建什么 | 你失去什么 |
|---|---|---|
| chat → copilot | 上下文注入、建议采纳率度量 | 用户注意力（每次建议都是一次打断） |
| copilot → autopilot | 状态机、工具权限、可回滚的副作用 | 即时纠错能力（错了要等下一轮） |
| autopilot → 后台自治 | 事件源、调度、记忆、审计、预算上限 | 全部人工监督（只剩事后审计） |

**判据：向右移动一格，必须有一样东西换来。** 换来的是"人的时间被省下来"或"响应速度提升 N 倍"。如果换不来，就不该动。

### 怎么做

1. **写清三问**：谁发起这次运行？谁在哪个节点批准？失败由谁承担、多久能发现？
2. **画出"副作用地图"**：哪些动作会改变外部世界（发邮件、改数据、付款、发布）。形态越靠右，副作用越要靠左确认。
3. **定义退出路径**：后台自治必须能"暂停—检查—回滚"，否则它不是一个产品，是一次赌博。
4. **给形态配预算**：chat 按次、copilot 按建议、autopilot 按任务、后台自治按"事件 × 唤醒次数"。

### 权衡与坑

- **形态不是越右越好。** 后台自治听起来最"智能"，但它的调试成本、审计成本、信任建立成本都是最高的。绝大多数业务场景，copilot 的投入产出比最好。
- **别把"无人值守"当卖点。** 无人值守的真正成本转移到了"事后审计"，如果审计做不出来，省下的人力会以事故形式还回来。
- **形态可以演进，但要留路。** 从 copilot 演进到 autopilot，最贵的不是模型，而是"当初没存状态"。第一版就应该把状态外置（M3 会讲），否则演进时要重写。
- **警惕"假 copilot"**：如果用户 95% 的情况都直接接受建议、不看内容，那它事实上已经是 autopilot，只是责任还挂在人身上——这是最危险的组合。

### 自测题

1. 一个"自动整理会议纪要并发到群里"的需求，属于哪种形态？请用三问（谁发起/谁批准/谁承担失败）回答，并指出它最容易在哪一步出事。
2. 为什么"假 copilot"（用户基本不看就接受）比明确的 autopilot 更危险？
3. 你的项目如果要从 copilot 演进到 autopilot，现在缺哪三样东西？

## 知识点 2：该不该用 Agent 的判据（A0-04）

### 一句话结论

**用不用 Agent，取决于三个可测量的问题：路径是否确定、错误是否可逆、结果是否可判定。** 三个都过关才该上；任何一个不过关，workflow、规则引擎或人机混合都更划算。

### 为什么重要

行业默认"新项目就该上 Agent"，这和"新项目就该上微服务"是同一种病。Agent 的代价是**不确定性**：步数不定、成本不定、结果不定。你付这笔钱，是为了换取"处理无法预先枚举的情况"的能力。如果这个能力你用不上，那你只是在为不确定性付费。

**先做一道算术。** 假设一个任务用固定 workflow 实现，5 步、每步 99% 可靠（确定性代码，很容易做到）：

```
workflow: 0.99⁵ ≈ 0.951     ← 成本固定、延迟固定、可测
agent   : 0.95¹⁰ ≈ 0.599    ← 步数不定、成本不定、需要评测体系
```

如果这个任务的输入分布是稳定的（比如"从固定格式的发票里抽字段"），用 Agent 就是**用 60% 的可靠性换一个你不需要的灵活性**。

反过来，如果输入分布不稳定（"帮我处理这个客户的各种奇怪请求"），workflow 会因为枚举不完而卡死——这时候 Agent 的不确定性是**必要成本**。

### 核心机制：三问筛选

| 问题 | 过关的样子 | 不过关怎么办 |
|---|---|---|
| **路径确定吗** | 完成任务的步骤每次都不一样，无法预先枚举 | 写成 workflow / 状态机 |
| **错误可逆吗** | 错了能撤销，或错了代价可接受 | 加人工审批，或改成只读/建议形态 |
| **结果可判定吗** | 有代码能检查的终态（测试通过、字段齐全、状态变更） | 先补判定手段，否则无法验收也无法回归 |

**第三问最容易被跳过，也最致命。** "结果可判定"不是"人看一眼觉得行"，而是"程序能说是或否"。没有可判定终态的系统，你既不能自动重试，也不能做回归测试，更不能在无人值守时保证质量——它只能永远挂在人身上。

**一个常被忽略的第四问：错误代价 × 犯错概率 是否可接受？** 这就是 Anthropic 在围栏那篇文章里用的框架：风险 = 失败概率 × 单次失败的破坏范围（他们叫 blast radius）。工程上能压的通常是后者——**限制它能碰的东西**，而不是指望它不犯错。

### 怎么做

1. **先写 workflow 版本**，再看它卡在哪。卡在"枚举不完的分支"上，才考虑 Agent。
2. **给每个分支标确定性**：能写成 if/else 的，绝不交给模型判断。
3. **设计终态检查器**（30 分钟能写完的那种）：文件存在？字段非空？测试通过？状态合法？
4. **算一次最坏情况**：步数上限 × 单步成本 × 重试次数，看这个数你是否愿意为一次失败买单。
5. **能降级就降级**：Agent 失败时回落到 workflow 或人工，比让 Agent 硬扛更专业。

### 权衡与坑

- **"我们以后会有复杂需求"是最贵的理由。** 为想象中的复杂度付今天的确定性，通常不划算。
- **Agent 不等于"更少的代码"。** 它把代码里的分支，换成了提示词里的判断和一堆兜底逻辑，维护成本往往更高。
- **小心"演示效应"。** 20 个精心挑的 demo 输入，证明不了分布上的可靠性。要看的是失败率与失败模式。
- **别用 Agent 做权限判断。** "这个人能不能看这条数据"必须是代码，且必须在工具层，不在提示层。

### 自测题

1. 用三问判断："自动给新提交的 PR 打标签并分派 reviewer"。哪一问可能不过关？怎么补？
2. 一个 5 步的确定性 workflow（每步 99%）与一个 10 步的 Agent（每步 95%），端到端可靠性各是多少？在什么条件下你仍然会选 Agent？
3. "限制它能碰的东西"为什么比"让它别犯错"更有效？请从可验证性角度说一句。

## 今日观察

- **四篇讲形态的文章，其实都在同一件事上打架：谁来兜底。** 从任务到目标，是把兜底从"人盯着"移到"目标定义清楚"；目标工程，是把兜底写进验收标准；托管智能体，是把兜底做成平台接口；科学家划线，是明确说"这几步我不交"。**形态选择的本质，是选一个兜底机制。**
- **一个反直觉点：自治度越高，对"终态可判定"的要求越硬。** chat 可以靠人脑判断"这回答行不行"，后台自治不行——它没有人在场，你必须事先把"行不行"写成代码。所以 A0-04 的第三问，是从 copilot 走向后台自治的**准入门槛**，不是加分项。
- **托管智能体那篇的教训值得单独记**：执行架里的每个"补救措施"，都是对模型缺陷的临时假设。这些假设要定期复查，否则会变成拖累——**架构债的一种，专门由模型进步产生。**
- **今天不需要你做任何技术选型**，只需要你承认一件事：形态是产品决策，不是工程细节。它一旦定错，M1–M9 的所有优化都在错误的坐标系里。
