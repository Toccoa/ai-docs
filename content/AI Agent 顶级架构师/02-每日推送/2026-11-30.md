## 今日速览

- **A1-02 Token 经济学与上下文窗口**：上下文有两条成本曲线，一条是钱（随 token 线性涨），一条是**精度**（随长度非线性降，业界叫 context rot）。所以真正的约束不是"窗口多大"，而是"多少 token 之后模型开始看不住"。把窗口开大，只解决了第一条。
- **A1-03 采样参数与可复现性**：`temperature=0` 不等于确定性。批处理顺序、GPU 浮点归约、MoE 路由、工具版本、环境镜像，任何一处漂移都能让"同样的输入"给出不同轨迹。**评测要的不是点复现，是分布复现。**

## 知识点 1：Token 经济学与上下文窗口（A1-02）

### 一句话结论

**上下文是有限注意力预算，不是免费硬盘。** 好的上下文工程，是在预算内找到那组"最小的高信号 token"。判断标准不是"塞够了吗"，而是"删掉这一段，模型还会做对吗"。

### 为什么重要

**第一条曲线：钱。** 输入 token 按量计费，所以"每轮把全部历史带上"的成本随轮数**平方增长**。

算一笔：10 轮对话，历史每轮增长 1,500 token，全程累加：

```
输入 token 总量 = 1,500 × (1+2+…+10) = 82,500
按 $3/M 计 = $0.2475 / 次任务
```

改成"只带最近 3 轮 + 一份 2,000 token 的滚动摘要"，每轮固定约 4,500 token：

```
输入 token 总量 = 10 × 4,500 = 45,000
按 $3/M 计 = $0.135 / 次任务
```

**省了 45%。** 而且这还没算缓存——命中的前缀通常只按 10% 计价，进一步拉开差距。

**第二条曲线：精度。** 这条更贵，因为它不体现在账单上。随着上下文变长，模型对其中信息的**准确召回能力下降**（context rot）。机制不是玄学：Transformer 里 n 个 token 之间有 **n² 个两两关系**，上下文翻倍，注意力要覆盖的关系翻四倍；模型在训练时见到的长序列又远少于短序列，对长程依赖的参数本来就更少。位置编码插值能让模型"处理"更长序列，但那是**渐变带**，不是消除退化。

**两件事合起来，得到一个反直觉结论：把窗口从 200k 开到 1M，不解决"我看不住 200k"的问题。**

### 核心机制：上下文的六个账户

把每次调用的上下文当预算表，六个账户各有上限：

| 账户 | 装什么 | 典型占比 | 涨起来最凶的原因 |
|---|---|---:|---|
| 系统提示 | 角色、规则、格式要求 | 5–15% | 规则越加越多，没人删 |
| 工具定义 | 工具名、schema、说明 | 10–30% | 工具数量线性增长 |
| 对话历史 | 用户与助手的往返 | 20–40% | 累加不裁剪 |
| 检索结果 | 文档片段、查询结果 | 10–30% | 一次塞 10 篇全文 |
| 工具输出 | 命令返回、报错、日志 | 10–40% | **最容易失控**，一条 stack trace 就几千 token |
| 工作区 | 笔记、计划、进度 | 5–10% | 不清理的临时文件 |

**"工具输出"是最常被忽略的账户。** 一个失败的命令可能返回 8,000 token 的报错与日志，而其中只有 20 行有用。不清理它，等于每轮都在为垃圾付费，还顺带稀释注意力。

### 怎么做

1. **给每个账户设硬上限**，超了就触发压缩而不是继续追加。
2. **四把刀，按代价从低到高用**：
   - **裁剪**：只保留工具输出的前 N 行 + 错误摘要（最便宜）。
   - **压缩**：把旧历史摘要成要点（丢掉原话，保留决策与未决问题）。
   - **外部化**：把长内容写进文件/笔记，上下文里只留"在哪、多大、怎么取"。
   - **按需检索**：不预加载，让模型在需要时自己查（增加延迟与失败点，最后才用）。
3. **每轮问一次"删掉这段会怎样"**。删了还能做对，说明它本来就不该在。
4. **把"上下文占用"变成可观测指标**：每轮记录六个账户各占多少，你会立刻看到谁在膨胀。

### 权衡与坑

- **压缩会丢细节。** 摘要适合丢"过程"，不适合丢"约束"（金额、ID、期限）。约束类信息应当结构化保留，不要摘要。
- **检索不是免费的。** 每次检索多一次往返、一个失败点、一段不确定的相关性。高频检索换来的不一定是精度。
- **外部化要求模型会读写。** 它得知道去哪找、格式是什么。没有约定好的笔记协议，外部化等于把信息扔进黑洞。
- **上下文缓存能省钱，但会掩盖设计问题。** 命中率高的系统可能只是"每轮都在重复同样的前缀"，不代表上下文用得好。
- **别用"窗口够大"当架构假设。** 按"精度开始下降的那个长度"设计，而不是按标称窗口设计。

### 自测题

1. 你的 agent 一次调用里，六个账户各占多少？哪一个是最大的？你上次删它是什么时候？
2. 为什么"上下文翻倍，注意力关系翻四倍"？这个机制如何解释"窗口开大不解决问题"？
3. 工具输出占了你多少 token？写一条规则，把它压到原来的 20%。

## 知识点 2：采样参数与可复现性（A1-03）

### 一句话结论

**`temperature` 改的是分布，不是事实；`seed` 定的是采样，不是系统。** 想要可复现，你要固定的是整条链路（模型版本、参数、提示词、工具、环境、并发），而 Agent 评测真正需要的不是"每次一样"，是"分布一样"。

### 为什么重要

团队最常做的两件事，都建立在错误假设上：

- "把 temperature 设成 0，结果就稳定了。" —— 不成立。温度 0 只是取最高概率 token，而**最高概率 token 会随批处理组成、浮点归约顺序、MoE 专家路由变化**。同一份输入在不同 batch 里，可能落到不同专家上，输出就分叉。
- "固定 seed 就能复现 bug。" —— 不成立。seed 只影响采样器；工具返回的时间戳、网络抖动、容器里的文件残留、模型供应商的静默升级，seed 一个都管不住。

**后果很具体**：你无法用"跑一次看看"来验证修复。昨天好的今天坏了，你不知道是代码变了还是环境变了。这时候唯一可靠的判断方式是**统计**：跑 k 次，看通过率与失败模式，而不是看单次输出。

### 核心机制：不可复现的五个来源

| 来源 | 例子 | 能不能控 |
|---|---|---|
| **采样** | temperature、top_p、seed | 能（但只是五分之一） |
| **数值非确定性** | 浮点归约顺序、并行 kernel、batch 组成 | 部分（禁批处理、固定并发可减小） |
| **模型版本** | 供应商静默更新权重 | 能（锁版本号 + 定期回归） |
| **环境** | 容器镜像、依赖版本、时区、文件残留 | 能（镜像固化、每次干净启动） |
| **外部世界** | 网页内容变了、API 返回变了、时间戳 | **不能**（只能记录快照） |

**这张表的用法**：前四项是你的责任，第五项是设计约束。对第五项，正确做法不是"求它别变"，而是**把外部输入录下来做回放**（录制—回放测试），这样评测才不被外部世界拖着走。

### 怎么做

1. **记录七元组**，每次运行都存：模型版本 / 采样参数 / 提示词哈希 / 工具版本 / 环境镜像 tag / 输入快照 / 随机种子。
2. **把"可复现"降级成"可比较"**：不追求两次输出逐字相同，追求同一批任务上的通过率与失败分布可比。
3. **评测跑 k 次**（k ≥ 3），报 `pass@k` 与 `pass^k` 两个数。前者衡量"有没有一次能成"，后者衡量"是不是每次都能成"。
4. **锁版本**：模型名后面跟具体版本，依赖用锁文件，镜像用 digest 而不是 latest。
5. **隔离环境**：每次评测用干净容器，别让上一次的残留文件影响这一次。

### 权衡与坑

- **追求严格确定性会牺牲性能。** 禁批处理、强制单并发能让结果更稳，但成本翻倍。只在"必须复现的回归场景"这么做。
- **`pass@k` 会系统性高估可靠性。** 8 个任务各跑 3 次，`pass@3 = 7/8` 看起来几乎全对，`pass^3 = 1/8` 说明只有一个任务次次都对。无人值守的系统，看后者。
- **温度不是"创造力旋钮"。** 低温不等于更准确，它只是更保守；有些任务低温反而更容易陷入重复。
- **别在评测里用生产环境的实时数据。** 数据会变，评测就不可比。要么快照，要么固定数据集。
- **"我们没改什么"通常是最危险的假设。** 供应商升级、依赖小版本更新，都在你没改的情况下改变行为。

### 自测题

1. 为什么 `temperature=0` 仍然可能给出不同输出？举两个机制。
2. 你的评测跑了 20 个任务各 3 次，结果 `pass@3 = 0.95`、`pass^3 = 0.55`。这两个数分别说明什么？如果这是无人值守系统，你该看哪个？
3. 外部世界不可控，你怎么让评测仍然可比？说出一种具体做法。

## 今日观察

- **五篇里有三篇在讲同一件事：上下文与执行架的边界正在融合。** 以前"上下文管理"是提示词层面的技巧，"执行架"是代码层面的编排；现在模型开始自己决定读什么、记什么、丢什么，两者的分界线必须重新画。
- **TransHarness 的提问方式值得抄**：它不问"这个执行架在基准上多高"，而问"它在新任务上还能不能保住优势"。这和 A0-05 的推翻条件是一回事——**任何在特定集合上调出来的东西，都要问迁移性。**
- **RegHarness 把"沉淀"变成可治理对象**：agent 从一次次步骤中留下的东西（笔记、技能、启发式），会变成下一轮的上下文与行为。**留下的东西越多，系统越难解释**——这解释了为什么"记忆"必须配"遗忘"。
- **一个提醒**：今天两篇 arXiv 都是 2026-11-25 的，属于"48 小时内"口径里最新的一批。这类论文的共同特点是**问题定义比方法更值得读**——方法是针对某个基准的，问题定义往往能迁移到你的系统。
