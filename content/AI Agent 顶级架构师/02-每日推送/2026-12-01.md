## 知识点 1：结构化输出与工具调用协议（A1-04）

### 一句话结论

**schema 是模型与系统之间的契约；系统必须假定对方会违约，并准备好三种处置：校验、修复、降级。** 只做"重试"是最常见也最没用的处置。

### 为什么重要

工具调用是整条链路上唯一"自然语言变结构化"的地方，也是错误最集中的地方。错误分两类，处置方式完全不同：

| 错误类型 | 例子 | 能否靠重试修好 |
|---|---|---|
| **语法错** | JSON 少括号、字段名拼错、类型不符 | 通常能（约束解码下基本消失） |
| **语义错** | 参数格式全对，但 `order_id` 是编的、金额单位搞错、时间用了今天 | **不能**，重试只会重复同一个幻觉 |
| **选择错** | 该调 A 工具却调了 B，或根本不该调工具 | 不能，需要改提示或改工具边界 |
| **时序错** | 并行调了两个互相依赖的工具 | 不能，需要改编排 |

**算一笔重试的账。** 单次成功率 92%，最多重试 3 次：

```
成功概率 = 1 − 0.08³ = 99.95%     ← 看起来很美
延迟 = 最坏 3 倍（尾部）
成本 = 平均 1.09 倍（大部分第一次就成）
```

但如果那 8% 里有**一半是语义错**（参数错但不报错），那么：

- 重试不会修好它们，只会**重复错误**；
- 更糟的是，语义错往往**不抛异常**——工具照常执行，副作用已经发生，你连"失败"都不知道。

**所以真正的架构问题不是"怎么提高成功率"，而是"怎么让语义错变成可发现的失败"。**

### 核心机制：契约的四道关

```
模型意图
  ↓ ① schema 约束（结构合法）
  ↓ ② 语义校验（值合理：枚举、范围、外键存在）
  ↓ ③ 副作用闸门（不可逆操作前确认/预演）
  ↓ ④ 结果校验（干完之后检查终态）
```

四道关里，**②④ 最常被跳过，也正是最值钱的两道**：

- ② 把"编出来的 ID"变成"校验失败"，让它从静默错误变成显式失败。
- ④ 把"工具说成功了"变成"世界真的变了"，防止工具返回 200 但实际没生效。

### 怎么做

1. **schema 最小化**：只暴露任务真正需要的字段；能用枚举就别用自由文本（`status: "pending" | "paid"` 比 `status: string` 强得多）。
2. **把校验写进工具**，不要写进提示词。工具内部检查：必填项、取值范围、外键是否存在、单位是否一致。
3. **返回结构化错误**，让模型能修：不要返回 `Error 500`，返回 `{"error":"invalid_field","field":"amount","expected":"number in CNY","got":"1,200 USD"}`。这条错误消息本身就是在教模型怎么改。
4. **不可逆操作加闸门**：删除、外发、付款前，先做一次"预演"（dry-run）或要求二次确认。
5. **幂等键**：给每个副作用操作带一个幂等键，重试时服务端能识别"这是同一次操作"。
6. **限制并行**：只在工具之间确实无依赖时才允许并行；有依赖的一律串行。

### 权衡与坑

- **严格 schema 会限制能力。** 字段越少越安全，但可能表达不了复杂意图。折中：核心操作严格，探索性操作宽松但只读。
- **约束解码只保证语法。** 它能保证"是合法 JSON"，不能保证"是合理 JSON"。别把两者混为一谈。
- **错误消息太长会吃上下文。** 一条 3,000 token 的堆栈对模型没用，反而挤掉有用信息。错误要给"摘要 + 关键字段"。
- **工具太多会导致选择错。** 20 个工具时模型开始乱选。能合并的合并，能分组的用一层路由。
- **别让模型决定"要不要确认"。** 审批规则必须由代码判定（金额阈值、操作类型），不由模型判断。

### 自测题

1. 你的工具返回的错误信息，模型能据此自我修复吗？举一条你现在的错误返回，改写成"可修复"的版本。
2. 为什么"语义错"比重试更危险？请从"是否有异常"和"是否有副作用"两个角度回答。
3. 四道关里，你现在缺哪一道？缺它的代价是什么？

## 知识点 2：推理模型对架构的影响（A1-05）

### 一句话结论

**推理模型把"质量"换成了"延迟与成本"，而这两者是按尾部放大的。** 在循环里用它，等于把每一步的等待乘上步数；所以架构问题不是"要不要用"，而是"哪一层用、预算多少、等待怎么被感知"。

### 为什么重要

先算延迟。一个 10 步的 agent 任务：

```
快模型：每步 3 秒  → 端到端 30 秒
推理模型：每步 25 秒 → 端到端 250 秒（4 分 10 秒）
```

**用户的耐心大约在 10–30 秒。** 250 秒不是"慢一点"，是"换了一种产品形态"——它必须是异步的、可离开的、有进度的。

再算并发。按 Little 定律，并发需求 ≈ 到达率 × 停留时间：

```
1 QPS 的系统
3 秒/请求  → 需要约 3 个并发槽
25 秒/请求 → 需要约 25 个并发槽（8.3 倍）
```

**同样的流量，基础设施需求翻 8 倍。** 这还没算成本：思考 token 通常按输出价计费，而输出价比输入价贵 3–5 倍。

### 核心机制：什么时候值得"想久一点"

| 场景 | 值得吗 | 原因 |
|---|---|---|
| 规划、拆解、多约束权衡 | **值得** | 错在源头，代价最高 |
| 难题诊断、根因分析 | **值得** | 一次想对比十次试错便宜 |
| 需要自检的判定 | 视情况 | 有明确判据时，代码比模型更可靠 |
| 格式化、字段填充、摘要 | **不值得** | 收益接近零，延迟翻几倍 |
| 简单工具调用、路由 | **不值得** | 快模型足够，且更快失败更好 |
| 高频交互（chat/copilot） | 慎用 | 感知延迟直接杀死体验 |

**判据：这次"想"能减少多少下游返工？** 规划错一次，后面 10 步全废；格式错一次，重试一次就好。把推理预算放在"错误传播最远"的位置。

### 怎么做

1. **分层放置**：规划层用推理模型（每任务 1–3 次），执行层用快模型（每任务 5–50 次）。
2. **给推理设预算上限**：限制思考 token 或时间，超了就让它"先给当前最优答案"。没有上限的思考，是最贵的死循环。
3. **异步化**：凡是超过 30 秒的任务，做成"提交—通知—查看"的模式，而不是让用户盯着转圈。
4. **管理感知延迟**：流式输出思考摘要（不是完整思维链）、显示当前步骤、给"还要多久"的估计。
5. **先试后升**：快模型先做，校验不过再升级到推理模型重做。这条策略在"大部分简单、少数难"的分布上能省一大笔。
6. **按 p95 设计容量**，不是按平均。思考长度方差很大，平均值会骗你。

### 权衡与坑

- **过度思考真实存在。** 简单任务上，推理模型可能绕远路、引入不存在的约束，反而不如快模型。
- **推理能力不能替代可验证性。** 想得再久，终态还是要有代码检查。推理模型不改变 A0-04 的第三问。
- **成本会失控在"重试"上。** 推理模型一次失败很贵，重试三次就是三倍。要给"升级重做"设次数上限。
- **别把思维链当审计日志。** 它不忠实、不完整，不能作为"系统为什么这么做"的证据。要证据就记 trace（M6）。
- **延迟预算是产品决策。** "能不能等 4 分钟"不是工程师能定的，要拿业务场景去谈。

### 自测题

1. 你的任务平均几步？如果把执行层换成推理模型，端到端会变成多少秒？还符合产品预期吗？
2. 为什么 Little 定律在 agent 系统里特别重要？请用"25 秒/请求、1 QPS"算出并发槽位。
3. 哪些步骤你现在用推理模型但其实不需要？换成快模型会损失什么？（如果答不出"损失什么"，那就是不需要）

## 今日观察

- **前三篇其实在讲同一个"边界"问题**：工具写得好（第 1 篇）、工具选得对（第 2 篇）、工具用得克制（第 3 篇）。第 3 篇的"过度编辑"尤其值得记：**它是最典型的"语法全对、语义越界"**——模型确实完成了任务，只是顺手做了你没授权的事。这正是 A1-04 里"语义错不抛异常"的实证。
- **第 4 篇的标题本身就是一条架构洞察**：失败让人发散，成功让人收敛。放到系统上就是——**惩罚失败会让 agent 变保守，奖励成功会让它变激进**，而这两种偏置都会在长时间运行后累积成系统性问题。所以 agent 的"学习/记忆"必须配节流。
- **执行架适配器那篇给了 A1-01 一个补充变量**：模型选型不是选权重，是选"权重 + 执行架"的组合。同一个模型，适配器不同，成本与表现都变。
- **一个可以立刻用的判断**：如果你的工具调用错误里有超过三成是"参数值不对但没报错"，那你缺的不是更强的模型，是四道关里的第 ②③④ 道。
