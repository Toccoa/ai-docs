## 今日速览

- **A0-01 Agent 的定义与系统边界**：Agent = 模型 + 循环 + 工具 + 状态。四件缺一件，它就不是 Agent，而是 prompt、workflow 或脚本。这个定义不是学术洁癖：它决定了你怎么测它、怎么给它算钱、出事时往哪一层归因。**换一个 harness 而模型不变，公开审计里准确率能差近 30 个百分点**——这说明"模型"从来不是被测对象，整个系统才是。
- **A0-02 架构师负责的质量属性**：你交付的不是"能跑"，而是五个属性之间的取舍记录：可靠、可观测、成本、安全、可演进。最重要的一条算术：**单步 95% 可靠的 10 步任务，端到端只有约 60%**（0.95¹⁰ ≈ 0.599）。所以架构师的工作不是把单步从 95% 提到 97%，而是让系统不必依赖每一步都成功。

## 知识点 1：Agent 的定义与系统边界（A0-01）

### 一句话结论

**Agent = 模型 + 循环 + 工具 + 状态。** 四件里缺任何一件，它都退化成更简单的东西；而架构师的第一项工作，是把这个四件套的边界画在纸上，而不是先去选框架。

### 为什么重要

行业里"Agent"这个词已经通胀到没有信息量：一个带 JSON 输出的 prompt 叫 Agent，一个 RPA 脚本加个 LLM 也叫 Agent，一个能自己跑两小时的编码系统也叫 Agent。这三种东西的**测试方式、成本模型、故障归因路径完全不同**，混着叫会导致三个具体后果：

1. **承诺错可靠性。** 你按"Agent"的想象承诺了自主完成率，实际交付的是一个每步都要人确认的 workflow，验收必然失败。
2. **算错钱。** workflow 的成本是线性的（步数 × 单价），自由循环的成本是**不确定的**（步数本身由模型决定）。用线性预算去接一个非线性系统，账单会教你做人。
3. **归错因。** 出问题时你说"模型不行"，但真正的故障点是循环没有终止条件、或者工具的错误语义被模型误读。归错层，下一次还会坏在同一个地方。

**证据：harness 是分数的一部分。** 此前本库收录的评测指南引用了对 Terminal-Bench 的一份审计：**保持模型不变、只更换 agent harness，准确率变化最高达到 29.9 个百分点**。同一份任务、同一个模型，换一层外壳，结论就从"能用"变成"不能用"。所以"这个模型行不行"这个问法本身是缺变量的——完整的问法是"这个模型 + 这套循环 + 这批工具 + 这个状态下，行不行"。

### 核心机制：四要素各管什么

```
        ┌─────────────────────────────────────────┐
        │  循环 (loop)                             │
        │   观察 → 决策 → 动作 → 再观察             │
        │   ↑                   ↓                  │
   状态 │                  工具                   │
 (state)│              (tools/副作用)             │
        │   ↑                                     │
        │  模型 (model)：唯一做"判断"的部件         │
        └─────────────────────────────────────────┘
```

| 要素 | 它负责 | 缺了会怎样 | 架构师要定的边界 |
|---|---|---|---|
| **模型** | 在不确定信息下做判断、生成下一步 | 退化成固定规则的脚本 | 哪些判断必须交给它，哪些禁止交给它 |
| **循环** | 把"一次生成"变成"多次尝试直到达标" | 退化成单轮 prompt | 最大步数、预算、终止条件、谁来判定结束 |
| **工具** | 让判断能改变外部世界 | 退化成纯聊天，说得对但做不成 | 工具粒度、权限、幂等、错误语义 |
| **状态** | 让第 7 步知道第 1 步发生了什么 | 每轮失忆，长任务必然崩 | 状态存哪、存什么、能不能重放 |

**关键判据（今天最该记住的一句）：判断权归模型，保证权归代码。**

- "这个工单该分给哪个组"——判断，交给模型。
- "转账金额不能超过 5000"——保证，写成代码，放在工具里，不写在 prompt 里。

把保证写成 prompt，等于把保险丝换成一张写着"请不要过载"的纸条。

### 怎么做：一张 A4 纸的边界图

拿到任何一个 Agent 需求，先做这四步（不需要写代码，20 分钟能画完）：

1. **写四要素清单**：模型用哪个、循环长什么样、工具有哪几个、状态存在哪。
2. **画一次完整循环**：从用户输入到终态，标出每一次"模型判断"和每一次"代码保证"。
3. **定义可判定终态**：什么条件下这件事算做完了？必须是代码能检查的条件（文件存在、记录状态变更、测试通过），不能是"模型说完成了"。
4. **标出不可逆动作**：删除、外发、付款、发布。这些位置必须有人或硬规则在场。

做完这四步，你会发现很多"Agent 需求"其实在第 3 步就死了——它没有可判定的终态，那它不是 Agent 项目，是需求没想清楚。

### 权衡与坑

- **自主性不是越多越好。** 自由度越高，长尾越长，测试越难覆盖。有合规和副作用的地方，主动收窄成状态机，是加分不是减分。
- **工具越多，上下文越脏。** 每个工具的定义都占 token，也都在稀释模型的注意力。工具数量应当由任务需要决定，不由"我们平台支持多少"决定。
- **"能自我反思"不等于"会变好"。** 没有外部信号（测试、评委、人）的自我反思，多数时候是在给自己的错误找理由。
- **别把编排框架当成架构。** 框架解决"怎么连起来"，不解决"连起来之后为什么是对的"。这两件事经常被混为一谈。

### 自测题

1. 一个系统：用户提问 → LLM 生成 SQL → 执行 → 返回结果。它是 Agent 吗？如果你的答案是"看情况"，请说出取决于哪两个条件。
2. 同事说"我们换了个更强的模型，Agent 的成功率从 62% 提到了 65%"。按今天的定义，你要追问他哪几件事，才能判断这个结论能否成立？
3. 为什么"转账金额不超过 5000"必须写在工具代码里，而不是系统提示词里？请从"保证权"和"可验证性"两个角度各说一句。

## 知识点 2：架构师真正负责的质量属性（A0-02）

### 一句话结论

架构师交付的不是"能跑"，而是**五个质量属性之间的取舍记录**：可靠、可观测、成本、安全、可演进。这五个属性互相拉扯，没有"全都要"，只有"这个场景下先保谁"。

### 为什么重要

**先算一道小学算术。** 假设一个 Agent 任务需要 10 个步骤，每步成功率 95%（这已经是很乐观的单步可靠性）：

```
0.95¹⁰ ≈ 0.599      ← 端到端约 60%
0.99¹⁰ ≈ 0.904      ← 单步提到 99%，端到端才 90%
```

这就是 Agent 架构的第一性约束：**端到端可靠性是单步可靠性的指数衰减**。它推出两个反直觉的结论：

1. **优化单步收益递减。** 单步从 95% 提到 97%，10 步的端到端只从 60% 提到 74%；而把任务拆成 5 步，端到端直接从 60% 跳到 77%。
2. **架构比调参更值钱。** 减少步数、让步骤可并行、让失败可恢复（checkpoint）、让终态可校验——这些是乘法级的改善；换更贵的模型是加法级的。

第二条还解释了为什么"再加一层 Agent 试试"经常让系统更差：每加一层，就多几步，指数衰减又多乘了一次。

### 核心机制：五个属性怎么互相拉扯

| 属性 | 它回答的问题 | 加它会牺牲什么 | 典型手段 |
|---|---|---|---|
| **可靠** | 每次都能做成吗 | 成本、延迟（重试与冗余都要钱） | 校验、重试、checkpoint、降级路径 |
| **可观测** | 坏了能不能看见 | 延迟、存储、接入工作量 | trace、语义约定、关键节点埋点 |
| **成本** | 一次要花多少 | 能力上限（便宜模型能力弱） | 模型分层、缓存、批处理、步数上限 |
| **安全** | 会不会造成不该有的后果 | 成功率、体验（多一次确认就少一分顺畅） | 最小权限、沙箱、人工审批、出口审计 |
| **可演进** | 三年后还改得动吗 | 当下的开发速度 | 边界清晰、契约化、决策记录 |

**这五行的每一行，都有一个"看起来免费、实际很贵"的陷阱**：

- 可靠性的陷阱是"无限重试"——它把失败变成了更慢的失败，还顺带把账单翻倍。
- 可观测性的陷阱是"全量记录"——把用户数据原样打进 trace，你同时收获了一个隐私事故。
- 成本的陷阱是"无脑降级"——把难任务也路由给便宜模型，省下的钱会以返工的形式还回去。
- 安全的陷阱是"提示词护栏"——写一句"不要泄露密码"，然后相信它。
- 可演进的陷阱是"先这样，以后重构"——概率系统的行为不可 diff，重构时你无法证明"行为没变"，于是没人敢动。

### 怎么做：把属性写成可验收的场景

架构评审上最没用的话是"我们要保证高可用"。有用的是**质量属性场景**，四段式：

```
刺激（什么发生了）→ 响应（系统应该做什么）→ 度量（怎么算达标）→ 取舍（牺牲了什么）
```

举三个真实的写法：

| 场景 | 度量 | 明确牺牲 |
|---|---|---|
| 上游模型 API 超时率升到 20% | 自动切备用模型，P95 延迟不超过 8 秒，任务失败率不超过基线 +2pp | 备用模型能力较弱，复杂任务成功率会降 |
| 模型试图调用"删除客户记录"工具 | 100% 拦截并转人工确认，无例外 | 该操作平均多花 2 分钟人工时间 |
| 单任务 token 消耗超过预算 3 倍 | 立即中止并回滚到上一个 checkpoint，记录完整轨迹 | 长任务可能被误杀，需要人工重跑 |

**为什么一定要写"牺牲了什么"？** 因为不写，这个取舍就会在半年后由某个不知情的人替你重新做一遍——通常是在一次事故之后，用最保守的方式。

### 权衡与坑

- **可靠性和安全经常互斥。** 多一道确认，成功率就掉一点；但少一道确认，事故率就涨一点。这不是技术问题，是业务风险偏好问题——**必须由能承担后果的人来定，不能由写代码的人默认**。
- **可观测性不是日志。** 日志回答"发生了什么"，trace 回答"为什么走到这一步"。Agent 的问题几乎都在"为什么"，只有日志的系统等于没有可观测性。
- **成本要按最坏情况算。** 自由循环的步数由模型决定，平均 4 步、长尾 40 步的系统，预算要按 40 步设计，否则一定有一批请求把账单打穿。
- **可演进性是最容易被牺牲、也最贵的。** 一个没人敢改的 Agent 系统，等于已经死了——它只是还没停机。

### 自测题

1. 一个 12 步的 Agent，单步成功率 92%。端到端大约是多少？如果只能做一个改动：把单步提到 95%，或者把步数压到 6 步，你选哪个，为什么？
2. "加一道人工确认"这个改动，同时影响了哪三个质量属性？请各说一句。
3. 用四段式（刺激 / 响应 / 度量 / 取舍）给你的项目写一个质量属性场景。写不出"取舍"那一栏，说明你还没想清楚。

## 今日观察

- **五篇文章，其实在回答同一个问题：怎么把"概率"关进"结构"里。** 多智能体那篇说，光加 agent 不涨能力，得让通信变成可训练的结构；主动性那篇说，给目标比给任务难，因为目标没有边界，必须靠记忆和 UX 造出结构；治理那篇说，结构就是轨迹本身；沙箱那篇说，结构是操作系统级的权限边界；上下文工程那篇说，结构是"每一步只装最小的高信号集合"。**架构师的工作，本质上就是造这些结构。**
- **上下文是这五篇的共同货币，但它有三种花法。** 多智能体花在"agent 之间的通信"上（容易浪费）；主动性 agent 花在"记忆"上（为了省下人的注意力）；上下文工程花在"装配"上（为了不被无关 token 稀释）。同一个 token 预算，花在哪一层，决定了系统长什么样。
- **一个反直觉点：可靠性问题往往不是"模型不够强"，而是"步数太多"。** 今天这两个知识点合起来给了一个可操作的杠杆——在换模型之前，先数一遍步数。把 10 步压到 6 步，比把单步从 95% 调到 99% 更划算。
- **另一处值得警惕的措辞**：主动性 agent 那篇里有一句话，"当你的下属变得很强时，你会发现自己成了瓶颈"——放到 Agent 上，瓶颈会从"你能不能做"变成"你能不能审"。这意味着**架构的重心会从执行层移到审批层**，而审批层现在几乎没有工具。
