# AI Agent 顶级架构师 · 知识地图

> 从 0 到能独立设计、评审、并把一个 Agent 系统推进到生产的高阶架构师。
> 全量 **59 个知识点 / 10 个模块**，按 M0 → M9 推进，每天 2 个，约 30 天走完一轮；之后转入「前沿跟踪 + 架构评审 + 真实系统归因」。

## 这张地图在讲什么

一句话：**Agent 不是一个更聪明的模型，是一个必须被设计的系统。**

普通软件系统的架构，难在规模和耦合；Agent 系统的架构，难在**执行主体本身是概率性的**。同一份代码、同一个模型，今天能过、明天不能过；同一个任务，换一个 harness 准确率能差几十个点。所以架构师在这里的工作不是"选个框架"，而是回答四个问题：

1. **边界在哪**——哪些事交给模型判断，哪些事必须写成代码？
2. **失败怎么收敛**——概率性组件出错是常态，系统怎么保证整体可用？
3. **代价是什么**——每个决策吃掉多少延迟、多少钱、多少可解释性？
4. **怎么演进**——今天能跑的 demo，怎么变成三年后还在维护的平台？

这四个问题贯穿全部 59 个知识点。每学一个点，都问自己一句：**它在上面四个问题里回答哪一个？去掉它，系统会怎么坏？**

## 主线：一次请求要穿过七道缝

```
用户意图
  ↓ ① 形态选择        ← M0：chat / copilot / autopilot，选错形态，后面全错
  ↓ ② 模型与推理      ← M1：能力、成本、延迟的三角
  ↓ ③ 循环与控制流    ← M2：谁决定下一步、什么时候停
  ↓ ④ 上下文与记忆    ← M3：模型此刻"看得见"的世界
  ↓ ⑤ 工具与副作用    ← M4：能碰什么、碰了能不能撤回
  ↓ ⑥ 编排与并发      ← M5：一个 agent 不够时怎么加
  ↓ ⑦ 运行与治理      ← M6/M7：可观测、可回滚、可问责
        ↓
      组织与演进      ← M8/M9：平台化、选型、90 天落地
```

**七道缝，每一道都能单独把系统做垮。** 架构师的价值，是知道当前系统的瓶颈在第几道缝，而不是把所有缝都加一层。

## M0 心智模型：先搞清楚你在造什么（5 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| A0-01 | Agent 的定义与系统边界 | Agent = 模型 + 循环 + 工具 + 状态；四件缺一件，就退化成 prompt 或 workflow |
| A0-02 | 架构师真正负责的质量属性 | 可靠、可观测、成本、安全、可演进——五个属性互相拉扯，没有全都要 |
| A0-03 | 四种形态：chat / copilot / autopilot / 后台自治 | 形态决定人机接口、失败代价与审批点，选错形态是最贵的架构错误 |
| A0-04 | 该不该用 Agent 的判据 | 路径确定就别用 Agent；用 workflow 能解决的，不要交给概率模型 |
| A0-05 | 架构决策记录与演进观 | 每个决策写清「当时假设什么、什么条件下要推翻」，否则三年后没人敢改 |

**出口标准**：能对着一个真实需求，写出它的形态选择、四要素边界，以及"为什么不用更简单的方案"。

## M1 模型层：把概率组件当零件用（6 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| A1-01 | 模型能力光谱与选型 | 强模型解决"会不会"，快模型解决"贵不贵"；先分层，再谈选型 |
| A1-02 | Token 经济学与上下文窗口的物理限制 | 上下文是 n² 注意力的预算，不是免费的硬盘 |
| A1-03 | 采样参数与可复现性 | temperature 只改分布不改事实；要可复现，得固定整条链路 |
| A1-04 | 结构化输出与工具调用协议 | schema 是契约；模型不遵守契约时，系统要有兜底而不是重试到超时 |
| A1-05 | 推理模型对架构的影响 | 想得久 ≠ 做得对；延迟与成本要按"最坏情况"设计 |
| A1-06 | 模型路由与级联降级 | 大部分请求用便宜模型，少数升级——路由器的判据本身就是架构资产 |

**出口标准**：能给一个业务场景画出「模型分层 + 路由 + 降级」的方案，并算出单位成本。

## M2 循环与执行架：系统的骨架（7 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| A2-01 | 三种循环：ReAct / Plan-Execute / Reflection | 自由度越高越像人，也越难测；先选能收敛的那一种 |
| A2-02 | 控制流：状态机 vs 自由循环 | 有合规、有副作用的地方必须收窄成状态机 |
| A2-03 | 终止条件与死循环防护 | 没有预算上限的循环，等于一个会烧钱的 bug |
| A2-04 | 上下文工程：压缩、摘要、卸载 | 上下文会"腐烂"（context rot），长任务必须主动做压缩与外部化 |
| A2-05 | 工具接口设计 | 工具是给模型看的 API：名字、粒度、错误语义都影响成功率 |
| A2-06 | 错误处理与重试语义 | 副作用操作不能盲目重试；幂等键与补偿事务要提前设计 |
| A2-07 | 执行架（harness）与框架选型 | 框架解决编排，不解决正确性；自研与托管的取舍看团队而非功能表 |

**出口标准**：能画出一个 agent 循环的完整状态转移图，标出所有退出路径与预算检查点。

## M3 记忆与知识：模型此刻看见的世界（6 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| A3-01 | 记忆分层：工作 / 情景 / 语义 / 程序性 | 四层记忆的写入频率与失效方式完全不同，混在一起必然腐坏 |
| A3-02 | 短期记忆与上下文装配 | 每一轮都是"重新组装一次视图"，不是"追加一段历史" |
| A3-03 | 长期记忆的写入与遗忘 | 什么该记、记成什么粒度、什么时候删——写入策略比检索策略更关键 |
| A3-04 | 把 RAG 正确接进 Agent | 检索是工具不是前置管道；由模型决定何时检索，比每轮都检索更省更准 |
| A3-05 | 记忆冲突与一致性 | 新旧事实冲突时靠什么裁决：时间戳、来源可信度，还是人 |
| A3-06 | 状态持久化与断点恢复 | 长任务要能"从第 7 步继续"，这要求状态可序列化、副作用可重放 |

**出口标准**：能设计一套记忆 schema，说清每类信息的写入时机、粒度、TTL 与冲突裁决规则。

## M4 工具与外部世界：能碰什么（6 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| A4-01 | 工具生态与 MCP | 协议统一了接入方式，没统一权限模型；接得越多，攻击面越大 |
| A4-02 | 最小权限与能力授权 | 给 agent 的权限应当是"这次任务需要的"，而不是"这个账号有的" |
| A4-03 | 沙箱与代码执行 | 代码执行是最强的工具，也是最需要隔离的工具；隔离级别决定能开放什么 |
| A4-04 | 浏览器与计算机操作 | 视觉/坐标级操作的脆弱性远高于 API，必须有回退路径 |
| A4-05 | 副作用与人工审批 | 不可逆操作（转账、外发、删除）必须有人在场，这是架构约束不是体验优化 |
| A4-06 | 工具调用的审计与可观测 | 每次调用都要能回答：谁授权的、改了什么、能不能撤 |

**出口标准**：能给出一份工具清单的权限矩阵（读/写/外发/不可逆），并指出哪些必须人工确认。

## M5 多智能体与编排：什么时候该加人（6 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| A5-01 | 单 Agent 的上限与多 Agent 的判据 | 加 agent 不自动提升效果；上下文隔离与并行才是真收益 |
| A5-02 | 编排拓扑：supervisor / pipeline / swarm / debate | 拓扑决定失败模式：中心化易瓶颈，去中心化难复现 |
| A5-03 | 通信协议与上下文隔离 | 交接（handoff）时传什么、不传什么，比用什么协议更重要 |
| A5-04 | 并发、竞态与共享状态 | 多个 agent 写同一份状态，等价于分布式系统的老问题 |
| A5-05 | 成本爆炸与预算分配 | 多 agent 的成本是乘法的；预算要按任务分配，不是按 agent |
| A5-06 | 多智能体的典型失败模式 | 互相确认错误、责任稀释、无限委派——协作的收益常被这些吃掉 |

**出口标准**：能对一个多 agent 方案说出"为什么不能用一个 agent + 更好工具"，并给出成本对比。

## M6 可靠性与生产化：从 demo 到线上（7 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| A6-01 | demo 到生产的三道坎 | 长尾、并发、成本——demo 只验证了主路径 |
| A6-02 | 可观测性：trace / span / 语义约定 | 看不到轨迹，就只能在出事后猜；trace 是治理的地基 |
| A6-03 | 评测门禁与回归 | 没有回归集的 agent，每次发版都是赌博 |
| A6-04 | 灰度、影子与回滚 | 概率系统的回滚要能"回放"，而不只是"回退代码" |
| A6-05 | 延迟工程 | 流式、并行、预取、缓存：用户感知的延迟不等于总耗时 |
| A6-06 | 成本工程 | prompt 缓存、批处理、模型降级——成本是架构指标，不是财务指标 |
| A6-07 | 事故响应与归因 | agent 事故要归因到层（模型/循环/工具/环境），否则修复只是碰运气 |

**出口标准**：能画出「离线回归 + 线上灰度 + 人工兜底」的三层发布架构，并定义每层的准入指标。

## M7 安全与治理：概率系统的攻击面（6 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| A7-01 | 提示注入的架构级防御 | 提示层防不住注入；要靠权限、隔离与出口审计 |
| A7-02 | 数据边界与隐私 | 上下文里进了什么，等于泄露了什么；脱敏要发生在进入之前 |
| A7-03 | 输出治理与合规 | 生成内容的合规责任在部署方，不在模型 |
| A7-04 | 供应链安全 | 模型、工具、MCP server、依赖包——每接一个就多一个信任方 |
| A7-05 | 人机责任边界 | 哪些决定不能交给模型，要写成制度而不是提示词 |
| A7-06 | 红队与对抗测试 | 用攻击者视角设计用例，比用测试覆盖率更接近真实风险 |

**出口标准**：能对一个 agent 系统做一次威胁建模，列出资产、入口、信任边界与缓解措施。

## M8 平台与规模化：一个人用变成一群人用（6 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| A8-01 | 内部 Agent 平台该提供什么 | 平台卖的是"少踩坑"，不是"多一个抽象层" |
| A8-02 | 多租户与资源隔离 | 共享模型配额时，一个租户的尖峰就是所有人的故障 |
| A8-03 | 自研 / 框架 / 托管 的选型矩阵 | 选型的真正变量是团队规模与维护年限，不是功能对比 |
| A8-04 | 组织与推动落地 | 架构师的一半工作是让别人愿意改 |
| A8-05 | 演进路线：单点 → 平台 → 基础设施 | 每个阶段的"该欠的债"不同，提前还债也是浪费 |
| A8-06 | 架构评审清单 | 一张能问出问题的清单，比一份漂亮的架构图有用 |

**出口标准**：能给出一份可执行的架构评审 checklist，并解释每一条对应的真实故障模式。

## M9 Capstone：把它做完（4 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| A9-01 | 企业级 Agent 系统设计 | 从需求、约束、非功能目标推到架构，再推回验证方式 |
| A9-02 | 架构评审实战 | 用真实方案做一次对抗式评审，练"问对问题" |
| A9-03 | 成本与容量规划 | 按峰值与长尾分别算，给出可承诺的 SLA |
| A9-04 | 90 天落地计划 | 从 PoC 到生产的阶段划分、验收标准与组织动作 |

**出口标准**：交出一份能被工程团队直接执行的架构方案（含取舍、风险、里程碑）。

## 怎么用这张地图

- **按顺序读**：每天 2 个点，M0 → M9，约 30 天。别跳，M0 的形态判断错了，后面全是补丁。
- **带着系统读**：每个点都套到你手上正在做的那个 agent 上，问"我这里是怎么做的"。
- **看前沿**：每天 5 篇业界文章，挂接到具体知识点；学不到的位置先收藏，到了再回读。
- **周日复习**：抽 2 个旧知识点，用"如果重做一次，哪里会不一样"来检验。

## 术语约定

| 中文 | 英文 | 本文用法 |
|---|---|---|
| 智能体 | agent | 能自主决定下一步动作的系统 |
| 执行架 | harness | 包住模型的循环、工具、上下文管理那一层 |
| 轨迹 | trace | 一次运行里所有步骤的记录 |
| 上下文 | context | 某一次推理时模型能看到的全部 token |
| 工具 | tool | 模型可以调用的外部能力 |
| 交接 | handoff | 把控制权与部分上下文交给另一个 agent |
| 编排 | orchestration | 决定谁在什么时候做什么 |

## 更新节奏

- **每日**：`02-每日推送` 一期（2 个知识点）+ `03-前沿文章` 5 篇（原文 + 中文译文）。
- **每周日**：间隔复习，不占新知识点。
- **每季度**：回审本图，删掉过时的、补上新增的，并在下方「变更记录」留痕。
