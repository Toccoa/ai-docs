## 为什么今天读这篇

这是 2026 年下半年最完整的一份「Agent 评测工程手册」：它把一次评测拆成可复用的组件，用一条真实的物理实验室任务从头走到尾，并且在每一步都告诉你**这一步可能怎么错**。对刚起步的人来说，它的价值不在于结论，而在于**它把"评测"从一次性动作变成了一个有生命周期的工程对象**。

## 三句话摘要

1. 评测设计经历了三代：问答式 → Agent 式 → 团队/群体式，每加一层软件，就多一个能改变分数的变量。
2. 构建一次 Agent 评测有八个步骤，其中最关键的两步是**先跑参考解（oracle）**和**故意构造一条捷径去攻击自己的评分器**。
3. 基准会坏、会饱和、会被污染；唯一可持续的应对是**按组件决定开什么源**，而不是全开或全不开。

## 译文

### 概述

AI 评测影响着人们构建、采用和信任哪些系统。一次评测给系统派任务、检查它的回答或动作、产出一个分数。因此，构建并维护一个有意义的评测需要实打实的工作：定义能体现领域专业性的任务、可靠地给它们打分、并检验结果是否支撑所声称的结论。当方法、代码和数据都不公开时，别人就很难审查或在此基础上继续做。

开源提供了一条路径，去构建更强、更新更频繁、更可比的评测，以及它们周边的基础设施。已有的任务、环境和工具给构建者一个起点，让精力可以放在领域专业性与验证上。把评测是怎么建起来的——包括哪里出过错——公开出来，别人才能发现错误、改进并复用。

Hugging Face Hub 是 AI 评测的一个聚集地：我们托管了大约 3500 个评测榜单，过去一年 Hub 上的评测数据集增长了约 **16 倍**，达到约 **17000 个**。最近几个月，我们还加入了对评测相关的 Agent 抽象的支持。例如 **Traces**（以易审阅、易分享的方式保存 agent 的工作过程）、**Benchmarks**（标记出被榜单用于评测模型的那些数据集）以及 **Environments**（展示被用作 Agent 强化学习或评测环境的数据集）。

本文覆盖四件事：

1. **评测的三个时代**：从检查答案，到检查 agent 做了什么，再到检查一组 agent 共同产出了什么。每前进一步，都多出一层可能改变分数的软件。
2. **一次 Agent 评测的步骤**：我们跟踪一个任务走完八个步骤，从一句 claim 到最终报告的分数。
3. **当基准出错时**：任务和评分器里的错误很常见，我们看它们是怎么被发现和纠正的。
4. **哪些该开源、为什么**：用一张表逐组件说明，什么可以公开、什么可以保留。

### 1. 评测设计是怎么变的

随着语言模型能力增强、能承担更复杂的工作，AI 评测设计演化出三种形态：**问答、Agent、团队/群体**。

- **问答式**基准（如 MMLU，2020；GPQA，2023）通过模型产出的答案来衡量知识与推理。
- 当模型开始能规划和用工具，**Agent 式**基准（如 SWE-bench、WebArena）把范围扩展到修复软件问题和在网站上完成任务。这类任务要求评测装置能考虑到系统运行的环境以及它做出的改动。
- 最近，多智能体研究又加了一个维度：**agent 之间如何协调、共同完成了什么**，包括去中心化的群体、由编排者管理的团队，以及协作完成科研工作的专用 agent。

本文聚焦 Agent 式评测，原因有两个。第一，由于用户与企业对 Agent 部署的兴趣，它在模型发布公告中正成为最突出的一类。第二，它是理解"评测设计如何影响模型表现"的一个好起点。团队与群体评测因为 agent 之间的交互而更复杂，本文不展开。

**一旦 agent 开始用工具完成任务，周边软件的每个部分都可能影响它的分数。** 例如，在一份对 Terminal-Bench 的审计中，研究者**保持模型不变、只更换 agent harness，准确率变化最高达到 29.9 个百分点**。要理解这种差异，就要拆开一次 Agent 评测的解剖结构，跟踪一个任务从"agent 收到的指令"到"判定它是否通过的那些检查"。

#### 一次 Agent 评测的解剖

一次 Agent 评测包含若干部分：

- **任务（task）** 给 agent 指令。
- **Agent harness** 把模型和它的工具包起来，让它在一个**固定版本的环境**里工作。
- 在一次 **rollout** 中，agent 从头到尾尝试这个任务：它可能跑若干条命令、观察输出、再重试，直到停下。
- **评测 harness** 为每个任务跑多次 rollout。
- 一次 rollout 结束时，**验证器（verifier）** 给环境的最终状态打分。
- 每次 rollout 还会留下一条**轨迹（trace）**；轨迹与分数一起，构成最终发布的证据。

每一部分都可以被单独发布、检查、复用。

#### 为什么基准的发布决策很重要

对独立评测的需求在增长。政策制定者、企业和研究者想要**可核验**的评测，而今天他们基本做不到：**98.2% 的模型-基准分数只由一方报告**，研究者也论证过**内部自评是不够的**。

与此同时，更多基准开始保留测试项以减少污染（题目或解法进入训练数据，使分数可能反映的是"以前见过"）。Artificial Analysis 表示，其在 2026 年 10 月发布的 Intelligence Index v5 中，**60% 建立在有私有测试集或留出答案的评测之上**。Google DeepMind 最近试点了**双盲评测**：一个安全飞地让外部评测者的测试提示词对模型提供方不可见，同时让模型权重对评测者不可见。这能减少污染，但**隐私本身不保证质量**，而且扣住支撑材料会让专家审查更难。我们认为，构建者仍可以、也应该分享基础设施、评分方法和关于任务设计的证据。审查的前提，是给别人一条质疑测量、纠正错误的途径——包括在公开不合适时进行受控审查。

### 2. 构建一次评测：复用、改造、验证

接下来我们为一个真实场景构建一次 Agent 评测：一个分析物理实验室测量数据的 agent。我们不从零开始，而是改造一个开放任务，这样大部分精力可以放在领域专业性和验证上。

八个步骤：**定义 claim → 找一个起点任务 → 原样跑一遍 → 改造任务 → 检查评测本身 → 跑起来并读轨迹 → 报告分数 → 比较模型**。

#### 方法

**Claim。** 设想一个物理实验室，希望 agent 对拉曼光谱做峰拟合。拉曼光谱是一种测量，其峰位揭示材料性质，这里是石墨烯。agent 的工作是普通的编码：读数据文件、对每个峰拟合曲线、保存结果。为了本文的目的，我们的 claim 刻意定得很窄：**拟合指定的峰、计算所要求的 D/G 比（一个峰的强度相对于另一个峰，可指示材料缺陷，我们也称缺陷比）、并稳定地保存准确结果**。要评审一整份实验报告，还需要额外的能力和证据。

**起点任务与基线。** 我们复用了 Harbor 的任务格式和 Terminal-Bench 的 `raman-fitting` 任务。Harbor 是一个开源评测 harness，Terminal-Bench 是一个"agent 在终端里完成任务"的开放基准。我们先跑任务的参考解（通过），然后用 Terminus-2（一个终端 agent harness）和 gpt-oss-120b（OpenAI 的开放权重模型）把原任务跑了三次。Harbor 跑在 HF Job 里，每次 rollout 用自己的 HF Sandbox，Inference Providers 提供模型响应。复用 runner 和任务格式，让我们能专注在物理、评分和审查上。**只有 agent harness 不需要新工作，其余每个组件都需要检查或新建。**

**改造。** 我们构建了 `raman-lab`：八条合成光谱，参数已知、噪声与缺陷水平各异。改造后拟合三个峰而不是两个，并报告缺陷比。我们用 agent 帮助生成光谱、人工审核、编写新指令、参考拟合和输出检查。新指令写明了原任务隐含的单位和参数定义。这八个任务是**开发集**（构建评测时使用的任务），更广的覆盖应当跟随真实测量的变化。

**检查。** 在跑更多模型之前，我们先测评测本身：跑参考解、一个什么都不做的 agent、以及一条跳过必需工作的捷径。参考解应当通过每一个任务，另外两个应当失败。我们的捷径直接从数据里读每个峰的高度、猜出宽度，**在全部八个任务上都给出了预期的缺陷比**，却没有真正做拟合——于是我们加上了对拟合本身的检查。

**捷径的意义。** 一个只检查比值的评分器会给这条捷径满分。这正是"答案对、过程错"的典型：像一个只抄了最后数字、没有写过程的学生。**要测的是输出所证明的东西**：更快的合法方法应当通过，跳过必需技能的方法不应当通过。领域专家可以帮助设定容差，让验证器接受替代性的正确拟合，但不接受错过任务要点的工作。

#### 结果

**基线。** 在原任务上，gpt-oss-120b **3 次 rollout 全部失败**。其中两次在观察到相关输出之前就宣布完成；第三次读不了数据文件（该文件用十进制逗号，参考解会先做转换）。**光看分数，分不清这些失败和"拟合错误"的区别；看轨迹才能分清。**

**轨迹与分数。** 在八个改造任务上，每个任务跑三次 rollout，**24 次中通过 11 次**。其中 **19 次**，模型在第一次回复里就调用了 `mark_task_complete`；这 19 次里有 **11 次没有产出结果文件**。有几次的开头是脚本因为缺 NumPy 或 SciPy 而失败（任务期望 agent 自己安装）。所以大多数失败来自**提前停止**或**缺依赖**，13 次失败里只有 2 次是拟合检查没过。**pass@3 = 7/8**（七个任务至少成功一次），**pass^3 = 1/8**（只有一个任务次次成功）。有人复核输出时，重试可以接受；无人值守处理需要一致性，所以第二个指标更重要。

按任务聚类后，平均通过率 **0.46**，标准误约 **0.11**。重跑一次，24 次里通过 10 次。只有八个开发任务，我们会对把任一结果外推到新光谱保持谨慎。

**模型比较。** 在同一组八个任务上比较六个模型。多个提供方可以用不同的量化和上下文上限服务同一个开放权重模型，所以每个模型固定一个提供方。把 DeepInfra 固定为提供方后，gpt-oss-120b 通过 13/24（此前用默认提供方是 11/24）。只有 gpt-oss-120b 在第一次回复里就宣布完成（22/24），其他五个模型一次都没有。

比较也暴露了开发集的局限：Qwen3.8-27B、DeepSeek-V4.1-Flash、MiniMax-M3.1-Flash 在 raman-lab 上**全部 24 次通过**，所以这些任务无法给它们排序——那需要更难的题。六个模型的推理总花费不到 **5 美元**；gpt-oss-120b 的中位 rollout 约 6000 token，MiniMax-M3.1 约 90000 token。

### 3. 苦涩的教训：当基准出错时

我们的捷径在没有拟合光谱的情况下给出了预期的缺陷比。**一个只检查比值的验证器会在全部八个任务上给它满分。** 我们是通过"故意用一个已知不完整的解去攻破评分器"发现这一点的，然后补上了对拟合光谱的检查。

这类错误很常见，而且会显著移动分数。一份对 Agent 基准的综述发现，**任务设置或奖励设计的缺陷可以把测得的表现移动最多 100%（相对值）**。

**公开审查是纠正基准的关键。** Terminal-Bench 2.1 在用户报告后修复了 **89 个任务中的 28 个**，其中一个任务的测试期望 Spark SQL，而指令要求的是 PostgreSQL；修正之后 **agent 排名保持稳定**。证据的可得性也决定了外部审计的工作量：CritPt 把参考解保密，审计它的物理学家不得不先自己解题，才在 **56 道题中的 21 道**里发现错误。OpenAI 对 SWE-bench Verified 的审计，在**任何人都能读到的任务与测试**基础上，发现所检查的 **138 道题中有 59.4% 存在实质问题**。2026 年 7 月，OpenAI 估计 **SWE-Bench Pro 约 30% 的任务是坏的**，并撤回了采用它的建议。**基准验证必须在发布之后继续。**

**除了代码，还要检查 claim。** 一个稳定的分数也可能测的是错的东西。《Measuring what Matters》由 **29 位专家评审审阅 445 个 LLM 基准**，发现任务与指标中反复出现的、损害**构念效度**（任务和指标是否支撑关于目标能力的 claim）的模式。例如，拟合合成光谱并不能证明 agent 会审阅实验报告——那可能还需要识别一次糟糕的测量，或者主动求助。如果每个任务都提供一条可用的光谱，测试就无法显示 agent 是否知道"什么时候不该拟合"。**《Harder Than the Task》**把这种担忧延伸到组织工作：权威、分散的知识和依赖关系可能决定成败，而作者发现**不到四分之一的知名基准声称覆盖了任何一个这样的维度**。

每个错误都值得一条简短记录：失败的假设、它是怎么被发现的、改了什么。记录还应写明受影响的版本，以及此前的分数是否仍然可比。

**污染 vs 饱和。** 上面那次 SWE-bench Verified 审计也发现了污染：每一个被测的前沿模型都能复现某些任务的参考补丁或逐字题目细节。SWE-bench 的公开仓库和广泛使用让任务暴露在训练数据里。**让坏测试被审查出来的开放性，同时也让题目更容易在评测前被遇到。**

但如果训练时对污染做了仔细控制，**仅仅隐藏测试集并不能防止饱和**。一项对 **60 个语言模型基准**的研究发现，公开与私有基准的饱和程度相似，结论是：**一旦基准被广泛采用，隐藏测试数据并不能阻止饱和**——一个好基准会因为饱和而退出使用，而开发者无法从中学习并继续构建。真正与更低饱和相关的是**专家策展**和**更大的测试集**。

这就留下一个实际发布问题：**在保护仍在使用的测试项的同时，能公开什么以供审查？**

### 4. 有策略地开源一次评测

不要把所有开放性当成全有或全无的决定，而是**逐组件**决定发布什么：保护仍在使用的测试任务不被泄漏，同时分享底层基础设施、评分方法和参考答案，让外部研究者可以审计并继续构建。

| 组件 | 可以公开的 | 可以保护的 |
|---|---|---|
| 任务 | 规格、类别、构建方法、公开的开发集划分 | 仍在使用的测试项与答案（单独的门控数据集，逐次审批） |
| 环境 | 容器定义、构建文件、固定依赖、合成夹具 | 私有数据、凭据、有许可的资产、危险细节 |
| Agent harness 与工具 | agent loop 代码、工具接口、适配器、权限、预算 | 密钥、私有服务、敏感工具实现 |
| Rollout 与轨迹 | 公开任务的轨迹、审查过的片段、分析代码 | 暴露任务、私有数据或受限模型行为的轨迹 |
| 参考解 | 公开样例的解法与代码 | 会暴露受保护题目的解法 |
| 评测 harness | 编排、模型配置、日志、聚合、版本记录 | 凭据、能识别题目的配置 |
| 验证器 | rubric、评分代码、容差、样例 | 会暴露受保护题目的参考答案与逻辑 |
| Claim 与任务设计 | 预期用途、选择理由、情境假设、验证证据 | 敏感源材料可能需要脱敏 |
| 结果 | 分数、不确定性、成本、排除项、局限 | 会泄漏任务的细节 |
| 更正 | 写明受影响版本的更正历史 | 更正背后的受保护样例 |

发布或退役一次评测之前，检查另一个构建者能否：

- 识别它测什么、预期用途是什么、哪些条件没有覆盖；
- 找到可复用的产物、它们的许可与版本，以及报告问题的途径；
- 看到"什么都不做的 agent"得多少分，并在可能时看到人类专家的得分；
- 在读到每个分数时同时读到它的不确定性，以及已知缺陷对该分数意味着什么；
- 知道哪些缺陷被发现、如何被处理、可能把结果移动多远；
- 知道任务将如何、何时被刷新，以限制污染与过拟合。

### 5. 结论：让评测有一个有用的"余生"

基准有生命周期：被构建、被采用、被针对优化，最终不再能区分它想区分的系统。上面那项饱和研究把 60 个基准中的 **29 个**评为高度饱和，且比例随年龄上升。饱和本身不是失败——它可能意味着能力已经到位。

**一个基准留下什么，取决于它有多开放。** 只发布分数，未来的人几乎没东西可跑、可改。当任务、环境、验证器和轨迹都开放时，每一样在榜单失效之后都还能继续工作：一道被解决的任务可以变成新 harness 的回归检查；它的环境和验证器可以孵化出更难的继任者。开放基准还会被修复和重新发布：MMLU 的题目变成了 MMLU-Redux，Terminal-Bench 2.0 通过社区贡献变成了 2.1。我们这次的走查本身就是这样一种"余生"：raman-lab 起源于一个为通用终端工作构建的基准里的单个任务。

### 附录 A：实操要点（精编）

- 环境：Harbor + HF Sandbox + Inference Providers；`harbor run -t <task> -a oracle` 先验参考解。
- 改造：八个合成长谱，三个峰，缺陷比；指令必须写明单位、参数定义、输出格式。
- 验证器三条规则：**评 agent 产出的东西**（检查保存的输出，而不是它声称完成）；**把每个被检查的事实写进指令**（单位、约定、容差、字段）；**用已知参数生成合成数据**，使参考答案可得，再复核样例是否代表目标问题。
- 必须的三组对照：参考解（应全过）、空操作 agent（应全败）、捷径（应全败）。
- 读轨迹的分类：解析数据、执行工具、过早停止、评分输出。
- 报告：`pass@k` 与 `pass^k` 并列；均值必须带按任务聚类的标准误；同时报 token、耗时与工具调用次数。

## 与路线图的挂接

- **E0-01 / E0-03**：这篇文章就是"五元组"的实物版——task、harness、env、trace、verifier 五个部件，每一个都能改分数。
- **E1-01 / E1-04**：从公开任务改造而不是从零造题；开发集只有 8 个任务时，作者明确说"不外推"。
- **E2-02 / E2-03**：验证器要检查终态而不相信 agent 的自我宣告；捷径实验是"结果评分 vs 过程评分"的教科书案例。
- **E4-06 / E7-05**：基准审计与有策略的开源，是"读榜的人"和"造榜的人"都该掌握的两件事。

## 三个自测问题

1. 为什么"参考解必须通过、空操作 agent 必须失败"这两条检查，能同时抓住任务错误和验证器错误？它们各自抓不住什么？
2. `pass@3 = 7/8` 与 `pass^3 = 1/8` 之间的巨大落差，在这个例子里主要由什么造成？如果换成一个"每次都会自我检查"的 harness，你预期这两个数怎么变？
3. 文章说"隐藏测试集不能防止饱和"。那么一个基准在什么信号出现时应该被退役？退役时最该保留的是什么？
