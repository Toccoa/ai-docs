## 三句话摘要

1. 固定模型、固定 harness、固定任务集，**只改容器资源配额**，Terminal-Bench 2.0 上最宽松与最严格配置差 **6 个百分点**（p < 0.01）。
2. 机制有两段：3 倍配额以内，多给的资源主要在**修基础设施可靠性**（错误率 5.8% → 2.1%），分数变化在噪声内（p = 0.40）；超过 3 倍以后，资源开始**真的帮 agent 解题**，分数才会明显上移。
3. 建议：**每任务同时指定"保证配额"与"硬上限"两个参数**，并校准到"下限与上限下的分数落在彼此的噪声范围内"。**榜上 3 个百分点以内的差距，在配置未公开前值得怀疑。**

## 译文

### 摘要式开头

像 SWE-bench、Terminal-Bench 这样的 Agent 编码基准，常被用来比较前沿模型的软件工程能力——榜首之间往往只差几个百分点。这些分数常被当成"模型相对能力的精确测量"，并越来越多地影响"部署哪个模型"的决策。**但我们发现：仅仅基础设施配置一项，就能产生超过这个差距的差异。** 在内部实验中，Terminal-Bench 2.0 上资源最充足与最紧张的配置之间相差 **6 个百分点（p < 0.01）**。

静态基准直接给模型输出打分，运行环境不影响结果。Agent 编码评测不同：模型拿到一个完整环境，写程序、跑测试、装依赖、多轮迭代。**运行时不再是被动的容器，而是解题过程不可分割的一部分。** 两个资源预算与时限不同的 agent，**做的不是同一张卷子**。

评测开发者已经开始考虑这一点。Terminal-Bench 2.0 在最新版本中按任务给出了推荐的 CPU 与内存。但**"指定资源"不等于"一致地执行资源限制"**。而且我们发现，**执行方式本身会改变这个基准最终测的是什么。**

### 起因

我们在 Google Kubernetes Engine 集群上跑 Terminal-Bench 2.0。校准环境时，我们注意到分数与基准官方榜单对不上，而且基础设施错误率高得离谱：**多达 6% 的任务因为 pod 错误失败**，其中大多数与模型解题能力无关。

分数差异的根源在于**资源限制的执行方式**。我们的 Kubernetes 实现把每任务的资源规格**同时当作下限和硬上限**：容器保证拿到指定资源，但一旦超出就立刻被杀。容器运行时通过两个参数执行资源限制：一个**保证配额**（预先保留的资源），一个**硬上限**（超过即杀）。当两者被设成同一个值时，**瞬时峰值没有任何余量**——一次短暂的内存波动就能 OOM-kill 一个本来会成功的容器。为了照顾这一点，Terminal-Bench 的榜单用了另一个沙箱提供方，其实现更宽松，允许临时超额分配而不终止容器，以换取基础设施稳定性。

这引出一个更大的问题：**资源配置到底多大程度影响评测分数？**

### 实验设计

为量化脚手架的影响，我们在 Terminal-Bench 2.0 上跑了 **6 种资源配置**，从严守每任务规格（1x，同时作为下限与上限）到完全不设限。其他一切保持不变：同一个 Claude 模型、同一个 harness、同一套任务。

### 结果

**成功率随资源余量上升**，主要由基础设施错误率单调下降驱动：严格限制时 **5.8%**，不设限时 **0.5%**。从严格限制到 3 倍余量（5.8% → 2.1%）的下降在 **p < 0.001** 上显著。余量越大，因超出配额而被杀的容器越少。

**1x 到 3x 之间，分数在噪声范围内波动（p = 0.40）。** 在 1x 时崩溃的大多数任务本来也会失败——这一点我们在数据里观察到了：agent 探索、撞到资源墙、被抢占，但它从来不在通往正确解法的路径上。

**大约从 3x 开始，趋势变了：成功率爬升快于基础设施错误率下降。** 从 3x 到不设限，基础设施错误又降了 **1.6 个百分点**，而成功率跳了将近 **4 个百分点**。多出来的资源让 agent 能尝试那些只有宽裕配额才可行的路径，比如拉取大型依赖、启动昂贵的子进程、跑内存密集的测试套件。不设限时，相对 1x 的总提升是 **+6 个百分点（p < 0.01）**。在边缘案例上，`rstan-to-pystan` 和 `compile-compcert` 这类任务在有内存余量时成功率显著改善。

### 这对测量意味着什么

**在 Terminal-Bench 规格的约 3 倍以内，额外的资源修的是基础设施可靠性问题**——即瞬时资源峰值。Terminal-Bench 维护者使用的沙箱提供方实际上是在幕后做这件事：**评测变得更稳定，但没有变得更简单**。

**超过 3 倍之后，额外的资源开始主动帮 agent 解决它原本解决不了的问题**，这说明**资源限制可以改变评测所测的东西**。紧的限制无意中奖励非常高效的策略；宽松的限制更宽容，奖励那些能更好利用全部可用资源的 agent。

一个写得精简、跑得快的 agent 在紧约束下表现好；一个用重型工具蛮力求解的 agent 在宽松约束下表现好。**两者都是值得测的东西，但如果不说明资源配置就把它们压成一个分数，差异——以及真实世界的可推广性——就无法解释。**

在 `bn-fit-modify`（一个需要贝叶斯网络拟合的 Terminal-Bench 任务）上，有些模型的第一步是安装标准 Python 数据科学栈（`pandas`、`networkx`、`scikit-learn` 及其工具链）。在宽松限制下这可行；在紧限制下，pod 在安装期间就 OOM，agent 连一行解法代码都没写。存在更精简的策略（只用标准库从零实现数学），有些模型默认就这么做，有些不会。**不同模型有不同的默认路径，而资源配置决定了哪条路径恰好能成功。**

我们在不同的 Anthropic 模型上复现了核心发现：效应方向一致，幅度不同。同样的趋势似乎也适用于 Claude 之外的模型，但我们没有严格测试。我们还在 Terminal-Bench 之外的评测上做了交叉实验：在 SWE-bench 上，把可用内存提高到基线的 **5 倍**，跨 **227 个问题、每个 10 个样本**。同样的效应成立，但幅度更小：分数仍随内存单调上升，5x 只比 1x 高 **1.54 个百分点**。SWE-bench 任务资源密集度更低，效应更小是预期之内的，但它说明**那里的资源分配也不是中性的**。

### 其他方差来源

资源分配不是唯一的隐藏变量。某些配置下，时限也开始起作用。

原则上，评测设置的每个元素都能影响最终分数：集群健康度、硬件规格、并发度，甚至出口带宽。**Agent 评测在构造上就是端到端系统测试，系统的任何组件都可能成为混淆变量。** 我们非正式地观察到，通过率随时段波动，很可能因为 API 延迟随流量模式与事故变化。我们没有正式量化这个效应，但它说明一个更大的问题：**"模型能力"与"基础设施行为"之间的边界，比单个基准分数所暗示的要模糊得多。** 模型提供方可以通过专用硬件把自己的评测基础设施隔离出来，外部评测者却很难做到同样的事。

公开基准通常意在测量纯模型能力，但实践中它们有把模型能力与基础设施怪癖混为一谈的风险。有时这是可取的（它支持对整个栈做端到端测试），但多数时候不是。**对于要公开分享的编码评测，在多个时间、多天运行有助于把噪声平均掉。**

### 建议

理想情况是每次评测都在完全相同的硬件条件下运行（评测脚手架与推理栈都一致），从而保证完全的可复现性。但这并不总是可行。

鉴于容器运行时实际上通过"保证配额 + 独立的硬杀阈值"两个参数执行资源限制，我们建议**评测按任务同时指定这两个参数，而不是固定一个值**。单一的精确规格会把保证配额与杀阈值设成相等，**留下零余量**：我们在 1x 记录的瞬时内存峰值就足以让评测失稳。把两个参数分开，能让容器有足够呼吸空间避免虚假 OOM，同时仍用一个硬上限防止分数虚高。

**两者之间的带宽应校准到"下限与上限下的分数落在彼此的噪声范围内"。** 例如在 Terminal-Bench 2.0 上，把上限设为每任务规格的 **3 倍**，基础设施错误率下降约三分之二（**5.8% → 2.1%，p < 0.001**），同时分数提升温和且完全在噪声内（**p = 0.40**）。这是一个合理的取舍：**基础设施混淆变量基本被中和，同时没有移除有意义的资源压力。** 具体倍数会随基准与任务分布而变，因此应当报告；但**用经验校准这个原则是通用的**。

### 为什么我们在意

这些发现对评测基础设施之外也有实际后果。基准分数越来越多地被用作决策输入，但这种关注（与依赖）并没有总是伴随运行与报告方式上的严谨。**就现状而言，榜首 2 个百分点的领先，可能反映真实的能力差异，也可能反映一方跑在更肥的硬件上，或者赶上了更幸运的时段，或者两者兼有。** 没有公开（或标准化）的设置配置，外部很难分辨——除非有关方愿意多走一步，在相同条件下复现客观结果。

对 Anthropic 这样的实验室，含义是：**Agent 评测的资源配置应当被当作一等实验变量，像提示词格式或采样温度一样被记录和控制。** 对基准维护者，公布推荐资源规格（Terminal-Bench 2.0 已经在做）能走很远，而**说明执行方式**能补上我们发现的这个缺口。对任何消费基准结果的人，核心结论是：**Agent 评测上的小分数差异，携带的不确定性比报告数字的精度所暗示的更大**——尤其是有些混淆变量根本难以控制。

在资源方法论标准化之前，我们的数据表明：**在评测配置被记录并对齐之前，榜上低于 3 个百分点的差异值得怀疑。** Terminal-Bench 在中等资源配置范围内的观测差异略低于 2 个百分点；朴素的二项置信区间本身就有 1–2 个百分点宽；我们记录的基础设施混淆变量**叠加在这之上，而不是包含在其中**。在资源配置范围的两端，差异可达 6 个百分点。

**几个百分点的领先，可能意味着真实的能力差距——也可能只是更大的虚拟机。**
