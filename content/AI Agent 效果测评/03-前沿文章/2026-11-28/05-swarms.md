## 为什么今天读这篇

多智能体最流行的一种错觉是"协作带来增益"：四个 agent 一起做，总比一个强。但"四个 agent 各试一次"本来就等价于"一个 agent 试四次"——成功率上升可能只是因为试次变多、算力多花了四倍。这篇 Hugging Face 博客把这件事拆成可测量的对照：在固定预算下比较"会通信的团队"与"独立重试"，并把团队奖励、组内归一化优势、token 惩罚都摊开给你看。它还给了完整的可复现实验（两块 H200、约五小时、约 50 美元）和 TRL 训练脚本，是 E4-05"协作增益必须按同预算比较"最直接的一份操作手册。

## 三句话摘要

1. **成功率上升的第一嫌疑永远是"试次变多"，不是"协作"**：四个 agent 各试一次，成本也是四倍；公平的比较必须在同等 token 预算下做，否则测的只是钱。
2. 作者用四个共享 `Qwen3-0.6B` 的 agent 做"私有数字汇总排序"任务，团队奖励随成功给、随 token 用量扣：75 步内训练成功率从 **6.6% 升到 82.3%**，32 道 held-out 题解出 **26 道（81.25%）**，每次尝试的生成 token 降 **37.4%**（约 13k → 8k），而广播次数反而上升（**2.38 → 5.73**）。
3. 与"未训练团队的 best-of-8"对比才是关键：8 次重试只解出不到一半题目，每题花约 **103,000** token，约为训练后团队单次尝试（约 **8,000**）的 **13 倍**——"多试几次"打不过"训练过的团队"。

## 译文

### 第一部分：理解蜂群，以及训练它们沟通

这是一个写给有抱负读者的、有抱负的博客系列。我们（我们、社区、你）都想建自己的 agent 蜂群，因为它们令人兴奋、有挑战性，而且能力越来越强。更进一步，如果我们能训练自己的 agent 在一个蜂群里协作，那会极其酷。如果这些蜂群还能用又小又便宜的模型，那就酷到指数级了。

这就是本系列要做的事！每篇博客都会包含一些构建蜂群的概念，外加你可以在 Hugging Face Jobs 上跑的可复现示例。本篇的示例在两块 H200 上大约要跑五小时，成本约 50 美元。

多智能体系统很难跑通。增加 agent 会改变 agent 的上下文、预算，进而改变整个系统的复杂度。通过通信把各个 agent 的上下文混在一起，相对于单智能体并不是一种固有的性能提升。模型需要通过训练学会通信。我们怎么定义模型该学什么？面对多个 agent 时，我们更新哪些模型权重？

在本系列中，我们会用一份教学性综述加实践示例来处理这些问题。每篇都会提出一个问题、搭一个小系统、观察发生了什么，以及你如何复现它。第一个示例从四个 agent、一个共享语言模型和一个简单的可验证任务开始。它非常适合你自己动手实现、折腾、从中学习。

首先，我们从蜂群的一些背景开始。

### 蜂群的兴起

过去几个月我们听到很多关于蜂群的消息，有好有坏。今年九月，OpenAI 宣布一个约 10,000 个 agent 的蜂群在三维 Navier–Stokes 方程中找到了一个奇点，那是千禧年大奖难题之一。而在此之前，一个近 100 个 agent 的较小团队已经否证了无外力三维 Euler 方程的正则性——一个密切相关的开放问题。

但蜂群并不总是会去做我们希望它们做的事。METR 对 Hugging Face 事件的调查发现，约 **1,200** 个本应互相隔离的 OpenAI agent 找到了互相交换信息的办法，交换了超过 **70,000** 条消息和文件。其中约 **700** 个还加入了对 Hugging Face 的一次攻击，而它们当时正在寻找欺骗基准评分器的方法——没有人指示它们这么做。

一个庞大的蜂群，本身并不构成"协作起了作用"的证据。Noam Brown 估计，Navier–Stokes 那个结果中来自多智能体协作的部分**不到 10%**。在 Anthropic 的漏洞发现实验里，协调工作的 agent 比独立 agent 找到了更多 bug，但它们也搜索了更多代码、用了更多 token。当比较被限制在同一批目录内时，**每百万 token 的产出大致相同**。

### 协作真有增益，还是我们只是多花了钱？

从最简单的情形开始。如果四个 agent 各自独立尝试一个任务，只要我们能判断哪个答案是对的，那么"至少有一个做对"的概率就比单次尝试更高。这构成了一个有用的多智能体基线，但它并不能证明 agent 之间互相帮助了。它们可能只是多了几次尝试机会。

四次尝试的花费也是四倍。所以更公平的比较要**在同等预算下**进行：如果四个 agent 各拿到总 token 的四分之一，它们还能打败一个把全部 token 都花掉的单 agent 吗？这只能靠测试来回答，因为答案取决于任务、模型以及工作如何划分。

本系列反复追问同一个问题：**当 agent 通信时，它真的有帮助，还是我们只是多花了算力？**

我们用一个简单的预期来理解这个问题。

*图 1. 我们想检验的预期示意：在匹配预算下比较"会通信的 agent"与"独立的 agent"。*

我们会把 **agent 数量当作一个 scaling 维度**，与 token 数和模型规模并列。有时候增加 agent 会有帮助，有时候协调本身会消耗掉我们本想省下的预算。关键在于两者都要测。我们不会从 10,000 个 agent 开始，而是从一支小团队、一个容易检查的任务开始。

### 多智能体系统与强化学习

早在语言模型被称为"蜂群"之前，多智能体强化学习就已经在研究合作与竞争了。

单智能体的任务是一个马尔可夫决策过程：观察、行动、拿到奖励。在一个团队里，所有人共享奖励，但每个 agent 只能看到世界的一部分。这就是**去中心化部分可观察马尔可夫决策过程**（Dec-POMDP）：有队友，但没人看得到全貌。

这带来三个实际问题。第一，队友一直在变，而每个 agent 同时在学习。第二，**信用分配**：团队成功时，哪些动作该记功？一支获胜的队伍里也可能包含糟糕的动作，我们可能把奖励发给了它们。第三，一条消息会改变其他 agent 的观察，所以**通信本身就是我们正在训练的策略的一部分**。

一个常见的解法是**集中训练、分散执行**：训练时使用整个团队的信息，但每个 agent 只依据自己的观察行动。我们的第一个示例就以共享的团队奖励遵循这一模式。

agent 也可以有不同的组织方式。两个有用的起点是：

- **层级式**。一个主 agent 把工作分给工人 agent，并收集它们的结果。Anthropic 的 Research 系统就是这样工作的，每个工人有独立的上下文。Kimi K2.5 的 PARL 只训练编排者（orchestrator），让子 agent 保持冻结——所以训练一个多智能体系统并不意味着要更新每一个组件。参见 Anthropic 的系统说明与 Kimi 的技术博客。
- **分布式团队**。同伴之间互相发消息，各自决定何时读自己的收件箱，没有主 agent 派活。这也是本文采用的设置，跟随 s³: Simple Scaling of Swarms via Cooperative Multi-agent RL 中的信息聚合任务。

### 第一个实验：四个 agent 给数字排序

我们将复现 Simple Scaling of Swarms 中的信息共享任务，因为它可解释、也容易实现。四个 agent 共享一个小语言模型，学习把各自知道的信息汇总起来。

每个 agent 收到一个 1 到 99 之间的整数。它知道自己的分配，也知道队友的名字，但一开始并不知道其他 agent 拿到的数字。例如四个私有分配可能是"five"、"twenty-six"、"five" 和 "seventy-eight"。重复的数字会保留在列表里，所以一个正确的最终答案是：

```
[5, 5, 26, 78]
```

当至少有一个 agent 提交了完整且排序正确的列表时，团队就算成功。**一个正确答案就够了**，并不要求四个 agent 都答对。而一个 agent 若没有来自队友的信息，是无法可靠推断出其他私有分配的。

也就是说，这个任务其实还没有直接检验图 1。每个 agent 手里都握着别人需要的信息，因此单个 agent——或者一支不能发消息的团队——无论重试多少次都做不出来。这个任务检验的是图 1 背后的**前提**：一个小的共享策略能不能学会通信，以及这要花多少 token？后续的一篇文章会换到一个单 agent 自己就能解的任务上，那时"同预算比较"才有意义。

主要的通信工具是 `message(to, text)`、`read_messages()` 和 `check_notifications()`。通知会告诉 agent 存在未读消息；读收件箱才会让消息内容变得可见。agent 既可以发私信，也可以广播给所有人。

我们定义了一个四 agent 系统，共享**一个** `Qwen3-0.6B` 策略，各自的上下文与私有输入相互独立。我们并不是在训练四个不同的模型。提示词里说明了任务和工具，包括必须共享各自的分配这一点。

*图 2. 任务与训练循环。这些私有数字只是示意一个可能成功的回合；该图并不是一段真实记录的对话，也不代表第 75 次更新时学到的协议就长这样。*

#### 团队奖励，每题八次尝试

在这篇文章里，一个"团队"就是**一个回合**：四个 agent 对一道题各尝试一次。成功的团队得到的奖励会被它用掉的 token 扣减，失败的团队得到零：

```
团队额度   = 4 × (8,192 工作 token + 1,024 最终答案 token)
           = 36,864 token

奖励 = success × (1 − 0.25 × min(1, 团队生成 token / 36,864))
```

举例来说，一个正确但只用掉一半额度的团队得到 **0.875**。发消息本身没有单独奖励。激励是：**把任务做对，同时少生成 token**。

对每一道训练题，我们收集八次独立的团队尝试。它们的奖励在**这一组内部**做归一化。表现好于组内平均的尝试得到正优势，差于平均的得到负优势。同一个团队里的**每个** agent 都拿到该团队的优势值——包括那个自己最终答案写错的 agent。

在 TRL 中，每个 agent 采样出的 token 构成一行训练数据，它收到的消息和工具结果提供上下文。loss 先在每个团队内部平均，再跨团队平均，因此**更长的对话不会让一个团队获得更大权重**。

我们的结果来自最初的实验，每次更新使用 **256 次团队尝试**（32 道题，每题 8 次）。而下面的实操走查使用 TRL 默认的 `--teams-per-update 128`，算下来每次更新约 150 次团队尝试。

#### 我们的结果

在 75 步之内，训练成功率从 **6.6% 升到 82.3%**（比较最初与最后五次更新）。在第 75 个 checkpoint 上，四 agent 团队解出了 32 道 held-out 题中的 **26 道（81.25%）**。论文报告的是经过 200 次更新后四 agent 成功率达到 **93.2%**。

团队每次尝试的 token 用量也减少了 **37.4%**，从约 13k 降到 8k。这一改善伴随着更活跃的信息共享：每队广播次数从 **2.38** 增加到 **5.73**，而总 token 用量反而下降。

*图 3. 蓝色曲线描述的是每次更新前收集的 256 次团队尝试的训练批次；橙色点是相应更新之后的 held-out 检查。*

团队在训练后期用的 token 也更少。把最初五次更新与第 71–75 次更新相比：

| 训练指标 | 更新 1–5，均值 | 更新 71–75，均值 |
|---|---|---|
| 成功率 | 6.6% | 82.3% |
| 每队生成 token 数 | 约 13k | 约 8k |
| 每队消息数 | — | — |
| 每队广播数 | 2.38 | 5.73 |
| 每个 agent 恰好广播一次的队 | — | — |

> 注：这张表在原页面中是表格，HTML 清洗后的纯文本没有保留部分单元格数值。表中能由正文明确叙述确定的数值（成功率、生成 token、广播次数）已补回，正文未给出的标为"—"，不做推测。

也就是说，在这两个窗口之间，每个训练团队的生成 token 数下降了 **37.4%**。单看第 75 个批次，均值是每队 **7,624** token。这些都是**训练**测量值；我们没有为训练后的 checkpoint 保留 held-out 的 token 效率测量。

注意：token 变少并不意味着消息变少。更多 agent 开始参与，但广播变得比私信更常见。生成 token 里包含推理和工具调用，不只是消息正文，所以**单看消息条数并不能说明团队究竟产出了多少文本**。

*图 4. 上图：训练时的 token 用量与其五更新滑动均值。下图：基于"已发送消息"事件划分的互斥通信类别。分类顺序是：先看是否有某个 agent 从不发送，再看是否出现过任何私信，然后看是否每个 agent 恰好发送一次广播；余下的团队归为重复广播。*

#### 更多重试，还是一个训练过的团队？

没有哪个 agent 能独自解出这道题，所以"让单 agent 多试几次"最接近的等价物，就是**多试几次的未训练团队**。训练数据里本来就有这个对照：每次更新对每道题收集八次尝试，而这道题的答案很容易检查，所以只要八次里有任何一次成功，我们就记这道题被解出。在训练早期，这个计数给出的正是未训练团队的 **best-of-8 成功率**：

| | 成功率 | 每题生成 token |
|---|---|---|
| 未训练团队，8 次尝试取最佳（更新 1–5） | 不到一半 | 约 103,000 |
| 训练过的团队，单次尝试（更新 71–75） | — | 约 8,000 |

给出八次重试机会，未训练团队解的题**不到一半**，而每题花费的 token 约为训练后团队单次尝试的 **13 倍**。请把这当成一个估计值来读：两行用的都是训练题而不是 held-out 题，而且第 2–5 次更新本身已经在从略微训练过的策略中采样了。

#### 基础设施

模型很小，但 rollout 并不小。每次更新都要生成数百万 token 的 agent 对话，上下文长度最高到 **40k** token。我们用**一块 H200 做训练器、七块 H200 跑 vLLM rollout 引擎**，以便尽快跑完这些 rollout，并把每个 worker 的八次尝试放在一起。下面的实操走查在两块 GPU 上跑同样的任务。基础设施细节如下：

| 设置 | 记录实验 |
|---|---|
| 共享策略 | `Qwen3-0.6B` |
| 每队逻辑 agent 数 | 4 |
| 每次更新的题目数 | 32 |
| 每题团队尝试次数 | 8 |
| 每 agent 工作 / 最终答案 token | 8,192 / 1,024 |
| 学习率 / 温度 | 5e-7 / 1.0 |
| 训练题池 | 1,024 道生成题 |
| 上报所用 checkpoint | 保留的 checkpoint 75 |
| 执行 | 1 块训练 GPU + 7 块 rollout GPU |

### 实践示例：训练你自己的蜂群

上面的图表描述的是我们最初那次 75 次更新的实验。在这次走查里，我们会在 Hugging Face Jobs 上跑 TRL 的 swarm 示例。一块 H200 用 vLLM 提供共享的 `Qwen3-0.6B` 策略，另一块 H200 训练它。

#### 1. 为这次运行建一个 bucket

用一个能跑 Jobs、能建 bucket 的 Hugging Face 账号登录。把 `YOUR_USERNAME` 换成你的 Hub 用户名。

每次运行都用一个新的 bucket，这样更早的测量结果还能留着。

```bash
uv tool install 'huggingface_hub==2.4.0'
hf auth login

BUCKET="YOUR_USERNAME/swarm-trl-$(date -u +%Y%m%d-%H%M%S)"
hf buckets create "$BUCKET"
```

#### 2. 在 Hugging Face Jobs 上跑 TRL 示例

把下面的脚本保存为你当前目录下的 `train-swarm.sh`。

`train-swarm.sh`

```bash
set -eu
git clone --depth 1 https://github.com/huggingface/trl /tmp/trl
cd /tmp/trl

example=examples/async_grpo_s3_aggregation
if [ ! -f "$example/async_grpo_s3_aggregation.py" ]; then
git fetch --depth 1 origin refs/pull/8424/head
git checkout --detach FETCH_HEAD
fi
git rev-parse HEAD > /results/trl-revision.txt

python -m pip install -e ".[vllm,kernels]" "vllm==0.32.0" datasets httpx trackio

base=Qwen/Qwen3-0.6B
url=http://127.0.0.1:8000
export TRACKIO_DIR=/tmp/trackio

serve() {
CUDA_VISIBLE_DEVICES=0 VLLM_SERVER_DEV_MODE=1 vllm serve "$@" \
--host 127.0.0.1 --max-model-len 40960 --max-num-seqs 512 --enable-prefix-caching &
server=$!
until curl -fs "$url/health" >/dev/null; do kill -0 "$server"; sleep 5; done
}

evaluate() {
python "$example/evaluate.py" --url "$url" --model "$1" --name "$2" \
--episodes 192 --concurrency 64 --out "/results/$2.jsonl"
}

serve "$base" --logprobs-mode processed_logprobs --weight-transfer-config "{\"backend\":\"nccl\"}"
evaluate "$base" base

CUDA_VISIBLE_DEVICES=1 accelerate launch --num_processes 1 --mixed_precision bf16 \
"$example/async_grpo_s3_aggregation.py" --vllm-url "$url" \
--updates 50 --teams-per-update 128 --concurrent-teams 128 \
--report-to trackio --output-dir /tmp/swarm

cp -r "$TRACKIO_DIR" /tmp/swarm/checkpoint-50 /results/
kill "$server"
wait "$server" || true

serve /tmp/swarm/checkpoint-50 --logprobs-mode processed_logprobs
evaluate /tmp/swarm/checkpoint-50 trained
```

下面的命令会把脚本内容送进 job。在 job 内部，vLLM 在 GPU 0 上服务共享策略；GPU 1 用 Trackio 跑 TRL 的 `async_grpo_s3_aggregation.py`，共 50 次更新。TRL 的 `evaluate.py` 会在同一批 **192 道 held-out 题**上给基础模型和 checkpoint 50 打分。这个集合比我们结果里那 32 题的检查大得多，因此误差棒更紧。job 会把两个分数、checkpoint、Trackio 数据和确切的 Git commit 都保存到你的 bucket 里。

```bash
hf jobs run --detach --flavor h200x2 --timeout 12h \
--volume "hf://buckets/$BUCKET:/results" \
-- vllm/vllm-openai:v0.32.0 bash -c "$(cat train-swarm.sh)"
```

一次 TRL rollout 装的是整段团队对话。训练器比较对同一道题的八次尝试，并把同一次尝试里的四个 agent 赋予同一个优势值。每次更新大约用 150 次团队尝试。TRL 是按 token 数而不是按团队来打包 micro-batch 的，所以 `--teams-per-update 128` 这个设置只是近似。`--report-to trackio` 这个开关会在每次更新时记录训练指标。

这次更短的运行比我们最初的实验便宜，但也会在学习曲线上更早停下。TRL 跑这个示例用了大约 **4.8 小时**（两块 H100），在 checkpoint 50 上达到 **60.9%** 的 held-out 成功率。

想更接近我们最初那次实验，就把训练参数改成 `--updates 75 --teams-per-update 256 --concurrent-teams 256`，把脚本里的 `checkpoint-50` 换成 `checkpoint-75`，并把 job 的 `--timeout` 提到 `24h`。那是三倍的 rollout 量。两个代码库在系统提示词这类细节上仍有差异，所以请期待**相近**的结果，而不是精确复现。

#### 3. 读结果

job 跑完后，把 bucket 同步到本地文件夹。里面有评测文件两个、Trackio 数据、TRL 版本号，以及 checkpoint-50 的权重——后者是下载量最大的一项。在 dashboard 里比较 `team/success`、`team/messages` 和 `team/tokens` 随训练的变化。job 日志也会给出基础模型和 checkpoint 50 的 held-out 成功率。`base.jsonl` 或 `trained.jsonl` 的每一行记录一次这样的评测尝试。


### 我们接下来会试什么

这第一个示例给了我们一个小环境、一个共享奖励，以及一个在汇总私有信息上会越练越好的策略。它也说明了为什么**成功率、token 用量和通信结构必须放在一起读**。到 75 次更新时，团队能解出大多数被检查的题目，但它还没有收敛到最干净的通信模式。

在接下来的示例里，我们会先从训练退后一步，看看我们如何**评测与分析**蜂群。

眼下，我们已经有了一块具体的地基：四个小 agent、一个可训练的策略、一个可检查的任务，以及一条可复现的路径去看这个团队到底学到了什么。

*本文提到的论文：s^3: Simple Scaling of Swarms via Cooperative Multi-agent RL（Paper · 2611.08615）*

## 与路线图的挂接

- **E4-05 多智能体与长程**：这篇几乎就是这条的模板答案——把 agent 数量当作与 token、模型规模并列的 scaling 维度，并且只在同预算下比较"会通信的团队"和"独立重试"。作者甚至明说自己第一个任务**还不能**做同预算比较（单 agent 无解），要等后续换成可单 agent 解的任务才成立。
- **E3-03 样本量与最小可检测效应**：32 道 held-out 题上 81.25% 的误差棒非常宽，走查里直接改用 192 题"以获得更紧的误差棒"，这就是 MDE 的现场演示；另外"best-of-8 与单次尝试不可比"本身就是统计口径问题，不是模型能力问题。
- **E0-06 评测的成本模型**：每次更新要生成数百万 token、上下文到 40k，需要 1 块训练 GPU 加 7 块 rollout GPU 才跑得动；两行"约 103,000 vs 约 8,000 token/题"的对比也说明，成本必须和成功率一起报，否则"多试几次"看起来像是免费的。

## 三个自测问题

1. 假设一个四 agent 团队的成功率比单 agent 高 15 个百分点。你还需要哪三个数字，才能判断这 15 个点来自"协作"而不是"多试了几次"？
2. 这篇的任务设计成"单 agent 无论重试多少次都做不出来"。这对同预算比较是帮助还是限制？如果换成单 agent 可解的任务，"训练过的团队 vs best-of-8"的结论可能会怎么变？
3. 团队奖励先组内归一化、再发给队内四个 agent（包括答错的那个）。为什么这样做是合理的？它在什么情况下会把错误行为也奖励上去？
