## 为什么今天读这篇

评测做到后来，绕不开一个很具体的问题：同一个任务到底要跑几次？这篇把这件事拆成了可操作的决策：先看结果稳不稳，再决定 k 取多少；同时把 pass@1、pass@k、pass^k 三个指标各自回答什么问题讲清楚了——单次尝试能不能成、多次里有没有一次能成、以及每次都成有多难。最有价值的是它给了预算分配的判据：什么时候该加试次，什么时候加试次已经没用、该去加任务。文中还有可用的锚点数字，可以直接拿来估算"要测出 2 个点，得跑多少轮"。

## 三句话摘要

1. 同一个任务多跑几次，才能把"成功率"和"稳定性"分开：每次试次都从空环境独立启动，不继承上一次的对话历史和中间产物。
2. 三个指标分工明确：pass@1 是单次成功率，pass@k 是 k 次里至少一次成功，pass^k 是 k 次全部成功——τ-bench 里 GPT-4o 单次 61.2%，但 pass^8 掉到 25% 以下。
3. 试次数量取决于波动大小和要检测的提升大小：波动中位水平下，检测 2 个百分点要每个系统约 9 次完整基准运行，检测 1 个百分点要 36 次。

## 译文

### 引言

当 Agent 在你的产品上完成一个任务之后，下一个问题就是：它能不能稳定地再完成一次。即使指令、工具和文档完全相同，它也可能走另一条路径、在活上花更长时间，或者卡在它上次轻松完成的事情上。

当开发者依赖 Agent 来使用你的产品时，不可预期的行为会打断他们的工作，让整个体验更难被信任。重复试次能帮你找到工作流在哪里断掉，并检验更清楚的文档、更好的工具或更有用的错误信息，是否真能让它们更稳定地完成任务。

### 为什么每个任务要跑多次试次

把同一个任务跑多次，能衡量 Agent 成功得有多稳定，也能暴露单次运行可能漏掉的失败。每次执行（也就是一个试次）都使用一套固定的 Agent 配置，独立启动：空环境，不携带另一次试次的对话历史或中间产物。在比较产品版本时，这种重复还能帮你判断某个改动是真的提升了表现，还是结果本来就会在运行之间波动。

Agent 的行为即使在看起来确定的设置下也会变化。在 2026 年的研究《On Randomness in Agentic Evals》中，研究者在 SWE-bench Verified 上收集了 60,000 条编码 Agent 轨迹。每种配置各做十次完整评测，从最低的那次到最高的那次，分数相差 2.2 到 6 个百分点。即使把底层 LLM 的 temperature 设为 0，波动依然存在。对依赖 Agent 干活的工程师来说，这种不一致会成为反复出现的摩擦来源。

多次试次还给你更多可检查的行为。一个通过四次、失败一次的任务，提供了比较不同路径的好机会：Agent 是不是找到了不同的文档？换了另一个工具？误读了一次返回？复盘这些差异，往往能指出一些你可以拿去验证的改动。

### 如何选择试次数量

下面的区间可以作为每个任务跑几次试次的起点。当结果在每次运行之间变化、你想找的是很小的提升，或者你想抓到一种很少发生的失败时，通常需要更多试次。

**按评测目标建议的试次数量**

| 评测目标 | 每个任务、每套配置的起始试次数 | 为什么从这里开始 |
| --- | --- | --- |
| 检查一个新任务及其校验 | — | 一次运行就能暴露明显的搭建或校验问题，免得你在重复试次上先花掉预算。 |
| 探索不一致的行为 | — | 少数几次运行就能暴露不同路径和反复出现的问题，让你先看到行为如何波动。 |
| 试点比较两个产品版本 | 每个版本 5–10 次 | 两个版本都重复跑，可以初步估计表现差距有多大、它在运行之间又波动多少。 |
| 检测一个小的提升 | 依据你初始结果的波动幅度，以及你想检测的提升有多小来定 | 小的增益更难与正常波动区分开。所需的次数取决于增益的大小和结果的波动程度。 |
| 调查罕见失败，或度量任务可靠性 | 依据你想检测的失败率，或你想确立的可靠性来选次数 | 不常见的失败在少数几次试次里可能根本看不到。要抓到它们，或者要支撑一个强的可靠性结论，所需预算必须与失败率和置信要求相匹配。 |

注：原文表格第 1、2 行的"起始试次数"单元格在清洗后的纯文本里为空，这里不做推测，保留为"—"。

即便是头部 AI 实验室，用的试次数也不一样。OpenAI 在 SWE-bench Verified 上每个任务平均跑四次尝试，Anthropic 平均跑 25 次试次。对你自己的评测来说，有用的次数取决于结果波动有多大、你想检测的提升有多小。针对编码 Agent 的研究显示，更小的提升可能需要多得多的重复。先做一次试点摸清这种波动，再用它来规划你的比较需要多少试次。

你想检测的提升越小，通常就需要越多试次，才能把它和正常波动区分开。举例来说，这项编码 Agent 研究估计，在它观测到的中位波动水平下，要检测 2 个百分点的提升，每个系统大约需要 9 次完整基准运行；检测 1 个百分点则需要 36 次。这些估计假设统计功效为 80%、显著性阈值为 5%，并且每次完整运行包含 500 个任务。

### 理解 pass@1、pass@k 与 pass^k

评测 Agent 时，有三个值得理解的指标：pass@1、pass@k 和 pass^k。前两个来自代码生成研究——那里的测试可以检查一个系统是在一次尝试中、还是在若干个候选里产出了可用的解。OpenAI 2021 年的 HumanEval 论文改进了这些概率的估计方法。

随着评测扩展到处理日常业务流程的 Agent，一致性成了另一个重要问题。2024 年的 τ-bench 论文引入了 pass^k，用来衡量 k 次独立试次全部成功的概率，再在任务间取平均。三个指标合起来，分别描述单次尝试上的成功、多次尝试内的成功，以及重复运行之间的一致性。

**衡量 Agent 的成功与一致性**

| 指标 | 它回答的问题 | 什么时候用 |
| --- | --- | --- |
| pass@1 | Agent 在单次尝试中成功的可能性有多大？ | 当 Agent 只有一次机会完成任务时，衡量表现。 |
| pass@k | k 次尝试中至少有一次成功的可能性有多大？ | 评测允许多次尝试、并且能辨认出正确结果的工作流。 |
| pass^k | k 次尝试全部成功的可能性有多大？ | 衡量 Agent 在重复运行中完成同一个任务有多稳定。 |

2024 年 τ-bench 零售评测的结果，说明了为什么值得在重复试次上衡量成功。GPT-4o 的函数调用 Agent 单次尝试的平均成功率为 61.2%，用 pass@1 衡量。它的 pass^8 分数低于 25%——也就是说，在任务间取平均，八次独立试次全部成功的概率不足 25%。

### 在加试次与加任务之间做选择

Agent 评测要花时间和算力，所以在"加任务"和"加试次"之间选，取决于你需要学到什么。重要的工作流或条件缺失时，就加任务。当你需要更强的证据、来说明 Agent 对你已覆盖的那些场景处理得有多稳定时，就加试次。

重复试次能帮你弄清 Agent 处理一个任务有多稳定，但重复的收益有上限。一旦对这类行为有了更清楚的图景，去测更多有代表性的任务、而不是对一小批任务跑更多次，也许更能说明整个产品的表现。用初始结果判断不确定性还留在哪里。如果你想检测的是很小的提升，可能需要更多任务、更多试次，或者两者都要。

### 结论

用重复试次评估 Agent 完成你产品所支持工作流的可靠程度。检查结果和执行轨迹，找出行为在哪里波动，并验证对工具、文档或错误信息的改动是否解决了这些问题。在重复与有代表性的任务覆盖之间取得平衡，让你的结果既能支撑关于单个工作流的结论，也能支撑关于整体产品体验的结论。

## 三个自测问题

1. 你的 Agent 单次成功率 61.2%，pass^8 却低于 25%。如果产品承诺的是"用户多试几次基本都能成"，这个组合说明问题出在哪里——是能力不够，还是稳定性不够？
2. 老板要你验证一个"大约 1 个百分点"的改进。按文中的估计，你需要多少次完整运行？如果预算只够 9 次，你会怎么改写这个结论的表述？
3. 什么信号出现时，说明该停止加试次、转而加任务？用"不确定性还留在哪里"这句话，给出一个可执行的判断步骤。
