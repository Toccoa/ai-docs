## 今日速览

- **E0-03 术语与组件**：`task / rollout / harness / verifier / trace` 五个词构成评测的最小词汇表。混用它们的人，通常也没分清自己改的是哪一层——而"改了哪一层"正是所有可比性的前提。
- **E0-04 信度、效度、区分度**：信度是"再测一次还一样吗"，效度是"测的是不是那件事"，区分度是"能不能把不同系统分开"。三者缺一，分数就只能当日志看，不能当证据用。

## 知识点 1：术语与组件（E0-03）

### 一句话结论

一次 Agent 评测由五个可独立替换的部件组成：**任务（task）、试次（rollout/trial）、执行架（harness）、验证器（verifier）、轨迹（trace）**；说清一个分数，等于说清这五个部件各自是什么版本。

### 为什么重要

**第一，同一个词在不同社区指不同的东西。** "harness" 至少有两个用法：

- **agent harness**：包住模型和工具的那层循环（工具接口、上下文管理、终止条件）。Terminal-Bench 审计里"只换 harness 差 29.9 个百分点"，换的是它。
- **eval harness**：跑 rollout、聚合分数、记录日志的那层框架（Harbor、Inspect、Terminal-Bench 的 runner）。Anthropic 那篇"资源配额差 6 个百分点"，改的是它管的容器。

这两层的方差完全不同，混成一个词，你就无法判断一份榜单到底在比什么。

**第二，组件边界就是责任边界。** 出问题时，"任务写错了""harness 提前终止了""镜像里少个包""评分器解析错了"是四个不同团队、四种不同修法。分不清组件，复盘就只能停留在"模型不行"。

**第三，组件化是单变量比较的前提。** 你只有先把五元组拆成五个可替换件，才可能做到"一次只动一个"。

### 核心机制

```
task（指令 + 初始状态 + 判据）
   │
   ├── rollout（一次完整尝试）──▶ 环境状态变更
   │        │
   │        ├── agent harness：模型 ↔ 工具 ↔ 上下文
   │        └── trace：消息、工具调用、观察、状态快照
   │
   └── verifier：读终态 → 判分
          │
          └── eval harness：调度 N 次 rollout、聚合、记录版本
```

| 术语 | 定义 | 谁负责 | 常见别名 | 混用的后果 |
|---|---|---|---|---|
| **task** | 一道题：指令 + 初始状态 + 成功判据 | 出题人 / 领域专家 | case、item、instance | 把"题难"误判成"模型弱" |
| **rollout / trial** | 对同一任务的一次完整尝试 | eval harness | run、attempt、episode | 把"抽样波动"当成"能力差异" |
| **agent harness** | 模型与工具之间的循环逻辑 | Agent 开发者 | scaffold、agent framework | 把脚手架收益算成模型能力 |
| **verifier / grader** | 读终态并判定通过与否 | 评测开发者 | oracle、checker、judge | 把评分 bug 当成模型进步 |
| **trace** | 结构化的全过程记录（含工具调用与状态） | eval harness | transcript（仅对话）、log | 只看结论，无法归因 |
| **suite** | 一组 task 的集合 | 评测负责人 | benchmark、dataset | 换题后仍与旧分数比较 |

两个容易混的细节：

- **transcript ≠ trace**。transcript 是对话文本；trace 还包含工具调用参数、返回值、文件 diff、环境快照。归因靠 trace，不靠 transcript。
- **trial ≠ rollout 的集合**。一次 trial 是"某任务的一次尝试"；一个 suite 的分数是"所有 trial 的聚合"。

### 怎么做

1. **建一张五件套清单**，每次评测前填一遍：任务版本、harness 版本、镜像 digest、验证器版本、rollout 次数。
2. **在报告里用固定句式**："在 *agent harness H@v1.4*、镜像 *img@sha256:…*、每任务 *k=3* 次 rollout 下，成功率 *0.46（聚类 SE 0.11）*"。
3. **给每个部件一个所有人**。没有所有人的部件，出问题时一定没人修。
4. **参照成熟约定**：Harbor 的任务目录（`instruction.md`、`task.toml`、`solution/`、`tests/`）、Inspect 的 sample/scorer 结构、HF Hub 的 `.eval_results` 与 trace 格式。用现成约定，比自创一套省三个月。

### 权衡与坑

- **别把"组件化"做成"八个仓库"**。小团队用一个仓库 + 清晰目录就够，关键是**版本可追溯**，不是物理隔离。
- **agent harness 与 eval harness 的日志会重叠**，但归属要分清：agent 的日志描述"它做了什么"，eval 的日志描述"我们怎么跑、怎么判"。
- **"模型"本身也是组件**，而且它包含权重版本与推理参数（temperature、reasoning effort、provider 量化）。同一个开放权重模型换 provider，HF 的例子里通过数从 11/24 变成 13/24。

### 自测题

1. 同事说"我们升级了 harness，分数涨了 4 个点"。你要追问哪两个问题，才能判断他说的是哪一层 harness？
2. 为什么"只看 transcript 做归因"会系统性高估模型的责任？举一个具体失败模式。
3. 如果只能记录一个版本号，你记镜像 digest 还是 harness 版本？为什么？

## 知识点 2：信度、效度、区分度（E0-04）

### 一句话结论

一个分数要能用来做决策，必须同时满足三件事：**可重复（信度）、测的是那件事（效度）、能把不同系统分开（区分度）**；三者是并列门槛，不是可以互相补偿的加分项。

### 为什么重要

**信度不够，你测到的是噪声。** Hugging Face 的例子里，同一配置重跑一次，24 次 rollout 通过数从 11 变成 10；按任务聚类后的标准误约 0.11。也就是说，两个模型差 3 个百分点，很可能只是重跑一次的结果。

**效度不够，你稳定地测错了东西。** 用"拒答率"衡量安全，在自杀自伤场景里方向是反的——拒答本身就是失败；用"技术任务通过率"衡量组织能力，而 522 个知名基准里只有 23% 声称覆盖任何组织维度。这两种错误都不会让数字变难看，只会让结论变错。

**区分度不够，你测对了但分不开。** 同一组 8 个任务上，三个模型全部 24/24 通过——任务本身没错，但它对这三个模型没有信息量。饱和的评测不是"大家都很好"，是"这把尺子到头了"。

### 核心机制

**信度（reliability）的三种检验：**

| 类型 | 问的问题 | 廉价做法 | 判据（经验值） |
|---|---|---|---|
| 重测信度 | 同配置再跑一次，结果一样吗 | 同配置跑两遍 | 差异落在各自 CI 内 |
| 评分者间信度 | 两个评分器/两个人，判得一样吗 | 30 条人工标注 vs judge | Cohen's κ ≥ 0.6 可用；≥ 0.8 较好 |
| 内部一致性 | 同一能力的多道题，答案一致吗 | 题目间相关 / Cronbach α | 太低说明题在测不同东西 |

**效度（validity）的三层：**

- **构念效度**：指标是否抓住了概念。检验方法：**反向构念检查**——想一个"该指标满分但系统很糟"的例子，想得出来就说明它不能单独用。
- **内部效度**：分数是否只由目标变量驱动。检验方法：**加一个不该有影响的扰动**（换选项顺序、换无关措辞），看分数动不动。
- **外部效度**：结论能否外推到目标场景。检验方法：**换一个部署形态/用户群/语言**，看结论是否还成立（API vs 产品差 34 个百分点，就是外部效度问题）。

**区分度（discrimination）的核心直觉：**

一道题的信息量，取决于它有多"接近五五开"。所有人都过、所有人都不过的题，对排序没有贡献；30%–70% 通过率的题信息量最大。这不需要真的跑 IRT，画一张**难度直方图**就能看出来。

### 怎么做

1. **信度体检（半天）**：同配置跑两遍，报告两次的差值与 CI。差值大于 CI，先查环境与评分器。
2. **效度体检（半天）**：写下 claim，再写"什么情况下这个指标会骗我"。写不出来，说明还没想清构念。
3. **区分度体检（一小时）**：按任务画通过率直方图。若超过一半的任务落在 0% 或 100%，这批题对当前模型组无效，需要换题或加难度。
4. **三条一起报**：分数 + 区间 + 难度分布。只报第一条的报告，不值得被相信。

### 权衡与坑

- **提高信度会诱导你缩小任务集**（少跑、少变、少错），但任务集一小，效度和区分度都会掉。三者要一起调。
- **κ 在类别极不平衡时会失真**（比如 95% 都是"通过"）。这时报 PABAK 或 Gwet's AC1，别硬报 κ。
- **区分度是相对的**：对弱模型有区分度的题，对强模型可能已经饱和。所以"这套题好不好"没有绝对答案，只有"对谁、在什么时候"。
- **不要把"显著"当成"有效度"**。样本足够大时，一个稳定测错东西的评测也能给出极小的 p 值。

### 自测题

1. 一个评测重跑两次，分数差 5 个点，但两次的 95% CI 都是 ±1 个点。这更像信度问题、效度问题还是区分度问题？下一步查什么？
2. 给你的评测设计一个"反向构念检查"：哪个指标拿满分反而说明系统很糟？
3. 为什么"任务太难"和"任务太易"对区分度的伤害是同一种？各举一个真实例子。

## 今日观察

1. **术语混乱不是语文问题，是测量问题。** 今天这两个知识点其实在说同一件事：你必须能把"我改了什么"和"我测到了什么"分别命名；命名不清，单变量比较就无从谈起。
2. **信度可以靠多跑解决，效度不能。** 多跑只能压缩随机误差，压不掉系统性偏差。所以预算应该优先花在"构念对不对"上，而不是"再多跑几次"。
3. **区分度和饱和是一枚硬币的两面。** 昨天讲的"pass@3 高、pass^3 低"，今天换个角度看就是区分度问题：这套题能把"会"和"稳"分开，但分不开三个都达到能力上限的模型。
