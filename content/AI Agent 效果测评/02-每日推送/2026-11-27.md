# 2026-11-27｜第 001 期：Agent 评测的第一性原理

> 今日 2 个知识点（E0-01 + E0-02）｜预计 22 分钟｜主题：**分数是一个系统的输出，不是模型的能力**
>
> 阅读方式：先看每点的「一句话结论」，再读「怎么用」，最后做自测。今天不要求记住定义，只要求建立一条判断链——**看到一个 Agent 的分数时，先问哪五个问题**。

---

## 今日速览

- **E0-01 Agent 评测不是"更大的 LLM 评测"**：单轮评测测的是"模型说了什么"，Agent 评测测的是"一个由模型、harness、环境、预算组成的系统，在任务分布上到达可判定终态的概率"。这不是措辞差别：固定模型、只换 harness，Terminal-Bench 上准确率可以差 **29.9 个百分点**；固定模型和 harness、只换资源配额，一个模型能差 **6 个百分点**（p < 0.01）。
- **E0-02 三层对象与两种问题**：能力（能不能做）、可靠性（每次都能做吗）、产品价值（值不值得用）是三个不同的问题，一个成功率数字最多回答其中一个。而在动手之前，你还要分清自己在问**观测问题**还是**因果问题**——前者只要横截面对比，后者必须单变量干预；混淆这两者，是"评测做完了但结论不能用"的最常见原因。

## 知识点 1：Agent 评测 ≠ 更大的 LLM 评测（E0-01）

### 一句话结论

Agent 评测的测量单元不是一段文本，而是**一条轨迹**；判定方式不是比对答案，而是**检查环境终态**；因此分数是五元组 `(模型, harness, 环境, 任务集, 预算)` 的函数，**任何只报"模型 + 分数"的结论都缺了四个自变量**。

### 为什么重要

先把三个结构性差异摆出来，它们决定了后面所有方法论：

| 维度 | 单轮 LLM 评测 | Agent 评测 |
|---|---|---|
| **被测对象** | 一次生成（prompt → completion） | 一次 rollout（多轮动作 + 观察 + 状态变更） |
| **判定依据** | 输出字符串（匹配 / 打分） | 环境终态（文件、数据库、页面、进程） |
| **分数方差来自** | 采样温度、prompt 措辞 | 采样 + 工具行为 + 环境配置 + 基础设施 + 任务难度 |
| **可复现性** | 固定 seed 基本可复现 | 固定 seed 也不够，环境会漂移 |

第三行是分水岭。单轮评测里，"环境"是常量；Agent 评测里，"环境"是**被测系统的一部分**——这一点如果没建立，后面学的统计、评分、工程化全部会建立在错误的假设上。

**证据一：harness 是分数的一部分，而且权重很大。**
Hugging Face 在 2026-11-23 的评测指南里引了一份对 Terminal-Bench 的审计：**保持模型不变、只更换 agent harness，准确率变化最高达到 29.9 个百分点**。这意味着两份"同一模型"的榜单成绩，很可能根本没在测同一件事。

**证据二：基础设施也是分数的一部分。**
Anthropic 在《Infrastructure noise in agentic coding evals》里做了更狠的实验：同一个 Claude 模型、同一个 harness、同一套任务，只改容器的资源配额，Terminal-Bench 2.0 上最宽松与最严格配置之间差 **6 个百分点**（p < 0.01）。机制并不神秘——资源给得紧，容器会在瞬时内存峰值时被 OOM kill，基础设施错误率从严格配置的 **5.8%** 一路降到不设限时的 **0.5%**；而当配额超过任务规格约 3 倍之后，多余的资源不再只是"修稳定性"，而是**真的在帮 agent 解题**（拉大依赖、跑重测试、开子进程），成功率开始跑赢基础设施错误率的下降速度。

**证据三：连产品形态都会改变分数。**
Anthropic 的安全评测文章给了一个更刺眼的数字：在 Claude Fable 5.1 的多轮安全评测上，**API（裸模型）与 claude.ai（带系统提示词）之间的"恰当响应率"差距高达 34 个百分点**。同一个模型，两种部署方式，两个世界。

把这三条放在一起，可以得出今天最重要的一句话：**你测的从来不是模型，是"模型 + 一整套装置"。**

### 核心机制：五元组

把任何一次 Agent 评测写成这个五元组：

```
run = (model, harness, env, task_set, budget)
score = f(run)
```

- **model**：权重版本 + 推理参数（temperature、max tokens、reasoning effort）
- **harness**：agent loop、工具接口、上下文管理、重试策略、终止条件
- **env**：容器镜像、依赖版本、资源配额、网络与权限、初始状态
- **task_set**：任务版本、数量、难度分布、评分脚本
- **budget**：每任务步数上限、token 上限、墙钟时间上限、并发度

**比较的铁律：一次只动一个。** 想比较模型，就冻结后四个；想比较 harness，就冻结其余四个。任何"我们换了模型，分数涨了 5 个点"的说法，在没有五元组的情况下都无法证伪——包括说这话的人自己也证伪不了。

### 怎么做

1. **报分数时同时报五元组**，哪怕只是脚注。做不到全报，至少报 harness 版本与环境镜像 tag。
2. **单次运行不是测量，是抽样**。每个任务至少跑 3 次，报 `pass@k`（k 次里成功一次）和 `pass^k`（k 次全成功）两个数，并附区间。
3. **失败必须归因到层**，而不是笼统写"模型能力不足"。最小归因分类：任务/环境问题、工具调用错误、规划错误、提前终止、判定错误。
4. **对"小差距"保持怀疑**。在基础设施噪声之上，2–3 个点的领先很难与"更好的机器"区分开。

### 权衡与坑

- **`pass@k` 会系统性高估可靠性。** Hugging Face 的实操案例很典型：8 个任务各跑 3 次，`pass@3 = 7/8`（看起来几乎全对），`pass^3 = 1/8`（只有一个任务次次都对）。如果这个 agent 是无人值守跑的，你该看的是后者。
- **别用平均值掩盖双峰。** 20 个任务里 10 个必过、10 个必败，均值 0.5 与"每个任务都五五开"的 0.5 是两种完全不同的系统。
- **固定 harness ≠ 固定基础设施。** 同一份镜像跑在 K8s 与跑在裸机上，资源超卖策略不同，分数就会不同。
- **不要跨 harness 比较历史分数。** harness 升级后，旧分数应当作废或标注，而不是接着画趋势线。

### 自测题

1. 同事说"我们换了个新模型，SWE 任务成功率从 62% 提到 65%"。你需要问哪五个问题才能判断这个结论是否成立？
2. 一个 agent 在 20 个任务上 `pass@5 = 0.9`、`pass^5 = 0.2`。这两个数字分别对应什么产品场景？如果你只能优化一个，你选哪个，为什么？
3. 为什么"固定随机种子"不足以让 Agent 评测可复现？举两个具体机制。

## 知识点 2：三层对象与两种问题（E0-02）

### 一句话结论

在选指标之前，先回答两个问题：**你要测的是能力、可靠性还是产品价值？你问的是观测问题还是因果问题？** 这两个问题决定了实验设计，而实验设计决定了结论能不能用。

### 为什么重要

**第一层分歧：能力 / 可靠性 / 产品价值。**

| 层 | 回答的问题 | 典型指标 | 常见误用 |
|---|---|---|---|
| 能力 | 这件事它**能不能**做到 | `pass@k`、最佳轨迹成功率 | 拿 `pass@k` 宣称"稳定可用" |
| 可靠性 | 它**每次**都能做到吗 | `pass^k`、失败率、失败模式分布 | 拿单次演示当 SLA |
| 产品价值 | 用了它，**人省了多少** | 任务完成时间、人工接管率、返工率、成本/任务 | 只用离线成功率替代业务指标 |

三层之间没有自动的推导关系。一个能力很强但可靠性很差的 agent，产品价值可能是负的——因为用户要为它的失败付出检查成本。

**第二层分歧：观测问题 vs 因果问题。**

Anthropic 在安全评测文章里给了一个干净的对照：

- 观测问题：「模型对可能助长饮食失调的内容，回应是否安全？」——描述现状，横截面比较就够。
- 因果问题：「修改系统提示词，会不会改变模型对该类内容的回应安全性？」——必须**单变量干预**，同一模型、同一任务集，只改提示词。

这两类问题的报告方式完全不同。观测结论只能写"两个配置下分数不同"，不能写"这个改动让它更安全了"。把观测当因果，是评测报告里最常见、也最难被发现的错误——因为数字看起来完全正常。

**第三层：构念效度（construct validity）——你测的到底是不是你想测的那件事。**

这是本知识点最值钱的部分，两个真实案例：

**案例一：用"拒答率"衡量安全，方向可能是反的。**
Anthropic 指出，在自杀与自伤相关对话中，**拒答本身就是失败**。一个对所有相关提示都拒答的模型，拒答率评测会拿满分，但它并不是更安全的模型——理想行为是共情回应并把用户引向人类支持资源。所以他们的多轮安全评测改用「恰当响应率」：按风险领域定制的 rubric 判定**整段对话**是否恰当，**一个坏回合就让整段失败**。

**案例二：把"任务"当分析单元，忽略了组织难度。**
arXiv 2611.03494《Harder Than the Task》指出：大量有经济价值的工作发生在组织里，成败不只取决于技术难度，还取决于活动之间的依赖、分散的知识、不同的权限、时间约束与利益冲突。他们把组织理论做成一套工作结构分类法去审现有基准，结论是：**不到四分之一的知名基准声称覆盖了任何一个组织维度**。也就是说，"技术上更难的任务"和"组织上更难的任务"是两种能力，现有榜单基本只测了前者。

**案例三：度量本身就是干预。**
回到 34 个百分点那个数字：同一个模型，API 与产品两个配置，安全响应率差 34 个百分点。如果你只报一个数，读者无法知道你测的是哪个系统。**构念效度的问题，往往不是"指标错了"，而是"指标被当成了全部"。**

### 核心机制：claim → construct → metric → design

任何一次评测，都可以写成四行：

```
Claim      ：一句可证伪的话（"该 agent 能在 5 分钟内独立完成 X 类工单的 80%"）
Construct  ：这句话里的关键概念怎么定义（"独立完成"= 无需人工编辑即可提交）
Metric     ：用什么数衡量构念（一次通过率 + 人工编辑率）
Design     ：怎么排除替代解释（同 harness、同预算、配对比较、区间估计）
```

四行里任何一行含糊，后面的工作都会白做。特别注意：**Claim 必须是可证伪的**。"这个 agent 很强"不是 claim，"这个 agent 在 50 条工单上一次通过率 ≥ 80%，且人工编辑率 < 10%"才是。

### 怎么做

1. **先写 claim，再选指标。** 写不出可证伪的 claim，说明你还没想清楚要做什么决策。
2. **给指标标注层级**：这个数是能力、可靠性还是价值？报告里分开写，不要混在一个"综合得分"里。
3. **区分观测与因果**，并在报告标题里就写清楚。观测结论用"在 X 配置下，A 比 B 高 N 个点"；因果结论才用"X 导致"。
4. **做一次"反向构念检查"**：如果一个系统在该指标上拿满分，但你知道它实际上很糟，那这个指标就不可单独使用。拒答率就是这样的指标。
5. **记录未覆盖的维度**。像《Harder Than the Task》那样，明确写"本次评测不覆盖组织/权限/协作维度"，比假装覆盖了要诚实得多，也有用得多。

### 权衡与坑

- **代理指标会漂移。** 用"工具调用次数"代理"效率"很常见，但 agent 可以通过无意义调用刷低/刷高这个数。
- **平均值会隐藏分层。** 按类别拆开报，比报总分有用十倍；不显著的变化也要报。
- **显著 ≠ 重要。** 样本足够大时，0.3 个点的差异也可能显著，但它不影响任何决策。
- **构念不是一次定好的。** 任务分布变了、用户变了，构念也要重审；建议每个季度做一次"这个指标还代表我们关心的事吗"的复盘。

### 自测题

1. 你的 agent 在内部 200 条任务上成功率 85%，老板问"能不能上线"。你需要补充哪三类信息才能回答？
2. "把温度从 0.7 降到 0.2，agent 更可靠了"——这是观测结论还是因果结论？要做成因果结论，实验该怎么设计？
3. 找一个你熟悉的评测指标，构造一个"拿满分但系统很糟"的例子，并说明该指标缺了哪个维度。

## 今日观察

1. **五篇文章其实在说同一件事：分数的方差主要不来自模型。** harness（29.9pp）、资源配额（6pp）、部署形态（34pp）、任务抽样（$225 → $47 的预算实验）、构念选择（拒答率 vs 恰当响应率）——每一个都能单独改变结论。这解释了为什么"评测"正在从"跑个榜单"变成一门工程学科。
2. **评测基础设施正在标准化。** Harbor + ATIF trace 格式、Inspect、HF Hub 的 `.eval_results` 与 trace viewer、预注册模板——2026 年下半年的共识是：**评测的可复现性靠格式和版本记录，不靠自觉**。
3. **评测开始有经济学。** 黑盒测试选择那篇论文的核心不是"省钱"，而是"用 20% 的预算得到可用的估计，并把剩下的预算花在早期失败发现上"。当你一天要跑几十次回归时，这个取舍比任何单点提升都重要。
