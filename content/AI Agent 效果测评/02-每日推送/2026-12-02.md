## 知识点 1：污染与泄漏（E1-05）

### 一句话结论

污染不是一个道德问题，是**评测的生命周期问题**：一道题被公开得越久、越有名，它作为"测量工具"的效力就越低——不管你有没有故意训练它。

### 为什么重要

**第一，污染已经普遍到无法忽略。** OpenAI 对 SWE-bench Verified 的审计发现：**每一个被测的前沿模型，都能复现某些任务的参考补丁或逐字题目细节**。这不是"某个模型作弊"，是"公开仓库 + 广泛使用"的必然结果。

**第二，独立评测正在成为硬需求，但供给不足。** HF 的数字：**98.2% 的模型-基准分数只由一方报告**。这让"这个分数可不可信"变成了一个结构性问题，而不是个别团队的严谨度问题。

**第三，隐藏测试集是必要但不充分的。** Artificial Analysis 说其 Intelligence Index v5 有 **60%** 建立在私有测试集或留出答案之上；Google DeepMind 在试点**双盲评测**（安全飞地同时隐藏测试提示词与模型权重）。但一项对 **60 个基准**的研究发现：**公开与私有基准的饱和程度相似**——**一旦基准被广泛采用，隐藏数据并不能阻止饱和**；真正与更低饱和相关的是**专家策展**和**更大的测试集**。

### 核心机制：三种泄漏

| 泄漏类型 | 机制 | 症状 | 手段 |
|---|---|---|---|
| **训练污染** | 题目/答案进入预训练或微调数据 | 分数虚高；逐字复现；对措辞变化极敏感 | 时间切分（用 cutoff 之后的题）、私有保留集、canary 字符串 |
| **基准过拟合** | 社区针对榜单反复调优 | 榜单分数涨、真实场景不涨 | 换题、双盲、留出集 |
| **提示泄漏** | 测试集内容出现在系统提示、few-shot、检索库 | 模型"恰好"知道答案 | 审计提示词与检索库；测试集隔离 |

**时间切分是最便宜的一道防线**：任务创建日期必须晚于被测评模型的训练截止日期。做不到时，至少标注"该题可能已被见过"。

**检测污染的四个信号**（按成本从低到高）：

1. **逐字复现**：让模型"背"题目，看它能否复述原文；
2. **补丁复现**：让模型直接给出参考补丁，看相似度；
3. **措辞扰动**：把题目换成同义改写，分数应基本不变；掉太多说明它记的是措辞；
4. **canary**：在题面里埋一个无意义字符串，看模型是否会复述出来。

### 怎么做

1. **给每道题记两个日期**：`created_at` 与 `model_cutoff_at`。`created_at < cutoff` 的题打上"可能污染"标签。
2. **建一个私有保留集**：20–50 条，只在发布前跑，不进 CI、不进公开仓库。
3. **做一次措辞扰动测试**：抽 20 条题，同义改写后重跑，看分数变化。掉 10 个点以上，就要怀疑记忆。
4. **记录"分数可比性"**：换题、换 judge、换 harness 时，明确写"与历史分数不可比"。

### 权衡与坑

- **开放与污染是一对矛盾**。公开题目才能被审查（SWE-bench 的审计正是靠公开），但公开就会被看见。实务答案是**分层开放**：基础设施、评分方法、退役题公开；在用的题放门控数据集。
- **"私有"不等于"安全"**。私有集也会饱和，只是慢一点。
- **别把饱和当成污染**。饱和是"大家都做到了"，污染是"大家背过了"。两者的处理方式不同：前者换题，后者换数据。
- **canary 会被清洗掉**。它不是保险，只是一道便宜的探测。

### 自测题

1. 一道题 2024 年公开、模型 cutoff 是 2025 年。它还能用吗？如果能，需要补什么标签？
2. 为什么"隐藏测试集"不能解决饱和？那它解决的是什么问题？
3. 设计一个成本低于 1 小时的污染探测实验，并说明它能排除什么、不能排除什么。

## 知识点 2：环境与工具（E1-06）

### 一句话结论

Agent 评测里，**环境是被测系统的一部分**：镜像、依赖、资源配额、网络策略、并发度，任何一项变了，分数就可能变；所以环境必须像代码一样**版本化、可复现、可审计**。

### 为什么重要

**第一，环境直接改分数。** Anthropic 的实验：同模型、同 harness、同任务，只改资源配额，Terminal-Bench 2.0 上最宽松与最严格相差 **6 个百分点**（p < 0.01）；基础设施错误率从 **5.8%** 降到 **0.5%**。

**第二，环境的失败会伪装成模型的失败。** HF 的例子里，多次失败的开头是"缺 NumPy/SciPy"——任务期望 agent 自己装，但没装成。**如果只看成功率，你会以为模型不会拟合光谱。**

**第三，依赖会腐烂。** Terminal-Bench 2.1 修了 **9 个**"外部依赖在发布后发生变化"的任务。题没变、模型没变，分数变了。

### 核心机制：环境清单

```yaml
image: <registry>/<name>@sha256:<digest>     # 必须用 digest，不用 tag
deps:
  lockfile: requirements.lock | package-lock.json
  install_at: build | runtime                # 谁负责装依赖，必须写清
resources:
  guaranteed: {cpu: 2, mem: 8Gi}             # 保证配额
  limit:      {cpu: 6, mem: 24Gi}            # 硬上限（建议 3x）
network: none | proxy:<allowlist>
concurrency: 8
reset: per_task | per_rollout
```

**两个关键决定：**

- **配额要写两个数**（保证 + 上限），不要写一个。写一个等于"零余量"，瞬时峰值就会 OOM。
- **依赖装在哪一层要写清**。装在镜像里（稳定、但改环境）还是让 agent 自己装（真实、但引入失败）——**这是构念选择，不是实现细节**。

### 怎么做

1. **镜像固定 digest**，每次评测记录 digest。
2. **每任务重置**：文件系统、数据库、缓存都要回到初始状态；否则前一次 rollout 会污染后一次。
3. **资源按"下限 + 3 倍上限"配**：Anthropic 的校准结论是，1x–3x 之间分数变化在噪声内（p = 0.40），3x 以上才开始"帮模型解题"。
4. **记录 env hash**：把镜像 digest + 依赖 lock + 配额 + 网络策略算成一个哈希，写进结果。
5. **定期做"环境回归"**：同一批题、同一模型，隔一个月重跑，看分数是否漂移。

### 权衡与坑

- **保真 vs 可控**：越接近真实环境，越不可控；越可控，越不像真实。建议**两套环境**：开发用可控的（快、稳），发布用保真的（慢、贵）。
- **mock 是有代价的**：mock 掉的外部服务不会失败，而真实服务会——这会系统性高估成功率。
- **并发会引入竞争**：并发高时，API 限流、磁盘 IO、内存峰值都会变，分数可能掉。并发度要固定并记录。
- **别忽略"时间"这个环境变量**：通过率会随时段波动（API 延迟随流量变化），公开评测应跨天多次运行。

## 今日观察

1. **M1 六个点其实在回答同一个问题：这道题凭什么算一道题。** 来源（E1-01）、规格（E1-02）、分层（E1-03）、难度（E1-04）、污染（E1-05）、环境（E1-06）——每一环都在决定"分数能不能被解释"。
2. **可复现性不是"严谨"，是"可争论"。** 只有别人能重跑，你的结论才可能被证伪；不能被证伪的结论，在工程上等于没有。
3. **污染与环境是两种"时间"问题。** 污染是题被时间淘汰，环境是环境随时间漂移。两者都提醒你：**评测是有保质期的。**
