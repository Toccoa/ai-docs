# AI Agent 效果测评 · 知识地图

> 从 0 到能独立设计、执行、并让老板相信一次 Agent 评测。
> 全量 56 个知识点，按 M0 → M8 顺序推进，每天 2 个，约 28 天走完一轮，之后转入「前沿跟踪 + 间隔复习 + 真实案例归因」模式。

## 这张地图在讲什么

一句话：**分数是怎么被生产出来的，以及它会在哪里骗你。**

普通 LLM 评测的链路是「输入 → 输出 → 比对答案」。Agent 评测的链路是「任务 → 环境 → 轨迹 → 终态 → 判定 → 聚合」。中间多了四个环节，每个环节都能单独把结论带偏：换一个 harness，Terminal-Bench 上的准确率可以差 **29.9 个百分点**；换一套资源配额，同一个模型在 Terminal-Bench 2.0 上可以差 **6 个百分点**（p < 0.01）；同一份评测跑在 API 和产品里，安全响应率可以差 **34 个百分点**。

所以这门课不教"哪个榜第一"，教的是**如何让一个数字变得可解释、可复现、可决策**。

## 主线：一个分数的五次变形

```
真实能力
  ↓ 被任务集采样        ← M1：你测的是不是你想测的那件事（构念效度）
  ↓ 被环境与 harness 放大/衰减  ← M4/M5：系统噪声
  ↓ 被评分器判定        ← M2：judge 的偏差与失效
  ↓ 被统计聚合          ← M3：区间、样本量、多重比较
  ↓ 被组织解读          ← M7：报告与决策
报告的分数
```

每学一个知识点，都问自己一句：**它在上面这条链的哪一环，去掉它，结论会怎么变？**

## M0 心智模型：先搞清楚你在测什么（6 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| E0-01 | 为什么 Agent 评测不是"更大的 LLM 评测" | 输出从一段文本变成一个轨迹，判定从比对答案变成检查环境终态 |
| E0-02 | 三层评测对象：能力 / 可靠性 / 产品价值 | 一个分数回答不了三个问题，先确定你要回答哪一个 |
| E0-03 | 评测系统的组件与术语 | task / rollout / harness / verifier / trace，这五个词混用，后面的讨论全部失焦 |
| E0-04 | 第一性原理：信度、效度、区分度 | 没有这三样，分数只是日志 |
| E0-05 | 分数的五类污染源 | 模型、harness、环境、评分器、抽样——比较之前先固定其中四个 |
| E0-06 | 评测的成本模型 | 一次 rollout 的真实成本 = token + 环境时长 + 人审 + 机会成本 |

**出口标准**：能对一个现成的榜单说出"这个分数在什么条件下才可比"，并列出至少 4 个必须固定的变量。

## M1 任务与数据集：评测的上限由题决定（7 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| E1-01 | 任务从哪里来 | 真实失败日志 > 用户访谈 > 公开基准 > 合成任务，顺序不能倒 |
| E1-02 | 任务规格化 | 指令、初始状态、成功判据、允许动作，缺一件就没法判分 |
| E1-03 | 数据集分层 | 冒烟、回归、能力、对抗、长尾，五层的更新频率完全不同 |
| E1-04 | 难度校准 | 太易饱和没有区分度，太难全 0 也没有；用"参考解必过、空解必败"卡住两端 |
| E1-05 | 污染与泄漏 | 时间切分、私有保留集、双盲评测，三种手段对应三种泄漏 |
| E1-06 | 环境与工具 | 沙箱、mock、状态快照、资源配额：环境是评测的一部分，不是背景 |
| E1-07 | 版本化与冻结 | 数据集要有语义版本；改一条任务，要能说清哪些历史分数失效 |

**出口标准**：能写出一个任务的四要素规格，并说明它测的是哪个子能力、不测什么。

## M2 评分器：从"看起来对"到"判定得了"（8 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| E2-01 | 评分器分类学 | exact / 程序化 / judge / 人审，四类各有明确的适用边界 |
| E2-02 | 确定性评分 | 状态断言、文件 diff、数据库终态：能写成断言的，永远不要交给模型 |
| E2-03 | 结果评分 vs 过程评分 | 结果回答"做成了吗"，过程回答"是否用了不该用的手段" |
| E2-04 | LLM-as-judge 的工程化 | rubric、少样本锚点、结构化输出、拒判机制 |
| E2-05 | judge 的偏差与元评测 | 位置偏差、长度偏差、自我偏好；用 κ 而不是准确率衡量一致性 |
| E2-06 | rubric 设计 | 原子、二元、显式排除项；"什么不算通过"比"什么算通过"更重要 |
| E2-07 | 多评分器与冲突裁决 | 投票、分级、仲裁者——评分器之间的冲突本身就是信号 |
| E2-08 | 人审不可替代的场合 | 边界判定、新颖失败模式、价值判断 |

**出口标准**：能为一类任务写出可执行的 rubric，并用 30 条人工标注算出 judge 与人的 κ。

## M3 指标与统计：让数字带上误差棒（7 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| E3-01 | 指标地图 | 成功率、pass@k、pass^k、步数、token、延迟、成本，各自回答什么问题 |
| E3-02 | 区间估计 | 同一任务的多次 rollout 不是独立样本，标准误必须按任务聚类 |
| E3-03 | 样本量与最小可检测效应 | "能测出 3 个点的差异"需要多少任务、多少次 rollout |
| E3-04 | 配对比较与显著性 | 同题对比的方差远小于两组均值对比，这是免费的统计功效 |
| E3-05 | 方差分解 | 把总方差拆到任务、采样、环境、judge 四个来源，才知道该加钱在哪 |
| E3-06 | 部分成功与分级得分 | 0/1 之外的记分方式，以及它引入的新偏差 |
| E3-07 | Goodhart 与指标作弊 | 只过测试、猜答案、刷长度、钻 judge 空子等七种典型形态 |

**出口标准**：给定一次评测的原始 rollout 结果，能算出带聚类标准误的均值，并判断两个模型的差异是否显著。

## M4 基准与 harness：读懂别人的分数（7 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| E4-01 | 工具调用基准 | BFCL、ToolBench、API-Bank：考的是"会不会调用"还是"该不该调用" |
| E4-02 | 网页与电脑操作 | WebArena、Mind2Web、OSWorld：环境保真度决定结论能外推多远 |
| E4-03 | 软件工程 | SWE-bench 家族、Terminal-Bench：任务修复率背后是"测试是否可信" |
| E4-04 | 通用助理与多轮 | GAIA、AssistantBench、τ-bench：多轮状态与用户模拟 |
| E4-05 | 多智能体与长程 | 协作增益必须按同预算比较，否则只是"多试了几次" |
| E4-06 | 基准审计 | harness 差异、测试 bug、饱和：读榜之前先读审计 |
| E4-07 | 自建还是用现成 | Inspect、promptfoo、LangSmith/Langfuse、Harbor 的取舍 |

**出口标准**：能对一份公开榜单写出"可信度备忘"：谁跑的、什么 harness、有没有审计、饱和了没有。

## M5 评测工程化：把评测接进研发流程（7 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| E5-01 | 离线流水线与 CI 门禁 | PR 级、日级、发布级三档，成本差一个数量级 |
| E5-02 | 在线评测 | A/B、shadow、canary、interleaving 的适用条件与陷阱 |
| E5-03 | Trace 与可观测性 | OTel GenAI 语义约定、span 结构、采样与脱敏 |
| E5-04 | 隐式反馈 | 重试、放弃、复制、编辑——最便宜也最难解释的信号 |
| E5-05 | Flaky 与回归治理 | 同一输入两次不同结果，先怀疑评测，再怀疑模型 |
| E5-06 | 成本-延迟-质量三角 | 三个数放在一张图上，才有得选 |
| E5-07 | 数据飞轮 | 线上失败 → 脱敏 → 任务化 → 进回归集，闭环的四个卡点 |

**出口标准**：能为一个真实项目画出"离线 + 在线 + 人审"的三层评测架构，并给出每层的频率与预算。

## M6 安全与鲁棒：评测的攻击面（5 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| E6-01 | 提示注入与工具滥用 | AgentDojo 一类基准在测什么、漏什么 |
| E6-02 | 权限边界与数据外泄 | 最小权限、能力令牌、出口审计 |
| E6-03 | 对抗与分布外 | 攻击面从"输入文本"扩展到"工具返回值" |
| E6-04 | 长程错误累积 | 第 20 步的错误如何让前 19 步白做 |
| E6-05 | 人机协作评测 | 审批、接管、纠错：HITL 的指标是"人省了多少"，不是"人点了几次" |

**出口标准**：能对一个 Agent 做一次威胁建模，并把每个威胁映射到可执行的评测用例。

## M7 组织与决策：让评测影响决策（5 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| E7-01 | 评测作为发布门禁 | 什么条件下允许上线，谁签字，回滚阈值是多少 |
| E7-02 | 评测报告写法 | 给工程、给老板、给客户的三套写法，指标顺序都不一样 |
| E7-03 | 选型协议 | 换模型/换供应商时，用同一套任务、同一套预算、同一套 harness |
| E7-04 | 团队与角色 | 方法专家、领域专家、平台工程的分工与交接物 |
| E7-05 | 伦理、合规与披露 | 负责任的披露，以及"评测本身的风险" |

**出口标准**：能写出一页纸的发布门禁：指标、阈值、样本量、责任人、回滚条件。

## M8 Capstone：四个必须动手的项目（4 点）

| 编号 | 知识点 | 一句话要点 |
|---|---|---|
| E8-01 | 从零搭 harness | 50 个任务、3 个模型、端到端跑通，含 trace 与聚合 |
| E8-02 | 真实 Agent 评测报告 | 选一个你手上的 Agent，产出可复现、带区间、带失败归因的报告 |
| E8-03 | 回归集与 CI | 把 E8-01 的 50 题接进 PR 流程，含 flaky 治理 |
| E8-04 | 复现一篇论文 | 用原文配置复现，再只改一个变量，看结论是否还成立 |

**出口标准**：E8-02 的报告能被一个没参与的人照着复现出来。

## 与 RAG 地图的关系

RAG 地图回答「**怎么把证据送进上下文**」，这张地图回答「**怎么证明送进去之后真的变好了**」。两者在 M3（统计）、M5（工程化）有交集，但评测地图的重心在**判定与归因**，不在检索与生成。

如果你已经在做 RAG，建议的衔接方式：把 RAG 地图里每个「效果提升」的结论，都拿这张地图的框架重新审一遍——它是不是同 harness、同预算、同任务集下测出来的？

## 每天推送里有什么

- **2 个知识点**：一句话结论 → 为什么重要 → 核心机制 → 怎么做 → 权衡与坑 → 3 道自测题
- **5 篇前沿文章**：当天的业界新文章，原文 + 中文译文都落到本地，并挂到对应知识点上
- **一个待办**：当天可以动手做的最小实验
