## 知识点 1：结构化查询与 Text-to-SQL 边界（R0-05）

### 一句话结论

**向量检索擅长"语义模糊、答案散落、需要综合"的问题；只要问题有明确的聚合、排序、精确匹配、口径依赖，就该走结构化查询。** 判据是问句的**可计算性**，不是数据的存放位置。

### 为什么重要

- 一个精确数字类问题走向量检索，注定失败且**失败得很难看**：它不会说"我算不出"，它会从某个 chunk 里抄一个看起来对的数字给你。这是比"拒答"严重得多的故障——错误带上了精度伪装。
- 【论文结论】Text-to-SQL 的真实难度远超公开榜单。Spider 2.0（ICLR 2025 Oral）用 **632 个来自企业真实工作流**的问题，数据库常有 **1000+ 列**，SQL 常超 100 行；Ji 等人（EMNLP 2026 Findings）进一步构造 BIRD-Ent / Spider-Ent，每个查询涉及 **4000+ 列**、文档总量 **150 万 token**，SOTA 模型只拿到 **39.1% EX（BIRD-Ent）/ 60.5% EX（Spider-Ent）**。
- 【论文结论，更要紧的一条】Jin 等人（CIDR 2026 / VLDB 2026）系统复核了两个主流 Text-to-SQL 基准的**标注质量**：BIRD Mini-Dev 的错误率 **52.8%**，Spider 2.0-Snow 的错误率 **62.8%**。修正后重评 16 个开源 agent，性能相对变化 **−7% 到 +31%**，排名变动 **−9 到 +9 位**。**换句话说：你照着榜单选型，可能选的是标注噪声。**
- 这条对架构师的意义：Text-to-SQL 不是"接个 API 就行"，它是一个有独立失败模式的子系统，且**外部基准不可直接信任**——你必须建自己的、按业务口径校验的小评估集。

### 核心机制 / 数据流

先用**四类问题**做路由，这是这一节最有用的产出：

| 问题类型 | 例子 | 该走的路 | 为什么 |
|---|---|---|---|
| 事实查找（语义模糊） | "文档里怎么描述降级策略？" | 向量检索 | 答案的表述不确定，靠语义匹配 |
| 精确匹配 | "错误码 E4012 是什么意思？" | BM25 / 关键词 + 元数据 | 术语必须逐字命中，向量会"相似但不等于" |
| 聚合与计算 | "上季度华东区退款率是多少？" | **Text-to-SQL** | 需要确定性计算；任何近似都是错的 |
| 综合推理 | "对比这两份合同的责任条款差异" | 检索 + 长上下文 + 生成 | 需要跨段综合，但不需要精确运算 |

**Text-to-SQL 的六段数据流**（注意第 2、3 段才是真正的瓶颈，不是第 4 段）：

```text
① 问题解析        → 判定是否需要 SQL、涉及哪些实体/时间/口径
② Schema Linking → 从上千列里召回相关的表与列（这是"检索"问题！）
③ 知识检索        → 业务口径、指标定义、同义词、枚举值含义
④ SQL 生成        → 单条 / 多步 / 工作流
⑤ 执行与自修复    → 语法错、空结果、超时 → 重写
⑥ 结果解释        → 数字 → 业务语言（也可用模板，省一次生成）
```

**注意第 ② 段**：Schema Linking 就是 RAG 里的召回问题，只是"文档"变成了"表列"。上一期的四层失败模型可以原样搬过来：schema 列没召回 = L1；召回了但选错 = L2；选对了但口径理解错 = L4。**同一个归因框架，换一个语料形态。**

【论文结论】Ji 等人提出的 DRAG（Dual-Retrieval-Augmented-Generation）正是把这件事显式化：**先做表结构检索 + 知识检索两路，再让模型生成 SQL**，而不是把整个 schema 塞进 prompt。

### 怎么做

1. **先写一张"问题类型 → 处理路径"路由表，写上不可用条件。**
   关键是写**反向规则**：例如"含'总计/占比/同比/排名/Top N'→ 必须走 SQL"；"含具体金额、日期、编号且要求精确 → 禁止只用向量检索"。这张表比任何 prompt 都值钱，因为它是**评审时的否决依据**。
2. **给 Text-to-SQL 建三个最小资产**（不用一开始就上语义层）：
   - **口径字典**：指标的计算定义（分母是谁、含不含退款、时区）、常见坑。20–50 条就够，纯 markdown。
   - **Schema 卡片**：每张核心表一句话描述 + 主键/外键 + 易混列的区别。这就是给第 ② 段做检索语料。
   - **20–50 条带正确 SQL 的本地回归集**，按业务口径人工核对过。**不要用公开榜单的数字当验收标准**（理由见上）。
3. **把执行结果当作一等证据：空结果、超时、行数异常必须回退而不是硬答。**
   一条 SQL 执行成功不等于语义正确。加三道最小校验：结果为空 → 触发"是不是过滤条件写错了"的重写；结果行数/量级偏离历史分布一个数量级 → 标记可疑；涉及金额 → 强制带口径说明输出。

### 权衡与坑

- **【我的建议】"可执行但语义错"是 Text-to-SQL 最危险的失败模式。** 文本幻觉看起来像幻觉，数字幻觉看起来像结论。所以数字类答案必须带三样东西：口径、时间范围、数据截止时间。缺一样就不该以肯定语气输出。
- **不要用"接一个大模型 + 全 schema"起步。** 上千列时 schema 本身就把上下文撑爆，且准确率崩。正确顺序是：先做 schema 检索（缩小到 10–20 个候选列），再做生成。
- **不要把 Text-to-SQL 当"另一种 RAG"来评估。** RAG 的 faithfulness 衡量"是否忠于证据"，但 SQL 的正确答案**不在任何一段文本里**——它在数据库里。你需要的是执行结果比对（EX / 结果集等价），这是另一套指标。
- **权限必须在 SQL 层做，不能靠 prompt。** 让模型"不要查工资表"是把行级权限交给了自然语言，这是安全漏洞而不是设计。

### 架构师视角

把系统想成**三个抽屉**，而不是一条管道：

- 抽屉 A：语义检索（模糊、综合类）
- 抽屉 B：结构化查询（聚合、精确、口径类）
- 抽屉 C：混合（先用 SQL 拿到候选集/统计，再用文本解释；或先检索找到实体，再查库）

路由层的错误代价是非对称的：**把 SQL 问题错路由到向量检索，比反过来严重得多**（前者产出精确的错数，后者最多答得啰嗦）。所以路由要**偏保守**：拿不准就往结构化走，或直接问用户澄清。

### 自测（先别翻答案）

1. "去年 Q3 我们的退货率比 Q2 高了多少？"和"我们的退货政策是怎么规定的？"——两个问题分别该走哪条路？如果第二个问题被路由到 SQL，会怎么坏？
2. 你的 schema 有 800 张表。为什么"把 schema 全塞进 prompt"不只是成本问题，而是**准确率**问题？你打算用什么做 schema 检索的语料？
3. 有人拿公开榜单说"我们的 Text-to-SQL agent 排名上升了 3 位"，你作为架构师会先问哪三个问题？（提示：其中一个是标注质量问题）

## 知识点 2：RAG 的成本与延迟模型（R0-06）

### 一句话结论

**RAG 的成本不是"每次调用多少钱"，而是四个乘数：索引摊销 × 检索深度 × 上下文长度 × 生成步数。** 延迟同理，是四个**串行段**相加，而真正的病根常常不在生成模型——在"每轮都做了本可以不做的事"。

### 为什么重要

- 没有成本模型，架构讨论会退化成偏好之争（"要不要加 rerank""要不要上 agent"）。有了模型，这些问题变成算术题。
- 【论文结论】成本与延迟的浪费大多是**结构性**的，不是参数没调好。Hussain 与 Nielbo（arXiv:2605.27220）在丹麦国家百科的生产流量上做了 20,000 次 query-workflow 评估：按**合成查询**估，超过 **90%** 的查询需要 LLM 查询增强（HyDE/扩展）才能达到高覆盖率；但在**真实流量**下，只有 **27.8%** 真的需要。他们把这种落差叫作 **Coverage Illusion（覆盖率幻觉）**——合成数据与真实分布的错配，会让你为 90% 的查询付增强的钱，只为其中 28% 的真实需要。
- 更关键的发现：**这个需求在检索前无法预测**（他们试了四类 ML 范式都失败），必须"检完才知道没召回到"。所以他们改成**后置级联**（cheapest-first，只在没搜到文档时升级到 LLM 增强），结果是：质量 **+0.140**（Composite Overall，对比 Always-HyDE）、延迟 **−31.8%**、**72.2%** 的真实查询无需增强即被服务。
- 【论文结论】成本还能是被攻击的对象。Liu 等人（WWW '26，arXiv:2606.02643）提出 RA-ICA/CREEP：往外部知识库注入"对检索高度相关、但会诱导超长输出"的恶意文档，**token 消耗最多放大 13.12 倍，成功率 >90%，而答案质量并不下降**——你甚至察觉不到自己在被攻击。这是 Denial-of-Wallet，属于安全预算，不是成本优化。

### 核心机制 / 数据流

**成本公式（把它写进设计文档，逐项打点）：**

```text
单次查询成本 ≈  E(q)                       # query embedding，可忽略
             +  R(k)                       # 检索：向量库按 QPS/存储计价，不是按 token
             +  RR(k × n_dim)              # rerank：k 个候选 × 每次打分，最容易被低估
             +  G(p_in, p_out)             # 生成：prompt tokens + 输出 tokens
             +  S × (上面全部)             # agent 步数 S —— 这是乘法，不是加法

月度总成本 ≈  单次成本 × QPS × 时长
           +  索引摊销：(N_tokens × 单价) × 重建次数/年
           +  存储与常驻内存（向量库的"房租"）
```

**延迟预算表（先定 SLO，再反推每段上限）：**

| 段 | 典型占比（经验值） | 主要杠杆 |
|---|---|---|
| 查询理解/改写 | 0–25%（开了 HyDE 就很高） | 只在该做的时候做（见上文的级联） |
| Embedding + 向量检索 | 5–15% | ANN 参数、缓存、先过滤后检索 |
| Rerank | 10–30% | 候选数 k、模型大小、并行/批处理 |
| 生成 TTFT + 输出 | 40–70% | 上下文长度、输出长度、流式 |

**三个可量化的杠杆（都不是玄学）：**

1. **Prompt caching（前缀稳定性红利）。** 【事实，官方文档】Claude 的 prompt caching 默认 **5 分钟**生命周期，每次命中会免费刷新；计价上（以 Sonnet 5.5 为例）基础输入 **$2/MTok**，5 分钟写缓存 **$2.50/MTok（1.25×）**，1 小时写 **$4/MTok（2×）**，**命中 $0.10/MTok（0.05×）**。对你的含义：**把"稳定前缀"和"可变内容"物理分开**——系统提示、schema 卡片、口径字典、few-shot 放前面（可缓存），检索到的 chunk 放后面。这可能是你最容易拿到的 10–20 倍单价差。注意一个坑：生命周期从**请求开始**计时，长响应会把你的窗口吃掉。
2. **按查询路由/级联，而不是全局固定配置。** 【论文结论】Mishra（arXiv:2606.02581）的 CA-RAG 用"策略包"（检索深度 + 生成配置）做 per-query 路由，在 28 条查询上做到**比"总是重检索"少 26% 计费 token、比"总是直答"低 34% 平均延迟**，质量持平。且他明确说：**节省是非均匀的，集中在简单查询上**——所以路由要配"复杂度护栏"。另一条独立路线是 FrugalGPT（arXiv:2305.05176）：级联可在**成本降低最多 98%** 的同时匹配最强单模型。
3. **拆掉不必要的串行段。** 生成段能流式就流式（体感延迟 ≠ 总延迟）；rerank 与"另一个数据源的检索"可以并行；"解释结果"这类步骤能用模板就不要再过一次模型。

### 怎么做

1. **先打点，再优化。** 每次查询落一行结构化日志：`组件名, 耗时ms, 输入tokens, 输出tokens, 缓存命中(bool), 成本(按单价算)`。没有分组件打点，你优化的一定是最显眼的那个组件，而不是最贵的那个。**经验上被低估最多的是 rerank（k 个候选 × 每次打分）和 agent 的步数乘子。**
2. **算三个数并写进 ADR：① 单查询成本分位（p50/p95）；② p95 端到端延迟的分解；③ 索引重建的年化成本。** 第三个最容易被忽略：换 embedding 模型、改切分策略都会触发全量重索引，这部分是"向量债"的利息。
3. **按性价比排序做优化，别按时髦度。** 【我的建议】顺序通常是：① 缓存稳定前缀 → ② 砍掉无收益的查询增强（等检完再升级）→ ③ rerank 候选数从 50 收到 20 → ④ 上下文去重与压缩 → ⑤ 才考虑换更小的模型。前四步不改准确率，第五步会。

### 权衡与坑

- **语义缓存的隐性代价是"过期答案"。** 命中率高很爽，但知识更新后你会在缓存里继续发旧答案。规则：缓存 key 必须含**索引版本号**；涉及"最新/当前/今年"类查询直接绕过缓存。
- **成本优化的天花板是"你没测量的那部分"。** 一个团队把生成成本砍了 40%，却发现 rerank 占了大头——因为从来没人给它打点。
- **别把 agent 步数当线性。** 步数是乘数：每步都带全量上下文时，3 步不是 3 倍而是可能 6–10 倍。加一步规划要先算这一步的期望收益。
- **成本攻击是真实威胁，不是学术玩具。** 若你的知识库里能进外部内容（网页、用户上传、工单），就要有"单查询 token 上限"和"异常输出长度熔断"，这是成本侧的 WAF。

### 架构师视角

成本和延迟是**同一个东西的两个面**：都来自"你让模型看了多少不该看的东西"。所以最有效的优化永远是**信息卫生**（少而准的上下文），而不是更聪明的调度。

一句话可以拿去对齐老板：**"我们不优化模型，我们优化的是每次回答所携带的上下文体积和串行步数。"**

### 自测（先别翻答案）

1. 你的 p95 延迟 4.2s：改写 0.9s、检索 0.2s、rerank 0.6s、生成 2.5s。老板要求 3s 内。列出你的三个动作，并说明每个的**代价**（不是收益，是代价）。
2. 生产日志显示：72% 的查询在"不加查询增强"时也能召回 gold 文档。你现在对全部查询都开了 HyDE。改造成本和收益各是什么？你会怎么灰度？
3. 有人提议"给所有查询加一层规划 agent 以提升质量"。用成本模型说明：在什么条件下这一步是划算的？请给出一个可判定的不等式。

- **【论文，2026-01】基准本身有 52.8% / 62.8% 的标注错误。** Jin 等人（CIDR 2026；VLDB 2026 版 arXiv:2601.08778）复核 BIRD Mini-Dev 与 Spider 2.0-Snow，修正后重评 16 个开源 agent：性能相对变动 **−7%~+31%**，排名 **−9~+9 位**。**结论：Text-to-SQL 的排名不可作为选型依据，必须自建口径级回归集。**
- **【论文，2026-05/06】RAG 的成本研究从"优化技巧"转向"结构性浪费"。** 生产流量证据（arXiv:2605.27220）显示合成查询会把"需要增强的比例"从真实值 **27.8%** 高估到 **90%+**；正确解法是**后置级联**而非前置路由。另一篇（arXiv:2606.02581）显示 per-query 策略包路由可省 **26%** token / 降 **34%** 延迟。
- **【论文，2026-05】成本成为攻击面（Denial-of-Wallet）。** WWW '26 的 RA-ICA/CREEP（arXiv:2606.02643）：注入恶意文档使 token 消耗最高放大 **13.12×**，成功率 **>90%**，且答案质量不降——**成本侧熔断应列入安全设计**。
