## 知识点 1：Rerank（R3-10）

### 一句话结论

重排是**两级检索的第二级**：第一级负责"别漏"（宽召回），第二级负责"别错"（精排序）；它的价值来自**让 query 与文档互相看见**（cross-encoder / listwise LLM 都能做到，双塔做不到），而它的成本必须按 **FLOPs 而不是延迟**来算，否则你无法在不同硬件、不同批量下比较方案。

### 为什么重要

**先看"LLM reranker 到底强在哪、弱在哪"。**

【论文结论】*How Good are LLM-based Rerankers?*（arXiv:2508.16757）系统评测了 **22 种方法 / 40 个变体**（LLM-based、轻量 contextual、zero-shot），覆盖 TREC DL19 / DL20 / BEIR，外加一个**专门测试"预训练没见过的新查询"的数据集**。结论很克制：
- **LLM reranker 在"熟悉查询"上确实更强**；
- **但对新查询的泛化能力参差不齐，而轻量模型能提供相当的效率**；
- **查询的"新颖度"显著影响重排效果**，这暴露了现有方法的局限。

→ 对你的含义：**"LLM rerank 一定更好"是没根据的**；在新领域/新问法上，一个训练良好的 cross-encoder 可能更稳，而且便宜一到两个数量级。

**再看"成本怎么被压下来"——这是 2025–2026 的主线：**

| 手段 | 机制 | 公开数字 |
|---|---|---|
| **token 级压缩**（CompRank） | 文档侧状态与候选顺序/查询上下文解耦 + 分段 token 压缩 + 免解码打分 | **只保留 10.2% 文档 token**，NDCG@10 **39.2 vs 39.7**（全 token）；对 500 候选仍稳定；端到端 **4.9×–9.5×** 加速 |
| **小模型预排 + LLM 只排 top-20**（CoRanking） | 小 reranker 把相关项推到前列，LLM 只在 20 条上做 listwise | **延迟降约 70%**，效果甚至优于纯 LLM 重排 |
| **单 token 解码**（FIRST） | 用第一个生成标识符的 logits 直接得到排列 | **推理加速 50%** |
| **压缩文档表示**（RRK） | 文档压成多 token 定长嵌入再 listwise | 8B 模型比 0.6–4B 的 reranker **快 3×–18×**，效果持平或更好 |
| **动态列表截断**（Dynamic RLT） | LLM 生成"参考文档"作为相关/不相关的支点，自适应步长窗口 | 相对既有 RLT 方法 **最多加速 66%** |

【论文结论】另外，**listwise LLM reranker 作为"相关性反馈信号"比 cross-encoder 更强**（FIRST 的实验结论）——也就是说，它不只用来排序，还能反过来教第一级检索器。

**再看"效率该怎么量"。**
【论文结论】*Efficiency-Effectiveness Reranking FLOPs*（arXiv:2507.06223）指出：既有研究用延迟、前向次数、输入/输出 token 数当效率代理指标，**这些指标依赖硬件与运行时选择（是否并行、batch size），而且没有体现模型规模**，导致"效率-效果权衡"根本无法解释。他们提出两个指标：
- **RPP（ranking metrics per PetaFLOP）**：每 PetaFLOP 换来多少排序质量（NDCG/MRR）；
- **QPP（queries per PetaFLOP）**：每 PetaFLOP 能处理多少查询。
并给出一个**不需要跑实验就能估算 FLOPs 的解析器**。
→ 【我的建议】这份"用 FLOPs 而不是延迟"的纪律，比任何单个 reranker 的选择都更有长期价值——因为它让你的选型**可跨硬件比较**。

### 核心机制 / 数据流

**四种重排形态（从便宜到贵）：**

```
① 无重排：      bi-encoder top-k 直接进上下文
② Cross-encoder：把 (query, doc) 拼一起过一遍编码器 → 一个相关性分
                 优点：query/doc 互相可见，精度高
                 缺点：每个候选一次前向 → 成本 ∝ 候选数
③ Listwise LLM： 把 N 条候选放进 prompt，让模型输出排列（或分数）
                 优点：能全局比较、可利用世界知识
                 缺点：上下文长、位置偏置、延迟高
④ 级联：        ① → 小 cross-encoder 粗筛 → LLM listwise 精排 top-20
                 优点：成本最低且效果常常更好（CoRanking）
```

**Cross-encoder 与 listwise 的关键差别（选型依据）：**

| 维度 | Cross-encoder | Listwise LLM |
|---|---|---|
| 打分粒度 | 逐条独立打分（可并行） | 全局互相比对 |
| 位置偏置 | 无 | **有**（CoRanking 专门为此训练了顺序调整器） |
| 上下文长度 | 单条（短） | N 条（长，是主要成本） |
| 可解释性 | 分数可比、稳定 | 分数常不可比（不同批次间） |
| 训练成本 | 中（需要相关性标注） | 低（zero-shot 可用） |

### 怎么做（3 步）

**第 1 步：先量"重排窗口"该开多大——这是最容易被拍脑袋的参数。**

```
对 k ∈ {20, 50, 100, 200}：
  固定 reranker，测最终 top-5 的命中率与 p95 延迟
判读：
  - 命中率在某个 k 后不再上升 → 你的召回已经饱和，加大窗口只是烧钱
  - 命中率还在明显上升 → 瓶颈在第一级召回，先修召回（R3-03/R3-04）
```
【论文结论】CompRank 的实验给出一个有用的参照：**在 30 条候选上训练，评估时扩到 500 条仍保持稳定**——但那是它的架构特性；**对普通 cross-encoder，窗口越大边际收益衰减得很快**。

**第 2 步：实现"小模型预排 + 大模型精排"的级联（性价比最高）。**

```python
def rerank_cascade(query, candidates, small_ce, llm_reranker,
                   pre_k=20, keep=5):
    # ① 小 cross-encoder 打分（便宜、可并行、无位置偏置）
    scored = [(c, small_ce.score(query, c.text)) for c in candidates]
    top = [c for c, _ in sorted(scored, key=lambda x: -x[1])[:pre_k]]
    # ② LLM 只在 top_k 上做 listwise（贵，但少而精）
    ranked = llm_reranker.rank(query, top)
    return ranked[:keep]
```
【论文结论】CoRanking 的做法正是这个形状，且它额外发现：**直接喂小模型的顺序会让 LLM 因位置偏置而次优**，所以他们训练了一个顺序调整器；**你可以先用一条更便宜的规则近似：把候选按"与 query 的字面重合度"重排后再喂**，或者**把最强的那条放在首位、其余随机**，以降低偏置影响。

**第 3 步：用 FLOPs 记账，而不是延迟。**

```
粗估（cross-encoder）：
  FLOPs ≈ 2 × 参数数 × 序列长度 × 候选数
  例：0.1B 参数、512 token、100 候选 → 约 1e13 FLOPs（10 TFLOPs）
listwise LLM：
  FLOPs ≈ 2 × 参数数 × (N × 每条 token 数 + 输出 token 数)
对比两者，得到"每 PetaFLOP 的 NDCG"（RPP）——这才是可比的效率数
```
【我的建议】把这个估算写进 ADR，配合第 003 期 R0-06 的延迟预算一起看：**延迟告诉你用户体验，FLOPs 告诉你账单与可扩展性**。

### 权衡与坑

- **坑 1：默认"LLM rerank 更强"。** 【论文结论】它在熟悉查询上更强，**对新查询的泛化参差**，而轻量模型效率相当（arXiv:2508.16757）。**新领域先测 cross-encoder。**
- **坑 2：用延迟当效率指标。** 【论文结论】延迟依赖硬件与 batch 设置，且不含模型规模信息（EER-FLOPs 的批评）。**跨方案比较请用 RPP/QPP。**
- **坑 3：忽略 listwise 的位置偏置。** 候选顺序会显著影响结果；CoRanking 专门训练了顺序调整器来解决它。**如果你直接按小模型分数排序后喂给 LLM，你拿到的不是最优。**
- **坑 4：重排窗口开太大。** 成本与候选数**线性**相关；而收益通常在 50–100 就饱和。**先画"窗口–命中率"曲线。**
- **坑 5：忘了重排也会"吃掉"融合的收益。** 第 012 期已证：融合提升的召回在 rerank + 截断后大部分被中和（生产部署 Hit@10 从 0.51 降到 0.48）。**重排和融合要一起评估，不能各自报功。**
- **坑 6：把 reranker 分数当"置信度"。** Cross-encoder 分数跨 query 不可比（第 012 期的 cosine 问题同源）；**用它排序，不要用它做阈值**（拒答请走 R3-09 的独立判别器）。
- 【我的建议】顺序：**先加最小 cross-encoder（便宜、稳定）→ 再按需上 listwise（只排 top-20）→ 最后才考虑 token 压缩/单 token 解码这类工程优化**。

### 架构师视角

- **重排是"召回预算"的分配器**：你把 k 从 50 提到 200，等于把成本乘 4，换来的可能是 1–2 个百分点的命中率。**这个交换必须被显式批准，而不是默认发生。**
- **它天然适合做"分级放行"**：高分候选直接进上下文、中间分候选进"待核实"、低分候选丢弃——这正是第 015 期"三种输出"（确定/有限/拒答）的上游依据。
- **观测出口**：`rerank_window`、`rerank_gain@final_k`（重排对最终 top-k 的增益）、`rpp`（每 PetaFLOP 的 NDCG）、`rerank_p95`、`position_bias_delta`（打乱输入顺序后结果的变动幅度——这是 listwise 的体检指标）。
- **一句话**：**重排不是"再排一次"，而是"用更贵的模型做一次更细的判断"**——所以它的每一分钱都要能被 `rerank_gain` 证明。

### 自测 3 题

1. 你的重排窗口是多少？你有没有画过"窗口大小 → 最终 top-5 命中率"的曲线？如果没有，你怎么知道 100 不是过度配置？
2. 你在新领域（模型没见过的问法）上比较过 cross-encoder 和 LLM reranker 吗？如果没有，你凭什么认为贵的一定更好？
3. 打乱候选顺序喂给 listwise reranker，最终 top-5 会变多少？这个数你测过吗？

## 知识点 2：检索结果去重与多样性（R3-11）

### 一句话结论

**去重解决"完全一样"，多样性解决"看起来不一样但信息一样"**；而 2026 年的受控实验给出了一个必须纠正的直觉：**重复副本与 LLM 改写都不会显著提升答案正确率，真正有效的是"不同体裁/来源的多样文档"——它把正确率提升了 17%–47%**。

### 为什么重要

**先把"重复"和"多样"分开——它们在指标上相似，在机制上完全不同。**

【论文结论】*How retriever redundancy and diversity impact RAG effectiveness*（Ross, Koopman, van der Vegt, Zuccon，arXiv:2608.13956，2026-08-14）做了一个**控制得很干净**的实验：他们用 **FictionalQA**（合成的虚构问答，确保**生成器的参数知识无法回答问题**，答案必须来自检索文档），构造三种检索结果集：
1. **Duplicate**：同一文档的完全相同副本；
2. **Paraphrased**：同一文档的 LLM 改写版本；
3. **Diverse**：**来自不同体裁**（新闻、博客等）的文档，各自以不同形式包含相关信息。
并且**控制了"哪些文档含精确答案、哪些含改写答案"**。

结果：
- **重复副本与 LLM 改写，都不会显著提升答案正确率**；
- **提供多样文档则大幅有益：正确率提升 17%–47%**；
- 更重要的一条：**这个提升由"文档体裁多样性"本身驱动，而不是因为生成器拿到了更多"更相关的答案"**。

→ 这句话把 R3-11 的目标彻底改写了：**你要的不是"更多条"，而是"不同来源的不同说法"**。这也解释了为什么很多团队"加大 k"没效果——加进去的是同一篇新闻的三个转载。

**第二条证据：多样性提升的是"选中相关内容的召回"。**
【论文结论】*Diversity Enhances an LLM's Performance in RAG and Long-context Task*（arXiv:2502.09017）：基于 **MMR（最大边际相关）与 FPS（最远点采样）** 把多样性引入内容选择过程，结果显示**显著提高了"在送进 LLM 之前选中相关句子/块"的召回率**，在问答与长文摘要上都有收益。
→ 注意这里衡量的是**选择阶段的召回**，而不是最终答案——这是一个更敏感、更早的观测点。

**第三条：这个方向已经有专门的框架与基准。**
【论文结论】AdaGReS（arXiv:2512.25052）：面向 **token 预算受限** 的 RAG，做**集合级目标**的冗余感知上下文选择（不是逐条排序，而是优化"整个上下文集合"的价值）。
【论文结论】RARE（arXiv:2604.19047）：**冗余感知的检索评测框架**，通过把文档拆分重组来构造更贴近真实的基准——因为既有基准常常"每题只有一份证据"，**天然测不出冗余的伤害**（这和第 011 期"证据稀疏"、第 015 期"多跳基准金标窄"是同一个病根）。

### 核心机制 / 数据流

**三种"看起来重复"的东西，处理方式不同：**

| 类型 | 判定方式 | 处理位置 | 手段 |
|---|---|---|---|
| **完全副本**（byte-exact） | 内容哈希 | 装配前 | 集合去重（第 006 期，微秒级） |
| **近重复**（转载、微改） | MinHash/LSH、相似度阈值 | 入库时 | 聚类去重（第 006 期，L1） |
| **同源不同说法**（同一事件的多篇报道） | **需要"来源/体裁"元数据** | 检索后 | **多样性选择（MMR/FPS）** |

**MMR 的机制（一句话）**：每次选下一条时，最大化
```
MMR = λ · sim(q, d) − (1 − λ) · max_{d' ∈ 已选} sim(d, d')
```
- `λ = 1` → 纯相关性（就是普通 top-k）
- `λ = 0` → 纯多样性（可能选出完全不相关的东西）
- 【我的建议】`λ` 从 **0.7** 起步试，按"最终答案正确率"调，而不是按"看起来是否多样"调。

**为什么"多样性"要靠元数据而非纯向量**：
同一事件的多篇报道，向量相似度往往很高（都在讲同一件事），**纯向量去重会把它们当重复删掉**——但实验说**它们恰恰是最有价值的**。所以你需要一个额外的维度：**source / genre / 视角**（第 006 期 R1-06 的元数据字段在这里第二次派上用场）。

### 怎么做（3 步）

**第 1 步：先量"你的 top-k 到底有多同源"。**

```
对 100 条真实 query，记录 top-10 的：
  ① unique_source_ratio = 不同 source 数 / 10
  ② unique_genre_ratio  = 不同 genre 数 / 10
  ③ dup_pair_rate       = 任意两条相似度 > 0.9 的比例
判读：
  ③ 高 → 先做去重（便宜、立刻见效）
  ①② 低 → 你在"同一篇的三个转载"上浪费预算，需要多样性选择
```
【我的建议】这两个比率比"top-k 分数"更能解释"为什么答不出来"。

**第 2 步：实现"去重 → 多样性"两段式，而不是只做一段。**

```python
def select_context(query, cands, k=5, lam=0.7, max_per_source=2):
    # ① 完全去重（内容哈希）
    seen, uniq = set(), []
    for c in cands:
        h = sha1(c.text.encode()).hexdigest()
        if h in seen: continue
        seen.add(h); uniq.append(c)
    # ② 来源配额（防止同一篇/同一站占满）
    quota, out = {}, []
    for c in uniq:
        if quota.get(c.source, 0) >= max_per_source: continue
        quota[c.source] = quota.get(c.source, 0) + 1
        out.append(c)
    # ③ MMR 多样性
    picked = []
    while len(picked) < k and out:
        best, best_score = None, -1e9
        for c in out:
            rel = c.score
            red = max((cos(c.vec, p.vec) for p in picked), default=0.0)
            s = lam * rel - (1 - lam) * red
            if s > best_score: best, best_score = c, s
        picked.append(best); out.remove(best)
    return picked
```
**注意第 ② 步先于第 ③ 步**：如果先做 MMR 再限来源，MMR 可能已经选了同源的三条，配额就失效了。

**第 3 步：用"跨体裁覆盖"做验收，而不是看"多样性指标"。**

```
构造 20 条"同一事实在多种体裁中出现"的问题：
  检索 top-5 后统计：覆盖了几种体裁（新闻/博客/官方文档/论坛）？
目标：平均体裁覆盖 ≥ 2.5
更好：用「去掉某体裁后答案是否变差」做消融，证明多样性真的有用
```
【论文结论】原论文用 FictionalQA 控制"参数知识不能作弊"，并用"控制哪些文档含答案"来分离混淆因素。**你也可以用"虚构实体"构造类似的小集**，这样模型的记忆不会掩盖检索问题。

### 权衡与坑

- **坑 1：以为"多给几条"就是多样。** 【论文结论】重复副本与改写版**都不显著提升正确率**。**加大 k 而来源不变，等于白花钱。**
- **坑 2：把"同源不同说法"当重复删掉。** 它们向量相似度高，纯相似度去重会误删——而实验显示**这类多样性正是收益来源**。**去重用哈希，不要用相似度阈值一刀切。**
- **坑 3：MMR 的 λ 拍脑袋。** λ 太低会选出"多样但不相关"的东西，反而降准确率。**必须用最终答案正确率调，而不是看多样性指标。**
- **坑 4：忽略体裁/来源元数据。** 没有 `source` / `genre` 字段，你只能退回纯向量多样性，效果差一截（第 006 期 R1-06 的元数据在这里是刚需）。
- **坑 5：在"证据稀疏"的评测集上验证多样性。** 【论文结论】RARE 指出既有基准常"每题一份证据"，测不出冗余伤害。**没有"冗余场景"的评测集，你看不到收益。**
- **坑 6：把多样性当全局开关。** 对"精确事实查询"（某个具体数值），多样性反而引入噪声；**对"综述/对比/判断类查询"，多样性收益最大**。→ 应该**按查询类型路由**。
- 【我的建议】顺序：**先做完全去重（零风险）→ 再做来源配额（低风险）→ 最后做 MMR（需要调 λ）**。

### 架构师视角

- **R3-11 把 M3 的"预算"概念闭合了**：候选预算（R3-04）、过滤选择性（R3-05）、重排窗口（R3-10）、上下文条数（R3-11）——**四个参数共同决定"你花多少钱买多少条独立证据"**。而"独立证据数"才是真正的质量变量。
- **它是"数据产品"思维的又一次体现**：`source` / `genre` 这类元数据不是"为了合规才建的"，它们直接决定你能不能做出多样性选择。
- **观测出口**：`unique_source_ratio`、`unique_genre_ratio`、`dup_pair_rate`、`genre_coverage@k`、`mmr_lambda`、`diversity_gain`（开启多样性前后最终答案正确率差）。
- **一句话**：**检索的终点不是"拿到 k 条"，而是"拿到 k 条彼此独立的证据"**——前者是工程指标，后者才是质量指标。

### 自测 3 题

1. 你的 top-10 里，`unique_source_ratio` 是多少？如果只有 0.3，你实际拿到的独立证据是几条？
2. 如果同一事实有三篇不同体裁的文档（官方公告、行业博客、论坛讨论），你会把它们当重复删掉，还是当多样性保留？依据是什么？
3. 你能证明"开启多样性后答案变好了"吗？如果只能看多样性指标（比如平均相似度下降），这算证明吗？

## 今日前沿插入

> 只写有实质更新、且能核验来源的内容。

**① 重排的成本被系统性压下来了（2025–2026，多篇）**
CompRank 只保留 **10.2% 文档 token** 而 NDCG@10 从 39.7 降到 39.2（几乎无损），端到端 **4.9×–9.5×** 加速，且训练 30 条、评估 500 条仍稳定（arXiv:2606.11700）；CoRanking 用"小模型预排 top-20 + LLM 精排"把**延迟降约 70%** 且效果不降（arXiv:2503.23427）；FIRST 用首 token logits **加速 50%**（arXiv:2406.15657）；RRK 把文档压成定长嵌入，8B 模型比小 reranker **快 3×–18×**（arXiv:2604.26483）。
**为什么值得注意**：这些手段共同说明——**重排贵的是"每个候选一次前向"这个结构，而不是模型本身**。

**② 重排的效率评价口径被纠正（arXiv:2507.06223）**
EER-FLOPs 指出延迟/前向次数/token 数都是"硬件相关且不含模型规模"的代理指标，提出 **RPP（每 PetaFLOP 的排序质量）与 QPP（每 PetaFLOP 的查询数）**，并给出无需实验即可估算 FLOPs 的解析器。

**③ LLM reranker 的优势被加了限定（arXiv:2508.16757）**
22 方法 / 40 变体、TREC DL19/DL20/BEIR + 新查询集：**LLM reranker 在熟悉查询上更强，但对新查询泛化参差，轻量模型效率相当**；查询新颖度显著影响效果。

**④ 冗余与多样性的作用被受控实验分开（arXiv:2608.13956，2026-08）**
FictionalQA（参数知识无法作弊）+ 三种检索集（重复/改写/多样）+ 控制"哪些文档含答案"：**重复与改写都不显著提升正确率；多样文档提升 17%–47%**，且**收益来自体裁多样性本身**，不是"更多相关答案"。

**⑤ 多样性提升的是"选择阶段的召回"（arXiv:2502.09017）**
MMR + FPS 引入多样性后，**送进 LLM 之前选中相关句/块的召回显著上升**，问答与摘要均受益。

**趋势观察（非定论）**
2026 年 M3 的收敛方向很清楚：**质量不再由"更多/更大"驱动，而由"更独立/更对的证据"驱动**——重排压成本、多样性压冗余、评价转向 FLOPs 与集合级目标（AdaGReS）。同时"冗余感知的评测集"（RARE）开始出现，说明社区意识到**评测集本身会掩盖冗余问题**。**属趋势观察。**
