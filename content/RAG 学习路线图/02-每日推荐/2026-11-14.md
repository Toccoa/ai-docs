## 知识点 1：清洗、去重与噪声（R1-05）

### 一句话结论

净化要分开处理两种东西——**完全一样的重复（byte-exact）**和**几乎一样 / 已过时的重复（fuzzy、stale）**；前者是零调参、微秒级的集合去重，后者才是真正污染 top-k 的那一类，而它造成的伤害不是"少了一条证据"，而是**主动把模型推向过时状态**。

### 为什么重要

**先看"重复从哪来"，这决定了你该在哪里修。**

【论文结论】一项三档实测（arXiv:2605.09611，2026-05-10，预印本）指出：检索结果里的重复**不是**滑窗切分的 overlap 造成的（overlap 的 chunk 内容并不 byte-identical），而是**检索机制**造成的，来源有三类：

1. 混合检索把稀疏、稠密、rerank 三路独立排序的结果做并集，**同一条入库记录通过多条路径被选中**；
2. 语料本身就存在跨文档 byte-identical 的段落（百科镜像、转载、引用样板）；
3. 多源摄取时同一内容以**不同 ID** 重复入库。

它给了一个很有画面感的描述：**top-k 返回 15 个 chunk，经常只是 5 个唯一段落各被返回了约 3 次。**

**再看量级：你的语料越"企业"，冗余越高。**

| 档位 | 语料 | 字节级削减 |
|---|---|---|
| 干净学术 | BeIR 六源、22.2M 段落 | 语料级 0.16%；每 query 级 0.07%（n=327 BM25 查询，top-30） |
| 企业版本化 | Wikipedia 条目修订 + arXiv 版本链 + StackExchange 问答，1,526 段落 | **24.03%**（行级 9.37%） |
| 多轮对话累计历史 | 5,000 条 WildChat 对话 | **80.34%**（50+ 轮对话达 96%+） |

第二档 24.03% 与预训练语料去重的公开数字同量级（Lee et al. 2022：C4 6.7%、RealNews 18.6%、ROOTS 21.67%），这说明**"版本化的、多源的企业文档"出现两成左右的冗余是正常预期，不是异常。**

**去重的代价极低，收益是定位在 top-k 与 token 上的。**

【论文结论】同一个工作做了 5 判断器质量面板（Gemini 2.5 Flash / Claude Sonnet 4.6 / Llama 3.3 70B / GPT-5.1 / Kimi K2，共 800 个 问题×供应商 对）：去重前后答案"实质不同"的比例，Wilson 95% 上界在干净域为 **1.40%–3.25%**、高冗余域为 **1.90%–4.34%**，四家供应商都低于 5% 门槛；判断器一致性 Fleiss κ = 0.775（干净域）/ 0.7288（高冗余域）。

【论文结论】成本侧：Python 内置 `set()` 在"top-k=15、ρ=3"的典型载荷（45 个 chunk → 15 个唯一、130.2 KB）上，中位 **1.29 μs**、p95 3.50 μs、p99 5.56 μs。而它对标的学习式压缩方案（LLMLingua 系列、REFRAG）是**有损**的，且自带 10–100 ms 推理开销。

**但"过时"这一类是另一回事：它是主动伤害，不是信息缺失。**

【论文结论】一项代码补全诊断研究（arXiv:2605.14478，2026-05-14，投稿 Information and Software Technology，n=17 个人工构造的 helper 签名变更样本，来自 5 个 Python 仓库，均在"隐藏 commit 新鲜度与期望签名"的中性化提示下）：

| 检索条件 | 写出过期引用的比例 |
|---|---|
| 只喂过期片段（stale-only） | Qwen2.5-Coder-7B-Instruct **15/17**、gpt-4.1-mini **13/17**（相对 current-only 分别高 **88.2 / 76.5 个百分点**） |
| 完全不检索 | 过期引用 **0 次**，但只有 **1/17** 的补全通过 |
| 混合当前 + 过期 | **加入有效当前证据可大幅救回过期失败** |

两个模型"会被过期片段带偏"的样本 Jaccard 重叠 75.0%。结论是：**检索到的上下文的时间有效性，是 Code RAG 鲁棒性的一个独立诊断变量**——过期上下文会主动偏置模型，而不是仅仅"少给了一条有用信息"。

### 核心机制 / 数据流

**定义（照抄能直接用）：**
- 多重度 `ρ(C) = |C| / |C≡_B|` = 检索到的 chunk 数 ÷ 唯一 chunk 数
- 削减比 `reduction = 1 − 1/ρ`
- 例：ρ=3 → 削减 66.7%；ρ=1.148 → 削减 14.13%

**三层净化，按"确定性 → 模糊性"排序，不要跳级：**

| 层 | 目标 | 手段 | 成本模型 | 关键性质 |
|---|---|---|---|---|
| L0 精确去重 | byte-identical 重复 | 内容哈希（或规范化后哈希）；检索后对 chunk 集合去重 | 微秒级、每 query | 零调参、可审计、可反查（删除时要用同一把哈希） |
| L1 近重复 | 转载、微改、模板段 | MinHash-LSH（Jaccard 阈值）或语义聚类 | 一次性离线 | 有损、需阈值；**互补而非替代 L0** |
| L2 陈旧 / 版本 | 同一主张的历史版本 | **只能靠元数据**（时间、版本、supersede 关系） | 见 R1-06 | 相似度方法在这里会失效 |

【论文结论】L0 与 L1 的互补性有直接数字：在 13,197 条真实 WildChat 提示上，精确去重覆盖了 **5.81%** 的重复，而 MinHash-LSH（datasketch，64 permutations、词级 3-gram、Jaccard 阈值 0.9）覆盖 **31.32%**。两者解决问题不同——一个抓无损的严格重复，一个抓有损的模糊近重复，工程上可以**串联**：装配前跑精确去重，入库时跑 MinHash-LSH 聚类。

**噪声与模板段落为什么特别坏：**
模板段落在同一批文档里反复出现，会把 BM25 的 IDF 压平——**一个词到处都有，它的区分度就趋近于零**，真正该起作用的业务关键词权重被稀释。同时模板段落常常"看起来相关"，是"高相似度但零信息"坏证据的主要来源。

【论文结论】对长、异构、弱结构的语料（历史档案、议会辩论、旧报纸，含 OCR 噪声与文档冗余），可以先用启发式做**语料级预裁剪（pre-targeting）**再建索引/图：检索召回 **+3–5%**，token 消耗 **−32–37%**，且不降低相关文档覆盖（ACL LaTeCH-CLfL 2026，2026-03，pp. 241–250，DOI 10.18653/v1/2026.latechclfl-1.23）。注意它的动机里明确列了"document redundancy"——**冗余与噪声要一起处理，不要只修一个**。

### 怎么做（3 步）

**第 1 步：先量三个数，再决定动作。** 别一上来就上语义去重。

```
① 入库层重复率 ρ_corpus
   = 全部 chunk 数 / 规范化内容哈希去重后的 chunk 数
   （规范化至少要做：去空白、统一换行、转小写不做——大小写有语义，别动）

② 检索输出层重复率 ρ_ret
   对 500 条真实 query 记录 top-k，统计
   unique_ratio = 唯一 chunk 数 / top-k
   报告它的均值、p10、p90

③ 模板集中度
   抽 200 页，统计"跨文档重复率 > 60% 的行"占比
   > 30% 说明你的页眉页脚/法务段落正在污染 IDF
```

判读：ρ_corpus ≈ 1 且 unique_ratio ≈ 1 → 你确实不需要做去重（干净学术语料就是这样）；ρ_ret 明显 > 1 → 优先在**装配前**加 L0（最便宜）；ρ_corpus > 1.05 但你只做了 L0 → 说明 fuzzy 那一档没处理。

**第 2 步：把 L0 放在"提示装配之前"这个位置。**

```python
# 位置：检索/rerank 之后，拼 prompt 之前
# 语义：对 chunk 字符串多重集做集合构造，任何正确实现结果相同
unique_chunks = list(dict.fromkeys(chunk_texts))   # 保序
# 若要多路检索合并后去重，先按 (doc_id, page, bbox) 归一化再取内容哈希
```

要点：这一步必须**可审计**（保留被去掉内容的哈希记录），因为它是你日后回答"为什么这条没被引用"的唯一凭据。L1 放到**入库时**跑，不要每条 query 都算。

**第 3 步：陈旧问题交给元数据，不要交给相似度。**

检索时**先按时间/版本过滤，再排序**（顺序很重要，反了就会出现"新旧版本混在同一段上下文里"），并保留冲突证据显式报告，而不是静默挑一个。细节见下面 R1-06 的"三个治理动作"。

### 权衡与坑

- **坑 1：把去重当成存储优化。** 【我的建议】它的收益定位在 top-k 名额和 prefill token 上，不在磁盘。如果你只汇报"省了多少存储"，说明你还没看到真正的收益点。
- **坑 2：用相似度去处理版本问题。** 同一主张的新旧版本语义相似度极高，向量分不出来，去重会把新旧一起丢掉，或者留下错的那一个。版本必须用元数据判定。
- **坑 3：过度清洗。** 去页眉页脚很容易连真标题一起删掉（第 004 期 R1-02 已踩过），更稳的做法是**打标签 + 检索时降权**，而不是物理删除。
- **坑 4：以为做了精确去重就干净了。** 上面 5.81% vs 31.32% 的数字说明这是两个不同的问题域。
- **诚实标注：** 那篇三档实测是**单作者预印本**，作者所属公司在做配套的商用引擎，且正文明说"各供应商的成本与 TTFT 测量留待后续工作"。它的质量面板设计（多供应商 judge、κ、Wilson 上界、预注册时间戳）比一般厂商博文严谨得多，但请把它当作**可信的方向 + 需要你自己复测的数字**，不要当成定论。而它引用的"约 80% 的生产 RAG 准确率问题源于数据质量（含重复）"是转引第三方工具厂商的说法，**我建议你不要引用这个数**。
- 【我的建议】把去重当作**上线前的一次性动作**，而不是一个持续优化的项目。它一天能做完，收益立刻体现在 `unique_ratio` 和 token 账单上。

### 架构师视角

- 净化不是"一个环节"，而是**三个不同位置的开关**，成本模型完全不同：
  - **入库层**（离线、一次性）：L0 + L1 + 模板剥离 + 语料预裁剪
  - **检索层**（在线、每 query）：L0 + 多样性重排（MMR，防止近重复挤满上下文）
  - **装配层**（在线、每 query）：最终集合去重 + token 预算裁剪
- **一等观测出口：`unique_ratio`。** 【我的建议】把它打在你的检索日志里。当它长期低于 0.7，说明你的链路正在白白浪费 top-k 名额——这是最便宜的体检指标之一，比任何离线评测都先发现问题。
- **与 R1-09 的接口**：删除/下架文档时，要用**同一把内容哈希**反查所有副本，否则删不干净；这也是 L0 用哈希而不是用向量做去重的一个隐性好处。

### 自测 3 题

1. 你的 top-k（比如 10）里平均有几个是唯一 chunk？如果你现在没有这个数，你打算怎么在半小时内量出来？
2. 用户问"现在生效的报销标准是什么"，而你的库里同时躺着 2024 与 2026 两版制度。你的链路靠什么决定用哪一版？靠相似度可以吗，为什么？
3. 同事说"我们的语料是官方文档，不会有重复，不用做去重"。这句话在什么前提下成立，在什么情况下会翻车？（提示：想想"多源摄取 + 混合检索 + 版本修订"这三件事各自贡献了什么。）

## 知识点 2：元数据设计（R1-06）

### 一句话结论

元数据是**检索之外的第二条通路**：它同时承担三个不可替代的角色——**过滤器**（缩小候选）、**治理开关**（谁能看、哪一版有效、能不能引用）、**归因坐标**（评测与回溯）；漏建它的代价不是"少了个字段"，而是权限、时效、版本这三类问题**在架构上无处可解**。

### 为什么重要

**证据一：元数据对准确率是可直接测量的增益。**

【论文结论】AMAQA（arXiv:2505.13557，2025-05）是首个把元数据纳入单跳 QA 的基准：26 个公开 Telegram 群约 **110 万条**英文消息 + **2 万条**酒店评论，配 **2,600 组**高质量问答，元数据含时间戳与群/频道名。带元数据后准确率：**GPT-4o 从 0.5 → 0.86**，开源 LLM 从 **0.27 → 0.76**。
（标注：这是 2025 年上半年的基准，不算本期前沿；但它是"元数据值多少分"最直接的一份公开证据。语料偏社媒/评论类，别直接外推到你的企业文档。）

**证据二：合规场景里，"相关"不等于"可用"。**

【论文结论】TrustRAG（EMNLP 2026 Main，2026-10，pp. 35002–35020）把这类失败正式化为三种**检索后治理失败**：
1. **未授权泄漏**（证据对当前用户不可访问）
2. **过期引用**（证据已被显式取代）
3. **无依据回答**（与其他有效证据存在未解决的冲突）

它的做法：在**检索器与生成器之间**插一层"元数据治理路由"——在生成前剔除不可采信证据；**当没有可采信证据时返回确定性拒答**；把未解决的冲突**保留下来交给"冲突报告式生成"**。在 Qwen-Max、DeepSeek-V3、GLM-4-32B-0414 上，三种失败相对无引导 RAG 及一批基线（prompting / filtering / routing / verification / recency）稳定下降；候选池扩大到 50 文档时优势依然存在。
**但请特别注意它的诚实之处**：该层的前提是"**正确且完整**的治理元数据"，论文专门做了**元数据噪声测试与人工审计**来刻画它对上游元数据质量与判断器选择的依赖。**换句话说：元数据错，治理层会自信地错。**

**证据三：没有元数据，你连归因都做不了。**

第 002 期的四层失败模型里，L3「用不好」与 L4「答不实」的分离要靠"哪个证据被用了、它是否有效"来判断；第 004 期你已经被问过"你的引用能精确到哪一层"。这两件事的共同前提都是元数据。

### 核心机制 / 数据流

**五类必建字段（按"什么时候用得上"排列，不是按"看起来全不全"）：**

| 类别 | 字段示例 | 用在哪 |
|---|---|---|
| ① 出处与定位 | `doc_id`、`source_uri`、`page`、`bbox`、`parent_id` | 引用定位、回溯、去重反查 |
| ② 时间与版本 | `created_at`、`updated_at`、`valid_from` / `valid_to`、`version`、`supersedes`、`is_current` | 时效、版本冲突、陈旧检测 |
| ③ 权限与治理 | `tenant`、`owner`、`acl`（允许的用户组/角色）、`sensitivity`（分级）、`retention` | 谁能看、能留多久、可否外发 |
| ④ 结构与类型 | `type`（正文/表格/图表/公式）、`level`/`hierarchy`、`lang` | 切分与父子回填、多语言路由、模态路由 |
| ⑤ 业务过滤维度 | 产品、地区、年度、口径等 | 精确匹配走过滤器，不走向量（回到 R0-05 的路由思想） |

**数据流（四跳，每跳都有校验点）：**

```
摄取时补齐 → 索引时分列 → 检索时先过滤后排序 → 生成时作引用/拒答依据 → 评测时作分组维度
   ↑ 推不出的标 unknown，不要编造        ↑ 选择性观察点        ↑ 冲突显式报告
```

**关于"过滤与向量的先后"——这是最容易含糊过去的地方：**
- **预过滤**（先按条件缩候选再算相似度）：选择性高时更快更准；选择性低时会退化成近全表扫描，或召回不足。
- **后过滤**（先向量再筛）：过滤条件苛刻时可能把结果**筛空**；更危险的是——**权限过滤放在这一步，日志/缓存/上下文里已经出现过了，泄漏已经发生。**
- 【我的建议】权限与时效走**预过滤**；业务维度（地区、口径）走预过滤并给"选择性"打点；只在过滤条件极度宽松时允许后过滤兜底。

### 怎么做（3 步）

**第 1 步：画一张"元数据用途表"，答不出用途的字段就是没用的字段。**

对每个候选字段问三句：**谁用它？做什么决定（过滤/排序/展示/拒答/评测分组）？缺失时怎么办？** 三句都答不上来 → 不建。理由：元数据同时是**维护负担**和**错误来源**，TrustRAG 的噪声测试已经把"上游元数据质量"列为系统性依赖项。

**第 2 步：定义"元数据契约"，用枚举而不是自由文本。**

```python
# 契约示例：字段、值域、缺失策略三者必须同时定义
META_CONTRACT = {
  "doc_id":     {"type": "str",  "required": True},
  "version":    {"type": "str",  "required": True},          # 例 "2026.3"
  "is_current": {"type": "bool", "required": True},          # 由源系统同步，禁止 LLM 推断
  "valid_from": {"type": "date", "required": True},
  "acl":        {"type": "list[str]", "required": True,      # 枚举化的组/角色 ID
                 "source": "upstream_acl_sync"},               # ⚠ 绝不能从正文猜
  "doc_type":   {"type": "enum", "values": ["policy","manual","report","faq"]},
  "lang":       {"type": "enum", "values": ["zh","en","mixed"]},
}
# 缺失策略：required 字段缺失 → 文档进隔离区，绝不带 null 混入索引
# 校验点：摄取产出、索引写入、检索过滤，三处都要校验存在性与值域
```

**第 3 步：把三个治理动作串成一条链，并加一条反事实验收。**

1. **检索前置过滤**：权限（谁能看）+ 时效（哪一版有效）→ 在候选进入上下文**之前**完成
2. **证据不足时确定性拒答**：没有可采信证据就明确说"没有"，而不是拿最相似的那条硬答
3. **冲突时显式报告**：把矛盾证据摊开讲，而不是悄悄选一个
4. **验收**：构造"用户无权访问某文档"的**反事实测试集**，要求**引用该文档的比例 = 0%**（不是"下降"，是 0）；再造一组"新旧两版同时存在"的问题，要求**版本混用率 = 0%**。

### 权衡与坑

- **坑 1：把权限当检索后过滤。** 先检索再删——日志、缓存、已经把内容拼进去的上下文，都泄漏过了。【我的建议】任何检索缓存、答案缓存的 key 都必须包含 **tenant/acl 指纹**。
- **坑 2：靠相似度解决版本问题。** 见 R1-05 坑 2。必须时间过滤 + 显式 `supersedes` 关系。
- **坑 3：元数据写成自由文本。** "2024"、"2024 年"、"FY24" 三种写法会让过滤条件写不准，也会让统计口径失真 → 用枚举 + 入库校验。
- **坑 4：把元数据增强当万能药。** 第 004 期讲过"元数据增强 + 层级感知切分对下游准确率的贡献大于换转换框架"，但那是**特定语料下的下游 QA 结果**；元数据的收益高度依赖它**是否真的被用于过滤或定位**，而不是它是否存在。建了一堆没被任何代码读过的字段 = 零收益。
- 【我的建议】第一版只建**能立刻用于过滤或引用定位**的字段（出处、页码/bbox、时间、版本、type、acl），其余等出现明确用途再加。

### 架构师视角

- **把元数据当接口契约，而不是文档属性。** 摄取 → 索引 → 检索 → 生成，每一跳都校验字段存在性与值域；缺必填字段的文档进隔离区。这样做的收益是：字段质量问题会在**入库时**暴露，而不是在用户投诉时暴露。
- **权限维度必须与缓存/日志一致。** OWASP 的 RAG 安全清单把"响应缓存导致跨用户数据泄漏与权限失效"单独列为一类风险 → https://cheatsheetseries.owasp.org/cheatsheets/RAG_Security_Cheat_Sheet.html
- **观测出口（建议直接加到你的探针表里）：**
  - `filtered_out_ratio`：被治理层剔除的候选比例（突然升高 = 上游元数据出问题了）
  - `empty_after_filter_rate`：过滤后为空的 query 比例（升高 = 过滤条件过紧，或索引入库不全）
  - `inadmissible_recall`：不可采信证据被引用的次数，**目标 0**
  - `version_mix_rate`：同一次回答里混入同一主张多个版本的比例，**目标 0**
- **一句话总结这两个点的分工**：R1-05 是"把垃圾从库里清掉"，R1-06 是"给剩下的每条内容发一张身份证"。

### 自测 3 题

1. 列出你系统里**现在实际存在**的元数据字段，逐个回答"它被谁用来做了什么决定"。有几个字段答不上来？那些字段正在消耗你的维护成本。
2. 你的检索缓存 key 里包含权限维度吗？如果不包含，请描述一个具体的跨用户泄漏场景（谁问什么，拿到谁的什么）。
3. 用户问"最新的差旅标准是多少"，库里新旧两版都有、入库时间都是"最近"。请从**元数据、检索、生成**三层各给出一个动作，保证答案来自新版。

## 今日前沿插入

**① 元数据从"过滤器"升级为"治理层"（EMNLP 2026 Main，2026-10）**
TrustRAG 把合规问答里的失败正式化为"未授权泄漏 / 过期引用 / 无依据回答"三类，并在检索器与生成器之间加一层元数据治理路由：生成前剔除不可采信证据、无证据时确定性拒答、冲突显式报告。它明确承认依赖"正确且完整的元数据"，并做了噪声测试。→ https://aclanthology.org/2026.emnlp-main.1533/
**为什么值得你注意**：这一层不是"更好的 prompt"，而是一个**新的组件位置**。如果你在做企业问答，这个位置迟早要建。

**② 去重的冗余量第一次被按"档位"实测（预印本，2026-05-10）**
同一份工作给出三档：干净学术 0.16% / 企业版本化 24.03% / 多轮对话 80.34%；去重后答案实质差异率的上界都 < 5%（多供应商 judge 面板）；精确去重在中位 1.29 μs 级别。→ https://arxiv.org/abs/2605.09611
**注意**：单作者预印本，作者公司在做配套商用引擎，成本/TTFT 测量尚未发布。方向可信，数字请自测。

**③ "过期上下文"被证明是主动偏置源，不只是信息缺失（论文，2026-05-14）**
代码补全诊断研究：只喂过期片段会诱导模型写出过期 API（15/17 与 13/17，相对只喂当前版本高 88.2 / 76.5 个百分点），而完全不检索虽然 0 次过期引用、却只有 1/17 通过。→ https://arxiv.org/abs/2605.14478
**为什么值得你注意**：这为"时效元数据"提供了危害机制上的证据——陈旧的伤害是**双向**的，删掉它不会自动变好，必须补上当前证据。

**④ 语料级预裁剪：召回涨、成本降（ACL LaTeCH-CLfL 2026，2026-03）**
对含 OCR 噪声与文档冗余的历史语料，先用启发式把语料缩到目标子集再建索引：召回 +3–5%、token −32–37%，覆盖不降。→ https://aclanthology.org/2026.latechclfl-1.23/
（此文落在 6 个月窗口边缘外一点，但它把"噪声与冗余一起处理"这件事讲得最直接，故收录并如实标注日期。）

**趋势观察（非定论，仅供你判断风向）**
工程侧的声音正在把"数据准备/净化"重新摆到第一位：多篇 2026 年的厂商技术博客把重复与陈旧列为生产 RAG 的首要故障源，并出现"在装配前做确定性去重"这类轻量组件的产品化倾向。这类内容属于**趋势观察**，不建议作为选型依据——真要看证据，回到上面①②③三篇。
