## 知识点 1：文档层级与父子关系（R1-07）

### 一句话结论

文档层级不是"排版美感"，而是**两条独立的检索通路**：**小块负责"被找到"**（高精度定位到某一句、某一段），**父块/章节负责"被读懂"**（提供定义域、前提条件、指代对象）；只建一种块，等于在精度与完整性之间二选一——而这两件事本来可以同时拿到。

### 为什么重要

**先看"只切小块"会丢什么。** 一段孤立的 `"逾期 30 天以上按 1.5 倍计息"`，检索很容易命中，但它脱离了三个上下文：这是哪个产品（个人贷/企业贷？）、哪个版本的合同、跟前面"宽限期 10 天"是什么关系。模型看到这句话，会自信地给出一个**适用范围错误的答案**。这类错误在第 002 期的四层模型里会同时污染 L3（用不好）和 L4（答不实），但根因在数据层。

**再看"只切大块"会丢什么。** 一个大章节 8,000 字塞进一个 chunk，向量被平均成一个主题包，**里面每一句话的检索信号都被稀释**——你在 L2 排不准，而且任何一句具体规则的 recall 都会掉。

**【我的建议】把它们当成两个通道而不是一个折中：**
- 检索通道用**小块**（句/段级），保证 `recall@n` 不被平均掉；
- 生成通道用**父块或兄弟窗口**（父块 = 它的 chapter/section 祖先；窗口 = 邻居 ±k 句），保证喂进去的东西有定义域。

【论文结论】层级信息确实会被检索与生成直接利用。cAST（Findings of EMNLP 2025，arXiv:2506.15655）在代码场景里按 AST 做**结构感知切分**：递归地把过大的语法节点拆成小块，**再把兄弟节点合并**使块自包含，在 code generation 与 retrieval 指标上均优于固定长度切分。关键不是"用 AST"这个技巧，而是它印证的两条原则：**(1) 切分边界应对齐语义边界；(2) 块要自包含，必要时向上合并而不是硬切。**

【论文结论】反过来，结构化地组织上下文也有收益。HTSIR（AAAI 2026，Microsoft Research）面向长上下文摘要，先把语料**按章节分组**、再建**层级摘要**来降低无关内容的干扰，作者报告在长上下文摘要/QA 任务上优于复杂的 Graph RAG 方案。*（说明：具体点数我在第三方解读里看到约 6 点的提升，但源页面我只核到方法与任务设定，**数字请以论文原文为准**。）*

**这就是为什么 R1-07 是 R2-03（父子块与句子窗口）的前置条件**：没有可信的层级元数据，父子块方案根本无从实现——你不知道谁是父。

### 核心机制 / 数据流

**先要有树，才谈得上父子。** R1-01 里定义的块结构要有 `parent_id` 与 `level`：

```
document
└─ section (level=1)          ← 章
   └─ subsection (level=2)    ← 节
      └─ block (level=3)      ← 段落 / 列表项 / 表格
         └─ sentence (level=4)← 句（可选，按需生成）
```

**四跳数据流：**

| 跳 | 动作 | 要点 |
|---|---|---|
| ① 建树 | 解析阶段用标题层级（字体/编号/`#` 标记）给每个块挂 `parent_id` | 层级来自**解析产物**，不要事后用正则从纯文本猜 |
| ② 双粒度索引 | 句子/段落块入向量库；父块（节级）只存不索引或单独索引 | 小块可加 `parent_id` 字段供回填 |
| ③ 检索 | 命中小块 → 沿 `parent_id` 取父块或取 ±k 句邻居 | k 一般 1–2 句；父块超长时用"首段 + 命中段落 + 尾段"截断 |
| ④ 组装 | 去重后按文档顺序排列，保留 `section_path` 作为上下文头 | 顺序信息本身就是证据（R1-02 的结论） |

**回答"要不要把标题塞进每个块"这个问题：要，但要塞"路径"而不是"标题"。**
`section_path = "第 3 章 / 3.2 利率与计息 / 3.2.4 逾期处理"` 这类字段同时干三件事：给嵌入模型补语境、给模型提供指代锚点、给引用提供人类可读位置。

### 怎么做（3 步）

**第 1 步：先量"层级可用率"，再决定建多深。**

```
抽 100 个文档，统计：
① 有可识别标题层级的文档占比      （< 60% → 先修解析，不要硬做父子块）
② 每块的 section_path 平均长度     （> 120 字 → 塞进嵌入会挤压正文，改用"只拼末两级"）
③ 层级深度分布                     （> 5 层的文档占比高 → 只保留 level ≤ 3）
```

**第 2 步：实现"小块检索 + 父块回填"。**

```python
# 索引：句子级块，带 parent_id 与 section_path
chunks = chunk_by_structure(blocks, target_tokens=180)   # 对齐段落/列表项边界
for c in chunks:
    c.embed_text = f"{c.section_path}\n{c.text}"          # 语境前缀只用于嵌入，不用于展示
    c.payload = {"parent_id": c.parent_id, "page": c.page, "bbox": c.bbox}

# 检索：先小块，再回填父块
hits = vector_search(q, k=30)
seen, assembled = set(), []
for h in hits:
    parent = get_parent(h.parent_id)                     # 节级块
    text = parent.text if len(parent.text) <= MAX_CTX else \
           parent.head + "\n…\n" + h.text + "\n…\n" + parent.tail
    key = hashlib.sha1(text.encode()).hexdigest()        # R1-05 的装配前去重在这里复用
    if key in seen: continue
    seen.add(key); assembled.append(text)
    if token_budget_exceeded(assembled): break
```

**第 3 步：用"指代题"验收，而不是用"事实题"。**
构造 20 道必须依赖层级才能答对的题，例如"这笔逾期利息按哪个产品的哪一版合同计算"、"这条豁免适用于第几类客户"。如果这些题的准确率显著低于事实题，说明你的父块没真正被用上（或者父块里根本没有定义域）。

### 权衡与坑

- **坑 1：父子块 = 上下文膨胀。** 父块一放大，prefill token 就涨。**必须给父块设 token 上限**（我建议 ≤ 1,500 token），超长时用"首段 + 命中段 + 尾段"三段式，而不是整节塞进去。
- **坑 2：父子块 = 重复计票。** 同一节里有 3 个子块命中 top-10，回填后你会把同一段父块喂 3 次——这是 R1-05 讲的 `ρ` 问题的另一种形态，**回填后一定要去重**。
- **坑 3：层级来自推断，不是来自解析。** 用正则从纯文本猜标题（"第 X 章"开头、全角数字编号），在多栏、扫描、非标准编号的文档上会大面积出错。宁可"没有层级"，也不要"错的层级"——错父子关系比无父子关系更难发现。
- **坑 4：把所有章节标题都拼进 `embed_text`。** 长路径会显著改变句子的嵌入分布，使"同样的句子挂了不同标题就检索不到"。**建议只拼末两级**，或者用独立的"语境字段"而不是混进正文。
- 【我的建议】父子块在多数企业问答里是**性价比最高的一次改动**（比换 embedding、加 rerank 都便宜），前提是层级可信。

### 架构师视角

- **层级是数据契约的一部分，不是检索技巧。** 把 `parent_id` / `section_path` / `level` 写进 R1-01 的 Block schema，让解析、切分、索引、检索四层都能读到；不要等到做 R2-03 时再从文本反推。
- **关注"回填率"这个观测出口**：`parent_fill_rate` = 成功回填父块的命中数 / 总命中数。它低于 0.9 说明层级断裂（父块找不到），是数据质量问题而不是检索问题——**这类问题在检索指标上完全看不出来**。
- **与引用体系耦合**：父块回填天然解决了"引用粒度"问题——你引用的是节而不是孤立一句时，用户更容易验证你答得对不对。

### 自测 3 题

1. 你的库里，一条命中记录能不能沿 `parent_id` 找到它所属的节？如果做不到，是解析没产出层级，还是切分丢了？
2. 用户问"这条规则对哪些客户生效"，你的上下文里有没有"哪些客户"这个定义域？如果没有，你靠什么保证模型不是瞎猜的？
3. 父子块回填后，你的 top-10 里实际喂给模型的独立段落数是几个？如果少于 5，你损失的是什么？

## 知识点 2：多语言与跨语言检索（R1-08）

### 一句话结论

跨语言场景里，**"在哪一步翻译"比"用哪个多语言 embedding 模型"更决定成败**——翻问题（tRAG）、翻文档（CrossRAG）、还是让多语言模型直接跨语言检索（MultiRAG），三者失败的**位置完全不同**，而"检索命中了但证据语言不一致"往往表现为**回答语言错**或**跨语言推理失败**，看起来像生成问题，其实是检索与组装的账。

### 为什么重要

**证据一：两种主流做法各有明确缺陷，且缺陷位置不同。**

【论文结论】EACL 2026 Findings（Ranaldi, Haddow, Birch；pp. 697–716）系统比较了三类多语言 RAG 策略：
- **tRAG**：把问题翻成英文再检索。结论是"useful, but suffers from **limited coverage**"——因为知识库里英文覆盖不全，或译文丢掉了原语言里的专有信息。
- **MultiRAG**：直接在多语言语料上检索（多语言 embedding）。结论是"improves efficiency … but introduces **inconsistencies due to cross-lingual variations in the retrieved content**"——检索面更广，但同一事实在不同语言里的表述差异会被一起取回。
- 作者提出 **CrossRAG**：**把检索到的文档统一翻成一种共同语言再送生成**，报告在知识密集型任务上显著提升，**对高资源和低资源语言都有效**。

**证据二：跨语言 RAG 的失败点，被证明主要在"检索与推理"，不在"生成外语"。**

【论文结论】XRAG（arXiv:2505.10089，2025-05；Findings of EMNLP 2025）用近期新闻构建基准、要求外部知识才能回答，并对每篇检索文档做相关性标注，覆盖单语检索与多语检索两种真实场景。在 5 个 LLM 上发现两个此前未被报告的挑战：
1. **单语检索设置下，所有被测模型都难以保持回答语言正确**——用户用中文问、证据是英文，模型容易用英文答，或答非所问地混语。
2. **多语检索设置下，主要难点在于"对跨语言检索到的信息做推理"，而不是生成非目标语言文本**。

**证据三：在企业语料上，跨语言掉点的根因被定位到 retriever 的排序。**

【论文结论】ArabicNLP 2025 *The Cross-Lingual Cost*（DOI 10.18653/v1/2025.arabicnlp-main.6）指出：以往研究多用维基百科类开放域基准，语言不均衡、与预训练数据重叠、内容被记忆，**把真实的检索困难掩盖了**。他们改用企业真实语料构建阿英双语基准（query 与支撑文档的语言独立随机组合），发现：**query 与证据语言不一致时性能大幅下降，而这种失败主要来自 retriever 难以跨语言排序**。两个简单修法就有效：**强制两种语言各取等量结果（balanced retrieval）**，或**翻译 query**。

### 核心机制 / 数据流

**三种策略 + 失败位置对照表：**

| 策略 | 翻译什么 | 什么时候对 | 典型失败 | 成本 |
|---|---|---|---|---|
| 多语言 embedding 直检（MultiRAG） | 不翻 | 语料多语且模型真的多语言 | 跨语言表述差异 → 内容不一致；低资源语言掉点 | 最低 |
| 翻译问题（tRAG） | query | 英文证据充分、问题短 | **覆盖不足**（库里没有英文对应）；译文丢细节 | 低（一次翻译） |
| 翻译证据（CrossRAG） | 检索结果 | 需要跨语言推理、多语证据混排 | 多一次生成前的翻译开销；译文错误直接进上下文 | 中（每文档一次） |
| 均衡取回（balanced retrieval） | 不翻 | 双语语料、可判断文档语言 | 需要可靠的语言识别与每语言配额 | 低 |

**四跳数据流（推荐的双语企业库形态）：**

```
① 入库：探测文档语言，写入 lang 元数据（R1-06 的字段之一）
② 检索：查询语言 L_q，检索时按 lang 分组
   - 组 A：与 L_q 相同语言
   - 组 B：其他语言
   按配额合并（balanced retrieval），而不是让相似度自由竞争
③ 组装：把组 B 的片段翻译成 L_q（或统一成英文），保留原文 id 以便引用回溯
④ 生成：要求用 L_q 回答并引用原文位置；引用指向"原文"，不是译文
```

**关于"要不要给每个块再存一份译文"：**
- 【我的建议】不要。译文会带来双重维护（原文更新译文就作废）与双份索引成本。
- 更稳的做法：**检索永远在原文上进行**（小块或大块皆可），**在装配阶段按需翻译命中的少量片段**。命中往往是 5–15 段，翻译成本可控，而且译文不会污染原始索引。

### 怎么做（3 步）

**第 1 步：先量"跨语言缺口"，不要先换模型。**

```
取 100 条真实 query（user_lang 分布按线上实际）
把证据按 lang 分成同语言 / 跨语言两桶，分别算：
① cross_lingual_share = 跨语言证据占总命中的比例
   （很低 → 你的跨语言问题本来就不严重，先别投入）
② cross_lingual_recall@5 与同语言 recall@5 的差
   （差 > 15 个百分点 → 值得做；差 < 5 个百分点 → 不值得）
③ answer_lang_mismatch_rate = 回答语言与提问语言不一致的比例
   （这个指标不需要金标，日志里就能算，非常便宜）
```

**第 2 步：上"均衡取回 + 装配时翻译"。**

```python
# 双语语料的最小可行方案：配额合并而非自由竞争
def retrieve_bilingual(query, lang_q, k=10, quota_ratio=0.5):
    same = search(query, filter={"lang": lang_q}, k=k)
    cross = search(query, filter={"lang": {"$ne": lang_q}}, k=k)   # 多语言 embedding 或查询改写
    n_cross = min(int(k * quota_ratio), len(cross))
    merged = same[: k - n_cross] + cross[:n_cross]
    # 装配阶段翻译（只翻少量片段），并保留原文 id
    for c in merged:
        if c.lang != lang_q:
            c.text_for_prompt = translate(c.text, to=lang_q)
            c.cite_anchor = c.doc_id, c.page          # 引用永远指向原文
    return merged
```

**第 3 步：把"回答语言"当成硬约束来验收。**
在系统提示里显式要求用 `{lang_q}` 作答，并在评测里加一条**不需要金标的自动检查**：`answer_lang_mismatch_rate`。XRAG 的发现（单语检索下所有模型都难保语言正确）说明这不是理论风险，是默认行为。在日志里落 `user_lang`、`evidence_lang_set`、`answer_lang` 三个字段，这条曲线就能自动画出来。

### 权衡与坑

- **坑 1：以为"换了多语言 embedding 模型就解决了"。** 多语言 embedding 解决的是"能跨语言匹配"，不解决"跨语言表述不一致"与"回答语言错"——后两者一个在组装层，一个在生成约束层。
- **坑 2：tRAG 的覆盖盲区。** 把中文问题译成英文再检索，前提是**库里有英文证据**。纯中文企业库上做 tRAG，等于自断召回。**先量 `lang` 分布再选策略。**
- **坑 3：翻译污染索引。** 把译文也入库、也建索引，短期检索好像更好，长期会因为"原文更新、译文没更新"制造出一整类陈旧证据（R1-05 的 L2 问题）。**译文不进索引。**
- **坑 4：引用指向译文。** 用户点开引用想核对，看到的是机器翻译——**引用必须锚定原文位置**（`doc_id + page + bbox`），译文只出现在 prompt 里。
- **坑 5：低资源语言的假性达标。** 用英文 + 中文验证没问题，就认为"多语言 OK"。低资源语言的掉点通常更陡，且会被"命中了几条"掩盖。
- 【我的建议】双语/多语支持的第一版只做三件事：`lang` 元数据、均衡取回、装配时翻译 + 语言约束。这三件都是低成本、可测的；换模型留到最后。

### 架构师视角

- **把"语言"当成一个一等的检索维度**，与 R1-06 的元数据契约同构：`lang` 必须是枚举、必须校验、必须能进过滤条件。它同时是路由键（走哪种策略）、配额键（balanced retrieval）和观测键（分语言算 recall）。
- **观测出口（建议加进探针表）：**
  - `cross_lingual_share`：跨语言证据占比（决定要不要投入）
  - `recall_gap_lang`：同语言 vs 跨语言的 recall@5 差值（决定投入多少）
  - `answer_lang_mismatch_rate`：回答语言错配率（不需要金标，最便宜）
  - `translation_fail_rate`：装配翻译失败/超长截断比例（装配层的隐性杀手）
- **一句话总结 R1-07 与 R1-08 的分工**：R1-07 让**证据在纵向上完整**（父块补齐定义域），R1-08 让**证据在横向上可比**（语言对齐后再让模型推理）。

## 今日前沿插入

**① 多语言 RAG 的第一份"策略级"对比（Findings of EACL 2026，2026-03）**
tRAG 覆盖不足 / MultiRAG 内容不一致 / CrossRAG（证据统一译成共同语言再生成）在知识密集型任务上显著更好，且高低资源语言都受益。→ https://aclanthology.org/2026.findings-eacl.35/
**为什么值得你注意**：这是"该在哪一步翻译"第一次被系统比较，而不是继续比 embedding 榜单。

**② 跨语言失败点的定位：检索排序，而非生成（ArabicNLP 2025）**
企业语料基准显示，query 与证据语言不一致时大幅掉点，根因是 retriever 跨语言排序；**均衡取回**或**翻译 query** 两个简单修法就能救回大量性能。→ https://doi.org/10.18653/v1/2025.arabicnlp-main.6
**为什么值得你注意**：这条修正了很多团队的默认假设（"生成阶段让它自己处理语言"）。

**③ 层级组织上下文仍然打赢复杂图谱（AAAI 2026）**
HTSIR 用"按章节分组 + 层级摘要"降低长上下文干扰，作者报告优于复杂 Graph RAG 方案。→ https://www.microsoft.com/en-us/research/publication/improving-long-context-summarization-with-multi-granularity-retrieval-optimization/
**为什么值得你注意**：对上期"R1-06 元数据是治理开关"是个补充——**结构信息（章节）本身就是最好用的元数据**，不必先建知识图谱。

**趋势观察（非定论）**
2026 年的多语言 RAG 工程讨论里，"均衡取回 + 装配时翻译"正在变成默认套路，同时开源多语言检索模型（如多语言 dense/late-interaction 系列）在持续缩小语种差距。**这些属于趋势观察**，选型请回到上面①②的具体设定去验证，不要拿榜单当结论。
