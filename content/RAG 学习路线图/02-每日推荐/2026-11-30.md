## 知识点 1：上下文压缩（R5-05）

### 一句话结论

**压缩不是“摘要一下”，而是“在 token 预算下保留最多可用信息”。** 2026 年的软压缩（DEX-Comp）在 **16× 压缩比**下平均准确率超过未调优的全上下文 RAG，TTFT 快 **4.4–23.7×**；但它的代价是**可解释性与引用对齐**——你必须为引用保留原始 span 的旁路。

### 为什么重要

- RAG 的上下文经常是 10–30 个 chunk；token 成本和延迟都集中在这里。
- 简单截断会丢信息；抽象摘要会引入失真；软压缩用连续表示，能在“信息密度”上更进一步。
- 但压缩比不是越大越好：**压得太狠，答案正确率、引用忠实度、位置效应都会变**。

### 核心机制：三种压缩

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 抽取式 | 选句子/span | 可引用、可解释 | 压缩比有限 |
| 摘要式 | LLM 重写 | 压缩比高 | 会失真、不可逐字引用 |
| 软压缩 | 编码成连续表示 | 压缩比最高、可预计算 | 不可解释、难引用 |

**DEX-Comp 的两阶段：**

```
Stage I  Pure Distillation：只从“教师答对”的样本学习 → 避免模仿教师错误
Stage II Hard Exploration：对“教师答错”的样本用结果型 RL → 直接优化答案正确率
```

### 怎么做

1. **先算账**：`生成 token 成本占比` 低于 50% 时，压缩的收益有限；先优化检索/重排。
2. **双通道**：`compressed_vector` 用于召回/生成，`raw_chunk` 用于引用/审计；用 `chunk_id` 对齐。
3. **压后三测**：答案正确率、`citation_unsupported_rate`、`answer_accuracy_by_position`。
4. **渐进压缩**：4× → 8× → 16×，每次用同一金标集比较；不要一次到极限。
5. **按内容类型分层**：表格/代码/数字不要软压缩；它们需要精确原文。

### 权衡与坑

- **坑 1：只看 token 成本，不看引用成本。** 压缩后无法定位原文，审计会崩。
- **坑 2：用摘要替代原文做引用。** 用户看到的“引用”是摘要，不是证据。
- **坑 3：忽略压缩对位置效应的影响。** 压缩会改变证据在上下文中的相对位置。
- **坑 4：拿 16× 当目标。** 16× 是论文设定；你的语料可能 4× 就掉点。
- 【我的建议】先做“抽取式压缩 + 双通道”，再考虑软压缩；软压缩适合高 QPS、低审计要求的场景。

### 架构师视角

- 压缩是**成本与可审计性的交换**；在强监管场景，可审计性优先。
- 观测出口：`compression_ratio`、`answer_accuracy`、`citation_unsupported_rate`、`ttft_p50/p95`。
- **一句话**：**压缩的目标不是“最短”，而是“在可审计的前提下最省”。**

### 自测 3 题

1. 你的生成 token 成本占总成本多少？如果不到一半，压缩真的能省钱吗？
2. 压缩后你还能把每个结论定位到原文的哪一句吗？
3. 16× 压缩在你的语料上最可能失败在哪里：表格、代码、数字、还是多跳？

## 知识点 2：证据冲突与时效（R5-06）

### 一句话结论

**RAG 的相似度检索没有时间模型。** 当事实变化时，旧证据与新证据的 embedding 可能几乎一样近，模型会**主动选择过期值**。实验里，过期检索能翻转 **30% 的 Llama 与 37% 的 Qwen** 答案；知识演化场景中，RAG **15–40%** 的回答会使用已被取代的旧值。**解决时效不能靠“清理旧文档”，要把有效期带进排序和提示。**

### 为什么重要

- 企业知识库天然有版本：制度、价格、API、政策都会变。
- 过期证据不是“无关”，而是“看起来非常相关但已经错了”——比没有证据更危险。
- 2026 年的两篇研究给了量化：**Stale-Document Poisoning** 与 **MemStrata**，都把“时效”从治理问题变成检索/生成接口问题。

### 核心机制：时间元数据 + 时效重排

```text
文档元数据：
  source_date, valid_from, valid_to, supersedes, is_current, authority

检索后：
  ① 同等相关时，优先 is_current / 更新的 source_date
  ② 若新旧冲突 → 保留多版本 + 标注有效期，不静默选一个
  ③ 对结构化事实 → (subject, relation, object, valid_from, valid_to)
     用规则退休旧值（MemStrata 思路）
```

**关键数字：**

- 过期证据翻转答案：**30% Llama / 37% Qwen**；明确要求“遵循文档”后升到 **66% / 75%**。
- 匹配的最新证据被遵循：**97–100%**；毒化率范围 **17–91%**。
- 余弦区分“矛盾”与“重复”：**AUROC 0.59（接近随机）**。
- MemStrata：演化知识准确率 **0.95–1.00**（RAG 0.20–0.47）；陈旧事实错误率 **15–40% → ~0%**。

### 怎么做

1. **元数据最小集**：`source_date`、`valid_from`、`valid_to`、`supersedes`、`is_current`、`authority`；没有这些，时效问题无法系统解决。
2. **检索后加“时效重排”**：同等相关时，优先 `is_current` 与更新的 `source_date`；但要防止“新但不可靠”压倒“旧但权威”。
3. **冲突显式化**：输出“两个版本 + 各自有效期 + 建议”，并标注冲突。
4. **对结构化事实建取代关系**：用规则退休旧值，不交给 cosine。
5. **评测集要含时效题**：专门设计“旧制度/新制度”问题，测 `stale_fact_error_rate`。

### 权衡与坑

- **坑 1：只信“最新”。** 最新可能是草稿/非权威；要同时看 authority。
- **坑 2：静默合并冲突。** 模型会随机选一个，且看起来很有信心。
- **坑 3：没有有效期元数据。** 再好的重排也无从下手。
- **坑 4：把 MemStrata 用在叙事文档。** 它适合结构化事实，不适合长文。
- 【我的建议】先补 `valid_from/valid_to/is_current` 三个字段；这是性价比最高的一步。

### 架构师视角

- 时效是**业务风险参数**：医疗/法务宁可拒答，也不要给旧值。
- 观测出口：`stale_fact_error_rate`、`conflict_detected_rate`、`current_source_ratio`、`answer_changed_after_time_filter`。
- **一句话**：**RAG 没有时间感，架构师必须替它装上。**

### 自测 3 题

1. 你的知识库里同一个事实有多个版本时，检索会返回哪个？你能控制吗？
2. 你的文档有 `valid_from/valid_to` 吗？没有的话，遇到“旧制度”问题你靠什么判断？
3. 如果新旧证据冲突，你的系统会“选一个”还是“展示冲突”？哪种更符合你的业务风险？

### 延伸阅读

- 【论文结论】Ahmed 等，《Stale-Document Poisoning: When Outdated Retrieval Overrides Correct Model Answers》，arXiv:2609.31342 → https://arxiv.org/abs/2609.31342 ｜ 精读：[证据时效与冲突](../05-前沿资料/2026-12-03-证据时效与冲突.md)

<details>
<summary>评分要点（先自己写完再看）</summary>

- **题 1**：停止条件不能只看“轮数”，应看**证据充分性**：① 是否覆盖问题分解后的所有子问题；② 关键实体/关系是否有证据；③ 是否存在未解决的冲突。可加“最小证据集”检查，而不是固定轮数。

- **题 3**：用**边际增益 / 边际成本**：`Δanswer_accuracy / Δlatency` 或 `cost_per_additional_correct`；当边际增益低于业务阈值（例如每多 1 秒换 <1pp 正确率）就停。
