## 今日速览

- **R0-01 RAG 第一性原理**：RAG 不是“向量库 + LLM”，而是一条 **证据供应链**；上限由证据质量决定，下限由生成约束决定。
- **R0-02 技术选型**：RAG、长上下文、微调、Agentic Search 不是四个互斥选项，而是四种“补知识”的手段，按知识形态与问题复杂度组合。

## 知识点 1：RAG 第一性原理与价值边界（R0-01）

### 一句话结论

**RAG 的价值不在于“检索”，而在于用可验证的外部证据，补偿模型在时效、私有知识和可追溯性上的缺陷。** 它把“模型记住什么”变成“系统能拿到什么、以及模型是否愿意照着说”。

### 为什么重要

- 很多 RAG 项目失败，不是模型不够强，而是把 **“语义相似”当成了“相关”**，又把 **“相关”当成了“充分”**。
- 作为架构师，你需要能回答：这套系统的误差主要来自哪里？是源数据、解析、切分、检索、排序、上下文，还是生成？
- 这个判断直接决定预算投向。经验上，**修解析 / 切分 / 加 rerank 的收益，通常大于换一个更大的 embedding 模型**；但这必须用你的评估集证明，不能当教条。

### 核心机制：五段证据链

```text
源文档 → 解析 → 切分/索引 → 检索/排序/过滤 → 上下文组装 → 生成/引用/拒答
  ↑        ↑         ↑              ↑                ↑              ↑
权威性   保真度    自包含性       召回率           证据密度        忠实度
时效性   结构化    可检索性       精确率           冲突处理        可追溯性
权限     元数据    版本           延迟/成本        位置效应        拒答准确率
```

每一段都有“漏损率”。端到端效果更像 **乘法**，不是加法：解析丢了表格结构，后面再强的 reranker 也救不回来；检索召回很高但上下文塞满噪声，faithfulness 反而会下降。

### 三个不等式

1. **语义相似 ≠ 相关**
   问“如何降低 Lambda 冷启动”，向量检索可能召回“什么是冷启动”的定义，因为语义很近，但它不回答“怎么降低”。
2. **相关 ≠ 充分**
   一个 chunk 提到“可以用 SnapStart”，但没有版本限制、配置步骤和坑；它相关，但不足以支撑可执行答案。
3. **充分 ≠ 会用**
   证据在 context 中间被忽略（lost in the middle），或者模型被参数先验带偏；这时答案错在“生成”，不在“检索”。

### 怎么做

1. **画出你的证据链**：从源文档到最终答案，逐段写“输入 / 处理 / 输出 / 失败模式”。
2. **给每一段配一个可观测指标**：
   - 解析：解析成功率、表格结构保留率
   - 切分：chunk 自包含率（脱离文档是否可读）
   - 检索：Recall@20、nDCG@10
   - 排序：rerank 后 top-5 的相关率
   - 生成：引用正确率、faithfulness、拒答准确率
3. **用 20 个真实 bad case 做归因**，不要凭感觉。每个 case 标注：错在检索、排序、上下文还是生成。
4. **先修最弱一环**：如果 70% 的错误是“根本没召回”，先别急着换生成模型；如果是“召回但没用对”，先查上下文组装和提示词。
5. **为“无答案”设计路径**：阈值、拒答模板、人工升级。一个不会说“不知道”的 RAG，在生产里很危险。

### 权衡与坑

- **只追求 Recall 会把噪声塞进上下文**，反而降低 faithfulness。检索指标和生成指标要一起看。
- **引用不等于正确**：模型可能引用一个并不支持该结论的 chunk。要做 citation entailment 检查，而不是只看“有没有链接”。
- **平均分会掩盖分层问题**：FAQ、多跳、时效、无答案四类问题的失败率可能完全不同，必须分层评估。
- **Demo 成功不等于系统可用**：5 个问题上的“看起来不错”，不能外推到 500 个真实问题。

### 架构师视角

- **RAG 是数据产品，不是模型功能。** 知识运营、权限、版本、评估集是长期成本；只算推理 API 的账会低估总成本。
- **先做“可解释的失败”，再做“更复杂的架构”。** 如果连错误归因都做不了，上 GraphRAG / Agentic RAG 只会让问题更贵、更难查。
- **一个有用的提问**：如果明天把生成模型换掉，这套 RAG 还能工作吗？如果答案是否定的，说明你的系统过度依赖某个模型的“脾气”。

### 自测（先别翻答案）

1. 你的系统里，检索错和生成错各占多少？你用什么证据得出这个比例？
2. 如果一个 chunk 脱离原文档就语义不清（比如“该公司营收增长 3%”），应该在哪一层修？怎么修？
3. 为什么“把 top-k 从 5 加到 20”可能让答案更差？在什么条件下它又会更好？

## 知识点 2：RAG / 长上下文 / 微调 / Agentic Search 的选型（R0-02）

### 一句话结论

**选型顺序不是“哪个技术更先进”，而是：知识是否静态可封装、问题是否需要多跳、错误成本有多高。** 四者不是互斥关系，真实系统往往是“RAG 为主，长上下文做小 corpus，微调管风格，Agentic 管复杂任务”。

### 为什么重要

- 选错路线的代价很高：用微调记事实，知识一更新就要重训，而且模型会“自信地记错”；用 RAG 做求和/排名，等于拿锤子拧螺丝。
- 架构师的价值，不是会搭某个框架，而是能在 **成本、延迟、可追溯、更新频率** 之间做取舍，并说清楚为什么。

### 四种手段的边界

| 维度 | RAG | 长上下文 | 微调 | Agentic Search |
|---|---|---|---|---|
| 知识更新 | 实时 / 增量 | 每次重新注入 | 需重训 | 实时 |
| 私有数据 | 强 | 强（放得下时） | 中 | 强 |
| 可追溯 | 强（引用） | 中 | 弱 | 中 |
| 延迟 / 成本 | 中 | 高 token | 低推理 / 高训练 | 高（多步） |
| 多跳 / 开放研究 | 中（需 agentic） | 弱 | 弱 | 强 |
| 典型场景 | 企业知识库、客服、文档问答 | 小 corpus、长文档分析 | 风格、格式、领域语感 | 多源研究、复杂任务 |

### 决策树

1. **先看知识规模与更新频率。**
   - 知识库小于约 20 万 tokens（约 500 页），且更新不频繁：**长上下文 + prompt caching** 可能更简单。Anthropic 在 Contextual Retrieval 一文里明确给过这个经验阈值。
   - 知识更大、更新更频繁、需要权限隔离：**RAG**。
2. **再看问题形态。**
   - 单跳事实问答：混合检索 + rerank 通常够用。
   - 多跳、开放研究、需要多工具：**Agentic RAG / Agentic Search**。
   - 关系密集（谁和谁有什么关系、跨实体推理）：考虑 **GraphRAG**。
   - 图表、扫描件、视频密集：考虑 **多模态 RAG**。
3. **再看能力缺口。**
   - 缺的是事实、时效、可追溯：**RAG**。
   - 缺的是风格、格式、领域表达：**微调**；事实仍然交给 RAG。
   - 缺的是聚合、计算、排序：**Text-to-SQL / 代码执行**，不要硬 RAG。
4. **最后看约束。**
   延迟、成本、权限、可追溯，四项一起排优先级。不要用“技术先进性”替代业务约束。

### 常见误区

- **用微调记事实**：知识更新要重训，且容易产生“自信幻觉”。微调更适合学“怎么说”，不适合学“说什么”。
- **用 RAG 做聚合计算**：问“上季度销售额总和”，应该走结构化查询；向量检索不擅长精确聚合。
- **长上下文塞满**：窗口变大不等于模型会均匀利用；中间位置的信息容易被忽略，成本也线性上升。
- **Agentic 过度设计**：多步规划带来延迟、成本和不可控；没有评估证明增益之前，不要上。
- **把“混合”当成“万能”**：混合检索、混合架构都需要调参和评估，不是拼起来就更好。

### 架构师视角

- 画一张 **2×2**：横轴“知识规模/更新频率”，纵轴“问题复杂度/多跳程度”。把你的场景放进去，先选默认架构，再留一个升级路径。
- 为每类问题设“最小架构”：
  - FAQ / 客服：hybrid retrieval + rerank + 引用 + 拒答
  - 合同 / 报告分析：父子块 + 长上下文 + 引用
  - 跨文档研究：Agentic RAG + 工具路由 + 验证
  - 报表 / 经营分析：Text-to-SQL + 少量 RAG 做解释
- 先做 4 周 PoC，固定五个指标：**答案正确率、引用正确率、拒答准确率、P95 延迟、单次成本**。没有这五个数，架构讨论会变成口味之争。

### 自测（先别翻答案）

1. 你的场景知识 50 万 tokens，每天更新一次，团队只有两个后端。你选什么？为什么？
2. 一个问题需要跨 3 份合同找冲突条款，普通 RAG 会在哪一步失败？你会怎么改造？
3. 微调和 RAG 同时使用时，边界怎么划？什么应该进微调，什么必须留在检索？

### 延伸阅读

- [Anthropic: Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval) — 除了方法本身，开头的“何时直接用长上下文”也值得读。
- [Duy Nguyen: Advanced RAG Techniques in 2026](https://duynguyenngoc.com/posts/advanced-rag-techniques-2026) — 把 Agentic、Graph、Multimodal、Bidirectional RAG 放在同一张演进图里。
- [Anthropic: Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) — 在决定“要不要上 Agentic RAG”之前，先分清 workflow 与 agent 的边界，能省掉很多过度设计。

## 今日前沿插入

> 以下标注为“趋势观察”，不是定论；目的是让你知道 2026 年大家在往哪走，而不是催你上架构。

- **Agentic RAG 正在从论文概念变成生产架构。** 典型形态是 `planner → query router → retriever(s) → relevance/faithfulness checker → generate + cite` 的循环，适合多源、多跳、需要验证的任务；简单 FAQ 用它是过度设计。可参考 [Duy 2026 的整理](https://duynguyenngoc.com/posts/advanced-rag-techniques-2026)。
- **GraphRAG 与多模态 RAG 的边界更清楚了。** 关系密集（法律、生物医药、组织知识）值得建图；图表/扫描件密集值得做多模态。两者的共同代价是“抽取与维护”，不是“检索”本身。
- **“更复杂”必须用评估证明。** RAG 不是零幻觉保证；如果检索质量差，更多上下文、更复杂的 agent 反而可能放大错误。上线前至少要有分层评估集和无答案测试。

**我的判断**：2026 年的 RAG 不是“越来越复杂的 RAG”，而是 **“按问题路由的 RAG 组合”**。默认架构应该简单，复杂架构只在评估证明有增益时启用。
