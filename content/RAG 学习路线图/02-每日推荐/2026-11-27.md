## 今日速览

- **R4-05 非对称检索**：query 与 document 在**长度、意图、语法形态**上天然不同，用同一套编码方式处理两者，是在用一个平均化的折中同时牺牲两端；而 2026 年的工业实践给出了一个**极便宜的解法**——**在索引期给文档加"领域描述性前缀"，零训练、18 种语言、400+ 客户实例上 Hit@5 提升 3–8%、A/B 的 CTR +4.2%**。

## 知识点 1：非对称检索（R4-05）

### 一句话结论

query 短、口语、意图窄；document 长、书面、多主题——**这是两种不同的文本分布**，所以"用同一套编码方式处理两者"本身就是一种折中；而修正这个折中最便宜的手段不是微调模型，而是**给两侧加不同的"角色标记"**（query 侧加任务指令、document 侧加领域前缀）。

### 为什么重要

**先把"不对称"的三个来源说清楚（这决定了你该在哪一侧动手）：**

| 不对称维度 | query 侧 | document 侧 | 后果 |
|---|---|---|---|
| **长度** | 3–20 词 | 100–1000 token | 嵌入被"平均"的程度不同；短文本方差大 |
| **意图** | 单一、明确 | 多主题、含噪声 | 文档向量是"主题包"，query 向量是"一个点" |
| **形态** | 疑问句、口语、缩写 | 陈述句、术语、结构化 | 词汇分布不同（第 011 期 BM25 的优势正来自这里） |

**证据一：索引期前缀是一个"零训练、可规模化"的修正。**

【论文结论】*Index-Time Prefix Injection for Multi-Tenant Retrieval*（Varshney & Naik，**ACL 2026 Industry Track**，pp. 2231–2240，DOI 10.18653/v1/2026.acl-industry.149，2026-07）面对的正是最苛刻的约束：**多租户企业搜索平台用一个共享检索模型服务数百个客户**，而**按客户微调通常被合同与监管禁止**，维护"每客户一个模型"也不可扩展。

他们的做法极简：**在索引时给文档前置一段"领域描述性自然语言前缀"**。论文给的例子是给 IT 知识库前置 `"IT service management knowledge article:"`，效果是**把该库的嵌入推向向量空间中更紧、更领域一致的区域**。

前缀怎么来？**三级策略**：
1. **数据政策允许时**：从文档样本用 LLM 生成；
2. **不允许时**：领域专家策展；
3. **兜底**：一个标准化的前缀库。

规模与结果：**18 种语言、400+ 客户实例部署**，**Hit@5 提升 3–8%，零模型训练**；**A/B 测试确认 CTR 提升 4.2%**。论文还专门讨论了失败模式与部署教训。

→ 为什么这条对你价值极高：**它是"不动模型、不动索引结构、只改索引文本"的改动**——成本接近零、可回滚、可 A/B。**如果你只从今天带走一件事，就带走这个。**

**证据二：query 侧的"指令"很容易被高估——模型经常根本没在听。**

【论文结论】*Your Prompt Should Do More: Effects of Retrieval Instructions in Embedding Models*（Myntti, Kanerva, Laippala, Ginter，arXiv:2610.10508，2026-10-07）研究的是**指令如何实际影响非对称检索中查询的表示**。背景是：prompted embedding 模型近年很热，很多工作把详细检索指令放进检索提示，**但已有数据集与研究表明当前模型经常无法可靠遵循这类指令**。

他们的核心发现很尖锐：**当评估中包含"查询侧干扰项"（query-side distractors）时，模型可能连简单的任务指令都无法遵循**。他们假设这由**当前嵌入模型的训练设置与评测方式**驱动，并验证：**加入查询侧干扰项做微调，能带来实质改善，且对其它任务影响极小**。

→ 含义有两层：
- **不要假设"我写了指令，模型就会遵守"**——必须在**带干扰项的评估集**上验证，否则你测的是一个"干净到不真实"的场景；
- 好消息是：**修它的代价不大**（加干扰项微调，对其它任务几乎无损）。

**证据三：为什么"查询侧永远在算"——非对称的经济学。**

【事实/算例】Vespa 的一篇工程文章把账算得很直白：**文档嵌入一次，查询永远在嵌**；按每百万 token 0.02 美元计，高 QPS 下**仅查询嵌入就可能超过每月 15,000 美元**。
→ 这解释了两件事：① 为什么"用大模型编码文档、用小模型编码查询"这种**非对称架构**有吸引力；② 为什么第 017 期说"查询期成本通常可忽略"是有前提的——**在超高 QPS 下它并不忽略**。

**证据四：统一模型会引入"移动目标"问题。**
【论文结论】DEPT（arXiv:2608.17632，2026-08-18）：让**同一个 decoder-only LLM 既生成查询扩展、又编码扩展后的查询与候选文档**，会带来一个结构性问题——**检索监督本应改进查询侧的扩展，但同一次更新也移动了作为检索目标的文档嵌入**。他们的解法是**保持调优后的文档嵌入接近缓存的初始嵌入**（直通解码让梯度仍能回传），从而把"查询-文档联合移动"转成"**针对近似稳定、白化的文档嵌入做查询侧适配**"。
关键收益一句：**这样做支持索引复用（index reuse）与在线难负例挖掘**。
→ 这正是 R4-05 与 R4-06 的交点：**"让文档侧稳定、只动查询侧"，既是效果问题，也是运维问题**（文档侧一动，索引就得重建）。

### 核心机制 / 数据流

**三种非对称实现方式（成本递增）：**

```
① 角色标记（最便宜）
   query:     "Instruct: Given a web search query, retrieve relevant passages\nQuery: {q}"
   document:  "IT service management knowledge article: {d}"
   → 零训练；改的是"索引文本"与"查询文本"，不改模型

② 非对称模型（中等）
   文档用大模型/长上下文模型编码，查询用小模型编码
   → 省查询期成本；但要保证两个空间的"可比较性"（通常需联合训练）

③ 联合训练 + 稳定文档侧（最贵）
   DEPT 式：文档嵌入保持接近缓存初值，梯度只作用于查询侧
   → 支持索引复用；实现复杂
```

**关键工程点：前缀加在"索引文本"上，不是加在"展示文本"上。**
```
入库：embed_text = prefix + "\n" + chunk_text     ← 只用于生成向量
展示：raw_text = chunk_text                        ← 用于引用与阅读
```
【我的建议】这个分离是必须的：如果前缀混进 `raw_text`，你的引用会带上"IT service management knowledge article:"这种噪声，用户会立刻发现。

**为什么前缀有效（机制假设）：**
```
领域前缀把"这篇文档属于哪个语域"这一信息注入向量
→ 同一租户/同一领域的文档被推到更紧的子区域
→ 跨领域的"看起来像"干扰被压缩（对齐第 012 期的各向异性讨论）
```
【论文结论】原文的表述是"shifts its embeddings into a tighter, more domain-coherent region of the vector space"——**注意这是"更紧、更领域一致"，不是"更准"**；效果来自**减少跨域混淆**，而不是提升单域内的语义理解。

### 怎么做（3 步）

**第 1 步：先量"你的不对称缺口"在哪一侧。**

```
取 50 条真实 query，对每条找 gold 文档，然后分别测：
  A 现状（两侧同处理）           → recall@5 基线
  B 只给 query 加任务指令         → 看 query 侧是否有救
  C 只给 document 加领域前缀      → 看 document 侧是否有救
  D 两侧都加                      → 看是否叠加
判读：
  B 明显提升 → 你的问题在"query 表达与索引语域不匹配"
  C 明显提升 → 你的问题在"多租户/多领域混在一个空间"
  都没提升   → 别在这上面花时间，去查切分或 rerank
```
【论文结论】ACL 2026 Industry 那篇的收益（3–8% Hit@5）正是"只加 document 侧前缀"得到的；而 arXiv:2610.10508 提醒你**query 侧指令要带干扰项测**，否则会高估。

**第 2 步：实现"前缀与展示分离"的索引写入。**

```python
def build_embed_text(chunk, tenant_profile):
    prefix = tenant_profile.domain_prefix        # 例："IT service management knowledge article:"
    return f"{prefix}\n{chunk.text}" if prefix else chunk.text

def index_chunk(chunk, embedder, store, tenant_profile):
    vec = embedder.encode(build_embed_text(chunk, tenant_profile))
    store.upsert(id=chunk.id, vector=vec, payload={
        "raw_text": chunk.text,                  # ← 展示与引用用这个
        "prefix": tenant_profile.domain_prefix,  # ← 可审计、可回滚
        "prefix_version": tenant_profile.version,
        "doc_id": chunk.doc_id, "page": chunk.page,
    })
```
**前缀必须版本化**（`prefix_version`）：改前缀等于改嵌入，**必须能识别出"这次召回变化是前缀改的"**，否则你无法归因。

**第 3 步：用"跨域混淆率"验收，而不只看 recall。**

```
跨域混淆率 = 在 top-10 里，来自"错误租户/错误领域"的文档占比
目标：该指标显著下降（因为前缀的作用正是"收紧领域一致性"）
同时看：recall@5 不能掉（防止"更紧"变成"更窄"）
```
【我的建议】这两个数一起看才完整：**前缀可能让召回更集中，但也可能把本该跨域召回的边缘案例挤掉**。

### 权衡与坑

- **坑 1：以为"加了指令模型就会听"。** 【论文结论】带查询侧干扰项时，**模型可能连简单指令都无法遵循**（arXiv:2610.10508）。**必须在带干扰的评估集上验证。**
- **坑 2：把前缀写进展示文本。** 用户会看到 `"IT service management knowledge article:"`。**embed_text 与 raw_text 必须分离。**
- **坑 3：前缀不版本化。** 改前缀 = 改全部向量。**没有 `prefix_version`，你无法解释"为什么昨天还好今天变了"。**
- **坑 4：以为"更紧"一定更好。** 【论文结论】原文说的是"tighter, more domain-coherent"，**代价是可能牺牲跨域召回**。要同时看 `recall@5` 与跨域混淆率。
- **坑 5：忽略查询期成本在高 QPS 下的量级。** 【事实/算例】文档嵌一次、查询永远在嵌；高 QPS 下查询嵌入可能成为主要成本项。**这时候"非对称模型"（小模型编查询）才是真解法。**
- **坑 6：统一模型训练时没锁住文档侧。** 【论文结论】DEPT 指出的"移动目标"问题：同一次更新既改查询侧又改文档侧，**导致索引无法复用**。
- 【我的建议】顺序：**先试 document 侧前缀（零训练、可 A/B）→ 再试 query 侧指令（带干扰项验证）→ 最后才考虑非对称模型/联合训练**。

### 架构师视角

- **非对称是一个"被低估的设计维度"**：我们花很多时间讨论"用哪个 embedding 模型"，却很少讨论"两侧是否该用同一种处理"。而后者**成本更低、可回滚、可 A/B**。
- **它天然适配多租户**：一个共享模型 + 每租户一个前缀，**既满足"不能按客户微调"的合规约束，又拿到了领域适配的收益**（这正是 ACL 2026 Industry 那篇的立论）。
- **观测出口**：`recall@5`（分租户/领域）、`cross_tenant_confusion_rate`（跨租户混淆率）、`prefix_version`、`query_embed_cost_share`（查询嵌入占总成本比例）。
- **一句话**：**"非对称"不是让两侧不一样，而是让两侧各自被正确地表达**——前缀与指令只是手段，判据始终是"检索有没有变准"。

### 自测 3 题

1. 你的 query 与 document 是用同一套方式编码的吗？如果是，你有没有测过"只给文档加领域前缀"能带来多少提升？
2. 你写的检索指令，在**带干扰项**的评估集上还成立吗？如果没测过，你怎么知道模型真的在听？
3. 你的索引文本与展示文本是同一个字段吗？如果是，加前缀后用户的引用会变成什么样？

## 知识点 2：模型迁移与重索引（R4-06）

### 一句话结论

换 embedding 模型**看起来是改一行配置，实际是一次全量数据迁移**：所有向量都要重算、索引要重建、查询要换编码器，而且**新旧向量不可混用**——所以正确形态是"**双写 + 双读 + 影子代次 + 灰度 + 可回滚**"，验收必须在**同一条查询流**上对比两个索引。

### 为什么重要

**先看清"为什么不能平滑切换"。**

```
旧：query --enc_v1--> q1   ;  doc --enc_v1--> d1   ;  sim(q1, d1) 有意义
新：query --enc_v2--> q2   ;  doc --enc_v2--> d2   ;  sim(q2, d2) 有意义
混用：sim(q2, d1)  ← 两个不同空间的向量，分数没有意义
```
【我的建议】这是最容易被忽略的一条：**迁移期间如果查询已经切到 v2、索引还是 v1，你得到的是"随机排序"，而且不会报错**——它会安静地把准确率打到接近随机，直到有人发现答案开始胡说。

**这就是为什么"双索引 + 原子切换"不是过度设计，而是唯一安全的形态。**

**再看工业界已经把这个流程标准化了。**
【事实】Qdrant 的官方教程给出了**两条零停机迁移路线**，并强调**要同时比较新旧模型的检索质量**（不是只看"迁移成功"）。
【事实】Zilliz 的 runbook 提供"**不重建 collection**"的迁移方式：在同一 collection 里**新增一个向量列**，新旧并存。
【事实】AWS 的工程文章给出 OpenSearch 索引更新嵌入模型的**两种生产级策略**，核心同样是"新字段/新索引 + 双写 + 切换"。

→ 三家不同厂商收敛到同一形状，说明这不是某家的偏好，而是**约束决定的**（数据量、可用性、可回滚）。

**再看一个"迁移期"特有的技术问题：跨模型检索。**
【论文结论】ERA（*Embed, Route, Adapt*，arXiv:2611.26919，2026-11）研究**冷启动跨模型潜在检索**：**让一个模型编码的查询去检索另一个模型编码的文档**，提出端到端系统（Embed-Route-Adapt）。
→ 它的价值不在"要不要用"，而在提醒你：**迁移期一定会出现"新旧共存"的窗口**，而这个窗口里的检索质量是可以被工程化处理的（而不是只能"等迁移完"）。

### 核心机制 / 数据流

**五阶段迁移（这是本节的主干）：**

```
阶段 0：准备
  - 新模型选型与验收（R4-01 的三列表：recall / 内存 / p95）
  - 冻结旧模型的版本号（embed_model_version = v1）
  - 准备"双索引"容量（存储要能放两份，见第 018 期的账）

阶段 1：双写（不读新）
  - 新增文档同时写 v1、v2 两个索引
  - 历史文档后台批量重算（走影子代次，第 008 期）
  - 查询仍只读 v1
  ⚠ 关键：v2 索引的 doc 与 v1 必须"同源同版本"，否则对比无效

阶段 2：影子读（不对外）
  - 对同一批线上 query，同时查 v1 与 v2，记录两边结果
  - 用离线金标算：recall@5 / recall@10 / 排序相关性
  - 用线上代理指标算：无答案率、引用命中率（若有日志）

阶段 3：灰度
  - 按流量比例（1% → 5% → 20% → 50%）把查询路由到 v2
  - 每组都保留"回滚开关"（一键切回 v1）
  - 关注：延迟、错误率、用户反馈

阶段 4：切换与清理
  - 全量切到 v2，v1 保留 1–2 周（可回滚）
  - 确认无回滚需求后，删除 v1 索引与旧向量
```

**"双读"的三种实现（按侵入性递增）：**

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **查询旁路**（shadow） | 只对抽样流量同时查两索引，不影响返回 | 零风险 | 只覆盖抽样，且无法测"用户反应" |
| **流量切分**（A/B） | 按用户/会话哈希分流 | 能测真实指标 | 需要稳定的分流键 |
| **双列共存**（同 collection） | 新旧向量列并存，查询指定列 | 迁移最平滑 | 受向量库能力限制 |

### 怎么做（3 步）

**第 1 步：先算"双写窗口有多长"——这决定你要不要分期。**

```
需要重算的向量数 N；单卡吞吐 T（向量/秒）；可用并行度 P
窗口时长 ≈ N / (T × P)
若 窗口 > 2 周 → 建议分批（按 doc 更新时间/租户/业务线），并让"已迁移"与"未迁移"共存
```
【我的建议】把"窗口时长"写进迁移计划的第一行。**很多迁移事故不是技术问题，是"以为一周能跑完，实际要一个月"**，然后在第 10 天被迫混用两个空间。

**第 2 步：实现"版本化查询路由"（这是回滚能力的核心）。**

```python
CURRENT = {"model": "v2", "index": "idx_v2"}      # 单一真源，可原子改写

def search(query, k=10):
    cfg = CURRENT
    qvec = ENCODERS[cfg["model"]].encode(query)    # 查询侧必须与索引侧同版本
    return STORES[cfg["index"]].search(qvec, k=k)

# 回滚 = 改一行（并确保缓存 key 含 model 版本）
def rollback():
    CURRENT.update({"model": "v1", "index": "idx_v1"})
```
**两条硬规则**：
1. **查询编码器与索引必须同版本**——这是唯一不能错的约束；
2. **所有缓存 key 必须含 `embed_model_version`**（第 006 期 R1-06 的"缓存 key 要含权限"，这里是同一个道理：**缓存必须包含"会让答案失效的维度"**）。

**第 3 步：用"同流对比"做验收，而不是各跑各的。**

```
对同一批 query（建议 200 条线上真实 query）：
  v1 结果：recall@5、recall@10、无答案率、p95 延迟
  v2 结果：同上
  diff  ：逐条看"v1 命中 v2 未命中"与"v2 命中 v1 未命中"的样本
判据：
  - 净提升 > 0 且"退化的样本"可解释（例如旧模型在长文档上更好）
  - p95 延迟不劣化超过 20%
  - 无答案率不上升
```
【我的建议】**逐条看 diff 是必须的**：只看汇总数字，你会漏掉"某类问题整体退化"（第 002 期：平均分会掩盖分层问题）。

### 权衡与坑

- **坑 1：混用两个空间的向量。** 查询切了 v2、索引还是 v1 → **随机排序，且不报错**。这是最危险的一条。
- **坑 2：缓存没带模型版本。** 切换后旧答案还在缓存里，你会以为"新模型没生效"。
- **坑 3：只在离线评测上对比。** 两个模型在不同评测集上各跑一遍，**不是同流对比**，结论不可比。
- **坑 4：没有回滚开关。** 迁移"只能前进"，一旦新模型在长尾上更差，你只能硬扛。
- **坑 5：低估重算窗口。** 见第 1 步。**窗口超预期是迁移事故的头号原因。**
- **坑 6：忘了下游依赖。** 语义缓存、聚类结果、MMR 的相似度阈值（第 016 期）、拒答阈值（第 015 期）**都依赖具体的相似度分布**——换模型后它们全部要重新校准。
- **坑 7：把"迁移完成"当终点。** 迁移后 1–2 周要盯 `recall` 漂移与用户反馈；**旧索引删除前，务必确认没有回滚需求**。
- 【我的建议】把迁移做成一份**清单**（checklist），而不是一次"操作"：清单里每一行都能被检查，才不会漏掉第 6 条那种"下游全要重校"的隐性工作。

### 架构师视角

- **R4-06 是 M4 的收口，也是整个"数据层"的收口**：它同时用到了 R1-09 的影子代次、R1-06 的元数据（版本号）、R3-04 的内存账、R4-04 的压缩（决定双写放不放得下）、R4-05 的非对称（决定"只动查询侧"能不能省一次重建）。
- **"能不能回滚"比"新模型多好"更重要**：一个提升 3 个点但无法回滚的迁移，风险高于提升 1 个点但能一键切回的迁移。
- **观测出口**：`embed_model_version`（当前生效）、`dual_write_lag`（双写延迟）、`shadow_recall_delta`（影子读的新旧差）、`rollback_count`、`cache_hit_by_model`（按模型分桶的缓存命中）。
- **一句话**：**换模型不是"升级一个依赖"，而是"换掉整个语料的坐标系"**——坐标系一换，所有历史结论都要重算。

### 自测 3 题

1. 你的查询编码器与索引是"同一个版本"这个约束，现在由什么保证？如果是靠人记着，那它迟早会错。
2. 如果明天要换 embedding 模型，你的重算窗口是多久？双写期间的存储够吗？
3. 换模型后，你的语义缓存、MMR 阈值、拒答阈值里，哪些需要重新校准？你能列出完整清单吗？

## 今日前沿插入

> 只写有实质更新、且能核验来源的内容。

**① 索引期前缀注入：零训练的领域适配，已在 400+ 客户实例上验证（ACL 2026 Industry，2026-07）**
多租户场景（不能按客户微调）下，给文档前置领域描述性前缀，**18 语言、400+ 实例、Hit@5 +3–8%、零训练、A/B 的 CTR +4.2%**；前缀发现三级策略（LLM 生成 / 专家策展 / 标准库兜底）。→ https://aclanthology.org/2026.acl-industry.149/

**② 检索指令"可能没被遵守"（arXiv:2610.10508，2026-10）**
在非对称检索中研究指令对查询表示的实际影响：**评估里加入查询侧干扰项后，模型可能连简单任务指令都无法遵循**；**加入干扰项微调可显著改善，且对其它任务影响极小**。

**③ 统一模型的"移动目标"问题（DEPT，arXiv:2608.17632）**
同一模型既生成查询扩展又编码文档时，检索监督会同时移动"检索目标"；**保持文档嵌入接近缓存初值**可把问题转成"只动查询侧"，**从而支持索引复用**。

**④ 迁移已被标准化为"双写 + 双读 + 切换"（多家厂商文档收敛）**
Qdrant 给出两条零停机路线并强调**要对比新旧模型检索质量**；Zilliz 支持"不重建 collection"（新增向量列）；AWS 给出 OpenSearch 的两种生产级策略。

**趋势观察（非定论）**
2026 年 M4 收官时的信号：**"改模型"正从"训练一个更好的"转向"用更便宜的手段改变两侧的表达"**（前缀、指令、非对称模型），而**"换模型"正从"改配置"变成"一次数据迁移工程"**。这两条合起来意味着：**embedding 层的竞争点正在从模型能力转向运维能力**。**属趋势观察。**
