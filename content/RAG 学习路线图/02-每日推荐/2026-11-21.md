## 知识点 1：ANN 索引（R3-04）

### 一句话结论

ANN 索引的本质是**用"可能漏掉一点"换"快几个数量级"**；HNSW 用图换延迟、IVF 用聚类换可调性、PQ 用压缩换内存，三者可以叠加——但**先用什么指标衡量"漏掉一点"是可接受的，比选哪种索引更重要**。

### 为什么重要

**先纠正一个可能让你过度工程的直觉：Recall@k 可能不是该优化的目标。**

【论文结论】*ANN Search: Recall What Matters*（arXiv:2606.04522）直接挑战了社区默认的评测方式：大家用"给定 Recall@k 下的吞吐"来调 ANN，但作者认为**真正重要的是检索结果的质量，而不是它与真实 kNN 集合的重叠率**。他们提出用 **1/Ratio@k（近似比的倒数）** 替代 Recall@k——它衡量的是"检索到的近邻与真实近邻在距离上差多少"，**无需裁判、无需调参、只用标准 benchmark 输入就能算**。他们的实验结论有两条很实用：
- **按 1/Ratio@k 优化，能在显著更低的计算开销下达到运营级质量阈值**（也就是说：你为了把 Recall@k 从 0.90 拉到 0.97 付出的算力，很可能买不到对应的效果）；
- **当下游指标（标签精度、语义相似度、BERTScore、LLM 打分）在 Recall@k 大幅下降时依然高度稳定**，而 1/Ratio@k 更贴近这种稳定性。

*> 这条对你的直接含义：**ANN 参数不该按"召回 0.95"这种拍脑袋目标调，而该按"下游指标不再提升"的那一点调。** 这也解释了为什么很多团队把 `efSearch` 从 64 提到 256、延迟涨了 3 倍，答案质量却没动。*

**三种索引的机制差异（这决定了它们各自的失效方式）：**

| 结构 | 机制 | 主要旋钮 | 强项 | 失效方式 |
|---|---|---|---|---|
| **HNSW**（分层可导航小世界图） | 多层图，上层稀疏做"跳远"、底层稠密做"精查"，贪心下降 + 候选队列 | `M`（每点连边数）、`efConstruction`、`efSearch` | 高召回下的低延迟；无需训练 | **内存随 N 线性且常数大**（边表）；**过滤时容易退化**（见 R3-05）；**无最坏情况保证** |
| **IVF**（倒排文件/聚类） | 先 k-means 分桶，查询时只搜最近的 `nprobe` 个桶 | `nlist`（桶数）、`nprobe` | 内存可控；**低选择性过滤场景更稳**；易分片 | 桶边界上的点会漏；`nprobe` 小则召回掉 |
| **PQ**（乘积量化） | 把向量切段、每段用码本量化，距离用查表近似 | `m`（段数）、`nbits` | **内存降 10–100 倍**；可放内存/GPU | 量化误差 → 召回上限被锁死；不擅长高精度重排 |

**参考坐标（经典文献，用于理解而非选型）**：HNSW 的原始论文（Malkov & Yashunin, arXiv:1603.09320）给出的是"分层图 + 贪心搜索"的完整设计与经验参数；Faiss（Johnson, Douze, Jégou, arXiv:1702.08734）则是"把 IVF/PQ/HNSW 组合成可调库"的工程范式——**你用的几乎所有向量库，都是这两条线的后代**。

**一个必须知道的结构性事实**：图方法（HNSW/NSG 等）**没有最坏情况查询时间保证**，存在让贪心搜索退化成近似线性扫描的数据分布；而基于聚类的结构虽然也有病态情形，但其代价更容易被"多探几个桶"这类参数控制住。→ **这也是为什么"低选择性过滤"场景下 IVF 常常打败 HNSW**（下面 R3-05 会给出实测结论）。

### 核心机制 / 数据流

**把三者看成"三层可叠加的压缩"：**

```
原始：N × d × 4 bytes                       （float32）
  ↓ IVF：分成 nlist 个桶，查询只碰 nprobe 个   → 减少"要扫多少"
  ↓ PQ ：每向量压到 m × nbits bits            → 减少"每个占多少"
  ↓ HNSW：建图，用边跳过大部分点               → 减少"要跳几步"
最终：内存 ↓10–100×，延迟 ↓1–3 个数量级，召回 ↓可控
```

**参数之间的耦合（这是调参时最容易踩的）：**

| 你调的东西 | 直接后果 | 间接后果（常被忽略） |
|---|---|---|
| `M` ↑ | 图更连通 → 召回↑ | 内存↑、构建时间↑；**过滤时无效边更多** |
| `efSearch` ↑ | 搜索更彻底 → 召回↑ | 延迟近似线性↑；**收益在某个点后急剧递减** |
| `nlist` ↑ | 桶更细 → 单桶更快 | 每桶样本变少 → 桶内代表性差、召回↓ |
| `nprobe` ↑ | 探更多桶 → 召回↑ | 延迟↑；到某个点等于全扫 |
| `m`(PQ) ↑ | 量化更精细 → 召回↑ | 内存↑；码本训练更慢 |

### 怎么做（3 步）

**第 1 步：先在"你的数据 + 你的查询"上画 QPS–质量曲线，而不是看别人的 benchmark。**

```python
import time

def sweep_ef(index, queries, k=10, ef_values=(32, 64, 128, 256, 512)):
    out = []
    for ef in ef_values:
        index.set_ef(ef)
        t0 = time.perf_counter()
        hits = [index.search(q, k) for q in queries]
        dt = (time.perf_counter() - t0) / len(queries)
        out.append({"ef": ef, "ms": dt * 1000,
                    "quality": downstream_quality(hits)})   # ← 用下游指标，不是 Recall@k
    return out
```
【我的建议】`downstream_quality` 用你真实的下游指标（答案命中率、nDCG、或 1/Ratio@k）。**把"质量不再提升"的那个 ef 记下来，它就是你的默认值。**

**第 2 步：按"内存预算"选压缩层，而不是按"最新论文"。**

```
内存 ≈ N × d × 4 bytes                    （原始向量，float32）
     + N × M × 2 × 4 bytes                （HNSW 边表，双向）
     + 码本开销                            （PQ，通常可忽略）

例：N=1e7, d=768, float32 → 原始 30.7 GB
    再开 M=16 的 HNSW 边表 → +1.28 GB
    若用 PQ(m=96, nbits=8) → 向量降到 ~0.96 GB（约 1/32）
```
【我的建议】先算这张账，再决定"要不要 PQ"。**很多团队的真实约束是内存，不是 QPS。**

**第 3 步：把"指标"从 Recall@k 换成双向验收。**
```
① 1/Ratio@k（或你自己定义的距离比）：衡量"近似有多近似"
② downstream_quality：衡量"下游是否感知到差异"
两者都平的区间 = 你可以在这一段随便省算力
```
【论文结论】这正是 arXiv:2606.04522 的核心主张：**Recall@k 高估了近似的代价**。

### 权衡与坑

- **坑 1：把 Recall@k 当业务指标。** 【论文结论】下游指标在 Recall@k 明显下降时仍稳定。**你可能在为感知不到的召回付钱。**
- **坑 2：以为 HNSW 总是最优。** 它在**内存受限**与**强过滤**两个场景下会输（后者见下一节）。**"默认 HNSW"是习惯，不是结论。**
- **坑 3：只调 `efSearch`，不看 `M`。** `M` 决定图的"连通性上限"，`efSearch` 只是在给定图上搜多深。**`M` 太小，`efSearch` 调到很大也补不回来。**
- **坑 4：忽略构建时间与重建成本。** 换 embedding 模型 = 全量重建索引（第 008 期 R1-09 的"影子代次"就是为这个准备的）。**构建 76 倍的差距在小语料上无感，在 10 亿级是小时级 vs 天级。**
- **坑 5：把 PQ 当"免费压缩"。** 量化误差会**锁死召回上限**——你用 PQ 压到 1/32，就不要指望它支撑"高精度重排"；补救办法是**用原始向量做二次重排**（rerank 阶段）。
- **坑 6：忘了"删除/更新"对图索引的伤害。** 图索引的删除通常是"标记 + 后台重建"，长期高频增删会让图退化（第 008 期的 churn 问题）。**这类退化在指标上表现为"缓慢的召回下滑"，很难归因。**
- 【我的建议】顺序：**先定内存预算 → 再定结构（IVF/HNSW）→ 再定压缩（PQ）→ 最后调 efSearch 到"质量平台期"。**

### 架构师视角

- **ANN 参数是"成本参数"，不是"质量参数"。** 它决定你花多少钱买到多少召回；而"够不够"必须由下游指标回答。
- **把"索引结构"当成可替换实现**：对外只暴露 `search(q, k, filter)`，内部允许按语料规模/过滤选择性切换 IVF/HNSW。这样你换库、换参数都不用改上层。
- **观测出口**：`ann_quality_curve`（QPS–下游质量曲线）、`ef_search_effective`（实际生效值）、`index_memory_gb`、`build_time_hours`、`churn_degradation`（增删后的召回漂移）。
- **一句话**：**别问"哪个 ANN 最好"，问"在我的内存预算和过滤分布下，哪个点在我的质量平台期上"。**

### 自测 3 题

1. 你的 `efSearch` 是多少？它对应的"下游质量"是多少？如果不知道，你怎么证明现在的值不是过度配置？
2. 你的索引内存里，向量本体和 HNSW 边表各占多少？如果边表占了三成，你会怎么选？
3. 如果只能给 ANN 加一个监控指标，你选 Recall@k 还是 1/Ratio@k（或距离比）？为什么？

## 知识点 2：元数据与权限过滤（R3-05）

### 一句话结论

"先过滤还是后过滤"**不是架构风格，而是由过滤选择性（selectivity）决定的可计算决策**：选择性高（过滤后还剩很多）→ 预过滤几无代价；选择性低（过滤后只剩极少）→ 后过滤会丢召回、预过滤会把 ANN 退化成暴力扫描；**而在真实数据库里，瓶颈常常是过滤检查与页访问，不是距离计算**——所以"算法论文的最优"经常不是"你系统的最优"。

### 为什么重要

**证据一：真实数据库里，系统开销会推翻算法结论。**

【论文结论】*An In-Depth Study of Filter-Agnostic Vector Search on a PostgreSQL Database System*（arXiv:2603.23710）开篇就批评：既有研究多在**专用库**里评测，做了大量"在企业级数据库里不成立"的乐观假设。他们的核心发现是：**最优算法并不只由距离计算成本决定，系统级开销（过滤操作、页访问、数据回取）同样主导**；并且**图方法（NaviX/ACORN 一类）可能产生极多的过滤检查与系统开销，常常抵消掉它们的理论优势**，反而不如**基于聚类的索引（ScaNN 一类）**。

**证据二：三种执行策略各有明确的失效区间，且"没有单一赢家"。**

【论文结论】*Filtered ANN Search in Vector Databases: System Design and Performance*（arXiv:2602.11443）把过滤策略统一成分类法，在 **FAISS / Milvus / pgvector** 三个系统里实测（自建关系型数据集 **MoReVec**：768 维文本 embedding + 丰富元数据），并提出 **Global-Local Selectivity（GLS）** 指标来量化"过滤器与查询向量的相关性"。三条结论：
1. **Milvus 通过"近似/精确混合执行"获得了更好的召回稳定性**；
2. **pgvector 的基于代价的优化器经常选出次优计划**——它会偏向近似索引扫描，**即使精确顺序扫描能在相近延迟下给出完美召回**；
3. **低选择性查询下，分区式索引（IVFFlat）优于图式索引（HNSW）**。

**证据三：不同执行顺序的"质量-尾延迟"曲线是可以被画出来的。**

【论文结论】*Vector+SQL Retrieval with Selectivity Workloads*（DOI 10.21015/vtse.v14i1.2353）在 arXiv / 新闻 / 电影三个域上构造可控选择性负载，并在**同一过滤候选集内计算精确真值**以保证公平，比较五种策略：
- **精确预过滤（exact prefilter）：准确率最高，但尾延迟最大**；
- **ANN 后过滤：更快，但严格过滤下召回显著下降**；
- **两阶段探测、分区对齐检索、自适应路由**：其中**自适应路由整体最稳**。

**证据四：低选择性下会出现"尾延迟非线性放大"。**
【论文结论】*Vector Databases Under Realistic Workloads*（IEEE，2026）：在带元数据过滤、持续增删、冷启动恢复三种生产负载下实测（含"filter-aware 真值 oracle"：bitmap 候选限制 + 自适应 FAISS flat），发现**过滤负载在低选择性下会触发超线性的尾延迟放大，即使召回仍然很高**；churn 会造成内存与尾延迟震荡；**热重启的恢复时间主要由索引重载与缓存预热决定，而不是进程启动**。

**证据五：既然没有单一最优，就"按查询路由"。**
【论文结论】*Query-aware Routing for Filtered ANN*（arXiv:2606.19898）：横跨多数据集、三类谓词评测后发现**没有任何单一方法占优，甚至在同一数据集同一谓词类型内，"最佳方法"也随查询变化**；他们用一个轻量 ML 模型预测各候选方法在该查询上的召回，再查离线 benchmark 表（方法/参数 → 实测召回与 QPS）选最优，**22 个特征被消减到 3 个**，在 5 个未见数据集上都取得最优的召回-QPS 平衡，路由开销可忽略。
【论文结论】*Efficient Filtered-ANN via Learning-based Query Planning*（arXiv:2602.17914）：预过滤需要昂贵的"每谓词建索引"，后过滤在低选择性下会"浪费计算且丢召回"；用学习式计划选择器从数据/查询统计量预测最优计划，相对强基线**最高 4× 加速且召回 ≥90%**。

### 核心机制 / 数据流

**先把"选择性"定义清楚（这是所有决策的自变量）：**

```
selectivity s = 满足过滤条件的向量数 / 总向量数
  s 接近 1（如 s > 0.2~0.3）  → 过滤几乎不缩小范围
  s 很小（如 s < 0.01）        → 过滤后只剩零星点
```

**三种执行顺序的代价模型：**

| 策略 | 做什么 | 何时最优 | 何时崩 |
|---|---|---|---|
| **预过滤（filter-then-search）** | 先算出候选 ID 集合，再在这个集合上做 ANN/精确搜索 | s 中等偏大；或候选集仍很大 | s 极小时，候选集太小 → **退化成暴力扫描**，且需要"按谓词建索引"的前置成本 |
| **后过滤（search-then-filter）** | 先 ANN 取 top-k'，再按谓词筛 | s 大（过滤掉的不多），且谓词选择性不可预知 | s 小时 **top-k' 里可能一个都不满足** → 召回断崖 |
| **内联/混合（inline / hybrid）** | 在图遍历或桶扫描过程中就地判断谓词 | 图/聚类结构支持时 | 过滤检查次数爆炸（图方法常见） |
| **自适应路由** | 按 s、谓词类型、查询特征选上面之一 | 负载异构 | 需要真值/校准数据与路由器维护 |

**为什么"图方法在强过滤下会翻车"（机制层）：**
HNSW 的贪心下降依赖"邻居大多相似"这个前提。当过滤把可达邻居大批排除后，**每次跳转都要检查大量不满足谓词的候选点**，有效步进变少 → 为了达到同样召回，需要把 `efSearch` 推到极大，甚至接近全图遍历。这正是 PostgreSQL 那篇里"图方法的过滤检查次数达到 prohibitive 量级"的机制解释。

### 怎么做（3 步）

**第 1 步：先量你的选择性分布，这是唯一能指导选型的数。**

```python
# 从线上日志里估：每条查询的 s = 过滤后候选数 / 总向量数
import numpy as np
s = np.array(selectivities)          # 例：[0.42, 0.31, 0.008, 0.005, ...]
for lo, hi in [(0, 0.01), (0.01, 0.1), (0.1, 0.5), (0.5, 1.0)]:
    m = ((s >= lo) & (s < hi)).mean()
    print(f"s∈[{lo},{hi}): {m:.1%} 的查询")
```
【我的建议】典型企业知识库（按租户/权限/时间过滤）会呈现**双峰**：多数查询 s 很大（几乎全库可查），少数查询 s 极小（严格权限或时间窗）。**双峰意味着你必须路由，而不是选一个策略。**

**第 2 步：按 s 写一个最小路由器（先规则，后模型）。**

```python
def choose_plan(s: float, n_total: int, k: int) -> str:
    est_candidates = s * n_total
    if est_candidates <= max(10_000, k * 50):
        return "exact_prefilter"      # 候选太少：直接暴力扫描更快且召回完美
    if s >= 0.30:
        return "ann_postfilter"       # 过滤掉的不多：先 ANN 再筛
    return "inline_or_ivf"            # 中间地带：内联过滤 / IVF 多探桶
```
【论文结论】这个形状与三篇实测一致：**候选极少时精确扫描反而更好**（pgvector 那篇说优化器"偏向近似索引扫描，即使精确顺序扫描能在相近延迟下给出完美召回"——那就是反例）、**s 大时后过滤够用**、**中间地带需要内联或分区索引**。

**第 3 步：给"权限过滤"设一条不可协商的规则：必须在候选进入上下文之前完成。**
```
① ACL 过滤用 bitmap/集合预过滤（不是"检索后删"）
② 缓存 key 必须含 tenant/acl 指纹（第 006 期 R1-06）
③ 监控 filtered_out_ratio 与 empty_after_filter_rate（过滤后为空的比例）
```
【我的建议】权限过滤的正确性 > 一切延迟优化。**如果某个优化会让"不可访问的证据"先进入候选集，就不做这个优化。**

### 权衡与坑

- **坑 1：用"库内 benchmark 分数"选过滤策略。** 【论文结论】PostgreSQL 那篇明确说：专用库里的乐观假设在企业级系统里不成立，**系统开销（过滤检查、页访问）会主导**。
- **坑 2：以为"后过滤 + 调大 k'"能救回召回。** 【论文结论】低选择性下 ANN 后过滤召回显著下降；把 k' 调大只是把"漏"换成"慢"，且可能仍不够。
- **坑 3：以为"预过滤总是更安全"。** 选择性极低时预过滤会让 ANN 退化成逐点扫描；且"按谓词建索引"有前置成本。
- **坑 4：只看平均延迟。** 【论文结论】低选择性下会出现**超线性尾延迟放大**，平均延迟看不出来。**必须看 p95/p99。**
- **坑 5：把权限过滤当成性能问题。** 它是**正确性/合规问题**（第 006 期 R1-06）：先检索后删，日志与缓存里已经泄漏过了。
- **坑 6：忽略"召回稳定性"。** 【论文结论】VLDB 的 FVS 教程把目标定成"**在声明式保证下让召回在各查询间稳定**"——**平均召回 0.9 但方差极大**的系统，比"稳定 0.85"更难运维。
- 【我的建议】选型顺序：**量 s 分布 → 规则路由 → 只在规则不够时上学习式规划 → 永远保留"精确扫描"作为兜底**。

### 架构师视角

- **过滤是"索引的一部分"，不是"检索之后的补丁"。** 它的代价必须在**索引设计阶段**就建模（要不要建 bitmap、要不要分区、要不要按维度建子索引）。
- **给"精确扫描兜底"留一个开关**：当 s 极小或近似方法的置信度低时，回退到精确扫描。这是最便宜的正确性保险。
- **观测出口**：`selectivity_dist`（选择性分布）、`filter_check_per_query`（每次查询的过滤检查次数——图方法的最大隐性成本）、`p99_latency_by_selectivity`、`recall_by_selectivity`（**按选择性分桶看召回**，这是最容易被平均值掩盖的）。
- **一句话**：**过滤的正确姿势是"让候选集在进入 ANN 之前就变小"，而不是"事后扔掉算错的东西"。**

## 今日前沿插入

> 只写有实质更新、且能核验来源的内容。

**① "别用 Recall@k 调 ANN"被系统论证（arXiv:2606.04522，2026）**
提出 **1/Ratio@k**（近似比倒数）替代 Recall@k：无需裁判、无需调参；**按下游质量优化可在显著更低算力下达标**；下游指标（标签精度/语义相似度/BERTScore/LLM 打分）**在 Recall@k 大幅下降时仍高度稳定**。
**为什么值得注意**：它直接质疑了几乎所有 ANN 调参流程的默认目标函数。

**② 真实数据库里，"算法最优"会被系统开销推翻（arXiv:2603.23710，2026）**
生产级 PostgreSQL 兼容系统上：最优算法不由距离计算成本决定，**过滤检查、页访问、数据回取同样主导**；**图方法（ACORN/NaviX 一类）的过滤检查次数可达 prohibitive 量级**，常抵消其理论优势。
**为什么值得注意**：这是"benchmark 分数 ≠ 你的系统"的最硬证据。

**③ 三种过滤策略各有明确失效区间，且没有单一赢家（arXiv:2602.11443 / 10.21015/vtse.v14i1.2353）**
前者在 FAISS/Milvus/pgvector 上实测：**Milvus 靠近似/精确混合执行获得更稳召回**；**pgvector 的优化器常选次优计划**（偏向近似索引扫描，即使精确扫描能在相近延迟下完美召回）；**低选择性下 IVFFlat 优于 HNSW**。后者给出质量-尾延迟曲线：精确预过滤准确率最高但尾延迟最大，ANN 后过滤更快但严格过滤下召回显著下降，**自适应路由最稳**。

**④ 过滤负载有"尾延迟非线性放大"（IEEE，2026）**
低选择性过滤会触发**超线性尾延迟放大，即使召回仍然很高**；churn 引起内存与尾延迟震荡；热重启主要受索引重载与缓存预热支配。
**为什么值得注意**：只报平均延迟的 benchmark，系统性地掩盖了这个现象。

**⑤ 路由化成为主流答案（arXiv:2606.19898 / arXiv:2602.17914）**
前者：**没有任何单一过滤 ANN 方法占优，甚至同一数据集同一谓词内最佳方法也随查询变化**；用 3 个特征的路由器在 5 个未见数据集上取得最优召回-QPS 平衡。后者：学习式计划选择相对强基线**最高 4× 加速且召回 ≥90%**。

**趋势观察（非定论）**
2026 年这一块的共识正在从"选一个最好的 ANN 算法"转向"**按查询/选择性路由 + 用下游指标而非 Recall@k 验收 + 把尾延迟当一等指标**"。同时"稳定召回（stable recall）"开始被当作可声明的目标，而不只是平均值。**属趋势观察。**
