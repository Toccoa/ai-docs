## 知识点 1：Grounded Prompt 设计（R5-07）

### 一句话结论

**Grounded Prompt 的核心不是“语气更严厉”，而是“把证据变成可引用的结构化输入，把回答变成可验证的结构化输出”。** 一句“请只根据资料回答”对模型是软约束；**证据编号 + 逐字引用 + 拒答字段**才是硬约束。

### 为什么重要

- 模型有强烈的“参数知识先验”：即使资料里没有，它也可能用自己的记忆补。
- 2026 年的引用研究（arXiv:2607.20527）说明：**“有引用”不等于“引用支持结论”**；提示词必须要求**逐字 quote + claim 级引用**。
- Prompt 是唯一能同时约束“证据使用、引用、拒答、格式”的层；设计不好，前面所有检索工作都会漏掉。

### 核心机制：四段式 Grounded Prompt

```text
[角色] 你是企业制度问答助手，只能使用下方证据回答。
[证据] <E1 source="..." page="..." date="...">原文...</E1>
       <E2 ...>...</E2>
[规则]
  1. 每个结论必须标注 [E#]；quote 必须逐字来自证据。
  2. 证据不足 → 输出 {"abstain": true, "reason": "..."}。
  3. 证据冲突 → 并列呈现，不静默选一个。
  4. 不得使用证据之外的知识。
[输出] 严格 JSON：{answer, claims[], citations[], abstain}
```

### 怎么做

1. **证据编号**：每块带 `E1..En`，并附 `source/page/date`；模型引用 `[E3]`，系统可回查。
2. **逐字 quote 校验**：生成后检查 quote 是否能在对应证据中检索到；不通过则降级/重试。
3. **拒答路径**：显式 `abstain` 字段 + 触发条件（无证据/证据冲突/证据不足）；不要用“我无法回答”这种自由文本。
4. **冲突规则**：要求模型列出冲突来源与时间，而不是选一个；业务侧再决定。
5. **分开“推理”和“交付”**：先自由推理，再按 schema 输出（见 11-29 的 R5-04）。

### 权衡与坑

- **坑 1：只写“不要幻觉”。** 这是愿望，不是约束；必须有引用和拒答结构。
- **坑 2：证据没有编号/来源。** 模型只能泛泛引用“根据资料”，审计无法定位。
- **坑 3：要求“必须回答”。** 这会逼模型在证据不足时编造；要允许 abstain。
- **坑 4：把长 prompt 当更强约束。** 过长的指令会降低遵从率；规则要少而硬。
- 【我的建议】把 Grounded Prompt 当成**接口契约**，不是文案；每条规则都要有对应的自动检查。

### 架构师视角

- Grounded Prompt 是**信任边界**：它决定模型能不能“越过证据”说话。
- 观测出口：`citation_coverage`、`quote_verbatim_rate`、`abstain_rate`、`unsupported_claim_rate`。
- **一句话**：**不要请求模型诚实，要设计一个让它难以不诚实的结构。**

### 自测 3 题

1. 你的 prompt 里，证据有编号和来源吗？模型引用后，你能回查到原文吗？
2. 如果证据不足，你的模型会拒答还是编造？你怎么测？
3. 你的“必须回答”指令，是否在逼模型跨越证据边界？

## 知识点 2：多轮对话改写（R5-08）

### 一句话结论

**多轮改写的目标不是“把句子补完整”，而是“还原用户这一轮真正想检索什么”。** 改写是概率性预处理：**默认关闭、按需触发、与原查询融合**；每轮都改写，既贵又容易把意图改坏。

### 为什么重要

- 多轮对话里，用户会说“那它的有效期呢？”“换成上海的呢？”——省略和指代让原始 query 无法直接检索。
- 但改写也会引入风险：把“上周那版”改成“最新版”，把时间限定抹掉；把“不要包含 X”改丢。
- 2026 年的研究（HYPER、CQC-RAG）都在回答同一个问题：**怎么在补全意图的同时，不引入新的偏差。**

### 核心机制：对话状态 + 条件触发

```text
对话状态：
  resolved_query：当前轮可独立检索的 query
  entities：人物/产品/时间/地点
  constraints：必须满足/必须排除
  last_turn：上一轮 query 与答案

触发改写：
  有指代（它/这个/那版） or 省略（“换成上海呢”） or 话题切换
  → 改写
  否则 → 直接用原 query
```

**两种 2026 思路：**

- **HYPER**：先提出一个暂定答案假设，再围绕“哪些证据能区分候选假设”去检索；适合诊断/排障/选型。
- **CQC-RAG**：生成一组语义等价、句法多样的 query，用**跨查询一致性**过滤证据；适合降低单次改写的偶然错误。

### 怎么做

1. **默认关闭**：只在检测到指代/省略/话题切换时改写；记录 `rewrite_rate`。
2. **保留原查询**：改写 query 与原 query 各检索一次，RRF 融合；**改写不能替换原查询**。
3. **保留约束**：把“不要包含/必须是/截止日期”作为结构化字段带入改写，不让模型自由发挥。
4. **测 `rewrite_delta`**：改写前后 top-10 重叠率、答案变化率、正确率变化；如果改写经常改变答案，先查意图是否被改坏。
5. **多候选择一任务**：试 HYPER 式“先假设、再找区分证据”；普通 FAQ 不要上。

### 权衡与坑

- **坑 1：每轮都改写。** 成本和延迟上升，且简单追问不需要改写。
- **坑 2：改写替换原查询。** 一旦改错，原始意图彻底丢失；必须融合。
- **坑 3：把时间限定改写掉。** “上周那版”不能改成“最新版”；时间/版本要保留。
- **坑 4：多查询一致性=一定正确。** 所有改写可能一起被同一篇误导文档带偏。
- 【我的建议】先把对话状态结构化，再决定要不要改写；没有状态，改写就是猜。

### 架构师视角

- 多轮改写是**意图保真**问题，不是“query 美化”问题。
- 观测出口：`rewrite_rate`、`rewrite_delta`、`entity_preservation_rate`、`constraint_preservation_rate`、`answer_changed_rate`。
- **一句话**：**改写的目标是让检索更懂用户，而不是让 query 更像教科书。**

### 自测 3 题

1. 你的系统每轮都改写吗？触发条件是什么？
2. 改写后 top-10 与原查询重叠多少？如果很低，是补全了意图还是改掉了意图？
3. 对“上周那版政策”这种 query，你会改写成“最新版”还是保留时间限定？为什么？

## 今日前沿插入

**① 引用核查器不可靠，引用评估要“命名仪器”（arXiv:2607.20527，2026-07）。**
不支持引用率随核查器严格度在 **3%–18%** 波动；负类一致性 **0.27–0.30**。→ [精读](../05-前沿资料/2026-12-01-引用忠实度与可追溯.md)

**② 多轮改写从“改写句子”转向“证据假设 + 一致性”（HYPER / CQC-RAG，2026）。**
HYPER 先提暂定答案，再找区分证据；CQC-RAG 用跨查询一致性过滤。两者都强调：**改写不是越多越好，而是越准越好。** → [精读](../05-前沿资料/2026-12-04-多轮对话查询改写.md)

**趋势观察（非定论）**
2026 年 M5 收尾的信号：**上下文工程的终点不是“更长”，而是“更可验证”**——引用可回查、拒答可表达、对话意图可保真。**属趋势观察。**
