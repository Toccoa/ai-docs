## 今日速览

- **R2-04 上下文增强切分**：Contextual Retrieval 是**目前少见的、有明确量化收益且成本可算的切分改进**（top-20 检索失败率 −35%，加 BM25 −49%，再加 rerank −67%）；但它的收益**依赖你做上下文化的那个模型**，并且在不同检索设定下会**方向相反**——所以它是"有条件的强手段"，不是默认开关。
- **R2-05 特殊内容切分**：代码、表格、FAQ、对话这四类内容的正确切法**不是"更小的块"或"更聪明的模型"，而是"换一个切分单元"**——代码按语法单元、表格按行组、FAQ 按问答对、对话按轮次与话题；用通用文本切分器处理它们，是最常见的结构性错误。

## 知识点 1：上下文增强切分（R2-04）

### 一句话结论

Contextual Retrieval 的做法是**在嵌入之前给每个块前置 50–100 token 的"这段在整篇文档里是什么位置/在讲什么"**，然后**同时**用它建向量和 BM25 索引；它的收益是**可量化的**（top-20 失败率 5.7%→3.7%，加 BM25 →2.9%，再加 rerank →1.9%），但代价是**每个块一次 LLM 调用**，且效果**取决于上下文化的质量**。

### 为什么重要

**先看这套方法到底做了什么（避免把它误解成"给块加个标题"）。**

【事实】Anthropic《Introducing Contextual Retrieval》（2024-09-19）给出的定义很具体：把**块级解释性上下文前置到块之前**，再去做嵌入（Contextual Embeddings）**和**建 BM25 索引（Contextual BM25）。示例是：

```
原始块：  "The company's revenue grew by 3% over the previous quarter."
上下文化："This chunk is from an SEC filing on ACME corp's performance in Q2 2023;
          the previous quarter's revenue was $314 million. The company's revenue
          grew by 3% over the previous quarter."
```

注意它补的不是"文档标题"，而是**三类消歧信息**：谁（ACME）、何时（Q2 2023）、前值（$314M）。这三样恰好是孤立块最常缺、而检索最需要的东西——这和第 007 期 R1-07 讲的"父块补齐定义域"是同一个问题，只是解法从"检索时回填"变成了"索引时前置"。

**收益与成本（都可核验）：**
【事实】同一篇报告的数字：**Contextual Embeddings 把 top-20 检索失败率降低 35%（5.7% → 3.7%）**；**再叠加 Contextual BM25 降低 49%（5.7% → 2.9%）**；**再加 rerank 降低 67%**。上下文化文本**通常 50–100 token**，用 Claude 3 Haiku 生成；在"800 token 块 / 8k token 文档 / 50 token 指令 / 100 token 上下文"的假设下，**一次性生成成本约 $1.02 / 百万文档 token**（靠 prompt caching 把整篇文档缓存住，避免每块重复传全文）。
*（标注：这是**厂商工程博客**，不是同行评审论文。数字可信度较高（有附录与方法说明），但请把它当"该团队在自建基准上的结果"，不要当普适定律。）*

**再看它的边界——两个独立的反面/限定证据：**

**限定 1：上下文化的质量是瓶颈，不是检索器。【论文结论】** CRAwLeR（arXiv:2606.21676，法律交叉引用场景）把"Anthropic 风格的上下文化"作为强基线，结果显示：最好的 **Recall@10 只有 55%（丹麦语）/ 59%（波兰语）**；消融与失败分析**把剩余差距归因于"做上下文化的那个 LLM"，而不是检索器**；并且**即使目标块进了 top-10，被标注的上下文块经常排在它前面**。→ 这句话的含义很尖锐：**给块补上下文会引入新的"看起来更相关"的干扰项**。

**限定 2：在不同检索设定下方向相反。【论文结论】** Zhou 等（arXiv:2602.16974，*Beyond Chunk-Then-Embed*）在统一框架里复现比较：**上下文化切分提升 in-corpus 检索，但降低 in-document 检索（needle-in-a-haystack）**。→ 如果你的核心场景是"在一份长文档里精确定位某条款"，**上下文化可能帮倒忙**。

**限定 3：上下文化 vs 晚切分，各有明确短板。【论文结论】** Merola & Singh（arXiv:2504.19754，ECIR 2025 workshop）：**contextual retrieval 更能保住语义连贯但计算开销更大；late chunking 效率更高但倾向于牺牲相关性与完整性**。

**限定 4：跨文档合成能超过它，但代价更高。【论文结论】** CDTA（arXiv:2601.05265，单作者预印本）：在多跳 HotpotQA 上 faithfulness **0.93**，对比 contextual retrieval **0.83**、semantic **0.78**；代价是索引成本更高。

### 核心机制 / 数据流

**四跳流程（把它当成一个"离线预处理 + 双索引"的工程）：**

```
① 切分（先按 R2-01/R2-02 定好边界与大小）
② 逐块上下文化：
   输入 = 整篇文档（走 prompt cache）+ 该块 + 固定指令
   输出 = 50–100 token 的定位说明（谁/何时/在哪一节/在讲什么）
③ 双索引：
   - 向量索引：embed(context + "\n" + chunk)
   - BM25 索引：对 context + chunk 建词项统计
   （注意：两者都要用"上下文化后的文本"，否则融合会错位）
④ 生成时区分"上下文"与"块"：
   prompt 里显式标注哪段是 situating context、哪段是原文，
   避免模型把"这段在讲什么"当成事实陈述去引用
```

**第 ④ 步是很多人漏掉的：** 【事实】Anthropic 原文明确提醒"response generation may be improved by passing it the contextualized chunk and **distinguishing between what is context and what is the chunk**"。上下文是"元信息"，不是"证据"——如果混在一起，引用会指向一段并非原文的说明。

**成本模型（写进你的 ADR）：**
```
一次性成本 ≈ 文档 token 数 × 单价（约 $1.02 / 百万 token，按上述假设）
增量成本   ≈ 每块一次 LLM 调用（块数 ≈ 语料 token / 块大小）
维护成本   ≈ 每次重索引都要重跑（→ 必须绑 CHUNKER_VERSION，见第 008 期）
```
【我的建议】上下文化成本**集中在索引期、不在查询期**，所以它对**高 QPS、低延迟**的系统特别友好；但对**频繁变更**的语料不友好（每次更新都要重算上下文）。

### 怎么做（3 步）

**第 1 步：先做一个"消歧缺口"测试，判断你到底需不需要它。**
```
取 30 个真实问题，找到它们的 gold chunk；
把 gold chunk **单独**（不带标题、不带邻居）喂给模型，问"这段在说什么、属于谁、什么时间"：
  - 若模型能答对 ≥ 90%  → 你的块本来就自包含，上下文化收益有限
  - 若大量答错（尤其"属于哪个产品/哪一版/哪一年"）→ 正是上下文化的靶心
```
【我的建议】这个测试 20 分钟能做完，比直接跑一次全量上下文化便宜三个数量级。

**第 2 步：实现"带缓存 + 可审计"的上下文化。**

```python
CTX_PROMPT = """<document>{doc}</document>
Here is the chunk we want to situate within the whole document
<chunk>{chunk}</chunk>
Please give a short succinct context to situate this chunk within the overall
document for the purposes of improving search retrieval of the chunk.
Answer only with the succinct context and nothing else."""

def contextualize(doc_text, chunk, llm, max_ctx_tokens=100):
    ctx = llm.generate(CTX_PROMPT.format(doc=doc_text, chunk=chunk),  # doc 走 prompt cache
                       max_tokens=max_ctx_tokens, temperature=0)
    ctx = ctx.strip()
    # 质量门：太短/太长/含"这是"等空话 → 丢弃，退回原块
    if len(ctx) < 15 or len(ctx) > max_ctx_tokens * 6:
        return chunk, None
    return f"{ctx}\n\n{chunk}", ctx

# 双索引都用同一份"上下文化文本"
embed_text = contextual_text
bm25_text  = contextual_text
# 元数据里存原块，供引用与展示
payload = {"raw_text": chunk, "ctx": ctx, "chunker_version": CHUNKER_VERSION}
```

**第 3 步：验收看三件事，而不是一件。**

| 看什么 | 为什么 |
|---|---|
| `retrieval_fail@20`（top-20 检索失败率，越低越好） | 这是它的主战场：5.7% → 3.7% / 2.9% |
| `context_block_outranks_target`（上下文块挤掉目标块的比例） | CRAwLeR 揭示的副作用，必须单独盯 |
| `ctx_gen_fail_rate`（上下文生成被质量门丢弃的比例） | 成本与质量的隐性指标 |

### 权衡与坑

- **坑 1：把上下文当证据。** 生成时若不区分"元信息/原文"，引用会指向一段模型生成的说明。**必须在 prompt 里显式分段标注。**
- **坑 2：只给向量索引加、忘了 BM25。** 【事实】Anthropic 的数据里，**35%（只向量）→ 49%（加 BM25）** 是关键增量；只做一半等于放弃一半收益。
- **坑 3：无脑全量重跑。** 上下文化是**索引期**成本，改块大小/改切分策略都会触发全量重算。**必须和 `CHUNKER_VERSION`、影子代次（第 008 期）绑定，做灰度。**
- **坑 4：以为对所有检索设定都有效。** 【论文结论】Zhou 等：in-corpus 变好、**in-document 变差**。做"单文档精确定位"的产品要单独验证。
- **坑 5：忽视它带来的排序干扰。** 【论文结论】CRAwLeR 显示上下文块会排到目标块前面。**这意味着你需要一个新的观测指标，而不是只看总召回。**
- **坑 6：上下文写得越长越好。** 【事实】原文说 50–100 token 即可；上下文越长，块嵌入被"元信息"稀释的风险越大。**我的建议：设硬上限，超了就走质量门丢弃。**
- 【我的建议】判断顺序：**先做"消歧缺口"测试 → 再做 BM25 混检 → 再考虑上下文化 → 最后才考虑跨文档合成（CDTA）**。每一步都用 recall 与"挤占率"两个数验收。

### 架构师视角

- R2-04 是 M2 里**唯一一个"用 LLM 换检索质量"的手段**，所以它天然要回答两个问题：**值不值（recall 增量 vs token 成本）**、**稳不稳（上下文质量是否可审计）**。前者用第 003 期的成本模型算，后者用 `ctx_gen_fail_rate` 与人工抽查 20 条来保证。
- **它是"索引期一次性投资"**，与 R2-03（查询期回填父块）形成互补：一个把语境固化进索引，一个在查询时动态补。**两者不必二选一，但别同时无脑上**——先把一个做对。
- **与 R1-06 元数据的接口**：上下文化的产物本质上是"自动生成的元数据"。**建议把它同时写进 `ctx` 字段**，这样即使将来不用它做嵌入，也能用于展示、过滤与归因。

## 知识点 2：特殊内容切分（R2-05）

### 一句话结论

代码、表格、FAQ、对话这四类内容，**通用文本切分器一定会切错**——不是参数没调好，而是**切分单元本身就不同**：代码的单元是语法节点，表格是行组+表头，FAQ 是问答对，对话是轮次/话题段；**换单元，而不是换参数。**

### 为什么重要

**先看代码：一个反直觉的硬结论。**

【论文结论】Wu, Gong, Jahangirova, Zhang（arXiv:2605.04763，2026）做了 864 组受控实验（4 种切分策略 × 4 检索器 × 5 生成器 × 9 组参数 × 2 个基准 RepoEval / CrossCodeEval），结论有两条特别值得记住：

1. **"按函数切"是最差的策略**：在 RepoEval 上比其它策略低 **3.57–5.64 个百分点**（Cliff's delta = −1.0，即几乎每个样本都更差）；而且在所有检索器-生成器组合下都成立。**Function chunking 在成本-质量 Pareto 前沿上从不出现。**
2. **真正的主导参数是"跨文件上下文长度"，不是块大小**：从 **2,048 提到 8,192 token 带来最多 4.2 个百分点**提升，而**块大小的影响更弱且非单调**。

第 1 条为什么反直觉？因为"按函数切"听起来最符合语义边界。但它的失败机制很清楚：**函数体往往依赖同文件的类型定义、导入、全局常量**——按函数切会把"函数"和"它能编译的前提"分开，得到一个"语义完整但不可用"的块。这也解释了第 2 条：**跨文件/跨块的上文长度比块本身多细更重要**。

对照另一条证据：【论文结论】cAST（Findings of EMNLP 2025，arXiv:2506.15655）用"**递归拆大 AST 节点 + 合并兄弟节点**"的方式，在 RepoEval 检索上 **Recall@5 +4.3 点**、SWE-bench 生成上 **Pass@1 +2.67 点**。注意它和"按函数切"的区别：cAST 是**先按大小约束递归下切、再把兄弟合并成自包含单元**，而不是机械地一个函数一块。

【论文结论】另外两条工程侧证据：SemChunk-C（arXiv:2606.23697）用 **17M–150M 参数的小编码器**做 C 系语言的**边界识别 + 功能分类**，报告边界准确率与语义连贯性可"匹配或超过更大的代码 LLM 切分器"；*Beyond More Context*（arXiv:2510.06606，ASE 2025 挑战赛）用**静态分析的块级检索**比最好的"文件级检索"再高 **6%**、比无上下文基线高 **16%**（Python），并强调**上下文顺序**同样重要。

**再看表格、FAQ、对话——它们各自有明确的"正确单元"：**

| 内容类型 | 错误切法 | 正确单元 | 为什么 |
|---|---|---|---|
| 代码 | 固定行数/按函数 | AST 节点（递归下切 + 兄弟合并） | 函数缺依赖不可用；cAST 证据 |
| 表格 | 按字符/按行 | **整表（小表）或行组 + 重复表头** | 第 005 期 R1-03：span 与多级表头丢失；LTEM 实验显示格式表达力决定准确率 |
| FAQ | 按段落/按字数 | **一问一答对**（question + answer 同块） | 拆开则问题与答案分离，检索命中问题却给不出答案 |
| 对话 | 按 token 滑窗 | **按轮次 + 话题段**，并剥离重复历史 | 第 006 期：多轮对话累计历史 byte-exact 冗余高达 **80.34%**（50+ 轮达 96%+） |

【论文结论】FAQ/结构化问答有直接证据：Maratov & Cankurt（DOI 10.47344/7we5dg32）在高校问答系统里比较"标准切分 vs **按行切（row-based）**"，人工评估认为**按行切在结构化数据集上给出更连贯、更相关的上下文**。

### 核心机制 / 数据流

**统一原则：先判类型，再选单元，最后才谈大小。**

```
① 类型判定（在解析产物上做，不靠猜）
   块级 type ∈ {code, table, faq_pair, dialogue_turn, prose}
   来源：R1-01 的 IR（type 字段）+ 少量规则（代码块标记、表格结构、Q/A 标记）

② 按类型选单元
   code      → AST（tree-sitter 等）：递归下切到 ≤ 目标 token，再合并兄弟
   table     → 小表整表；大表按行组切，每块重复 caption + 表头 + 单位
   faq_pair  → question + answer 必须同块；多个短 FAQ 可合并到目标大小，但不可拆对
   dialogue  → 按轮次边界切；同一话题的多轮合并；重复历史先按 R1-05 去重
   prose     → 回到 R2-01/R2-02 的常规策略

③ 统一到同一套"块契约"（否则下游无法处理）
   每块都要有：type、section_path、page/bbox、parent_id、source_hash、CHUNKER_VERSION

④ 分别评估（这是最容易漏的一步）
   按 type 分层看 recall，而不是只看总体
```

**为什么第 ④ 步关键？** 因为不同类型的失败会被平均值掩盖：代码块 recall 0.5、正文 0.9，总体可能是 0.85 —— 看起来"还不错"，但你的代码问答其实已经废了。这和第 002 期"平均分会掩盖分层问题"是同一条纪律。

### 怎么做（3 步）

**第 1 步：先量"类型分布"与"类型分层 recall"。**
```
对 200 个文档统计 type 分布：
  code / table / faq_pair / dialogue / prose 各占多少？
对每类各取 20 个问题，分别测 recall@5：
  若某类 recall 明显低于 prose（>15pp），它就是你的切分短板
```
【我的建议】大多数团队会发现短板在**表格**与**代码**——正好是前几期反复出现的两个坑（第 005 期、第 007 期）。

**第 2 步：给代码上 AST 切分（最小实现）。**

```python
import tree_sitter_languages  # 或 tree-sitter + 各语言 grammar

def chunk_code(src: str, lang: str, target=400, max_tokens=800):
    parser = tree_sitter_languages.get_parser(lang)
    tree = parser.parse(src.encode())
    def walk(node):
        text = src[node.start_byte:node.end_byte]
        n = count_tokens(text)
        if n <= target:
            return [text]
        kids = [c for c in node.children if c.type not in ("comment",)]
        if not kids:
            return [text[: text.rfind("\n")]]        # 无子节点可切 → 按行兜底
        out = []
        for c in kids:
            out += walk(c)
        return merge_siblings(out, max_tokens)        # 关键：合并兄弟，保证自包含
    return [c for c in walk(tree.root_node) if c.strip()]
```
两个要点：**递归下切**（不是"一个函数一块"）、**合并兄弟**（让块自包含）。cAST 的收益就来自这两点。

**第 3 步：给 FAQ 与对话各加一条硬规则。**
```
FAQ：断言每个 chunk 满足 question_regex 命中 且 answer 非空；
     不满足则视为切错，回退到"按对切"。
对话：先按 turn 边界切，再按"话题变化"合并；
     合并前先做 byte-exact 去重（第 006 期），否则你会把重复历史翻倍塞进上下文。
```

### 权衡与坑

- **坑 1："按函数切"听起来对、实测最差。** 【论文结论】Wu 等的 864 组实验里它比其它策略低 3.57–5.64pp。**别用直觉代替实验。**
- **坑 2：只优化块大小，忽略跨块上下文长度。** 【论文结论】同一研究：**跨文件上下文 2k→8k 带来最多 4.2pp**，而块大小影响更弱且非单调。**在代码场景，"多给点相关文件"比"把块切得更细"更有效。**
- **坑 3：表格按行切却不重复表头。** 第 005 期已讲：没有表头的行组等于没有列名的数字。**每块必须带 caption + 表头 + 单位。**
- **坑 4：FAQ 把 Q 和 A 拆开。** 检索命中问题块，但答案块没被召回 → 模型只能瞎编。**问答对是不可分割的最小单元。**
- **坑 5：对话按 token 滑窗。** 会把一个回答切成两半，还会重复历史。**先按轮次，再按话题，最后去重。**
- **坑 6：只按总体指标评估。** 必须按 type 分层（见上）。
- 【我的建议】优先级：**表格 → 代码 → FAQ → 对话**。前两者对准确率的伤害最大，后两者更多是成本与一致性。

### 架构师视角

- **R2-05 的本质是"承认内容是多态的"。** 一条管线处理五类内容，必然有一类被牺牲。正确做法是**一个统一契约 + 多个切分器**（和第 008 期"一个接口 + 多实现 + 回归集"同构）。
- **切分器要能被独立灰度**：`chunker_version = {code: "ast-v1", table: "rowgroup-v1", faq: "pair-v1"}`。这样你改代码切分时不必重跑表格。
- **观测出口**：`recall_by_type`（分层召回）、`chunk_type_dist`（类型分布漂移）、`code_chunk_compile_rate`（代码块能否解析——一个便宜且强的质量信号）、`faq_pair_integrity`（Q/A 同块率）。
- **一个可以立刻用的体检**：**把每个代码块单独拿去 parse 一次**。解析失败率高说明你的代码块被切断了语法结构——这比任何离线评测都更快发现问题。

### 自测 3 题

1. 你的代码块能单独解析通过吗？如果不能，你现在是按什么切的？改成 AST 递归+兄弟合并需要多少工作量？
2. 你的 FAQ 里，问题和答案在同一个 chunk 吗？如果不在，检索命中问题时模型看到的是什么？
3. 如果只能按类型改进一类内容，你会选表格还是代码？用你自己的分层 recall 数据回答，而不是直觉。

## 今日前沿插入

> 只写有实质更新、且能核验来源的内容。

**① 上下文增强切分有了"可算账"的基线（Anthropic，2024-09-19）**
Contextual Embeddings 让 top-20 失败率 5.7%→3.7%（−35%），加 Contextual BM25 →2.9%（−49%），再加 rerank −67%；上下文 50–100 token，约 **$1.02 / 百万文档 token**（靠 prompt caching）。
**为什么值得注意**：它是少数把"方法 + 数字 + 成本"一起给的工程报告。**但属厂商博客，按"该团队自建基准"引用。**

**② 上下文化不是万灵药，副作用被量化了（arXiv:2606.21676 / arXiv:2602.16974）**
CRAwLeR：Anthropic 风格上下文化的强基线在法律交叉引用场景 Recall@10 只有 **55%/59%**，**残差归因于做上下文化的 LLM**，且上下文块常把目标块挤出前排；Zhou 等：上下文化**提升语料检索、降低文档内检索**。
**为什么值得注意**：这两条给了你"什么情况下不该上"的判据。

**③ 代码切分被大规模证伪了一个常识（arXiv:2605.04763，2026）**
864 组实验：**按函数切比其它策略低 3.57–5.64pp**（Cliff's delta=−1.0），**跨文件上下文长度（2k→8k，最多 +4.2pp）才是主导参数**，块大小影响更弱且非单调。
**为什么值得注意**：它直接推翻"按语义单元切就一定好"的直觉——**语义完整 ≠ 可用**。

**④ 小模型也能做代码边界切分（arXiv:2606.23697）**
SemChunk-C 用 **17M–150M** 参数编码器做 C 系语言的边界识别 + 功能分类，报告可匹配或超过更大的代码 LLM 切分器。
**为什么值得注意**：如果你不想为切分调用大模型，这是一条成本可控的路。

**趋势观察（非定论）**
2026 年的切分讨论明显在从"通用最优参数"转向"**按内容类型分治 + 按查询条件决策**"（R2-03 的条件式扩张、今天的按类型切分器）。同时"切分策略"正在被当作**发布对象**（版本化 + 灰度 + 可回滚）而不是一次性脚本。**属趋势观察。**
