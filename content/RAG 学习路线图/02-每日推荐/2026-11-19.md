## 知识点 1：切分评估（R2-06）

### 一句话结论

**端到端指标测不出切分好坏**，因为大多数 QA 基准的"证据太稀疏"（一个问题的答案往往只靠一句话，切分随便切都能命中）；要评切分，必须用**内禀指标（块是否自包含、是否完整、是否守尺寸）+ 分层召回（按问题类型/内容类型）+ 一个证据密集的专用评测集**。

### 为什么重要

**先看"为什么端到端测不出来"——这是有明确诊断的。**

【论文结论】HiChunk/HiCBench（arXiv:2509.11552）的第一步就是分析"**为什么现有 RAG 评测基准不足以评估文档切分质量**"，结论是**证据稀疏（evidence sparsity）**：多数基准里，一个问题的证据集中在一两句话上，无论你怎么切，总有一块能命中，于是切分策略之间的差异被抹平了。他们的对策是**手工标注多层级切分点 + 合成"证据密集"的 QA 对（答案需要多段证据）+ 标注证据来源**，再配一个 Auto-Merge 检索算法。
*> 这条对你的直接含义：如果你现在用一套"一句话答案"的 QA 集去对比两种切分策略，发现"差不多"，**很可能是你的评测集测不出来，而不是切分真的没差别。***

**再看"能不能不依赖下游、直接评切分"——可以，而且有效。**

【论文结论】*Adaptive Chunking*（arXiv:2603.25333）提出五个**内禀的、基于文档本身**的切分质量指标：
- **References Completeness（RC）**：块内被引用的实体/引用是否都在块内（指代完整）；
- **Intrachunk Cohesion（ICC）**：块内凝聚度；
- **Document Contextual Coherence（DCC）**：块与整篇文档的语境一致性；
- **Block Integrity（BI）**：块完整性（是否被硬切断）；
- **Size Compliance（SC）**：尺寸合规。

并用这套指标做**按文档选择切分策略**的"自适应切分"。报告的结果是：**不改模型、不改 prompt**，答案正确率从 **62–64% 提到 72%**，成功回答的问题数从 **49 提到 65（+30% 以上）**。
*> 这条的意义：**切分质量可以脱离下游答案被测量**，而且"按文档选策略"比"全局选一个策略"更好。*

**第三条：评估必须"分层"，否则平均值会骗你。**
这一点在第 010 期已经埋下（按 type 分层 recall），这里补上它的方法论理由：【论文结论】Zhou 等（arXiv:2602.16974）在统一框架下比较时发现，**同一策略在 in-corpus 与 in-document 两种检索设定下方向相反**（上下文化提升前者、降低后者）。→ **一个总分必然掩盖方向相反的两种效应。**

### 核心机制 / 数据流

**三层评估体系（我建议的最小可用形态）：**

```
第一层：内禀指标（不看下游，快、便宜、可自动化）
   - 块自包含：块内指代是否有先行词（用规则或小模型判）
   - 块完整性：是否在句子/结构边界处结束
   - 尺寸合规：块长分布是否落在目标区间
   - 覆盖率：原文被覆盖的比例（防止切分"丢内容"）

第二层：分层召回（看检索，不看生成）
   - recall@k 按「问题类型」（事实/多跳/摘要/无答案）分层
   - recall@k 按「内容类型」（正文/表格/代码/FAQ）分层
   - 额外看：答案是否完整落在**单一**块内（boundary_intact_rate）

第三层：证据密集端到端（少量、精挑）
   - 30–50 条"必须多段证据才能答"的问题（对齐 HiCBench 的思路）
   - 看 faithfulness 与引用正确率
```

**为什么第一层最重要：** 它是**唯一能在"换嵌入模型/换生成模型"之前就先做一遍**的评估。等你把下游全跑完才发现切分有问题，返工成本已经是索引重建级别。

### 怎么做（3 步）

**第 1 步：先量"边界完整性"，这是最便宜也最能暴露问题的一个数。**

```python
def boundary_intact_rate(chunks):
    """答案被切断的比例：块尾不是句末、或块首缺主语 → 记为可疑"""
    bad = 0
    for c in chunks:
        t = c.text.strip()
        tail_ok = t.endswith(("。", "！", "？", ".", "!", "?", "：", ":"))
        head_ok = not t.startswith(("但", "而", "因此", "此外", "该", "这", "其", "并且"))
        if not (tail_ok and head_ok):
            bad += 1
    return 1 - bad / len(chunks)
```
【我的建议】这个数低于 0.85 就说明你的切分在"硬切"，先修边界，再谈其它。

**第 2 步：建"内禀指标"的自动化检查（对齐 RC / BI / SC 的思路）。**

```
对每个块检查：
① 覆盖：原文被所有块覆盖的比例 ≥ 0.99（防丢内容）
② 完整：块内出现的代词/指代（"该条款""上述""其"）是否有先行词
③ 尺寸：95 分位块长 ≤ 目标上限的 1.5 倍（防超大块）
④ 重复：块间 byte-exact 重复率（对齐 R1-05 的 ρ）
```
这四条都能写成纯规则 + 少量正则，不依赖 LLM，**可以进 CI**。

**第 3 步：造一个"证据密集"的小评测集（这是关键投资）。**

```
取 30–50 个真实问题，改造为「必须两段以上证据才能答」的形式：
  原题：Q3 营收是多少？                 （单段证据 → 测不出切分差异）
  改造：Q3 营收相对 Q2 的变化，是否符合激励条款的触发条件？
        （需要「Q3 数据 + Q2 数据 + 条款文本」三段证据）
标注：每题的 gold_evidence_spans（可跨块）
指标：evidence_coverage@k（top-k 覆盖了几段 gold evidence）
```
【论文结论】HiCBench 的构造方式正是"合成证据密集的 QA 对 + 标注证据来源"，目的就是**让切分差异显形**。你不必复现它的规模，20–30 条就足以区分策略。

### 权衡与坑

- **坑 1：用"一句话答案"的 QA 集评估切分。** 证据稀疏会把差异抹平（HiCBench 的核心诊断）。**你可能因此得出"切分不重要"的错误结论。**
- **坑 2：只看总分。** 必须按问题类型、内容类型分层（Zhou 等的相反结论就是最好的反例）。
- **坑 3：只测"找到没有"，不测"完整不完整"。** 一个块包含答案的一半，recall 依然算命中。**必须单独看 `boundary_intact_rate` 与"答案是否完整落在单块内"。**
- **坑 4：内禀指标当成绝对真理。** RC/ICC/DCC/BI/SC 是"互相补充的一组"，不是单一分数；而且它们与下游效果**相关但不必然等价**。**用它们做排序与筛查，不用它们做最终验收。**
- **坑 5：换模型后不重测切分。** 块大小最优值随嵌入模型漂移（第 009 期 Bhat 等），**切分评估必须跟着模型走**。
- 【我的建议】把"内禀指标 + 分层召回"做成 CI 里的两个门：任何切分/嵌入变更都必须过这两关，端到端评估留到发版前。

### 架构师视角

- **R2-06 是 M2 的方法论收口**：前面五点（策略、大小、父子、增强、特殊内容）都在"做"，这一点在"验"。**没有它，M2 的所有选择都只是偏好。**
- **评估集是资产，不是脚本。** 那个 20–30 条的"证据密集集"会跟你走完整个项目周期，它的价值远高于任何一次参数调优。
- **观测出口**：`boundary_intact_rate`、`evidence_coverage@k`、`recall_by_type`、`chunk_size_p95`、`coverage_ratio`（原文覆盖率）。
- **一个立刻可用的判断**：如果你换了三种切分策略而端到端指标几乎不动——**先怀疑评测集，再怀疑结论。**

### 自测 3 题

1. 你的评测集里，有多少题是"一句话就能答"的？如果超过一半，你用它评估切分策略能得到什么结论？
2. `recall@5` 命中了含答案的块，但答案被切成两半——这个"命中"对生成有用吗？你应该加哪个指标才能发现它？
3. 如果只能给切分加一个自动化门禁，你选"内禀指标"还是"端到端 faithfulness"？为什么？

## 知识点 2：BM25 与稀疏检索（R3-01）

### 一句话结论

BM25 的价值不在"它能替代向量"，而在**它擅长向量不擅长的两类查询：精确词项（编号、错误码、专有名词）与需要严格满足属性约束的查询**；2026 年的复现研究给出了极端对照——同一个系统，在"语义捷径"型基准上稠密检索领先一倍，在"约束满足"型基准上**词汇检索反超到 0.96，而稠密检索崩到 0.02**。

### 为什么重要

**证据一：约束型查询上，稠密检索会崩，词汇检索会赢。**

【论文结论】*Reproducing Complex Set-Compositional Information Retrieval*（arXiv:2605.03824）在 QUEST 与新建的 **LIMIT+**（相关性取决于**任意属性谓词与约束满足**，而不是预训练知识）上做了对比：
- 在 QUEST 上，最好的神经检索器 Recall@100 **>0.41**，BM25 **0.20** —— 稠密检索确实领先一倍多；
- **但增益不能迁移到 LIMIT+**：最强的 QUEST 方法从 **Recall@100 ≈0.42 崩到 0.02 以下**，而**经典词汇检索升到 ~0.96**；
- 按组合深度分层：**代数稀疏与词汇方法更稳定，稠密方法崩塌**。

这句话的重量：**稠密检索的优势很大程度上依赖"语义捷径"**（即预训练里见过类似语义模式）。一旦查询要求"满足 A 且排除 B 且等于 C"这种字面约束，**它没有可靠的机制去满足**，而倒排索引有。

**证据二：BM25 在很多真实域里就是强基线，不是陪跑。**

【论文结论】*Assessing the Performance Gap Between Lexical and Semantic Models*（arXiv:2506.12895，CJEU 法律段落检索）：
- **BM25 是强基线，在 7 个指标中有 4 个超过现成的稠密模型**；
- 在**更少重复、更长查询**的场景里，BM25 优于稠密模型；
- 但**在领域数据上微调过的稠密模型，在多数指标上反超 BM25**。

→ 结论不是"BM25 更好"，而是：**"用现成稠密模型替换 BM25" 这个动作，在很多域里没有收益；真正的收益来自领域微调或混合。**

**证据三：稀疏检索也在进化，但代价是算力。**

【论文结论】*Efficiency and Effectiveness of SPLADE Models on Billion-Scale Web Document Title*（arXiv:2511.22263）：在千万到十亿级语料上比较 BM25 / SPLADE / Expanded-SPLADE：**SPLADE 系列检索效果优于 BM25（尤其复杂查询），但计算成本更高**；引入**文档中心剪枝、top-k 查询词选择、带词阈值的布尔查询**可显著降本；**Expanded-SPLADE 在效果与效率之间平衡最好**。

**证据四：混合检索的"效率账"必须算清。**
【数据点】一项 Cranfield 对比（Zenodo 10.5281/zenodo.18221719）：混合（BM25 + 稠密 + RRF + cross-encoder rerank）在 P@10 上 **+41%**、R@20 **+67%**；但 **BM25 快约 800 倍**（15.3ms vs 12.4s 平均延迟）。*（单一数据集、绝对分数很低，看相对差与延迟比即可。）*

### 核心机制 / 数据流

**BM25 到底在算什么（一句话版）：**
```
score(q, d) = Σ_{t∈q} IDF(t) · [ tf(t,d)·(k1+1) ] / [ tf(t,d) + k1·(1 − b + b·|d|/avgdl) ]
```
三个可调旋钮，含义比数值重要：

| 参数 | 作用 | 调大的后果 | 常见起点 |
|---|---|---|---|
| `k1` | 词频饱和速度 | 词频影响更持久（长文档更吃香） | 1.2–2.0 |
| `b` | 文档长度归一化强度 | 更惩罚长文档 | 0.5–0.75（长文档差异大的语料往下调） |
| `IDF` | 词项稀有度（由语料决定） | —— | 由语料统计决定，**模板文本会把 IDF 压平**（第 006 期 R1-05） |

**为什么它对"编号/错误码"特别有效：** `TS-999` 这种 token 在稠密空间里没有稳定的语义邻域，但在倒排索引里是**精确匹配**——一次查表就命中。这正是第 003 期 R0-05 路由表里"精确匹配走 BM25/关键词"的机制依据。

**稀疏检索的三个档位（选型用）：**

| 档位 | 代表 | 效果 | 成本 | 何时用 |
|---|---|---|---|---|
| 经典词汇 | BM25 | 强基线，约束型查询稳 | 极低（毫秒级） | **默认必上** |
| 学习型稀疏 | SPLADE / uniCOIL / DeepImpact | 复杂查询更好 | 中（倒排更大、查询更慢） | 语义缺口明显但又要可解释 |
| 扩张型稀疏 | Expanded-SPLADE | 大规模上平衡最好 | 中高（需剪枝） | 亿级语料 + 复杂查询 |

### 怎么做（3 步）

**第 1 步：先证明"你的场景需不需要 BM25"，用一个查询分层实验。**
```
把你的真实 query 分四层各取 30 条：
  A 精确词项（编号、错误码、人名、型号）
  B 约束满足（"满足X但不含Y""等于/不等于/区间"）
  C 语义模糊（概念解释、同义改写）
  D 多跳/综合
分别测：BM25-only / dense-only / hybrid(RRF) 的 recall@10
```
【我的建议】你大概率会看到 **A、B 两档 BM25 显著更好，C 档 dense 更好**——这就是你"必须做混合"的证据，也告诉你融合权重该偏向谁。

**第 2 步：混合检索的最小实现（RRF，无需调权重）。**

```python
def rrf_fuse(runs: dict[str, list[str]], k: int = 60) -> list[str]:
    """runs: {'bm25': [doc_id...], 'dense': [doc_id...]}"""
    score = {}
    for name, ranked in runs.items():
        for rank, doc_id in enumerate(ranked, start=1):
            score[doc_id] = score.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(score, key=score.get, reverse=True)

# 用法：两路各取 top-50 → RRF → 取 top-20 → 交给 rerank
fused = rrf_fuse({"bm25": bm25.search(q, 50), "dense": dense.search(q, 50)})[:20]
```
**为什么用 RRF 而不是加权分数：** BM25 分数与余弦相似度**量纲不同**，直接加权需要归一化，而归一化本身会引入不稳定性。RRF 只用**排名**，天然免疫量纲问题——这也是第 009 期"融合"话题的工程落点。

**第 3 步：给 BM25 做三件"卫生"工作（不做就等于白上）。**
```
① 规范化：统一大小写策略、处理连字符/下划线（TS-999 / TS999 / ts_999 应能互相命中）
② 去模板：先按 R1-05 剥掉页眉页脚/法务段落，否则 IDF 被压平
③ 分词：中文要专门处理（字符 n-gram 或词典分词），英文保留编号完整性
```
【我的建议】第 ① 条最容易被忽略：**产品编号/错误码的写法变体**是 BM25 在真实业务里"看起来失效"的头号原因。

### 权衡与坑

- **坑 1：以为"上了向量就可以去掉 BM25"。** 【论文结论】LIMIT+ 上稠密检索从 0.42 崩到 0.02，而词汇检索到 0.96。**去掉 BM25 是把一类查询直接判死。**
- **坑 2：以为"BM25 一定要被替换"。** 【论文结论】CJEU 研究里 BM25 在 7 个指标中 4 个超过现成稠密模型。**"换模型"不等于"变好"，领域微调才是真正有效的动作。**
- **坑 3：把 BM25 分数和余弦相似度直接加权。** 量纲不同，必须先归一化或用 RRF。**直接加权是最常见的静默 bug。**
- **坑 4：不调 `k1`/`b` 就断言"BM25 不行"。** 长文档差异大的语料，`b` 该往下调；短文本语料（标题、FAQ）表现与长文档完全不同。
- **坑 5：忘了 IDF 会被模板文本压平。** 这是 R1-05 与 R3-01 的交点：**清洗没做好，BM25 一定表现差**，而你可能会误判成"BM25 过时了"。
- **坑 6：忽略延迟账。** 混合 + rerank 的延迟可能是纯 BM25 的数百倍（上面的 800× 数据点）。**先确认你的 SLO 撑不撑得住。**
- 【我的建议】BM25 的正确位置是**"必上的第一路召回"**，而不是"过渡方案"。它的成本近乎为零，收益集中在最难伪装的查询类型上。

### 架构师视角

- **R3-01 是 M3 的地基**：后面 R3-03（混合与融合）、R3-10（rerank）、R3-11（去重与多样性）都建立在"两路召回各自擅长什么"这个判断上。**先把这个判断用你自己的分层实验坐实。**
- **BM25 是"可解释性"的来源**：命中是因为词项匹配，你能向用户解释"因为包含 TS-999"。稠密检索给不出这种解释。**在合规/审计场景里，这一点本身就是选型理由。**
- **观测出口**：`bm25_only_hit_rate`（仅 BM25 命中的比例——这个数越高说明你越不能去掉它）、`dense_only_hit_rate`、`fusion_gain`（融合相对单路的 recall 增量）、`p95_retrieval_latency` 分路。
- **一句话**：如果 `bm25_only_hit_rate` 高于 10%，你的系统里 BM25 就不是"可选组件"，而是**承重墙**。

### 自测 3 题

1. 你的查询里，有多少是"精确词项"或"约束满足"型？如果没有分层统计过，你有什么依据判断可以不要 BM25？
2. 你把 BM25 分数和向量相似度直接加权了吗？如果是，你怎么保证权重在两个不同量纲上仍然有意义？
3. 如果 `bm25_only_hit_rate = 18%`，你会把它解读成"BM25 很重要"还是"稠密模型不行"？这两种解读会导致什么不同的动作？

## 今日前沿插入

> 只写有实质更新、且能核验来源的内容。

**① 混合检索的优势被"证明是有条件的"（arXiv:2605.03824，2026）**
在 QUEST 上神经检索 Recall@100 >0.41 vs BM25 0.20；但在约束满足型基准 LIMIT+ 上，**最强神经方法从 0.42 崩到 <0.02，而词汇检索升到 ~0.96**；按组合深度分层，**稀疏/词汇更稳、稠密崩塌**。
**为什么值得注意**：它把"稠密优于稀疏"这句话限定到了"存在语义捷径"的场景，给出了反例的量化边界。

**② BM25 在领域检索里仍是强基线（arXiv:2506.12895）**
CJEU 法律段落检索：**BM25 在 7 个指标中 4 个超过现成稠密模型**；领域微调后的稠密模型才在多数指标反超。
**为什么值得注意**："换模型"不必然变好，"领域适配"才是变量。

**③ 切分评估被诊断出"测不出来"（arXiv:2509.11552）**
HiChunk 指出既有 RAG 基准因**证据稀疏**而无法评估切分质量，提出多层级切分点标注 + 证据密集 QA 对 + Auto-Merge 检索。
**为什么值得注意**：如果你用稀疏证据集测切分，得到的"没差别"结论可能是评测集的锅。

**④ 切分质量可以脱离下游被测量（arXiv:2603.25333）**
五个内禀指标（RC/ICC/DCC/BI/SC）驱动的"按文档选自适应切分"，**不改模型与 prompt**，正确率 62–64% → 72%，成功答题数 49 → 65。
**为什么值得注意**：它给出了"切分评估进 CI"的可操作路径。

**趋势观察（非定论）**
2026 年的检索侧讨论正在从"稠密 vs 稀疏"转向"**按查询类型路由 + 融合**"，并且越来越多工作强调**评测集本身的有效性**（证据密度、构造效度、标注质量）。这与第 003 期 R0-05 的路由表、以及第 006 期"基准标注错误率 50%+"是同一股风。**属趋势观察。**
