## 知识点 1：RAG 四层失败模型（R0-03）

### 一句话结论

**RAG 的失败不是一个"幻觉问题"，而是四个可分离的损耗点：检索不到（L1）、排不准（L2）、用不好（L3）、答不实（L4）。** 归因的价值在于：每一层对应不同的修复成本和不同的观测量，认错层会把预算花在没用的地方。

### 为什么重要

- 大多数团队的第一个错误不是"模型不行"，而是**把 L1/L2 的失败当成了 L4 的失败**，于是去换更大的模型、加更严的 prompt、上更贵的 judge——全都打不中。
- 【论文结论】Leung 等人在 DragonBall-EN 上人工核验了 832 个真实错误，分布是：**切分 29.7%、检索 31.5%、重排 7.1%、生成 32.7%**。其中"编造内容"（Fabricated Content）只有 34 个，占比约 4%。也就是说：**幻觉只是四层里的一小块，而且是相对小的一块。**
- 你上一期的问题之所以难回答，是因为它缺一个**可测量的中间量**。这一期给三个：`recall@k`、`recall@n`、`sufficiency rate`。

### 核心机制 / 数据流

四层不是四个模块，是**四个断点位置**。同一个 bad case 只应该被归到一层：

```text
用户问题
   │
   ├─ L1 检索不到 ────── 证据根本没进候选集
   │     观测量：recall@k（gold span 是否在 top-k 里）
   │     典型原因：解析丢了表格、切分切断了条件、同义词/缩写没覆盖、query 没改写
   │
   ├─ L2 排不准 ──────── 证据进了 top-k，但没进最终的 n
   │     观测量：recall@n（n ≪ k），以及 recall@k 与 recall@n 的落差
   │     典型原因：缺 rerank、元数据过滤缺失、多路召回没融合
   │
   ├─ L3 用不好 ──────── 证据在 context 里，但没被用上
   │     观测量：sufficiency rate + "证据在位 vs 不在位"的正确率差
   │     典型原因：context 过长/噪声多、证据被挤到中段、多文档冲突未处理
   │
   └─ L4 答不实 ──────── 证据够、也在场，但答案错、或该拒答没拒答
         观测量：faithfulness、abstention accuracy、数值/时序错误率
         典型原因：参数先验压过证据、指令冲突、格式服从失败
```

**关键判据：`recall@k` 高但 `recall@n` 低 = L2；两个都低 = L1；两个都高但答案错 = L3 或 L4。**

区分 L3 和 L4 需要一次"证据注入实验"（下面第 3 步）：把 gold evidence span 强行拼进 context 再问一遍。若这样能答对 → 断点在 L1/L2；若仍然答错 → 断点在 L3/L4。

**L3 和 L4 的分离靠"充分性"这个量。** 【论文结论】Joren 等人（ICLR 2025）把 context 是否"充分"（sufficient = 包含做出确定回答所需的全部信息）做成了一个可计算的判断，用 1-shot 提示的 Gemini 1.5 Pro 做 autorater，在 115 条人工标注上达到 **93% 准确率 / F1 0.935**。他们的核心发现对我们特别有用：

- 大模型在 context **充分**时答得很好；但在 context **不充分**时，它们倾向于**硬答而不是拒答**。SOTA 模型在不充分 context 下仍有 **35%–62%** 的概率答对（是/否类问题接近 50% 的瞎猜水平）。
- 所以"答错"里有一大类根本不是生成层的错，而是**上游没给够证据、下游又不会说"我不知道"**——这是跨 L1 和 L4 的复合故障，只修一头没用。

### 怎么做

1. **建一个带 span 标注的 golden set（50–100 条就够）。**
   每条要三个字段：问题、参考答、**gold evidence span（字符级片段，不是文档 ID）**。没有 span，你永远分不开 L1 和 L2——因为"文档召回了"和"证据句召回了"是两件事。

2. **埋三个探针，先测再改。**
   - `recall@k`：gold span 是否落在 top-k（k 取你实际喂给 rerank 的候选数，常见 20–50）。
   - `recall@n`：gold span 是否落在最终进 context 的 n 条里（n 常见 3–8）。
   - `sufficiency rate`：对最终 context 跑一次充分性判断，统计"不充分"的比例。
   三个数画成一张表，你的瓶颈象限就出来了。

3. **做一次 oracle-context 实验做交叉验证。**
   取 30 条 bad case，把 gold span 直接拼到 prompt 最前面（绕过检索），重跑。答对率显著回升 → 你的问题主要在 L1/L2；几乎没回升 → 主要在 L3/L4。这个实验半天能做完，信息量超过一周的调参。

### 权衡与坑

- **`recall@k` 是可以刷的假指标。** 把 k 从 5 拉到 50，recall 一定涨，但 L3 的噪声和成本一起涨。所以真正定容量的是 `recall@n`，`recall@k` 只用来判断"要不要加 rerank"。
- **自动归因只能产出候选，不能产出结论。** 【论文结论】Leung 等人的 RAGEC 自动归因与人工标注的**阶段判定一致率只有 57.8%**，错误类型准确率 **40.3%**，而且系统性地**过度归咎生成器**（人更倾向归咎检索）。所以：自动归因用来做分流和排序，最终定性必须人工看 20–30 条样本。
- **修一层会把错误推到另一层，这不是失败。** 同一篇论文里，做完针对性改进后切分层错误从 29.7% 降到 16.4%、检索层从 31.5% 降到 24.3%，但生成层从 32.7% **升到 53.9%**（总错误 832 → 534）。总错误在降，说明改进有效；生成层占比升高只是因为它成了新的短板。看到这个数字不要慌，要看总数。
- **别把四层当瀑布模型。** 实际排障顺序常常是反的：先做 oracle-context 判断"是不是检索的锅"，再决定往上游查还是往下游查。

### 架构师视角

四层对应的不是四个团队，而是**四份预算和四个 SLO**：

| 层 | 谁负责 | 主要投入 | 可承诺的 SLO 例子 |
|---|---|---|---|
| L1 检索不到 | 数据/解析 + 检索 | 解析器、切分策略、混合检索、query 改写 | `recall@50 ≥ 0.90` |
| L2 排不准 | 检索 | reranker、元数据过滤、融合权重 | `recall@5 ≥ 0.80` |
| L3 用不好 | 上下文工程 | 组装顺序、去重去噪、冲突消解 | `sufficiency rate ≥ 0.85` |
| L4 答不实 | 生成/产品 | 引用约束、拒答策略、结构化输出 | `faithfulness ≥ 0.90`，错误拒答率 ≤ 5% |

【我的建议】把这张表直接变成你 RAG 项目的周会看板。它最大的作用不是"监控"，而是**让争论有落点**：当有人说"模型不行"，你只需要问"哪一层的数掉了"。

### 自测（先别翻答案）

1. 你的系统 `context_precision = 0.90`、`context_recall = 0.55`、`faithfulness = 0.92`，但用户抱怨"答非所问"。四层里最可能断在哪一层？`faithfulness` 高这一点，排除了什么？
2. 把 top-k 从 5 提到 20，`recall@20` 从 0.62 涨到 0.88，但答案正确率没动，`faithfulness` 从 0.91 掉到 0.83。瓶颈在哪一层？下一步该改什么、**不该**改什么？
3. 你要向老板证明"错误主要来自切分而不是检索"。设计一个最小实验（不许要新数据集、不许标注 500 条），说明你控制了什么变量、看哪个数、结论怎么下。

## 知识点 2：最小闭环与 7 个组件（R0-04）

### 一句话结论

**一个能上线的最小 RAG，不是七个组件都"有"，而是七个组件都有可观测出口。** "最小"的定义应该是：**每一层都能被单独证伪**——你能关掉它、看效果掉多少。

### 为什么重要

- 最小闭环的真正用途不是"先跑起来"，而是**给你一个可做 ablation 的基线**。没有基线的系统，你无法判断后来加的 hybrid 检索、rerank、query 改写到底有没有用。
- 【论文结论】Barnett 等人的七点失败清单里有一个容易被忽略的结论：**RAG 的健壮性是在运行中演化出来的，不是设计时一次性设计出来的**；而且很多问题只有在真实运行中才能被发现。这直接否定了"先设计完美架构再上线"的路线。
- 七个组件正好可以**一一映射到四层的观测点上**——这就是为什么这两期要放在一起讲。

### 核心机制 / 数据流

```text
① 摄取与解析 ──→ ② 切分与知识单元 ──→ ③ 索引 ──→ ④ 检索与融合 ──→ ⑤ 重排与过滤 ──→ ⑥ 上下文组装 ──→ ⑦ 生成与引用/拒答
   保真度            自包含性          可检索性       召回率            精确率            证据密度          忠实度/可追溯
   └────────────────── L1 ──────────────────────────┘ └── L2 ──┘ └── L3 ──┘ └──── L4 ────┘

横切两条：评估与可观测性（贯穿全链）｜权限、版本与删除（贯穿全链）
```

每个组件的**最小可观测出口**：

| # | 组件 | 最小输出契约 | 必须有的一行日志 |
|---|---|---|---|
| ① | 摄取与解析 | 原文 → 带结构的文本（标题层级、表格、页码） | `doc_id, version, parse_status, 丢字率` |
| ② | 切分 | 文本 → chunk（保留父文档指针 + 标题路径） | `chunk_id → doc_id, 起止 offset` |
| ③ | 索引 | chunk → 向量 + 关键词 + 元数据 | `index_version, embedding_model, 更新方式` |
| ④ | 检索 | query → top-k 候选（多路，带分数） | `k, 各路召回数, 融合后顺序` |
| ⑤ | 重排 | top-k → top-n（带重排分） | `n, 重排前后排名变化` |
| ⑥ | 组装 | top-n → prompt（去重、排序、加来源标记） | `最终 token 数, 被丢弃条数及原因` |
| ⑦ | 生成 | prompt → 答案 + 引用 + 拒答标记 | `引用是否可定位, 是否触发拒答` |

**注意第 ⑥ 行**：Barnett 的 FP3"Not in Context"就是组装层把已召回的文档丢掉了。如果你的组装层没有"被丢弃条数及原因"这条日志，这个故障对你完全不可见。

### 怎么做

1. **先定契约，再选技术。** 上表七行先写进设计文档，每行至少一个字段能在日志里查到。做不到的行，就是你上线后会瞎猜的地方。
2. **MVP 选型按"最钝但可证伪"的原则。**
   - 解析：能保留标题层级和表格结构的即可，不必上版面模型；
   - 切分：结构感知（按标题切）+ 固定上限，不做语义切分；
   - 索引：向量单路 + 元数据过滤，**先不上 hybrid**；
   - 检索/重排：top-20 → rerank → top-5，rerank 是投入产出比最高的一层，优先上；
   - 生成：强制引用 + 显式拒答分支。
3. **上线前跑五个体检。** ① 重索引是否幂等（同文档两次索引结果一致）；② 文档更新/删除能否传播到索引；③ 引用能否点开定位到具体段落；④ 拒答路径是否真的接通（拿一个语料外问题测）；⑤ 成本与延迟是否有分组件打点。

### 权衡与坑

- **别一次上五个高级件。** hybrid + rerank + query 改写 + 图谱 + agent 一起上，出问题时你无法归因。每加一件，先记录"关掉它掉多少"。
- **"有组件"不等于"有出口"。** 很多团队有 rerank，但没有记录重排前后排名变化，于是永远不知道 rerank 是在帮忙还是在伤害。
- **拒答不是兜底文案，是一条独立路径。** 它需要自己的评估集（语料外问题 + 边界问题），否则你测的永远是"能答的时候答得对不对"。
- 【我的建议】把"最小"理解为**可删性**：每一个组件都要能被一个开关关掉，并且关掉后指标可测。做不到这一点的架构，复杂度就是债务而不是资产。

### 架构师视角

七个组件 → 四层观测 → 四个 SLO，这是一条完整的落地链。你上一期那个问题"我最弱一环是解析、切分还是生成"，用这套东西可以在一周内变成一句有数的话，例如：

> "L1 的 `recall@50 = 0.93` 但 `recall@5 = 0.61`，L2 是主要瓶颈；L3 的 sufficiency rate 只有 0.72，说明即使排对了证据也不够用；L4 的 faithfulness 0.94 说明生成不是问题。"

这句话比任何架构图都更能指导预算。

### 自测（先别翻答案）

1. 七个组件里，如果只能先给一个加可观测性，你加哪个？给出你的判断依据（提示：想"哪个组件的故障最不可见"）。
2. 用户反馈"答案里给了文档名，但点进去找不到那句话"。这属于哪个组件的问题？为什么它不算生成层的问题？
3. 老板要求两周上线。列出你愿意砍掉的三项能力和绝不砍的三项能力，各写一句理由。
