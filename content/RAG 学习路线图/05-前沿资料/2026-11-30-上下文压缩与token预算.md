# 上下文压缩与 token 预算：省的是钱，赌的是忠实度

> **定位**：前沿资料 · 单篇精读 · 关联知识点 R5-05（上下文压缩）、R0-06（成本模型）、R5-03（引用）
> **主源**：Shuyu Guo 等，《Compression Beyond the Uncompressed: A Two-Stage Training Recipe for Soft Context Compression in RAG》（DEX-Comp），arXiv:2609.05152（2026-09）
> **本地存档**：[HTML 全文](原文/html/2609.05152-full.html)（PDF 在本网络下载不完整，已删；摘要页 [见此处](原文/html/2609.05152.html)）
> **证据强度**：中—高（arXiv 预印本，多基准、多骨干，但需同行评审复核）

## 一句话结论

上下文压缩已经从“摘要一下”进化到**可训练的软压缩**：把文档编码成紧凑的连续表示，可以**预计算、跨查询复用**。DEX-Comp 在 **16× 压缩比**下平均准确率超过未调优的全上下文 RAG，TTFT 快 **4.4–23.7×**。但压缩的核心风险不是“压得不够小”，而是**压掉了引用所需的对齐信息**——**省 token 的同时，可能把可追溯性一起省掉**。

## 三个硬结论

**① 软压缩可以“超过不压缩”（在特定条件下）。**
DEX-Comp 用两阶段训练：`Pure Distillation` 只从“教师答对”的问题学习，避免模仿教师的错误；`Hard Exploration` 对教师答错的问题用结果型强化学习直接优化答案正确率。结果：**16× 压缩**在五个开放域 QA 基准、top-5 到 top-30 检索深度上**超过所有评测的压缩基线，并平均超过未调优的全上下文 RAG**；TTFT 降低 **4.4–23.7×**。

**② 压缩的收益是“乘法”，但成本也是。**
```
总成本 ≈ 检索成本 + 压缩编码成本 + 生成 token 成本 × 压缩后长度 + 解码延迟
```
压缩只在**生成 token 占主导**时划算；如果检索/编码本身很贵，或者压缩模型很大，端到端未必省。

**③ 压缩与引用是一对矛盾。**
软压缩把原文变成连续表示，**不再保留原始 span**；而引用要求“每个结论能定位到原文的哪一句”。两者可以共存，但需要**双通道**：压缩表示用于召回/生成，原始块保留用于引用与审计。

## 精评：值钱的地方

1. **给出了“压缩可以不掉点”的强证据**：16× 还能超过未调优全上下文，说明“压缩=损失”不是铁律。
2. **两阶段训练的思路可迁移**：先学“教师对的”，再对“教师错的”做结果优化——这比单纯蒸馏更稳健，适合任何“教师不完美”的场景。
3. **TTFT 4.4–23.7×** 是产品体验层面的硬收益，不只是成本。

## 精评：不能当真（或容易被误读）的地方

- **预印本，且教师/基准选择会影响结论**；“超过未调优全上下文”不等于“超过精心调优的全上下文”。
- **压缩比不是越大越好**：16× 是这篇的设置，换语料/任务可能不同；不要拿一个数字当目标。
- **软压缩的“不可解释性”**：连续表示难以审计。对法务、医疗、金融等强引用场景，**不能只用软压缩**。

## 对你的动作

1. **先算账再压缩**：用你的真实 token 价格与 QPS 算 `生成成本占比`；低于 50% 时，压缩的收益有限。
2. **双通道**：`compressed_vector` 用于召回/生成，`raw_chunk` 用于引用与审计；两者用 `chunk_id` 对齐。
3. **压后必测三件事**：答案正确率、`citation_unsupported_rate`、`answer_accuracy_by_position`（压缩可能改变位置效应）。
4. **从小比例开始**：先 4×，再 8×、16×；每次都用同一套金标集对比，不要一次跳到极限。

## 自测

1. 你的生成 token 成本占总成本多少？如果不到一半，压缩真的能省钱吗？
2. 压缩后你还能把每个结论定位到原文的哪一句吗？如果不能，你的引用是“装饰”还是“证据”？
3. 16× 压缩在你的语料上可能失败在哪里：表格、代码、数字、还是多跳？
