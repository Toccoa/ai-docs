# 向量压缩：int8 几乎免费，binary 每个任务都亏

> 定位：前沿资料 · 主题合并（向量压缩 / Matryoshka）
> 关联知识点：R4-04（向量压缩）、R3-04（ANN 索引内存账）、R0-06（成本与延迟模型）
> 主源两篇：
> - 《To MRL or not to MRL: Text Embeddings are Robust to Truncation Without Matryoshka Learning, Except In Heavy Truncation Scenarios》**EMNLP 2026 Findings**，arXiv:2605.16608
> - 《Balancing hierarchical representation and quantization: A performance trade-off in text embeddings》**Information Sciences 763 (2027) 124271**，arXiv:2611.06859
> 入库日期：2026-11-27 ｜ 证据强度：两篇同行评审期刊/会议论文

## 一句话结论

压缩有两件事可以放心做、两件事要小心：**int8 几乎免费**（在 pair classification 与 rerank 上与 float32 统计不可区分）；**维度减半一次通常安全**（m=16 以上检测不出）；但**binary 在每个任务类别上都显著更差**、**连续减半两次总能检测出退化**；而且最刺眼的一条是——**检索任务的退化远快于其它所有类别**，所以“总榜没掉”不能作为上线依据。

## 结论一：截断鲁棒性未必来自 Matryoshka（arXiv:2605.16608）

这是此前没人做过的对照：**把 MRL 用的同一套截断，同时施加到“用 MRL 训练”与“没用 MRL 训练”的模型上**。结果：
- **除非重度截断（压缩至少 80%），非 MRL 模型的截断嵌入与 MRL 模型相当，且常常更好**；
- 这暗示**“截断鲁棒性”未必来自 MRL**；
- 所以**要不要付 MRL 的额外训练成本，取决于你是否需要重度截断**。

对你的直接含义：**只打算压到一半（768→384）的话，你不一定需要 MRL 模型**。这推翻了“压缩必须用 MRL”的采购逻辑。

## 结论二：量化与降维如何叠加（arXiv:2611.06859）

规模很大：**MTEB 的 38 个任务 × 4 个 transformer 嵌入模型 × {1D 与 2D 层级表示} × {float32 / int8 / binary} = 每任务 168 种配置**；效率维度分开报告（理论单向量存储 + 端到端评估时间），并用 **Friedman 检验 + Nemenyi 事后分析**做统计判定。结论：

| 结论 | 具体数字 |
|---|---|
| int8 vs float32 | 在 pair classification 与 rerank 上**统计不可区分**，整体**最多差 1.5 个百分点** |
| binary | **每个任务类别都显著更差** |
| 维度减半一次 | **m=16 以上统计检测不出** |
| 连续减半两次 | **总能检测出** |
| 组合最优 | **8× 降维 + int8 = 单向量存储降 32 倍，保留 94.4% 效果** |
| 加速 | **没有证据表明量化能加速评估**；真正显著缩短时间的是**从中间层采样** |
| 最敏感的任务 | **检索（retrieval）退化远快于其它所有类别** |

## 精评：值钱的地方

1. **把“压缩”从经验变成了可分级授权**：你可以拍板“int8 上、binary 不上”，因为有统计检验支撑，而不是“某博客说可以”。
2. **“8× 降维 + int8 = 32×、94.4%”** 是一个极其实用的目标点：你要的 32 倍，**不需要碰 binary**。
3. **“量化不加速”这条纠正**很重要：省存储 ≠ 省延迟，很多方案的收益被高估。

## 精评：不能当真（或容易被误读）的地方

- **“整体最多差 1.5 个百分点”是跨任务平均**，而论文自己说**检索退化最快**。所以**必须按 retrieval 子集单独验收**，不能引用平均值来批准检索场景的压缩。
- **评测时间只测了一次**（作者自己标注为"indicative"），所以“量化不加速”的证据强度弱于存储结论。
- **MRL 那篇的结论有边界**：压缩 ≥80% 时 MRL 仍有价值。别把它读成“MRL 无用”。
- 两篇都基于**英文 MTEB 任务**，中文/领域语料上的退化曲线要自己测。

## 对你的动作

1. **先算存储账**：`N × dim × bits/8`，把 float32 / int8 / binary × 全维 / 半维 / 1/8 维列一张表。
2. **默认上 int8**（无需逐次审批）；**binary 只能做粗筛层**，后面必须接 int8/float32 重排。
3. **只在 retrieval 子集上验收**，四列一起报：recall@5、recall@10、存储、p95。
4. **压缩是一次“度量变更”**：相似度分布变了，语义缓存、MMR 的 λ、拒答阈值都要重校。

## 自测

1. 你的索引现在多少 GB？只上 int8（4×）能省到多少？够解决问题吗？
2. 维度从 768 压到 192（连续减半两次），你预计 recall 掉多少？打算用什么数据证明？
3. 有人提“binary 索引省 32 倍”，你会要求补哪两级结构才同意上线？
