## 一、一句话结论

**记忆不是"把对话存下来"，而是在四层之间搬运货物：底层真实但难用，顶层好用但极易写错。** 记忆系统的质量由两件事决定——**分层的物理隔离**，和**一个离线校对者（dreaming）**；而不是由"存了多少"决定。

对 RAG 架构师而言最重要的一句：**这是 RAG 的一个反向问题**。RAG 检索的是"世界的知识"，记忆检索的是"自己的经验"；RAG 的上限由解析与切分决定，记忆的上限由**显著性判断**（该不该记）和**抽象能力**（会不会压缩）决定。

## 二、为什么这件事现在值得入库

| 变化 | 含义 |
|---|---|
| **模型开始自己判断"什么值得记"** | 记忆从"人工维护的配置文件"变成"模型自己写的经验库"，`MEMORY.md` 这类手工文件退化为索引 |
| **离线整理（sleep-time compute）成本下降到可做** | Letta & UC Berkeley 的 sleep-time compute（[arXiv 2504.13171](https://arxiv.org/abs/2504.13171)）从论文走进托管产品（Claude Managed Agents 的 dreaming） |
| **出现了能测记忆的 benchmark** | CL-Bench 1.0 把"跨 session 学习"变成可打分任务，记忆第一次有了**可分代的数字** |
| **失败模式被具体复现了** | 月见山陷阱、合同写冲突、wiki 膨胀到 1.77× ——都是可复现的、有数字的失败，不是"记忆很重要"这类空话 |

## 三、定义边界（先划清，避免误用）

**agent memory 的定义**（原文）：Claude 从经验中获得、跨 session 保留、并且能作为 context 读回来的知识。

**明确排除三样**：

| 被排除的东西 | 为什么不算记忆 | 工程含义 |
|---|---|---|
| 权重更新 / 微调 | 不是"读回来"，是"改掉了" | 不可审计、不可回滚、不可单条删除 |
| in-context learning | 跨不了 session | 单次对话内的学习不是记忆 |
| **compaction（压缩）** | 那是"同一个 session 的续命" | **把 compaction 当 memory 做，得到的是会失真的摘要链，不是可审计的知识库** |

> 这条边界对你直接有用：知识库里最容易被混为一谈的三件事——**会话压缩（维持当前窗口）、RAG 知识库（世界的知识）、agent memory（自己的经验）**——上表就是分界线。

## 四、四层栈（本文的核心结构）

```text
┌──────────────────────────────────────────────┐
│ L1 Transcripts       系统自动写·不可编辑·全文可搜 │ ← 唯一 ground truth
├──────────────────────────────────────────────┤
│ L2 Memory notes      模型边干边判断后写          │ ← 显著性判断的产物
├──────────────────────────────────────────────┤
│ L3 Representations   由 L1+L2 计算出的表征/wiki  │ ← dreaming 离线建
├──────────────────────────────────────────────┤
│ L4 Injected context  每次 session 预加载         │ ← 必须极小
└──────────────────────────────────────────────┘
```

| 层 | 谁写 | 决定性约束 | 失效方式 |
|---|---|---|---|
| **L1 Transcripts** | 系统（app） | 不可编辑、可搜索 | 太大，直接塞进 context 会稀释注意力 |
| **L2 Memory notes** | 模型自己 | 写的时候不知道以后有没有用（Kierkegaard 悖论） | 误记、记冗余、记过期状态 |
| **L3 Representations** | dreaming（离线） | 维护要算力；会累积错误 | 抽象失败→膨胀；抽象过度→丢细节 |
| **L4 Injected context** | dreaming 晋升 | **必须极小**，否则降低指令遵从 | 一条错笔记污染**每一个** session |

**L4 的量级参考**：Claude Code 只把 `MEMORY.md` 的**前 200 行 / 25KB** 作为索引进 context。原文还警告：**过长的指令文件会降低遵从率**——这和你"提示词越写越长、效果反而变差"的直觉是同一件事。

## 五、Dreaming：离线做的五件事

dreaming 不是"压缩"，是**有明确批评标准的重写**：

| 职能 | 做什么 | 可复现的例子 |
|---|---|---|
| **纠错** | 用 transcript（不可编辑的原始记录）校对笔记 | 月见山：笔记写"宝可梦中心在东侧"，实际在西侧 |
| **建表征** | 从 L1+L2 计算 wiki | Stainless 语料 350,000 文件 / 420M token → wiki |
| **晋升** | 把少数笔记提升到注入层 | `global.md`＝当前目标 + 计划 + 使用记忆的规则 |
| **聚焦** | 按目标裁掉无关页 | 合同任务：一合同一页、一页一 writer |
| **补漏** | 扫死链、补缺失页 | 9 条指向不存在页面的链接被重指 + 新增 3 页 |

## 六、关键数字（可直接引用的部分）

### 6.1 CL-Bench 1.0：记忆是可学习的能力（跨 session 学习闭环）

| 模型 | 无记忆 | 有记忆 | 增益 |
|---|---|---|---|
| **Opus 5.5** | 0.655 | **0.838** | +0.183 |
| Sonnet 5.5 | 0.644 | 0.833 | +0.189 |
| Opus 5 | 0.564 | 0.828 | +0.264 |
| Opus 4.7 | 0.383 | 0.700 | +0.317 |
| Sonnet 5 | 0.306 | 0.610 | +0.304 |
| Sonnet 4.6 | 0.330 | 0.364 | +0.034 |

**必读的反直觉点**：**更强的模型"从记忆获得的增益"反而更小**，因为它的 baseline 本来就高。→ 评估任何记忆系统时必须**同时报 baseline**，否则会把"模型变强"误读成"记忆没用"，或把"记忆有用"误读成"模型变强"。

### 6.2 硬规则是负收益（本文最实用的一条）

"只记录失败"（record only failures）这一条硬规则，让记忆的增益**崩掉**：

| 模型 | 增益变化 |
|---|---|
| **Opus 5** | **−0.234** |
| Opus 4.7 | −0.150 |
| Sonnet 4.6 | −0.020 |

而弱模型的真实问题不是"记错东西"，是**根本不读记忆目录、也不验证自己的猜测**。改成提示"先读记忆再回答、显式验证你的猜想"后，Sonnet 4.6 从 **0.364 → 0.641**（接近翻倍）。

> **规则**：告诉模型"记忆是干什么用的"，但**不要**告诉它"该怎么用"。硬规则是弱模型的拐杖，是强模型的枷锁。这条可以直接迁移到你的 RAG prompt 治理：**约束用途 > 约束写法**。

### 6.3 判断力比容量重要（Claude Plays Pokémon 对照，约 step 10,000）

| | Sonnet 3.7 | Fable 5 |
|---|---|---|
| 文件数 | **413 文件 / 225 文件夹** | **9 文件 / 2 文件夹 + `global.md`** |
| 字符数 | 977,930 | **43,406** |
| 徽章 | 1 | **4** |

- Sonnet 3.7 假设"一切都可能重要"，为每场战斗、每个道具、每个 NPC 建一个文件；但游戏状态持续变化，它的详尽记录**一直在过期**。到第 10,000 步，它开始第四套 "master" 记忆，**接下来 17 步建了 6 个文件、删了 9 个，游戏里一步没走**。
- Fable 5 只记**游戏不会告诉你的东西**：屏幕每回合都能读到的（钱、坐标）→ 存了是冗余；策略 / 计划 / 验证过的规则 → 只有写下来才存在。

> 对 RAG 的迁移：**"记什么"的决定权应交给能判断显著性的模型；"记多少"必须有预算上限。** Sonnet 3.7 的病，和知识库里"什么文档都入库、不做筛选"是同一个病。

### 6.4 表征不是万灵药（三个反例）

| 情况 | 结果 |
|---|---|
| 24 题里过半需**跨文档**检索/判断/算术 | wiki **87%** vs 纯 search **73%** ✅ |
| 判据基本能在**单文档**内文本搜到 | wiki **无增益**（≈search） ❌ |
| wiki 膨胀到**比源文件还大** | 10 文档 115KB → 68 页/255 链接/**203KB（1.77×）** ❌ |

第三条被作者用博尔赫斯《论科学的精确性》里"和帝国一样大的地图"讽刺：**地图画得和领土一样大，就不再是地图**。

> **判据（可直接写进架构评审）**：wiki / 抽象层值得建，**当且仅当"必须跨文档综合"是任务的主要成本**。单文档查找类任务，wiki 是纯开销。

### 6.5 wiki 的规模效应（Stainless 语料）

| 配置 | 分数 | 备注 |
|---|---|---|
| 纯 wiki（dreaming 2 → 128 session） | 13% → **48%** | 随 session 数持续上升 |
| wiki + search | 54% → **61%** | 最高 |
| 纯 search | 53% → 53% | **恒定，不随 session 增长** |

规模：2 个 session 后 103 页 / 766 链接 → 128 个 session 后 222 页 / 12,893 链接（页数 2.2×，链接 16.8×）。每题省约 20,000 token。

> 这条最有价值：**纯检索是"不会变聪明"的架构**。它的分数不随使用时间增长；只有加入了"写回/综合"这一环，系统才在积累。

### 6.6 多 agent 写冲突（合同任务）

| 做法 | 结果 |
|---|---|
| 四个 agent 同写 `provisions.md`，互相覆盖 | **41/57（72%）** |
| 一合同一页、一页一 writer、条款**逐字引用** | **57/57（100%）** |

> 这条几乎可以不做修改地搬进多 agent RAG 的知识库写入流程。**"逐字引用"是关键**——它把"我理解的条款"变回"原文的条款"，消除了改写损失。

## 七、落成工程：八条可直接抄的规则

1. **先分四层，再写代码。** 不可变记录（transcript）与可重建投影（notes / wiki / injected）必须**物理分开**。
2. **注入层必须小成一个索引。** 200 行 / 25KB 是可参考量级：我知道什么、去哪找、往下指的链接。
3. **说清用途，别规定写法。** "有一个 memory 目录可用"对强模型就够；"只记失败"会直接扣分。
4. **给记忆一个可校验的对象。** dreaming 能纠错的前提是 **transcript 还在且不可编辑**。
5. **把"晋升到注入层"当成发布流程。** 一条错笔记进的是每一个 session。
6. **给 wiki 设预算。** 页数 / 体积封顶，或按访问频次决定维护算力。
7. **算清楚 dreaming 的账。** 按轮次计费；聚焦**易变信息**，别指望"检查全部记忆"可行。
8. **防止多 agent 写冲突。** 一份文档一页、一页一个 writer、原文逐字引用。

## 八、与 RAG 知识库的接口（本文对你最有用的部分）

| 维度 | RAG 知识库 | Agent memory |
|---|---|---|
| 知识来源 | 世界（文档、网页、数据库） | **自己的经验**（做过什么、错在哪） |
| 更新频率 | 低（摄取 → 索引 → 上线） | **高**（每个 session 都可能在写） |
| 唯一事实源 | 原文（保留出处） | **transcript**（不可编辑） |
| 抽象层 | 摘要 / 层次索引 / GraphRAG | **wiki / notes** |
| 注入方式 | 检索（按需取） | **检索 + 预加载**（每 session 必带一小块） |
| 主要风险 | 检索不到、排不准、答不实 | **记错、记冗余、过期、污染每一个 session** |
| 谁做抽象 | 离线摄取流水线 | **dreaming（离线）** |

**三个可以直接迁移到 RAG 的结论**：

1. **双层 = 检索层 + 预加载层。** 你现在的 RAG 只有"检索"，没有"每 session 必带的一小块索引"。加上 L4（我知道什么 / 去哪找），能显著减少"检索词写偏"导致的 L1 失败。
2. **抽象层要能被子集校验。** wiki 能纠错，是因为 transcript 在。RAG 里对应的是：**任何摘要/图谱节点都必须能追溯到原文 chunk**，否则纠错无从下手。
3. **"经验回写"要单开一层。** 用户反馈、纠错记录、bad case 归因结论，**不应该**混进知识库正文——它们是 memory，不是文档。混在一起会同时污染检索和审计（对应 R6-08）。

## 九、权衡与坑（原文自己留的开放问题 + 社区质疑）

| 问题 | 原文态度 / 社区意见 |
|---|---|
| **在线写 vs 离线写** | 在线写：捕捉当下显著性，但**分走当前任务注意力**；离线写：不打扰任务，但**产出对当前 session 不可见** |
| **记忆怎么不过期** | "持续检查全部记忆"不现实。应聚焦易变信息，或按访问频次调 dreaming 节奏 |
| **transcript 搜索能否当底座** | "合理"。表征 + 搜索有效，但维护表征要算力，且要防错误/幻觉在表征里累积 |
| **最硬的上限** | **没有模型能知道下一轮会发生什么**——这是原理性上限，不是工程缺陷 |
| **社区质疑 1**：markdown 不是真记忆 | 反方：文件形态的记忆**可审计、可删、可迁移**；埋进权重就只能等下一个版本 |
| **社区质疑 2**：自动记忆多是噪音 | 多位实践者已关闭自动记忆，手动删掉 95% 条目。他们要的不是"记得更多"，是**更好的"该不该记"判断**与**作用域（scope）** |

## 十、自测（先别翻答案）

1. 你的场景里，"transcript 等价物"是什么？它现在可编辑吗？如果不可追溯，第 4 条工程规则（dreaming 纠错）在你这里为什么必然失效？
2. 纯 search 基线恒定 53%、纯 wiki 从 13% 涨到 48%——如果你的 RAG 只做检索，**它靠什么随时间变好**？如果没有，你缺的是哪一环？
3. 把"只记失败"这条规则翻译成 RAG 语言：你有没有正在用"只检索某类文档""只信某类来源"的硬规则？它在你的场景里是拐杖还是枷锁？
