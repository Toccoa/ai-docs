## 一句话结论

这门课只解决一件事：**让你亲手把"一次检索"升级成"会路由、会调用工具、会自己决定查几轮"的循环**。54 分钟买的是手感，不是可上线的系统——没有评估、没有成本、没有失败恢复。

## 课程骨架

| 课时 | 时长 | 讲什么 |
| --- | --- | --- |
| Intro | 2 分钟 | Agentic RAG 与 Naive RAG 的差别 |
| Router Query Engine | 9 分钟 | 多个索引并存时，先选"该查哪个库" |
| Tool Calling | 10 分钟 | 把检索器包装成工具，让模型决定何时调用 |
| Building an Agent Reasoning Loop | 11 分钟 | 推理循环：观察 → 决定 → 再查 |
| Multi-Document Agent | 10 分钟 | 跨文档比较与汇总 |
| Conclusion | 1 分钟 | 收尾 |

配套：4 个代码示例（notebook 形态，需要自己拼起来跑）+ 1 个测验。难度标注 Beginner。

## 这四级台阶为什么是对的

它选的四步，正好补上 [R0-04 的最小闭环](../02-每日推荐/2026-11-09.md)里最常缺的两件东西：

- **路由器**：真实系统里从来不止一个索引（文档库、代码库、数据库、FAQ）。没有路由器，用户问"上季度营收"和"这个函数怎么调"会走同一条链路，必有一半答得烂。
- **推理循环**：Naive RAG 是"查一次就答"，agentic 是"查了发现不够，改写查询再查"。这是从"检索增强"到"检索即工具"的那一步。
- 工具调用的抽象让检索器可以和其他能力（计算器、SQL、API）平级竞争，模型自己挑。

所以这 54 分钟的**结构价值大于内容价值**：它给了一条"从链到循环"的最小改造路径。

## 精评：能买到的

1. **一条可照抄的升级路径**。已经有一个能跑的单跳 RAG，按 router → tool → loop → multi-doc 四步改，每一步都能单独验证，不会一次性推倒重来。
2. **"检索器就是一个工具"这个视角**。想通这点之后，很多设计问题（要不要多路召回、要不要给模型选库）就变成普通工程问题。
3. **多文档比较的演示**。跨文档汇总（"这几份合同在违约金条款上有什么不同"）是 agentic 最自然的用武之地，也是最难用单跳链路做到的。

## 精评：买不到的

1. **评估**。全课没有讲"怎么知道改完变好了"——没有 golden set、没有 recall/faithfulness、没有 AB。学完照着做，很可能**感觉变聪明了，指标其实没动**。
2. **成本与延迟**。循环意味着不确定次数的 LLM 调用。真实系统必须卡死"最多几轮、总预算多少、超时怎么办"，这些课里一个字没有。
3. **失败恢复**。工具报错、检索为空、循环不收敛——agentic 系统 80% 的工程时间花在这三件事上。
4. **可移植性**。示例深度绑定 LlamaIndex 的抽象。学完能懂概念，但换成 LangGraph 或自研编排，代码要重写。
5. **代码示例要自己拼**。4 个 notebook 是分片演示，不是一条能跑的完整管线（没有环境、没有数据准备）。

## 学完立刻做的三件事

1. **加路由器**：把你现有的索引按"问题类型"切开（文档 / 代码 / 数据），先用规则路由跑通，再换成模型路由
2. **给每个工具写清"什么时候别用"**：工具描述里写反例，比写正例更能减少误调用
3. **加 trace + 轮数上限**：把每一轮的查询、召回、决策打日志，硬性限制最多 3 轮。没有这两样，agentic 系统不可调试

## 自测（先别翻答案）

1. 你的系统现在有几个索引？如果只有一个，"加路由器"还有意义吗？
2. 推理循环最多几轮？超过几轮之后，多查一次带来的收益通常为负？为什么？
3. 如果要给这门课补一节 20 分钟的课，你补哪一节？（提示：想想上线前最后一道关是什么）
