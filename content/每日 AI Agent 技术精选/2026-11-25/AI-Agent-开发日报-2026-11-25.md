## 二、今日必读

### 1. Google 语义治理策略：把"这次调用该不该做"交给语义判定

- **来源与日期**：Google 技术案例，2026-11-24（要点经 AI Agent Store 周报转述）
- **链接**：https://aiagentstore.ai/ai-agent-news/this-week

**为什么现在读**
这是本周最硬的运行时安全数字：**AgentDojo 上的攻击成功率从 48.7% 降到 0.9%**，而良性任务效用只损失约 **2.6 个百分点**。机制不复杂但很关键——每次提议的工具调用，都要同时对照**纯文本策略**与**用户原始请求**，而不是只查权限列表。它专门对付"指令藏在文件或工具输出里"的间接注入。

**核心要点**
1. 机制：在动作执行**之前**，逐个工具调用做语义级校验（策略 + 原始意图对齐），而不是事后审计或纯 RBAC。
2. 收益：攻击成功率 **48.7% → 0.9%**；良性任务效用代价约 **2.6pp**。
3. 为什么权限列表不够：权限只回答"能不能调这个工具"，不回答"这次调用是否符合用户意图"。
4. 落地建议（原文）：在支持策略的网关（文中为 Google Agent Gateway）先开 **dry-run**，优先压测高风险流程，监控拒绝率与"长期被误拦"的任务，再迭代纯文本规则。
5. 提醒：效果数字来自厂商案例研究，**需在自有流量上复测**，尤其关注误拦。

**怎么读**
15 分钟。落地顺序：先写 3–5 条最关键的纯文本策略（例如"不得向外部地址发送客户数据"），在 dry-run 下跑一周，看拦截分布，再决定是否阻断。

### 2. DeepMind：agent 团队 + Lean，产出可验证的量子电路改进

- **来源与日期**：Google DeepMind 研究发布，2026-11-24（要点经 AI Agent Store 周报转述）
- **链接**：https://aiagentstore.ai/ai-agent-news/this-week

**为什么现在读**
这是"agent 做科研"里少见的**工程可验证**类型：不是生成论文，而是产出**机器可检验的证明**与更省的量子电路。它把上周的 /teamwork、AlphaProof 串成了同一条方法线——**agent 搜索 + 形式验证**，而且这次给出的是可直接用的资源估计改进。

**核心要点**
1. 组合：Gemini 4 agent 团队 + **Lean 形式验证**，产出可证明正确的量子电路改进。
2. 效果：目标问题（聚变、化学模拟）的资源估计最高降低约 **11.8×**（一个任务），另一个任务最高 **8×**。
3. 开源：配套 Lean 库与材料已发布，可复用。
4. 方法可迁移：agent 负责大规模搜索与试错，形式检查负责判定——**人的介入点从"逐条审"变成"选性质"**。
5. 适用范围：适合有明确正确性判据的重工程问题（协议、电路、调度），不适合判据模糊的业务逻辑。

**怎么读**
15 分钟。若你做硬科技/基础设施，可先拿开源 Lean 资产跑一个小任务，量化"迭代成本是否下降"，再决定是否扩大。

### 4. 审计要审"状态迁移"，不是"工具日志"

- **来源与日期**：arXiv:2611.23346（据 dev.to 汇总转述，2026-11-17）
- **链接**：https://dev.to/hlinor/tool-call-logs-are-not-enough-agent-governance-now-has-to-audit-state-transfers-5aio

**为什么现在读**
很多团队以为"记了工具调用日志就等于可审计"。这篇给出量化反驳：在 240 条轨迹（120 正常 + 120 注入故障）上，**只看工具调用日志只能抓到 16.7% 的问题**；改用完整的**状态迁移审计 schema** 后达到 **98.3%**，且**误报率 0%**。

**核心要点**
1. 规模：240 条轨迹，其中 120 条注入故障。
2. 差距：工具日志 **16.7%** vs 状态迁移审计 **98.3%**；后者误报 **0%**。
3. 为什么：问题往往不在"调了哪个工具"，而在"状态被改成了什么"——只记录调用，看不到副作用。
4. 实践含义：审计要记录**关键状态的变更前后值**（文件、配置、数据库行、外部资源），而不仅是请求参数。
5. 阅读提醒：数字来自汇总文章转述，**未直接核验原文实验设置**。

**怎么读**
20 分钟。今天可做：给你的 agent 定义 3–5 个"关键状态"（谁改了、改成什么、能不能回滚），先补这部分日志，再谈更复杂的检测。

### 5. Apsis：agent 工作流的静态安全分析

- **来源与日期**：arXiv:2611.28469（cs.SE），2026-11-21 提交；被 ICSE 2027 接收（扩展版）
- **链接**：https://arxiv.org/abs/2611.28469

**为什么现在读**
大多数 agent 安全工具是"运行时拦截"，这篇是**静态分析**：在 agent 工作流跑起来之前，分析它的结构找风险。它给出了学术级别的精确率/召回率，并且真的在 13 个框架的语料里挖出了 **36 个此前未知的 bug**——这类工具适合放进 CI，而不是等线上出事。

**核心要点**
1. 工具：Apsis，面向 agentic workflow 的静态安全分析器。
2. 语料：覆盖 **13 个框架**。
3. 指标：**精确率 91% / 召回 84%**。
4. 结果：发现 **36 个此前未知的 bug**；扩展版被 **ICSE 2027** 接收。
5. 使用建议：把它当"上线前的静态检查"，与运行时的语义策略（必读 1）形成前后夹击。

**怎么读**
20 分钟。对平台团队：先看它支持哪 13 个框架、报告长什么样；若你们用 LangGraph/Deep Agents 一类框架，值得评估接入成本。

### 6. Replay Fidelity：回放保真度决定评测是否可信

- **来源与日期**：arXiv:2611.11216（日期未确认，据索引转述）
- **链接**：https://export.arxiv.org/pdf/2611.11216

**为什么现在读**
昨天我们推荐了"录制 + 确定性回放"做回归（Tether）。这篇补上了它的**可信度前提**：回放能复现多少真实失败？在 **71 个历史 AppWorld 失败**上，回放把"准入"的差距从 **26 压到 4**——也就是说，不解决保真度，回放结果会系统性偏离真实行为。

**核心要点**
1. 研究对象：**71 个历史 AppWorld 失败**案例的回放保真度。
2. 关键数字：准入差距 **26 → 4**（说明改进后的回放更接近真实失败分布）。
3. 工程含义：回放是"同一输入 + 已录制响应"的确定性验证，**不能证明换模型/改 prompt 后的行为**；保真度必须单独评估。
4. 建议：给你的回放集做一次"保真度抽检"——随机抽 N 条，用真实模型重跑，看结论是否一致。
5. 阅读提醒：日期与实验细节未直接核验。

**怎么读**
15 分钟。配合昨天的 Tether 使用：**回放做门禁，抽检保真度做校准**，两者缺一不可。

## 四、今日观察

**1. 治理的判定点从"能不能"移到"该不该"。**
Google 的语义策略把攻击成功率打到 0.9%，靠的不是更严的权限表，而是**每次调用都对照用户原始意图**。这解释了一个长期困惑：为什么权限做得很细，agent 还是会被"藏在文件里的指令"骗——因为权限检查的是工具，语义检查的是目的。

**2. 审计对象要从"调用"换成"状态"。**
工具日志 16.7% 对状态迁移 98.3%，这个差距不是工程实现问题，而是**观测对象选错了**。对做 agent 平台的团队，这条应该直接改 schema：记录关键状态的前后值，而不是只记请求参数。

**3. 形式验证正在成为 agent 能力的放大器。**
DeepMind 用 agent 团队 + Lean 拿到 11.8× 的资源估计改进，与上周 /teamwork 的数学成果同构：**在判据明确的领域，agent 的产出可以被机器验收，因此能规模化累积**。这也是"哪些领域该先交给 agent"的最可靠判据。

**4. 商业闭环打开后，风控成为新工程面。**
Walmart 对 Muse 开放结账，与美联航禁止 agent 订票形成对照。差别不在技术，而在**有没有 agent 专用的授权与风控接口**。接下来一年，"agent 档案 + 分级授权 + 独立风控画像"会成为电商与旅行平台的标配工程件。
