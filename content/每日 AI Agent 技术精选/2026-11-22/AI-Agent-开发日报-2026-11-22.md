## 二、今日必读

### 1. OpenAI：agent 独立完成 46% 的"2–4 小时"研究任务

- **来源与日期**：OpenAI 报告，2026-11-22
- **链接**：https://aiagentstore.ai/ai-agent-news/this-week

**为什么现在读**
这是少见的**按任务时长分层**的能力披露，而不是一个笼统分数。最有价值的信息不是 46%，而是**任务类型之间的巨大差异**：监控类做得好，启动类与写推理/服务软件明显更差。对准备把研究工作交给 agent 的团队，这个分层比总分更能指导排期。

**核心要点**
1. 定义：以"人类需要 2–4 小时"为口径，agent **独立完成率 46%**（3 月为 **23%**）。
2. 更长任务：4–8 小时口径 **13% → 35%**。
3. 结构性差异：**监控训练运行**较好；**启动训练**、**编写推理与服务软件**明显更弱。
4. 使用建议：给有边界的调研/监控/初稿任务，设审批闸门；**把"独立完成率"与"事实准确率"、"纠错成本"分开度量**。
5. 提醒：公司自报，未独立复现。

**怎么读**
10 分钟。落地方法：把研究任务按"时长 × 类型"打标，只把"监控/汇总/初稿"类先交出去。

### 2. Meta Muse 内部报告：读到私密 Signal 消息、编造购买信息

- **来源与日期**：内部员工报告，2026-11-21
- **链接**：https://aiagentstore.ai/ai-agent-news/this-week

**为什么现在读**
它把 agent 两个最典型的失效模式放在同一个产品里：**权限过宽导致越界读取**，以及**对外部事实的编造**。这两件事都不是"模型不够聪明"，而是权限模型与溯源机制缺失——因此可以在工程层修。

**核心要点**
1. 问题一：Muse agent 在内部测试中**暴露或引用了私密 Signal 消息**。
2. 问题二：在部分内部测试中**编造购买信息**。
3. 处置：内部修复 + 平台层面关于 agent 权限与隔离的讨论。
4. 应要求的保证：**agent 能访问什么、能在输出里呈现什么**，必须是可测试的显式约定。
5. 建议验收用例：① 让它访问一个不该读的会话，看是否被拒并留痕；② 问一个它没有数据支撑的问题，看是否明确说"不知道"。

**怎么读**
10 分钟。给产品加这两个用例，成本极低，能挡住大部分"看起来能用但会出事"的版本。

### 3. Tether 0.4.0：录制轨迹的确定性回放，让 agent 变更可回归

- **来源与日期**：Tether 0.4.0，2026-11-22 发布
- **链接**：https://aiagentstore.ai/ai-agent-news/this-week

**为什么现在读**
改 prompt、换模型、收紧权限——这些变更现在大多靠"跑几个例子看看"。Tether 的做法是把**录制的 agent 运行**变成可回放的测试：**不调用模型**直接重放，然后断言工具调用序列、最终文件内容、是否超出步数/成本上限。这让 agent 变更第一次能进 CI 门禁。

**核心要点**
1. 能力：回放录制轨迹，**不请求模型**即可执行。
2. 可断言项：**调用了哪些工具**、**最终文件内容**、**是否遵守步数与成本上限**。
3. 用途：合并前验证 prompt、工具权限、模型升级、安全规则的变更。
4. 关键限制：回放只对**相同输入与已录制响应**成立；换模型或改 prompt 后的差异需新录制覆盖。
5. 落地建议：把"改 prompt/工具/权限"的 PR 接进 CI 门禁，让回放失败阻断合并。

**怎么读**
15 分钟。今天可做：挑 5 条有代表性的历史运行录下来，作为你 agent 的第一个回归集。

### 4. Replay Fidelity：回放保真度决定评测是否可信

- **来源与日期**：arXiv:2611.11216（**日期未确认**，按索引页收录；补读）
- **链接**：https://export.arxiv.org/pdf/2611.11216

**为什么现在读**
它与必读 3 构成一对：回放做门禁很好用，但**回放能复现多少真实失败**决定了门禁是否可信。该工作在 **71 个历史 AppWorld 失败**上测回放保真度，把"准入"的差距从 **26 压到 4**——不解决保真度，回放结论会系统性偏离真实行为。

**核心要点**
1. 对象：**71 个历史 AppWorld 失败**案例的回放保真度。
2. 关键数字：准入差距 **26 → 4**（改进后更接近真实失败分布）。
3. 工程含义：回放是"同输入 + 已录制响应"的确定性验证，**不能证明换模型/改 prompt 后的行为**。
4. 建议：给回放集做**保真度抽检**——随机抽 N 条，用真实模型重跑，看结论是否一致。
5. 提醒：日期与实验细节未直接核验。

**怎么读**
15 分钟。配合必读 3 使用：**回放做门禁，抽检保真度做校准**，缺一不可。

### 5. Multi-step SWE：长链条任务，最强模型仅 18.5%

- **来源与日期**：arXiv:2611.07166，2026-11-06（补读）
- **链接**：https://arxivsignals.io/papers/2611.07166

**为什么现在读**
大多数基准只看"单步能否修好"，这个专门测**依赖链**：一个任务的第 5 步必须建立在第 1–4 步的产物之上。结果是九个前沿模型里最强的只解出 **18.5%**，且有 **38/69** 个任务**没有任何模型解出**——这比"平均分差几个点"更能说明长程工程的真实水位。

**核心要点**
1. 规模：**69 个任务**，每个任务是 **5–15 步**的依赖链。
2. 语言：**9 种**。
3. 结果：最强模型 **18.5%**；**38 个任务**无人解出。
4. 解读：失败集中在"前一步的隐性约束在后续被遗忘"——与终止滞后、上下文断裂是同一族问题。
5. 使用提醒：数字来自索引转述，建议以原文评分口径为准。

**怎么读**
15 分钟。对你团队的含义：**别用单步任务的成功率去估长程交付**；至少要有一条"多步依赖"的验收链。

### 6. Agent READMEs：2,303 份上下文文件的实测

- **来源与日期**：arXiv:2511.12884，2025-11-17（补读）
- **链接**：https://paperswithcode.co/paper/2511.12884

**为什么现在读**
所有人都在写 `AGENTS.md` / `CLAUDE.md`，但很少有人量过它们到底写了什么。这份实证研究统计了 **1,925 个仓库里的 2,303 份 agent 上下文文件**，给出了内容分布——最刺眼的结论是**安全与性能提示的覆盖率不到 15%**。

**核心要点**
1. 样本：**1,925 个仓库、2,303 份**上下文文件。
2. 内容分布：构建/运行命令 **62.3%**、实现细节 **69.9%**、架构 **67.7%**。
3. 短板：**安全 14.5%**、**性能 14.5%**。
4. 含义：绝大多数上下文文件在教 agent"怎么跑"，而不是"不能做什么"——这恰好与"规则会从 prompt 里丢失"（11-23 的 Formalize or Lose It）互为因果。
5. 使用建议：把安全/禁止项从上下文文件里抽出来，做成**可执行检查**，而不是期待 agent 每次读到。

**怎么读**
15 分钟。对照检查你自己的 `AGENTS.md`：有没有"禁止项"？有没有"性能红线"？如果都没有，你缺的正是最贵的那部分。

## 四、今日观察

**1. "能力自报"与"可核验"之间，隔着三道折扣。**
OpenAI 报 46% 独立完成，但 Multi-step SWE 只有 18.5%、SWE-CoVork 完整交付不足 8%、回放保真度还要再打折。三者不矛盾——它们测的是**不同长度的任务**。做交付预估时，先问"我的任务链有多长"，再套对应数字。

**2. 回放是门禁，不是证明。**
Tether 让"改 prompt 就回归"变得廉价，但 Replay Fidelity 提醒：回放只覆盖已录制的输入与响应。**门禁 + 保真度抽检**才是完整方案；只做前者，会在换模型时给出虚假的安全感。

**3. 上下文文件正在教 agent"怎么跑"，而不是"不能做什么"。**
2,303 份文件的统计里，安全与性能提示各只有 14.5%。这解释了为什么"规则在交接中丢失"——一开始就没写，或者写了也没被执行。**把禁止项做成可执行检查**，是唯一能在多 agent 协作里不丢的办法。

**4. 越权与编造，是同一个"缺少显式约定"的问题。**
Muse 的两类事故都不是能力不足：一类是权限边界没写清，一类是事实来源没约束。可以用两个测试用例挡住大部分风险——**越权访问**与**无依据断言**。
