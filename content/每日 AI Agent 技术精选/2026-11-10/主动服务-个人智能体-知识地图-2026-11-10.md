# 主动服务（个人智能体）知识地图

> **主题**：Agent 开发中的「主动服务」——从「你问它答」到「它先开口」
> **整理日期**：2026-11-10 ｜ 覆盖：学术主干 8 篇 / HCI 经典 6 篇 / 产品一手材料 4 份 / 工程长文 4 篇
> **一句话**：主动服务不是「agent 更自主」，而是把**「什么值得现在占用你的注意力」这个判断**从人手里挪到机器手里——所有工程难点、产品风险、伦理争议，全长在这个「挪」字上。

---

## 0. 先看结论（如果你只读 60 秒）

1. **主动服务有三条彼此独立的轴：发起（谁开口）、判断（谁拍板）、执行（谁动手）**。业界最常犯的错是把它们捆在一起谈「自主性」。正确的组合是：**发起上极度主动，判断上给出理由，拍板上极度克制**。
2. **「事件发生了」≠「你该开口」**。中间必须有两层过滤：相关性（跟你当前目标有关吗）和时机（你现在能被搭话吗）。跳过这两层的产品，本质是「换了皮的 webhook 转发器」。
3. **打断是有价格的，而且价格随时刻浮动 20 倍以上**。按公开的工程估算（收益 10 分钟、成本 15 分钟），**60% 命中率只是打平**。这就是为什么「模型置信度」不能直接当产品阈值。
4. **学术上已经把问题拆干净了**：ProAgentBench 把主动帮助拆成 `timing prediction` + `assist content generation`；Pare 把 App 建模成有限状态机以便模拟「活跃用户」；ProAct 把「交互之间的空闲算力」当成可投资源。三篇合起来就是「何时 / 说什么 / 提前做什么」。
5. **产品侧三种取向已经分化**：Pulse = 每日简报（低打扰、高覆盖）；Gemini Personal Intelligence = 默认关闭 + 逐应用授权（隐私优先）；Copilot Autopilot / ambient agent = 常驻后台持续干活（生产力优先）。没有一种是「全自主」。
6. **判断一份主动服务做没做工程，只看一件事：有没有人在「闭嘴」这件事上做过设计**。默认开口、靠阈值事后补，永远补不完。

## 1. 概念校准：先把「主动」这个词拆开

### 1.1 三代交互范式（这张表是整篇的地基）

| 维度 | CLI（命令） | Chat（对话） | Proactive（主动） |
|---|---|---|---|
| **谁发起** | 人，精确指令 | 人，给意图 | **机器，读上下文先判断** |
| **机器承担什么** | 执行 | 补细节、澄清 | **判断「什么值得现在说」** |
| **人的角色** | 操作员 | 提问者 | **审查者 / 否决者** |
| **失败形态** | 报错（响，但你立刻知道） | 坏答案（看得见，你能改） | **打断（你没看见，但已经付费了）** |
| **你不用它时的价值** | 0 | 0 | **仍在累积**（它在后台观察、准备） |
| **真正省下的是** | 手 | 手 + 一部分脑 | **脑（决策前的筛选）** |

最后一行是理解整个赛道的钥匙：chat agent 帮你处理**你已决定要处理**的信息；proactive agent 帮你决定**哪些信息值得处理**——往上游挪了一格。

### 1.2 学术定义：主动住在「指令没说完的地方」

UIUC + Google + Stanford + Berkeley + CMU 的联合综述《Proactive AI for Superintelligent Agents》（Ke Yang, Jiateng Liu 等，2026，1,410 篇引用文献 / 80 篇深读 / 13 个应用域）给了一个我认为目前最精确的定义：

> **Proactiveness is the ability to exercise *delegated residual discretion*.**
> （主动性 = 行使「被委托的剩余裁量权」。）

配套的两个概念：

- **explicit task instructions（显式任务指令）**：brief 里写明的目标、约束、资源、计划。
- **residual decision space（剩余决策空间）**：brief 没说的部分——偏好权衡、流程顺序、意外应对、重规划。

于是主动性有了可测量、可授权的边界：**agent 在剩余决策空间里做决定，但不越出显式约束**。这一句话同时解释了「为什么主动有用」（长周期任务无法在开头写全）和「为什么主动危险」（剩余空间也是越权的入口）。

该综述把能力拆成 **6A**：`Awareness`（维持情境）/ `Anticipation`（识别未来需求）/ `Agenda formation`（形成承诺）/ `Arbitration`（裁定是否该介入）/ `Action`（在授权内行动）/ `Adaptation`（从结果学习）。作者特别指出：**Anticipation 和 Arbitration 是自发起工作独有的两个需求**，其余四个在普通 agent 里已有成熟角色，但「主动版本」需要实质改造。

### 1.3 四个容易混的名词

| 名词 | 触发者 | 核心能力 | 典型代表 | 常见误读 |
|---|---|---|---|---|
| **Ambient agent** | 事件流 | 监听、并发处理多个事件 | LangChain email assistant | 「无人值守全自动」——官方明确否认 |
| **Proactive agent** | 上下文 + 事件 | 判断需求、发起帮助 | ProactiveAgent、Pulse | 「更聪明的通知」——它是决策系统 |
| **Personal agent** | 用户长期数据 | 个性化、持续性、主动性 | Gemini Personal Intelligence | 「读我全部数据」——默认关闭 + 逐应用授权 |
| **Autonomous agent** | 自己定的目标 | 自主规划与执行 | AutoGPT 一类 | 和主动混为一谈——**这是最关键的一次偷换** |

**proactive ≠ autonomous decision-making**：前者是「谁发起」，后者是「谁拍板」。把两者混同，产品就会从「贴心」滑向「越界」。

## 2. 为什么是现在：三大地基

主动服务在 2010 年代就有人做（Google Now、Cortana），没成。差别不在模型聪明程度，而在**它有没有「值得主动」的前提条件**。

| 地基 | 缺了会怎样 | 今天的解法 |
|---|---|---|
| **持久记忆** | 不知道你昨天卡在哪，就没有判断依据，只能猜 | 长期记忆 + 语义检索的 namespaced KV；operational working set |
| **Agent runtime / sandbox** | 关掉标签页状态就蒸发；长跑任务失败会带走主环境 | 隔离沙箱 + 可暂停/恢复的执行状态（checkpoint） |
| **事件触发** | 只能轮询或定时器，要么慢要么贵 | CDC / webhook / cron + 分布式锁 + 幂等 |

三者互相支撑，缺一不可：**无记忆** → 临场判断靠薄上下文；**无 runtime** → 记忆无法在你离开时工作；**无 trigger** → 退回定时器。任何「主动」产品如果这三样只做了一样，它的主动必然是表演性的。

同一个模型、同一个 prompt、同一套工具，**唯一差别是持久记忆**，效果差距能有多大？《Continuants: Toward a Theory of Behavioural Persistence in Long-Running LLM Agents》（Zenodo DOI 10.5281/zenodo.20349035）的配对客服实验给了一个刺眼的答案：

- **有记忆的 agent，每工单工具调用效率高 3.7–4.9 倍**，且差距随会话拉长而扩大；
- 但让人做**成对偏好比较**时，**无状态对照组赢下 74.5%–80.7%** 的决定性比较（绝对打分完全看不出这个差距）。

作者把机制命名为 **「New Guy Syndrome」**：无记忆 agent 会持续保持道歉、过度配合、客气的「新人腔」，用礼貌和含糊掩盖上下文缺失——单看每条回答都不算差，成对比较时立刻露馅。给工程的含义很直接：**记忆的价值不能靠绝对打分评测，必须用配对/偏好评测**。

## 3. 学术主干：五篇把问题拆开的论文

### 3.1 一张对照表

| 论文 | 回答的问题 | 方法核心 | 关键数字 |
|---|---|---|---|
| **Proactive Agent**（arXiv 2410.12361，清华 THUNLP + 面壁，ICLR'25） | 模型能不能学会「该不该主动」？ | 真人活动 → 生成主动任务 → 人工标注 accept/reject → 训 reward model 当自动评估器 → 造 ProactiveBench → 微调 | **F1 = 66.47%**，超过所有开源/闭源基线；ProactiveBench **6,790 events** |
| **ProAgentBench**（arXiv 2602.04482） | 真实场景里怎么评？ | 分层框架：**timing prediction + assist content generation** 两段；隐私合规真实数据 | **28,000+ events、500+ 小时**真实会话；**burstiness B=0.787**；长期记忆显著提升预测准确率 |
| **Pare**（Apple ML Research，arXiv 2604.00842） | 怎么在「有状态 App」里测？ | 把 App 建模为**有限状态机** + 动作空间；跑 user simulator + proactive assistant 两个 LLM agent | **Pare-Bench: 143 个任务**，覆盖 communication / productivity / scheduling / lifestyle |
| **ProAct**（arXiv 2605.25971） | 空闲时间该干什么？ | 用对话历史 + 持久记忆预测即将到来的需求，在提问前迭代取信息、补知识缺口 | 轮次 **−14.8%**、用户投入 **−11.8%**、幻觉率 **−28.1%**；ProActEval **200 场景 / 40 领域** |
| **ProVoice-Bench**（arXiv 2604.15037） | 语音主动会不会更糟？ | 首个主动语音 agent 评测；4 类新任务、1,182 样本、多阶段合成 | 主要失败模式：**over-triggering** + 推理不足 |

### 3.2 各自最值得抄的一点

**ProActive Agent 的「reward model 当裁判」**：主动行为没有唯一正确答案，人工标注贵且慢。它的做法是把「人会不会接受这次主动帮助」变成一个可训练的判别器，然后用它当自动评估器批量造数据。**这套「判别器 → 数据 → 微调」的飞轮，是所有主动服务做冷启动时最该复用的方法论。**

**ProAgentBench 的「burstiness」**：真实人的交互是**突发**的（一阵密集、一阵沉寂），LLM 合成数据是均匀的（B=0.787 这个指标就是用来证明差异的）。工程含义：**用合成数据训出来的时机预测器，会系统性地误判「什么时候该安静」**——因为它没见过真正的沉寂。

**Pare 的 FSM 建模**：把 App 当扁平 tool-calling API，抓不住「有状态、顺序性」的交互（比如「先打开草稿，再改收件人，再发送」）；而主动介入恰恰发生在中间状态。**它的 user simulator 是在 FSM 上跑的 ReAct agent，带动作约束**——这是目前最接近「真实用户会怎么动」的评测装置。

**ProAct 的「空闲算力」视角**：agent 只在被 prompt 后才算，等于把 99% 的时间浪费了。把这段时间用来**预先取信息、补缺口、备证据**，用户提问时就能直接给结论而非「我去查一下」。注意它同时降了轮次、投入和**幻觉**——因为答案是在用户问之前就验证过的。

**ProVoice-Bench 的冷水**：SOTA 多模态模型的头号失败不是「不懂」，是**过度触发**。这个结论对所有模态都成立。

### 3.3 还有两条学术支线

- **对话侧**：`Proactive Conversational AI: A Comprehensive Survey`（Yang Deng, Lizi Liao, Wenqiang Lei, Grace Hui Yang, Wai Lam, Tat-Seng Chua，ACM TOIS，DOI 10.1145/3715097）。它把「主动」定义为 agent **主导对话走向系统侧目标**，覆盖开放域/任务型/信息寻求三类对话。配套还有一篇立场文 `Towards Human-centered Proactive Conversational Agents`（arXiv 2404.12670），提出 **Intelligence / Adaptivity / Civility** 三维度，其中 **Civility（得体）** 正是「不打扰」的学术化表达：「Without thoughtful design, proactive systems risk being perceived as intrusive.」
- **规划侧**：`Proactive Language Agents for Real-World Planning`（ACL Findings EMNLP 2024，https://aclanthology.org/2024.findings-emnlp.636.pdf ），把「主动」形式化为规划问题：目标不完备时先澄清、再规划。

## 4. 交互理论：这件事 HCI 已经研究了 25 年

做 agent 的人常以为「主动」是 LLM 时代的新问题。实际上「系统该不该先开口」有一整套成熟结论，最核心的一篇是 1999 年的。

### 4.1 Horvitz 的混合主动框架（CHI '99）

**Eric Horvitz, _Principles of Mixed-Initiative User Interfaces_**，CHI 1999，引用 2,567。

它的中心论点至今没有被超越：**是否打断，应该由期望效用决定**——把「这次沟通带来的收益」和「打断造成的成本」都建模，再决定行动。混合主动（mixed-initiative）意味着人与系统**都可以发起**，而仲裁权在效用函数里，不在「谁更聪明」里。

配套阅读：
- _In Pursuit of Mixed-Initiative Computing_ — https://erichorvitz.com/mixedinit.htm
- _Reflections on Challenges and Promises of Mixed-Initiative Interaction_（CRA，2007）— https://cra.org/ccc/wp-content/uploads/sites/2/2018/01/mixed_initiative_reflections.pdf

> 注：原文 PDF 为 `application/pdf`，工具链无法直接抽取正文，以上结论来自该文长期被引用的核心主张（期望效用仲裁），未逐字引用。

### 4.2 三条被实证过的 HCI 结论

| 结论 | 证据 | 对工程的直接含义 |
|---|---|---|
| **时机是独立维度，跟内容好坏无关** | MuC 2024 车内主动语音联合分析（DOI 10.1145/3670653.3670672）：某些情境因素本身「适合/不适合」开口；内容相关性则整体提升接受度 | 不要把「相关性模型」当成「时机模型」，两者要分别建模、分别评估 |
| **用户是否愿意回应是可预测的** | IMWUT 3 周田野研究（13 人，改造版 Google Home，DOI 10.1145/3494965）：ML 预测「此刻是否愿意被打断」**准确率 71.6%**；自报无聊/情绪与感知可打扰度显著相关 | 「能否被打断」是个可学的信号，哪怕是弱信号也比没有强 |
| **通知投递方式不可持续** | Dagstuhl Seminar 17161《Ambient Notification Environments》（DOI 10.4230/DagRep.7.4.38）：直接通知数量指数增长，当前投递方式**不会 scale**；出路是环境化、上下文内嵌、不打断 | 长期看，「推送」会被「嵌入到工作流里」替代；现在的卡片式推送是过渡形态 |

另外两条佐证：
- **用户是想要主动的**：`A Survey on Different Means of Personalized Dialog Output for an Adaptive Personal Assistant`（DOI 10.1145/3213586.3226198，1,051 名德语 + 499 名美国被试）发现 proactivity 被明确期待，但对数据使用普遍负面——**期待主动和信任数据是两件事**。
- **主动可以建模成意图推断**：KDD 2016《Contextual Intent Tracking for Personal Assistants》（DOI 10.1145/2939672.2939676）用 KP2（Kalman filter regularized PARAFAC2）做 nowcasting，把「上下文 → 当下意图」建成个性化动态系统。这是 Siri / Google Now 时代的正规做法，今天可以用 LLM 重做一遍。

## 5. 产品侧：三种已经落地的取向

### 5.1 对照表

| 产品 | 触发源 | 输出形态 | 权限姿态 | 最值得学 | 已知失败 |
|---|---|---|---|---|---|
| **ChatGPT Pulse**（OpenAI，2025-09-25） | 聊天记录 + 反馈 + 已连接应用（日历/邮件） | 每日一组个性化卡片，移动端 | 主动**呈现**，不主动执行 | 「一天一次」的节奏感：把打扰总量做成预算 | 卡片相关性依赖上下文质量；Pro 用户限定 |
| **Gemini Personal Intelligence**（Google，2026-01-14） | Gmail / Photos / YouTube / Search | 回答中内联个人上下文 | **默认关闭**，逐应用授权，可随时关 | 把「同意」做成产品第一屏；回答里标注引用了哪条个人数据 | 官方承认 **over-personalization** 与时机失手 |
| **Copilot Autopilot**（Microsoft，2026-09-25） | 常驻后台 + 工作流事件 | 持续产出、跨应用推进 | 长期运行，人审关键节点 | 「persistent, proactive and personal agent that keeps working even when you're not」 | 权限面最大，治理成本最高 |
| **Ambient agent**（LangChain，2025-01-14） | 事件流（邮件等） | 在 Agent Inbox 里以「待办」呈现 | notify / question / review 三档 | **把 HITL 拆成三种模式**，而不是一个「批准」按钮 | 事件风暴下的过触发 |

### 5.2 各自的原文要点

**Pulse**（https://openai.com/index/introducing-chatgpt-pulse/ ，中文版 https://openai.com/zh-Hans-CN/index/introducing-chatgpt-pulse/ ）
官方定位句：「By combining conversation, memory, and connected apps, ChatGPT is moving from answering questions to a **proactive assistant**」。它的关键设计选择是**节奏**：不是实时推送，而是每天一次「为你做过的研究」。这是一个很聪明的降风险手段——**把 N 次打扰压缩成 1 次可预期的打扰**，用户心理账户从「被打断」变成「看简报」。

**Gemini Personal Intelligence**（https://blog.google/innovation-and-ai/products/gemini-app/personal-intelligence/ ，Josh Woodward）
这份公告是「主动服务的前置条件」写得最认真的一份：
- **off by default**，用户逐 app 选择授权，可随时关闭；
- 回答时**尽量标注引用了哪条个人数据**，可当场纠正（"Remember, I prefer window seats"）；
- 可对单次对话关闭个性化，或用临时会话；
- **对健康等敏感数据不做主动假设**（avoid making proactive assumptions about sensitive data like your health）；
- 不直接用 Gmail/Photos 训练，只用 prompt/response 训练。
官方坦承两类失败：**inaccurate responses** 和 **over-personalization**（把不相关的事连起来），以及时机与细微处失手。最有说服力的例子：相册里有几百张高尔夫照片 → 系统判断「你爱高尔夫」，而实际你爱的是**儿子**。这是「相关性 ≠ 意图」的完美案例。

方法论文档：https://ai.google/static/documents/building_personal_intelligence.pdf

**Copilot Autopilot**（https://blogs.microsoft.com/blog/2026/09/25/introducing-the-new-copilot-with-home-code-and-autopilot/ ）
Microsoft 的路线是「常驻」：Home（Chat + Cowork 合一）、Code、Autopilot。Autopilot 的定义句值得抄进 PRD：**"a persistent, proactive and personal agent that keeps working even when you're not"**。配套能力：Copilot Studio 的 persistent agents、**proactive Teams messages**（https://learn.microsoft.com/en-us/microsoft-copilot-studio/advanced-proactive-message ）、M365 Copilot 移动端 proactive push。

**LangChain ambient agents**（Harrison Chase，2025-01-14，https://www.langchain.com/blog/introducing-ambient-agents ）
这篇是「主动服务」最清晰的工程定义来源，四个可直接落地的点：

1. **定义**：「listen to an event stream and act on it accordingly, potentially acting on multiple events at a time」。两个特征：不被人类消息（唯一）触发；允许多 agent 同时跑。
2. **明确反对全自主**：「we do not think that ambient agents are necessarily completely autonomous」——关键在「何时、以何种方式与人交互」。
3. **HITL 三模式**（这套分类到今天仍然最好用）：

| 模式 | 什么时候用 | 系统做什么 |
|---|---|---|
| **notify** | 值得知道，但不该动手 | 只告知，不采取动作 |
| **question** | 缺关键信息 | 停下来问，不许猜（防幻觉） |
| **review** | 动作危险/不可逆 | 必须人批：可 approve、可直接改、可给反馈 |

4. **HITL 的三重价值**：降低上线风险（lower the stakes）、模仿人类沟通方式以建立信任与采纳、为长期记忆提供反馈信号。第 3 点常被忽略——**审批流本身就是数据采集管道**。

它同时列出 LangGraph 的三个必需基建：**persistence**（每个 node 存状态，可暂停等人）、**原生 interrupt**、**长期记忆（带语义检索的 namespaced KV）**，平台内置 cron job。

补充：工作目录里的《深度精讲：Agents Are Going Async》讲的是同一问题的另一个切面（并行与响应性），可以对照读。

## 6. 工程架构：把「主动」做成一条流水线

### 6.1 四段触发链（多数产品只做了 ① 和 ④）

```
① Event      有没有信号？          ← 便宜，事件流/CDC/cron
② Relevance  跟本周重点有关吗？    ← 需要记忆与目标模型
③ Timing     你现在能被搭话吗？    ← 最难，需要状态感知
④ Speak      提示，还是咽下去？    ← 需要阈值与策略
```

大多数产品的实际实现是 `① → ④`，跳过 ②③。后果是：**系统会把每一个「技术上发生了的事」当成「值得说的事」**。这就是「换了皮的 webhook 转发器」。

时机信号本身很薄，但够用：日历状态、最近活动（键鼠/编辑）、响应延迟、你通常保护深度工作的时间段。注意一句反直觉的话：**「日历显示空闲」不等于你空闲**。

### 6.2 决策系统六步（Applied Labs 的抽象）

一句话立论：**「A proactive agent is a decision system, not a notification system. It turns signals into governed actions.」**

主循环：

```
Detect a signal → resolve the customer → load memory
→ apply policy → take an action → write back the outcome
```

（原文是客服场景，把 `customer` 换成 `user / 对象` 即为通用形态。）

**① signal 是观察，不是决策。** 一个可用信号必须有七样东西：

| 要素 | 作用 | 缺失后果 |
|---|---|---|
| 可解析的身份 | 说的是谁/哪一单 | 张冠李戴 |
| 时间戳 + 新鲜度窗口 | 防过期事件迟到触发 | 拿三天前的状态做今天的决定 |
| 严重度 / 置信度 | 决定走哪条通道 | 一切都同级，等于没有优先级 |
| 来源 | 可追溯、可解释 | 出事无法复盘 |
| 去重规则 | 一次事故别发五条 | 用户第一周就静音 |
| 业务 owner | 异常时知道该找谁 | 无人负责的自动系统 |
| 抑制条件 | 什么时候**不该**触发 | 过触发 |

原文那句值得抄进设计文档：**「最好的主动系统，压制噪声事件与触发有用事件同样用心。」**

**② operational memory = 最小可用工作集。** 目标不是把所有事实灌给 agent，而是为**本次决策**凑齐必需项（订单状态、承诺窗口、是否曾就物流联系过、补偿资格、渠道同意、是否需要 owner 复核）。这是「记忆」在主动场景里与 RAG 最大的区别：**你要的不是最相关，而是刚好够决策**。

**③ action policy 是核心抽象。** 九个字段：`Trigger / Audience / Context / Decision rule / Allowed actions / Channel / Frequency / Approval / Fallback / Measurement`。

第一个策略必须**窄**。原文给的样例可以直接当模板：
> 延迟超 1 天触发 → 排除有开放人工工单的客户 → 读订单、历史联系、补偿资格 → 确认延迟且无例外才发 → 例外路由给支持运营并附来源 → 每单最多一条延迟通知 → 跟踪避免的工单数、回复、升级、CSAT。

**④ connectors 要有界。** 好的是业务动作：`check make-good eligibility`、`send approved delay update`、`route review packet to owner`。危险的是裸系统访问：`query anything in the order database`、`send arbitrary outbound message`、`change any CRM owner`。**暴露业务动作，而不是裸系统访问。**

**⑤ 最值钱的往往不是外呼，是主动路由。** 在工单变老之前，把「为什么需要关注 / 什么信号触发 / 查了哪些数据 / 适用什么策略 / 建议下一步 / 该谁接」打包给人类。人从「开始调查」变成「带着上下文开始」。这一条对内部工具类 agent 尤其重要——它几乎不需要「说服用户」，只需要「把人从 40 分钟的上下文重建里救出来」。

**⑥ writeback 才是闭环。** 每次外呼、挽回、路由、交接、失败都写回记忆与分析。没有 writeback 的主动系统，第二次还会犯第一次的错。

🔗 https://appliedlabs.ai/blog/how-proactive-agents-work

### 6.3 触发层与执行层必须分开（Tian Pan 的三个失败模式）

反面起点是一行 crontab：

```cron
0 9 * * * python run_agent.py
```

> 「This works until it doesn't.」

**失败模式 1：执行重叠。** 9:00 的 run 因上游 API 慢跑了 90 分钟，10:00 又起一个；两个实例读同一状态、各自决策、写同一目标 → 重复发票、重复通知、互相矛盾的更新。「fix 不是把 cron 间隔拉长」，而是**把 trigger 层与 execution 层分开**：分布式锁 + 幂等检查（是否已做过）+ 完成记录后再释放锁。

**失败模式 2：用 polling 冒充事件驱动。** 成熟替代是 **CDC**（Kafka + Debezium、AWS DMS、库原生复制流）：**延迟降低 70–90%**，空闲时**零算力成本**。5 分钟一轮的轮询，在变更稀疏时 99%+ 的时间是纯浪费。四类触发源的选择标准基本是「数据源能发什么」：

| 触发源 | 实现 | 延迟/保真 | 适用 |
|---|---|---|---|
| DB 变更 | CDC / trigger → queue | 最低延迟、最高保真 | 自家数据库 |
| API 事件 | webhook → MQ 缓冲 | 中 | 第三方服务 |
| 时间 | cron + 分布式锁 + 幂等 | 最低保真 | 兜底、周期性任务 |
| 状态漂移 | 监控检测指标偏离后发事件 | 中 | 「本该如此」类异常 |

**失败模式 3：幂等不是可选项，它就是架构。** at-least-once 语义下重复是必然的。四步：

```
事件带全局唯一 ID
→ 处理前查 processed-events 表
→ 已处理：直接返回成功
→ 未处理：处理 + 记 ID，同一事务提交
```

常见错误是把「记 ID」放在工作之后的另一次调用里：崩溃会留下「已处理无记录」（重试重复执行）或「有记录未处理」（永远不执行）。

🔗 [Proactive Agents: Event-Driven and Scheduled Automation for Background AI](https://tianpan.co/blog/2026/04/16/proactive-agents-event-driven-scheduled-automation)
同作者延伸：[The Idempotency Crisis](https://tianpan.co/blog/2026/04/19/llm-agents-event-stream-idempotency) ｜ [The Write Side of the Agent（可逆性）](https://tianpan.co/blog/2026/05/07/agent-write-side-reversibility-action-layer) ｜ [The Cascade Problem](https://tianpan.co/blog/2026/04/19/agent-side-effects-cascade-problem-production)

### 6.4 一次完整的分层（把上面拼起来）

```
┌─ 感知层 ─────────────────────────────┐
│ CDC / webhook / cron / 指标漂移       │  → 信号（带 ID、时间戳、新鲜度）
└──────────────┬───────────────────────┘
               ▼
┌─ 相关性层 ───────────────────────────┐
│ 用户目标 / 长期记忆 / 当前项目上下文    │  → 这件事对他重要吗
└──────────────┬───────────────────────┘
               ▼
┌─ 时机层 ─────────────────────────────┐
│ 活动状态 / 日历 / 历史工作节律 / 打扰预算│ → 现在能说吗（可学，71.6% 可达）
└──────────────┬───────────────────────┘
               ▼
┌─ 策略层（action policy）──────────────┐
│ 九个字段 / 通道 / 频率 / 审批 / 兜底    │  → 说、攒着、还是咽下
└──────────────┬───────────────────────┘
               ▼
┌─ 执行层（runtime）────────────────────┐
│ 锁 + 幂等 + checkpoint + 沙箱          │  → 只做授权内动作
└──────────────┬───────────────────────┘
               ▼
┌─ 回写层 ─────────────────────────────┐
│ 结果 / 失败 / 用户反馈 → 记忆 + 指标     │  → 下次更准；也是唯一的信任来源
└──────────────────────────────────────┘
```

## 7. 打断经济学：把「该不该说」算出来

这是目前公开材料里唯一把「打扰」做成可计算模型的一篇：**Xinwei Xiong (cubxxw), _When the AI Agent Starts Prompting You, What Has Actually Changed_**（2026-07-15）。它也是我认为中文作者里最完整的「主动服务」框架文，建议直接当主线读。

🔗 https://github.com/cubxxw/blog/blob/main/content/en/ai-agent/posts/proactive-agent-it-prompts-you.md

### 7.1 收益与成本的定义

**收益 G**：一次准确提示省下的时间。经验值 5–15 分钟，取中位 **10 分钟**。

**成本 C** 由三部分组成：

| 组成 | 量级 | 说明 |
|---|---|---|
| 处理成本 | ≈0.5 分钟 | 看、判断、回应 |
| **重入成本（re-entry）** | **10–20 分钟** | 若你正在深度工作中——这才是大头 |
| **信任折价** | 无法用分钟计价 | 但它是杀手：错几次之后，通道就废了 |

可计价部分：深度工作中 **C ≈ 15 分钟**；本来在摸鱼 **C ≈ 1.5 分钟**。同一个提示在不同时刻，成本可差 **20 倍以上**——这就是「时机」既最难又最值钱的原因。

### 7.2 期望值表

`E = p × G − (1 − p) × C`，取 G = 10、C = 15：

| 命中率 p | 期望收益 E | 结论 |
|---|---|---|
| 0.5 | **−2.5 分钟** | 净损失 |
| 0.6 | **0** | 刚好打平 |
| 0.7 | +2.5 分钟 | 勉强值 |
| 0.8 | +5 分钟 | 明显值 |
| 0.9 | +7.5 分钟 | 值得 |

**结论：60% 命中率只是打平。** 把模型自报的置信度当产品阈值是错的——那个数字长期虚高，且与「这一刻是否该说」不是同一个量。

### 7.3 更真实的公式

```
E_real = p × G − (1 − p) × C − trust_discount(consecutive errors)
```

且一旦信任折价被触发，前两项归零。**收益逐条累积，信任掉得更快**。「保住这个通道」比「最大化通知量」重要得多。

推论三条：

1. **起步就该用保守阈值**，只在观测结果支持时下调。
2. 主动提示**不是普通的平衡分类器**：假阳与假阴代价不对称——漏掉只损失「可能的收益」，打扰则付出「可见的成本 + 通道折旧」。
3. 因此**失败形态应该是「有点安静」**，而不是「用户已静音」。

### 7.4 冷启动是致命的

主动的价值高度依赖「它多懂你」，而这需要时间沉淀。**上线两天的主动 agent 大概率是骚扰**。多数 PM 严重低估这段「净负体验期」；而冷启动恰恰是产品最想「表演活跃」的阶段——**激励方向刚好相反**。

这解释了为什么 Pulse 用「每日一次」、Personal Intelligence 用「默认关闭」：它们都在用产品结构对抗冷启动的冲动。

## 8. 反模式：五种「假主动」

| 假主动 | 表现 | 判据 |
|---|---|---|
| **定时问候** | 每天 9 点「今天想做点什么？」 | 这是闹钟，不是判断 |
| **webhook 转发器** | 有事件就推，跳过相关性/时机 | 消息队列冒充助手 |
| **失忆者** | 第一天就敢替你判断 | 没有记忆的主动是赌博 |
| **只增不减者** | 把「活跃度/推送量」当北极星 | 指标在奖励噪音 |
| **越界者** | 把「主动发起」偷换成「主动决策」 | 不可逆动作没有闸门 |

统一的判据一句话：**看有没有人在「闭嘴」这件事上做过工程**。默认开口、靠阈值事后补，是永远补不完的——因为「默认开口」意味着每个新场景的默认值都是错的。

对应的三条真实事故形态（来自前述工程文）：

- **执行重叠** → 重复发票 / 重复通知 / 互相矛盾的状态更新；
- **重复投递** → 同一个事故发五条；
- **过期触发** → 用三天前的状态做今天的决定（缺新鲜度窗口）。

## 9. 冷水：五条必须正视的风险

**1. 过度触发已被实证。** ProVoice-Bench 把 over-triggering 列为当前模型的主要失败；Gemini 官方公告里也承认时机与细微处的失手。这不是「模型不够强」，而是**「该不该说」本质上是效用判断，不是语言能力**。

**2. 相关性 ≠ 意图（over-personalization）。** 高尔夫照片的案例值得反复引用：几百张照片证明「出现过」，不证明「喜欢」。同理，用户点过一次招聘广告，不代表他在找工作。**从行为反推意图时，必须区分「发生过」和「在意」**——而这需要记忆的**否定证据**（他后来没再碰过），绝大多数记忆系统不存否定证据。

**3. 隐私与同意是前置条件，不是合规章节。** Gemini 的做法（默认关闭 / 逐应用授权 / 标注引用来源 / 敏感数据不主动假设 / 临时会话）可以当成一份「主动服务的准入清单」。特别注意那条：**对健康等敏感领域不做主动假设**——因为主动假设的错误成本远高于被动回答。

**4. 判断错误会复合。** 「读上下文略错 → 排优先级略错」两级小错叠加，会把建议指向完全错误的方向。信息流水线每多一个自动决策就多乘一次误差，而「主动」又加了一环。这也是为什么 action policy 要**窄**：窄策略的误差不会复合，宽策略会。

**5. 长跑 agent 的行为漂移，静态 benchmark 看不见。** Continuants 的反向结果（无状态组赢 74.5–80.7%）提醒我们：**偏好/语气层面的退化，绝对打分测不出来**。做主动服务必须有配对评测（同一情境下有记忆 vs 无记忆、主动 vs 被动），否则你会在「分数上升」的同时「体验下降」。

## 10. 工程清单（可直接当 PR 评审项）

### 触发
- [ ] 触发源是事件而不是轮询？稀疏变更场景是否已换 CDC/webhook？
- [ ] 每个信号带全局唯一 ID、时间戳、**新鲜度窗口**？
- [ ] trigger 层与 execution 层分离？有分布式锁吗？
- [ ] 「处理 + 记录已处理」在**同一事务**里？
- [ ] 有去重规则（同一事故只发一条）？

### 判断
- [ ] 相关性层和时机层是**两个独立模型**，不是一次 LLM 调用？
- [ ] 每次提示都记录了一个估出来的 `p`（不是模型自报置信度）？
- [ ] 「你现在能否被打断」是一等公民（哪怕只用日历 + 近十分钟活动 + 历史深度工作窗）？
- [ ] 记忆给的是**最小可用工作集**，而不是全量事实？
- [ ] 存了否定证据（「他没再碰过」）吗？

### 表达
- [ ] 提示**分层**：可攒到自然休息点的 / 值得现在响一声的 / 必须立刻打断的？
- [ ] 大多数提示落在第一层？（多数产品把一切都当第二层）
- [ ] 有打扰预算（每天/每周上限）？
- [ ] 反馈路径极便宜，且区分「没用」与「有用但不是现在」？（前者调相关性，后者调时机）

### 权限
- [ ] connectors 暴露的是**业务动作**，不是裸系统访问？
- [ ] 不可逆动作（发邮件、动钱、改生产配置、删记录）一律停在 HITL 闸门前？
- [ ] HITL 三模式（notify / question / review）都实现了，而不是只有一个「批准」？
- [ ] 默认关闭 / 逐项授权 / 可解释引用来源（涉及个人数据时）？

### 度量
- [ ] 北极星不是「推送量/活跃度」？
- [ ] 跟踪的是：接受率、后续动作率、静音率、**信任折旧**（连续错误后的响应率变化）？
- [ ] 有配对评测（主动 vs 被动、有记忆 vs 无记忆），而不只是绝对打分？

> 一句话原则：**安全活在 harness 里，不在模型的自觉里。**（Safety lives in the harness, not in the model's good intentions.）

## 14. 这份材料没覆盖到的

诚实标注，避免误导：

1. **Horvitz 1999 的原文正文**未能逐段核对（PDF 无法直接抽取文本），文中对它的引用限于长期被引用的核心主张（期望效用仲裁、混合主动），未做逐字引用。
2. **中文媒体对 Pulse 的二次报道**只做了标题级引用（正文未逐篇核对），数字与细节建议以 OpenAI 官方公告为准。
3. **多 agent 协作下的主动**（谁有权发起、冲突如何仲裁）几乎没有成熟材料，这是明显空白——「六个 agent 都想主动」时的仲裁问题，目前只能借用 6A 里的 `Arbitration` 概念，没有工程方案。
4. **成本侧**：主动服务的算力账（常驻监听 + 事件驱动推理 vs 按需调用）没有找到可靠的实测数据。ProAct 的「空闲算力」是收益侧叙事，不是成本模型。
5. **纵向用户研究**几乎没有：现有研究多为数周级（3 周已是长的），但「主动服务需要时间沉淀信任」意味着真正的效果要按月看。这是学术界和工业界共同的缺口。
