## 一、今日必读（7 条）

### 1. Anthropic《Claude Fable 5.2 and Mythos 5.2》

**为什么现在读**：这不只是一次模型升级——发布文里藏着一个多 agent 编排的里程碑实验：**一个工程师让 Fable 5.2 从空文件夹开始造操作系统，模型协调 1,000+ 个 subagent、连续 8 天写代码/测试/评审，最终产出一个能在笔记本上启动的系统**（含内核、磁盘/键盘/网络驱动、持久化文件存储、窗口、登录界面、安装器）。

**核心要点**
- **Agent 基准全面抬升**：FrontierCode 2.0 49.1%（Xhigh）vs Opus 5.5 45.5%；FrontierSWE v2 69.9% vs 62.3%；Terminal-Bench-Science 74.6%（Mythos 75.3）vs 58.7%；OSWorld 2.1 89.3% vs 87.2%；WANDR 82.1% vs 72.3%。
- **成本/延迟**：$8 / $40 每百万 token（输入/输出），比 5.1 便宜；输出速度提升最多 30%；可选 fast mode 再快 2.5 倍（$16 / $80）。
- **Agent 角色新用法**：Fable 5.2 可以当 **Advisor**（Haiku/Sonnet/Opus 遇到难题时咨询它），也可以当 **Orchestrator**（把简单任务分给更小的模型）——这直接对应"贵模型做规划、便宜模型做执行"的架构。
- **生产信号**：Anthropic 核心代码库中 **>90% 的合并变更由 Claude 编写**（人类指导）；一个 agent 团队把关键生产服务从 Python 迁移到 Rust，启动速度提升约 **26 倍**。
- **安全**：为 Fable 5.2 开发了针对 sandbox escape 等行为的新评估；官方称高风险错位风险仍低。

**怎么读**：先看 *Coding* 一节（OS 实验 + 26 倍迁移），再看 *Effort and efficiency*（High effort ≈ Opus 5.5 Max，成本约一半）。如果你在做 agent 编排，重点研究 Advisor / Orchestrator 两个角色怎么接进现有 harness。

🔗 https://www.anthropic.com/claude-fable-and-mythos-5-2

### 2. LangChain《What Is Eval-Driven Development? How to Improve AI Agents》

**为什么现在读**：把"eval"从上线前的一次性验收，变成和 TDD 一样的开发循环。对任何"改了 prompt 不知道变好还是变坏"的团队，这是一套可以直接照抄的流程。

**核心要点**
- **EDD 三步**：① 定义"好"是什么（写 spec）；② 先写 eval 再写功能；③ 每次改动都跑实验对比。
- **Spec 四要素**：*When*（何时触发）、*Do*（该做什么）、*Don't*（不该做什么）、*Keep intact*（哪些现有行为不能坏）。示例：内部文档 agent 新增 `create_ticket` 工具——报障时调用；how-to 问题不建单；`search_docs` / `web_search` 原有路由不能被破坏。
- **数据集从真实流量来**：用户措辞和边缘 case 往往超出你的想象；LangSmith 可直接把线上 run 加进 dataset。
- **一次只改一个 behavior**：避免多个改动互相污染归因。
- **闭环**：eval 跑在 CI 和生产；线上失败样本回流成新 dataset 条目。

**怎么读**：10 分钟；直接拿你手上正在迭代的一个 agent behavior，按四要素写一版 spec，再补 5–10 条 dataset。重点看它如何避免"修一个坏一个"。

🔗 https://www.langchain.com/blog/what-is-eval-driven-development

### 3. Simon Willison《Locating the source of a mysterious beep with Claude》

**为什么现在读**：一个"agent 从零造出真实世界系统"的完整案例——不是 demo，是为了解决家里储藏室间歇性蜂鸣，用多台设备做声源三角定位。它展示了 coding agent 在"硬件 + 网络 + 时序"这类 messy 问题上的实际工作方式。

**核心要点**
- 问题本身很"脏"：蜂鸣间隔长、房间堆满箱子、人耳无法定位。
- Simon 让 Claude Code 构建了 **Beep Locator**：多台设备分散在房间，记录蜂鸣到达时间，做三角定位。
- 文章 2,000 字左右，包含失败、调整和最终方案——比"一次成功"的 demo 更有参考价值。
- 对 agent 开发者的启示：**agent 的价值往往在"一次性、非复用"的脏活上**，而不是替代标准工程流程。

**怎么读**：当故事读，15 分钟；注意观察 Simon 如何拆问题、如何给 agent 提供"可验证的信号"（时间戳、设备 ID），这比 prompt 技巧更可复用。

🔗 https://simonwillison.net/2026/Nov/9/mysterious-beeps/

### 4. MemoryDojo：Agent memory 的投毒基准（arXiv 2611.09721）

**为什么现在读**：昨天 Anthropic 讲了"memory 怎么组织"，这篇讲"memory 怎么被攻击"。当 agent 开始跨会话持久化记忆，**记忆投毒**就是一个独立的攻击面——而且比 prompt injection 更隐蔽，因为污染会留在系统里。

**核心要点**
- 构建了 **155 条多会话、长时程轨迹**，覆盖 4 个领域，支持 5 种 memory 系统。
- 专门评测"通过 agent memory 实施的投毒"：攻击者不需要每次对话都注入，只要让一条错误记忆被写入并长期保留。
- 对做 memory / 个人助理 / 长期 agent 的团队：**记忆的写入权限、来源标注、过期与纠错机制**要和检索一起设计，而不是事后补。
- 与 Anthropic 的 "dreaming" 形成对照：dreaming 是"用 transcript 纠错"，投毒是"让 transcript 本身不可信"——所以纠错必须有独立 ground truth。

**怎么读**：先看 abstract 和 threat model；如果你在做 memory，重点看它如何定义"污染成功"以及五种 memory 系统的差异。

🔗 https://arxiv.org/abs/2611.09721

### 5. MEMOIR：免训练的记忆生命周期（arXiv 2611.07631）

**为什么现在读**：和 Anthropic 的 memory 长文同一天前后出现，思路互补——不训练模型，靠"写入前判断 + 事后归因"管理记忆生命周期。

**核心要点**
- **Training-free**：不改模型权重，用 judge-gated consolidation（判断是否值得写入）+ retrospective attribution（事后把结果归因到具体记忆）管理记忆。
- 在 **1,905 条去重 LoCoMo QA** 上，evidence recall@5 比裸 cosine 检索提升 **11.92 个百分点**。
- 对工程团队的启示：memory 的效果很大程度取决于"写入策略 + 归因"，而不是换更大的向量库。
- 与 Anthropic "不要规定记什么、给模型判断权"的结论可以互相印证。

**怎么读**：看 method 部分的两个 gate（consolidation / attribution）；对照你现在的 memory pipeline，问"谁决定这条记忆该不该留"。

🔗 https://arxiv.org/abs/2611.07631

### 6. Simon Willison《parse_number() as a SQLite extension: C vs Rust》

**为什么现在读**：一个"让 agent 做性能优化"的漂亮案例，而且有硬数字。它说明：**给 agent 一个明确的基线（"追上或超过 Rust"），比笼统的"优化一下"有效得多。**

**核心要点**
- 起点：Rust 扩展 321 KB（rusqlite）/ 298 KB（sqlite-loadable-rs），C 扩展只有 14 KB——但 **Rust 更快**，因为 Rust 的 `strtod` 约是 C 的两倍快。
- 关键 prompt：*"写一个 C 解析函数，追上或超过 Rust 实现"*。Claude 用 **Clinger's fast path** 做到了。
- 200 万行、每行净耗时（越低越好）：

  | 数据 | 初始 C | 新 C | rusqlite | sqlite-loadable |
  |------|--------|------|----------|-----------------|
  | 混合 | 67 ns | **19 ns** | 46 ns | 41 ns |
  | 纯整数 | 25 ns | **16 ns** | 36 ns | 32 ns |
  | 纯小数 | 106 ns | **18 ns** | 55 ns | 47 ns |

- 方法论：先让 agent 做"两种实现的对比"，再给明确目标做"追赶"，最后让它把过程写成 research report。

**怎么读**：10 分钟；重点抄它的 prompt 结构——**基线 + 目标 + 可测量指标**。做 agent 性能调优的人可以直接复用这个"对比 → 追赶 → 报告"三段式。

🔗 https://simonwillison.net/2026/Nov/8/sqlite-parse-number-c-vs-rust/

### 7. Google Gemini 把个人 Drive 文件与邮件送进人工审核

**为什么现在读**：如果你在 Gmail / Drive / Workspace 之上构建 agent，这是一个必须知道的**信任边界变化**。Google 2023 年明确承诺个人内容"不会被人工审核员看到"，现在这个承诺被悄悄反转了。

**核心要点**
- 2023 年博客承诺：Gmail / Docs / Drive 的个人内容 "is not seen by human reviewers"。
- 更新后的 Google Help Answer 16836988，以及 2023 年博客在 **10 月 16 日**的编辑，明确承认连接的 Drive/邮件会进入人工审核流程。
- 官方警告原文大意：审核员看到的"可能就是这个邮件或文件本身"，"如果应用里有你不想让审核员看到的机密信息，不要把它连接到 Gemini Apps"。
- 实测显示这种摄取确实会发生（repo 里有复现与文档）。
- 对 agent 开发者的含义：**"模型能访问"不等于"数据只留在模型推理里"**。做企业 agent 时，数据流向要写进 threat model，而不只是隐私政策。

**怎么读**：15 分钟；重点看 repo 里的时间线与官方链接。如果你在做 Workspace 集成，立刻检查数据分类与合规边界。

🔗 https://github.com/thisisme6598/gemini_files

## 三、今日观察

1. **多 agent 编排进入"工程量级"**：1,000+ subagent、8 天、一个能启动的 OS——这不是"模型更聪明"的单点故事，而是 **harness 设计（任务分解、评审、合并、冲突解决）** 的胜利。接下来区分团队的不再是"用哪个模型"，而是"能不能组织 1,000 个 agent 不互相踩踏"。
2. **Eval 正在左移 + 右移**：左移到开发循环（EDD：先写 eval 再写功能），右移到生产（线上失败回流 dataset）。Fable 5.2 的 FrontierCode 也是同一逻辑——**"会不会被 merge"比"像不像代码"更接近真实目标**。
3. **Memory 研究分成两路**：一路研究"怎么组织"（Anthropic dreaming、MEMOIR 的 gate + 归因），一路研究"怎么被攻击"（MemoryDojo 的投毒）。两条线必须一起看——**没有独立 ground truth 的 memory，纠错机制本身也会被污染**。
4. **模型静默漂移是隐形风险**：HN 上 729 分的 "Opus 5.5 nerfed?" 讨论提醒我们，同一个 prompt 的行为可能在某个日期后变化。Agent 的 eval 不只要测"能不能完成"，还要测"分布有没有漂移"。
