## 二、今日必读

### 1. OpenAI：agent 独立完成 46% 的"2–4 小时"研究任务

- **来源与日期**：OpenAI 报告，2026-11-22（要点经 AI Agent Store 周报转述）
- **链接**：https://aiagentstore.ai/ai-agent-news/this-week

**为什么现在读**
这是少见的、**按任务时长分层**的能力披露，而不是一个笼统的 benchmark 分数。它给出的最有价值信息不是 46%，而是**任务类型之间的巨大差异**：监控类做得好，启动类与写推理/服务软件明显更差。对准备把研究工作交给 agent 的团队，这个分层比总分更能指导排期。

**核心要点**
1. 定义：以"人类需要 2–4 小时"为口径的研究任务，agent **独立完成率 46%**，而 3 月时为 **23%**。
2. 更长任务：4–8 小时口径从 **13% → 35%**。
3. 结构性差异：**监控训练运行**表现较好；**启动训练**、**编写推理与服务软件**明显更弱。
4. 使用建议：给 agent 明确的、有边界的调研/监控/初稿任务，并设审批闸门；**把"独立完成率"与"事实准确率"、"纠错成本"分开度量**。
5. 提醒：以上为公司自报，未独立复现。

**怎么读**
10 分钟。落地方法：把你团队的研究任务按"时长 × 类型"打标，只把"监控/汇总/初稿"类先交出去；"启动/上线/写服务"类保留人工主导。

### 2. Bell Canada 遭"agentic"攻击者入侵：非生产环境也需要生产级防护

- **来源与日期**：威胁简报，2026-11-21 报道（事件发生于 11-17；经 AI Agent Store 周报转述）
- **链接**：https://aiagentstore.ai/ai-agent-news/this-week

**为什么现在读**
这是"agentic 攻击者"从概念进入**真实入侵事件**的一条：攻击者访问的是**预生产**的 Maximo 环境（用于下单与开通电信网络连接），偷走的是企业客户信息与部分网络相关 IP 数据。它同时打破两个幻觉——"非生产环境不重要"和"攻击者只会按固定脚本走"。

**核心要点**
1. 目标：**预生产** Maximo 环境（负责订购与开通网络连接），并非面向客户的生产系统。
2. 被窃数据：姓名、职位、企业邮箱、电话、地址，以及部分网络相关的 IP 数据。
3. 为什么叫"agentic"：攻击者能跨系统自适应推进，而不是执行单一路径脚本。
4. 直接风险：这些数据足以支撑定向钓鱼、冒充、凭据窃取与后续入侵，即使客服业务未中断。
5. 建议动作：把非生产环境按生产标准管；把"类 agent 的自动化与服务账号"收到最小权限；对"发现 → 提权 → 收集 → 外传"的异常序列告警。

**怎么读**
15 分钟。今天就查一件事：预生产环境里是否存在能访问生产数据的凭据？这一条通常比任何检测规则都更有效。

### 3. Meta Muse 内部报告：读到私密 Signal 消息、编造购买信息

- **来源与日期**：内部员工报告，2026-11-21（经 AI Agent Store 周报转述）
- **链接**：https://aiagentstore.ai/ai-agent-news/this-week

**为什么现在读**
它把 agent 两个最典型的失效模式放在同一个产品里：**权限过宽导致越界读取**，以及**对外部事实的编造**。这正好对上昨天的两条工程结论——权限要在系统层收（而不是靠模型自律），事实要能溯源（而不是靠模型自信）。

**核心要点**
1. 问题一：Muse agent 在内部测试中**暴露或引用了私密 Signal 消息**。
2. 问题二：在部分内部测试中**编造购买信息**（fabricated purchase information）。
3. 处置：内部修复 + 平台层面关于 agent 权限与隔离的讨论。
4. 买方/平台方应要求的保证：**agent 能访问什么、能在输出里呈现什么**，必须是可测试的显式约定，而不是产品文档里的一句话。
5. 建议的验收测试：把"越权读取"与"事实编造"做成对抗用例，纳入上线门禁。

**怎么读**
10 分钟。给自己产品加两个测试用例即可：① 让 agent 访问一个它不该读的会话，看是否被拒绝并留痕；② 问一个它没有数据支撑的问题，看是否明确说"不知道"。

### 4. OpenAI 小范围测试 Dots：常驻 agent 进入付费产品

- **来源与日期**：OpenAI，2026-11-21（经 AI Agent Store 周报转述）
- **链接**：https://aiagentstore.ai/ai-agent-news/this-week

**为什么现在读**
"常驻 agent"从演示走向**付费用户的默认预期**：会话之间持续运行、能连应用、在后台推进任务。这会改变两件事——用户对 agent 的产品预期，以及你必须提供的权限/审计能力。

**核心要点**
1. 形态：**persistent, always-on** agent，在对话之间运行，可连接应用。
2. 范围：先小范围 ChatGPT Plus 用户测试，并向符合条件的 **Business Standard** 工作区开放。
3. 对集成方的含义：如果你的 agent 支持后台任务/回调/事件触发，用户会默认它"一直在跑"。
4. 必须配套：更硬的权限控制、速率限制、审计日志——否则一次越权就是持续性的。
5. 阅读提醒：具体能力边界与限制未见完整披露，以官方文档为准。

**怎么读**
10 分钟。检查你的 agent 是否具备三件事：后台任务的**幂等**、**可撤销**、**可审计**。缺一件就不要做成"常驻"。

### 5. SWE-Recreation：只看像素，把应用重建出来

- **来源与日期**：arXiv:2611.26311（cs.SE），2026-11-19 提交
- **链接**：https://arxiv.org/abs/2611.26311

**为什么现在读**
大多数 coding 基准给的是"目标 + 规格"，这个基准给的是"**只有一个能点的界面**"：agent 只能看渲染后的像素、用鼠标键盘操作，看不到 DOM、源码、日志或后端。这更接近"接手一个没人文档化的老系统"，也更能暴露**探索能力**的短板。

**核心要点**
1. 设定：agent 只看到**渲染像素**，通过指针与键盘操作，**无 DOM / 源码 / 日志 / 后端**访问；需要自己探索、生成复刻品、并在评测前自检。
2. 规模：**54 个真实应用**（28 个网站 + 26 个 Android 应用），**1,446 条隐藏需求**，描述多步、有状态的工作流，并显式排除超出重建范围的行为。
3. 评测：固定 judge 依据**像素证据**判定工作流；另一个事后 judge 估计**探索覆盖度**。
4. 结果：五个前沿系统最高仅 **0.530 加权保真度**，**22.9%** 的需求被完全复现（按应用等权平均）。
5. 诊断：作者把差距拆成"探索证据不足"与"实现不到位"两类——**先看不全，再做不对**。

**怎么读**
20 分钟。对做 browser/computer-use agent 的团队，这是目前最贴近真实任务的评测之一；重点看它如何用"探索覆盖度"把失败归因分开。

### 6. EverydayBench：最好配置 54.55%，加时间不等于加完成

- **来源与日期**：arXiv:2611.25146，2026-11-20（据索引与摘要转述，未逐节读原文）
- **链接**：https://arxiv.org/abs/2611.25146

**为什么现在读**
"日常任务"是最难评的一类：它们不需要高深推理，但要求把多件事按顺序做对。这个基准的价值在于**否定了一个常见假设**——给 agent 更多时间/预算，并不自动带来更多完成。这与上周 Termination Lag（解对了还继续跑）形成呼应。

**核心要点**
1. 规模：**77 个人工编写的日常任务**、**23 种 agent 配置**。
2. 结果：最好的配置通过率 **54.55%**——接近一半的日常任务仍失败。
3. 反直觉结论（摘要）：**"花更多时间本身并不会产生更多已完成任务"**。
4. 解读：失败多来自流程性错误（顺序、状态、遗漏），而不是"想得不够久"；加预算只会放大无效探索。
5. 使用提醒：数字与结论据索引页转述，**以原文的评分口径为准**。

**怎么读**
15 分钟。对照自查：你的 agent 失败样本里，有多少是"步骤顺序错"而不是"知识不足"？如果是后者居多，加预算没用，要改流程与状态管理。

### 7. Muru 与"AI 作为一种生活方式选择"：19 篇开发日志里的分工

- **来源与日期**：Graham Dumpleton 的 Muru 系列，2026-11-04 至 11-22（Simon Willison 11-21 推荐）
- **链接**：https://github.com/muruhq/muru ｜ https://grahamdumpleton.me/posts/2026/11/ai-as-a-lifestyle-choice/

**为什么现在读**
这是一份罕见的"**边做边公开**"的 AI 辅助工程记录：mod_wsgi 作者用三周写了 19 篇设计日志，边设计边用 AI 实现一个 Rust 版 Python 应用服务器（Muru）。其中《AI as a lifestyle choice》那篇说清了分工的真相——AI 承担了大量表面工作，但**"判断什么还不够好"仍然是人**。

**核心要点**
1. 项目：Muru，一个面向 ASGI/WSGI 的 Rust 服务器，目标是开发与生产都能用；作者是 mod_wsgi 的原作者。
2. 节奏：**三周 19 篇**设计/实现日志（从"二十年 mod_wsgi 之后"到"lazy imports 什么时候有用"）。
3. 核心观点（引述）："AI 可能在表面做了很多工作，但**决定什么还不够好**仍然是我；二十年犯错的积累在这里起作用。"
4. 方法价值：把"设计决策"写成公开日志，本身就是给 agent 提供**可检验的上下文**——比让 agent 猜架构更有效。
5. 对团队的启示：AI 辅助不是"减少思考"，而是把人的时间从"写"移到"判断与验收"。

**怎么读**
20 分钟：先读《AI as a lifestyle choice》，再挑两篇技术日志（例如"releases, not restarts"或"canaries without a service mesh"）看设计与实现的往复。

## 四、今日观察

**1. 平均分正在失去信息量，"任务类型 × 时长"才是选型依据。**
OpenAI 的 46% 与 35% 背后是"监控强、启动弱"；SWE-Recreation 的 22.9% 与 EverydayBench 的 54.55% 都在说同一件事：**agent 的能力高度依赖任务结构**。对工程团队，正确的做法不是问"哪个模型分高"，而是把自己的任务按类型分层，逐层测。

**2. "agentic 攻击者"进入真实事件，资产分级要重做。**
Bell Canada 的事件打的是**预生产**环境，却拿到了企业客户信息与网络 IP 数据。这提醒我们：**环境标签（prod/staging）不等于数据敏感度**。真正该问的是"这个环境里有哪些凭据能通向哪里"——这也是 agent 平台自身的安全模型问题。

**3. 常驻 agent 的产品化与权限事故是同一枚硬币。**
Dots 开始给付费用户提供"一直在跑"的 agent；同一周 Meta 的内部报告显示"读到私密消息 + 编造购买信息"。**always-on 的第一性问题不是能力，而是权限、隔离与可撤销**。任何准备做后台常驻的产品，都应先把幂等、撤销、审计三件事补齐。

**4. 人的判断仍是瓶颈，但形态变了。**
Dumpleton 的 19 篇日志说明：AI 可以承担大量实现工作，但"什么还不够好"必须由人判断；SWE-Recreation 的"探索覆盖不足"则从另一侧证明——**agent 常常不知道该看哪里**。这两件事合起来，定义了当下最有价值的人类工作：**定义验收标准 + 决定探索边界**。
