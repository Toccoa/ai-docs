### 1. Google Cloud《The open AI-native stack on Kubernetes》

**为什么现在读**：Agent 的运行瓶颈正在从"模型够不够聪明"转向"基础设施能不能扛住大量长时间等待的会话"。这篇把 KubeCon 前后的一组 CNCF 项目串成了完整答案：**Agent Substrate 负责生命周期、llm-d 负责推理、gVisor 负责隔离、OpenRL 负责后训练**。

**核心要点**
- **问题的本质是"等待"**：Google 的数据是 agent 有 **90%–95% 的运行时间在等**（等工具、等审批、等下一个 turn）。所以关键不是"常驻 Pod"，而是**挂起/恢复**。
- **Agent Substrate**（11-05 捐给 CNCF，GKE 上 GA）：容器密度约为标准运行时的 **10 倍**；支持 **每秒 500+ 次挂起/恢复**；被暂停的会话可在 **500ms 内恢复**；底层用 OCI 容器 + Cloud Hypervisor microVM 或 gVisor。演示中 **8 个物理 Pod 承载 250 个有状态会话**。
- **llm-d 1.0**：prefix-cache-aware 路由 + 分层 KV cache（HBM → 主机内存 → 本地 NVMe / Lustre / 对象存储）；官方数据是 **KV cache 命中率 35% → 70%，多轮 agent 负载的 TTFT 降低 70%–85%**。
- **OpenRL**：Kubernetes 原生的 RL 后训练服务，4 个 Python 原语（`forward_backward` / `optim_step` / `sample` / `save_state`），配合 KubeRay + Kueue 调度。
- **gVisor**：内核级沙箱，专门隔离不可信的 agent 代码执行。

**怎么读**：平台/基础设施团队必读。重点抄三个指标去压测自己的栈：**KV cache 命中率、sandbox 冷启动延迟、挂起-恢复时延**；另外要求任何 agent 运行时供应商提供 sandbox escape 测试结果。

### 2. VulnCheck《After 7 months, Glasswing overwhelms maintainers with underwhelming findings》

**为什么现在读**：这是目前对"AI 找漏洞"最硬的一次第三方对账。Anthropic 的 Project Glasswing 宣传的是"发现了成千上万个高危漏洞"，七个月后 VulnCheck 把账本摊开——**发现量、修复量、重复率、误报率**四个数字放在一起，结论相当冷静。

**核心要点**
- **442 个 CVE** 归因于 Anthropic，约占今年 93,450 个 CVE 的 **0.5%**；其中只有 **2 个**（0.45%）被观察到在野利用。
- **37,966 条 finding**，只有 **7,349 条（19.4%）**公开，**217 条**标记修复；**1,654 条（4.4%）**被标为重复，**419 条**撤回。重复数是修复数的 7.5 倍。
- 9 月到 11 月：新增 **11,813** 条 finding，只多修了 **15** 条——发现与修复的缺口在扩大。
- **curl 的现实检验**：34 条已发布报告中，**19 条被判定"不是漏洞"**，6 条确认为低危，9 条待评估——误报率 **55.9%**，确认率仅 17.6%，且全是低危。
- Anthropic 的应对是把验证负担前移给维护者（OSS Scanner），并明说报告"完全由模型生成，未经人工审核"。
- 方法论启示：**"真阳性率"必须把 duplicate / withdrawn 算进去**；agent 产出（漏洞报告、告警、评审意见）都需要独立的人类验证环节，否则只是把 triage 成本转移给下游。

**怎么读**：安全团队和所有做"agent 自动产出报告"的团队必读。重点看它如何定义"可利用"和"修复"，以及 curl 那组数据的统计口径。

🔗 https://www.vulncheck.com/blog/anthropic-glasswing-november-update

### 3. LangChain《How Workday Built an Enterprise-Scale AI Agent Platform》

**为什么现在读**：一个 4 人团队如何在最严格的合规环境下，把 agent 平台的**原型周期从 4–5 个月压到 1 天以内**。它不是"我们用了 LangGraph"的软文，而是把治理层、SDK、协议支持拆开讲清楚了。

**核心要点**
- **Agent System of Record**：治理层，控制 agent 被允许访问哪些 API——这是整个平台的地基。
- **"Workday LangChain"**：一个 Python SDK，把 LangChain 原语包一层，统一走公司内部的 LLM gateway、RAG 检索和其他内部服务。
- **LangGraph 选型理由**：图模型不预设"agent 应该长什么样"，从简单 ReAct 到复杂确定性工作流都能表达；平台只提供标准基础设施。
- **A2A / MCP 已在生产**：因为底层 agent server 原生支持，每个 graph 更新都自动反映到服务端——领导问协议策略时可以直接回答"已经在跑"。
- 团队从 4 人扩到约 30 人；Workday 服务超过一半的 Fortune 500。
- 关键经验：平台的价值是**把认证、安全、合规、基础设施抽象掉**，让业务团队只剩两个问题——"这个 agent 做什么"和"graph 长什么样"。

**怎么读**：正在建内部 agent 平台的人必读。重点看"治理层先行"的顺序——先定 API 访问边界，再谈开发体验。

🔗 https://www.langchain.com/blog/how-workday-built-an-enterprise-scale-ai-agent-platform-with-langgraph-and-langsmith

### 4. Anthropic《Prompting Claude Fable 5.2》——说清"代码归谁"

**为什么现在读**：一句话就能改变 coding agent 的重构行为，而且有实验数字。对每天都在调 system prompt 的人，这是本周性价比最高的一条。

**核心要点**
- 默认行为：如果 prompt 没提代码归属，或把代码库描述成"别人的"，模型倾向于**在现有结构上追加**——即使这会重复已有代码。
- 加一句：`This codebase is yours: what it's for and how it's built are your call, and you'll keep building on it.`
- 效果：在 Anthropic 的小型编码任务测试中，模型**约一半**的尝试会合并重复代码；不加这句话时**不到十分之一**。
- 解释力：这解释了为什么 agent 在陌生 repo 里更保守、更爱复制粘贴——它对"我有没有权限改结构"有自己的判断。
- 可迁移：同样的"所有权框架"可以用于文档、测试、架构决策——**你在 context 里如何描述事实，会直接改变 agent 的行为**。

**怎么读**：5 分钟；直接把这句话加进你的 coding agent system prompt，观察一周。

🔗 https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2#say-who-owns-the-code

### 5. GoogleChrome《modern-web-guidance》

**为什么现在读**：Coding agent 的训练数据有"时间胶囊"问题——它们会写 2019 年的 JavaScript。这个 repo 用 **skills + policies** 的方式，把"现代 Web 最佳实践"注入 agent，而且一次覆盖 Claude Code、Codex、Cursor、Grok 等多个插件生态。

**核心要点**
- 3.2k stars、Apache-2.0；仓库里同时有 `.claude-plugin`、`.codex-plugin`、`.cursor-plugin`、`.grok-plugin`、`.agents/plugins`——**同一套内容，多种 agent 宿主**。
- 结构分两层：`skills/`（教 agent 用现代 API）+ `policies/`（约束 agent 不要做什么）。
- 解决的问题很具体：agent 默认写 `var`、回调、旧版 DOM API；这里给出可执行的替代方案与迁移规则。
- HN 239 分，说明"给 agent 补课"已经成为独立需求。

**怎么读**：10 分钟；把 skills 装进你常用的 coding agent，重点看 policies 如何写"禁止项"——这比"请用现代写法"有效。

🔗 https://github.com/GoogleChrome/modern-web-guidance

### 6. Simon Willison《Muse Ember》与 Gemini 4 Carbon 的定价

**为什么现在读**：Agent 的成本优化正在从"换更便宜的模型"变成"按任务选模型 + 控制 reasoning token"。这篇把三家小模型的价格、推理档位和"每任务成本"放在一张图上，很适合用来重算路由表。

**核心要点**
- **Muse Ember**：$0.10 / $0.50 每百万 token（≤200k），超过 200k 后 $0.30 / $1.50；6 个 reasoning 档位（minimal → max）。
- 在 Artificial Analysis 的 **Intelligence Index vs Cost per Task** 图上，Ember 正好落在帕累托前沿：xhigh 约 34 分 / $0.12，max 约 36 分 / $0.14；对比 Haiku 5.5 xhigh 约 34.5 分 / $0.25。
- Ember 比同门 Muse Wonder 便宜约 **40 倍**，pelican 质量相当。
- **Gemini 4 Carbon**：$2 / $10 每百万 token，12 月 1 日翻倍到 $4 / $20——如果你在做成本模型，这条时间线要写进预算。
- 关键提醒：**price-per-token 已经没有意义**，不同模型的 reasoning token 消耗差异巨大，要看"每任务成本"。

**怎么读**：10 分钟；拿你 agent 的真实任务跑一遍三家模型，按"每完成任务成本"而不是"每百万 token 价格"选型。

🔗 https://simonwillison.net/2026/Nov/10/muse-ember/

### 7. Simon Willison《Yonkers Rises》与 Antigravity `/swarm`

**为什么现在读**：多 agent 协作从"写代码"扩展到"做资产"——3D 建模、着色器、音效、音乐各自有 subagent。这是一个可围观的、完整的多 agent 创意工作流。

**核心要点**
- Simon 给 Fable 5.2 Medium 的 prompt：把 Yonkers 做成巨大机甲站起来、在曼哈顿/皇后区/布鲁克林跺脚，使用 OpenStreetMap 数据；模型正确推断出 "átomos" 是手机键盘把 "stomps" 打错了。
- 更值得注意的是 Google Antigravity 的 **`/swarm`**：Carbon 用它做了一个开放世界 3D 游戏——把 Mountain View 校园做成"鹈鹕骑 GBike"的探索场景。
- 分工：subagent 在 Blender 里根据 Omni / Nano Banana 的参考图建 3D 资产；另一个写 Three.js + WebGL shader；再用 Web Audio 程序化音效 + Lyria 配乐。
- 信号：**"swarm" 正在成为 IDE 的一等功能**；多 agent 编排的下一站是"资产管线"，而不只是代码仓库。

**怎么读**：看视频 + 读 Simon 的 prompt；注意它如何把"一个模糊的创意"拆成可并行的子任务。

🔗 https://simonwillison.net/2026/Nov/10/llm-gemini/

## 三、今日观察

1. **Agent 基础设施的瓶颈是"等待"**：90%–95% 的时间在等工具、等审批、等下一 turn。所以 Agent Substrate 的核心指标不是吞吐，而是**挂起密度、恢复时延、每秒恢复次数**；llm-d 的核心指标是 **KV cache 命中率**。这比"支持多少并发"更接近真实负载。
2. **"AI 找漏洞"需要第三方审计**：Glasswing 的数字说明，发现量不等于修复量，更不等于可利用量。任何 agent 自动产出的报告（漏洞、告警、评审、合规结论）都必须配独立验证，否则只是把 triage 成本转移给下游。
3. **小模型 + 路由是成本主线**：Ember 落在帕累托前沿，Gemini 4 Carbon 两周后涨价——agent 的成本模型要按"每任务成本"重算，而不是盯每百万 token 单价。
4. **一句话改变 agent 的行为**：把代码库描述成"你的"，模型就从"保守追加"切换到"主动重构"。Context 里的事实描述不是背景信息，而是**行为开关**。
