# 切分从“调参数”走向“按条件决策”

> 定位：前沿资料 · 主题合并（切分策略与上下文扩张）
> 关联知识点：R2-01（切分策略全景）、R2-02（块大小与 overlap）、R2-03（父子块与句子窗口）、R0-06（成本模型）
> 主源三篇：
> - 《A Systematic Analysis of Chunking Strategies for Reliable Question Answering》arXiv:2601.14123（2026-01-20）
> - SCAR：《Semantic Continuity-Aware Retrieval》arXiv:2606.16661（预印本）
> - 《Beyond Chunk-Then-Embed: A Comprehensive Taxonomy and Evaluation of Document Chunking Strategies》arXiv:2602.16974
> 入库日期：2026-11-27 ｜ 证据强度：一篇端到端系统研究 + 一篇单作者预印本 + 一篇复现型评测

## 一句话结论

2026 年这三篇合起来改写了切分的提问方式：**不要再问“最优块大小/重叠是多少”，要问“在什么条件下扩、扩多少、什么时候停”**——因为 overlap 在端到端上几乎无可测收益（却涨成本）、块大小的影响在 k≥2 时会被兜住、而无脑扩邻域会稀释信号。

## 三个硬结论

**① overlap 是无效变量，且有明确的“上下文悬崖”**（arXiv:2601.14123）
在 Natural Questions 上做端到端评估（SPLADE 检索 + Mistral-8B 生成），系统变换切分方法（token / sentence / semantic / code）、块大小、**重叠**、上下文长度。四条结论：
- **overlap 没有可测收益，却增加索引成本**；
- **句子级切分性价比最高**（在约 5k token 以内与语义切分打平）；
- **超过约 2.5k token 出现“上下文悬崖”**，质量下降；
- **最优上下文取决于目标**：语义质量在小上下文时最好，精确匹配在大上下文时更好。

**② 扩张应当“条件式”，而不是固定窗口**（SCAR，arXiv:2606.16661）
固定长度切分会导致**边界碎片化**；静态加窗与父块检索能提召回，但**带来显著 token 开销**。SCAR 按“查询-邻居相关性”与“结构连续性惩罚”决定是否扩，阈值是**相对量**（相对每个块的自身相关性），因此在 3 个嵌入模型间可迁移而不必重校准。数字：4 个语料（RFC / GDPR / 10-K / 并购协议）、N=320 查询（其中 160 条边界碎片化），**边界碎片查询上 92.8% recall，只用 7.84 个块**，比静态窗口（10.16 个块）**少 22.9%**；RAGAS 评估显示**忠实度保持，同时上下文 token 降 27.1%**。

**③ 上下文化的效果“任务相反”**（arXiv:2602.16974）
统一到两个维度（分割方法 × 嵌入时机），在两个检索设定上比较：
- **in-corpus：简单结构感知方法优于 LLM 引导方法**；
- **in-document（needle-in-a-haystack）：LumberChunker 最好**；
- **上下文化切分提升 in-corpus，但降低 in-document**；
- **块大小与 in-document 效果中度相关，与 in-corpus 只弱相关**。

## 精评：值钱的地方

1. **overlap 被端到端判为无效变量**，这直接省掉一大笔索引成本（按 1/(1−O/B) 放大）。这句话以前只能靠经验争论，现在有实验。
2. **“上下文悬崖”给了 k 一个物理上限**：`k_max ≈ 悬崖阈值 / 块大小`。这比拍一个 k=10 强得多。
3. **SCAR 把“扩不扩”变成可计算的相对阈值**，并且给了“同召回但块数更少”的目标形态——这是一个比“块大小”更值得优化的指标。

## 精评：不能当真（或容易被误读）的地方

- **SCAR 是单作者预印本**，数字漂亮但需自测；它的“跨模型可迁移”只在其设定内验证过。
- **2601.14123 只在 NQ + SPLADE + Mistral-8B 一套设定上做**，换检索器/生成器可能变。**它证明的是“overlap 在这套设定下无收益”，不是“永远无收益”。**
- **in-corpus 与 in-document 的结论相反**，意味着任何“平均分”都会掩盖方向相反的效应。**不要用总分选策略。**
- 三篇都没有回答“**表格/代码**该怎么切”——那是另一个问题域（见 11-13 表格那篇的说明）。

## 对你的动作

1. **把 overlap 默认设 0**；如果句子被切断，先改边界（句子/段落切分），别用 overlap 兜底。
2. **画一条“k → recall”曲线**：若 recall@1 与 recall@8 差距 <5pp，块大小调优的空间很小。
3. **给扩张设预算**：`max_expansions_per_query`、`max_extra_blocks`，并把 `avg_blocks_fed` 与 `expansion_rate` 打进日志。
4. **按检索设定分开测**：语料检索与文档内定位的结论可能相反。

## 自测

1. 你的 overlap 是多少？如果改成 0 重测一次，你预计 recall 会掉多少？为什么？
2. 你一次回答平均塞多少 token？有没有越过 2.5k 那个悬崖？
3. 同一父块被 3 个子块命中时，你现在喂几次？这个数能测出来吗？
