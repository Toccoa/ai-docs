# 结构化输出与格式限制：能解析，不等于答得对

> **定位**：前沿资料 · 主题合并（结构化输出）· 关联知识点 R5-04（结构化输出）、R5-07（Grounded Prompt）
> **主源一**：Zhi Rui Tam 等，《Let Me Speak Freely? A Study on the Impact of Format Restrictions on Performance of Large Language Models》，arXiv:2408.02442（2024-08-05）
> **主源二**：2026 年多方工程基准（结构化输出 hit rate / retry 成本）
> **本地存档**：[2408.02442 摘要页](原文/html/2408.02442.html)
> **证据强度**：中—高（2024 实证研究 + 2026 工程基准；后者多为厂商/博客，作趋势看）

## 一句话结论

**格式约束会损害推理能力，而且约束越严，损害越大。**  JSON mode / schema / 严格解析让输出“可用”，但可能让模型“变笨”。正确做法不是“不要结构化”，而是**把推理与格式分开**：先让模型自由推理，再用一个受约束的步骤产出结构化结果。

## 三个硬结论

**① 格式限制会显著降低推理表现（2024 实证）。**
Tam 等在多种常见任务上对比“自由生成”与“强制 JSON/XML 等结构化格式”：**结构化约束下推理能力显著下降；约束越严格，下降越大**。这不是某个模型的问题，而是“生成空间被压缩”的普遍效应。

**② “能解析”与“答得对”是两个指标。**
2026 年的工程基准普遍把结构化输出拆成两个数：**schema 合规率（hit rate）**与**任务正确率**。很多方案 hit rate 99%+，但正确率下降；**用重试次数换合规，可能只是在掩盖推理失败**。

**③ 约束解码（constrained decoding）不是免费的。**
它通过过滤 token 采样保证 schema，但会改变模型的概率路径；对简单抽取友好，对需要多步推理的任务可能有害。**结构化输出适合“结果协议”，不适合“思考过程”。**

## 精评：值钱的地方

1. **给出了一个反直觉但可操作的结论**：不要让模型“在 JSON 里思考”；JSON 是交付格式，不是推理格式。
2. **把“合规率”和“正确率”分开**，直接可用于验收：先看 hit rate 是否达标，再看正确率是否被格式拖累。
3. **对 RAG 的直接含义**：答案 + 引用 + 置信度常被要求放在一个 JSON 里；这很容易让模型为了填字段而牺牲论证质量。

## 精评：不能当真（或容易被误读）的地方

- **2024 年的模型结论**；2026 年新模型在结构化输出上更好，但“约束越严越伤推理”的机制仍在，需用自己的模型复测。
- **任务类型差异大**：分类/抽取类任务可能几乎不受影响；多跳推理/数学/规划类更敏感。
- **“先自由思考再 JSON”会多一次调用/多一段 token**；要算成本，不是无脑两段式。

## 对你的动作

1. **两段式输出**：第一段自由文本（推理/草稿），第二段严格 JSON（结论/引用/置信度）；两段用明确分隔符。
2. **schema 最小化**：只保留下游真正要用的字段；字段越多，模型越容易“为了填满而编”。
3. **验收双指标**：`schema_hit_rate` 与 `task_accuracy` 一起看；若 hit rate 升、accuracy 降，回退。
4. **对强约束场景用“校验 + 重试”而不是“更强约束”**：先解析，失败再让模型修正，而不是把 schema 收得更死。

## 自测

1. 你的结构化输出 schema 有多少字段？其中几个是下游真正会用的？
2. 你测过“自由文本 vs JSON”的推理正确率差异吗？差多少？
3. 当 schema 解析失败时，你的重试策略是“再试一次”还是“让它解释哪里不符合”？哪种更可能引入幻觉？
