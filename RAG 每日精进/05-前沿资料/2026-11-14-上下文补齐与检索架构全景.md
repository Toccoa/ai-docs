## 一、一句话结论

**检索失败的大头不在"模型不会搜"，而在"你切出来的块自己看不懂自己"。** Anthropic 用一次几乎零算法的操作（给每个 chunk 补一句它属于哪份文档、哪一年、上一季数字是多少）把 top-20 检索失败率从 5.7% 压到 2.9%，再叠一层 rerank 压到 1.9%；Duy Nguyen 把 2026 年的架构地图摊开，告诉你这类索引侧改进之后还有哪些岔路；DeepLearning.AI 那门 54 分钟的课只解决一件事——让你亲手把 router / tool calling / reasoning loop / multi-doc 这四级台阶各走一遍。

三篇连起来的判断是：**索引侧补上下文是性价比最高的一刀（一次性成本，收益确定）；rerank 是第二刀（每次查询都付费，但便宜）；agentic 是第三刀，贵且慢，必须有评测护栏才敢上；graph / multimodal 是第四刀，数据要求把大多数人挡在门外。**

## 三、第一篇：Anthropic《Contextual Retrieval》

### 3.1 它修的是哪一层故障

原文的问题描述非常朴素，值得逐字理解：传统 RAG 把文档切成几百 token 的块再编码，**这个过程本身丢掉了上下文**。

它举的例子是 SEC 财报。某个块里只有一句：

> The company's revenue grew by 3% over the previous quarter.

这个块单独看，**不知道是哪家公司、哪个季度、上一季基数多少**。于是它既难被检索到（query 里带 ACME、Q2 2023 时匹配不上），也难被用好（就算召回了，模型也不知道 3% 是谁的 3%）。

对应到 R0-03 的四层失败模型，这精确落在第一层「**检索不到**」——而且是**索引侧的、结构性的**检索不到，不是你 query 改写能救回来的那种。

### 3.2 方法（原文翻译）

核心操作一句话：**在把 chunk 拿去建索引之前，先让模型给它写一段"这句话在整份文档里的位置说明"，然后把这段说明拼在 chunk 前面。**

原文给的转换示例：

```text
原始块：
The company's revenue grew by 3% over the previous quarter.

补上下文后的块：
This chunk is from an SEC filing on ACME corp's performance in Q2 2023;
the previous quarter's revenue was $314 million.
The company's revenue grew by 3% over the previous quarter.
```

补出来的这段说明通常 **50–100 token**，会被前置到 chunk 前面，然后**同时**用于两处建索引：

1. **Contextual Embeddings** —— 向量索引
2. **Contextual BM25** —— 词法索引（BM25 负责精确匹配，比如 `Error code TS-999` 这种 embedding 抓不到的字符串）

技术上没有新东西，关键是"谁来写这段说明"：**用模型自己写**（原文用 Claude 3 Haiku），因为人工标注几百万个 chunk 不现实。原文给的核心 prompt 只有三行意思：

> 这是整份文档；这是要放进整份文档里的某个块；请给出一段简短的、能把该块定位到整份文档中的上下文，**只输出这段上下文，别的都不要**。

成本靠 prompt caching 摊平：把整份文档缓存一次，之后每个 chunk 引用缓存，不必重复传全文。原文给的估算口径是——**800 token 的块、8k token 的文档、50 token 指令、100 token 上下文 → 一次性预处理成本 1.02 美元 / 百万文档 token**。

### 3.3 四个数字（可直接引用）

评测指标是 **1 − recall@20**，也就是"相关文档没进 top-20 的比例"。语料覆盖代码库、小说、arXiv 论文、科学论文四类，embedding 配置取最优的 Gemini Text 004。

| 配置 | 失败率 | 相对下降 |
|---|---|---|
| 基线（普通 embedding + BM25） | 5.7% | — |
| + Contextual Embeddings | 3.7% | **35%** |
| + Contextual Embeddings & Contextual BM25 | 2.9% | **49%** |
| + Rerank（top-150 → top-20） | 1.9% | **67%** |

另外三个可引用的结论：

- **top-20 比 top-10 好，top-10 比 top-5 好**。原文直接试了 5 / 10 / 20，20 最优。这条和"少给几块降低干扰"的直觉相反。
- **rerank 的正确位置在第一次召回之后、塞进 prompt 之前**：先捞 150 块，reranker 打分，留 20 块。原文用的是 Cohere reranker。
- **小语料别上 RAG**：知识库小于 **20 万 token（约 500 页）**时，直接把整份知识库塞进 prompt + prompt caching 更简单（延迟降 2 倍以上、成本降最多 90%）。

### 3.4 精评：它值钱的地方，和它没告诉你的地方

**值钱的地方**

1. **它把"检索失败"从玄学变成了可归因的工程量。** 之前大家谈"RAG 效果不好"，只能笼统地调 chunk size、换 embedding。这篇明确指出失败原因是**chunk 剥离了指代信息**，并且给出一个可复现的修法。这个归因方式比数字更重要——你可以在自己的语料上原样复刻这个假设检验。
2. **它顺手否掉了三条看起来更聪明的路**，而且是否掉得很干脆：给每个块贴"通用文档摘要"（原文说"实验过，收益非常有限"）、HyDE（假设文档嵌入）、摘要索引（"评估过，性能低"）。这个信息量很大：**补"这篇文档讲什么"没用，补"这个块在文档里的哪个位置"才有用**。前者是泛泛的语境，后者是消歧所需的最小信息。
3. **它是少数明确给了成本数字的论文级工程博客。** 1.02 美元/百万 token 这个数，你可以直接拿去算自己的语料要不要做这件事。

**没告诉你的地方（引用时必须带上的限定）**

1. **指标只测"检索到没"，不测"答得对不对"。** 1 − recall@20 是纯检索指标。原文自己也说"应当跑评测，把上下文和 chunk 区分开喂给模型可能更好"——这句话说明**下游生成收益是推断的，不是测出来的**。你在汇报里不能说"检索失败率降 67%，所以回答质量提升 67%"。
2. **相对降幅会骗人。** 5.7% → 1.9%，相对降 67%，绝对只降 **3.8 个百分点**。如果你的基线失败率是 30%，同样"相对降 67%"意味着绝对降 20 个点，价值天差地别；反过来，基线 2% 时这个优化基本没意义。**先在你自己语料上量基线**，再决定要不要做。
3. **上下文是模型写的，可能写错。** 原文没有报告上下文生成的质量，也没有说误生成率。对表格密集、跨文档指代（"见上文第 3 节"）的语料，补出来的定位说明可能是幻觉，而它会被**同时**写进向量和 BM25 索引，污染是双份的。工程上必须做抽样人工审。
4. **它是一次性成本，但不是一次性工作量。** 语料每次更新都要重跑上下文生成；文档越多、更新越频繁，这笔账越接近"每次入库都翻倍"。这正是 R0-06（成本与延迟模型）该算的那笔账：**索引侧成本 × 更新频率 vs 检索侧成本 × 查询量**。
5. **2024 年 9 月的模型和价格**。当时用 Haiku 生成上下文，现在同样的活更便宜也更好，但"更便宜的模型写上下文，质量会不会掉"这个问题原文没答。

**一句话取舍**：如果你的语料是**长文档、有明确主体（公司/项目/时间）、更新不频繁**，这是投入产出比最高的一刀，先做它再谈别的。如果你的语料是**短片段、表格、代码**，先做人工抽样看模型能不能写出靠谱的定位说明——写不出来，这个方法就是负收益。

## 四、第二篇：Duy Nguyen《Advanced RAG Techniques in 2026》

### 4.1 分类学（原文翻译）

原文的主线是"从 naive 到 production-grade"，把 2023 年以来的变体拍成一张演进图：

```text
Naive RAG (2023)
  └─ Advanced RAG (2024)
       ├─ Agentic RAG (2025)
       ├─ Graph RAG (2025)
       ├─ Multimodal RAG (2025–2026)
       ├─ Bidirectional RAG (2026)
       └─ MiA-RAG / HGMem / Graph-O1 (2026)
```

它开篇就否掉了"naive RAG 够用"这个前提，理由是**三个企业级缺口**：

1. **实时数据访问**——传统 ingest 管线的延迟撑不住
2. **知识图谱整合**——需要检索"相互关联的事实"，而不只是"最相似的块"
3. **细粒度访问控制**——否则 AI 平台本身变成数据泄露的通道

各架构的一句话定位（按原文）：

| 架构 | 它多做了什么 | 什么时候用 |
|---|---|---|
| **Agentic RAG** | 不再"检索一次就生成"，而是先规划、再路由到不同工具（向量库 / 知识图谱 / Web API），召回后做**相关性检查**与**来源核验**，最后带引用生成 | 复杂问题、多源、需要推理与事实核验 |
| **Graph RAG** | 向量检索 + 知识图谱遍历（实体关系），补上"谁给谁打工""哪个药和哪个病相互作用"这类关系问题 | 关系密集的领域：法规、生物医药、企业知识库 |
| **Multimodal RAG** | 文本 / 图片 / 表格 / 图表分别嵌入（图片走 CLIP），统一进向量库 | 技术文档、论文、病历、商品目录 |
| **Bidirectional RAG** | 除了读，还把**通过验收的答案**写回语料库；关键是那个验收层（grounding、引用核查、新颖性检测），防止幻觉答案变成明天的"source" | 知识会随使用而增长的场景 |
| **MiA-RAG / HGMem / Graph-O1** | 更前沿的三个方向：层级全局摘要（mindscape）、超图工作记忆、MCTS + RL 探索子图 | 长文档叙事问答、多跳问题、文本属性图上的问答 |

原文还给了一张选型决策树，逻辑是：

```text
数据关系密集？ ── 是 → Graph RAG
      │否
单轮查询？ ── 否 → Agentic RAG
      │是
纯文本？ ── 否 → Multimodal RAG
      │是
   Advanced RAG（rerank / HyDE / self-query）
```

### 4.2 评测：它给了门槛数字

原文建议用 Ragas 起步，四个指标 + 一个"实践目标"：

| 指标 | 测什么 | 原文给的目标 |
|---|---|---|
| Faithfulness | 答案是否有检索到的证据支撑 | > 0.90 |
| Answer Relevancy | 答案是否回答了问题 | > 0.85 |
| Context Precision | 召回块的信噪比 | > 0.80 |
| Context Recall | 相关信息是否召回全了 | > 0.85 |

### 4.3 精评：这是导航贴，不是证据贴

**它做对的事**

1. **把"该上哪种架构"写成了决策树。** 多数 RAG 综述只会罗列，这篇给了判据（关系密度 / 轮次 / 模态），哪怕判据粗糙，也比没有强——你能拿它跟老板对齐"我们该不该上 Graph RAG"。
2. **它点出了三个企业缺口里最容易被忽略的那个：细粒度访问控制。** 这一条对内网知识库是生死线，而绝大多数 RAG 教程根本不提。工程上要记住一个细节：**ACL 必须在检索前做前置过滤，不能检索后过滤**——后过滤会泄露"文档存在"这一事实本身，而且 top-k 会被无效文档占满。
3. **它诚实地说 RAG 不是万灵药**：引用斯坦福对法律 RAG 工具的审计仍发现两位数幻觉率，以及 2025 年一项医学研究里"检索差会让答案更差"。这句话比全文的架构罗列都值钱。

**不能当真的事**

1. **代码片段跑不起来，别复制。** `create_openai_tools_agent` 在新版 LangChain 已不是推荐写法；示例还用 `gpt-4o`；`extract_entities` 这种函数直接留空。把它当**伪代码**看，意图是对的。
2. **arXiv 编号（2512.xxxxx）我无法逐条核实。** 2512 是 2025 年 12 月的预印本区间，这类编号新到可能还没经过任何复现。引用 MiA-RAG / HGMem / Graph-O1 时，请说"有论文提出"，不要说"已被验证"。
3. **Ragas 的 0.90 / 0.85 是行业口头经验，不是统计显著的门槛。** 小样本上这些指标的置信区间宽到没意义——这一点和 Demystifying Evals 那篇讲的"20–50 个任务上 5 个百分点大概率是噪声"是同一个道理。**别拿它当 KPI 卡点，拿它当趋势线。**
4. **决策树缺了最重要的第一问："这个问题到底该不该用 RAG？"** 按 Anthropic 的口径，语料小于 20 万 token 就该直接塞上下文；按 R0-02 的口径，结构化查询该走 Text-to-SQL。决策树从"确定要用 RAG"开始，等于默认跳过了选型。

## 五、第三篇：DeepLearning.AI《Building Agentic RAG with LlamaIndex》

### 5.1 课程骨架（原文信息）

- 讲师：**Jerry Liu**（LlamaIndex 联合创始人兼 CEO）
- 难度 Beginner，**54 分钟**，6 节视频、4 个代码示例、1 个计分测验（PRO）
- 更新于 2025-10-07

六节课的时长与内容：

| 课 | 时长 | 讲什么 |
|---|---|---|
| Introduction | 2m | agentic RAG 是什么，和标准 RAG 管线的差别 |
| **Router Query Engine** | 9m | 给一个 query，路由器在两个查询引擎（Q&A / 摘要）之间选一个，在**单份文档**上执行 |
| **Tool Calling** | 10m | 让 LLM 不只选函数，还要**推断该传什么参数** |
| **Building an Agent Reasoning Loop** | 11m | 从单次工具调用升级成**多步推理循环** |
| **Building a Multi-Document Agent** | 10m | 把研究 agent 扩展到多份文档（课程用 arXiv 论文做对比） |
| Quiz | 10m | 计分测验 |

原文自己做了一个对比，值得抄：标准 RAG 管线适合"少量文档上的简单问题"；agentic 的做法是**根据初步发现调整后续检索**，因此能在多文档之间导航、摘要、对比。

### 5.2 这四级台阶是对的

把这四节课的名字连起来看，其实是一条很干净的递进：

```text
① 路由      query → 选一个引擎          （决策：用哪个工具）
② 工具调用  query → 选函数 + 填参数      （决策：怎么用这个工具）
③ 推理循环  多步：看结果 → 再决定下一步   （决策：要不要再查一次）
④ 多文档    跨文档导航、对比、汇总        （决策：查哪几份）
```

这四级正好对应 R0-04「最小闭环与 7 个组件」里最容易缺的那几个：**路由器**（很多人的 RAG 只有一条路）、**循环与终止条件**（很多人的 agent 只会调一次工具）、**跨文档的聚合**（很多人的检索是单文档 top-k）。

### 5.3 精评：54 分钟买到的是手感，不是工程判断

**它真能给的东西**

1. **骨架。** 学完你会知道 agentic RAG 不是一个玄学名词，就是"路由 + 工具 + 循环 + 多文档"四件事的组合。这个祛魅价值很高。
2. **多步推理的代码形态。** 第 3 课那个 reasoning loop 是分水岭：从"LLM 选个函数"到"LLM 看到函数返回后再决定下一步"，这中间差的不是代码量，是**终止条件怎么设计**。

**它给不了的东西（别指望）**

1. **没有评估。** 54 分钟里没有一个字讲"怎么知道这个 agent 变好了"。学完你只会写能跑的 demo，不会写能上线的系统——而 agentic RAG 恰恰是**最难评估**的那一类（多步、路径不唯一、错误会累积）。
2. **没有成本与延迟。** agent 每多一步就多一次 LLM 调用，成本是标准 RAG 的 N 倍。这直接影响 R0-06 那笔账，但课程里没有。
3. **没有失败恢复。** 工具调用失败、检索为空、循环不收敛——这三件事在生产里天天发生，课程里全没有。
4. **生态绑定 LlamaIndex。** 概念（router / tool / reasoning loop）可以迁移到 LangGraph、OpenAI Agents SDK，代码不能。别把 LlamaIndex 的 API 当成 agentic RAG 的定义。

**学完该立刻做的三件事**

1. 给自己现有语料加一个 **router**：先分清"问事实"和"要摘要"，这两类问题的检索策略本来就该不同。
2. 给每个工具的描述补一句 **"什么时候不该用它"**。工具描述是路由的唯一依据，写"搜索文档"等于没写。
3. 加 **trace**：把每一步的工具选择、参数、返回、耗时打出来。没有 trace 的 agent 无法调试，只能靠运气。

## 六、三篇拼成一条工程顺序（对齐 R0-03 的四层失败模型）

| 失败层（R0-03） | 典型症状 | 这一层的修法 | 对应篇目 |
|---|---|---|---|
| **检索不到** | 明明库里有，就是没召回 | 补 chunk 上下文（索引侧）+ hybrid（向量 + BM25） | Anthropic 第一篇 |
| **排不准** | 召回了，但排在 20 名以后 | rerank（先捞 150，再留 20） | Anthropic 第一篇 |
| **用不好** | 20 块都在，模型答偏 | 区分"上下文"与"chunk"再喂；必要时上 agent 多轮取证 | 第一篇的"跑评测"提示 + 第三篇 |
| **答不实** | 答案没有出处或出处不对 | 引用核验 + 相关性/来源检查（agentic 的 verify 环节） | 第二篇的 agentic 架构 |
| **（超出检索）** | 问题本身不该用 RAG | 小语料直接塞上下文；结构化问题走 Text-to-SQL | 第一篇的 20 万 token 阈值 + R0-02 |

**顺序建议（按投入产出比排）**：

1. **先量基线**：在你的语料上测 1 − recall@20。低于 5% 就别做上下文补齐，收益看不见。
2. **补上下文**（一次性成本）→ **加 hybrid + rerank**（每次查询成本，但便宜）。
3. **上评测**，再考虑 agentic（贵、慢、需要护栏）。
4. **最后**才是 graph / multimodal——它们的门槛不在代码，在数据和标注。

## 九、权衡与坑（把三篇的坑合起来看）

| 坑 | 说明 | 怎么绕 |
|---|---|---|
| **把相对降幅当绝对收益** | −67% 是 5.7→1.9，绝对 3.8 个点 | 汇报时永远同时给基线和绝对值 |
| **把检索指标当生成指标** | recall@20 高 ≠ 答得好 | 检索指标和端到端指标分开测，两套都要 |
| **上下文补出幻觉** | 模型写的定位说明会被双份索引进向量和 BM25 | 抽样人工审 30–50 个块，看有没有"编造出处" |
| **忘了重算成本** | 每次文档更新都要重跑上下文生成 | 把"更新频率 × 语料规模"纳入入库预算 |
| **ACL 做成后过滤** | 检索后过滤会泄露"文档存在" | 前置过滤，按 chunk 打权限标签 |
| **拿 agentic 当默认解** | 成本 N 倍、延迟高、难评估 | 先把单轮 RAG 的 recall 打上去，再谈多轮 |
| **课程当能力证明** | 54 分钟只够建立手感 | 学完自己实现一个 router + trace，再谈用不用框架 |
| **综述里的 arXiv 编号** | 太新，未经复现 | 说"有论文提出"，不说"已验证" |

## 十、自测（先别翻答案）

1. 你的语料现在的 **1 − recall@20** 是多少？如果没测过，你凭什么判断"补上下文"对你有没有用？
2. Anthropic 说"给块贴通用文档摘要收益非常有限，补位置信息才有用"——用你自己的语料解释这个区别：为什么前者是语境，后者是消歧？
3. 如果你的知识库只有 8 万 token，却还在维护一套向量库 + BM25 + rerank，你付出的运维复杂度换到了什么？
