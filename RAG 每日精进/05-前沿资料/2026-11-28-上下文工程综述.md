# 上下文工程：从 RAG 到多智能体

> **定位**：前沿资料 · 主题综述 · 关联知识点 R5-01（上下文组装）、R5-02（Lost in the Middle）、R6-06（Agentic RAG）
> **主源**：Lingrui Mei 等，《A Survey of Context Engineering for Large Language Models》，arXiv:2507.13334（2025-07-17，v1；后续有更新）
> **本地存档**：[PDF](原文/pdf/2507.13334.pdf) ｜ [HTML 全文](原文/html/2507.13334-full.html)
> **证据强度**：高（1400+ 篇论文的系统综述）；但它是**综述**，具体数字要回到被引论文核对。

## 一句话结论

2026 年再看“上下文工程”，它已经不是“把 top-k 塞进 prompt”的别名，而是一套**三层系统**：**上下文检索与生成 → 上下文处理与管理 → 系统实现（RAG / 记忆 / 工具推理 / 多智能体）**。它给架构师最重要的提醒是：**模型“读得懂复杂上下文”的能力，明显强于它“写出同样复杂长文”的能力**——所以别把系统的失败都归因于“模型不够强”，很多时候是上下文供给与输出约束没设计好。

## 三个硬结论

**① 上下文工程有清晰的分层，不是一个技巧集合。**
综述把基础组件分成：`context retrieval & generation`、`context processing`、`context management`；再把它们组合成系统级实现：RAG、memory systems、tool-integrated reasoning、multi-agent systems。这个分层的价值在于：**每一层都能单独设指标、单独做消融**，而不是把“效果不好”笼统归因给模型。

**② 存在一个“能力不对称”。**
模型在**理解复杂上下文**上很强，但在**生成同样复杂、长篇、结构化的输出**上明显更弱。对 RAG 的直接含义：检索增强能提升“读”，但不会自动提升“写”；如果产品要长报告、复杂表格、可执行方案，**输出侧需要单独设计**（结构化、分步、验证），不能指望 RAG 一并解决。

**③ 上下文工程正在从 RAG 扩展到记忆与多智能体。**
综述把 memory 与 tool-integrated reasoning 作为与 RAG 并列的系统实现，而不是 RAG 的子功能。这解释了一个常见困惑：**为什么“知识库问答”做得不错，但“有记忆的助手”很难**——因为它们复用的只是检索组件，**记忆的写入、压缩、遗忘与注入是另一套工程**。

## 精评：值钱的地方

1. **给了一个可以对着团队讲清楚的分层语言**：以后再有人说“我们做 RAG”，你可以追问：你说的是检索层、上下文处理层，还是系统实现层？
2. **“理解强、生成弱”的不对称**，是很多 RAG 产品“答得对但写得差”的根因。它把问题从“换个更大的模型”转成“输出侧要不要拆步骤 / 加 schema / 加验证”。
3. **把 memory 与 RAG 并列**，帮你避免一个常见架构错误：把 agent memory 当成“又一个向量库”。

## 精评：不能当真（或容易被误读）的地方

- **综述不是实验**。它说“1400+ 篇”，不等于这 1400 篇都支持同一结论；引用具体数字时必须回到原文。
- **分层是分析框架，不是部署顺序**。不是每个系统都要建全三层；小系统可能只需要“检索 + 组装”。
- 综述的覆盖面广，**对 2026 年最新工业实践（agentic harness、上下文腐烂的工程量化）不可能全部覆盖**，要配合单点论文看。

## 对你的动作

1. 用三层框架给你的系统画一张图：**检索/生成层、处理/管理层、系统实现层**，每层写 1 个指标。
2. 检查你的产品是否属于“理解强、生成弱”：如果是，优先在输出侧加**结构化模板 + 分步生成 + 自检**，而不是继续加检索。
3. 如果要做记忆，**不要复用 RAG 的索引设计**；先读记忆栈条目（`2026-11-10-记忆栈-四层与dreaming.md`），把 transcript / notes / wiki / injected 四层分开。

## 自测

1. 你的系统里，“读不懂上下文”和“写不好输出”各占失败案例的多少？你有分开统计吗？
2. 如果模型理解能力已经足够，为什么你的长报告仍然结构混乱？这是检索问题还是输出工程问题？
3. 你的 agent memory 和知识库是同一个索引吗？如果是，写入冲突时你怎么区分“世界的事实”和“自己的经验”？
