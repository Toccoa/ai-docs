# 多轮查询改写：别让“改写”把用户意图改没了

> **定位**：前沿资料 · 主题合并（多轮检索）· 关联知识点 R5-08（多轮对话改写）、R3-07（查询理解与改写）
> **主源一**：Hangeol Chang 等，《HYPER: Hypothesis-Guided Planning for Evidence-Seeking Retrieval》，arXiv:2603.19008（2026-03-19）
> **主源二**：Yanjia Sun 等，《CQC-RAG: Robust Retrieval-Augmented Generation via Cross-Query Consistency》，arXiv:2606.13438（2026-06-11）
> **经典参考**：Fengran Mo 等，《ConvGQR: Generative Query Reformulation for Conversational Search》，arXiv:2305.15645（2023-05-25）
> **本地存档**：[HYPER 摘要页](原文/html/2603.19008.html) ｜ [CQC-RAG 摘要页](原文/html/2606.13438.html) ｜ [ConvGQR 摘要页](原文/html/2305.15645.html)
> **证据强度**：中—高（三篇预印本/会议论文；HYPER 与 CQC-RAG 有方法创新，需自测）

## 一句话结论

**多轮对话里的“改写”不是一个必开的预处理，而是一个有风险的决策。** 好的改写能补全指代与省略；坏的改写照把“上周那版”改成“最新版”，**把用户意图改没了**。2026 年的趋势是：**从“改写成一句更完整的 query”转向“围绕证据假设做规划”和“多查询一致性自检”**。

## 三个硬结论

**① 对话检索的难点是“意图依赖历史”，不是“句子不完整”。**
ConvGQR 指出：当前轮的真实检索意图依赖对话历史；但用“人工改写”当监督信号训练改写器，会限制模型生成更好的检索 query。它用“生成式查询重构 + 查询图”来同时做改写与扩展。

**② 别只改写，先提出“证据假设”。**
HYPER 把 RAG 从“主题相关检索”转向“证据寻求检索”：先基于问题提出一个**暂定答案假设**，再围绕“哪些证据能区分候选假设”去检索。对诊断、排障、选型这类“多个候选中选一个”的任务，**主题相关的上下文往往不足以做决定**。

**③ 多查询一致性可以当“自检信号”。**
CQC-RAG 先生成一组**语义等价但句法多样**的查询，引入受控的查询多样性；再通过**跨查询一致性**筛选证据/答案，降低“某个改写碰巧召回误导文档”的风险。核心不是“多问几次”，而是**用一致性做过滤**。

## 精评：值钱的地方

1. **“证据假设”是一个可复用的设计**：比“把问题改写得更长”更接近人类专家的检索方式。
2. **多查询一致性**给你一个不依赖标注的鲁棒性信号：同一意图的多个表达，检索结果应该收敛。
3. **ConvGQR 的提醒很重要**：不要用人工改写当唯一金标——人工改写的 query 不一定是最利于检索的 query。

## 精评：不能当真（或容易被误读）的地方

- **HYPER 是 training-free 规划**，不是“永远更好”；它增加一次规划调用，延迟和成本上升。
- **CQC-RAG 的多查询会放大检索成本**；在 QPS 高的系统里，可能得不偿失。
- **“一致性高”也可能是“一起错”**：如果所有改写都被同一篇误导文档带偏，一致性反而掩盖错误。要和金标/引用核查一起用。

## 对你的动作

1. **改写默认关闭，按需触发**：只在检测到指代（“它/这个/那版”）、省略、话题切换时改写；不要每轮都改。
2. **保留原查询做融合**：改写 query 与原 query 各检索一次，RRF 融合；**改写不能替换原查询**。
3. **记录 `rewrite_delta`**：改写前后 top-10 重叠率、答案变化率；如果改写经常改变答案，先查意图是否被改坏。
4. **对“多候选择一”的任务**，试 HYPER 式“先假设、再找区分证据”；对普通 FAQ，不要上。

## 自测

1. 你的系统每轮都改写吗？改写触发条件是什么？
2. 改写后 top-10 与原查询重叠多少？如果很低，是补全了意图还是改掉了意图？
3. 对“上周那版政策”这种 query，你会改写成“最新版”还是保留时间限定？为什么？
