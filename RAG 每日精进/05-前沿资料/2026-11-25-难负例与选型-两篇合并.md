# 合成难负例会主动帮倒忙；选型是流水线决策而非排名查询

> 定位：前沿资料 · 主题合并（对比学习 / embedding 选型）
> 关联知识点：R4-01（Embedding 选型）、R4-02（对比学习与难负样本）、R4-03（领域适配）
> 主源两篇：
> - 《When Hard Negatives Hurt: Bridging the Generative-Discriminative Gap in Hard Negative Synthesis for Retrieval》**KDD 2026**，arXiv:2606.01304
> - 《Choosing a Text Embedding Model: A Practical Benchmarking and Decision Framework》arXiv:2607.23507（2026-07-26 技术报告）
> 入库日期：2026-11-27 ｜ 证据强度：一篇 KDD 主会论文 + 一篇单一作者技术报告

## 一句话结论

两篇分别打掉了两个流行假设：**“用 LLM 合成难负例能提升检索”**（错，方法不当会**主动降低**性能）、**“从榜单挑第一名总没错”**（错，榜单第一**很少**是某个具体部署的最优选择）。

## 难负例：为什么“合成”会帮倒忙

论文先把难负样本挖掘的三条内在局限讲清楚：
1. **负例受语料可用性约束**（想找“差一点就对”的反例，语料里不一定有）；
2. **按检索器分数选择，而非按诊断价值选择**（分数高 ≠ 对训练有用）；
3. **随检索器变强，越来越多被“假阳性”污染**（把“检索器认为不相关、其实相关”的样本当负例，直接教错）。

LLM 合成看似是有原则的替代（不受语料限制、可定向、无假阳性风险），但**朴素地加入对比学习，常常反而降低检索性能**。根因被形式化为 **“生成-判别鸿沟”（generative–discriminative gap）**：**LLM 生成优化的是流畅、合理；对比学习需要的是在决策边界上有策略的相关性违反**。

两种复合失效模式：
- **判别无关生成**：LLM 缺乏对“查询信息需求”的显式建模，产出通用或**话题漂移**的文本，**提供不了对比信号**；
- **来源依赖捷径**：分布上的伪影让模型靠“**这段是生成的还是真实的**”来区分，而不是靠相关性 → **梯度漂移，主动破坏优化**。

解法 **CausalNeg** 两个模块：① **CoT 引导的反事实扰动**——把“这篇文档为什么满足查询”分解成显式信息需求，然后**外科式地违反其中单个需求**，构造**硬度可控、可解释**的负例；② **查询视角熵最大化**——把生成负例**分散在相似度谱上**，最小化“来源身份”与“相似度分数”的互信息，**压制捷径利用**。

## 选型：为什么榜单不管用

报告开篇的判断很直接：选 embedding 是构建检索系统里**最有影响、却最常被草率处理**的决定之一，而**“排行榜第一”的模型很少是某个具体部署的最优选择**。它做的是把模型选择放回**完整流水线**：embedding 怎么产生、怎么索引与大规模检索、**分块策略如何塑造检索质量**；并按**任务 / 延迟 / 成本 / 部署约束**给建议，而不是给一个排名。

## 精评：值钱的地方

1. **“假阳性随模型变强而恶化”这条机制**极其重要：它意味着**你越努力挖难负例，越容易挖到标错的真相关**——这是一个反直觉但可检验的论断。
2. **CausalNeg 的第一个模块可以直接抄思路**：把“满足查询”拆成 3–5 个必要条件，然后只违反一个 → 负例硬度可控、且**错在哪可解释**。
3. **“来源捷径”提醒你检查数据混合比例**：如果合成负例在文风/长度/格式上有系统性差异，模型学的是“识别生成文本”。

## 精评：不能当真（或容易被误读）的地方

- **KDD 那篇的结论是“朴素加入会变差”，不是“合成负例无用”**。它给了修法（CausalNeg），所以正确读法是“需要精心设计”，不是“别用”。
- **选型那篇是单一作者的技术报告，且评测对象包含一个商业 API 模型（T3EM）**，存在利益相关性；其框架价值大于其具体排名。
- 两篇都**没有给出“你的场景该不该微调”的判据**——那需要你自己的 A/B/C/D 归因（召回不到 / 排不准 / 生成错 / 不该召回）。

## 对你的动作

1. **先测 `pairwise_accuracy`**：取 20 组“只差一个条件”的真实文档对，看检索器能否把正确的那份排在前面。这个数比 recall 更能暴露判别力缺失。
2. **如果要合成负例，用“条件违反”模板**，并配套防来源捷径（混入真实负例、分散到相似度谱）。
3. **选型报告必须三列**：recall、索引内存、p95 延迟。只报 recall 的报告不完整。
4. **动手微调前先做归因**：微调只治“正确文档根本没被召回”，治不了“排不准/不该召回/生成错”。

## 自测

1. 用“2024 版制度”的内容做 query，你的检索器能把 2024 版排在 2026 版之前吗？这个 `pairwise_accuracy` 测过吗？
2. 你的微调负例从哪来？如果是“检索器高分但未标注”，你怎么处理其中的假阳性？
3. 你的选型报告除了 recall，还报了哪两个数？
