## 知识点 1：GraphRAG（R6-03）

### 一句话结论

**GraphRAG 的收益只在“关系密集 + 多跳 + 需要解释路径”时成立。** 如果问题主要是局部事实查找，建图不划算；如果图不完整，GraphRAG 可能比平坦 RAG 更自信地错。**先做“关系必要性”测试，再决定建不建图。**

### 为什么重要

- 企业知识里大量问题是关系型：“这个合同关联哪些供应商？”“这条法规影响哪些产品？”
- 平坦向量检索只能找“相似文本”，找不到“沿关系走多跳”的证据。
- 但 GraphRAG 的构建成本（实体抽取、消歧、关系维护、更新）很高；2026 年的基准研究（BRINK）还指出：**现有 KG-RAG 的推理能力被高估**。

### 核心机制：图的两条检索路径

```text
局部检索（local）：
  查询 → 实体识别 → 图邻域扩展（1–2 跳）→ 子图 → 生成

全局检索（global）：
  查询 → 社区摘要/主题簇 → 全局证据 → 生成

混合：
  向量检索找入口实体 → 图扩展补关系 → 合并排序
```

**GraphRAG 的引用是轨迹级的：**

```
答案 ← 最终引用节点
     ← 图遍历路径（visited_nodes / edges）
     ← 访问过但未引用的邻域（也会影响答案）
```

### 怎么做

1. **先做关系必要性测试**：抽 30 个问题，标注“是否需要跨实体/多跳”；<20% 先别建图。
2. **从“元数据图”起步**：文档-章节-实体-权限关系，比全量知识图谱便宜，且能解决多租户/权限。
3. **验收分层**：局部事实题、关系题、多跳题、全局聚合题分开看；不要用平均分。
4. **引用记录路径**：`visited_nodes`、`cited_nodes`、`traversal_edges`；审计时能还原。
5. **图不完整时允许拒答**：缺失关键边时，输出“证据不足”，而不是自信地错。

### 权衡与坑

- **坑 1：为所有问题建图。** 局部事实题用图，成本高、收益低。
- **坑 2：图不完整但强行回答。** BRINK 的结论：知识不完整时推理有限。
- **坑 3：只检查“引用是否支持答案”。** GraphRAG 的答案可能依赖未引用的邻域；要审计轨迹。
- **坑 4：忽略更新成本。** 图会过期；实体/关系变更要同步。
- 【我的建议】先做 hybrid + 元数据图；只有当关系题占比高且图质量可控时，才上完整 GraphRAG。

### 架构师视角

- GraphRAG 是**关系资产的变现**，不是“更高级的向量库”。
- 观测出口：`relationship_question_ratio`、`graph_coverage`、`path_length`、`citation_path_coverage`、`answer_accuracy_by_type`。
- **一句话**：**图不是用来“存更多”，而是用来“回答关系”。**

### 自测 3 题

1. 你的业务问题里，有多少必须“沿关系走多跳”才能回答？有数据吗？
2. 你的知识图谱完整度如何？缺失关系时，系统会拒答还是自信地错？
3. 如果 GraphRAG 的答案依赖一条未被引用的边，你的引用审计能发现吗？

## 知识点 2：Self-RAG / Corrective RAG（R6-04）

### 一句话结论

**Self-RAG / Corrective RAG 的核心是“检索后自检”：证据相关吗？充分吗？支持结论吗？不好就重查、换源或拒答。** 它把“检索质量”变成生成循环里的一个可判断节点；但自检本身有成本，也可能与生成器“一起错”。

### 为什么重要

- 普通 RAG 默认“检索结果是对的”，但真实系统里检索经常错：召回无关、证据不足、来源过期。
- CRAG 用轻量检索评估器给文档质量打分，按置信度触发“正确/模糊/错误”三种动作，必要时走 web 搜索兜底。
- 2026 年的 Self-Correcting RAG 进一步把“上下文选择”形式化为**背包问题（MMKP）**，并用 **NLI 引导的 MCTS** 在测试时探索推理路径、验证忠实度。

### 核心机制：检索评估 → 动作

```text
检索 → 评估器（相关性/充分性/忠实度）
  ├─ 高置信：直接用
  ├─ 中置信：补充检索 / 改写 query
  └─ 低置信：换源（web/其他库）/ 拒答 / 转人工
```

**Self-Correcting RAG 的两段：**

```
输入侧：MMKP 选择上下文（在 token 预算下最大化信息密度，去冗余）
输出侧：NLI-guided MCTS 探索推理轨迹，验证答案是否被证据支持
```

### 怎么做

1. **先做“检索质量分类器”**：相关/部分相关/无关；用 100–200 条标注训练或规则冷启动。
2. **定义动作与预算**：每种置信度对应什么动作、最多重试几次、何时拒答；不要无限循环。
3. **自检与生成分离**：用独立模型/NLI 做忠实度检查；不要让生成器自己判自己。
4. **测“净收益”**：`selfcheck_gain`（修正后正确率提升）vs `selfcheck_cost`（延迟/ token）；只在净收益为正的 query 类型上启用。
5. **保留证据链**：每次重查记录原因与结果，便于归因。

### 权衡与坑

- **坑 1：自检模型和生成模型同源。** 会一起错，自检变成“自我确认”。
- **坑 2：无限重试。** 必须有 `max_retries` 和降级路径。
- **坑 3：对所有 query 都自检。** 简单事实题不需要，成本会翻倍。
- **坑 4：只测平均，不测分层。** 自检可能只对多跳/模糊问题有效。
- 【我的建议】先从 CRAG 式“轻量评估器 + 三档动作”开始；Self-RAG 的 MCTS 属于高成本进阶，确认有收益再上。

### 架构师视角

- 自检是**可靠性投资**：它把“检索错误”从不可见变成可处理。
- 观测出口：`retrieval_confidence_distribution`、`selfcheck_gain`、`selfcheck_cost`、`fallback_rate`、`over_refusal_rate`。
- **一句话**：**普通 RAG 假设检索是对的；Self/Corrective RAG 假设检索可能错，并为此准备动作。**

### 自测 3 题

1. 你的系统有没有“检索质量评估”节点？如果没有，检索错了你怎么知道？
2. 自检和生成是同一个模型吗？如果是，你怎么防止“一起错”？
3. 自检带来的正确率提升，能覆盖它的延迟/成本吗？你量过吗？
