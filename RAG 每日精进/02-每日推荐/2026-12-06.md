## 知识点 1：记忆 vs 知识库（R6-09）

### 一句话结论

**知识库回答“世界是什么”，记忆回答“我经历过什么、用户偏好什么、当前任务进行到哪”。** 把两者混在一个向量库里，会导致写入冲突、权限混乱与“记忆污染知识”。正确形态是**分层记忆栈**：L1 原始 transcript（不可编辑、可搜索）→ L2 notes（模型判断后写）→ L3 representations（离线整理）→ L4 injected context（每次只注入极小一部分）。

### 为什么重要

- 很多 team 把“记忆”当成“再建一个向量库”，结果：① 错误记忆被检索进每个 session；② 知识库更新与记忆更新互相打架；③ 无法单条删除/审计。
- Anthropic 2026 年的工程文把记忆拆成四层，并明确排除三类“假记忆”：**权重更新、in-context learning、compaction**（会话压缩不是记忆）。
- 关键判据：**强模型从记忆中的增益更小**（要同报 baseline）；**硬规则可能负收益**（文中 Opus 5 −0.234）；**抽象层只在“需要跨文档综合”时才值得建**。

### 核心机制：四层栈

```text
L1 Transcripts     系统自动写、不可编辑、全文可搜   ← ground truth
L2 Memory notes    模型边干边判断后写                ← 显著性与经验
L3 Representations 由 L1+L2 计算出的 wiki/摘要       ← dreaming 离线建
L4 Injected ctx    每次 session 预加载，必须极小      ← 影响所有回答
```

**Dreaming（离线整理）做的五件事：**
筛选、去重、合并、抽象、标注冲突/时效。它不是“压缩”，而是**有批评标准的重写**。

### 怎么做

1. **先分边界**：知识库 vs 记忆 vs 会话压缩，三者在 schema、权限、TTL 上分开。
2. **L4 极小**：注入上下文控制在几千 token；只放“当前任务最相关的偏好/状态”，不要塞整个 wiki。
3. **写入要有显著性判断**：不是每句话都记；记录“为什么值得记”（用户明确偏好/反复出现/高价值事实）。
4. **可删除/可审计**：每条记忆带 `source_turn_id`、`created_at`、`confidence`、`expires_at`；支持单条删除。
5. **离线整理**：定期做去重/合并/过期；不要让 L2 无限膨胀。

### 权衡与坑

- **坑 1：把 compaction 当 memory。** 会话压缩得到的摘要链会失真，不可审计。
- **坑 2：L4 太大。** 过长的注入会降低指令遵从，反而让模型忽略关键信息。
- **坑 3：记忆无 TTL。** 用户偏好会变；过期记忆会误导。
- **坑 4：用强模型就不做 baseline。** 文中说强模型增益更小，必须同报 baseline 才能判断记忆是否值得。
- 【我的建议】先做 L1 + L2 + 极小 L4；L3 的 wiki 抽象层等“跨文档综合”需求明确后再建。

### 架构师视角

- 记忆是**产品资产**，知识库是**企业资产**；两者的治理责任人不同。
- 观测出口：`memory_write_rate`、`memory_hit_rate`、`injected_tokens`、`stale_memory_rate`、`memory_delete_latency`。
- **一句话**：**知识库记“世界”，记忆记“你”；不要用同一个库同时干两件事。**

### 自测 3 题

1. 你的 agent 记忆和知识库是同一个索引吗？如果是，写入冲突怎么处理？
2. 你的 L4 注入多少 token？有没有因为“记忆太长”导致指令遵从下降？
3. 一条错误记忆，你能在多久内定位并删除？

## 知识点 2：RAG + Reasoning（R6-10）

### 一句话结论

**检索与推理不是两阶段，而是交替循环：推理产生“我需要什么证据”，检索提供证据，证据再修正推理。** 但交替会带来成本、延迟与“什么时候停”的问题；正确形态是**带预算的循环 + 独立验证器**，而不是无限自我反思。

### 为什么重要

- 多跳问题、诊断问题、比较问题，往往需要“先推理出中间实体，再检索验证”。
- 2026 年的 Self-Correcting RAG（arXiv:2604.10734）把上下文选择建成 MMKP、用 NLI-guided MCTS 在测试时探索推理路径；MM-R2（arXiv:2607.22643）则强调“先推理要查什么、在哪查，再检索”。
- 但推理循环容易失控：轮数越多，延迟/成本越高，且可能“越推越偏”。

### 核心机制：检索-推理交替

```text
问题
  ↓
推理：我需要哪些证据？哪些是已知/未知？
  ↓
检索：查子问题/实体/关系
  ↓
验证：证据支持吗？还缺什么？
  ↓
推理：更新假设/答案
  ↓
充分？→ 输出；不足？→ 下一轮（受预算约束）
```

**两种控制方式：**

- **广度优先**：先分解子问题，并行检索，再综合；适合多跳。
- **深度优先**：沿一条假设链逐步检索/验证；适合诊断/排障。

### 怎么做

1. **显式维护“证据缺口”**：每轮记录已知/未知/冲突；停止条件看“缺口是否闭合”，不看轮数。
2. **设预算**：`max_rounds`、`max_tokens`、`timeout`；超过就返回“部分答案 + 不确定性”。
3. **独立验证器**：用 NLI/引用核查判断“证据是否支持当前结论”，不要让推理器自评。
4. **保留轨迹**：记录每轮的 query、证据、假设变化；便于归因与审计。
5. **按问题类型启用**：多跳/诊断启用；单跳事实不启用。

### 权衡与坑

- **坑 1：无限反思。** 没有预算的 self-reflection 会烧钱且不提升。
- **坑 2：推理器自评。** 会自我确认；要用独立验证器。
- **坑 3：只增加轮数，不产生新证据。** 多轮检索若 query 不变，只是重复查同一批文档。
- **坑 4：忽略延迟。** 多轮循环的 P95 延迟可能不可接受。
- 【我的建议】先做“两轮：分解 + 验证”，确认收益后再加轮；不要一上来 MCTS。

### 架构师视角

- RAG + Reasoning 是**用计算换证据**；必须能说清“多一轮带来多少正确率”。
- 观测出口：`rounds_per_query`、`evidence_gap_closure_rate`、`marginal_accuracy_per_round`、`p95_latency`、`cost_per_query`。
- **一句话**：**推理负责“知道该找什么”，检索负责“证明它”；两者交替，但必须有刹车。**

### 自测 3 题

1. 你的多跳流程是固定轮数，还是看“证据缺口”停止？
2. 你的验证器是独立的，还是生成器自己说“我觉得够了”？
3. 多一轮检索带来的正确率提升，能覆盖它的延迟/成本吗？
