## 知识点 1：引用与可追溯（R5-03）

### 一句话结论

**引用忠实度是句子级、可验证的“支持关系”，不是文档级的“相关链接”。** 一个结论引用了 3 篇文档，但只有 1 篇真正支持它，就不算“引用正确”。而且，**用来判断引用是否忠实的核查器本身会有 3%–18% 的波动**，所以引用率必须带“核查器 + 协议”一起报告。

### 为什么重要

- 在法务、医疗、金融场景，**“有引用”是合规底线**；但“引用不支持结论”比“没有引用”更危险，因为用户会相信它。
- 2026 年的实证（arXiv:2607.20527）显示：同一批 agent 输出，**不支持引用率**会因核查器严格度从 **约 3% 变到 18%**；不同核查器在“该标红哪些”上的负类一致性只有 **0.27–0.30**。这意味着：**没有命名核查器的引用指标，不可跨系统比较**。
- 作为架构师，你需要把“引用”设计成**数据契约**，而不是提示词里的礼貌要求。

### 核心机制：引用链

```text
生成答案
  ↓
拆成 claim（原子结论句）
  ↓
为每个 claim 找 evidence span（原文逐字片段）
  ↓
判断 support：entailed / partial / unsupported
  ↓
输出：claim ↔ source_id ↔ page ↔ quote ↔ support
  ↓
审计：抽样人工复核 + 自动核查器校准
```

**最小引用 schema：**

```json
{
  "claim_id": "c1",
  "claim": "该制度自 2026-07-01 起生效",
  "source_id": "doc-123",
  "page": 7,
  "quote": "本制度自 2026 年 7 月 1 日起施行。",
  "support": "entailed"
}
```

### 怎么做

1. **强制“逐字 quote”**：引用必须包含原文中可检索到的连续片段；没有 quote 的引用，一律视为“参考”而非“证据”。
2. **句子级拆分**：把长答案拆成 claim，逐条判定 support；不要用一个文档级“相关”覆盖整段答案。
3. **核查器校准**：抽 100 条人工标金标，测核查器的 `support_recall` 与 `unsupported_precision`；不达标不上线。
4. **上线后监控**：`citation_unsupported_rate`、`citation_coverage`（有引用的 claim 占比）、`quote_verbatim_rate`。
5. **冲突引用显式化**：多份证据冲突时，输出“支持/反对”两组，不要只挑支持结论的那篇。

### 权衡与坑

- **坑 1：只统计“有没有引用”。** 这会把“引了一篇相关文章”算成正确，掩盖不支持。
- **坑 2：用 LLM 核查但不校准。** LLM 核查器有严格度偏差；必须用人类金标校准。
- **坑 3：引用整篇文档而不是 span。** 用户点进去找不到依据，信任会崩。
- **坑 4：为了引用而引用。** 模型可能编造 quote；要有“quote 必须能在原文检索到”的硬校验。
- 【我的建议】先把引用 schema 和数据管道建好，再谈“引用率提升”；没有 schema，指标不可比。

### 架构师视角

- 引用是**审计接口**：它让 RAG 从“聊天机器人”变成“可复核的知识系统”。
- 观测出口：`citation_unsupported_rate`、`citation_coverage`、`quote_verbatim_rate`、`claim_count_per_answer`。
- **一句话**：**引用不是给用户看的装饰，是给系统审计的凭证。**

### 自测 3 题

1. 你的系统里，“有引用”的比例是多少？“引用确实支持结论”的比例是多少？两个数都测了吗？
2. 你的引用能定位到原文的哪一句/哪一页吗？还是只能定位到文档？
3. 如果核查器把“部分支持”判成“支持”，你的业务能接受吗？你会怎么校准？

## 知识点 2：结构化输出（R5-04）

### 一句话结论

**结构化输出是“交付协议”，不是“思考方式”。** 强制 JSON/XML 会压缩模型的生成空间，**显著降低推理能力，且约束越严降得越多**；正确做法是：先自由推理，再用受约束的步骤产出结构化结果，并把“schema 合规率”和“任务正确率”分开验收。

### 为什么重要

- RAG 的下游常常是工单、审批、数据库：没有结构化输出，系统无法消费。
- 但 2024 年的实证（arXiv:2408.02442）显示：**格式限制下推理能力显著下降；越严格的格式约束，下降越大**。
- 2026 年的工程基准进一步把问题拆成两个指标：**schema hit rate（能否解析）**与**task accuracy（答得对不对）**。很多方案 hit rate 99%，accuracy 却掉了。

### 核心机制：两段式输出

```text
第一段：自由推理（自然语言）
  - 分析证据、比较冲突、形成结论
第二段：结构化交付（JSON）
  - 只放下游需要的字段
  - 每个字段有明确来源/引用
```

**一个 RAG 答案 schema：**

```json
{
  "answer": "string",
  "confidence": "high|medium|low",
  "claims": [
    {"claim": "string", "citations": ["E1"], "support": "entailed|partial|unsupported"}
  ],
  "abstain": false
}
```

### 怎么做

1. **两段式**：先让模型自由写“推理草稿”，再用第二次调用/同一调用的后半段产出 JSON；两段用明确分隔符。
2. **schema 最小化**：只保留下游真正消费的字段；字段越多，模型越容易“为了填满而编”。
3. **双指标验收**：`schema_hit_rate` + `task_accuracy`；若 hit rate 升而 accuracy 降，回退。
4. **校验 + 重试**：先解析；失败时让模型“指出不符合的字段并修正”，而不是简单重试。
5. **允许 abstain 字段**：结构化输出必须能表达“不确定/无答案”，否则模型会被迫编造。

### 权衡与坑

- **坑 1：在 JSON 里写思维链。** 字段化的“reasoning”往往变成形式化废话；把推理放在自由段。
- **坑 2：schema 过度设计。** 20 个字段的 schema 会让模型顾此失彼。
- **坑 3：把“解析成功”当“任务成功”。** 这是最常见的验收错误。
- **坑 4：强制枚举导致幻觉。** 如果 `category` 只有 5 个选项，而真实答案不在其中，模型会硬选一个；要留 `other/unknown`。
- 【我的建议】对高价值任务，宁可多一次调用做“自由推理 + JSON 交付”，也不要为了省一次调用牺牲正确率。

### 架构师视角

- 结构化输出是**系统集成契约**：它决定了 RAG 能否进入工作流，而不是停在聊天窗口。
- 观测出口：`schema_hit_rate`、`task_accuracy`、`retry_rate`、`abstain_rate`、`field_missing_rate`。
- **一句话**：**让模型自由地想，让它严格地交。**

### 自测 3 题

1. 你的 schema 有多少字段？其中几个是下游真正会用的？
2. 你测过“自由文本 vs JSON”的推理正确率差异吗？差多少？
3. 如果 schema 解析失败，你的重试是“再试一次”还是“让它解释哪里不符合”？哪种更容易引入幻觉？

## 今日前沿插入

**① 引用核查器本身不可靠（arXiv:2607.20527，2026-07）。**
同一批输出，不支持引用率会因核查器严格度在 **3%–18%** 间波动；负类一致性仅 **0.27–0.30**。论文给出“金标锚定 + split-conformal”的可部署方案。→ [精读](../05-前沿资料/2026-12-01-引用忠实度与可追溯.md)

**② 格式约束会降低推理（arXiv:2408.02442，2024-08）。**
结构化格式下模型推理能力显著下降；约束越严格，下降越大。2026 工程基准进一步强调“hit rate ≠ accuracy”。→ [精读](../05-前沿资料/2026-12-02-结构化输出与格式限制.md)

**趋势观察（非定论）**
2026 年输出层的竞争点：**“可解析”正在变成基础能力，“可审计 + 不伤推理”才是差异化**。引用 schema 与两段式输出会成为生产 RAG 的默认配置。**属趋势观察。**
