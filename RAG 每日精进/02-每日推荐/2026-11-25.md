- **R4-01 Embedding 选型**：选型的正确单位不是"哪个模型最强"，而是**"在我的语料 + 我的查询分布 + 我的延迟/成本约束下，哪几个候选值得跑一次自己的金标集"**；2026 年的技术报告把这件事说得更直白：**排行榜第一的模型，很少是某个具体部署的最优选择**。

## 知识点 1：Embedding 选型（R4-01）

### 一句话结论

选型要沿**四个轴**做约束求解——**语言覆盖、领域契合、维度/存储、上下文长度**——然后用**自己的金标集**做最终裁决；榜单只能用来"筛候选"，不能用来"做决定"，因为榜单的任务分布、文档长度、领域词表都和你的语料不同。

### 为什么重要

**证据一：这件事被明确批评过。**

【论文结论】*Choosing a Text Embedding Model: A Practical Benchmarking and Decision Framework*（Baidya，arXiv:2607.23507，2026-07-26，技术报告）开篇就点明：选 embedding 是构建检索系统里**最有影响、却最常被草率处理**的决定之一，而**"排行榜第一"的模型很少是某个具体部署的最优选择**。它做的事情正是我们一直在强调的：**把模型选择放回完整检索流水线里**——embedding 怎么产生、怎么索引与大规模检索、**分块策略如何塑造检索质量**——而不是孤立地比分数。报告在英文检索任务上把 T3EM（商业 API 模型）与一批开源模型对比，并把结论放回 MTEB 的七类任务全景（分类、聚类、语义相似、重排、pair classification、bitext mining、摘要）里讨论，最终给出按**任务 / 延迟 / 成本 / 部署约束**分类的建议。

→ 对你最有用的一句：**选型是一个"约束求解"问题，不是一个"排名查询"问题。**

**证据二：MTEB 的用法本身有讲究。**
【趋势观察】2026 年多篇工程文章的共同建议是：**只看 MTEB 的 Retrieval 子集（用 nDCG@10），不要看总榜**；因为总榜把分类、聚类、摘要等任务混在一起，而你的场景是检索。（这类建议来自厂商/工程博客，属**趋势观察**，但方向与上面的技术报告一致：**任务匹配 > 综合分数**。）

**为什么"四个轴"缺一不可——各自的失败症状：**

| 轴 | 选错的症状 | 怎么量 |
|---|---|---|
| **语言覆盖** | 中英混合库里，英文查询召回中文证据时掉点；低资源语言更陡 | 按语言分桶算 recall（第 007 期 R1-08 的 `recall_gap_lang`） |
| **领域契合** | 通用模型在你领域词表上"像但不对"（这正是 R4-02 的主题） | 领域内金标集的 recall@k，对比通用集 |
| **维度 / 存储** | 768→3072 维让索引内存涨 4 倍，检索延迟上升 | 直接算：`N × d × 4 bytes`（第 013 期 R3-04 的账） |
| **上下文长度** | 块大于模型最大长度 → 被截断（且**静默截断**，不报错） | 检查 `chunk_tokens_p99 vs model_max_tokens` |

**"维度"这一轴值得单独说，因为它最容易被低估。**
【论文结论】第 013 期引过的 *Scaling Laws for Embedding Dimension*（arXiv:2602.05062）已经给出：维度与效果是幂律关系，**在与训练任务一致的评测上维度越大越好（收益递减），但在不那么一致的评测上，某些任务反而随维度增大而变差**。同时存储与检索成本线性上升。→ **"加大维度"不是无风险操作，它是一个有拐点的交易。**

### 核心机制 / 数据流

**选型的正确流程（把"决定"和"筛选"分开）：**

```
① 约束先行（不看模型，先看自己）
   - 语言：库里各语言占比？查询语言分布？
   - 长度：chunk_tokens 的 p50/p99？模型最大长度够不够？
   - 存储：能承受的索引内存上限（决定维度上限）
   - 部署：必须私有化？必须 CPU？必须低延迟？
② 候选筛选（用公开榜单，只用 Retrieval 子集）
   - 按 ①的约束过滤掉不合格的（长度不够、语言不支持、维度太大）
   - 剩下 5–8 个候选，不再排名
③ 本地裁决（用自己的金标集，30–50 条）
   - 同一套切分、同一套 chunk、只换 embedding
   - 指标：recall@5 / recall@10 + 索引内存 + p95 延迟
④ 成本复核（把 embedding 成本并入 R0-06 的乘数模型）
   - 索引期：语料 token × 单价（一次性 + 每次重建）
   - 查询期：query token × QPS（通常可忽略，除非超短 query 高并发）
```

**为什么第 ③ 步必须"只换 embedding"？** 因为第 004 期已经证明：**元数据增强与层级切分对下游准确率的贡献，可能大于换模型本身**（arXiv:2604.04948）。如果你同时改了切分又换了模型，你无法归因。

**一个常被忽略的耦合：embedding 的最大长度 ↔ 你的块大小。**
```
若 chunk_tokens_p99 = 900，而模型最大长度 = 512
  → 后 388 个 token 被静默截断
  → 你的 recall 下降，但你以为是模型不行
【我的建议】把 max_tokens 当作硬约束筛模型，而不是事后发现
```
这与第 010 期 R2-04 的"上下文化会加长块"直接相关：**给块加了 100 token 上下文后，很多块会越过模型的长度上限**。

### 怎么做（3 步）

**第 1 步：先算"你能不能负担得起某个维度"。**

```python
def index_memory_gb(n_chunks: int, dim: int, float_bytes=4, overhead=1.15):
    raw = n_chunks * dim * float_bytes / 1e9
    return raw * overhead          # overhead：索引结构/元数据/对齐

for d in (384, 768, 1024, 1536, 3072):
    print(d, f"{index_memory_gb(2_000_000, d):.1f} GB")
```
【我的建议】把这张表放在选型会议的第一页。**很多"效果最好的模型"在第一页就被内存预算淘汰了**——这不是妥协，这是约束。

**第 2 步：搭一个"只换 embedding"的对比台。**

```python
CANDS = ["model_a", "model_b", "model_c"]     # 从 ① 的约束筛出来的
results = {}
for m in CANDS:
    emb = load_embedder(m)
    idx = build_index(chunks, embed_fn=emb.encode,   # 同一批 chunks，同一份元数据
                      normalize=True)                 # 统一归一化，避免度量混淆
    rec5 = mean(recall_at(idx, q, gold, 5) for q, gold in golden_50)
    results[m] = {"recall@5": rec5, "mem_gb": index_memory_gb(len(chunks), emb.dim),
                  "p95_ms": p95_latency(idx, queries)}
```
**三个必须一起报的数**：`recall@5`、`索引内存`、`p95 延迟`。**只报 recall 的选型报告是不完整的**（第 013 期讲过：中间指标涨、端到端跌是常态）。

**第 3 步：用"几何体检"做交叉验证（第 012 期的方法，在这里复用）。**

```
对每个候选算：
  ① top1_var_ratio（最主导维度方差占比）→ 判断 cosine 是否合适
  ② mean_pairwise_cos → 判断相似度是否有区分度
  ③ 对抗查询通过率（否定/角色互换）→ 判断组合敏感性
若某模型 recall 高但 ② 很平（所有对都 0.7+）→ 它的"高 recall"可能是脆弱的
```

### 权衡与坑

- **坑 1：从总榜挑第一名。** 【论文结论】排行榜第一很少是具体部署的最优（arXiv:2607.23507）。**榜单筛候选，金标集做决定。**
- **坑 2：只看 recall，不看内存与延迟。** 一个 3072 维模型 recall 高 2 个百分点，但索引内存翻 4 倍、延迟翻倍——**这在你的成本模型里可能直接不成立**。
- **坑 3：忽略最大长度的静默截断。** 超过模型上限的部分**不报错、直接丢弃**。**必查 `chunk_tokens_p99`。**
- **坑 4：同时改切分和模型。** 【论文结论】切分/元数据的贡献可能大于换模型（第 004 期）。**一次只改一个变量。**
- **坑 5：以为"多语言模型"就等于"多语言好用"。** 多语言模型的**跨语言检索**能力与**单语言内**能力是两回事（第 007 期 R1-08：跨语言的主要难点在检索排序）。**要按语言分桶测。**
- **坑 6：忘了重建成本。** 换 embedding = 全量重建索引（第 008 期 R1-09 的 `index_epoch`）。**一次换模型的代价是"重建时间 + 双倍存储（影子代次）"。**
- 【我的建议】顺序：**约束筛选 → 内存/延迟预算 → 只换 embedding 的金标对比 → 几何体检 → 才谈微调（R4-03）**。

### 架构师视角

- **embedding 是"不可逆的基础设施选择"**：它决定了索引结构（维度→内存）、检索度量（第 012 期）、甚至切分策略（最大长度↔块大小）。**所以它值得一次正式的 ADR，而不是一次试用。**
- **把"换模型"设计成可回滚的发布**：与第 008 期的影子代次共用一套机制——新模型建新 epoch，旧 epoch 保留到验证通过。**这比"效果好就切"重要得多。**
- **观测出口**：`recall@5 / recall@10`（分语言、分领域）、`index_memory_gb`、`p95_embed_latency`、`truncation_rate`（被截断的块比例）、`top1_var_ratio`。
- **一句话**：**embedding 选型的产出不是"一个模型名"，而是"一张在你语料上可复现的三列对比表"**（recall / 内存 / 延迟）。

### 自测 3 题

1. 你的块 `p99` 长度是多少？你的 embedding 模型最大长度是多少？如果前者大于后者，你损失了哪部分内容？
2. 如果你把 embedding 从 768 维换到 1536 维，索引内存涨多少？你的机器/预算能承受吗？
3. 你的选型报告里，除了 recall，还报了哪两个数？如果只报 recall，评审时会漏掉什么风险？

## 知识点 2：对比学习与难负样本（R4-02）

### 一句话结论

embedding 的判别能力**由训练时的负样本定义**——你希望它区分什么，就要在训练里让它见过"差一点就对"的反例；而 2026 年被形式化的核心难题是**生成-判别鸿沟**：**LLM 擅长生成"流畅合理"的文本，但对比学习需要的是"在决策边界上有策略地违反相关性"**，二者错位会导致合成负样本**反而降低检索性能**。

### 为什么重要

**先把"看起来像但不相关"翻译成训练语言。**
对比学习（InfoNCE 一类）的目标是：
```
对一个 query q、正例 d+、负例 d−：
  最大化 sim(q, d+) 的同时，最小化 sim(q, d−)
```
如果你的负例都是"随机取的另一篇文档"，模型学到的判别边界就是"**这个话题 vs 另一个话题**"——它能把"讲保险的"和"讲烘焙的"分开，但**分不开"2024 版报销制度"和"2026 版报销制度"**。这两者在嵌入空间里几乎同向（第 012 期讲过：组合改写保持高相似度），而你的负样本里从来没有这类反例，所以模型从未被要求学会区分它们。

**这就是"看起来像但不相关"的机制根源：不是模型"不懂语义"，而是它的负样本没有覆盖你的判别需求。**

**【论文结论】难负样本挖掘的三个内在局限。**
*When Hard Negatives Hurt*（Zhang 等，**KDD 2026**，arXiv:2606.01304）把这件事讲得很透。难负样本挖掘已成为训练检索器的主流策略，但它有三个内在限制：
1. **负例受语料可用性约束**（你想找"差一点就对"的反例，语料里不一定有）；
2. **按检索器分数选择，而不是按诊断价值选择**（分数高 ≠ 对训练有用）；
3. **随着检索器变强，越来越多被"假阳性"污染**（那些"检索器认为不相关、其实是相关"的样本被当成负例，直接教错）。

**LLM 合成负样本看起来是有原则的替代方案**（不受语料限制、可定向、无假阳性风险），**但论文明确说：朴素地把生成负例加入对比学习，常常反而降低检索性能。**

**根因被形式化为"生成-判别鸿沟"（generative-discriminative gap）**：LLM 生成优化的是**流畅、合理**；对比学习需要的是**在决策边界上有策略的相关性违反**。论文识别出两种复合失效模式：
- **判别无关生成（discriminative-agnostic generation）**：LLM 缺乏对"查询信息需求"的显式建模，于是产出**通用或话题漂移**的文本，**提供不了对比信号**；
- **来源依赖捷径（source-dependent shortcuts）**：分布上的伪影让模型能靠"**这段是生成的还是真实的**"来区分，而不是靠相关性——导致**梯度漂移，主动破坏优化**。

**解法：CausalNeg（两个模块，都可抄思路）。**
1. **CoT 引导的反事实扰动**（数据构造）：把"这篇文档为什么满足该查询"**分解成显式的信息需求**，然后**外科式地违反其中单个需求**，从而构造出**硬度可控、可解释**的负例；
2. **查询视角熵最大化**（训练时）：把生成的负例**分散在相似度谱上**，最小化"来源身份"与"相似度分数"之间的互信息，**压制捷径利用**。

**再看一个真实工业案例——它给出的是"预期管理"的教训。**
【论文结论】*Negative Data Mining for Contrastive Learning in Dense Retrieval at IKEA.com*（Agapaki & Gill，arXiv:2605.00353，2026-05-01）：他们用**产品层级分类 + 产品属性**构造语义上有挑战的负例，并用 **LLM-as-judge 对全部候选产品打分**（而不是稀疏人工标注或随机采样）来生成训练数据。结果：
- **离线：加拿大市场真实用户查询上，类别准确率平均 +2.6%**；
- **但长尾查询的线上 A/B：用户参与度指标无统计显著差异（p > 0.05）**；
- 他们把差距归因到**用户搜索行为**：**67% 的热门搜索零点击率超过 50%**——也就是说，**大量搜索会话无论排序如何都不会产生点击**。

→ 这一段的价值不在"+2.6%"，而在它诚实地说出了：**离线检索质量提升，不必然转化为线上参与度**（这正是第 013 期 R7-06 要讲的"离线 vs 在线"，提前给你打了预防针）。

**第三条：这已经是一个"阶段感知"的设计问题。**
【论文结论】MeVer at CheckThat! 2026（arXiv:2605.24236）：提出**聚类感知的难负样本挖掘**——利用检索候选池的语义结构来构造更有信息量的负例；结论是**难负样本挖掘应当被视为"阶段感知的设计问题"，而不是单一检索技巧**。

### 核心机制 / 数据流

**三类负样本，以及它们的"教给模型什么"：**

| 负例类型 | 怎么来 | 教模型区分什么 | 风险 |
|---|---|---|---|
| **随机负例** | 从库里随机抽 | 话题级差异（保险 vs 烘焙） | 对细粒度判别几乎无帮助 |
| **批内负例**（in-batch） | 同一 batch 里其他 query 的正例 | 中等难度差异 | 受 batch 组成影响，不稳定 |
| **难负例**（hard negative） | 检索器高分但未标注为正 | **决策边界上的细微差异** | **假阳性污染**（可能是真相关） |
| **合成负例**（LLM 生成） | 让 LLM 改写正例、违反某个条件 | **可控、可解释的硬度** | **生成-判别鸿沟**、来源捷径 |

**"假阳性污染"为什么会随模型变强而恶化（机制）：**
```
检索器变强 → 它召回的高分未标注文档里，"其实相关但没标注"的比例上升
          → 这些被当作难负例 → 模型学到"把相关的判为不相关"
          → 这是主动的教错，而不是噪声
```
【论文结论】这正是上面论文列的第 3 条局限（"increasingly contaminated by false positives as the retriever improves"）。**换句话说：越努力挖难负例，越容易挖到"标错的真相关"。**

**一个可操作的合成负例模板（对齐 CausalNeg 的第 1 个模块）：**
```
给定 (query, 正例文档)：
① 让 LLM 写出"这篇文档满足该查询的 3–5 个必要条件"
   例（问"逾期利息怎么算"）：产品类型=个人贷；期限口径=按日计息；利率=年化 18%；
                              起算日=还款日次日；宽限期=10 天
② 针对其中**一个**条件做最小违反（其余保持不变）：
   改"宽限期=10 天" → "宽限期=3 天"
③ 该文档即为"硬度可控、可解释"的难负例：
   它与正例只差一个条件，但答案确实不同
④ 同时记录"违反了哪个条件"，作为可审计的训练标签
```
【我的建议】这个模板的好处是：**你能控制硬度**（违反 1 个条件 = 难；违反 3 个 = 中），而且**负例的"错在哪"是可解释的**——这对于排查"模型为什么学歪"极有价值。

### 怎么做（3 步）

**第 1 步：先诊断"你的检索器分不清什么"——用对抗对，不用指标。**

```
取 20 组"只差一个条件"的真实文档对（新旧版本、不同产品、不同地区）：
  (d_a, d_b) 同一主题，但答案不同
测：用 d_a 的内容做 query，检索器能否把 d_a 排在 d_b 之前？
统计 pairwise_accuracy = 正确的比例
若 < 0.7 → 你的 embedding 在这个维度上没有判别力
```
【我的建议】这个测试比 recall 更能暴露问题：**recall 会掩盖"把相近的两条混在一起"**，因为召回的都算命中。

**第 2 步：如果你要微调，按"条件违反"构造负例（而不是随机挖高分文档）。**

```python
def build_hard_negatives(query, positives, llm, n_conditions=3):
    negs = []
    for pos in positives:
        conds = llm.extract_necessary_conditions(query, pos.text)[:n_conditions]
        for c in conds:
            neg_text = llm.minimally_violate(pos.text, condition=c)  # 只违反这一条
            negs.append({"text": neg_text, "violated": c, "source": "synthetic"})
    return negs
```
【论文结论】两个必须配套的防护：① **不要让模型能靠"来源"区分**——训练时把合成负例与真实负例混合、并分散到相似度谱上（CausalNeg 的熵最大化）；② **抽样人工核验**——合成负例里"其实仍然相关"的比例（假阳性率）必须被测量，而不是假设为零。

**第 3 步：验收要"分层"，别只看总 recall。**

```
必须分开报的四项：
  ① recall@k（整体）
  ② pairwise_accuracy（只差一个条件的文档对）
  ③ hard_negative_false_positive_rate（合成/挖掘负例中实为相关的比例）
  ④ 领域外 recall（换一个没见过的域）
若 ① 涨而 ② 不涨 → 你只是在"更会认话题"，没学会细粒度判别
若 ① 涨而 ④ 跌 → 过拟合到你的语料分布
```
【论文结论】这与第 012 期那篇"结构负样本训练会降低零样本检索能力"的结论互相印证：**细粒度判别能力与泛化能力常常是此消彼长的**。

### 权衡与坑

- **坑 1：以为"难负例越多越好"。** 【论文结论】难负例受语料约束、按分数选而非按诊断价值选、且**随模型变强而假阳性污染加重**。**挖得越狠，标错的风险越大。**
- **坑 2：直接用 LLM 生成负例。** 【论文结论】朴素加入生成负例**常常降低检索性能**（生成-判别鸿沟）。**必须做"条件违反 + 硬度控制 + 防来源捷径"。**
- **坑 3：忽略来源捷径。** 如果合成负例在文风、长度、格式上有系统性差异，模型会学"识别生成文本"而不是"识别不相关"。**混入真实负例 + 熵最大化是必要的。**
- **坑 4：只看离线指标。** 【论文结论】IKEA 案例：离线 +2.6%，**长尾查询线上 A/B 无显著差异（p>0.05）**，且 67% 热门搜索零点击率 >50%。**离线涨点不等于线上有效**（第 013 期 R7-06）。
- **坑 5：把"假阳性"当噪声容忍。** 它不是随机噪声，它是**系统性的反向信号**——把相关的教成不相关。
- **坑 6：一次改太多。** 同时换 embedding 模型 + 改切分 + 加难负例训练，你无法归因（第 004 期的方法论纪律）。
- 【我的建议】**先做第 1 步的诊断，再决定要不要微调**：如果你的 pairwise_accuracy 已经不低，微调的收益很可能小于"加 rerank + 加多样性"（第 016 期）。

### 架构师视角

- **embedding 的判别边界是"产品需求"，不是"模型属性"。** 你需要它区分"新旧版本 / 不同产品 / 不同地区"，就必须在训练或选型阶段把这三类反例喂进去——**否则它永远分不清，而你会误以为是模型不够大。**
- **R4-02 与 R1-06、R3-09 是一条线**：**版本判别**（元数据能不能过滤）、**误导拒答**（证据冲突能不能识别）、**细粒度检索**（embedding 能不能分开）——三者解决的是同一个业务需求"别拿错的那份"。**优先用元数据过滤解决（便宜可靠），embedding 微调是最后手段。**
- **观测出口**：`pairwise_accuracy`（对抗对）、`hard_neg_fp_rate`（负例假阳性率）、`ood_recall`（域外召回）、`source_shortcut_gap`（合成负例与真实负例的相似度分布差异）。
- **一句话**：**embedding 不是"越大越懂"，而是"被教过什么才懂什么"**——你想让它分清新旧版本，就得让它在训练里见过"只差一个版本号"的反例。

## 今日前沿插入

> 只写有实质更新、且能核验来源的内容。

**① embedding 选型被明确批评为"常被草率处理的决定"（arXiv:2607.23507，2026-07）**
技术报告指出：**排行榜第一很少是具体部署的最优选择**；主张把模型选择放回完整流水线（embedding 产生 → 索引与大规模检索 → **分块策略如何塑造检索质量**），并按任务/延迟/成本/部署约束给建议。→ https://arxiv.org/abs/2607.23507

**② 难负样本合成被证明"方法不当会变差"（KDD 2026，arXiv:2606.01304）**
把难负样本挖掘的三条局限（语料受限、按分数选而非按诊断价值、假阳性随模型变强而恶化）形式化，并给出**生成-判别鸿沟**与两种失效模式（判别无关生成、来源依赖捷径）；CausalNeg 用"CoT 反事实扰动 + 查询视角熵最大化"解决。→ https://arxiv.org/abs/2606.01304
**为什么值得注意**：它是"合成数据不是免费午餐"最具体的一次实证。

**③ 工业界案例：离线涨点未必转化为线上（arXiv:2605.00353）**
IKEA 用产品层级 + 属性构造难负例、LLM-as-judge 全量打分，离线类别准确率 **+2.6%**，但**长尾查询线上 A/B 无显著差异（p>0.05）**；归因到 **67% 热门搜索零点击率 >50%**。

**④ 难负样本挖掘被定位为"阶段感知的设计问题"（CheckThat! 2026，arXiv:2605.24236）**
聚类感知的难负样本挖掘，利用候选池的语义结构构造更有信息量的负例。

**趋势观察（非定论）**
2026 年 M4 开工时的一个明显信号：**"更大的 embedding"不再是主线，改选型方法论（约束求解 + 本地金标）与负样本质量（诊断价值而非分数）**成为重点。同时"合成负例"从"便宜好用"转向"需要精心设计才不伤效果"。**属趋势观察。**
