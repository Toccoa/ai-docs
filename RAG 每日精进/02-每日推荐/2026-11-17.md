## 知识点 1：块大小与重叠（R2-02）

### 一句话结论

块大小没有通用最优，**重叠则先别调**——多项端到端研究的结论是"重叠没有可测收益、只增加索引成本"；所以你的实验设计应该是**一维扫块大小、重叠固定为 0（或极小）**，而不是在二维网格里盲搜。

### 为什么重要

**先看三条互相独立、但指向同一件事的证据。**

**证据 A：重叠收益为零。【论文结论】** Bennani & Moslonka（arXiv:2601.14123，2026-01，Natural Questions 端到端、SPLADE 检索 + Mistral-8B 生成）系统变换了切分方法（token / sentence / semantic / code）、块大小、**重叠**与上下文长度，给出的四条结论里第一条就是：**overlap provides no measurable benefit and increases indexing cost**。同一篇还有两条对你有用的：**句子级切分性价比最高**（在约 5k token 以内与语义切分打平）；**超过约 2.5k token 会出现"上下文悬崖"**，质量下降。

**证据 B：重叠变量在其他研究里是"不确定"的。** 在葡萄牙语法律域的研究里，结论是"**更大的块更好，但重叠的影响仍不确定（inconclusive）**"。两篇说法不完全一样，但方向一致：**没有任何一篇给出"重叠 X% 最优"的可复现结论。**

**证据 C：块大小的最优点会漂移，而且和嵌入模型耦合。【论文结论】** Bhat 等（arXiv:2505.21700）：**结论型/事实型数据集偏好 64–128 token，需要全局理解的数据集偏好 512–1024 token**；并且**不同嵌入模型的块大小敏感度不同**（Stella 受益于大块、Snowflake 受益于小块）。

**再看一个"块大小影响到底有多大"的对照实验，它会修正你的直觉。【论文结论】** Manepalli & Dasari（Zenodo，10.5281/zenodo.18226194，SQuAD v1.1，300 组 QA，固定嵌入与索引只变块大小/重叠）：
- Grounded@1：小块 84.3%、中块 84.3%、大块 84.7%（**差异 <0.5 个百分点**）
- **Grounded@2 与 Grounded@4：三种块大小完全一样（91.0% / 95.0%）**

**这句话的意思是：块大小的影响在 k 变大时会被"兜住"。** 如果你的链路是"取 top-5 再拼上下文"，那么块大小调优的收益上限本来就不高——**这是你必须先知道的天花板，否则会把一周时间花在 0.4 个百分点的波动上**。

**但块大小不是不重要，它影响的是另一件事：成本与"上下文悬崖"。** 把块放大，检索到的 token 数会涨；一旦总上下文越过那个"悬崖"（上面约 2.5k token 的观察），质量反而掉。

### 核心机制 / 数据流

**三个量互相耦合，必须一起决定：**

```
块大小 B（token）  ──决定──▶  单块信息量  ──决定──▶  嵌入是否"被平均掉"
      │                                                  │
      ├─决定──▶ k × B ≈ 检索到的有效 token 量 ──决定──▶ 是否越过"上下文悬崖"
      │
      └─决定──▶ 索引条目数 ≈ 语料 token / B ──决定──▶ 存储与检索成本
重叠 O：索引条目数为 N/(B−O)，存储与 embedding 成本按 1/(1−O/B) 放大
        （B=512、O=10% → 成本 ×1.11；O=25% → ×1.33；O=50% → ×2）
```

**重叠的真实代价（容易忽略的三点）：**
1. **嵌入成本与存储 ×1/(1−O/B)** —— 上表直接算；
2. **重复命中**：同一段内容出现在 2–3 个块里，top-k 会被同源副本占满（这正是第 006 期 R1-05 讲的 `ρ` 问题，`unique_ratio` 会掉）；
3. **"部分更新的陷阱"**（第 008 期 R1-09 讲过）：重叠让一个变更段落横跨多块，增量更新只修其中一部分，就会留下**新旧混排的同一段文字**。

【我的建议】**默认 O = 0**。只有当"句/段边界被硬切断导致明显的信息损失"时才加，而且加到能覆盖一个完整句子的量即可（一般 ≤ 1 个句子，约 20–50 token），不要用"百分比"当参数。

### 怎么做（3 步）

**第 1 步：先确定你的天花板在哪。** 用你现有索引，固定所有其它变量，只测 k：把 k 从 1 拉到 10，看 recall 从多少涨到多少。
```
若 recall@1 ≈ recall@8（差距 <5pp） → 块大小的收益空间很小，别调它
若 recall@1 远低于 recall@8         → 收益空间大，值得扫块大小
```
【事实】上面 SQuAD 那个实验的 Grounded@1 = 84.3% 与 Grounded@4 = 95.0% 就是这个形状：**k 已经是你的主要杠杆**。

**第 2 步：一维扫块大小，重叠固定为 0。**

```python
# 只扫一维：B ∈ {128, 256, 512, 1024}，O = 0
results = {}
for B in (128, 256, 512, 1024):
    idx = build_index(corpus, chunker="sentence", target_tokens=B, overlap=0)
    for q in golden_30:
        hit = any(gold_span in c.text for c in idx.search(q, k=5))
        results.setdefault(B, []).append(hit)
    print(B, "recall@5 =", mean(results[B]),
          "avg_tokens =", mean(len([c for c in idx.search(q, k=5)]) for q in golden_30))
```
验收看**两个数**：`recall@5` 与 `平均检索 token 数`。**同时变好的那个 B 才是答案**；如果 recall 持平而 token 涨，说明你在买没用的上下文。

**第 3 步：用"上下文悬崖"给 k 设上限，而不是给 k 设一个习惯值。**

```
k_max = floor(悬崖阈值 / B)      # 例：阈值取 2500 token，B=512 → k_max ≈ 4
```
【论文结论】Bennani & Moslonka 观察到越过约 2.5k token 后质量下降，并指出**最优上下文取决于目标**：语义类指标在小上下文时最好，精确匹配类在大上下文时更好。→ **这意味着"k 固定"本身就是错的**：检索式问题取小 k、抽取式问题取大 k，用**问题类型路由 k**（这和第 003 期 R0-05 的路由思想同源）。

### 权衡与坑

- **坑 1：把 overlap 当"保险"。** 直觉上"多给点重叠，就不怕切断句子"，但端到端数据显示它没带来可测收益，只带来成本和重复命中。**先用边界对齐（句子/段落切分）解决切断问题，不要用重叠去补。**
- **坑 2：把"块大小"当全局参数。** 它是**与语料域、任务类型、嵌入模型耦合**的；你换了嵌入模型，最优 B 可能整体移动（Bhat 等：Stella 偏大块、Snowflake 偏小块）。
- **坑 3：拿"平均分"决策。** 块大小对不同问题类型的影响方向可能相反（抽取式 vs 全局理解），**必须分层看**，否则平均值会把两个相反的效应抵掉。
- **坑 4：无视 1024 那一档的塌陷。** 多份材料都显示"非常大的块"会掉（Aalto 的学位论文：1024 token 在两种架构上一致降准确率，而 256→512 的 token 成本涨了 >50%、换来的准确率提升只有 ≤2 个百分点）。**大块是成本黑洞，不是质量保险。**
- **坑 5：只在检索指标上优化。** 块变大后，检索召回可能不变，但**生成端**要处理更多无关内容。要同时看「检索 token 数」与「答案断言的可支撑比例」。
- 【我的建议】把块大小与重叠写进 `CHUNKER_VERSION`（第 008 期 R2-01 已建立），任何改动都要能按版本对比，而不是靠记忆。

### 架构师视角

- **块大小是"预算分配问题"，不是"质量调参问题"。** 在同一份 token 预算下，你有三种花法：**更大的块**、**更多的 k**、**更小的块 + 父子回填**。上面证据说明前两者的边际收益递减很快，第三种（R2-03）往往更划算。
- **给"检索到的有效 token 数"设一个硬上限**（SLO 形式），比给块大小设默认值更管用。它同时约束了成本（第 003 期 R0-06）与质量（上下文悬崖）。
- **重叠 = 0 是一个可以捍卫的设计决策**，前提是你能证明切分边界对齐了语义边界（R2-01 的结构感知切分）。**先把边界做对，再谈重叠；顺序反了，重叠就永远是拐杖。**

### 自测 3 题

1. 你现在被切分切断的信息，有多少比例是靠 overlap 补回来的？能不能改成"按句/段边界切"来解决同样的损失、同时少付 10–30% 的索引成本？
2. 如果你的 k 从 1 到 8 的 recall 曲线很平（差距 <5pp），你还应该花时间扫块大小吗？为什么？
3. 你的链路里，"一次回答平均塞进去多少 token"这个数现在能查到吗？如果查不到，你怎么知道自己有没有越过上下文悬崖？

## 知识点 2：父子块与句子窗口（R2-03）

### 一句话结论

**小块负责"被找到"，父块/邻域负责"被读懂"**——这是解耦，不是折中；但 2026 年的新证据给了它一个重要的修正：**扩张必须是条件式的（按需、按相关性判断），无脑加窗口/加父块会稀释而降低召回**。

### 为什么重要

**先讲清"为什么需要两条通道"（第 007 期 R1-07 已埋下伏笔）。**
- 只用小块：检索精度高，但块常常缺定义域/指代对象 → 生成端"答得自信但范围错"。
- 只用大块：信息完整，但嵌入被平均、每一句话的检索信号被稀释 → 召回掉。

**新证据 1：固定加窗口是有代价的。【论文结论】** SCAR（arXiv:2606.16661，预印本）明确指出：固定长度切分会导致**边界碎片化**（关键证据被切在两个块里）；静态加窗口（static windowing）和父块检索能提高召回，**但带来显著的 token 开销**。它提出**条件式扩张**：按"查询-邻居相关性"与"结构连续性惩罚"决定是否扩，阈值是相对量（相对每个块的自身相关性），因此在 3 个嵌入模型间可以**不重新校准**就迁移。
它的数字（4 个语料：RFC / GDPR / 10-K / 并购协议，N=320 条查询，其中 160 条边界碎片化）：**边界碎片查询上 92.8% recall，只用了 7.84 个块**，比静态窗口（10.16 个块）**少 22.9%**（paired bootstrap p<0.0001，Cohen's d=−1.49）；RAGAS 评估显示**保住了生成忠实度，同时上下文 token 降 27.1%**。
*（标注：单作者预印本，作为方向性证据；但它给的"条件式"判据非常可抄。）*

**新证据 2：上下文化/上下文增强并不总是帮忙，"任务依赖"非常明显。【论文结论】** Zhou 等（arXiv:2602.16974，*Beyond Chunk-Then-Embed*，复现多项既有研究）把切分统一到两个维度（分割方法 × 嵌入时机），在两个检索设定上比较：**in-corpus 检索**与 **in-document 检索（needle-in-a-haystack）**。结论：
- **in-corpus：简单结构感知方法优于 LLM 引导方法**；
- **in-document：LumberChunker 最好**；
- **上下文化切分（late chunking 类）提升 in-corpus，但降低 in-document**；
- **块大小与 in-document 效果中度相关，与 in-corpus 只弱相关**——说明"方法差异不只是块大小造成的"。

**这条对你的直接含义**：如果你的业务是"整篇文档里找一句话"（合同/手册里的条款定位），**上下文化式的小块+邻居窗口未必是解**；如果是"跨文档语料检索匹配"，结构感知 + 适度的父子回填更稳。

**新证据 3：扩张的收益可以量化到"减少多少块"。** 上面 SCAR 的 92.8% recall / 7.84 块就是可对比的锚点：**如果你现在为了拿 92% 的召回要喂 10 个块，那么条件式扩张的目标就是"同样召回、但块数更少"。** 这是一个比"块大小"更值得优化的指标。

### 核心机制 / 数据流

**三种形态，粒度不同、代价不同：**

| 形态 | 检索单元 | 供给单元 | 代价 | 适用 |
|---|---|---|---|---|
| 句子窗口 | 单句（极小） | 命中句 ± k 句 | 低（k=1–2） | 定义/事实密集、句间强依赖 |
| 父子块 | 子块（段/句） | 父块（节） | 中（父块可能很长） | 结构化文档（R1-07 有可信层级） |
| 条件式扩张（SCAR 式） | 子块 | 按相关性决定是否含邻居 | 低—中 | 想同时压召回与 token |

**数据流（推荐形态）：**

```
① 检索：只用小块（子块/句），保证嵌入不被平均
② 候选聚簇：同一父块/同一文档的多个命中先合并（避免"重复计票"，见 R1-05）
③ 条件式扩张：
   若 该块的查询相关性 ≥ τ_rel  → 只给该块（高置信，不必扩）
   若 该块较边界化（与邻居共享被切断的实体/指代）→ 扩 ±1 块或换父块
④ 组装：按文档顺序、去重、受 token 上限约束
⑤ 记账：记录"扩张触发了多少次"，这是成本与质量之间的核心旋钮
```

**判定"是否边界化"的廉价信号（不用模型）：**
- 块首句缺少主语/以连词开头（"因此""此外""该条款"）；
- 块尾句没有句末标点，或不构成完整语义；
- 块内出现指代词但块内无先行词；
- 相邻块共享专有名词但只在一块出现（实体被切断）。

### 怎么做（3 步）

**第 1 步：先用"边界碎片查询集"证明问题存在。**
```
构造（或用 SCAR 的思路构造）：20–30 条"答案被切在块边界"的问题
  → 标注 gold_span 与它落在两块中的位置
测：单块检索的 recall@5、需要喂几个块才能覆盖答案
```
【我的建议】这张小集合是后面所有对比的基准。**没有它，"上不上父子块"就是口味之争。**

**第 2 步：实现条件式扩张（而不是固定窗口）。**

```python
def expand(hit, hits_by_parent, tau_rel=0.6, max_extra=1):
    # ① 高置信命中：不扩，直接给小块（省 token）
    if hit.score >= tau_rel * max(h.score for h in hits_by_parent):
        return [hit]
    # ② 同一父块内已有其它命中 → 直接给父块（合并，避免重复计票）
    if len(hits_by_parent) > 1 and hit.parent_id:
        return [get_parent(hit.parent_id)]
    # ③ 边界化判定：缺先行词 / 块尾不完整 → 扩 ±max_extra 个兄弟块
    if is_boundary_fragmented(hit):
        return neighbor_window(hit, radius=max_extra)
    return [hit]
```

**第 3 步：用三个数做验收（缺一不可）。**

| 指标 | 含义 | 目标形态 |
|---|---|---|
| `recall@k`（检索侧） | 能否找到 | 不降 |
| `avg_blocks_fed`（供给侧） | 喂几个块 | **下降**（SCAR：10.16 → 7.84） |
| `faithfulness`（生成侧） | 是否答得实 | 不降（SCAR 报告保住忠实度） |

【事实】SCAR 的对比形状就是这张表的范例：**召回 92.8% + 块数减少 22.9% + token 降 27.1% + 忠实度保持**。你的目标不是复现它的数字，而是复现它的**形状**。

### 权衡与坑

- **坑 1：无脑父块 = 无脑扩上下文。** 父块可能是整节 3,000 token，一扩就越过上下文悬崖（R2-02 的 2.5k 观察）。**必须给父块设 token 上限 + 三段式截断**（首段 + 命中段 + 尾段）。
- **坑 2：多个子块命中同一父块 → 同一父块被喂多次。** 这是 `ρ` 问题的复现，**扩张后必须按内容去重**（第 006 期同款哈希去重）。SCAR 之所以能"少喂 22.9% 的块"，一半功劳来自合并而不是扩张。
- **坑 3：以为"条件式扩张"跨模型可迁移是免费的。** SCAR 报告它的**相对阈值**可以跨 3 个嵌入模型迁移，但那是它的特定设定。**你换模型时要重测 τ_rel。**
- **坑 4：忘了 in-document vs in-corpus 的相反结论。** 上下文化提升语料检索、**降低**文档内检索（Zhou 等）。如果你的核心场景是"在一份长合同里定位条款"，别照搬"上下文增强"。
- **坑 5：把句子窗口的半径当成固定 k=2。** 半径应按"切断了多少信息"决定，而不是按习惯。半径越大，重复与噪声越多。
- 【我的建议】先做"父子块合并去重"（几乎零风险、立刻降低 `avg_blocks_fed`），再考虑条件式扩张（需要 τ_rel 调参）。

### 架构师视角

- **R2-03 的本质是"检索单元 ≠ 供给单元"** ——这和 R1-07（层级）、R2-04（上下文增强）、R5-01（上下文组装）是同一根线的四个截面。你在 R2-03 定下的接口（`hit → [blocks]`）会被后面三期反复复用。
- **给扩张建一个显式开关与预算**：`max_expansions_per_query`、`max_extra_blocks`。没有预算的概念，扩张会吃掉你第 003 期算出来的所有成本收益。
- **观测出口**：`avg_blocks_fed`、`expansion_rate`（触发了扩张的比例）、`dedup_drop_rate`（合并去重丢弃的比例）、`ctx_tokens_p95`。前两个管质量，后两个管成本。
- **一个反常识的结论值得记住**：在语料检索场景里，**"简单结构感知 + 条件扩张"经常打赢"复杂 LLM 引导切分"**（Zhou 等的结论方向）。复杂度不是免费的，也不是必然有效的。

## 今日前沿插入

> 只写有实质更新、且能核验来源的内容。

**① 重叠（overlap）第一次被端到端判为"无效变量"（arXiv:2601.14123，2026-01）**
在 Natural Questions 上、SPLADE + Mistral-8B 的完整链路里，重叠**没有可测收益且增加索引成本**；句子级切分性价比最高；**超约 2.5k token 出现上下文悬崖**；最优上下文随目标（语义 vs 精确匹配）变化。→ https://arxiv.org/abs/2601.14123
**为什么值得注意**：它把"overlap 要不要加"从经验之争变成了可被判定的实验问题。

**② 块大小的影响有天花板，k 才是主杠杆（Zenodo 10.5281/zenodo.18226194）**
SQuAD v1.1 上固定其它变量只变块大小/重叠：Grounded@1 三档差异 <0.5pp，**Grounded@2 与 @4 三档完全相同（91.0% / 95.0%）**。→ https://doi.org/10.5281/zenodo.18226194
**为什么值得注意**：它说明"块大小调参"的收益上限很低——先确认你的 k 曲线是否已经很平。

**③ 上下文扩张从"固定窗口"走向"条件式"（arXiv:2606.16661）**
SCAR 用相对阈值 + 结构连续性惩罚决定是否扩邻域：边界碎片查询 92.8% recall、块数 10.16→7.84（−22.9%）、token −27.1%、忠实度保持。**单作者预印本，方向参考。** → https://arxiv.org/abs/2606.16661

**④ 上下文化切分的效果"任务相反"（arXiv:2602.16974）**
统一框架复现比较：**in-corpus 变好、in-document 变差**；in-corpus 上简单结构感知优于 LLM 引导切分。→ https://arxiv.org/abs/2602.16974

**趋势观察（非定论）**
2026 年关于切分的讨论正从"找最佳参数"转向"**按任务/按查询做条件式决策**"（条件式扩张、按目标选 k、按域选方法）。同时，"切分 + 索引代次 + 发布流程"被当成同一个工程问题处理（第 008 期已建立 `CHUNKER_VERSION`）。**属趋势观察，请用自己的矩阵验证。**
