## 知识点 1：表格抽取与表示（R1-03）

### 一句话结论

表格存进知识库的正确形态是**一份自包含的结构化表示 + 一段可检索的自然语言描述**（HTML 或 LTEM 这类可表达 span/层级表头的格式存结构，一句话摘要存语义），而不是把表格拍平成文本行，也不是只塞一段 Markdown。

### 为什么重要

- **表格是 RAG 里“差距最大”的一个问题类型。** 上一期引用的 *From PDF to RAG-Ready*（arXiv:2604.04948）显示：同一个解析框架下，基础切分与层级切分在**表格类问题**上相差 **33 个百分点**，是所有问题类型里差距最大的。表格不是“少数文档才有的边角料”，它是准确率差的主要来源。
- **格式选择有明确的量化依据。** LTEM（EMNLP 2026 Main，arXiv:2610.29188）把表格结构拆成 **6 个原子特征（F1–F6）与 6 个复杂度档（L1–L6）**，用 1,089 张合成表做受控实验，结论是：**LTEM（增强版 Markdown，显式编码跨行跨列与多级表头）在 5 个 SOTA LLM 上达到与 HTML 相当的准确率，但 token 成本更优；相对 LaTeX 产生明显更少的无效输出**。同一实验里，生成任务上 HTML 仍最好。
- **表格抽取本身仍是公开难题。** *Benchmarking Table Extraction from Heterogeneous Scientific PDF Documents*（KDD '26，arXiv:2511.16134，86k 页）的结论直白：现有方法在**异构数据上缺乏泛化性**，在鲁棒性与可解释性上都有限制。也就是说，不要期待“选到一个永远不会错的表格工具”。

### 核心机制 / 数据流

**先搞清楚你缺的是哪一种“结构”。** 表格结构可以拆成几个正交维度（LTEM 的 F1–F6 是一份可用的清单，这里用通俗说法）：

| 维度 | 典型形态 | 丢了会怎样 |
|---|---|---|
| 跨行/跨列合并（span） | “财务指标”横跨三列 | Markdown 无法表达 → 变成空单元格，读表的人（模型）不知道这三列共用一个表头 |
| 多级表头 | 第一行“2024 年”，第二行“Q1/Q2/Q3/Q4” | 列名变成“Q1”，年份语境丢失 → 模型答“Q1 是 1200 万”却不知道该说哪一年 |
| 分区/分块 | 表内有“资产”“负债”小标题行 | 小标题被当成数据行 → 聚合计算时被当成一条记录 |
| 跨页续表 | 第 12 页表头 + 第 13 页继续 | 两张表被当成两张独立的表 → 无法回答“全表总和是多少” |

**数据流（表格专用的旁路）：**

```
页面 → ① 表格区域检测（bbox）→ ② caption 捕获（通常在表上方！）
     → ③ 单元格重建（span/表头层级/空单元格）→ ④ 双表示生成
        ├─ 结构表示：HTML 或 LTEM（保留 span 与层级表头）
        ├─ 语义表示：一句话摘要 + 关键列/单位/口径（用于向量检索）
        └─ 表内事实：可选，把每行转成一句自然语言（用于细粒度检索）
     → ⑤ 切分策略：小表整表入库；大表按行组切，但每块都带完整表头
```

**双表示是关键，不是冗余。** 检索阶段匹配的是“用户问题 ↔ 表格的语义”，这需要摘要那一路；生成阶段需要的是“精确的行列关系”，这需要结构那一路。只有一面，就总有一边是瘸的。

### 怎么做

1. **给表格建一条独立旁路，而不是让通用解析器顺手处理。** 用版面检测先把表格区域框出来，再对这块区域单独跑表格识别；通用 OCR 会把表格当正文处理，行列关系从一开始就没建立。
2. **存 HTML（或 LTEM），同时存一句摘要。** 最小可用形态长这样：
   ```json
   {
     "type": "table",
     "doc_id": "annual-report-2024",
     "page": 12,
     "caption": "表 3：2024 年各季度营收（单位：万元）",
     "structure_format": "html",
     "structure": "<table><thead><tr><th rowspan=2>指标</th><th colspan=4>2024 年</th></tr><tr><th>Q1</th><th>Q2</th><th>Q3</th><th>Q4</th></tr></thead><tbody>...</tbody></table>",
     "summary": "表 3 给出 2024 年四个季度的营收，指标为营业收入与净利润；Q4 营收最高。",
     "columns": ["指标", "2024 Q1", "2024 Q2", "2024 Q3", "2024 Q4"],
     "unit": "万元",
     "row_count": 2
   }
   ```
   注意 `caption`、`unit`、`columns` 这三个字段——它们决定了跨页表能不能合并、模型会不会把“万元”读成“元”、以及能否用列名做过滤。
3. **大表按行组切，但每块都重复表头 + caption。** 一个 500 行的台账，切成 20 块、每块 25 行；每块文本前面都拼上“表 3（单位：万元）列：指标 / 2024 Q1 …”。这是一个**便宜且高收益**的动作：单表行数超过阈值（建议 30–50 行）后再切，切之前先试“整表 + 摘要”是否已经够用。
4. **用“能不能算出来”做验收，而不是用 TEDS。** 表格类问题金标集里至少要包含三类：单值查找（“Q3 营收是多少”）、跨行聚合（“全年合计”）、跨页拼接（“第 12–13 页表格的总额”）。这三类分别对应上表的 span 丢失、表头丢失、续表未合并三种失败。

### 权衡与坑

- **Markdown 表格是“看起来对、实际错”的陷阱。** 它渲染得好，但一旦出现合并单元格，就必须退化成空单元格或重复值，行列语义就断了。用 Markdown 存表格**只在表格是简单二维网格时才安全**；一旦有 span，就要 HTML 或 LTEM。
- **HTML 的 token 成本。** HTML 比 Markdown 贵不少。LTEM 这条路线（arXiv:2610.29188）的价值就在于：在保留 span 与层级表头的前提下，把成本压回接近 Markdown 的水平。**我的建议**：如果表格密集（如财报、技术规范），HTML/LTEM 值得付这个 token；如果表格稀疏且简单，Markdown + 摘要更划算。
- **LaTeX 作表格格式要小心。** 同一论文报告 LaTeX 产生**明显更多无效输出**（模型写出的 LaTeX 编译不过 / 结构错）。LaTeX 更适合**公式**，不适合当表格的通用存储格式。
- **坑：caption 漏采。** 表格标题通常在表**上方**（图表标题通常在下方），如果按“图和标题在一起”的直觉处理，表格的标题会被漏掉，而标题往往包含单位、口径、时间范围这些决定性信息。
- **坑：把表格当知识图谱。** 有人会想“干脆把表拆成三元组”。这对关系型查询很诱人，但代价是复杂的抽取链路 + 大量信息损失。**我的建议**：先做“结构表示 + 摘要”这个最小闭环，只有在需要多表关联计算时再引入 Text-to-SQL（回到 R0-05）。

### 架构师视角

表格是**唯一一个“检索单元的粒度和它天然的结构粒度严重不匹配”的内容类型**：一张表在结构上是一个整体，在检索上你可能只需要其中一行。所以要设计成三层，而不是一层：

1. **表级块**：结构表示 + 摘要，负责“这张表是讲什么的”；
2. **行组块**：带完整表头的子块，负责“具体某几行”；
3. **关键词/列值索引**：把 `columns`、`unit`、关键数值写入元数据，让精确匹配走过滤器而不是向量（这又回到 R0-05 的路由思想）。

另外，给表格加一个**可失败标记**：识别置信度低的表（空单元格比例过高、行列数异常）打上 `table_quality: low`，在答案里显式提示“该表结构可能不完整”，比默默出错强得多。

## 知识点 2：图表与公式（R1-04）

### 一句话结论

图表和公式都不能“当作正文去 OCR”：图表要同时产出**可计算的数据**（能跑 Python 的字典/表格）和**可检索的文字**（一句话结论），公式要产出**能渲染、能回写的 LaTeX 源码**并和上下文一起入库——三者共同点是：**只存图像或只存识别出的字符，都等于没存。**

### 为什么重要

- **图表里装了大量“答案只存在于图里”的知识。** 趋势、峰值、拐点、异常点这些信息，在正文里往往只有一句“如图所示”，真正的数据在图上。如果图只留一个文件名或一句 caption，这类问题在 L1 就注定召回不到。
- **公式被“像正文一样识别”会彻底失效。** 公式一旦被拆成零散符号（如把 ∑ 识别成 S、把下标识别成独立字符），它在语义空间中既不像数学表达式、也不像自然语言，检索和生成两头都不可用。上一期 *Structured Layout Priors*（arXiv:2605.19866）里中文子集**表格 TEDS 从 0.01 提升到 0.36** 这个数字，侧面说明了“结构化内容被当扁平文本处理”能烂到什么程度。
- **两条路线都有可核验的近期进展。** 图表侧：chart-to-dictionary + Program-of-Thought（arXiv:2605.28874）用 Python 程序作为中间量来保证统计事实正确；公式侧：DocTron-Formula（arXiv:2508.00311）用通用 VLM + CSFormula 数据集（行/段/页三个层级的多学科复杂公式）做 SFT，在多样式、多学科、复杂版式上报告 SOTA。

### 核心机制 / 数据流

**图表：三条路线，别只选一条。**

| 路线 | 做法 | 优点 | 失败模式 |
|---|---|---|---|
| 描述式 | VLM 看图写一句/一段摘要 | 便宜、易检索 | 数值幻觉：说“增长约 3 倍”而图上是 2.1 倍 |
| 数据还原式 | 图 → 底层数据（表格或字典） | 数值可核验、可计算 | 坐标轴刻度读错 → 整列偏移 |
| 代码式（Program-of-Thought） | 图 → Python 程序 → 运行得到统计量 | 结论可复现、可审计 | 依赖模型会写对代码；执行环境要隔离 |

*From Data to Insights*（arXiv:2605.28874）提的 **chart-to-dictionary** 是数据还原式的一种更灵活变体：与其强行还原成规整表格，不如还原成字典/JSON，再让轻量 VLM 用 zero-shot PoT 生成 Python 去算统计量。论文报告它在语义与事实指标上与现有 chart summarization 方法**相当**——注意是“相当”，不是“碾压”，所以它目前的定位是**一条值得采用的工程路线**，不是已被证明的最优解。

**公式：目标不是“识别出符号”，是“还原出可编译的 LaTeX”。**

```
页面 → ① 公式区域检测（行内 vs 行间）
     → ② 转 LaTeX 源码
     → ③ 校验：能否被 KaTeX/MathJax 解析？（编译不过的丢回去重试或降级）
     → ④ 入库三件套：LaTeX 源码 + 渲染图（可选）+ 上下文一句话说明
```

第 ④ 步的“上下文一句话说明”经常被忽略：`\sum_{i=1}^{n} w_i x_i` 本身几乎不可检索，但“加权求和，权重为 w_i”这句话是可检索的。**公式的可检索性来自它的解释，不来自它的源码。**

### 怎么做

1. **图表走“双产物”入库。** 每张图存两条记录：一条是 `chart_data`（还原出的数据 + 图类型 + 轴标签 + 单位 + 出处页），一条是 `chart_summary`（一句话结论，用于向量检索）。两条通过 `figure_id` 关联。**只用摘要、不存数据**是常见错误：一旦用户问“峰值出现在第几个月”，摘要里没写，你就只能重新跑一次 VLM。
2. **公式只保留 LaTeX + 解释，不要把 LaTeX 直接塞进 embedding 文本。** 建议块结构：
   ```markdown
   [公式 2.3，第 7 页] 加权求和的损失函数定义：
   $$ L = \sum_{i=1}^{n} w_i \ell(y_i, \hat{y}_i) $$
   含义：对各样本损失按权重 w_i 加权求和；w_i 由类别频率倒数确定。
   ```
   检索匹配的是“加权求和的损失函数”，生成时模型看到的是完整 LaTeX。
3. **建一个 20 张图的小验收集，专门盯数值。** 每题只问一个可从图上读出的数（“第 3 季度的柱子高度对应多少”），比较模型答案与真值。**只看摘要写得顺不顺是没用的**——图表的失败几乎是静默的数值偏移，语义上完全通顺。这一步 30 分钟能做完，但它决定了你敢不敢让产品回答图表类问题。
4. **公式做“可渲染性”门禁。** 入库前用 KaTeX 解析一次，解析失败的公式打 `formula_status: broken`，不走检索主链，改为回退到渲染图。这条门禁比任何公式识别准确率指标都实用。

### 权衡与坑

- **数值幻觉是图表的主要风险，而且是“看起来最专业”的那类错误。** arXiv:2511.16134 讲表格抽取“缺乏泛化性、鲁棒性有限”，图表只会更糟——因为图表连行列结构都没有。**我的建议**：凡是图表给出的数字，在答案里标注“来自图表 XX（数据由模型还原，存在误差）”，别让它和正文事实混在一起。
- **代码执行路线有安全与稳定性代价。** PoT 要在隔离环境里跑模型生成的 Python，不能直接用主进程 `exec`；同时它对不可执行的图（如示意图、流程图）完全无效——这类图仍然只能走描述式。
- **公式的“行内 vs 行间”判断容易错。** 行内公式被误判成行间会切断句子，行间被误判成行内会让公式混进正文语义。一个廉价判据：看这块区域是否独占一行且上下有显著留白。
- **坑：只处理“独立成块的图表”。** 很多关键信息在**图表内的标注文字**（数据标签、图例、坐标轴标题）里，这些文字和图表是一体的，拆开处理就会丢。检测到图之后，把图内文字一并抽取并挂在 `chart_data` 上。

### 架构师视角

图表与公式的共同本质是：**它们是“高信息密度、低可检索性”的内容**。所以架构上的正确做法是**在摄取阶段一次性把“可检索性”做出来**，而不是指望检索时再补救：

- 对每一个 chart/figure/formula 块，强制产出三元组：`结构/源码` + `人类可读解释` + `出处定位（页 + bbox）`；
- 把“解释”那一条放进向量索引，把“结构/源码”放进对象存储，按 `figure_id` 关联；
- 在评测集里给图表题、公式题**单独打标签**，按类型看 recall 与 faithfulness——否则你会被整体分数掩盖掉“图表类问题全错”这个事实。

最后一句实话：**图表和公式不值得在第一版就做得很重**。先把“正文 + 表格”做对（那是 80% 的问题），图表与公式用一个廉价的“描述式 + 出处”方案兜住，等有了真实 bad case 再升级成数据还原或 PoT。

- **【论文结论】表格格式的选择第一次有了受控实验依据。** *LTEM*（EMNLP 2026 Main，[arXiv:2610.29188](https://arxiv.org/abs/2610.29188)，2026-10-21 v1 / 10-24 v2）把表格结构拆成 6 个原子特征（F1–F6）+ 6 个复杂度档（L1–L6），用 STB 基准（1,089 张合成表，按复杂度分层）在 5 个 SOTA LLM 上系统比较 Markdown / CSV / HTML / LaTeX / LTEM。结论：**LTEM 理解准确率与 HTML 相当、token 成本更优；相对 LaTeX 无效输出显著更少；生成任务上 HTML 仍最好**。这解释了为什么“Markdown 够用”和“必须上 HTML”两种说法都能找到拥护者——取决于表里有没有 span 与层级表头。
- **【论文结论】表格抽取至今仍是开放难题。** *Benchmarking Table Extraction from Heterogeneous Scientific PDF Documents*（KDD '26，[arXiv:2511.16134](https://arxiv.org/abs/2511.16134)，2025-11-20 v1 / 2026-07-31 v2）覆盖 86k 页、39k 样本，同时对子任务与端到端打分并度量不确定性。结论：现有方法在**异构数据上缺乏泛化性**，鲁棒性与可解释性均有限。含义：表格链路必须自带质量门禁，不能指望单一工具。
- **【论文结论】层级表头需要用“树”来喂模型。** *RealHiTBench*（ACL 2025，[arXiv:2506.13405](https://arxiv.org/abs/2506.13405)，v2 2025-12-14）在 25 个 SOTA LLM 上测 LaTeX / HTML / PNG 三种输入，并给出 **TreeThinker**（把多级表头组织成树再做推理），验证“改善模型对表格层级结构的感知”是有效方向。这与上一期的“层级感知切分贡献大于换框架”是同一个结论在表格上的版本。
- **【趋势观察】图表侧从“描述”转向“还原 + 计算”。** 2026 年的工作明显在往“图 → 数据/代码 → 可核验结论”走（PoT、chart-to-code 系列，如 [ChartGen, arXiv:2507.19492](https://arxiv.org/abs/2507.19492) 用代码引导合成 222.5K 图-代码对）。方向明确，但各家数字来自自建基准，跨域效果仍需自测——**这是趋势，不是定论**。
