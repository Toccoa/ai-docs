## 知识点 1：多租户与知识隔离（R6-11）

### 一句话结论

**多租户隔离的第一原则是“默认拒绝”：不能证明有权访问的数据，一律不进入检索候选。** 过滤必须发生在**检索前/检索中**，而不是生成后再隐藏；同时，**缓存 key、日志、评测集**都必须带租户维度，否则隔离会在“看不见的地方”漏掉。

### 为什么重要

- 多租户 RAG 最危险的事故不是“答错”，而是**跨租户数据泄露**。
- 2026 年的多租户检索研究（ACL 2026 Industry，索引期前缀注入）说明：多租户场景常常**不能按客户微调模型**，只能靠“共享模型 + 租户前缀 + 严格过滤”来兼顾效果与合规。
- 隔离做不好，还会导致“检索到无权文档 → 触发拒答/错误答案”，污染体验。

### 核心机制：三层隔离

| 层级 | 做法 | 隔离强度 | 成本 |
|---|---|---|---|
| 物理隔离 | 每租户独立索引/库 | 最强 | 最高 |
| 逻辑隔离 | 共享索引 + `tenant_id` 过滤 | 中 | 低 |
| 行级权限 | 文档级 ACL + 用户/角色过滤 | 中—高 | 中 |

**关键原则：**

```text
候选生成阶段就过滤（pre-filter）
  → 不允许“先召回再隐藏”
缓存 key = hash(query + tenant_id + user_acl_version + index_version)
日志/评测集 = 必须带 tenant_id / acl 维度
```

### 怎么做

1. **先定隔离级别**：按合规要求选物理/逻辑/行级；不要默认“逻辑隔离”。
2. **预过滤**：在向量检索/BM25 查询里带 `tenant_id` 与 ACL 条件；不要后置过滤。
3. **缓存隔离**：`cache_key` 含 `tenant_id`、`acl_version`、`index_version`；否则会串答案。
4. **权限变更传播**：ACL 变化要触发缓存失效与索引更新；否则旧权限会残留。
5. **反事实测试**：构造“无权用户问有权文档”的测试，验证 `unauthorized_recall = 0`；并测“跨租户缓存是否命中”。

### 权衡与坑

- **坑 1：后置过滤。** 先召回再隐藏，既浪费又可能通过其他信号泄露。
- **坑 2：缓存不隔离。** 同一 query 不同租户命中同一缓存，直接串数据。
- **坑 3：日志/评测集泄露。** 训练/评测数据混租户，模型可能记住。
- **坑 4：权限变更不失效。** 用户被移除权限后，仍能通过缓存拿到旧答案。
- 【我的建议】先做“预过滤 + 缓存 key 隔离 + 反事实测试”三件套；这比任何模型优化都优先。

### 架构师视角

- 多租户是**安全边界**，不是“功能开关”；它应该写进 ADR 与上线检查清单。
- 观测出口：`unauthorized_recall`（应为 0）、`cross_tenant_cache_hit`（应为 0）、`acl_version_lag`、`prefilter_selectivity`。
- **一句话**：**隔离不是“不让模型说”，而是“不让数据进来”。**

### 自测 3 题

1. 你的检索是预过滤还是后置过滤？如果是后置，怎么证明没有泄露？
2. 你的缓存 key 包含租户/权限版本吗？如果不包含，会发生什么？
3. 用户权限被收回后，他还能通过缓存拿到旧答案吗？你怎么测？

## 知识点 2：黄金集构建（R7-01）

### 一句话结论

**黄金集不是“找 50 个问题”，而是“用分层抽样构造一个能暴露系统短板的测试集”。** 必须覆盖：问题类型（事实/推理/摘要/计算）、难度、**无答案**、**证据冲突**、**时效**、**权限**；并且**冻结版本**，否则无法做回归。

### 为什么重要

- 没有黄金集，所有“优化”都是感觉；有了黄金集，才能做 A/B、归因、回归。
- 2026 年的 RAGRouter-Bench（arXiv:2602.00296）提供了一个可借鉴的结构：**7,727 条 query、4 个领域、3 类 query**，并引入 query-corpus 兼容性；说明“评测集设计”本身是一个独立问题。
- 黄金集的质量决定你能否发现“检索涨、答案跌”这类问题。

### 核心机制：分层设计

```text
维度 1：问题类型   factual / reasoning / summarization / computation
维度 2：难度       单跳 / 多跳 / 跨文档 / 全局
维度 3：对抗类型   无答案 / 证据冲突 / 时效过期 / 越权 / 误导
维度 4：来源分布   各文档类型、各租户、各语言
每条样本：question + gold_answer + gold_evidence(spans) + type + difficulty + tags
```

**最小规模建议：**

- 冷启动：**50–100 条**，覆盖 4 类问题 + 2 类对抗；
- 上线前：**200–500 条**，每类至少 20 条；
- 回归：冻结版本，每次改动跑同一套。

### 怎么做

1. **从真实日志采样**：不要自己编问题；用真实 query，按类型分层。
2. **标注 gold evidence**：不只标答案，还要标“支持答案的原文 span”；否则无法归因检索/生成。
3. **加入对抗样本**：无答案（看起来可答）、冲突（新旧版本）、时效（旧制度）、越权（无权文档）。
4. **冻结版本**：`golden_set_v1`，改动要记录变更；不要边测边改。
5. **分层报告**：按类型/难度出分，不要只报平均分。

### 权衡与坑

- **坑 1：只收集“能答对”的问题。** 这会高估系统；必须有无答案/难例。
- **坑 2：只标答案，不标证据。** 答案错时无法判断是检索错还是生成错。
- **坑 3：评测集泄露到训练/提示。** 会导致过拟合；要隔离。
- **坑 4：用平均分做决策。** 分层差异会被掩盖。
- 【我的建议】先做 100 条、带 gold evidence 的分层集；比 1000 条无标注问题有用得多。

### 架构师视角

- 黄金集是**架构决策的证据**：没有它，所有“上不上 GraphRAG/Agentic”的讨论都是口味。
- 观测出口：`golden_set_coverage`（类型/难度覆盖）、`inter_annotator_agreement`、`per_type_accuracy`、`regression_delta`。
- **一句话**：**评测集不是“测试用例”，而是“你对自己系统的认知边界”。**

### 自测 3 题

1. 你的评测集有多少条？覆盖了哪些问题类型？有没有无答案/冲突/时效/越权？
2. 你的 gold 标注包含证据 span 吗？如果没有，答案错时你怎么归因？
3. 你最近一次改动，是用同一套冻结评测集对比的吗？还是“感觉变好了”？

## 间隔复习（连续第 29 天，不占新知识点名额）

抽两个已完成点：**R5-01 上下文组装**（第 020 期）与 **R4-05 非对称检索**（第 019 期）。3 道题，先自己答，再看评分要点。

**题 1（设计）**：你的上下文组装器把 20 个 chunk 按分数降序塞进去，答案正确率却下降。请给出三个优先排查方向。
**题 2（归因）**：你给文档加了领域前缀后，跨租户混淆率下降，但 recall@5 也下降了。这算成功还是失败？怎么判断？
**题 3（取舍）**：如果“首尾放强证据”提升了简单题、但损害了多跳题，你会怎么路由？

<details>
<summary>评分要点（先自己写完再看）</summary>

- **题 1**：① **位置效应**：最强证据可能在中间被忽略（R5-02）；② **重复/噪声**：20 个 chunk 可能大量重复，`unique_source_ratio` 低；③ **输出预留不足**：上下文塞满导致答案被截断；④ **冲突未处理**：多版本文档互相矛盾。优先测 `answer_accuracy_by_position` 与 `unique_source_ratio`。
- **题 2**：不是单纯成功或失败，要看**净收益**：`Δrecall@5` 与 `Δcross_tenant_confusion` 联合判断；如果混淆率大幅下降、recall 只小幅下降，且业务更怕跨租户泄露，则可接受；否则回退或调前缀强度。关键：**两个指标都要看，不能只看一个**。
- **题 3**：按**问题类型路由**：简单事实题用“首尾 sandwich”；多跳/跨文档题用“按证据链顺序/结构分组”，不强行 sandwich；并用分层评估验证。

</details>
