## 知识点 1：增量索引与删除（R1-09）

### 一句话结论

增量索引的核心不是"怎么只重算变化的部分"（那是工程优化），而是**"用哪三个键把源系统、块、向量三者对齐"**——`doc_id + content_hash + index_epoch`；只有这三个键同时存在，"更新"才不会变成"留旧"，"删除"才不会变成"只是查不到"。

### 为什么重要

**先看这类失败的形状。** 【我的建议】把下面的场景当自检：一份合同 3 月版被 5 月版取代，语料里两份都在，两块的元数据都是 `is_current: true`（因为增量管线只写不删）。用户问"违约金比例是多少"，你检索命中 3 月版的块，模型如实引用了一个**已经失效的规定**。这个回答在传统指标下几乎无法被判错：召回命中、上下文包含、答案与上下文一致。**这就是 R1-06 里 `version_mix_rate` 要盯 0 的原因，也是 R1-09 存在的理由。**

【论文结论】"过期上下文不只是少一条证据，它会主动把模型推向过时状态"这个判断，在第 006 期引用过的代码补全诊断研究里被直接测过：只给**过期**的 helper 签名，Qwen2.5-Coder-7B-Instruct 在 15/17 个样本上写出了过期引用（相对只给当前签名高出 88.2 个百分点），gpt-4.1-mini 是 13/17（+76.5 个百分点）；而**完全不检索**反而一次过期引用都不写（只是通过率只剩 1/17）。

**再看删除。** 【事实】数据集/知识库的"删除"在工程上有三层完全不同的含义：
1. **从检索结果里排除**（打 `is_deleted` 标记，查询时过滤）——最常见，也最容易被当成"删完了"；
2. **从索引结构里移除**（向量记录真正从索引/段里消失，例如段合并后的物理清除）；
3. **使被检索必然伴随的衍生数据失效**（缓存、对话记忆、摘要、embedding 副本、下游报表）。

【我的建议】绝大多数"删了还会被答出来"的事故出在**第 3 层**：向量删了，但 prompt 缓存或语义缓存里还留着旧答案；或者对话记忆里把上周的旧回答当事实复述。**删除必须是一个跨组件的清单，而不是一次 `DELETE`。**

### 核心机制 / 数据流

**三个键，各解决一个问题：**

| 键 | 作用 | 缺失时的典型症状 |
|---|---|---|
| `doc_id` | 块的归属身份（谁的儿子） | 更新时无法判断"该删谁"，只能追加 → 重复与版本混用 |
| `content_hash` | 内容指纹（这一块变没变） | 重算全部 embedding（成本爆炸）或漏算（内容变了但块没变） |
| `index_epoch` | 索引代次（这一版何时生效） | 无法原子切换、无法回滚、无法区分"旧索引"与"新索引" |

**五步增量流程（我的推荐形态）：**

```
① 变更检测（源侧）
   upstream 增量接口 / 变更日志 / 定时全量 diff（mtime+size 或 content_hash）
   → 产出 change_set = {added[], modified[], deleted[]}

② 解析与切分只针对 added + modified
   对每个新块算 content_hash（sha1(text)）

③ 写入"影子代次"
   index_epoch = epoch_new；所有新块以 epoch_new 写入
   旧块保持 epoch_old，但不删

④ 一致性与验收门（关键，见下方代码）
   抽样检查：同一 doc_id 是否同时存在两个 epoch 的块？
   反事实检查：取 20 条"已删除文档专属问题"，应 100% 拒答或答不到

⑤ 切换与清理
   把"当前读 epoch"原子切到 epoch_new
   确认流量正常后再物理删除 epoch_old 的块（延迟清理，便于回滚）
```

**为什么是"影子代次"而不是"就地更新"？** 因为它们失败的成本完全不同：就地更新在写一半时挂掉，会得到一个**部分新旧混合**的索引，而这个状态在指标上看起来只是"略微变差"；影子代次最坏情况是"新版本没生效"，**旧版本仍然完整可用**，且天然支持回滚。

### 怎么做（3 步）

**第 1 步：先量三个数，判断你现在是哪一档。**
```
① stale_ratio   = 库中 is_current=false 的块数 / 总块数（或：最近 30 天有更新的文档中，索引里仍有旧版本的比例）
② delete_probe_pass = 取 20 篇"已下架文档"的专属问题去问，答不出来的比例（目标 100%）
③ update_lag    = 源文更新时间 → 索引可见时间 的 p95（小时）
```
【我的建议】三个数里，**②最便宜也最能暴露问题**：不需要金标，只需要你确知"哪些文档已经下架"。

**第 2 步：实现"档案级替换 + 代次切换"。**

```python
import hashlib, time, uuid

def hash_block(text: str) -> str:
    return hashlib.sha1(text.encode("utf-8")).hexdigest()

def ingest_incremental(doc, store, epoch=None):
    epoch = epoch or f"{time.time_ns()}-{uuid.uuid4().hex[:6]}"
    blocks = parse_and_chunk(doc)                      # 复用 R1-01/R2-xx 的产物
    for b in blocks:
        b.hash = hash_block(b.text)
        # 同一块内容未变 → 复用旧向量，只换 epoch 指针（省 embedding 成本）
        existing = store.find_one(doc_id=doc.doc_id, content_hash=b.hash)
        vec = existing.vector if existing else embed(b.embed_text)
        store.upsert(id=f"{doc.doc_id}:{b.ordinal}:{epoch}",
                     vector=vec,
                     payload={**b.payload,
                              "doc_id": doc.doc_id,
                              "content_hash": b.hash,
                              "index_epoch": epoch,
                              "is_current": False})   # 先不可见
    # 全部写完才翻转，避免半成品被检索到
    store.set_current_epoch(doc.doc_id, epoch)

def delete_document(doc_id, store, cache, memory):
    store.mark_deleted(doc_id)        # ① 检索层立刻不可见（最优先）
    store.compact_later(doc_id)       # ② 物理清理由后台任务做，可回滚
    cache.invalidate_by_tag(doc_id)   # ③ 缓存：语义缓存必须按 doc 打标签
    memory.invalidate_by_doc(doc_id)  # ④ 对话记忆/摘要里引用过该 doc 的片段
```

**第 3 步：把"反事实验收"写进上线门。**
一组不需要模型判断的自动测试，每次索引变更后跑：
```
for q in probe_questions_of_deleted_docs:     # 20 条
    assert answer_or_citation_not_from(q, deleted_doc_ids) is True
for doc in recently_updated_docs:             # 20 篇
    assert only_one_epoch_visible(doc.doc_id) is True
assert store.count(filter={"is_current": False, "age_days": ">7"}) == 0   # 旧代次已清
```

### 权衡与坑

- **坑 1：把"过滤掉"当"删掉了"。** 标记删除只解决了"不被检索"，没解决"缓存里还有"。**缓存（语义缓存、prompt 缓存）必须按 `doc_id` 打标签才能被删**——这一点和你第 006 期学的"缓存 key 要含权限维度"是同一个道理。
- **坑 2：把 overlap 当成"安全网"。** 切分重叠会让一个变更段落出现在多个块里，**只更新其中一部分块**就制造出"新旧混排的同一段文字"。按 `doc_id` 全量替换比"按块差量修补"安全得多。
- **坑 3：只对 `doc_id` 做 upsert，不做归档。** 很多向量库的 upsert 是"按主键覆盖"，如果你的主键是 `doc_id`（一个文档一个向量），那叫**摘要索引**，不是块索引；如果主键是随机 id，upsert 永远命中不了，等于每次都在追加。**主键设计就是删除设计。**
- **坑 4：忘记删"衍生答案"。** 上一轮的回答被写进对话记忆（R6-09 的话题），文档下架后模型仍会复述。**记忆条目要带 `source_doc_ids` 才能被定向删除。**
- **坑 5：增量管线没有"全量对账"。** 增量一定会漂移（漏事件、乱序、重试）。【我的建议】每周跑一次全量对账（`源文件数与索引文档数`、`每文档块数`、`每个 doc 的 epoch 唯一性`），把漂移变成可发现的数字。
- 【我的建议】删除的**合规意义**大于工程意义：一个"删了但还能被答出来"的系统，在审计里等价于没删。

### 架构师视角

- **R1-09 是整个 M1 的收口**：解析（R1-01/02）给你块，表格图表（R1-03/04）给你特殊块，去重（R1-05）给你唯一化，元数据（R1-06）给你身份，层级（R1-07）给你父子，语言（R1-08）给你语言维——**没有 R1-09，前面全部是"某个时刻的快照"，而不是"持续正确的系统"**。

## 知识点 2：切分策略全景（R2-01）

### 一句话结论

切分没有"正确答案"，只有**"在你的语料上可被证伪的选择"**——因为三篇独立研究给出的"最佳策略"互相不一致（段落分组最好 / 递归最好 / 语义聚类不比固定更好），而它们都成立；**能被复现的只有"方法"，不是"参数"**。

### 为什么重要

**先摆事实：这个领域没有共识。** 我把最近一年几篇系统评测的结论并排放在一起，你会发现它们指向不同的"最佳"：

| 研究 | 设定 | 结论 |
|---|---|---|
| Shaukat 等，arXiv:2603.06976（2026-03） | **36 种**切分方法 × **6 个领域** × **5 个嵌入模型**，LLM 打分的 nDCG@5 | **段落分组（Paragraph Group）最好**：均值 nDCG@5≈**0.459**、Precision@1≈**24%**、Hit@5≈**59%**；固定字符切分最差（nDCG@5 **<0.244**、P@1≈2–3%）；**领域差异明显**：生物/物理/健康偏爱动态 token 尺寸，法律/数学偏爱段落分组 |
| Taiwo & Yusoff，DOI 10.5121/csit.2026.160507 / arXiv:2603.24556（2026-03） | 油气企业文档（文本手册、表格重的规范、P&ID 图） | **结构感知切分**在 top-K 上整体最好，且**计算成本显著低于语义与基线方法**；但**四种方法在 P&ID 图上都无效** |
| Lavarec & Du，IJAI 15(2)（2026） | SaaS 编辑内容，2,419 组 QA | **递归切分在所有指标上稳定最优**；小块利于定位，中等偏大的块利于语义对齐与生成；**LLM 切分有竞争力但没有超过最好的递归配置** |
| Kreileder 等，arXiv:2607.01852（2026-07） | 长篇结构化学位论文 + RAGAS | **聚类式语义切分没有优于固定/递归**；且 RAGAS 的 faithfulness 在此设定下"可信度有限" |
| Qu, Tu, Bao，Findings of NAACL 2025（DOI 10.18653/v1/2025.findings-naacl.114） | 文档检索 / 证据检索 / 检索后生成 三任务 | **语义切分的算力开销没有被稳定的收益证明** |
| Bhat 等，arXiv:2505.21700（2025-05） | 长文档多数据集 + 多嵌入模型 | 结论型数据集 **64–128 token** 更好，需全局理解的数据集 **512–1024 token** 更好；**不同嵌入模型对块大小敏感度不同**（Stella 喜欢大块，Snowflake 喜欢小块） |

**这些结论并不矛盾，它们在告诉你同一件事**：**切分策略与语料结构、嵌入模型、评测任务是耦合的**。所以：
- 任何人告诉你"语义切分一定比固定切分好"，你可以直接问"在哪个语料、哪个模型、哪个指标上"；
- 你真正应该抄的是**方法**：结构感知边界、块内自包含、按任务选粒度；
- 你真正应该量的是**你自己的 recall@n**，而不是别人的 nDCG。

**顺带一个反直觉的坑**：Kreileder 等还报告，在他们那个设定下 **RAGAS 的 faithfulness 本身不够可靠**。这意味着"用 RAGAS 当唯一裁判去选切分策略"这件事本身就有风险——**裁判要和被测对象分离**（这也是 M7 评估要单独讲的）。

### 核心机制 / 数据流

**五种切分的机制与适用面（这是你该背的"地图"，不是参数）：**

| 策略 | 边界依据 | 强项 | 典型失败 | 成本 |
|---|---|---|---|---|
| 固定长度 | 字符/token 数 | 可预测、可批量 | 切断句子与表格，跨语言长度差异大 | 最低 |
| 递归/分隔符 | 段落→句子→词 逐级回退 | 边界自然、实现稳定 | 对无段落标记的文本退化为固定切分 | 低 |
| 结构感知 | 标题/表格/代码块/列表（R1-01 的 IR） | 保住语义单元，**多数评测里性价比最高** | 依赖解析质量；P&ID 之类空间信息无效 | 中 |
| 语义聚类 | 相邻句嵌入相似度阈值 | 主题连贯 | 阈值敏感、成本高、**不稳定的收益** | 高 |
| 上下文增强（late chunking / contextual retrieval） | 先嵌入整篇再按 token 池化 / 给每块生成上下文前缀 | 让块带上全局语境 | 上下文生成有额外 LLM 成本与错误传播 | 中—高 |

**晚切分与上下文检索的对比，有明确结论：**
【论文结论】Merola & Singh（arXiv:2504.19754，ECIR 2025 workshop）：**contextual retrieval 更能保住语义连贯，但计算开销更大；late chunking 效率更高，但倾向于牺牲相关性与完整性**。同一现象在检索层面也被观察到——
【论文结论】CRAwLeR（arXiv:2606.21676，2026-06）在法律交叉引用这一窄场景里构造了"必须依赖上下文才能答对"的数据集，最好的 Recall@10 只有 **55%（丹麦语）/ 59%（波兰语）**，而且**残差归因于做上下文化的那个 LLM，而不是检索器**；即使目标块进入了 top-10，被标注的**上下文块经常排在它前面**。这句话对架构师的意义是：**"给块补上下文"这个动作本身会引入新的排序噪声**，你要为它单独建一个"目标块是否被上下文块挤下去"的观测。

**跨文档碎片化也是切分的问题**：
【论文结论】CDTA（arXiv:2601.05265，单作者预印本）在多跳 HotpotQA 上报告 faithfulness **0.93**，对比 contextual retrieval **0.83**、semantic **0.78**；k=3 时仍保持 0.91，而语义方法掉到 0.68；代价是**索引成本更高**（需要跨文档合成）。*（单作者 + 预印本，把它当"方向性证据"，不要当定论。）*

**统一的选型决策树（我的建议）：**

```
① 有可信的结构（标题/表格/代码块）？──是──▶ 结构感知切分（默认起点）
    │                                          ↓ 若下游问题常跨章节 → 加父子块(R1-07)
    否
    ↓
② 文本长度分布均匀、无段落标记？──是──▶ 递归切分，目标 200–500 token
    │                                   （结论型问答取下界，需全局理解取上界）
    否
    ↓
③ 语义单元明显但结构不可得（会议纪要、聊天记录）？──是──▶ 语义聚类 + 小阈值滑窗
    ↓
④ 只在①②③都做过、并且 recall@n 已量化后，才考虑 late chunking / contextual retrieval
   （先接受它们会带来新的排序噪声）
```

### 怎么做（3 步）

**第 1 步：给自己的语料做一次"切分基线矩阵"，不要只跑一种。**
```
对每种策略 {固定, 递归, 结构感知} × 每种目标大小 {128, 256, 512, 1024 token}
  → 建临时索引 → 用 30 道题测 recall@5 / recall@10
记录三元组：(策略, 大小, recall@5)
【建议】先只看 recall，不看 faithfulness —— faithfulness 会把"检索没找到"和"生成没用好"混在一起。
```
【事实】Bhat 等的发现直接支撑这个设计：**块大小的最优点随任务类型移动**（64–128 vs 512–1024），所以"一个大小打天下"在一开始就是错的。

**第 2 步：把"块自包含"当成独立验收项，而不是切分的副产品。**
抽查 20 个块，只问一句：**"单看这一块，能不能判断它说的是谁、关于什么、在什么条件下？"**
- 不能 → 要么上移边界（结构感知），要么加语境前缀（`section_path`，R1-07 的做法），要么回填父块。
- 【论文结论】cAST（第 007 期引过）在代码上的做法就是这个原则：递归拆大节点后**把兄弟节点合并**，让块自包含。
- 【论文结论】CDTA 走向了另一个极端：把**跨文档**的同一主题合成一个块。它在多跳任务上有效，但代价是索引成本与"合成内容的可追溯性"——**合成块的引用粒度天然变差**，你要自己判断能不能接受。

**第 3 步：把"切分版本"写进索引身份。**
```python
CHUNKER_VERSION = "struct-v2-512"   # 策略 + 目标大小 + 预留补丁位
# 与 R1-09 的 content_hash 组合：
chunk_key = sha1(f"{doc_id}:{CHUNKER_VERSION}:{ordinal}:{text}").hexdigest()
```
**理由**：切分策略变更意味着**全部块都失效**，这必须能被识别为"一次全量重建"，而不是"内容没变所以复用旧向量"。没有 `CHUNKER_VERSION`，你换策略时会悄悄复用旧向量，然后把"策略没生效"误读为"策略无效"。

### 权衡与坑

- **坑 1：拿别人的"最佳"当自己的默认值。** 上表五篇研究的最佳策略各不相同，而它们都对。**默认值只是起点，不是结论。**
- **坑 2：只测检索指标就下结论。** 检索赢、生成输的组合很常见（块越小定位越准，但拼起来越碎）。
- **坑 3：把语义切分当"更高级"。** 【论文结论】NAACL 2025 那篇的结论就是：**开销没有被稳定收益证明**。它在"语义单元明显、结构不可得"的场景才有位置。
- **坑 4：忽略嵌入模型的块大小敏感度。** Bhat 等明确报告不同嵌入模型的最优块大小不同——**换 embedding 模型时要重跑块大小矩阵**，不要沿用上次的最优值。
- **坑 5：为 LLM 切分付出成本却没换来收益。** Lavarec & Du 的结论：LLM 切分"有竞争力但没有超过最好的递归配置"。**先跑递归，再决定要不要烧 LLM。**
- **坑 6：认为"跨文档合成块"没有代价。** 引用的可追溯性和索引成本是两个硬成本（CDTA 自己也承认索引成本更高）。

### 架构师视角

- **R2-01 的正确产出不是"一套参数"，而是一张你自己的表**：`策略 × 大小 × 语料域 → recall@5`。这张表会在你换嵌入模型、换业务线、换文档类型时反复被用到。
- **切分策略必须可版本化、可灰度、可回滚**（与 R1-09 的代次机制共用一套基础设施）——否则你永远不敢动它。
- **切分和层级、元数据是一件事的三面**：结构感知切分产出边界，R1-07 产出父子，R1-06 产出身份。三者共享同一个 IR，别分成三条管线。

## 今日前沿插入

**① 切分策略评测的"共识是没共识"（2026-03 / 2026-07，两篇独立系统评测）**
arXiv:2603.06976 用 36 种方法 × 6 域 × 5 模型给出"段落分组最优、固定字符最差、领域差异明显"；arXiv:2607.01852 在学位论文语料上给出"聚类语义切分没有优于简单策略"。两篇设定不同、结论方向不同——**这正是"没有通用最优"的证据**。
**对你的含义**：切分选型要落成你自己的矩阵，而不是抄榜单。

**② 上下文增强不是免费的午餐（arXiv:2504.19754 + arXiv:2606.21676）**
late chunking 高效但倾向牺牲相关性与完整性；contextual retrieval 更连贯但更贵。法律交叉引用场景的 CRAwLeR 显示：**上下文化后的块经常把真正目标块挤出前排**，且残差归因于做上下文化的 LLM。
**对你的含义**：上"上下文增强"时，必须新增一个"目标块是否被上下文块挤下去"的观测指标。

**③ 跨文档切分（CDTA，arXiv:2601.05265）**
把同一主题跨文档合成一个块，在多跳 QA 上报告 faithfulness 0.93（vs contextual retrieval 0.83、semantic 0.78），但索引成本更高。**单作者预印本，属方向性证据。**
**对你的含义**：如果你的业务是"多份文档拼起来才能答"（合同+附件+制度），值得做一次小规模验证；如果是一问一文档，别急着上。

**趋势观察（非定论）**
2026 年工程侧的主旋律是"**结构感知 + 上下文增强 + 可量化矩阵**"，而不是继续发明新的切分算法；同时也开始有人把"切分"和"索引代次"当成同一个发布问题来处理（切分策略变更 = 一次全量重建）。**属趋势观察**，请用你自己的矩阵验证。
