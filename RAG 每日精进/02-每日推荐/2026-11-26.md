## 知识点 1：领域适配（R4-03）

### 一句话结论

"领域不适配"这个症状有**四种解法**，成本从低到高是：**加 rerank → 补元数据过滤/查询改写 → 换更强模型 → 微调 embedding**；而绝大多数团队直接跳到最后一个，是因为**没先证明前三个不够**——而前三个都不动索引，第四个要全量重建。

### 为什么重要

**先把"通用 embedding 到底缺什么"说精确。**

【论文结论】*Domain-Specific Text Embedding Models for Entity Resolution*（Sapram, Raju, Konda，arXiv:2608.16161，2026-08-17）指出：**通用文本嵌入是为"语义相似"设计的，并没有为"区分代表同一真实实体的记录"做优化**。这个区别对你极其关键：
- **语义相似**：这两段文字在讲同一类事吗？
- **身份判别**：这两条记录是**同一个**客户/产品/合同吗？

在实体解析、重复记录检索这类任务里，**微小的文本差异可能保持身份，也可能改变身份**。他们的做法是：构造一个合成数据集（含**保持身份的变体**与**有挑战性的非匹配**），对两个常用嵌入模型做**triplet 微调**，用**基于 margin 的相似度评估**比较微调前后；结果是**在"区分真匹配与高度相似的非匹配"上有实质提升**，说明**领域特定的 triplet 训练能有效重塑通用嵌入空间**。

→ 这条回答了你从第 017 期带过来的那个问题：**"只差一个版本号"的文档分不开，是嵌入空间的结构问题，而 triplet 训练正是重塑它的手段。** 但要记住代价：**它重塑的是整个空间，所以你旧语料上的检索行为也会一起变。**

**再看"训练数据从哪来"这件事，2026 年有了方法论级的答案。**

【论文结论】*Self-improving data synthesis can scale embedding-model adaptation across domains and tasks*（Lyu 等，arXiv:2610.14730，2026-10）提出 **SYNTRA**：一个"自改进的 agentic 数据合成框架"，把**少量检索样例**变成**可复用的合成指令**。给定未标注语料 + 少量相关 query-document 对，它**推断隐式的信息需求与相关性判据**，再用**对试产出的反馈**来改进"查询生成"与"相关性判定"的指令。实验规模：**24 个数据集 / 15 个领域**。关键结论：
- **同一套合成工作流产出的训练数据是有效的**，**即使对已经很强的嵌入模型也有益**（无论它原本有没有标注训练集）；
- **自改进在全部 6 个评测任务上都增强了监督信号，其中 4 个优于人工校准**；
- **在 MS MARCO 上，增益在 32 倍的数据量范围内持续**。

→ 对你的含义：**"没有标注数据所以不能微调"这个理由，在 2026 年已经不成立了**——你可以从 20–50 个相关对起步。但这恰恰让"该不该微调"这个问题更需要纪律：**当门槛变低，乱用的成本就变高。**

**再看一个必须面对的错位：领域适配的收益常常不体现在业务指标上。**

第 017 期引的 IKEA 案例（arXiv:2605.00353）已经给过一次教训：**离线类别准确率 +2.6%，长尾查询的线上 A/B 却无统计显著差异（p > 0.05）**，原因是**67% 的热门搜索零点击率超过 50%**。→ **在决定微调之前，先确认你的业务指标对"排序变好"是敏感的。**

### 核心机制 / 数据流

**四种解法的对比（这是本节的主表）：**

| 解法 | 解决什么 | 动索引？ | 可回滚？ | 见效周期 | 主要风险 |
|---|---|---|---|---|---|
| **加 rerank**（R3-10） | 排序不准（候选里已有对的） | 否 | 是（开关） | 天 | 延迟与成本 |
| **元数据过滤 / 查询改写**（R1-06 / R3-07） | 该排除的没排除、该扩的没扩 | 否（改检索逻辑） | 是 | 天 | 过滤条件写错、改写跑偏 |
| **换更强/更匹配的模型**（R4-01） | 空间本身不够好 | **是（全量重建）** | 半（影子代次） | 周 | 内存/延迟上涨 |
| **微调 embedding**（本节） | 空间缺少你要的判别维度 | **是（全量重建）** | 难（模型版本化） | 周—月 | **过拟合、泛化下降** |

**为什么顺序必须是"便宜的先"？**
```
加 rerank 的收益 ≈ 把"已在候选里的正确项"排上来
元数据过滤的收益 ≈ 把"本来就不该在候选里的"去掉
微调的收益 ≈ 让"从没进过候选的正确项"能被召回
```
【我的建议】这三者的收益**不重叠**，而成本差一个数量级。**先诊断"你的错误属于哪一类"，再选对应解法**——这又是第 002 期四层失败模型的用法：L1（召回不到）才可能靠微调救；L2（排不准）该先上 rerank。

**微调的数据形态（三种，按难度）：**

| 形态 | 构造方式 | 适合 |
|---|---|---|
| **正对**（query, positive） | 真实 query + 命中文档 | 只能做对比学习时（依赖 in-batch 负例） |
| **三元组**（query, pos, neg） | 显式给出负例 | 有明确"易混淆"负例时（R4-02 的条件违反） |
| **蒸馏**（query, 教师分数） | 用 reranker/LLM 给候选打分，再蒸馏到双塔 | 有强 reranker、想把它"压进"embedding 时 |

### 怎么做（3 步）

**第 1 步：先做"错误归因"，判断该不该动 embedding。**

```
取 50 条 bad case，逐条标注：
  A 正确文档根本没进 top-50（召回不到）        → 可能靠微调/换模型
  B 正确文档在 top-50 但没进 top-5（排序问题）  → 先上 rerank
  C 正确文档在 top-5 但答案错（生成问题）       → 别动 embedding
  D 正确文档不该被召回（权限/版本/时效）        → 元数据过滤
统计四类占比：
  若 B+C+D > 70%  → 先别微调，做 rerank / 过滤
  若 A > 40%      → 微调或换模型才可能有帮助
```
【我的建议】这张归因表比任何基准都重要。**微调只能治 A，治不了 B/C/D。**

**第 2 步：如果确实要微调，用"少量真实对 + 合成扩增"的最小配方。**

```python
# 最小可行配方（对齐 SYNTRA 的思路：少样例 → 推断需求 → 合成 → 反馈迭代）
seed_pairs = load_real_pairs(n=30)          # 30 条真实 (query, positive)
for round in range(3):                       # 2–3 轮即可，别贪多
    instr = infer_relevance_criteria(seed_pairs, feedback=last_feedback)
    syn = synthesize(seed_pairs, instr, n=1000)          # 生成 query & 相关判定
    syn = filter_by_judge(syn, judge=strong_reranker)     # 用强模型做质量门
    model = finetune_triplet(base_model, seed_pairs + syn, epochs=1)
    last_feedback = evaluate(model, dev_set)              # 反馈下一轮指令
```
三条纪律：
1. **留出 dev 集，且它必须来自真实分布**（不能是合成数据）；
2. **每轮都测"域外召回"**——微调最容易牺牲的就是泛化（第 017 期：结构负样本训练让零样本 nDCG@10 掉 8–9%，中等模型最多 40%）；
3. **模型要版本化**（`embed_model_version`），和第 008 期的 `index_epoch` 绑定，否则回滚时会新旧向量混用。

**第 3 步：验收用"四列表"，缺一不可。**

```
① recall@5（域内，真实 dev 集）
② recall@5（域外，另一条业务线或公开集）      ← 防过拟合
③ pairwise_accuracy（只差一个条件的文档对）  ← 防"只学会认话题"
④ 索引内存 + p95 延迟                        ← 防"用算力换分数"
```
【论文结论】第 ③ 项正是第 017 期讲的诊断法，而 2608.16161 的"margin-based 相似度评估"本质上就是看**真匹配与高相似非匹配之间的间隔有没有被拉开**——**间隔没拉开，说明你只是把整体相似度平移了，没有学会判别。**

### 权衡与坑

- **坑 1：跳过 rerank 直接微调。** 微调只治"召回不到"，治不了"排不准"。**先归因。**
- **坑 2：以为"没标注就不能微调"。** 【论文结论】SYNTRA 用 30 级别样例 + 合成扩增，在 24 数据集 / 15 领域上有效，甚至对强模型也有增益。**门槛低了，但纪律要更严。**
- **坑 3：只测域内。** 【论文结论】微调常牺牲泛化；**必须单独报域外召回**。
- **坑 4：合成数据当 dev 集。** 合成数据只能用来训练和筛选，**验收必须用真实分布**。
- **坑 5：一次只改一个变量。** 同时换模型 + 微调 + 改切分，你无法归因（第 004 期的纪律）。
- **坑 6：忽略"业务指标对排序不敏感"。** 【论文结论】IKEA：离线 +2.6%、线上无显著差异（p>0.05），归因于 67% 热门搜索零点击率 >50%。**先确认你的指标会动。**
- 【我的建议】把微调当成**最后一张牌**，且必须满足三个前提：① 归因显示 A 类占多数；② rerank 与元数据过滤已做到位；③ 你有真实 dev 集与域外测试集。

### 架构师视角

- **微调是唯一会让"历史向量失效"的操作**（换模型也是）。所以它必须与第 008 期的**影子代次 + 原子切换**绑定：新建 epoch、验证通过再切、旧 epoch 保留以便回滚。
- **它与 R4-01 共用同一张决策表**：选型是"在现有模型里挑"，微调是"造一个新模型"；**两者的验收指标应该完全一致**（recall/内存/延迟/域外），否则你无法比较"换"与"训"哪个划算。
- **观测出口**：`recall_in_domain`、`recall_out_domain`、`pairwise_accuracy`、`margin_gap`（真匹配与高相似非匹配的相似度间隔）、`embed_model_version`。
- **一句话**：**微调不是"让模型更懂你的业务"，而是"改变它认为什么算相似"**——这个定义一旦改动，你所有旧的评测结论都要重跑。

### 自测 3 题

1. 你的 50 条 bad case 里，A（召回不到）/ B（排不准）/ C（生成错）/ D（不该召回）各占多少？如果没分过类，你凭什么决定微调？
2. 微调之后，你怎么证明"域外能力没坏"？如果只用域内 dev 集，你会漏掉什么？
3. 如果微调让域内 recall@5 涨了 4 个点、域外掉了 6 个点，这笔交易在你的业务里划算吗？取决于哪些前提？

## 知识点 2：向量压缩（R4-04）

### 一句话结论

压缩有三条正交的轴——**降维（Matryoshka/截断）、量化（int8/binary）、层级表示**——2026 年的实测给了分级结论：**int8 几乎免费、binary 有明确代价、维度减半一次安全、连续减半两次必然可检测**；而**检索任务对压缩的敏感度显著高于其它任务类别**，所以"平均分没掉"不能作为上线依据。

### 为什么重要

**先破除一个流行的误解：Matryoshka 不是"截断能用的必要条件"。**

【论文结论】*To MRL or not to MRL: Text Embeddings are Robust to Truncation Without Matryoshka Learning, Except In Heavy Truncation Scenarios*（Takeshita 等，**EMNLP 2026 Findings**，arXiv:2605.16608）做了一件此前没人做的事：**把 MRL 用的同一套截断，应用到"用 MRL 训练"和"没用 MRL 训练"的模型上做对比**。结论：
- **除非重度截断（把维度压缩至少 80%），非 MRL 模型的截断嵌入与 MRL 模型相当，且常常更好**；
- 这暗示**"截断鲁棒性"未必来自 MRL**；
- 所以**要不要付 MRL 的额外训练成本，取决于你是否需要重度截断**。

→ 对你的含义：**如果你只打算压到一半（768→384），你不一定需要 MRL 模型**；如果你要压到 1/8 甚至更狠，才值得为 MRL 付训练成本。**这直接推翻了"压缩必须用 MRL"的采购逻辑。**

**再看"量化与降维如何叠加"——这是本节的硬数字。**

【论文结论】*Balancing hierarchical representation and quantization: A performance trade-off in text embeddings*（Ponel 等，**Information Sciences 763 (2027) 124271**，arXiv:2611.06859，2026-11-04）做了一个规模很大的实证基准：**MTEB 的 38 个任务 × 4 个 transformer 嵌入模型 × {1D 与 2D 层级表示} × {float32 / int8 / binary 量化}，每个任务 168 种配置**；每种效率维度分开报告（理论单向量存储 + 端到端评估时间），并用 **Friedman 检验 + Nemenyi 事后分析**做统计判定。结论：
- **int8 与 float32 在 pair classification 与 rerank 上统计不可区分**，整体最多差 **1.5 个百分点**；
- **binary 量化在每个任务类别上都显著更差**；
- **维度减半一次，在 m=16 以上统计检测不出；连续减半两次，总能检测出**；
- **8 倍降维 + int8 组合 = 单向量存储降 32 倍，保留 94.4% 的基线效果**；
- **没有证据表明量化能加速评估**，而**从中间层采样能显著缩短评估时间**（这句很重要：**省存储 ≠ 省时间**）；
- **检索（retrieval）的退化远快于其它所有任务类别**，所以结论必须**按任务类别分开报**。

→ 这段把"压缩"从经验变成了**分级授权**：你可以拍板"int8 上、binary 不上"，因为这是有统计结论支撑的。

**再看压缩在"层级表示"里的另一条路径。**
【论文结论】同一篇的 1D/2D 层级表示，对应的是 MRL（一维前缀截断）与 2D 形式的层级嵌入；它的结论与上一条一致：**层级表示与量化是两条正交的轴，可以叠加**（8× 降维 + int8 = 32× 存储、94.4% 效果）。

**还值得一提的是"压缩与检索质量的关系"的工业侧对照：**
【趋势观察】2026 年多篇工程文章给出的经验区间是：**int8 相对 float32 的精度损失通常在 1–3%**（"对训练良好的模型"），而 **binary 单独使用时召回损失明显**，常见缓解是**binary 做粗筛 + int8/float32 做重排**。这些是**厂商/工程博客口径，属趋势观察**——但方向与上面的学术结论一致。

### 核心机制 / 数据流

**三条压缩轴的机制与代价（这张表是决策依据）：**

| 轴 | 机制 | 存储收益 | 质量代价 | 何时用 |
|---|---|---|---|---|
| **降维/截断** | 取前 k 维（MRL 训练过则各前缀自洽） | 线性（768→384 = 2×） | **减半一次通常可接受；连续减半必然可测** | 内存吃紧、且不追求极致召回 |
| **int8 量化** | 每维映射到 256 级整数 | **4×** | **与 float32 基本不可区分**（整体 ≤1.5pp） | **默认就该用** |
| **binary 量化** | 每维 1 bit（符号） | **32×** | **每个任务类别都显著变差**，检索尤甚 | 只做"粗筛 + 重排"，不做唯一索引 |
| **组合** | 8× 降维 + int8 | **32×** | **保留 94.4%** | 内存极紧但仍要可用 |

**为什么"检索退化最快"（机制）：**
```
检索的判定是"排序"——要在 top-k 边界上区分"几乎一样好"的候选
量化/降维引入的误差，恰好作用在"分数挨得很近"的那批候选上
→ 分类任务只要"过不过阈值"，容错大
→ 检索任务要"精确排序"，容错小
```
【我的建议】所以**用分类任务的压缩结论去指导检索，是系统性错误**。必须**在 retrieval 子集上单独验收**。

**一个"粗筛 + 重排"的组合（把 binary 放到它该在的位置）：**
```
① 第一级：binary 向量做 ANN 粗筛（32× 存储、位运算极快）→ top-1000
② 第二级：int8 或 float32 对 top-1000 重排 → top-50
③ 第三级：rerank（R3-10）→ top-5
```
【我的建议】这个三层结构能把 binary 的召回损失"关在第二级里"，同时享受它的存储与速度红利。**但第二级必须保留原始精度**——否则误差会叠加。

### 怎么做（3 步）

**第 1 步：先算"你到底省了多少"，再决定值不值。**

```python
def storage_gb(n: int, dim: int, mode: str) -> float:
    bits = {"float32": 32, "int8": 8, "binary": 1}[mode]
    return n * dim * bits / 8 / 1e9

n, d = 2_000_000, 768
for mode in ("float32", "int8", "binary"):
    for k in (d, d // 2, d // 8):
        print(f"{mode:8s} dim={k:4d} → {storage_gb(n, k, mode):6.1f} GB")
```
【论文结论】把这张表与"8× 降维 + int8 = 32×、保留 94.4%"对上：**你要的那 32 倍，不需要碰 binary**。

**第 2 步：在 retrieval 子集上单独做压缩验收（不要用总榜）。**

```python
results = {}
for cfg in [("float32", 768), ("int8", 768), ("int8", 384),
            ("int8", 96), ("binary", 768)]:
    mode, dim = cfg
    idx = build_index(chunks, quantize=mode, dim=dim)
    results[cfg] = {
        "recall@5":  recall(idx, golden_50, k=5),       # ← 只看 retrieval
        "recall@10": recall(idx, golden_50, k=10),
        "gb": storage_gb(len(chunks), dim, mode),
        "p95_ms": p95(idx, queries),
    }
```
**四列一起报**：`recall@5 / recall@10 / 存储 / p95`。**只报存储节省的方案，是无法被批准的。**

**第 3 步：给压缩设"分级授权表"，写进 ADR。**

```
默认允许：int8（4×，≤1.5pp 代价）——无需逐次审批
需审批：  维度减半一次（若 retrieval recall 掉 ≤2pp）
禁止：    binary 作为唯一索引（必须配 int8/float32 重排）
特例：    8× 降维 + int8（32×，保留 94.4%）——需在 retrieval 子集上单独验证
```
【我的建议】这张表的价值在于：**它把"能不能压"从每次讨论，变成了一次性决策**。

### 权衡与坑

- **坑 1：以为"压缩必须用 MRL 模型"。** 【论文结论】非 MRL 模型的截断嵌入与 MRL 相当甚至更好，**除非压缩 ≥80%**（arXiv:2605.16608）。**轻中度压缩不必换模型。**
- **坑 2：用"平均分"验收压缩。** 【论文结论】**检索退化远快于其它任务类别**（arXiv:2611.06859）。**必须在 retrieval 子集上单独测。**
- **坑 3：把 binary 当唯一索引。** 【论文结论】binary 在**每个任务类别**上都显著更差。**它只能是粗筛层。**
- **坑 4：以为量化能省时间。** 【论文结论】**没有证据表明量化加速评估**；真正显著缩短时间的是**从中间层采样**。**省存储 ≠ 省延迟**（这和第 013 期"ANN 参数是成本参数"是同一类纠正）。
- **坑 5：连续减半两次还觉得"没差多少"。** 【论文结论】减半一次检测不出，**连续减半两次总能检测出**。**两次减半是明确的质量台阶。**
- **坑 6：压缩后不重建评测基线。** 压缩改变了相似度分布，**第 012 期的 `mean_pairwise_cos`、阈值、甚至 rerank 的分数校准都会变**。**压缩是一次"度量变更"，不是一次"存储优化"。**
- 【我的建议】顺序：**先上 int8（几乎免费）→ 再看是否需要降维（一次减半）→ 最后才考虑 binary 粗筛，且必须配重排。**

### 架构师视角

- **压缩是"把质量换成钱"的显式交易**，所以它必须和 R0-06 的成本模型、R3-04 的内存账共用同一张表——**三者其实是同一件事：你的索引能装下多少有效信息。**
- **它对"换模型"有直接影响**：第 017 期说维度是选型四轴之一；今天补上下半句——**如果 int8 + 一次降维就能把 3072 维压到可接受，那么"维度太大"可能不再是淘汰理由。** 这会改变你的候选集。
- **观测出口**：`recall@5 / recall@10`（retrieval 子集）、`storage_gb`、`p95_ms`、`quantization_delta`（压缩前后的 recall 差）、`binary_rescore_gain`（binary 粗筛 + 重排相对纯 binary 的增益）。
- **一句话**：**压缩的真正问题不是"能不能压"，而是"压完之后，你还敢不敢用同一套阈值去判断相关性"**——大概率不敢。

### 自测 3 题

2. 如果你把维度从 768 压到 192（连续减半两次），你预期 retrieval recall 会掉多少？你打算用什么数据证明？

## 今日前沿插入

> 只写有实质更新、且能核验来源的内容。

**① "截断鲁棒性未必来自 MRL"（EMNLP 2026 Findings，arXiv:2605.16608）**
首次把"MRL 用的同一套截断"同时施加到 MRL 与非 MRL 模型上：**除非压缩 ≥80%，非 MRL 的截断嵌入与 MRL 相当、常常更好**。→ 是否付 MRL 训练成本，**取决于你是否要重度截断**。https://arxiv.org/abs/2605.16608

**② 量化与层级表示的交互被大样本量化（Information Sciences，2026-11，arXiv:2611.06859）**
38 任务 × 4 模型 × {1D/2D} × {float32/int8/binary} = 168 配置/任务，Friedman + Nemenyi 检验：**int8 与 float32 在 pair classification 与 rerank 上不可区分（整体 ≤1.5pp）**；**binary 每类都显著更差**；**减半一次检测不出、连续减半两次总能检测出**；**8× 降维 + int8 = 32× 存储、94.4% 效果**；**量化未显示加速评估**；**检索退化最快**。

**③ 领域适配的数据瓶颈被"自改进合成"绕开（arXiv:2610.14730，2026-10）**
SYNTRA：30 级别真实对 → 推断隐式需求与判据 → 合成 → 反馈迭代；24 数据集 / 15 领域；**同一工作流对强模型也有效**；**自改进在 6 个任务上全增强、4 个优于人工校准**；MS MARCO 上 **32× 数据量范围内增益持续**。

**④ 身份判别需要"重塑空间"，而非"更好的通用模型"（arXiv:2608.16161，2026-08）**
通用嵌入为"语义相似"优化，**不为"识别同一实体"优化**；triplet 微调 + 合成身份变体/高相似非匹配，**显著拉开真匹配与高相似非匹配的间隔**。

**趋势观察（非定论）**
2026 年 M4 的中段信号很一致：**"改模型"的门槛在下降（合成数据可自举），"压模型"的结论在细化（分级授权），但两者的验收口径在收紧（必须分任务、分域、分检索子集）。** 换句话说，**能力更便宜了，判断更贵了**。**属趋势观察。**
