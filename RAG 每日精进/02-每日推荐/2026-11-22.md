- **R3-06 多向量与晚交互**：晚交互（late interaction）把"一个块一个向量"改成"每个 token 一个向量 + 查询时逐 token 取最大相似再求和"，因此**它保住了细粒度匹配能力**，但代价是存储与内存成倍增长；好消息是 2025–2026 的一连串工作（固定向量数、token 剪枝、查询侧剪枝、mmap 服务）已经把这份代价压掉了一大半。

## 知识点 1：多向量与晚交互（R3-06）

### 一句话结论

晚交互把「查询–文档」的匹配从"两个点算一次余弦"改成"**每个查询 token 与每个文档 token 各算一次，取最大，再求和**"（MaxSim）；这让它既能像双塔一样预计算，又能像交叉编码器一样做细粒度匹配——**代价是存储按 token 数放大 1–2 个数量级**，而近两年的工程进展正在把这个代价压到可接受。

### 为什么重要

**先把机制说清楚：它到底比单向量多做了什么。**

```
单向量（bi-encoder）：
   q ──▶ 1 个向量 ─┐
                   ├─▶ 一次余弦 ──▶ 分数
   d ──▶ 1 个向量 ─┘

晚交互（ColBERT 式）：
   q ──▶ [q1, q2, ..., qm]         （每 token 一个向量）
   d ──▶ [d1, d2, ..., dn]
   score = Σ_i max_j (qi · dj)     ← MaxSim：每个查询词找它最像的文档词
```
**关键差别在第 3 行**：`max` 是"或"语义——只要文档里有一个 token 与查询词高度匹配，这一项就拿到高分。所以它**天然抗"局部匹配"**：单向量会把"这份合同禁止转租"与"这份合同允许转租"平均成两个很像的向量，而 MaxSim 会分别匹配到"禁止"/"允许"这两个 token。

【论文结论】Col⋆ 的复现研究（Wang, Macdonald, Tonellotto, Ounis，SIGIR 2023，DOI 10.1145/3539618.3591916）对"晚交互到底在匹配什么"给了很反直觉的答案：
- **晚交互从词汇匹配（lexical matching）获得的收益，大于从语义匹配获得的收益**；
- 高频 token 更倾向于做语义匹配，其它 token 家族不同；
- **[CLS] 这类特殊 token 在晚交互里扮演非常重要的角色**；
- 语义匹配的行为**随 tokenizer 变化**。

→ 这条对架构师的意义很直接：**晚交互强，部分是因为它更接近一个"细粒度的词项匹配器"，而不是因为它更"懂语义"。** 这也解释了为什么它在 OOD（领域外）场景稳——词项匹配不依赖训练分布。

**再看作"什么时候值得"的证据：**
【论文结论】LIR 研讨会（ECIR 2026，arXiv:2511.00444）对晚交互的定位总结得很准：它在**泛化性与鲁棒性（尤其 OOD）**上有优势，并且**特别适合"基于推理"与"跨模态"的检索**；但同时也带来**效率、易用性、系统集成**三方面的显著挑战。

【论文结论】ColPali（arXiv:2407.01449）把晚交互用在**页面图像**上：不做 OCR，直接用 VLM 产出多向量嵌入 + 晚交互匹配，在 ViDoRe 上**大幅超过现有文档检索管线，同时更简单、更快、端到端可训练**。
【论文结论】但复现研究（SIGIR 2025，DOI 10.1145/3726302.3730285）补了两条冷静的限定：**晚交互确实带来可观的效果提升，但也引入了推理期的计算低效**；而且查询 token 并不能真的"匹配到图像块"，它倾向于匹配**含视觉相似 token 的块或邻近块**。

**最后看"代价被压到什么程度"——这是决定你能不能上它的关键：**
| 优化手段 | 效果 | 出处 |
|---|---|---|
| **固定向量数**（每文档编码成固定个向量，不再按 token 数） | 保留大部分效果；磁盘上定长 → **OS 分页管理更好** | arXiv:2504.01818 |
| **token 剪枝（有原则的）** | 用 **30% 的 token** 保持 ColBERT 的效果 | SIGIR '25（DOI 10.1145/3726302.3730100） |
| **查询侧剪枝** | 查询嵌入 32→3，**效果无统计显著差异**，检索文档数 **−70%**，端到端 **2.65× 加速** | SIGIR '21（DOI 10.1145/3459637.3482162） |
| **维度压缩（Matryoshka）** | 128→64 维对效果影响很小，**存储降最多 50%** | Jina-ColBERT-v2 |
| **mmap 服务** | **RAM 降 90%**，可跑在便宜机器上；多阶段混合打分降延迟 | arXiv:2504.14903 |

### 核心机制 / 数据流

**完整链路（注意它比单向量多出来的一步）：**

```
① 离线：文档 → token 级嵌入（n 个向量/块）→ 存"多向量索引"
② 在线：查询 → token 级嵌入（m 个向量）
③ 候选生成：先用便宜的近似（如聚类/倒排）选出候选块
④ 精排：对候选做 MaxSim 打分（m × n 次点积）
⑤ 剪枝/截断：按需保留 top-k
```

**存储估算（做决策前先算这张账）：**
```
单向量：N × d × 4 bytes
晚交互：N_blocks × avg_tokens × d' × 4 bytes
  例：100 万块 × 平均 120 token × 128 维 × 4 bytes ≈ 61 GB
     若压到 64 维 → 30.7 GB；若再按 30% 剪枝 → ≈ 9 GB
```
【我的建议】先把这三档算出来，再决定"要不要上晚交互"。**在 30% 剪枝 + 64 维压缩后，它可能比你想的便宜得多；而在没做任何优化时，它可能直接撑爆你的内存预算。**

**为什么它能当"rerank"用（这是最划算的用法）：**
晚交互的打分是 `m × n` 次点积，比 cross-encoder 的全注意力便宜得多，但比单向量余弦贵。所以常见的性价比配置是：**BM25/单向量做召回 → 晚交互做精排 → （可选）cross-encoder 收尾**。

### 怎么做（3 步）

**第 1 步：先做一个"细粒度是否必要"的判定实验。**

```
取 30 条现有 query，各造 1 个"只差一个关键词"的对照（否定/数量/主体）：
  测三种配置的 top-5 命中：
    A 单向量
    B 单向量 + cross-encoder rerank
    C 晚交互（ColBERT 式）
判据：
  - 若 B 已经补上了 C 的差距 → 你不需要晚交互，加 rerank 更便宜
  - 若 C 明显优于 B → 你的场景需要 token 级匹配（长文档、条款密集、代码/表格）
```
【我的建议】这个实验能省掉一次昂贵的索引重建。**多数团队的答案是 B**——所以先测，别先上。

**第 2 步：如果上，从"最省"的配置开始，而不是论文默认配置。**

```python
# 配置优先级：固定向量数 > 维度压缩 > token 剪枝 > 查询剪枝
cfg = {
    "doc_vectors": "fixed_k",      # 每块固定 k 个向量（如 32），不按 token 数（arXiv:2504.01818）
    "dim": 64,                     # Matryoshka 压到 64，存储约减半
    "token_pruning": 0.3,          # 保留 30% token（SIGIR'25 的有原则剪枝）
    "query_pruning": 3,            # 查询只留 3 个嵌入（高频词优先）
    "scorer": "maxsim",
}
```
【论文结论】这四项各自都有公开证据支撑（见上表），**组合使用是合理外推，但不是某一篇论文的实测组合**——所以上线前必须自己测。

**第 3 步：把它接成"两段式"，别当唯一召回。**

```
BM25 / 单向量 top-100  →  晚交互 MaxSim 精排  →  top-10  →  生成
```
【我的建议】理由有三：① 晚交互的候选生成仍需便宜的近似索引；② 你的 BM25 在约束型查询上依然更强（第 011 期）；③ 精排阶段可以按需跳过——**当候选数很少（低选择性过滤后）时，直接精确打分更划算**。

### 权衡与坑

- **坑 1：以为晚交互"更懂语义"。** 【论文结论】Col⋆ 的结论是它**从词汇匹配获益更多**。如果你指望它解决"同义改写"问题，可能会失望——那更多是 embedding 训练与查询改写的事。
- **坑 2：忽略存储与内存。** 按 token 存向量，量级差异是 10–100 倍。**先算账再选型**（上表给了四档压缩手段）。
- **坑 3：在零样本场景迷信 ColBERT。** 【论文结论】有研究指出 **ColBERT 在零样本场景常不如 BM25**（isotropy/anisotropy 平衡问题，HIL 那篇的出发点）。**领域外效果要单独测。**
- **坑 4：把"固定向量数"当成无损。** 【论文结论】arXiv:2504.01818 的说法是"保留**大部分**效果"。**它是权衡，不是免费。**
- **坑 5：忘了推理期的计算低效。** 【论文结论】ColPali 的复现研究明确指出晚交互**引入推理期计算低效**（MaxSim 是 m×n 次点积）。**延迟预算要按候选数×token 数重算。**
- **坑 6：在多语言/长文档上直接套英文配置。** Jina-ColBERT-v2 需要专门的长上下文 + 多语言训练框架，**不是把英文模型换个 tokenizer 就行**。
- 【我的建议】判断顺序：**先测"交叉编码器 rerank 够不够"→ 不够再上晚交互 → 上就从固定向量数+64 维+30% 剪枝起步**。

### 架构师视角

- **晚交互是"用存储换精度"的交易**，和 R3-04 的 ANN 是同一个思想的两端：ANN 用近似换速度，晚交互用空间换精度。**两者都要用"下游质量"而不是中间指标验收**（第 013 期）。
- **它天然适配"证据要逐字核对"的场景**（法条、条款、代码、参数表）——因为这些场景的答案正确性依赖**具体 token 是否出现**，而不是整体语义像不像。
- **观测出口**：`maxsim_score_dist`（分数分布，看是否有区分度）、`multi_vector_storage_gb`、`rerank_latency_p95`（按候选数分桶）、`lexical_vs_semantic_contribution`（如果能做消融，量化"到底靠词项还是语义"）。
- **一句话**：**单向量是"把文档读薄成一个印象"，晚交互是"保留每个词的去向"**——你需要哪一个，取决于你的答案是否依赖某个具体的词。

### 自测 3 题

1. 你的场景里，答案正确性是否依赖"某个具体 token 是否出现"（条款编号、参数、错误码）？如果是，单向量 + rerank 够吗？你测过吗？
2. 如果把块存成每 token 一个向量，你的存储会涨多少倍？在"固定向量数 + 64 维 + 30% 剪枝"之后又是多少？
3. 有人说"晚交互比 BM25 更懂语义，所以可以替掉 BM25"。用今天学到的两条结论反驳他。

## 知识点 2：查询理解与改写（R3-07）

### 一句话结论

改写/扩展/分解/HyDE 这些手段的真正作用，是**补上"检索器看不到的那部分"**（口语 → 术语、短查询 → 上下文、抽象问题 → 假设答案）；但它们也把系统从"确定的映射"变成"随机的映射"——2026 年的基准显示，**同一意图的不同问法会让 Adaptive RAG 的检索决策与准确率大幅波动，而模型变大并不能修复这种脆弱性**。

### 为什么重要

**证据一：表面改动能显著改变检索行为——这是改写的"风险面"。**

【论文结论】*How You Ask Matters! Adaptive RAG Robustness to Query Variations*（arXiv:2604.10745）构建了第一个"语义完全相同但表面形式多样"的大规模基准（人工改写 + 模型生成改写），从**答案质量、计算成本、检索决策**三个维度评估 Adaptive RAG：
- 发现**严重的鲁棒性缺口**：**仅表面层面的小改动就会显著改变检索行为与准确率**；
- **更大的模型表现更好，但鲁棒性并没有随之改善**。

→ 这条对"改写"是一记警钟：**如果你用 LLM 改写查询，你就把一个稳定的输入变成了一个高方差的输入**；而"更大的模型"不是解药。

**证据二：改写确实能补上"覆盖率"——但要小心合成数据的误导。**

【论文结论】Coverage Illusion（arXiv:2605.27220，丹麦国家百科生产流量，20,000 组 query-workflow）：按**合成查询**估计，超过 **90%** 的查询需要 LLM 增强（HyDE/扩展）才能达到高覆盖；但在**真实流量**下，只有 **27.8%** 真的需要。而且**这个需求在检索前无法预测**（四类 ML 范式都失败），必须"检完才知道"。
→ 所以他们改成了**后置级联**（cheapest-first，只在检索无结果时升级到 LLM 增强）：质量 **+0.140**、延迟 **−31.8%**、**72.2%** 的真实查询无需增强即被服务。

**证据三：检索器有"盲点"，而改写/补文档能治。**

【论文结论】*With Argus Eyes*（arXiv:2602.09616）定义了"盲点"：**与查询相关、但与查询嵌入相似度低的实体**，检索器根本召不回。根因是训练导致的偏置——这些实体被映射到嵌入空间的不可达区域。他们提出 **RPS（Retrieval Probability Score）**，可以**在索引前**从实体嵌入几何预测盲点风险（不用跑昂贵的检索评测）；并用 **ARGUS** 从知识库定向补文档。效果：在 BRIGHT / IMPLIRET / RAR-B 上对所有被测检索器一致提升，**平均 +3.4 nDCG@5、+4.5 nDCG@10**，困难子集提升更大。

**证据四：HyDE 的机制与局限。**
【事实】HyDE（Gao 等，arXiv:2212.10496）的做法是：**先让 LLM 生成一段"假设性答案文档"，再用它的嵌入去检索真实文档**。它把"短查询 vs 长文档"的非对称匹配，转成"文档 vs 文档"的对称匹配——这正是"补上检索器看不到的那部分"的典型手法。
【我的建议】但要注意两个前提：① 假设文档**必须领域正确**（LLM 对你不熟的领域会编出误导性文档，把检索带偏）；② 它**增加一次生成调用**，延迟与成本都要计入（第 003 期 R0-06）。

**证据五：多查询/分解能突破"信息平台"。**
【论文结论】ERM4 的 Query Rewriter+（arXiv:2407.10670）：单查询会遇到**信息平台（Information Plateau）**，生成多个查询可以突破；同时把问题改写到**消除歧义**以澄清意图；配套 **Knowledge Filter**（滤掉不相关知识）、**Retriever Trigger**（减少冗余检索）。两个模块基于指令微调的 **Gemma-2B**，在六个 QA 数据集上验证。
→ 注意它用的是小模型（2B）——**"改写用小模型"是合理的工程选择**，因为改写的任务是"重述"，不是"推理"。

### 核心机制 / 数据流

**五类改写手段，各自的"补什么"与"风险"：**

| 手段 | 补什么 | 收益来源 | 主要风险 |
|---|---|---|---|
| **规范化改写**（口语→术语、补主语） | 词汇鸿沟 | 查询更接近索引用词 | 改错术语 → 直接跑偏 |
| **扩展/同义**（多查询、同义并列） | 表达多样性 | 覆盖面 | 噪声进入候选；成本上升 |
| **分解**（多跳拆子问） | 推理链 | 多跳问题可解 | 子问顺序错 → 连锁错；调用次数×n |
| **HyDE**（生成假设答案再检索） | 查询-文档不对称 | 短查询匹配长文档 | 领域幻觉 → 检索被带偏；多一次生成 |
| **路由/判需**（要不要改写） | 成本 | 只在该改时改 | 判据不准 → 漏召回（Coverage Illusion） |

**关键设计原则（我的建议，基于上面证据推导）：**

```
① 改写必须"可回退"：保留原始 query 的检索结果，与改写结果做并集/融合，
   而不是用改写结果替换原查询。
② 改写必须"可观测"：记录 rewrite_delta（改写前后 top-k 的重叠率），
   重叠过低说明改写把意图改掉了。
③ 改写必须"按需"：默认不改，只在检索置信度低时升级（后置级联）。
④ 改写模型要小：任务是重述不是推理，2B 级别足够，省下的预算给 rerank。
```

**"改写把意图改掉了"的三种典型信号（可直接监控）：**
- 改写后 top-1 与原始 top-1 完全无关（`jaccard(orig_top10, rewritten_top10) < 0.2`）；
- 改写后命中的文档**时间/版本**与原始不同（说明改写引入了不同实体的联想）；
- 改写后答案的**引用来源**与原查询的 gold 文档不一致。

### 怎么做（3 步）

**第 1 步：先做"改写必要性"的分层测量，别全局开启。**

```
按查询类型分层各取 30 条：
  A 短查询（<5 词，缺上下文）        → 改写收益通常最大
  B 含口语/缩写/内部黑话           → 规范化收益最大
  C 多跳/比较类                     → 分解收益最大
  D 已经很长很具体                  → 改写通常无益甚至有害
对每层测：原始 / 改写 / 并集 三种配置的 recall@10
```
【论文结论】Coverage Illusion 的核心教训就是：**合成查询会高估改写需求（90% vs 真实 27.8%）**。所以这个实验必须用**真实流量样本**。

**第 2 步：实现"后置级联"而不是"前置全开"。**

```python
def retrieve_with_optional_rewrite(q, idx, tau_ok=1):
    hits = idx.search(q, k=20)
    if len(hits) >= tau_ok and hits[0].score >= REL_OK:      # 够了就别改
        return hits, {"rewritten": False}
    variants = expand(q)                                      # 同义扩展 or 分解 or HyDE
    extra = [idx.search(v, k=20) for v in variants]
    merged = rrf_fuse([hits] + extra)[:20]                    # 与原结果融合，不替换
    return merged, {"rewritten": True, "n_variants": len(variants)}
```
【论文结论】这正是 Coverage Illusion 报告的形态：**只有在检不到时升级**，用 27.8% 的增强覆盖了 72.2% 的查询，同时延迟降 31.8%。

**第 3 步：把 HyDE 当"可选增强"，并给它加领域约束。**

```
① 只在"短查询 + 该领域有大量训练/文档支撑"时启用 HyDE
② 假设文档要短（3–5 句），过长会引入噪声
③ 用"假设文档的嵌入"与"原查询嵌入"取平均或拼接，而不是完全替换
④ 记录 hyde_drift：假设文档里出现的实体，是否在原查询或 gold 文档中出现
   —— 若大量实体凭空出现，说明 HyDE 在编造方向
```

### 权衡与坑

- **坑 1：全局开启改写。** 【论文结论】真实需求只有 27.8%，而你为此付 90% 的调用成本 + 全量延迟。
- **坑 2：用改写结果"替换"原查询。** 一旦改写跑偏，你连原来的正确答案都拿不到了。**要融合，不要替换。**
- **坑 3：以为"换更大的模型"能提升改写鲁棒性。** 【论文结论】*How You Ask Matters* 明确说：模型更大表现更好，但**鲁棒性没有相应改善**。
- **坑 4：在你不熟的领域用 HyDE。** 假设文档会编出"听起来很专业"的错误方向，把检索带得更远。**领域不熟时，宁可扩同义词也不要生成假设答案。**
- **坑 5：忽略改写对"时效/版本"的破坏。** 改写可能把"2026 年新规"泛化成"相关规定"，从而召回旧版（第 008 期 R1-09 的陈旧证据问题）。
- **坑 6：不做"改写前后一致性"监控。** 没有 `jaccard(orig_top10, rewritten_top10)` 这类指标，你无法知道改写是帮忙还是帮倒忙。
- 【我的建议】顺序：**先做规范化（口语→术语，最安全）→ 再做按需扩展 → 再考虑分解 → 最后才考虑 HyDE**。

### 架构师视角

- **改写是"概率性的预处理"，必须按概率的方式管理**：默认关闭、按需触发、结果融合、全程留痕。**任何"默认开启、替换原查询"的改写都是风险源。**
- **它和 R3-09（相关性阈值与拒答）是一对**：改写解决"查不到"，拒答解决"不该答"。**两个都缺，系统要么漏、要么编。**
- **观测出口**：`rewrite_rate`（触发改写的比例）、`rewrite_delta`（改写前后 top-k 的 Jaccard）、`rewrite_gain`（改写带来的召回增量）、`rewrite_latency_delta`、`hyde_entity_drift`（假设文档的凭空实体比例）。
- **一句话**：**改写的目标是"让检索器看见原本看不见的东西"，不是"让问题变得更好看"**——两者的区别在于，前者可以用召回证明，后者只能用感觉辩护。

### 自测 3 题

1. 你的系统对每条 query 都做改写吗？如果真实需求只有约 28%，你多付的那部分成本买到了什么？
2. 改写后的结果，你是"替换"原结果还是"融合"？如果替换，一次改写跑偏会导致什么？
3. 你能量出"改写前后 top-10 的重叠率"吗？如果它低到 0.2，你会把它解读为"改写很有效"还是"改写改错了意图"？怎么区分？

## 今日前沿插入

> 只写有实质更新、且能核验来源的内容。

**① 晚交互的"性价比边界"被系统化（ECIR 2026 workshop，arXiv:2511.00444）**
LIR 研讨会的定位陈述：晚交互在**泛化性与鲁棒性（尤其 OOD）**上有优势，**特别适合推理型与跨模态检索**；但**效率、易用性、系统集成**是三大挑战。同时 2025 年的多项工作把存储代价压下来：固定向量数（arXiv:2504.01818）、30% token 剪枝（SIGIR'25）、查询嵌入 32→3 且效果无显著差异 + 2.65× 加速（SIGIR'21）、mmap 使 RAM −90%（arXiv:2504.14903）。
**为什么值得注意**：它把"晚交互太贵"这个印象更新成了"贵，但有四档可调的压缩"。

**② 晚交互的收益更多来自"词项匹配"（SIGIR 2023，DOI 10.1145/3539618.3591916）**
Col⋆ 的复现研究结论：**晚交互从词汇匹配获得的收益大于语义匹配**；`[CLS]` 等特殊 token 作用显著；语义匹配行为随 tokenizer 变化。
**为什么值得注意**：这修正了"晚交互 = 更强语义"的常见误解。

**③ 查询改写被证明会显著改变系统行为（arXiv:2604.10745，2026）**
首个"语义相同、表面多样"的大规模基准：**表面小改动显著改变检索决策与准确率**；**模型更大并不能改善鲁棒性**。
**为什么值得注意**：它给"全局开启 LLM 改写"提供了一个明确的反例。

**④ 改写需求的真实比例远低于合成估计（arXiv:2605.27220）**
合成查询估计 >90% 需要增强，真实流量只有 **27.8%**；且"是否需要"在检索前不可预测 → 后置级联（质量 +0.140、延迟 −31.8%、72.2% 查询免增强）。

**⑤ 检索盲点可在索引前预测（arXiv:2602.09616）**
RPS 从实体嵌入几何预测"低相似但相关"的盲点风险；ARGUS 定向补文档后在 BRIGHT/IMPLIRET/RAR-B 上平均 **+3.4 nDCG@5 / +4.5 nDCG@10**。

**趋势观察（非定论）**
2026 年这两块的共同趋势是"**把'更强的模型'换成'更对的决策'**"：晚交互用压缩与剪枝换可部署性，改写用后置级联与融合换稳定性。同时"检索盲点/覆盖率"开始被当作**可预测、可预修的对象**（RPS、Coverage Illusion 都在这个方向上）。**属趋势观察。**
